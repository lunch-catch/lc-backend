# 인증 (auth)

관리자, 점주, 사용자의 로그인과 토큰 재발급, 로그아웃을 다룬다. 점주 회원가입과 카카오 로그인(가입 포함)도 여기 둔다.
세 역할의 로그인 수단은 다르지만 토큰 정책(94행) 하나를 따르므로 한 문서에 모았다.
공통 규약(경로, 응답 봉투, 상태 코드, 식별자, 시각)은 `README.md`를 따르고 여기서는 반복하지 않는다.

| 근거 | 기준 |
|---|---|
| 요구사항 | 명세서 V49 기능 5~7행(관리자), 31~34행(점주), 62, 64, 65행(사용자), 94행(공통 토큰 정책) |

관리자 계정 발급(4행)은 `admin.md`, 사용자 온보딩(63행)과 탈퇴(89행)는 `member.md`, 점주 튜토리얼 확인 처리는 `owner.md`에 있다.

| `POST` | `/v1/owner/auth/signup` | 점주 회원가입 | 공개 | 31 |
| `POST` | `/v1/owner/auth/login` | 점주 로그인 | 공개 | 32 |
| `POST` | `/v1/owner/auth/refresh` | 점주 토큰 재발급 | 공개(Refresh Token) | 33 |
| `POST` | `/v1/owner/auth/logout` | 점주 로그아웃 | OWNER | 34 |

## 성능 목표

| API | 에러율 | 근거 |
|---|---|---|
| 로그인 3종 | 0.1% 미만 | 보안을 위해 비밀번호 확인이 의도적으로 느리다. 응답 지연 시간 목표는 두지 않는다 |
| 재발급 3종 | 0.1% 미만 | 10:50 알림 직후 앱을 연 사용자가 한꺼번에 재발급할 수 있다 |
| 회원가입, 로그아웃 | 0.1% 미만 | |

목표 TPS와 응답 지연 시간은 트래픽이 몰리는 API에만 둔다. 인증 API는 에러율만 본다.

## 공통 토큰 정책 (94행)

| 토큰 | 형식 | 유효 기간 | 쿠키 |
|---|---|---|---|
| Access Token | JWT | 30분 | `accessToken`, `HttpOnly`, `SameSite=Strict`, `Path=/`, `Max-Age=1800` |
| Refresh Token | Opaque(무작위 문자열) | 관리자 1일, 점주 14일, 사용자 14일 | `refreshToken`, `HttpOnly`, `SameSite=Strict`, 역할별 `Path` 와 `Max-Age` |

**Access Token 은 인증이 필요한 모든 요청에 실려야 하므로 `Path=/` 다.**
**Refresh Token 은 재발급과 로그아웃에서만 쓰므로 역할별로 좁힌다.**

| 역할 | `Path` | `Max-Age` |
|---|---|---|
| 관리자 | `/v1/admin/auth/` | `86400` (1일) |
| 점주 | `/v1/owner/auth/` | `1209600` (14일) |
| 사용자 | `/v1/auth/` | `1209600` (14일). 자동 로그인을 체크하지 않으면 붙이지 않는다 |

```
Set-Cookie: accessToken=<JWT>; HttpOnly; SameSite=Strict; Path=/; Max-Age=1800
Set-Cookie: refreshToken=<opaque>; HttpOnly; SameSite=Strict; Path=/v1/auth/; Max-Age=1209600
```

`Path=/` 로 두면 안 되는 이유가 둘이다. 피드 조회처럼 Refresh 가 필요 없는 모든 요청에 14일짜리
토큰이 따라가 접근 로그와 프록시에 남는 면이 넓어진다. 그리고 쿠키 이름이 `refreshToken` 하나이므로
한 브라우저에서 역할을 바꿔 로그인하면 서로를 덮어쓴다.

`Path` 자체는 같은 오리진 안에서 격리를 보장하지 않는다. 진짜 방어는 `HttpOnly` 와
`SameSite=Strict` 이고, `Path` 는 노출 면을 줄이는 층 하나로 둔다.

- **토큰은 쿠키로만 오간다.** 응답 본문에 토큰을 싣지 않고, 클라이언트는 토큰 값을 읽거나 `Authorization` 헤더에 싣지 않는다
- **사용자가 자동 로그인을 체크하지 않으면** `refreshToken` 쿠키에 `Max-Age` 를 붙이지 않는다(세션 쿠키). 브라우저를 닫으면 사라진다(64행)
- **Refresh Token은 회전한다.** 재발급할 때마다 새 토큰을 주고 이전 토큰은 폐기한다. 이미 폐기된 토큰이 다시 오면 탈취로 보고 그 계정의 세션을 모두 끊는다(6, 64, 94행)
- **로그아웃하면 Access Token도 막는다.** 로그아웃 전에 발급된 Access Token은 만료 전이라도 거부한다(7, 34, 94행)

**점주 상태는 토큰을 받을 때 정해진다.** 로그인이나 재발급 시점의 점주 상태(`ONBOARDING`, `ACTIVE`)로 접근 범위가 정해지므로, 상태가 바뀐 뒤에는 재발급을 한 번 받아야 반영된다. "접근 제어" 절 참고.

## 관리자

### `POST /v1/admin/auth/login`

관리자 ID와 비밀번호로 로그인한다(5행).

**요청**

```json
{
  "loginId": "admin01",
  "password": "********"
}
```

**응답** `200` 과 두 쿠키

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "adminId": 1,
    "name": "정규동",
    "role": "SUPER_ADMIN"
  }
}
```

**동작**

1. `loginId` 로 계정을 찾는다. **계정이 없어도 비밀번호 비교를 한 번 수행해** 응답 시간으로 계정 존재 여부가 드러나지 않게 한다
2. 비밀번호가 맞고 상태가 `ACTIVE` 인지 본다. 하나라도 아니면 사유를 구분하지 않고 같은 실패로 돌려준다
3. 세션을 저장하지 못하면 **로그인도 실패**로 처리한다(5행)
4. 두 토큰을 쿠키로 내려준다

로그인 실패 횟수에 따른 계정 잠금은 이번 범위에 없다(5행 "향후 확장").

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `AUTH-001` | `loginId` 또는 `password` 누락 |
| `401` | `AUTH-002` | 계정 없음, 비밀번호 불일치, 사용 불가 상태(`DELETED`). 셋을 구분하지 않는다 |
| `503` | `AUTH-003` | 세션 저장 실패 |

### `POST /v1/admin/auth/refresh`

Refresh Token으로 두 토큰을 다시 받는다(6행). 요청 본문은 없고 `refreshToken` 쿠키만 보낸다.

**응답** `200` 과 새 두 쿠키, 본문 `data` 는 로그인 응답과 같다.

**동작**

1. 쿠키의 Refresh Token이 유효하고 만료되지 않았는지 확인한다
2. 새 Refresh Token으로 교체한다. **같은 토큰으로 동시에 두 요청이 와도 하나만 성공한다**
3. 이미 교체된 토큰이 다시 오면 그 계정의 세션을 모두 끊는다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `401` | `AUTH-004` | Refresh Token이 없음, 유효하지 않음, 만료, 폐기됨 |
| `401` | `AUTH-005` | 이미 교체된 Refresh Token의 재사용. 그 계정의 세션을 모두 끊는다 |

### `POST /v1/admin/auth/logout`

현재 로그인한 관리자의 세션을 끝낸다(7행). 요청 본문은 없다.

**응답** `204`. 두 쿠키를 `Max-Age=0` 으로 내려 브라우저에서도 지운다.

- Refresh Token을 폐기한다. 로그아웃 전에 받은 Access Token은 만료 전이라도 거부된다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `401` | `AUTH-006` | Access Token이 없거나 유효하지 않음 |
| `503` | `AUTH-003` | 로그아웃 처리 실패. 잠시 후 다시 시도한다 |

## 점주

### `POST /v1/owner/auth/signup`

이메일과 비밀번호로 점주 계정을 만든다(31행). 가입 직후 상태는 `ONBOARDING` 이다.

**요청**

```json
{
  "email": "owner@example.com",
  "password": "********"
}
```

비밀번호 확인 입력의 일치 여부는 프론트가 검사한다. 서버는 비밀번호 확인 값을 받지 않는다.

**응답** `201`

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "ownerId": 55,
    "status": "ONBOARDING"
  }
}
```

- **역할은 서버가 `OWNER` 로 정한다.** 클라이언트가 역할을 보내도 무시한다
- 가입만 하고 로그인은 하지 않는다. 쿠키를 내려주지 않으므로 이어서 로그인을 부른다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `OWNER-001` | 이메일 형식 오류, 비밀번호 형식 오류, 필수값 누락 |
| `409` | `OWNER-002` | 이미 가입한 이메일 |

### `POST /v1/owner/auth/login`

이메일과 비밀번호로 로그인한다(32행).

**요청**

```json
{
  "email": "owner@example.com",
  "password": "********"
}
```

**응답** `200` 과 두 쿠키

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "ownerId": 55,
    "status": "ACTIVE",
    "tutorialViewed": false
  }
}
```

| 필드 | 뜻 |
|---|---|
| `status` | `ONBOARDING` 이면 프론트는 입점 등록 화면으로 보낸다. 이 상태에서는 입점 등록 API만 열린다 |
| `tutorialViewed` | `ACTIVE` 일 때만 싣는다. `false` 면 프론트가 최초 튜토리얼을 보인다. 완료 처리는 `owner.md` |

**동작**

1. 계정이 없어도 비밀번호 비교를 한 번 수행한다(관리자와 같다)
2. 상태가 `ONBOARDING` 또는 `ACTIVE` 일 때만 로그인시킨다. `SUSPENDED`, `WITHDRAWN` 이면 거부한다
3. 최근 로그인 시각을 갱신하고 두 토큰을 내려준다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `AUTH-001` | `email` 또는 `password` 누락 |
| `401` | `AUTH-002` | 계정 없음, 비밀번호 불일치, `SUSPENDED`, `WITHDRAWN`. 사유를 노출하지 않는다 |
| `503` | `AUTH-003` | 세션 저장 실패 |

### `POST /v1/owner/auth/refresh`

관리자 재발급과 같다(33행). 추가로 Refresh Token에 연결된 점주의 **현재 상태**를 다시 확인한다.

- `SUSPENDED`, `WITHDRAWN` 이면 재발급하지 않는다
- 재발급 시점의 점주 상태를 반영한다. **가게 최종 등록(42행)으로 `ACTIVE` 가 된 점주는 재발급을 한 번 받아야** 전체 점주 API가 열린다. 프론트는 최종 등록 성공 직후 이 API를 부른다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `401` | `AUTH-004` | Refresh Token이 없음, 유효하지 않음, 만료, 폐기됨, 재발급할 수 없는 계정 상태 |
| `401` | `AUTH-005` | 이미 교체된 Refresh Token의 재사용 |

### `POST /v1/owner/auth/logout`

관리자 로그아웃과 같다(34행). 응답은 `204` 이고 두 쿠키를 지운다.

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `401` | `AUTH-006` | Access Token이 없거나 유효하지 않음 |
| `503` | `AUTH-003` | 로그아웃 처리 실패(34행). 잠시 후 다시 시도한다 |

## 사용자

### `POST /v1/auth/kakao/login`

카카오 인가 코드를 받아 로그인한다. 처음 온 사용자면 가입까지 한다(62행).

**요청**

```json
{
  "authorizationCode": "kakao-auth-code",
  "redirectUri": "https://launchcatch.example/oauth/kakao",
  "autoLogin": true
}
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| `authorizationCode` | 예 | 카카오 로그인 화면이 돌려준 인가 코드 |
| `redirectUri` | 예 | 인가 요청에 쓴 리다이렉트 주소. 카카오가 같은 값을 요구한다 |
| `autoLogin` | 예 | 자동 로그인 체크 여부. `false` 면 Refresh Token을 세션 쿠키로 내려준다(64행) |

**응답** `200` 과 두 쿠키

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "memberId": 1024,
    "nickname": "점심헌터",
    "newMember": true,
    "onboardingCompleted": false
  }
}
```

| 필드 | 뜻 |
|---|---|
| `newMember` | 이번 요청으로 가입했으면 `true` |
| `onboardingCompleted` | `false` 면 프론트는 온보딩 폼(63행)으로 보낸다. 다음 로그인 때도 끝나지 않았으면 다시 보낸다 |

**동작**

1. 인가 코드로 카카오 인증을 마치고 카카오 회원번호를 얻는다
2. 회원번호로 사용자를 찾는다. 없으면 가입시킨다. 닉네임과 프로필 이미지는 **처음 가입할 때만** 카카오에서 가져온다
3. 성별과 연령은 카카오에서 받지 않는다(온보딩에서 받는다). 기기 식별자는 수집하지 않는다
4. **정지 이력이 있는 회원번호의 재가입은 거부한다.** 탈퇴 후 재가입해도 같은 회원번호라 하루 3개 발급 제한과 정지 이력이 이어진다(89행)
5. 두 토큰을 내려준다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `AUTH-001` | 필수 필드 누락 |
| `401` | `MEMBER-001` | 카카오 인가 코드나 ID 토큰 검증 실패 |
| `403` | `MEMBER-002` | 정지 이력이 있는 회원번호의 재가입 |
| `503` | `AUTH-003` | 세션 저장 실패 |

### `POST /v1/auth/refresh`

관리자 재발급과 같다(64행). 카카오 재인증은 필요 없다.

- 처음 로그인할 때의 `autoLogin` 을 이어받는다. 세션 쿠키로 받았으면 새 Refresh Token도 세션 쿠키다
- 이미 쓴 Refresh Token이 다시 오면 그 사용자의 세션을 모두 끊는다

**오류**: 관리자 재발급과 같다(`AUTH-004`, `AUTH-005`).

### `POST /v1/auth/logout`

서비스 세션을 끝낸다(65행). 응답은 `204` 이고 두 쿠키를 지운다.

- Refresh Token을 폐기한다. 로그아웃 전에 받은 Access Token은 거부된다
- 카카오 쪽 로그아웃도 요청한다. 카카오 계정 자체를 로그아웃시키지는 않는다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `401` | `AUTH-006` | 로그인 상태가 아님 |

## 접근 제어

**권한은 역할로 판정한다.** 경로 접두어와 역할이 맞지 않으면 `403` 이다(94행).

| 경로 | 허용 역할 |
|---|---|
| `/v1/admin/**` | `ADMIN`, `SUPER_ADMIN` (계정 발급 4행은 `SUPER_ADMIN` 만) |
| `/v1/owner/**` | `OWNER` |
| `/v1/**` (위 둘 제외) | `MEMBER` |
| 목록의 공개 7개 | 누구나 |

**점주는 상태로 한 번 더 막는다.** 점주 상태가 `ONBOARDING` 이면 입점 등록 API(약관 동의, 가게 기본 정보, 사업자 검증, 영업시간, 이미지, 메뉴, 최종 등록, 35~42행)만 열고 나머지 점주 API는 `403` 이다(32행).

입점 등록 API의 확정 경로는 `store.md`에 있다.

**접근 제어 오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `401` | `AUTH-006` | Access Token이 없거나, 만료됐거나, 로그아웃 전에 발급됨 |
| `403` | `AUTH-007` | 역할이 맞지 않음 |
| `403` | `AUTH-008` | `ONBOARDING` 점주가 입점 등록 외 API를 부름 |

권한이 없으면 리소스 존재 여부와 상관없이 `403` 이다(README 상태 코드).

## 오류 코드
