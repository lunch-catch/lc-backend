# 광고 서빙 (adserving)

스와이프 피드, 찜과 패스, 노출 수집, 피드 필터, 찜 목록, 피드 배정 진단을 다룬다.
공통 규약(경로, 인증, 응답 봉투, 상태 코드, 식별자, 시각)은 `README.md`를 따르고 여기서는 반복하지 않는다.

| 근거 | 기준 |
|---|---|
| 요구사항 | 명세서 V51 기능 30, 67~71, 74~76, 92, 96~97, 99~100행. 비즈니스 규칙의 공정성 절 |
| 저장 구조 | `db/migration/adserving/` 의 `V1`, `V2`: `ad_candidate`, `serve_log`, `impression_log`, `swipe_log`, `wishlist`, `feed_filter`, `feed_filter_category`, `feed_visit_daily`. 공통 DDL 규약은 같은 폴더의 `README.md` |
| 설계 | `../architecture/런치캐치_도메인_구조와_의존성_설계.md` 1.3, 2.2, 2.4 |

## 목록

| 메서드 | 경로 | 하는 일 | 권한 | 행 |
|---|---|---|---|---|
| `GET` | `/v1/feed` | 스와이프 피드 10장 | MEMBER | 67, 96, 97, 99 |
| `POST` | `/v1/swipes` | 찜 또는 패스 | MEMBER | 68 |
| `POST` | `/v1/impressions` | 카드 표시 이벤트 수집 | MEMBER | 69, 100 |
| `GET` | `/v1/feed-filter` | 내 피드 필터 | MEMBER | 70 |
| `PUT` | `/v1/feed-filter` | 피드 필터 저장 | MEMBER | 70 |
| `GET` | `/v1/wishlist` | 찜 목록 | MEMBER | 75, 74 |
| `POST` | `/v1/wishlist` | 가게 상세에서 찜 | MEMBER | 74 |
| `DELETE` | `/v1/wishlist/{campaignId}` | 찜 삭제 | MEMBER | 76 |
| `GET` | `/v1/admin/feed-diagnosis/feeds` | 사용자 피드 배정 진단 | ADMIN, SUPER_ADMIN | 30 |

가게 추천 차단(71, 92행)과 캠페인 기준 진단(30행 후반)은 저장 구조에 근거가 없어 경로를 적지 않았다. `아직 정해지지 않은 것`에 남겼다.

`/v1/feed` 와 `/v1/feed-filter` 는 단수다. 사용자당 하나뿐인 리소스라 목록이 없다(`feed_filter` 의 PK 가 `member_id` 하나다).
그래서 필터 저장도 항목 추가가 아니라 전체 교체인 `PUT` 이다. `/v1/wishlist` 는 README 의 경로 절이 예시로 쓰는 표기를 따른다.

## 성능 목표

| API | 목표 TPS | 응답 지연 시간 | 에러율 | 근거 |
|---|---|---|---|---|
| `GET /v1/feed` | 500 | p99 500ms | 0.1% 미만 | 피크 동시 접속 5,000명(비기능 11행) x 최근 60초 6회 제한(67행) / 60초 = 500이 상한 |
| `POST /v1/swipes` | 5,000 | p99 300ms | 0.1% 미만 | 피드 1회에 카드 10장. 500 x 10 = 5,000 |
| `POST /v1/impressions` | 10,000 | p99 200ms | 0.1% 미만 | 비기능 13행. 에러율은 노출 유실률 목표(비기능 18행)와 맞춘다 |
| `GET /v1/wishlist` | 500 | p99 300ms | 0.1% 미만 | 10:50~11:00에 5,000명이 10초 안에 몰린다고 본다 |
| `POST`, `DELETE /v1/wishlist` | | | 0.1% 미만 | 가게 상세의 찜과 삭제 |
| `GET`, `PUT /v1/feed-filter` | | | 0.1% 미만 | 설정 화면 |
| `GET /v1/admin/feed-diagnosis/feeds` | | | 1% 미만 | 관리자 조회 |

**에러율은 서버 오류(5xx)와 시간 초과만 센다.** 입력 오류(4xx)와 속도 제한(`429`)은 의도한 거부라 뺀다.
`429` 를 넣으면 제한이 잘 작동할수록 에러율이 오른다. 운영 알림 기준(비기능 40행, 노출 수집 오류율 1% 초과)은 목표와 따로 둔다.
**목표 TPS와 응답 지연 시간은 트래픽이 많이 몰리는 API 넷에만 둔다.** 나머지는 에러율만 본다. 검증은 k6 시나리오(10:00~12:59, 특히 10:50~11:05)로 한다.

## 피드

### `GET /v1/feed`

서빙 시간대(10:00~12:59)에 현재 위치 기준 카드 10장을 내려준다. 배분 슬롯 3장(1, 4, 7번)과 관련성 슬롯 7장이며
**클라이언트는 받은 순서를 바꾸지 않는다**(67행). 피드에서는 찜과 패스만 할 수 있고 발급 버튼은 없다.

**요청**

| 파라미터 | 위치 | 필수 | 뜻 |
|---|---|---|---|
| `latitude` | 쿼리 | 아니오 | 현재 위도 |
| `longitude` | 쿼리 | 아니오 | 현재 경도 |

위치를 보내지 않으면 사용자의 마지막 저장 위치를 쓴다(67행 "위치 획득에 실패하면 마지막 수동 입력 위치 사용").
둘 중 하나만 보내면 `400` 이다.

```
GET /v1/feed?latitude=37.4979&longitude=127.0276
```

**응답** `200`

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "status": "SERVING",
    "feedId": "01925f3a-7c1e-7b2a-9d4e-3f5a6b7c8d9e",
    "radiusM": 1000,
    "nextFeedAvailableAt": "2026-10-01T10:15:40+09:00",
    "cards": [
      {
        "serveId": "01925f3a-7c1e-7b2a-9d4e-3f5a6b7c8da0",
        "servedAt": "2026-10-01T10:15:30.123+09:00",
        "campaignId": 101,
        "storeId": 55,
        "storeName": "점심식당",
        "categoryCode": "KOREAN",
        "distanceM": 420,
        "discount": { "target": "ALL", "type": "PERCENT", "value": 20 },
        "issueOpenTime": "11:00",
        "usableStartTime": "12:00",
        "usableEndTime": "14:00",
        "issueQuantity": 30,
        "posterUrl": "/v1/campaigns/101/poster"
      }
    ]
  }
}
```

| 필드 | 뜻 |
|---|---|
| `status` | `SERVING`, `OUT_OF_SERVING_HOURS`(서빙 시간대 밖), `NO_CANDIDATE`(후보 없음) |
| `feedId` | 이 요청 한 번의 카드 묶음 ID. `SERVING` 일 때만 |
| `radiusM` | 반경 확장(1 -> 2 -> 3 -> 5km)을 거쳐 실제로 쓴 사용자 반경 |
| `nextFeedAvailableAt` | 다음 피드를 요청해도 거부되지 않는 가장 이른 시각. 지금 바로 요청할 수 있으면 응답 시각과 같다. `status` 와 상관없이 항상 준다 |
| `cards[].serveId` | 카드 1장의 식별자. 노출, 스와이프 요청에 그대로 돌려보낸다 |
| `cards[].discount` | `target` 은 `ALL`, `MENU`. `type` 은 `PERCENT`, `AMOUNT` |
| `cards[].issueQuantity` | 선착순 발급 수량(표시용). 잔여 수량은 피드에 싣지 않는다 |
| `cards[].posterUrl` | 포스터 주소. 사용자 포스터 조회 API(poster.md)의 경로다 |

- 서빙 시간대 밖이면 `status` 가 `OUT_OF_SERVING_HOURS` 이고 `cards` 는 빈 배열이다. 클라이언트는 "내일 10시에 만나요"를 보인다. 노출과 차감이 없다
- 후보가 없으면 `NO_CANDIDATE` 와 빈 `cards` 다
- "광고" 라벨은 서버가 내려주지 않는다. **모든 카드에 클라이언트가 항상 표시한다**(67행, 표시광고법)
- 슬롯 유형과 배정 근거는 응답에 싣지 않는다. 서버의 serve 기록에만 남는다
- 마지막 카드에 닿았을 때 지금 시각이 `nextFeedAvailableAt` 이후면 바로 다음 피드를 요청한다. 아직 전이면 "N초 후 새 카드"를 보여 주고, 그 시각에 한 번 요청한다
- 포스터는 피드 응답에 HTML로 싣지 않고 주소로 준다. 클라이언트는 이 주소를 불러 `data.html` 을 `<iframe sandbox srcdoc=...>` 에 그린다. 점주가 만든 HTML이라 앱 화면과 격리한다
- 피드에 나오는 캠페인은 활성화를 마친 캠페인이고, 활성화 뒤에는 포스터를 고칠 수 없다(55행). 그래서 같은 주소는 항상 같은 포스터이며 브라우저 캐시를 그대로 쓴다

**서버가 하는 일**

1. 그날의 후보 스냅샷(`ad_candidate`)에서만 후보를 찾는다. 서빙 중에 다른 도메인 테이블을 읽지 않는다(96행)
2. 배분 3장은 예산 소진 진행률 오름차순, 관련성 7장은 관련성 점수(거리 45, 카테고리 선호도 35, 할인 20) 순이다(96, 97, 99행). 예산 소진 진행률이 1.2를 넘거나, 그날 유효 노출 수가 노출 상한(그날 예약액 / 그날 단가 x 1.05)에 닿은 캠페인은 두 슬롯 모두에서 뺀다(99행). 진행률, 그날 예약액, 단가는 정산의 `BudgetQueryService`로 읽고, 유효 노출 수는 광고 서빙이 자기 노출 로그로 센다. 예산에 닿은 뒤 상한까지 들어온 노출은 과금하지 않는다(`NOT_BILLED_BUDGET`, 103행)
3. 피드 필터의 카테고리는 10장 전부에, 정렬은 관련성 7장에만 적용한다(70행)
4. 같은 사용자에게 같은 캠페인은 하루 2회, 한 세션 1회까지만 내려준다. 30분 활동이 없으면 새 세션이다(비즈니스 규칙)
5. 카드마다 serve 기록을 인메모리 캐시(TTL 30분)에 쓰고, 응답 뒤 `serve_log` 와 그날 첫 요청 위치(`feed_visit_daily`)를 비동기로 쓴다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `COMMON-002` | 위도와 경도 중 하나만 보냄, 범위 밖 좌표 |
| `403` | `ADSERVING-001` | 온보딩(성별, 연령대)을 마치지 않음(63행) |
| `422` | `ADSERVING-002` | 위치를 보내지 않았고 저장 위치도 없음 |
| `429` | `ADSERVING-003` | 사용자 ID 기준 최근 60초 6회 초과(67행). IP 기준 제한은 없다 |

**요청 제한**

- 사용자 ID 기준 **최근 60초 동안 6회**까지 받는다(67행). 분 단위로 끊어 세지 않는다
- 거부된 요청(`429`)은 횟수에 넣지 않는다. 그래서 알려 준 시각에 다시 요청하면 거부되지 않는다
- 서빙 시간대 밖이나 후보가 없어 카드 없이 끝난 요청도 `200` 이면 횟수에 넣는다
- `429` 응답에는 `Retry-After` 헤더를 준다. 다시 요청할 수 있을 때까지 남은 초이며, 올림한 정수다

```
HTTP/1.1 429 Too Many Requests
Retry-After: 37
```

- 클라이언트는 `Retry-After` 초가 지난 뒤 **한 번만** 다시 요청한다. 앱이 화면에 보일 때만 다시 요청하고, 실패하면 반복하지 않는다

성능 목표는 `성능 목표` 표를 따른다.

## 찜과 패스

### `POST /v1/swipes`

카드를 오른쪽(찜) 또는 왼쪽(패스)으로 넘긴다. 노출은 카드가 보인 순간 이미 집계되므로
**어느 쪽으로 넘겨도 노출 수와 과금은 달라지지 않는다**(68행).

**요청**

```json
{
  "serveId": "01925f3a-7c1e-7b2a-9d4e-3f5a6b7c8da0",
  "campaignId": 101,
  "action": "WISH",
  "occurredAt": "2026-10-01T10:15:34.020+09:00"
}
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| `serveId` | 예 | 피드 응답의 카드 식별자 |
| `campaignId` | 예 | 카드의 캠페인 |
| `action` | 예 | `WISH` 또는 `PASS` |
| `occurredAt` | 예 | 클라이언트에서 넘긴 시각 |

**응답** `200`

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": { "applied": true }
}
```

- **같은 사용자가 같은 `serveId` 로 다시 보내면 최초 1건만 반영한다.** 두 번째부터는 `applied: false` 로 성공을 돌려준다. 키는 `(serveId, 요청 사용자)` 다(68행, `swipe_log` PK)
- 다른 사용자가 같은 `serveId` 로 보낸 스와이프는 그 사용자의 기록으로만 남고 원래 사용자의 스와이프를 막지 않는다
- `WISH` 면 찜 목록에 넣는다. 이미 찜한 캠페인이면 찜 목록은 그대로 둔다. 찜한 캠페인은 그날 피드에 다시 나오지 않는다. 찜은 사용자 당일 이력이라 00:00에 초기화된다(102행 (9), 비즈니스 규칙 43행)
- `PASS` 면 그날 그 캠페인을 다시 내려주지 않는다
- 기록은 30일 관련성 카테고리 선호도에 쓰이고, 분석에는 `SwipedEvent` 로 비동기 전달된다

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `COMMON-002` | `action` 값이 잘못됨, 필수 필드 누락 |
| `404` | `ADSERVING-004` | `campaignId` 가 그날 후보에 없음 |

## 노출 수집

### `POST /v1/impressions`

카드가 스와이프 피드의 맨 위 카드로 보인 순간 1건씩 즉시 보낸다(69행). 성능 목표는 `성능 목표` 표를 따른다(100행).

**클라이언트 규칙**

- 서버가 내려준 카드라도 그 카드까지 넘기지 않았으면 보내지 않는다. 앱이 백그라운드에 있는 동안의 카드도 보내지 않는다
- 화면을 벗어나는 순간에도 전송이 끝나도록 `keepalive` 옵션을 쓴다
- 실패하면 1회 재시도하고 포기한다. 집계되지 않은 노출은 차감도 되지 않는다
- **응답에 의존하지 않는다.** 화면을 벗어나며 보낸 요청은 응답을 못 받을 수 있다(100행)

**요청**

```json
{
  "serveId": "01925f3a-7c1e-7b2a-9d4e-3f5a6b7c8da0",
  "campaignId": 101,
  "displayedAt": "2026-10-01T10:15:31.880+09:00",
  "latitude": 37.4979,
  "longitude": 127.0276,
  "viewedMs": 2140
}
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| `serveId` | 예 | 피드 응답의 카드 식별자 |
| `campaignId` | 예 | 카드의 캠페인 |
| `displayedAt` | 예 | 클라이언트 표시 시각 |
| `latitude`, `longitude` | 예 | 표시 시점 위치. 서버가 소수점 3자리로 반올림해 저장한다 |
| `viewedMs` | 아니오 | 카드를 본 시간. 참고 지표 |

요청 사용자는 본문이 아니라 토큰으로 정한다.

**응답** `202`

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": { "validity": "VALID", "invalidReason": null }
}
```

| 필드 | 값 |
|---|---|
| `validity` | `VALID`, `INVALID` |
| `invalidReason` | `INVALID` 일 때 `EXPIRED_OR_UNKNOWN`(serve 기록 없음, 30분 초과), `NOT_OWNER`(다른 사용자의 serveId) |

**서버가 하는 일**

1. serve 기록이 캐시에 있는지 본다. 없으면 `EXPIRED_OR_UNKNOWN`
2. serve 기록의 사용자와 요청 사용자가 같은지 본다. 다르면 `NOT_OWNER`
3. 유효하면 한 트랜잭션 안에서 `impression_log` 에 저장하고, 처음 저장된 유효 노출이면 정산의 `PointDeductor` 로 노출 차감을 부른다. 그날 후보가 쿠폰 소진이면 차감을 부르지 않고 `sold_out` 으로 적는다(`NOT_BILLED_SOLD_OUT`)
4. 과금 판정(`BILLED`, `NOT_BILLED_BUDGET`, `NOT_BILLED_PAUSED`)은 정산이 자기 기록에 남긴다(103행). 노출 저장, 판정, 원장이 함께 커밋된 뒤 응답하고, 실패하면 함께 롤백된다. 무효 노출도 사유와 함께 저장하고 차감은 부르지 않는다

- **과금 상태는 응답에 싣지 않는다.** 점주의 과금 정보라 사용자에게 줄 이유가 없다. 미과금 노출도 유효 노출이다
- **같은 사용자가 같은 `serveId` 로 다시 보내면 저장하지 않는다.** 키는 `(serveId, 요청 사용자)` 다(100행, `impression_log` PK). 다른 사용자가 먼저 보낸 무효 노출이 원래 사용자의 유효 노출을 막지 못한다. 중복 요청도 `202` 와 최초 판정을 돌려준다
- 요청이 많아지면 여러 건을 묶어 받는 방식으로 바꿀 수 있고, 검증과 중복 처리는 같다(100행)

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `COMMON-002` | 필수 필드 누락, `serveId` 형식 오류 |

무효 노출은 오류가 아니다. `202` 와 `INVALID` 로 돌려준다.

## 피드 필터

### `GET /v1/feed-filter`

**응답** `200`

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": { "categories": ["KOREAN", "JAPANESE"], "sort": "DISTANCE" }
}
```

저장한 적이 없으면 `categories: []`(전체), `sort: "DISTANCE"` 를 돌려준다.

### `PUT /v1/feed-filter`

필터를 통째로 바꾼다. 계정에 저장되어 다시 접속해도 유지된다(70행).

```json
{ "categories": ["KOREAN", "JAPANESE"], "sort": "DISCOUNT_RATE" }
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| `categories` | 예 | 업종 코드 목록. **빈 배열은 전체 카테고리다**(70행 예외) |
| `sort` | 예 | `DISTANCE`(거리순), `DISCOUNT_RATE`(할인율순) |

**응답** `200`, 저장한 필터를 돌려준다. 다음 피드 요청부터 적용된다.

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `COMMON-002` | 없는 업종 코드, 허용되지 않은 정렬 값 |

## 찜 목록

### `GET /v1/wishlist`

찜한 캠페인 목록이다(75행). **광고 서빙은 찜 목록만 돌려준다.** 잔여 수량, 발급 가능 여부, 하루 발급 잔여 횟수는
클라이언트가 받은 `campaignId` 들로 쿠폰 API를 따로 불러 합친다. 광고 서빙이 쿠폰을 부르면 도메인 간 순환이 생기기 때문이다(75행).

| 파라미터 | 필수 | 뜻 |
|---|---|---|
| `campaignId` | 아니오 | 주면 그 캠페인만. 가게 상세에서 찜 여부를 볼 때 쓴다(74행) |

**응답** `200`

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "wishlist": [
      {
        "campaignId": 101,
        "storeId": 55,
        "storeName": "점심식당",
        "storeImageUrl": "https://cdn.example.com/stores/55/logo.jpg",
        "discount": { "target": "MENU", "type": "AMOUNT", "value": 3000, "menuName": "갈비살 정식" },
        "wishedAt": "2026-10-01T10:15:34.020+09:00"
      }
    ]
  }
}
```

- `wishedAt` 은 `wishlist.created_at` 이다. 찜할 때 행을 만들고 취소하면 행을 지우므로 둘이 같다
- 찜한 시각 내림차순이다. 찜은 캠페인이 끝나면 자동으로 빠지므로 진행 중인 캠페인 수만큼만 쌓여 페이지네이션을 두지 않는다
- `storeName`, `storeImageUrl`, `discount` 는 그날 후보 스냅샷에서 채운다. 스냅샷에 없는 캠페인이면 `null` 이다
- `storeImageUrl` 은 가게 대표 이미지(가게 이미지 중 LOGO) 주소다. 가게가 대표 이미지를 올리지 않았으면 `null` 이다. 낮에 이미지를 바꾸면 다음 날 00:00 스냅샷부터 반영된다
- `discount.menuName` 은 할인 대상이 `MENU` 일 때만 값이 있고, `ALL` 이면 `null` 이다
- 0건이면 빈 `wishlist` 다. 클라이언트가 빈 상태 화면과 피드 이동 버튼을 보인다
- 이 화면 조회는 노출이 아니다. 클라이언트가 분석 수집 API로 `wishlist_view` 를 따로 보낸다(75행)

### `POST /v1/wishlist`

가게 상세의 "찜해두기"(74행)다. 피드의 찜은 `POST /v1/swipes` 로 한다.

```json
{ "campaignId": 101 }
```

**응답** `201`. 이미 찜한 캠페인이면 `200` 과 기존 항목을 돌려준다. 키는 `(사용자, 캠페인)` 이다(`wishlist` UNIQUE).

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `404` | `ADSERVING-004` | 캠페인이 그날 후보에 없음 |

### `DELETE /v1/wishlist/{campaignId}`

**응답** `204`. 찜 목록에 없는 캠페인이어도 `204` 다.

- 삭제한 캠페인은 그날 피드에 다시 나오지 않는다(76행)
- 10:50 선착순 오픈 알림 대상에서도 빠진다. 알림이 10:50에 찜 목록을 읽어 보내므로 따로 취소할 것이 없다(76행)

## 피드 배정 진단 (관리자)

### `GET /v1/admin/feed-diagnosis/feeds`

특정 사용자의 피드 한 묶음이 어떻게 구성됐는지 본다(30행). 기록을 바꾸지 않는다.

| 파라미터 | 필수 | 뜻 |
|---|---|---|
| `feedId` | 둘 중 하나 | 피드 묶음 ID |
| `memberId`, `at` | 둘 중 하나 | 사용자와 시각. 그 시각 직전의 피드 묶음을 찾는다 |

**응답** `200`

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "found": true,
    "feedId": "01925f3a-7c1e-7b2a-9d4e-3f5a6b7c8d9e",
    "memberId": 3001,
    "servedAt": "2026-10-01T10:15:30.123+09:00",
    "cards": [
      { "slotPosition": 1, "slotType": "ALLOCATION", "campaignId": 101, "storeId": 55, "serveId": "01925f3a-..." }
    ],
    "settings": { "slotRatio": "3:7", "relevanceWeights": { "distance": 45, "category": 35, "discount": 20 }, "dailyImpressionCap": 2 }
  }
}
```

- `cards` 는 `serve_log`, `settings` 는 그 시각에 적용된 플랫폼 설정값 이력에서 읽는다
- 기록이 없으면 `found: false` 로 돌려준다. 화면은 "기록 없음"을 보인다(30행 예외)

**오류**

| 상태 | 코드 | 언제 |
|---|---|---|
| `400` | `COMMON-002` | `feedId` 도 `memberId` 와 `at` 도 없음 |
| `422` | `ADSERVING-005` | 서빙 기록 보관 기간(13개월) 밖의 시각 |

## 다른 도메인에 공개한 기능

HTTP가 아니라 도메인 contract의 Java 클래스로 노출한다. 클라이언트는 쓰지 않는다.

| 공개 항목 | 쓰는 도메인 | 하는 일 |
|---|---|---|
| `WishlistQueryService` | coupon, notification | 찜 여부(83행 발급 자격), 찜 보유 사용자(79행 10:50 발송 대상) |
| `CandidateStateUpdater` | coupon | 선착순 소진 시 그날 후보에 소진 표시(96행) |
| `ImpressionServedEvent`, `SwipedEvent` | analytics | 전환 퍼널 기록(impression, wish, pass). 비동기 |

## 오류 코드

요청 형식이 틀린 경우처럼 **판정에 업무 지식이 필요 없는 실패는 공통 코드를 쓴다.**
필수값 누락, 좌표 범위, `action` 과 정렬 값과 업종 코드 같은 고정 값, `serveId` 형식, 둘 중 하나는 있어야 하는 조건은
요청 타입의 애노테이션이 판정하므로 `COMMON-002` 로 온다. 공통 코드 목록은 `README.md` 의 공통 오류 코드 절에 있다.

여기에는 후보, 사용자 상태, 정책을 봐야 판정할 수 있는 실패만 둔다.

| 코드 | 상태 | 메시지 |
|---|---|---|
| `ADSERVING-001` | `403` | 온보딩을 완료한 뒤 피드를 이용할 수 있습니다. |
| `ADSERVING-002` | `422` | 위치를 설정한 뒤 피드를 이용할 수 있습니다. |
| `ADSERVING-003` | `429` | 잠시 후 다시 시도해 주세요. |
| `ADSERVING-004` | `404` | 오늘 노출 중인 캠페인이 아닙니다. |
| `ADSERVING-005` | `422` | 조회할 수 있는 기간이 지났습니다. |
