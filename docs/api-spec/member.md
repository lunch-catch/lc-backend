# 사용자와 회원 관리 API

FR-007~FR-009, FR-059~FR-063, FR-074~FR-075, FR-084~FR-088, FR-090~FR-091을 기준으로 한다. 공통 인증과 토큰 계약은 `auth-api-spec.md`, 공통 규약은 `api-spec.md`를 따른다. 서버가 하는 일과 그렇게 정한 이유는 설계서 [member-api-design.md](../design/member/member-api-design.md)에 있다.

구현 범위는 아래 "API 목록"의 구현 대상 표이며, 그 밖의 API는 "구현 제외" 절에 이유와 함께 모아 둔다. 구현 제외로 둔 것은 이번 계약에 포함하지 않으며 다시 채택하려면 해당 절의 확정 항목을 먼저 정한다.

**2026-10-18 변경 (설명만):** 요청과 응답은 그대로다. 관심 가게(FR-074, FR-075)는 member가 아니라 광고서빙의 캠페인 단위 찜(`/v1/wishlist`)으로 제공된다는 사실을 적고 `feed-api-spec.md`를 가리켰다. 카카오 웹훅 절 끝에 잘못 붙어 있던 `409 MEMBER-002`를 온보딩 오류 표로 옮겼다. 탈퇴 뒤 카카오 연결 해제, 웹훅 처리, 내부 컬럼 처리, 데이터 보존, 서버 쪽 미정 항목은 설계서로 옮겼다.

## 온보딩과 프로필

`PUT /v1/members/me/onboarding`은 `gender`(`MALE`, `FEMALE`, `OTHER`), `ageGroup`(`AGE_20S`, `AGE_30S`, `AGE_40S`, `AGE_50_PLUS`), `locationOptIn`, `notificationOptIn`을 모두 받는다. 성별과 연령대가 없으면 완료할 수 없다. 위치 동의를 거부한 회원은 가입할 수 있지만 피드와 지도 이용 제한을 안내받는다. 성별과 연령대는 온보딩 이후 수정하는 API가 없다. `SUSPENDED` 회원도 온보딩할 수 있다.

### 입력 필드

| 필드 | 타입 | 온보딩 PUT | 내 정보 PATCH |
|---|---|---|---|
| `gender` | 문자열 enum | 필수, null 불가 | 수정하지 않음 |
| `ageGroup` | 문자열 enum | 필수, null 불가 | 수정하지 않음 |
| `notificationOptIn` | 불리언 | 필수, null 불가 | 선택, 생략·null이면 유지 |
| `locationOptIn` | 불리언 | 필수, null 불가 | 선택, 생략·null이면 유지 |
| `nickname` | 문자열 | 받지 않음 | 선택, 1~20자이며 공백만 있는 값은 거절함 |

PATCH는 수정할 값이 최소 하나 있어야 한다. 동의 값을 다시 같은 값으로 보내면 동의 시각을 바꾸지 않는다. 두 API 모두 아래의 내 정보 응답과 같은 모양으로 `200`을 반환한다.

가입 진행 상태는 별도 회원 상태값이 아니라 `member_profile.onboarding_completed_at`으로 판단하며, 응답은 `onboardingCompleted` 불리언을 제공한다. 미완료 회원은 다음 로그인 뒤 온보딩 화면으로 이동한다.

응답의 `feedAvailable`은 `onboardingCompleted`와 `locationOptIn`이 모두 `true`일 때만 `true`다. 온보딩을 마치지 않았거나 위치정보 수집에 동의하지 않으면 `false`다(FR-060: 온보딩을 마치지 않으면 피드를 이용할 수 없다).

**2026-10-07 변경:** 온보딩과 내 정보 응답에 `feedAvailable`을 추가하고, `SUSPENDED` 회원의 온보딩을 허용한다고 명시했다.

**2026-10-09 변경:** `feedAvailable`의 정의를 `locationOptIn`과 같은 값에서 `onboardingCompleted && locationOptIn`으로 바로잡았다. FR-060이 온보딩을 마치지 않으면 피드를 이용할 수 없다고 정하고, 온보딩 전에도 내 정보 수정으로 `locationOptIn`을 바꿀 수 있어서 두 정의가 달라지는 경우가 있었다.

`GET /v1/members/me`과 `PATCH /v1/members/me`은 닉네임, 성별, 연령대, 두 동의 상태와 `onboardingCompleted`를 다룬다. 조회 응답에는 읽기 전용 nullable `profileImageUrl`을 포함한다. 닉네임은 1~20자와 공백만 있는 값의 금지를 검증하며 별도 문자 종류 제한은 없다. 닉네임과 프로필 이미지는 카카오에서 최초 가입과 탈퇴 뒤 재가입 때 가져오고, 이후 사용자가 수정할 수 있는 것은 닉네임뿐이다.

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "memberId": 1,
    "nickname": "점심헌터",
    "profileImageUrl": null,
    "status": "ACTIVE",
    "onboardingCompleted": true,
    "feedAvailable": true,
    "profile": {
      "gender": "FEMALE",
      "ageGroup": "AGE_20S"
    },
    "consents": {
      "notificationOptIn": false,
      "notificationOptedInAt": null,
      "locationOptIn": true,
      "locationOptedInAt": "2026-10-07T09:00:00+09:00"
    },
    "createdAt": "2026-10-01T09:00:00+09:00"
  }
}
```

온보딩 전에는 `profile`이 `null`이다. `profileImageUrl`과 동의 시각은 값이 없으면 `null`이다.

**2026-10-07 변경:** 내 정보 응답의 실제 구조를 `memberId`, `status`, `profile`, `consents`, `createdAt`, `feedAvailable`까지 명시했다.

| 응답 | 코드 | 언제 |
| --- | --- | --- |
| `200` | | 성공 |
| `400` | 공통 검증 오류 | 필수 값 누락 또는 허용 값 밖 |
| `400` | `MEMBER-001` | 이미 탈퇴한 회원 |
| `409` | `MEMBER-002` | 이미 온보딩을 완료함 (온보딩 API) |

## 대표 저장 위치

회원당 한 개의 대표 위치를 제공한다. 사용자는 인증 쿠키로 식별하며 요청에 `memberId`를 보내지 않는다. 여러 위치를 추가하거나 목록으로 관리하는 API는 제공하지 않는다.

### `PUT /v1/member-profiles/location`

위치 전체를 대체한다. 온보딩 전에도 저장할 수 있고 위치 수집 동의를 저장의 선행 조건으로 검사하지 않는다.

| 필드 | 타입 | 필수·null | 제약과 동작 |
|---|---|---|---|
| `locationNickname` | 문자열 | 선택, null 허용 | 최대 50자, 생략·null이면 기존 별칭을 비움 |
| `roadAddress` | 문자열 | 선택, null 허용 | 최대 255자, 생략·null이면 기존 주소를 비움 |
| `latitude` | 숫자 | 필수, null 불가 | -90 이상 90 이하 |
| `longitude` | 숫자 | 필수, null 불가 | -180 이상 180 이하 |

주소 문자열만 보내는 요청은 받지 않는다. 주소 검색을 사용하면 검색 결과의 좌표를 함께 보내야 한다. 위치 동의가 없으면 클라이언트는 GPS를 수집하지 않고 주소 검색으로 선택한 좌표를 보낼 수 있다. 서버는 좌표가 GPS인지 주소 검색 결과인지 구분하지 않는다.

```json
{
  "locationNickname": "회사",
  "roadAddress": "서울특별시 강남구 테헤란로 1",
  "latitude": 37.4979000,
  "longitude": 127.0276000
}
```

성공하면 아래 네 필드를 `data`에 담은 `200`을 반환한다. 좌표는 저장 위치의 정밀도를 유지하며 노출 로그에 적용하는 소수점 3자리 반올림 규칙을 적용하지 않는다.

### `GET /v1/member-profiles/location`

본문과 쿼리 없이 현재 위치를 조회한다. 응답은 다음과 같다.

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": {
    "locationNickname": "회사",
    "roadAddress": "서울특별시 강남구 테헤란로 1",
    "latitude": 37.4979000,
    "longitude": 127.0276000
  }
}
```

응답 필드의 타입은 PUT 입력과 같으며 모두 null을 허용한다. 프로필이나 저장 위치가 없으면 네 필드가 모두 `null`인 `200`이다.

### `DELETE /v1/member-profiles/location`

본문 없이 삭제하며 `204`를 반환한다. 위치가 없거나 이미 삭제됐어도 같은 응답이다. 온보딩 완료 상태와 위치 수집 동의는 유지한다. 저장 위치를 지우면 현재 위치를 얻지 못한 피드의 대체 위치도 없어진다. 피드의 위치 선택 규칙은 [피드 명세](./feed-api-spec.md)를 따른다.

| 응답 | 코드 | 언제 |
|---|---|---|
| `400` | `COMMON-002` | PUT의 좌표 누락·범위 또는 문자열 길이 검증 실패 |
| `400` | `COMMON-003` | PUT의 요청 본문을 해석할 수 없음 |
| `400` | `MEMBER-001` | PUT 처리 중 이미 탈퇴한 회원임이 확인됨 |
| `401` | `AUTH-005` | 인증이 없거나 유효하지 않음 |
| `403` | `AUTH-006` | MEMBER 역할이 아님 |

## 탈퇴

`POST /v1/members/me:withdraw`는 카카오 재인증(`GET /v1/auth/kakao/authorize?reauth=true`, `prompt=login`)에서 받은 `authorizationCode`와 `state`, 선택 `reason`(255자 이하)을 받는다. callback의 state는 재인증을 시작한 탭의 `sessionStorage` 값과 먼저 대조한다. 서버는 카카오 로그인과 같은 검증을 하고, 재인증한 카카오 계정이 현재 로그인한 회원의 계정인지 확인한다.

`reason`은 탈퇴 처리의 참고 입력일 뿐 DB나 운영 감사 로그에 저장하지 않으며, 처리 뒤 폐기한다.

```json
{ "authorizationCode": "...", "state": "...", "reason": "선택 입력" }
```

서버는 다음 순서로 처리한다.

1. 재인증 코드를 검증한다.
2. 회원을 `WITHDRAWN`으로 바꾸고 개인정보를 즉시 비식별 처리한다. 행은 남긴다(소프트 삭제).
3. Refresh Token을 폐기하고 그 전에 받은 Access Token도 막으며, `accessToken`과 `refreshToken` 쿠키를 `Max-Age=0`으로 만료한다.
4. DB에 탈퇴를 반영한 뒤 카카오 연결 해제를 요청한다. 해제가 실패해도 탈퇴는 완료로 응답하고 서버가 나중에 다시 시도한다. 프론트가 따로 할 일은 없다.

연결 해제의 처리 순서와 재시도는 설계서에 있다.

| 응답 | 코드 | 언제 |
| --- | --- | --- |
| `204` | | 탈퇴 완료 |
| `401` | `AUTH-007` | 카카오 재인증 정보가 유효하지 않음(`state` 불일치, 인가 코드 검증 실패 등) |
| `400` | `MEMBER-001` | 이미 탈퇴한 회원 |
| `503` | `AUTH-002` | 인증 토큰을 폐기하지 못함 |

### `GET`·`POST /webhook/kakao/unlink`

카카오가 연결 해제를 서버로 통보하는 서버 간 경로다. **프론트는 부르지 않는다.** 최초 가입 계정의 연결 해제 통보는 서버가 탈퇴 처리하고 토큰을 폐기한다. 그 뒤 그 회원의 요청은 `401 AUTH-005`다. 재가입 계정의 통보는 과거 계정의 통보와 구분할 수 없어 자동 탈퇴하지 않고 경보로 남긴다. 판정 데이터와 한계는 [구조와 동작 설계](../design/member/member_구조와_동작_설계.md#연결-해제-웹훅의-구분-한계)가 갖는다.

이메일과 휴대폰은 수신, 수정, 응답하지 않는다. 프로필 사진은 카카오 선택 동의로만 수집하며 직접 업로드나 수정 API는 제공하지 않는다. 선택 동의가 없거나 카카오 응답에 사진이 없으면 `profileImageUrl`은 `null`이다.

### 탈퇴 시 데이터 처리

| 데이터 | 처리 | 상태 |
| --- | --- | --- |
| `nickname` | 고정 문구 `탈퇴한 회원`으로 교체 | 확정 |
| 성별, 연령대 | 삭제. 재가입하면 온보딩을 다시 받는다 | 확정 |
| 저장 위치 | 삭제 | 확정 |
| 알림, 위치 동의 | `false`, 동의 시각 `null` | 확정 |
| 토큰 | 모두 폐기 | 확정 |
| `profileImageUrl` | `null`로 삭제 | 확정. 탈퇴 뒤 재가입 시 카카오 선택 동의와 응답이 있으면 다시 저장하고, 없으면 `null`로 둔다 |
| `lastLoginAt` | `null`로 삭제 | 확정. 탈퇴 회원의 마지막 로그인 시각은 관리자 목록에도 내리지 않는다 |
| `reason` | 저장하지 않고 처리 뒤 폐기 | 확정 |

카카오 회원번호는 탈퇴 이력에 보관하지만 어떤 응답에도 내리지 않는다. 재가입 식별과 제한을 판정하는 데 쓴다. 내부 컬럼의 처리는 설계서에 있다.

**2026-10-07 변경:** 탈퇴 회원의 닉네임 문구를 `탈퇴한 회원`으로 확정했다.

### 재가입

같은 카카오 계정으로 다시 가입하면 새 회원과 새 `memberId`를 발급한다. 이전 계정의 찜·쿠폰·필터·회원 쿠폰 요약은 새 계정에 연결하지 않는다. 재가입 시 카카오에서 받은 닉네임과 프로필 이미지를 반영하고 온보딩과 동의를 다시 받는다.

탈퇴한 당일은 한국 시각 기준으로 `403 MEMBER-004`를 반환한다. 다음 날 00:00부터 날짜 제한이 풀린다. 과거 어느 탈퇴 이력이든 정지된 적이 있으면 `403 MEMBER-003`으로 거부한다. 이전 카카오 연결 해제 작업이 남으면 `409 MEMBER-005`로 보류한다. 작업 재시도를 포기한 경우도 완료로 취급하지 않는다.

**2026-10-07 변경:** 재가입 시 닉네임과 프로필 이미지를 카카오 응답으로 다시 반영하는 것으로 확정했다.

## 관리자 사용자 목록

```
GET /v1/admin/members?status=ACTIVE&joinedFrom=2026-09-01&joinedTo=2026-09-30&keyword=홍&page=0&size=20&sortBy=joinedAt&sortDir=desc
```

> **페이지 방식 (2026-10-09 결정, 2026-10-13 범위 명확화):** 이 사용자 목록과 아래 점주 목록은 페이지 번호로 이동하고 전체 건수를 확인하는 화면이라 `page` 방식을 유지한다. 이 선택을 모든 관리자 조회에 적용하지 않는다. 다른 목록의 방식은 각 API의 명세를 따른다. 페이지 방식의 예외는 공통 규약 문서가 아니라 해당 API의 명세가 소유한다.

| 파라미터 | 필수 | 설명 |
| --- | --- | --- |
| `status` | 아니오 | `ACTIVE`, `SUSPENDED`, `WITHDRAWN` |
| `joinedFrom`, `joinedTo` | 아니오 | 가입일(`member.created_at`) 범위. 양끝 포함, `yyyy-MM-dd`, KST 날짜 기준 |
| `keyword` | 아니오 | 닉네임 접두사를 검색한다. 앞뒤 공백을 제거하며 값이 없거나 공백뿐이면 검색 조건에서 빠진다. 숫자도 닉네임으로 처리한다. `%`·`_`·`!`는 공통 LIKE 모듈로 이스케이프해 문자 그대로 검색한다 |
| `page`, `size` | 아니오 | `page`는 0부터(기본 0). `size`는 기본 20, 최대 100 |
| `sortBy`, `sortDir` | 아니오 | `joinedAt`(기본)·`lastLoginAt`·`nickname`·`memberId` / `desc`(기본)·`asc`. 값이 같으면 `memberId`가 `sortDir`과 같은 방향. `lastLoginAt`이 `null`인 행은 방향과 관계없이 맨 뒤 |

**2026-10-07 변경:** 닉네임 검색을 인덱스를 사용할 수 없는 완전 부분 일치에서 접두사 일치로 변경했다.

**2026-10-08 변경:** 페이지 크기 20 고정을 풀고 `size`·정렬 옵션을 추가했다. 사용자 계정 정지 API가 구현 제외라 `SUSPENDED`는 현재 해당 행이 없다. 필터는 정지 기능 도입을 대비해 남긴다.

**2026-10-13 변경:** `searchType`과 회원 ID 검색을 제거했다. `keyword`만 보내면 닉네임 접두사로 검색한다. 회원 ID 응답과 `sortBy=memberId` 정렬은 유지한다. 프론트는 검색 종류 선택을 제거하고 닉네임 검색어만 보낸다.

```json
{
  "code": "SUCCESS",
  "message": "...",
  "data": {
    "items": [
      { "memberId": 1, "nickname": "홍길동", "status": "ACTIVE",
        "joinedAt": "2026-09-30T09:00:00+09:00", "lastLoginAt": "2026-10-01T09:55:00+09:00" }
    ],
    "page": 0, "size": 20, "totalElements": 1
  }
}
```

- 필수 데이터는 회원 ID, 닉네임, 상태, 가입일이고 `lastLoginAt`은 선택 데이터다. 로그인 성공 때마다 갱신하며, 기록이 없으면 `null`이다.
- 성별, 연령대, 동의 상태, 카카오 회원번호는 목록 응답에 내리지 않는다.
- 탈퇴 회원은 서버가 탈퇴 시점에 비식별 처리한 값(닉네임 `탈퇴한 회원`)을 그대로 표시하고 `lastLoginAt`은 `null`이다. 조회 시점에 별도로 마스킹하지 않는다.
- 조건에 맞는 회원이 없으면 `items`는 빈 배열이다.

| 응답 | 코드 | 언제 |
| --- | --- | --- |
| `200` | | 조회 성공 |
| `400` | 공통 검증 오류 | 날짜 형식 오류, `joinedFrom`이 `joinedTo`보다 늦음, `page`가 음수, `size`가 1~100 밖, 허용되지 않는 `status`·`sortBy`·`sortDir` |
| `401` | | 인증되지 않음 |
| `403` | | 관리자 역할이 아님 |

## 관리자 점주 목록 (member 구현 제외)

**2026-10-07 변경:** 아래 내용은 참고용 기존 계약으로 남기되 member 도메인에서 구현하지 않는다. owner 도메인이 store 조회 계약으로 가게 정보를 조합하고, 최종 계약은 owner 도메인이 정한다.

```
GET /v1/admin/owners?status=ACTIVE&joinedFrom=2026-09-01&joinedTo=2026-09-30&keyword=런치&page=0
```

> **페이지 방식:** 사용자 목록과 같은 이유로 `page`를 쓴다(위 「관리자 사용자 목록」의 페이지 방식 주석 참고).

사용자 목록과 같은 규약이며 응답 항목과 검색 대상만 다르다. 점주 1계정은 가게 1개이므로 한 줄이 점주와 가게를 함께 나타낸다.

| 파라미터 | 필수 | 설명 |
| --- | --- | --- |
| `status` | 아니오 | `ONBOARDING`, `ACTIVE`, `SUSPENDED`, `WITHDRAWN`. V51은 활성, 정지, 탈퇴만 적었으나 점주 상태 정의에 `ONBOARDING`이 있어 함께 받는다 |
| `joinedFrom`, `joinedTo` | 아니오 | 가입일(`owner.created_at`) 범위. 사용자 목록과 같은 규칙 |
| `keyword` | 아니오 | 숫자만이면 `ownerId` 일치, 아니면 상호 부분 일치 (제안) |
| `page` | 아니오 | 기본 0. 페이지당 20건 고정. 정렬은 가입일 최신순이고 같으면 `ownerId` 내림차순 |

```json
{
  "code": "SUCCESS",
  "message": "...",
  "data": {
    "items": [
      { "ownerId": 7, "storeName": "런치식당", "status": "ACTIVE", "storeRegistered": true,
        "businessNo": "123-45-*****", "joinedAt": "2026-09-20T10:00:00+09:00", "lastLoginAt": "2026-10-01T09:00:00+09:00" }
    ],
    "page": 0, "size": 20, "totalElements": 1
  }
}
```

| 필드 | 필수 데이터 | 출처 |
| --- | --- | --- |
| `ownerId` | 예 | `owner.owner_id` |
| `storeName` | 예 | 가게 도메인의 `store.name`. 가게를 만들기 전 점주는 `null` |
| `status` | 예 | `owner.status` |
| `joinedAt` | 예 | `owner.created_at` |
| `storeRegistered` | 예 (가게 최종 등록 여부) | `store.finalized`. 가게가 없으면 `false` |
| `businessNo` | 선택 | `store.business_registration_number`를 부분 마스킹. 없으면 `null` |
| `lastLoginAt` | 선택 | `owner.last_login_at` |

- 목록은 점주 계정이 기준이다. 상호와 최종 등록 여부, 사업자등록번호는 가게 도메인 데이터라 점주 도메인이 가게 도메인의 조회 기능을 호출해 채운다. 목록 API는 점주 도메인 패키지에 둔다.
- 이메일, 대표자 성명, 비밀번호 관련 값은 응답에 내리지 않는다.
- 상호로 검색하려면 가게 도메인이 상호 검색 결과의 점주 ID 목록을 돌려주는 조회가 필요하다. 1만 건 기준 1초 이내를 지키려면 목록 한 페이지의 점주 ID를 묶어 한 번에 조회한다.
- 조건에 맞는 점주가 없으면 `items`는 빈 배열이다.

### 탈퇴 점주 표시 (제안)

FR-007은 "탈퇴한 점주는 개인정보를 마스킹한 뒤 목록에 표시"라고만 하고 대상 필드를 정하지 않았다. 사용자와 달리 점주 탈퇴 시점에 비식별 처리하는 절차가 아직 없으므로, 목록 응답을 만들 때 `status`가 `WITHDRAWN`이면 서버가 다음처럼 가린다.

| 필드 | 일반 점주 | 탈퇴 점주 |
| --- | --- | --- |
| `storeName` | 그대로 | 그대로 (사업체 정보이자 V51 필수 표시 항목) |
| `businessNo` | 부분 마스킹 (`123-45-*****`) | 전체 마스킹 (`***-**-*****`) |
| `lastLoginAt` | 그대로 | `null` |

| 응답 | 코드 | 언제 |
| --- | --- | --- |
| `200` | | 조회 성공 |
| `400` | 공통 검증 오류 | 날짜 형식 오류, 기간 역전, `page`가 음수, 허용되지 않는 `status` |
| `401` | | 인증되지 않음 |
| `403` | | 관리자 역할이 아님 |

## 구현 제외

### 회원과 점주 상태 변경 (FR-009, 권장)

권장 우선순위여서 이번 구현 범위에 넣지 않는다. 정지 API가 없으므로 관리자 화면은 정지 버튼을 두지 않는다. 회원 목록의 `SUSPENDED` 필터는 남기지만 지금은 해당하는 회원이 없다. 정지 기능을 다시 채택할 때 정할 서버 쪽 항목은 설계서에 있다.

### 사용자 상세 조회

정지와 강제 탈퇴 판단용으로 제안했던 `GET /v1/admin/members/{memberId}`는 구현하지 않는다.

### 관심 가게 (FR-074, FR-075)

member에서는 만들지 않는다. 광고서빙이 캠페인 단위 찜(`/v1/wishlist`)으로 제공하며 요청과 응답은 `feed-api-spec.md`를 따른다.

# 아직 정해지지 않은 것

| 항목 | 현재 기준 |
| --- | --- |
| 탈퇴 점주 마스킹 대상 | 위 표는 제안이며 `storeName`을 그대로 둘지 확정 필요 |
| 관리자 목록의 탈퇴 시각 표시 | 목록 응답에 `withdrawnAt`이 없음. 필요하면 추가 |
| 탈퇴 회원 쿠폰 즉시 만료 | 쿠폰 도메인과 처리 방식 합의 필요. 정해지기 전까지 탈퇴 회원의 쿠폰 표시는 쿠폰 명세를 따른다 |
| 점주 목록 `keyword`의 상호 검색 | 제공 방식 미정 |

탈퇴 회원 파기 시점, 법정 보존 기간처럼 서버 쪽에서 정할 미정 항목은 설계서에 있다.
