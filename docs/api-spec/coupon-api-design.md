# 쿠폰 API 설계

클라이언트 계약은 [쿠폰 API 명세](./coupon-api-spec.md)를 따른다.
첨부 명세와 합의한 이벤트 스냅샷 방향을 정리한 설계다.
스키마 변경은 쿠폰 도메인의 `V2__coupon_event_snapshot.sql`, 테이블 매핑은 `coupon.entity`의 엔티티 5개에 반영했다. 스냅샷 필드는 `CouponEvent`에 직접 선언한다.
API 처리와 엔티티의 생성·검증·상태 변경 로직은 별도 구현 대상이다.

## 이벤트 스냅샷 저장

`coupon_event`에 스냅샷 컬럼을 직접 추가한다.
발급된 쿠폰은 기존 `coupon_event_id`로 이벤트를 참조하며, 별도 스냅샷 테이블이나 회원별 스냅샷 행을 만들지 않는다.
같은 이벤트에서 발급된 모든 쿠폰이 같은 스냅샷을 공유한다.

| 스냅샷 대상 | 이벤트에 저장할 컬럼 |
| --- | --- |
| 사용 매장 | `store_id`, `store_name` |
| 대표 이미지 | `store_image_object_key`. 이미지가 없으면 `NULL` |
| 할인 조건 | `discount_target_type`, `discount_type`, `discount_value` |
| 대상 메뉴 | `target_menu_id`, `target_menu_name`, `target_menu_price`, `target_menu_discounted_price` |
| 사용 가능 시간 | 기존 `usable_start_at`, `usable_end_at` |

`MENU`이면 메뉴 네 컬럼은 모두 필수이며, `ALL`이면 모두 `NULL`이다.
할인 전·후 가격은 원 단위이며 `0 <= target_menu_discounted_price <= target_menu_price`를 만족한다.
계산 정책을 먼저 확정한 뒤 할인 후 가격까지 스냅샷에 저장한다.
메뉴 할인 계산은 고정된 할인 전·후 가격을 기준으로 하며 원본 가격이나 현재 반올림 정책으로 재계산하지 않는다.
실제 사용 시 확정한 할인액은 `coupon_usage_history.discount_amount`에 보존한다.
지원하는 할인 조합은 메뉴 정률 할인, 메뉴 정액 할인, 전체 주문 정액 할인이다.
전체 주문 정률 할인은 지원하지 않으며 해당 조합으로 쿠폰 이벤트를 생성하지 않는다.
메뉴 수량, 반올림과 할인 상한의 세부 정책은 미확정 업무 정책에서 결정한다.

이벤트 생성 시 campaign·store의 공개 contract로 스냅샷을 준비하고 완성한 행을 INSERT한다.
대상 메뉴가 해당 매장에 속하는지 생성 시 검증하며, 도메인 간 참조에는 FK를 추가하지 않는다.
혜택·사용 시간 스냅샷은 생성 이후 수정하지 않는다. 이후 원본 변경은 새 이벤트에 반영한다.
`created_at`을 이벤트 및 스냅샷 생성 시각으로 사용하며 별도 스냅샷 생성 시각은 두지 않는다.
이벤트 운영 상태의 변경은 스냅샷 변경과 구분한다.

가게명·혜택·메뉴 조회와 QR 사용 계산은 이벤트에 저장한 값을 사용한다.
발급 요청마다 원본 표시 정보를 조회하거나 스냅샷을 새로 생성하지 않는다.
목록은 이벤트를 조인하거나 일괄 조회하여 조립하고, 쿠폰별 원본 도메인 조회가 발생하지 않도록 한다.
매장 관리 권한과 계정 상태는 현재 정보로 검증하며 과거 점주 ID를 스냅샷 인가 기준으로 사용하지 않는다.

대표 이미지에는 URL 대신 객체 키를 저장하고 조회 시 URL을 구성한다.
스냅샷에서 참조하는 객체는 쿠폰 보존 기간 동안 삭제하거나 덮어쓰지 않도록 이미지 소유 도메인과 보존 계약을 맞춘다.
매장 좌표는 이벤트에 저장하지 않으며 위치 검사 시 스냅샷의 `store_id`로 store의 공개 contract를 조회한다.
최소 주문액·안내 문구의 스냅샷 추가 여부는 아직 확정하지 않았다.

기존 `UNIQUE(campaign_id, business_date)`와 `UNIQUE(coupon_event_id, member_id)`를 유지하여 캠페인당 하루 이벤트 한 건과 이벤트당 회원 발급 한 건을 보장한다.
매장별 이벤트 조회를 위해 `(store_id, business_date)` 인덱스를 추가한다.
이 인덱스를 매장당 하루 이벤트 한 건으로 제한하는 UNIQUE로 바꾸지는 않는다.
스키마 변경은 기존 V1 수정이 아닌 새 쿠폰 도메인 마이그레이션으로 반영한다.
기존 데이터의 스냅샷 보완은 아래 정책을 확정한 뒤 적용하며 임의의 기본값이나 현재 원본 값으로 과거 혜택을 채우지 않는다.

## 확정 업무 정책

| 항목 | 정책 |
| --- | --- |
| 할인 조합 | `MENU + PERCENT`, `MENU + AMOUNT`, `ALL + AMOUNT` 지원. `ALL + PERCENT` 제외 |
| 위치 기준 | 이벤트에 좌표를 저장하지 않고 `store_id`로 현재 매장 정보를 조회 |
| 발급 시간 | 시스템에서 정한 발급 시간을 사용하며 쿠폰 사용 가능 시간으로 대체하지 않음 |
| 사용 이력 조회 | 조회 기간의 길이에 상한을 두지 않고 커서 페이지네이션 적용 |
| 점주 상태 | `OWNER` 역할과 현재 `ACTIVE` 상태 모두 요구. 그 외 점주 상태는 `403`이며 상태 오류는 OWNER 도메인이 소유 |
| 오늘 이벤트 조회 대상 | `ACTIVE`, `SCHEDULED` 이벤트만 조회. `PAUSED`, `ENDED` 제외 |
| 과거 가격 | 해당 이벤트 생성 시 확정한 과거 메뉴 가격과 할인 조건을 조회·사용 기준으로 유지. 현재 가격으로 대체하지 않음 |
| 기존 발급 쿠폰 | 캠페인 중단·종료 후에도 원래 사용 가능 시간 안에서 QR 생성·사용 허용. 쿠폰·QR 상태와 현재 계정·매장 권한 검사는 유지 |
| 사용 완료된 QR 재요청 | `409 COUPON-016`, "이미 사용된 쿠폰입니다."로 응답. 기존 성공 결과를 다시 반환하지 않으며 쿠폰 사용과 이력을 추가하지 않음 |
| 회원 상태 검증 | 발급·QR 생성·갱신·새 사용 확정 시 쿠폰 소유 회원의 현재 `ACTIVE` 상태 요구. `SUSPENDED`, `WITHDRAWN`은 거절. 발급은 `403 COUPON-003`, QR 생성·갱신·사용 확정은 `403 COUPON-017` |
| 조회의 usable | `ISSUED`이고 사용 가능 시간 안이면 `true`. 회원 계정 상태는 계산과 목록 필터에 포함하지 않으며 최종 사용 가능 여부는 처리 시 별도 검증 |
| 쿠폰 조회 식별자 | 목록·단건 응답에서 `eventId` 제외. 발급된 쿠폰의 조회·QR 생성·삭제는 `memberCouponId` 사용. 이벤트 스냅샷 연결은 서버 내부에서 유지하며 발급 요청과 이벤트 상태 조회의 `eventId`는 유지 |

## 발급 성능 목표

| 구분 | 기준 |
| --- | --- |
| 총 요청 수 | 50,000건 |
| 유입 구간 | 발급 시작 후 30초 |
| 순간 피크 | 첫 10초 25,000건 = 2,500 RPS |
| 나머지 유입 | 이후 20초 25,000건 = 1,250 RPS |
| HTTP 5xx, 네트워크 드롭 | 0.1% 이하. 혼잡 503도 포함 |
| API P95 | 700ms 이하 |
| API P99 | 1000ms 이하 |
| 중복 발급 | 0건 |
| 1인 일 최대 3건 초과 | 0건 |
| 재고 초과 발급 | 0건 |
| 성공 응답과 DB 발급 건수 불일치 | 0건 |

## 미확정 업무 정책

API 규약에 맞추는 과정에서 정할 수 없는 업무 정책은 구현 전에 별도로 확정한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 메뉴 할인 계산 | 메뉴 수량, 할인 상한, 원 미만 반올림 및 가격을 초과하는 정액 할인 처리. 할인 후 메뉴 가격은 이벤트 생성 전에 계산 정책을 확정하여 저장 |
| 전체 주문 정액 할인과 주문 금액 | 주문 금액이 스냅샷 할인액보다 작은 경우의 사용 허용 여부와 기록할 할인액. 점주 확인으로 처리할지, QR 사용 요청에 주문 금액을 추가해 서버에서 검증·계산할지도 미확정 |
| 최소 주문액·안내 문구 | 최소 주문액 조건과 사용 제한 문구를 쿠폰에서 지원할지, 지원한다면 스냅샷과 조회 응답에 어떻게 보존할지. 최소 주문액은 주문/POS 결제액을 받지 않는 계약에서 점주가 확인할지, 입력 계약을 추가할지 |
| 위치 검사 | 스캔 위치와 매장 간 허용 거리 및 거리 계산 방식. 캠페인의 노출 반경과 쿠폰 사용 반경은 별개로 결정 |
| 시스템 발급 시간·표시 상태 | 시스템의 구체적인 발급 시간 설정값·종료 조건 및 조회 대상 이벤트 상태와 발급 시간 경계가 함께 해당하는 경우의 표시 상태 우선순위 |
| 보관 기간 | 점주 사용 이력과 누적 쿠폰 요약의 보존 방식. API 조회 기간의 길이는 제한하지 않음 |
| 점주 상태 오류 코드 | ACTIVE 외 점주 상태를 거절할 OWNER 오류 코드와 메시지. 허용 상태와 HTTP 403은 확정 |
| 대표 이벤트 | 같은 매장에 ACTIVE·SCHEDULED 상태의 오늘 이벤트가 여러 건일 때 한 항목을 선택하는 우선순위와 동점 기준 |
| 기존 쿠폰 보완 | 기존 이벤트의 과거 정보 복원을 위한 데이터 출처와 보완 방법. 기준은 과거 가격이며 현재 값을 대신 채우지 않음 |

## 구현 정합성 확인

- 공통 응답은 `ResponseEnvelope`, 커서 목록은 `CursorPageResponse`를 재사용한다.
- 오류는 `CouponErrorCode`와 `CouponException`으로 정의하고 기존 `GlobalExceptionHandler`를 사용한다.
- COUPON 코드, 상태, 메시지는 명세의 오류 표와 일치시킨다. STORE 오류는 store 도메인 소유다.
- 스냅샷 생성 시 campaign·store의 공개 contract를 사용한다. 찜과 현재 계정·매장 관리 권한의 검증도 소유 도메인의 contract를 사용하며 다른 도메인의 엔티티나 repository를 직접 참조하지 않는다.
- 회원 상태는 member의 공개 contract로 DB 현재 상태를 확인한다. 인증 토큰의 과거 상태나 조회 시점의 `usable`로 대체하지 않는다. 점주가 호출하는 QR 사용에서도 쿠폰 소유 회원을 기준으로 확인한다. 회원 상태에 `ONBOARDING`은 없으며 온보딩 완료 여부는 별도 정보다.
- 스냅샷이 준비되지 않은 이벤트는 발급을 열지 않는다. 이후 발급·조회·사용에서 현재 원본 값으로 대체하지 않는다.
- 재고, 일일 한도, 중복 발급, QR 단일 사용은 동시 요청에서도 불변식을 지켜야 한다.
- QR 사용, 삭제, 갱신은 쿠폰 상태와 QR 버전을 검사해 직렬화한다.
- 새 QR 사용 확정 시 쿠폰 잠금을 확보한 뒤 서버 시계에서 현재 시각을 한 번 읽는다. 이 시각으로 QR과 쿠폰의 유효 시간을 검사하고 사용 이력의 `useTime`에도 동일하게 반영한다.
- 사용 완료된 QR의 식별용 해시와 쿠폰·사용 이력의 연결을 사용 이력 보존 기간 동안 유지한다. 원문 QR 토큰은 로그에 남기지 않는다. 인증과 현재 매장 관리 권한 검증 후 사용 완료 여부를 QR 만료 검사보다 먼저 확인하여 재요청을 `COUPON-016`으로 구분한다.
- 미사용 쿠폰 삭제는 `REMOVED` 상태로 보존하며 쿠폰 행과 발급 횟수, 중복 발급 기록을 유지한다.
- 경로, 필드, 상태 코드, 시간대, 삭제 멱등성, 커서 동점 정렬과 필터 변경 시 초기화 규칙, 오류 카탈로그와 스냅샷 표시·사용 기준의 일치를 계약 검증에 포함한다.
- 공통 README의 타입 변환·필수 쿼리 누락 오류 설명은 현재 `GlobalExceptionHandler`와 쿠폰 명세의 `COMMON-003` 정의에 맞춰 정리해야 한다.
- 쿠폰 API는 별도 구현 대상이다. 오류 enum과 문서 카탈로그 검증도 API 구현 시 함께 반영한다.
