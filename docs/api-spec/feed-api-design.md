# 광고 서빙 (adserving) API 설계

광고 서빙 API를 서버가 어떻게 처리하는지와 그렇게 정한 이유를 적는다. 요청, 응답, 오류는 명세서 `feed-api-spec.md` 에 있고 여기서는 반복하지 않는다.
명세서는 프론트가 보는 계약이고, 이 문서는 백엔드가 구현할 때 보는 문서다. 계약이 바뀌면 명세서를, 내부만 바뀌면 이 문서를 고친다.

| 근거 | 기준 |
|---|---|
| 요구사항 | 명세서 V51 기능 30, 67~71, 74~76, 92, 96~97, 99~100행. 비즈니스 규칙의 공정성 절 |
| 저장 구조 | `db/migration/adserving/` 의 `V1`, `V2`: `ad_candidate`, `serve_log`, `impression_log`, `swipe_log`, `wishlist`, `feed_filter`, `feed_filter_category`, `feed_visit_daily`. 공통 DDL 규약은 같은 폴더의 `README.md` |
| 설계 | `../architecture/런치캐치_도메인_구조와_의존성_설계.md` 1.3, 2.2, 2.4 |

## 목록과 요구사항 행

| 메서드 | 경로 | 행 |
|---|---|---|
| `GET` | `/v1/feed` | 67, 96, 97, 99 |
| `POST` | `/v1/swipes` | 68 |
| `POST` | `/v1/impressions` | 69, 100 |
| `GET`, `PUT` | `/v1/feed-filter` | 70 |
| `GET` | `/v1/wishlist` | 75, 74 |
| `POST` | `/v1/wishlist` | 74 |
| `DELETE` | `/v1/wishlist/{campaignId}` | 76 |
| `GET` | `/v1/admin/feed-diagnosis/feeds` | 30 |

가게 추천 차단(71, 92행)과 캠페인 기준 진단(30행 후반)은 저장 구조에 근거가 없어 경로를 적지 않았다. `아직 정해지지 않은 것`에 남겼다.

**경로 이름.** `/v1/feed` 와 `/v1/feed-filter` 는 단수다. 사용자당 하나뿐인 리소스라 목록이 없다(`feed_filter` 의 PK 가 `member_id` 하나다).
그래서 필터 저장도 항목 추가가 아니라 전체 교체인 `PUT` 이다. `/v1/wishlist` 는 README 의 경로 절이 예시로 쓰는 표기를 따른다.

## 성능 목표

| API | 목표 TPS | 응답 지연 시간 | 에러율 | 근거 |
|---|---|---|---|---|
| `GET /v1/feed` | 500 | p99 500ms | 0.1% 미만 | 피크 동시 접속 5,000명(비기능 11행) x 최근 60초 6회 제한(67행) / 60초 = 500이 상한 |
| `POST /v1/swipes` | 5,000 | p99 300ms | 0.1% 미만 | 피드 1회에 카드 10장. 500 x 10 = 5,000 |
| `POST /v1/impressions` | 10,000 | p99 200ms | 0.1% 미만 | 비기능 13행. 에러율은 노출 유실률 목표(비기능 18행)와 맞춘다 |
| `GET /v1/wishlist` | 500 | p99 300ms | 0.1% 미만 | 10:50~11:00에 5,000명이 10초 안에 몰린다고 본다 |
| `POST`, `DELETE /v1/wishlist` | | | 0.1% 미만 | 가게 상세의 찜과 삭제 |
| `GET`, `PUT /v1/feed-filter` | | | 0.1% 미만 | 설정 화면 |
| `GET /v1/admin/feed-diagnosis/feeds` | | | 1% 미만 | 관리자 조회 |

**에러율은 서버 오류(5xx)와 시간 초과만 센다.** 입력 오류(4xx)와 속도 제한(`429`)은 의도한 거부라 뺀다.
`429` 를 넣으면 제한이 잘 작동할수록 에러율이 오른다. 운영 알림 기준(비기능 40행, 노출 수집 오류율 1% 초과)은 목표와 따로 둔다.
**목표 TPS와 응답 지연 시간은 트래픽이 많이 몰리는 API 넷에만 둔다.** 나머지는 에러율만 본다. 검증은 k6 시나리오(10:00~12:59, 특히 10:50~11:05)로 한다.

## `GET /v1/feed`

**서버가 하는 일**

1. 그날의 후보 스냅샷(`ad_candidate`)에서만 후보를 찾는다. 서빙 중에 다른 도메인 테이블을 읽지 않는다(96행)
2. 배분 3장(1, 4, 7번)은 예산 소진 진행률 오름차순, 관련성 7장은 관련성 점수(거리 45, 카테고리 선호도 35, 할인 20) 순이다(96, 97, 99행). 예산 소진 진행률이 1.2를 넘거나, 그날 유효 노출 수가 노출 상한(그날 예약액 / 그날 단가 x 1.05)에 닿은 캠페인은 두 슬롯 모두에서 뺀다(99행). 진행률, 그날 예약액, 단가는 정산의 `BudgetQueryService`로 읽고, 유효 노출 수는 광고 서빙이 자기 노출 로그로 센다. 예산에 닿은 뒤 상한까지 들어온 노출은 과금하지 않는다(`NOT_BILLED_BUDGET`, 103행)
3. 피드 필터의 카테고리는 10장 전부에, 정렬은 관련성 7장에만 적용한다(70행)
4. 같은 사용자에게 같은 캠페인은 하루 2회, 한 세션 1회까지만 내려준다. 30분 활동이 없으면 새 세션이다(비즈니스 규칙)
5. 찜한 캠페인과 패스한 캠페인은 사용자 당일 이력으로 뺀다. 이력은 00:00에 초기화된다(102행 (9), 비즈니스 규칙 43행)
6. 카드마다 serve 기록을 인메모리 캐시(TTL 30분)에 쓰고, 응답 뒤 `serve_log` 와 그날 첫 요청 위치(`feed_visit_daily`)를 비동기로 쓴다

**정한 이유**

- **위치를 보내지 않으면 저장 위치를 쓴다.** 67행 "위치 획득에 실패하면 마지막 수동 입력 위치 사용"
- **응답의 `radiusM` 은 캠페인의 노출 반경과 다른 값이다.** 탐색 반경은 1000, 2000, 3000, 5000 으로 넓혀 가고(67행 반경 확장), 캠페인이 지정하는 노출 반경은 `ad_candidate.target_radius` 의 500, 1000, 2000, 3000 이다. 단위가 같고 이름이 비슷해 `target_radius` 를 그대로 내려주기 쉬운데, 그러면 명세에 없는 `500` 이 나간다. 시간대 밖에는 후보를 찾지 않아 반경이 없어 `null` 이다
- **"광고" 라벨을 서버가 내려주지 않는다.** 모든 카드가 광고라 표시광고법상 항상 표시해야 한다(67행). 서버가 켜고 끌 값이 없다
- **슬롯 유형과 배정 근거는 응답에 싣지 않는다.** 클라이언트가 쓸 곳이 없고, 배정 방식이 드러나면 공정성 정책을 거꾸로 이용할 수 있다. serve 기록(`serve_log`)에만 남겨 관리자 진단에서 본다
- **잔여 수량을 싣지 않는다.** 쿠폰이 소유한 값이라 광고 서빙이 읽으면 도메인 간 순환이 생긴다. 소진되면 쿠폰이 `CandidateStateUpdater` 로 알려 후보에서 뺀다
- **포스터는 HTML이 아니라 주소로 준다.** 카드 10장마다 포스터 본문을 실으면 응답이 무거워지고 캐시를 쓸 수 없다. 피드에 나오는 캠페인은 활성화를 마친 캠페인이고, 활성화 뒤에는 포스터를 고칠 수 없어(55행) 같은 주소는 항상 같은 포스터다. 그래서 주소에 버전을 붙이지 않고 `ad_candidate` 에 주소를 저장하지도 않는다. `campaignId` 로 만든다

**요청 제한 구현**

- 사용자마다 최근 60초 안의 요청 시각을 Valkey에 두고 센다. 분 단위 고정 창으로 세면 경계에서 두 배까지 받거나 `Retry-After` 가 들쭉날쭉해진다
- `Retry-After` = 가장 오래된 요청 시각 + 60초 - 지금(올림). `nextFeedAvailableAt` 도 같은 계산이다
- 거부된 요청은 횟수에 넣지 않는다. 넣으면 알려 준 시각에 다시 요청해도 또 거부될 수 있다
- IP 기준 제한은 두지 않는다. 공용 네트워크(회사, 학교)에서 여러 사용자가 한 IP를 쓴다(67행)

## `POST /v1/swipes`

- 중복 키는 `(serveId, 요청 사용자)` 다(68행, `swipe_log` PK). 다른 사용자가 같은 `serveId` 로 보낸 스와이프는 그 사용자의 기록으로만 남고 원래 사용자의 스와이프를 막지 않는다
- `WISH` 면 `wishlist` 에 넣는다. 이미 있으면 그대로 둔다(`wishlist` UNIQUE)
- 기록은 30일 관련성 카테고리 선호도에 쓰이고, 분석에는 `SwipedEvent` 로 비동기 전달된다

## `POST /v1/impressions`

**서버가 하는 일**

1. serve 기록이 캐시에 있는지 본다. 없으면 `EXPIRED_OR_UNKNOWN`
2. serve 기록의 사용자와 요청 사용자가 같은지 본다. 다르면 `NOT_OWNER`
3. 유효하면 한 트랜잭션 안에서 `impression_log` 에 저장하고, 처음 저장된 유효 노출이면 정산의 `PointDeductor` 로 노출 차감을 부른다. 그날 후보가 쿠폰 소진이면 차감을 부르지 않고 `sold_out` 으로 적는다(`NOT_BILLED_SOLD_OUT`)
4. 과금 판정(`BILLED`, `NOT_BILLED_BUDGET`, `NOT_BILLED_PAUSED`)은 정산이 자기 기록(`deduction_result`)에 남긴다(103행). 노출 저장, 판정, 원장이 함께 커밋된 뒤 응답하고, 실패하면 함께 롤백된다. 무효 노출도 사유와 함께 저장하고 차감은 부르지 않는다

**정한 이유**

- **과금 상태는 응답에 싣지 않는다.** 점주의 과금 정보라 사용자에게 줄 이유가 없다. 미과금 노출도 유효 노출이다
- **중복 키는 `(serveId, 요청 사용자)` 다**(100행, `impression_log` PK). 다른 사용자가 먼저 보낸 무효 노출이 원래 사용자의 유효 노출을 막지 못한다
- **`202` 를 쓴다.** 서버는 처리를 끝내고 판정을 돌려주지만, 클라이언트는 화면을 벗어나며 보낸 요청의 응답을 받지 못할 수 있어 응답에 의존하지 않는다(100행)
- **`invalidReason` 은 유효면 `null` 이다.** 사유는 무효일 때만 뜻이 있다. `impression_log.invalid_reason` 도 같은 규칙이라 `invalid_reason IS NOT NULL` 이 곧 무효 노출이다
- 요청이 많아지면 여러 건을 묶어 받는 방식으로 바꿀 수 있고, 검증과 중복 처리는 같다(100행)

## `GET`, `PUT /v1/feed-filter`

- `categories` 의 빈 배열을 전체 업종으로 읽는다(70행 예외). "아무것도 고르지 않음"을 따로 둘 이유가 없다
- 필터는 `feed_filter`(정렬)와 `feed_filter_category`(업종)에 나눠 저장하고, `PUT` 은 둘을 한 트랜잭션에서 통째로 바꾼다

## `GET`, `POST`, `DELETE /v1/wishlist`

- **잔여 수량과 발급 가능 여부를 광고 서빙이 합쳐 주지 않는다.** 광고 서빙이 쿠폰을 부르면, 쿠폰이 발급 자격 확인을 위해 이미 광고 서빙의 찜 여부를 읽고 있어(83행) 도메인 간 순환이 생긴다(75행). 클라이언트가 화면에서 합친다
- `storeName`, `storeImageUrl`, `discount` 는 그날 후보 스냅샷(`ad_candidate`)에서 채운다. 스냅샷에 없는 캠페인이면 `null` 이다. 대표 이미지는 가게 이미지 중 LOGO다
- `wishedAt` 은 `wishlist.created_at` 이다. 찜할 때 행을 만들고 취소하면 행을 지우므로 둘이 같다
- 페이지네이션을 두지 않는다. 찜은 캠페인이 끝나면 `CampaignEndedEvent` 로 자동으로 빠지므로 진행 중인 캠페인 수만큼만 쌓인다
- `POST` 의 중복 키는 `(사용자, 캠페인)` 이다(`wishlist` UNIQUE)
- `DELETE` 뒤 10:50 알림 대상에서 빠지는 것은 따로 처리할 것이 없다. 알림이 10:50에 찜 목록을 읽어 보낸다(76행)

## `GET /v1/admin/feed-diagnosis/feeds`

- `cards` 는 `serve_log`, `settings` 는 그 시각에 적용된 플랫폼 설정값 이력에서 읽는다
- 기록이 없으면 오류가 아니라 `found: false` 로 돌려준다(30행 예외)

## 다른 도메인에 공개한 기능

HTTP가 아니라 도메인 contract의 Java 클래스로 노출한다. 클라이언트는 쓰지 않는다.

| 공개 항목 | 쓰는 도메인 | 하는 일 |
|---|---|---|
| `WishlistQueryService` | coupon, notification | 찜 여부(83행 발급 자격), 그날 서빙 가능한 캠페인을 찜한 사용자(79행 10:50 발송 대상) |
| `CandidateStateUpdater` | coupon | 선착순 소진 시 그날 후보에 소진 표시(96행) |
| `ImpressionServedEvent`, `SwipedEvent` | analytics | 전환 퍼널 기록(impression, wish, pass). 비동기 |

## 오류 코드를 나눈 기준

**판정에 업무 지식이 필요 없는 실패는 공통 코드를 쓴다.** 필수값 누락, 좌표 범위, `action` 과 정렬 값과 업종 코드 같은 고정 값, `serveId` 형식,
둘 중 하나는 있어야 하는 조건은 요청 타입의 애노테이션이 판정하므로 `COMMON-002` 로 온다.
`ADSERVING-` 코드는 후보, 사용자 상태, 정책을 봐야 판정할 수 있는 실패에만 둔다.

## 명세서를 나누며 새로 적은 것 (확인 필요)

이전 문서에 없던 값이라 명세서에 적으면서 정했다. 다르면 명세서와 함께 고친다.

| 위치 | 적은 내용 | 근거 |
|---|---|---|
| `GET /v1/feed` `latitude`, `longitude` | 범위 -90 ~ 90, -180 ~ 180 | 좌표 범위 오류가 `COMMON-002` 라고만 적혀 있었다 |
| `GET /v1/feed` `nextFeedAvailableAt` 예시 | 응답 시각과 같은 값으로 바꿨다 | 첫 요청이면 바로 다음 요청이 가능하다 |
| 진단 `slotType` | `ALLOCATION`, `RELEVANCE` | 이전 예시에 `ALLOCATION` 만 있었다 |
| 진단 `found: false` | `feedId`, `memberId`, `servedAt`, `settings` 는 `null`, `cards` 는 빈 배열 | 이전 문서는 `found` 만 적었다 |
| `POST /v1/wishlist` 오류 | `400 COMMON-002`(`campaignId` 누락) 추가 | 다른 API와 같은 규칙 |

## 아직 정해지지 않은 것

| 항목 | 요구사항 | 현재 스키마 또는 명세 |
|---|---|---|
| 가게 추천 차단과 차단 목록 | 71, 92행(권장). 96행 후보 조건 "차단 가게 아님" | 차단 목록 테이블이 없다. 후보 조건 하나가 근거 없이 남아 있다 |
