# 런치캐치 알림 운영

| 항목 | 내용 |
|---|---|
| 목적 | 깃허브 활동과 배포 결과를 Slack 으로 알리는 구성과 설정 절차를 한곳에 둔다 |
| 근거 | 리뷰 대기로 막힌 PR 이 쌓이는 문제. 리뷰어로 등록된 사실을 본인이 모르는 것이 원인이다 |
| 관련 문서 | `런치캐치_도메인_구조와_의존성_설계.md` 2.2(담당자별 도메인), `../code-convention/build-gate-guideline.md`(차단 게이트는 G-BUILD 하나뿐이다) |

## 1. 무엇을 누가 알리나

| 알리는 것 | 보내는 주체 | 형태 | 멘션 |
|---|---|---|---|
| 리뷰어로 등록됨 | `.github/workflows/slack-notify.yml` | 채널 글 | **등록된 리뷰어** |
| 새 이슈 | GitHub 공식 Slack 앱 (`issues`) | 채널 글 | 없음 |
| PR 열림과 병합 | GitHub 공식 Slack 앱 (`pulls`) | 채널 글 | 없음 |
| PR 리뷰와 승인 | GitHub 공식 Slack 앱 (`reviews`) | 채널 글 | 없음 |
| 배포 성공과 실패 | `.github/workflows/deploy.yml` | 채널 글 | 없음 |

멘션이 붙는 것은 리뷰 요청 하나다. 나머지는 알고만 있으면 되는 정보다. 멘션을 전부 붙이면 멘션이 의미를 잃는다.

## 2. 왜 둘로 나뉘나

공식 Slack 앱이 코드 0 줄로 이슈와 PR 과 리뷰를 다 덮는다. 유지할 것이 없으니 덮이는 칸은 전부 앱에 맡긴다.

**앱이 못 하는 칸이 하나 있다.** 리뷰 요청을 채널로 보내는 구독 옵션이 없다. 앱은 이것을 개인 DM 으로만 보내고, DM 은 각자 `/github signin` 을 한 사람에게만 간다. 한 명이 안 하면 그 사람만 조용히 못 받고, 본인도 못 받는다는 사실을 모른다. 확인할 방법이 없는 설정은 설정이 아니다.

그래서 그 칸만 워크플로가 메운다. 멤버 ID 맵은 저장소에 한 번 넣으면 끝이고, 누가 빠졌는지는 맵을 보면 바로 보인다.

## 3. Slack 앱 설정

### 3.1 워크스페이스에 설치 (1회, 관리자)

Slack 아무 채널에서 `/github` 를 치면 설치 안내가 뜬다. 또는 Slack App Directory 에서 `GitHub` 검색 후 **Add to Slack**. 워크스페이스 정책에 따라 관리자 승인이 필요하다.

### 3.2 계정 연결 (각자 1회)

```
/github signin
```

채널 글만 받으면 안 해도 되지만, 비공개 저장소를 구독하거나 개인 DM 을 받으려면 필요하다. 지금 `lc-backend` 는 public 이라 구독 자체에는 필요하지 않다.

### 3.3 채널 구독

```
/github subscribe lunch-catch/lc-backend
/github subscribe lunch-catch/lc-backend reviews
```

`reviews` 는 기본으로 꺼져 있어 따로 켠다. 이것이 PR 승인 알림이다.

### 3.4 시끄러운 것 끄기

```
/github unsubscribe lunch-catch/lc-backend commits deployments
```

| 기능 | 끄는 이유 |
|---|---|
| `commits` | 기본 브랜치 push 마다 찍힌다. 릴리스 머지 알림과 중복이다 |
| `deployments` | `deploy.yml` 이 이미 Slack 으로 보낸다 |

**`workflows` 를 켜지 마라.** 그것이 G-BUILD 와 SonarCloud 같은 CI 결과 알림이고 기본으로 꺼져 있다. 켜면 PR 마다 push 마다 찍혀서 채널이 체크 결과로 덮이고, 리뷰 요청 멘션까지 묻힌다.

기능 이름은 공식 문서가 정한 것만 쓴다. 없는 이름을 주면 Slack 이 에러를 낸다.

| 기본 | 기능 |
|---|---|
| 켜짐 | `issues`, `pulls`, `commits`, `releases`, `deployments` |
| 꺼짐 | `workflows`, `reviews`, `comments`, `branches`, `commits:*`, `discussions`, `+label:"..."` |

### 3.5 확인

```
/github subscribe list features
```

## 4. 워크플로 설정

`slack-notify.yml` 이 쓰는 시크릿 두 개다. **둘 다 없으면 경고만 남기고 통과한다.** PR 병합은 막히지 않는다.

### 4.1 `SLACK_WEBHOOK_ACTIVITY`

Slack 에서 Incoming Webhook 을 만들어 그 URL 을 넣는다. 알림 채널은 Slack 앱을 구독한 채널과 같은 곳으로 둔다.

셸 이력에 URL 이 남지 않게 표준입력으로 넣는다. `gh secret set --body` 를 쓰면 이력 파일에 평문으로 남는다.

```bash
umask 077 && cat > "$TMPDIR/wh"   # URL 붙여넣고 Ctrl+D
gh secret set SLACK_WEBHOOK_ACTIVITY < "$TMPDIR/wh"
rm -P "$TMPDIR/wh"                # GNU 환경이면 shred -u
```

### 4.2 `SLACK_MEMBER_IDS`

깃허브 로그인을 Slack 멤버 ID 로 잇는 JSON 객체다. 멤버 ID 는 Slack 프로필의 `...` > `멤버 ID 복사` 로 얻는다.

```json
{
  "devjohnpark": "U01...",
  "muzimzz": "U02...",
  "yongmaru789": "U03...",
  "MinhyeokChoi99": "U04...",
  "gyudongjeong": "U05..."
}
```

맵에 없는 사람은 멘션 없이 `@로그인` 글자로 적힌다. 멘션은 안 되지만 누구인지는 보이므로 일부만 넣고 시작해도 된다.

**변수가 아니라 시크릿에 넣는다.** 이 저장소는 public 이라 Actions 로그도 공개되는데 변수는 마스킹되지 않는다. 자격증명은 아니지만 공개 로그에 흘릴 이유가 없다.

### 4.3 사람이 바뀌면

담당자가 바뀌면 이 맵과 `.github/CODEOWNERS` 를 함께 고친다. CODEOWNERS 가 리뷰어를 지정하고 이 맵이 그 사람을 Slack 에서 찾으므로, 한쪽만 고치면 알림이 `@로그인` 글자로 떨어진다.

## 5. 배포 알림

`deploy.yml` 이 `SLACK_WEBHOOK_DEPLOY` 를 쓴다. **아직 등록되어 있지 않아 지금은 조용히 건너뛰는 중이다.** 같은 웹훅을 재사용하거나 배포용 채널을 따로 둘 수 있다. 등록 방법은 4.1절과 같다.

알림 실패가 배포 결과를 바꾸지 않는다 (BLD-2-05). 성공한 배포가 실패로 보이면 재실행하게 되고, ECR 이 IMMUTABLE 이라 같은 태그를 다시 밀다 막힌다.

## 6. 설정을 바꿀 때 알아야 하는 것

**이벤트 값을 셸에 끼워 넣지 않는다.** PR 제목에 `$(...)` 나 역따옴표가 들어오면 러너에서 실행된다. `jq` 가 `$GITHUB_EVENT_PATH` 를 직접 읽게 해서 셸을 아예 거치지 않는다. 메시지를 고칠 때 `${{ github.event... }}` 를 `run` 안에 쓰면 이 보호가 깨진다.

**페이로드를 출력하지 않는다.** 공개 로그에 Slack 멤버 ID 가 남는다. 디버깅할 때 `set -x` 나 `echo "$PAYLOAD"` 를 넣었다면 지우고 올린다.

**`permissions: {}` 를 유지한다.** 이 워크플로는 이벤트 페이로드만 읽고 저장소에 접근하지 않는다. 권한을 열면 공개 저장소에서 토큰이 하는 일이 늘어난다.

**트리거를 `pull_request` 밖으로 넓힐 때는 기본 브랜치를 본다.** `issues` 와 `pull_request_review` 같은 이벤트는 **기본 브랜치의 워크플로만** 돈다. 기본 브랜치는 `develop` 이라 `develop` 에 병합하면 동작한다. `pull_request` 는 PR 의 머지 ref 에 있는 워크플로가 돌아서 기본 브랜치와 무관하다.

**포크 PR 에서는 알림이 꺼진다.** 시크릿이 전달되지 않아 웹훅이 비고, 그러면 경고만 남기고 통과한다. 팀원은 모두 이 저장소의 브랜치로 작업하므로 실사용 경로에는 영향이 없다. `pull_request_target` 으로 바꿔 시크릿을 받으려 하지 말 것. 신뢰할 수 없는 코드에 시크릿을 노출하는 경로다.

**리뷰어가 여럿이면 사람마다 한 번씩 온다.** `contract/` 변경은 CODEOWNERS 가 호출자까지 리뷰어로 붙이므로 메시지가 넷까지 간다. 각자 다른 사람을 멘션하므로 중복은 아니다.

## 7. 승인 알림에 멘션이 필요해지면

지금 승인은 Slack 앱이 채널 글로만 알린다. PR 작성자가 "이제 병합할 수 있다" 를 모르고 지나가는 일이 반복되면, 그 칸을 워크플로로 옮긴다. 둘을 같이 켜면 중복이므로 **앱 쪽을 먼저 끈다.**

```
/github unsubscribe lunch-catch/lc-backend reviews
```

그리고 `slack-notify.yml` 에 트리거와 분기를 되살린다.

```yaml
on:
  pull_request:
    types: [review_requested]
  pull_request_review:
    types: [submitted]

jobs:
  notify:
    if: >-
      github.event_name == 'pull_request'
      || github.event.review.state == 'approved'
```

`jq` 쪽에는 `$GITHUB_EVENT_NAME` 을 `--arg name` 으로 넘기고 분기를 하나 더 둔다. 승인은 PR 작성자를 멘션한다.

```
"[승인] \(link($ev.pull_request)) 를 \($ev.review.user.login) 가 승인했다. \(ping($ev.pull_request.user.login))"
```

`pull_request_review` 는 기본 브랜치의 워크플로만 돈다. 기본 브랜치가 `develop` 이라 `develop` 병합으로 동작한다.
