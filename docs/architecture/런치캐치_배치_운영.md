# 런치캐치 배치 운영

| 항목 | 내용 |
|---|---|
| 목적 | 배치 서버를 띄우고 운영하는 규칙을 한곳에 둔다 |
| 근거 | 명세서 V51 기능 102행(하루 시간표 스케줄러), 구현 방식 시트의 102행 항목과 비즈니스 규칙 27행 항목, ERD `batch_execution_log` |
| 관련 문서 | `런치캐치_도메인_구조와_의존성_설계.md` 2.1 규칙 6(스케줄러 책임), 2.4(배치를 별도 jar로 떼지 않는 이유) |

## 1. 서버 구성

배치 서버는 별도 코드가 아니라 같은 jar를 `batch` 프로필로 띄운 서버다. API 서버 N대는 기본 프로필로, 배치 서버 2대는 `spring.profiles.active=batch`로 배포한다. `application-batch.yml`에만 `launchcatch.scheduler.enabled: true`를 두고, 스케줄러 설정 클래스(`global.config.SchedulingConfig`)는 `@ConditionalOnProperty`로 이 값이 true일 때만 뜬다. `@EnableScheduling`은 메인 클래스가 아니라 이 설정 클래스에만 둔다. 각 도메인의 `job/` 클래스는 어느 서버에나 들어 있지만, 스케줄러가 없는 서버에서는 실행되지 않는다. 장애 대응 중 자동 실행을 멈출 때는 프로필은 그대로 두고 환경변수 `LAUNCHCATCH_SCHEDULER_ENABLED=false`로 끈다.

```java
@Configuration
@ConditionalOnProperty(name = "launchcatch.scheduler.enabled", havingValue = "true")
@EnableScheduling
public class SchedulingConfig {
}
```

스케줄러 자체는 여기서 `@Bean`으로 만들지 않는다. `ops/job/DailyJobScheduler`의 `@Component`다. 어느 서버에나 들어 있고, `@EnableScheduling`이 없는 서버에서는 `@Scheduled`가 붙은 메서드가 돌지 않는다.

그 클래스는 저장소를 직접 받지 않고 `BatchExecutionService`를 받는다. `job/`은 Entry 계층이고 Repository는 Service만 쓸 수 있어서, 저장소를 주입받으면 `계층_의존_규칙`이 떨어진다.

## 2. 두 서버를 함께 쓰는 규칙

두 배치 서버는 모두 스케줄러를 켜고 같은 시각에 작업을 시도한다(액티브-액티브). 한쪽만 켜 두면 00:00에 장애가 났을 때 사람이 전환해야 하기 때문이다.

| 항목 | 규칙 |
|---|---|
| 중복 실행 | 작업 시작 시 `batch_execution_log`에 RUNNING 행을 먼저 넣는다. UNIQUE (job_name, business_date)에 걸리면 실행하지 않는다 |
| 00:00 묶음 | (1)~(10)은 `DAILY_0000` 행 하나로 점유한다. 점유한 서버가 단계를 차례로 실행하고, 단계마다 자기 job_name으로 행을 남긴다. 점유에 실패한 서버는 묶음 전체를 건너뛴다. 단계마다 따로 점유하면 앞 단계가 끝나기 전에 다른 서버가 뒤 단계를 실행할 수 있다 |
| 생존 신호 | 실행 중인 서버는 별도 스레드에서 30초마다 자기 행의 `updated_at`을 갱신한다. 갱신은 `owner_id`가 자기일 때만 하며, 0건이면 이미 넘겨받은 것이므로 다음 단계로 가지 않고 멈춘다 |
| 이어받기 | 다른 서버는 1분마다 RUNNING이면서 `updated_at`이 2분보다 오래된 행을 찾아 조건부 UPDATE로 `owner_id`를 바꾼다. 1건이 바뀐 서버만 이어받는다. 00:00 묶음은 SUCCESS가 아닌 첫 단계부터 다시 실행한다. 모든 작업이 멱등이라 겹쳐 실행된 단계가 있어도 결과는 같다. 이어받은 사실은 관리자에게 알린다 |
| 실패 | FAILED는 자동으로 다시 실행하지 않는다. 관리자에게 알리고, 관리자가 같은 (작업명, 영업일)로 수동 재실행한다. 재실행은 새 행을 넣지 않고 기존 FAILED 행을 RUNNING으로 되돌리며 `finished_at`과 `failure_reason`을 비우고 `owner_id`를 실행하는 서버로 바꾼다. 이 UPDATE도 status가 FAILED일 때만 걸리게 해 두 번 눌러도 한 번만 실행된다 |
| 하루 한 번이 아닌 작업 | 캠페인별 사용 종료 시각마다 도는 쿠폰 만료는 job_name에 캠페인 id를 붙여 같은 키로 막는다 |
| 설정값 | 영업일 경계 작업은 Caffeine 캐시를 거치지 않고 실행 시점의 값을 DB에서 읽는다. 서버마다 최대 5분까지 다른 값을 볼 수 있기 때문이다 |
| 시각 | 두 서버는 NTP로 시계를 맞추고, 영업일은 Asia/Seoul 기준으로 판단한다 |
| 장애 | 배치 서버가 모두 멈춰도 피드, 노출 차감, 쿠폰 발급은 API 서버에서 계속 처리된다 |

```java
@Modifying
@Query("""
    UPDATE BatchExecutionLog l
       SET l.ownerId = :me, l.updatedAt = :now
     WHERE l.jobName = :jobName AND l.businessDate = :date
       AND l.status = 'RUNNING' AND l.updatedAt < :staleBefore
    """)
int takeOver(String jobName, LocalDate date, String me,
             LocalDateTime now, LocalDateTime staleBefore);
```

## 3. 구현

2장의 규칙은 `ops` 가 갖는다. 작업 내용은 각 도메인이 `ops.scheduler.DailyJob` 을 구현해 등록한다(설계 문서 규칙 6).

| 규칙 | 어디 |
|---|---|
| 중복 실행 차단 | `BatchExecutionService.claim`. `batch_execution_log` 의 유일 제약 위반을 "이미 점유됐다" 로 읽는다 |
| 00:00 묶음 점유와 단계 진행 | `DailyJobScheduler.runDailyBundle`, `runStep` |
| 생존 신호 | `DailyJobScheduler.sendHeartbeat` -> `BatchExecutionService.renewOwned`. 단계마다 `renew` 로 점유를 다시 확인하고 0건이면 멈춘다 |
| 이어받기 | `DailyJobScheduler.takeOverStale` -> `BatchExecutionService.takeOverStale`. 찾은 뒤 조건부 UPDATE 로 한 번 더 판정해 1건을 받은 서버만 이어받는다 |
| 실패와 수동 재실행 | `BatchExecutionService.fail`, `retry`. `retry` 는 상태가 `FAILED` 일 때만 걸려 두 번 눌러도 한 번만 실행된다 |
| 관리자 알림 | `BatchAlert`. 알림 채널이 생기면 알림 도메인이 구현해 `@Primary` 로 올린다. 그때까지는 `LoggingBatchAlert` 가 로그로 남긴다 |

판정은 모두 조건부 UPDATE 로 두고 바뀐 행 수를 본다. 읽고 나서 판단하면 두 서버가 같은 상태를 읽고 둘 다 자기 것이라고 믿는 구간이 생긴다.

### 돌려 보고 알게 된 것

* **스케줄러 스레드 풀이 1이면 생존 신호가 돌지 않는다.** 묶음이 그 하나를 붙잡고 있어서, 멀쩡히 일하는 서버의 행이 2분 뒤 멈춘 것으로 보여 다른 서버가 빼앗는다. `application-batch.yml` 이 `spring.task.scheduling.pool.size` 를 4로 둔다
* **감사 시각의 시간대를 고정해야 한다.** 기본 제공자는 JVM 기본 시간대로 `created_at` 을 넣는데, 애플리케이션은 `Clock`(Asia/Seoul)으로 `finished_at` 을 넣는다. `chk_batch_finished` 가 두 시각을 견주므로 기준이 갈리면 안 된다. `JpaAuditingConfig` 가 `DateTimeProvider` 를 `Clock` 에 묶는다
* **상태와 종료 시각, 실패 사유는 한 문장에서 함께 바꿔야 한다.** `chk_batch_finished` 와 `chk_batch_failure_reason` 이 짝을 요구한다. 한쪽만 바꾸면 저장이 거부되고, 그 거부는 배치가 실패를 기록하려는 순간에 터져서 실패 기록 자체가 사라진다
* **묶음도 등록된 단계도 아닌 작업은 이어받아도 다시 돌릴 길이 없다.** 소유자만 바꿔 두면 내 생존 신호가 그 행을 영원히 살아 있게 만들어 아무도 멈춘 것을 모른다. 그래서 실패로 닫고 알린다

### 아직 비어 있는 것

2장의 나머지 셋은 구현이 없다.

| 규칙 | 왜 비어 있나 |
|---|---|
| 00:00 묶음의 단계 (1)~(10) | 각 도메인이 `DailyJob`을 구현해 등록할 자리다. 지금은 등록된 것이 없어 묶음이 바로 성공으로 닫힌다 |
| 설정값을 캐시 없이 읽기 | 플랫폼 설정값 조회 자체가 아직 없다. 그 코드가 생길 때 영업일 경계 작업만 캐시를 거치지 않게 둔다 |
| 시계 맞추기 | 배포 설정이라 코드가 아니다. 영업일 판정은 `ClockConfig`가 Asia/Seoul로 고정했다 |
