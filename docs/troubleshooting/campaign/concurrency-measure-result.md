# 활성화, 템플릿 수정, 배치 점유의 동시성 측정 결과

시나리오와 불변식의 정의는 [concurrency-measure-definition.md](concurrency-measure-definition.md) 가 갖는다. 이 문서는 그 정의대로 돌린 결과와 한계만 적는다. 불변식 번호는 정의 문서의 번호다.

## 1. 결론

- 6개 시나리오 모두에서 불변식 위반은 0건이었다. 새로 올린 이슈는 없다.
- 위반 0건은 불변식이 항상 참이라는 증명이 아니다. 시나리오마다 정해진 N회 동안 한 번도 거짓이 되지 않았다는 관측이다. 회차 100번에서 한 번도 나오지 않았다면, 회차당 위반 확률의 95% 신뢰구간 상한은 약 3%(3/N)다. 그보다 드문 경쟁은 이 측정으로 걸러지지 않는다.
- 검수 스텁의 지연은 가정이다. 실제 S3와 Rekognition 의 응답 시간을 재서 넣은 값이 아니다.

## 2. 측정 조건

| 항목 | 값 |
|---|---|
| 반복 횟수 N | 조건마다 100 (`MEASURE_ROUNDS=100`) |
| 난수 씨앗 | 1090 |
| 검수 스텁 지연 | 0, 100, 500, 1000, 3000 ms (`MEASURE_DELAYS_MS=0,100,500,1000,3000`) |
| 템플릿 동시 수정자 수 K | 8 |
| 측정한 커밋 | `303e5322b` (브랜치 `test/1090-concurrency-scenarios`) |
| 실행 | `./gradlew integrationTest --tests "*RaceIntegrationTest"` 한 번, 전체 약 32분 |
| 환경 | Windows 11, Java 21.0.11, Docker 29.6.1, Testcontainers 의 MySQL 8.4 와 Valkey 9, 커넥션 풀 최대 8 |

테스트는 한 JVM 안의 스레드 경쟁이다. 서버 여러 대의 네트워크 지연은 만들지 않는다.

## 3. 시나리오 A. 활성화 경쟁

### 3.1 A1. 포스터를 덮어쓰는 경쟁

활성화 한 건과 `PosterUploadService.createOrOverwritePoster` 한 건을 동시에 출발시켰다. 지연마다 N=100이다.

| 지연 | A1-1 | A1-2 | A1-3 | A1-4 | SCHEDULED 응답 | 거부(CAMPAIGN-006) |
|---|---|---|---|---|---|---|
| 0ms | 0 | 0 | 0 | 0 | 1 | 99 |
| 100ms | 0 | 0 | 0 | 0 | 3 | 97 |
| 500ms | 0 | 0 | 0 | 0 | 1 | 99 |
| 1000ms | 0 | 0 | 0 | 0 | 0 | 100 |
| 3000ms | 0 | 0 | 0 | 0 | 0 | 100 |

### 3.2 A1. 포스터 텍스트를 고치는 경쟁

활성화 한 건과 `PosterEditService.update` 한 건을 동시에 출발시켰다. 지연마다 N=100이다.

| 지연 | A1-1 | A1-2 | A1-3 | A1-4 | SCHEDULED 응답 | 거부(CAMPAIGN-006) |
|---|---|---|---|---|---|---|
| 0ms | 0 | 0 | 0 | 0 | 61 | 39 |
| 100ms | 0 | 0 | 0 | 0 | 0 | 100 |
| 500ms | 0 | 0 | 0 | 0 | 0 | 100 |
| 1000ms | 0 | 0 | 0 | 0 | 0 | 100 |
| 3000ms | 0 | 0 | 0 | 0 | 0 | 100 |

거부는 모두 `CAMPAIGN_STATE_NOT_ALLOWED`(CAMPAIGN-006)였다. 검수가 끝난 뒤 `schedule` 이 행 잠금을 잡고 포스터의 `updatedAt` 을 비교해 바뀐 것을 잡은 경우다. 이 경로는 의도된 거부이고 위반이 아니다.

변경 동작이 시작한 시점은 지연 범위를 실제로 덮었다. 덮어쓰기의 시작 시점 평균은 0ms 조건에서 0ms, 100ms 조건에서 60ms, 500ms 조건에서 252ms, 1000ms 조건에서 494ms, 3000ms 조건에서 1402ms였고 최대는 지연 값 이하였다.

### 3.3 A2. 같은 캠페인의 동시 활성화

같은 점주가 같은 캠페인을 동시에 두 번 활성화했다. 지연마다 N=100이다.

| 지연 | A2-1 | A2-2 | A2-3 | A2-4 | 중복 검수 호출이 있던 회차 | 검수 호출 수 평균 |
|---|---|---|---|---|---|---|
| 0ms | 0 | 0 | 0 | 0 | 100 | 2.00 |
| 100ms | 0 | 0 | 0 | 0 | 100 | 2.00 |
| 500ms | 0 | 0 | 0 | 0 | 100 | 2.00 |
| 1000ms | 0 | 0 | 0 | 0 | 100 | 2.00 |
| 3000ms | 0 | 0 | 0 | 0 | 100 | 2.00 |

중복 검수는 코드가 감수하는 선택이라 위반이 아니다. 이 측정에서는 모든 회차에서 두 호출이 모두 검수까지 갔다.

### 3.4 A3. 검수를 기다리는 동안의 DB 커넥션

단언 없이 기록만 한 관측이다. 회차마다 5ms 간격으로 읽은 활성 커넥션 수의 최대값과 평균을 모았다. 이 값은 같은 시나리오의 다른 스레드가 쓰는 커넥션도 함께 세므로 활성화 한 건이 쥔 커넥션 수가 아니다.

| 지연 | 회차별 최대값의 평균 | 회차별 최대값 중 가장 큰 값 | 회차별 평균의 평균 |
|---|---|---|---|
| 0ms | 2.00 | 2 | 1.39 |
| 100ms | 1.12 | 2 | 0.29 |
| 500ms | 1.03 | 2 | 0.07 |
| 1000ms | 1.01 | 2 | 0.04 |
| 3000ms | 1.00 | 1 | 0.01 |

지연이 길어질수록 평균이 거의 0으로 내려간다. 검수를 기다리는 동안 커넥션을 쥐지 않는다는 설계와 맞는 모양이다.

## 4. 시나리오 B. 템플릿 동시 수정

K=8명이 같은 템플릿을 동시에 수정했다. 조건마다 N=100이다.

| 조건 | B1 | B2 | B3 | B4 | B5 | B6 | 수정 후 살아 있는 버전 수 |
|---|---|---|---|---|---|---|---|
| 수정 전 버전 1개 | 0 | 0 | 0 | 0 | 0 | 0 | 9 (전 회차) |
| 수정 전 버전 18개 | 0 | 0 | 0 | 0 | 0 | 0 | 20 (전 회차) |

두 번째 조건은 8건이 상한 20을 넘기는 경우다. 100회차 모두 살아 있는 버전이 정확히 20개로 정리됐다.

단언 없이 기록한 시간이다. 단위는 ms다.

| 조건 | 구간 | 표본 | 평균 | p50 | p95 | 최대 |
|---|---|---|---|---|---|---|
| 버전 1개 | 저장 구간 | 800 | 74.45 | 69.09 | 142.84 | 424.83 |
| 버전 1개 | 수정 호출 전체 | 800 | 112.36 | 102.84 | 196.85 | 765.72 |
| 버전 18개 | 저장 구간 | 800 | 60.06 | 59.44 | 104.39 | 165.69 |
| 버전 18개 | 수정 호출 전체 | 800 | 89.16 | 87.76 | 138.81 | 198.64 |

저장 구간은 `TransactionTemplate.execute` 를 부른 시점부터 돌아온 시점까지이고 행 잠금을 기다린 시간이 들어 있다.

## 5. 시나리오 C. 배치 점유 경쟁

조건마다 N=100이고 회차마다 영업일을 새로 썼다.

| 시나리오 | 불변식 | 위반 | 승자가 정확히 하나였던 회차 |
|---|---|---|---|
| C1. 서버 2대 동시 점유 | C1-1 ~ C1-4 | 모두 0 | 100 / 100 |
| C2. 서버 3대 동시 이어받기 | C2-1 ~ C2-4 | 모두 0 | 100 / 100 |

승자가 몰리지는 않았다. C1 은 서버 A 가 56번, 서버 B 가 44번 이겼다. C2 는 서버 A, B, C 가 각각 34번, 40번, 26번 받았다. 단언 없이 기록한 시간은 아래와 같다.

| 구간 | 표본 | 평균 | p50 | p95 | 최대 |
|---|---|---|---|---|---|
| `claim` | 200 | 20.80 | 19.21 | 28.88 | 129.04 |
| `takeOverStale` | 300 | 21.58 | 19.03 | 32.79 | 63.90 |

`claim` 이 일시적 실패(교착, 락 대기 시간 초과)로 한 번 더 시도한 횟수는 코드가 세지 않아 기록하지 못했다. 그런 실패가 있었더라도 `claim` 안에서 흡수되어 예외로는 올라오지 않았다(C1-4 위반 0).

## 6. 한계

- **씨앗이 고정하는 것.** 고정한 것은 시작 시점에 주는 흔들림의 열뿐이다. 스레드의 실제 실행 순서는 운영체제가 정하므로 회차의 결과가 재현된다는 뜻이 아니다.
- **스텁 지연은 가정이다.** 0에서 3000ms 범위는 코드의 시간 제한(S3 읽기 시도당 3초, 전체 5초, Rekognition 5초)을 따라 정한 값이다. 실제 응답 시간이 이 범위에서 어떻게 분포하는지는 이 측정이 알려 주지 않는다.
- **A1 에서 SCHEDULED 가 되는 회차가 적다.** 흔들림이 `[0, 지연]` 이라 포스터 변경이 검수를 기다리는 동안 끼어들고, 지연이 100ms 이상이면 거의 모든 회차가 `schedule` 의 확인에서 거부된다. SCHEDULED 응답이 나온 회차는 텍스트 수정 0ms 61회와 덮어쓰기 0·100·500ms 5회(1·3·1회), 합 66회다. 이 회차들에서는 A1-1 을 실제로 비교했다. 다만 덮어쓰기의 5회는 포스터 변경이 거부된(`changeRejected`) 회차라 포스터가 그대로였고, 변경이 반영된 뒤 SCHEDULED 로 가는 경로를 지난 회차는 텍스트 수정 0ms 조건 쪽이 사실상 전부다. SCHEDULED 응답이 없는 조건에서만 A1-1 은 상태가 DRAFT 라서 자명하게 참이다. 검수 이후에서 잠금 사이의 아주 좁은 틈을 노려 변경을 넣는 측정은 하지 않았다.
- **A1-1 의 비교 기준.** 검수가 본 포스터는 검수 스텁이 불리는 순간 별도 연결로 읽은 값이다. 스텁이 불린 직후에 변경이 커밋되는 아주 좁은 틈에서는 이 값과 실제 검수의 입력이 다를 수 있다.
- **시작 시점의 기준.** 동작의 시작 시점은 각 스레드가 출발 래치에서 깨어난 시각을 기준으로 잰다. 래치를 연 시각 기준보다 스레드가 깨어나는 시간만큼 작게 기록된다. 그 차이의 크기는 따로 재지 않았다. 표의 시작 시점 평균은 지연 범위를 덮었는지 보려는 용도이고 불변식 판정에는 쓰이지 않는다.
- **커넥션 수.** 5ms 간격 표본이라 그보다 짧게 쥐었다 놓은 커넥션은 놓칠 수 있고, 다른 스레드의 커넥션도 함께 센다. 풀 최대가 8이라 그 한도 안에서의 값이다.
- **워밍업을 따로 빼지 않았다.** 클래스 로딩과 첫 쿼리의 비용이 첫 회차에 섞여 있어 최대값이 이를 반영할 수 있다. 템플릿 수정의 첫 조건 최대값(765.72ms)이 두 번째 조건(198.64ms)보다 큰 것이 그 흔적으로 보인다. 다만 순서가 고정이라 워밍업과 조건 차이를 이 측정만으로 나눌 수는 없다.
- **배치 점유의 동시 출발.** 흔들림 없이 동시에 출발시켰다. 서버 사이의 시계 차이와 네트워크 지연은 만들지 않았다. 점유는 한 JVM 안의 커넥션 사이 경쟁이다.
- **범위.** 이 측정은 한 JVM 안의 스레드 경쟁이다. 서버 여러 대의 처리량과 운영 부하는 재지 않았다.
