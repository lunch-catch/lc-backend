# 활성화, 템플릿 수정, 배치 점유의 동시성 측정 정의

이 문서는 동시성 시나리오를 반복해서 돌리기 전에, 시나리오마다 무엇이 항상 참이어야 하는지를 정한다. 결과 문서는 이 문서의 불변식 번호로 위반 횟수를 적는다.

측정은 통합 테스트로 돌린다. 테스트는 불변식에만 단언을 건다. 결과의 분포와 대기 시간은 기록만 하고 통과나 실패의 기준으로 쓰지 않는다. 불변식을 어긴 회차가 나오면 테스트가 실패하고, 그 결함은 이 이슈에서 고치지 않고 새 이슈로 올린다.

## 1. 측정 대상과 범위

| 시나리오 | 대상 | 도메인 |
|---|---|---|
| A. 활성화 경쟁 | `CampaignActivationService`, `CampaignStatusService.schedule`, `PosterUploadService`, `PosterEditService` | campaign |
| B. 템플릿 동시 수정 | `TemplateReviseService` | campaign |
| C. 배치 점유 경쟁 | `BatchExecutionService` | ops |

이미 통합 테스트가 있는 동시성은 다시 재지 않는다. 하루 예산 변경과 `pause`, 취소와 00시 전환, 쿠폰 조건 덮어쓰기, 노출 대상 수정, 배치 점유 1회, 수동 재실행 중복이 그것이다.

아래는 측정하지 않는다.

- 운영 환경의 부하와 처리량. 이 측정은 한 JVM 안의 스레드 경쟁이고 서버 여러 대의 네트워크 지연을 만들지 않는다.
- AWS 호출의 실제 지연. 검수의 S3 읽기와 Rekognition 호출은 스텁으로 대신한다.
- 모델의 응답. 템플릿 생성은 `bedrock.model-id` 가 없을 때 켜지는 `FakeTemplateHtmlGenerator` 가 고정 HTML 로 대신한다.

## 2. 판정 용어

| 용어 | 뜻 |
|---|---|
| 회차 | 동시 출발부터 모든 스레드가 끝날 때까지의 한 번 실행 |
| N | 시나리오와 조건 하나를 반복한 회차 수 |
| 위반 | 회차 하나에서 불변식이 거짓이 된 것 |
| 관측 | 단언하지 않고 기록만 하는 값 |

위반 0건은 불변식이 항상 참이라는 증명이 아니다. N회 동안 한 번도 거짓이 되지 않았다는 관측이다. N이 작으면 드문 경쟁은 지나갈 수 있다.

## 3. 불변식

### 3.1 시나리오 A. 활성화 경쟁

활성화는 검수를 트랜잭션 밖에서 한다. 검수가 끝나고 `schedule` 이 캠페인 행 잠금을 잡기 전까지 포스터가 바뀔 수 있고, 이 틈이 시나리오 A 가 재는 대상이다.

**A1. 포스터를 덮어쓰거나 고치는 경쟁**

활성화 한 건과 포스터 변경 한 건을 동시에 출발시킨다. 변경은 덮어쓰기(`PosterUploadService.createOrOverwritePoster`)와 텍스트 수정(`PosterEditService.update`) 두 가지를 따로 돌린다.

| 번호 | 불변식 |
|---|---|
| A1-1 | 캠페인이 `SCHEDULED` 이면 저장된 포스터는 검수가 본 포스터와 같다 |
| A1-2 | 캠페인이 `DRAFT` 로 남았으면 활성화 응답은 `SCHEDULED` 가 아니다 |
| A1-3 | 캠페인 상태는 `DRAFT` 나 `SCHEDULED` 둘 중 하나다 |
| A1-4 | 예상하지 못한 예외(`CampaignException` 이 아닌 예외)로 끝난 스레드가 없다 |

검수가 본 포스터는 검수 스텁이 불리는 순간에 읽은 값으로 정한다. 덮어쓰기는 `objectKey` 로, 텍스트 수정은 `updated_at` 으로 비교한다.

관측으로 세는 값은 둘이다. 활성화가 끝난 방식(`SCHEDULED` 응답, `DRAFT` 응답, 오류 코드별 거부)의 횟수는 포스터 변경이 검수 도중에 끼어든 회차가 몇 번이었는지 보여 준다. 포스터 변경 동작이 시작한 시점은 흔들림이 지연 범위를 실제로 덮었는지 보여 준다.

**A2. 같은 캠페인의 동시 활성화**

같은 점주가 같은 캠페인을 동시에 두 번 활성화한다.

| 번호 | 불변식 |
|---|---|
| A2-1 | 최종 상태는 `SCHEDULED` 이다 |
| A2-2 | `DRAFT` 에서 `SCHEDULED` 로 바뀐 상태 변경 로그가 정확히 1건이다 |
| A2-3 | 응답이 `SCHEDULED` 인 호출이 정확히 1건이다 |
| A2-4 | 나머지 호출은 `CAMPAIGN_STATE_NOT_ALLOWED` 로 거부된다 |

중복 검수 호출 수(1 또는 2)는 관측으로 기록한다. 코드가 이 낭비를 감수하는 선택이라고 적어 두었으므로 위반이 아니다.

**A3. 검수를 기다리는 동안의 DB 커넥션**

이 값은 관측만 한다. 활성화가 검수를 기다리는 동안 커넥션을 쥐지 않는다는 설계의 결과를 확인하려는 것이다. 검수 스텁이 지연되는 동안 `HikariPoolMXBean` 의 활성 커넥션 수를 5ms 간격으로 읽어 회차마다 최대값과 평균을 기록한다. 이 값은 같은 동작을 하는 다른 스레드가 쓰는 커넥션도 함께 세므로 활성화 한 건이 쥔 커넥션 수가 아니다. 단언은 하지 않는다.

**A4. 스텁 지연과의 무관성**

A1 과 A2 의 불변식은 검수 스텁의 지연 값과 무관하게 지켜져야 한다. 지연 값마다 A1 과 A2 를 따로 돌리고 결과 문서에 지연별 위반 횟수를 적는다.

### 3.2 시나리오 B. 템플릿 동시 수정

K명의 관리자가 같은 템플릿을 동시에 수정한다. 서비스를 직접 부르고 스레드마다 다른 관리자 ID 와 다른 `requestId` 를 쓴다. 관리자당 분당 3회 제한에 걸리지 않게 하려는 것이다.

| 번호 | 불변식 |
|---|---|
| B1 | 성공한 호출이 K건이다 |
| B2 | 응답의 버전 번호가 서로 겹치지 않는다 |
| B3 | 응답의 버전 번호가 빈틈없이 이어진다 |
| B4 | 저장된 버전 행의 `(template_id, version_number)` 에 중복이 없다 |
| B5 | 살아 있는(소프트삭제되지 않은) 버전이 20개를 넘지 않는다 |
| B6 | 살아 있는 버전의 번호는 가장 높은 번호에서 아래로 이어진다 |

조건은 둘이다. 하나는 버전이 적은 템플릿이고, 다른 하나는 살아 있는 버전이 상한 바로 아래(18개)여서 이 K건이 상한을 넘기는 템플릿이다. 두 번째 조건에서 B5 와 B6 이 의미를 가진다.

저장 구간의 대기 시간(p50, p95, 최대)은 관측으로 기록한다. 저장 구간은 `TransactionTemplate.execute` 를 부른 시점부터 돌아온 시점까지다. 행 잠금을 기다린 시간이 여기 들어간다.

### 3.3 시나리오 C. 배치 점유 경쟁

**C1. 두 서버의 동시 점유**

서로 다른 `BatchServerId` 를 가진 서비스 두 개가 같은 작업과 영업일을 동시에 점유한다. 회차마다 영업일을 새로 쓴다.

| 번호 | 불변식 |
|---|---|
| C1-1 | `claim` 이 `true` 인 서버가 정확히 하나다 |
| C1-2 | 저장된 행의 `owner_id` 는 이긴 서버의 값이다 |
| C1-3 | 저장된 행의 `attempt_no` 는 1이다 |
| C1-4 | `claim` 에서 예외가 올라온 스레드가 없다 |

C1-1 이 지켜진 회차의 비율이 이 시나리오의 주된 관측값이다. 비율은 100% 가 아니면 위반이 있다는 뜻이다. 일시적 실패(교착, 락 대기 시간 초과)로 `claim` 이 한 번 더 시도한 횟수는 코드가 세지 않으므로 기록하지 않는다.

**C2. 서버 세 대의 동시 이어받기**

생존 신호가 2분 넘게 멈춘 실행 중 행 하나를 서버 세 대가 동시에 이어받으려 한다. 행의 소유자는 죽은 네 번째 서버다. 회차마다 영업일을 새로 쓴다.

| 번호 | 불변식 |
|---|---|
| C2-1 | `takeOverStale` 이 그 행을 돌려준 서버가 정확히 하나다 |
| C2-2 | 저장된 행의 `owner_id` 는 그 서버의 값이다 |
| C2-3 | 저장된 행의 `attempt_no` 는 2다 |
| C2-4 | `takeOverStale` 에서 예외가 올라온 스레드가 없다 |

## 4. 반복 횟수와 난수

| 항목 | 값 |
|---|---|
| 기본 반복 횟수 | 5 (환경변수 `MEASURE_ROUNDS` 로 바꾼다) |
| 난수 씨앗 | 1090 (고정) |
| 두 번째 동작의 시작 시점 | 동시 출발 뒤 0 이상 지연 이하의 범위에서 무작위. 첫 동작은 출발과 함께 시작한다 |
| 템플릿 동시 수정자 수 K | 8 |

기본 반복 횟수를 작게 두는 이유는 `./gradlew check` 의 실행 시간을 늘리지 않으려는 것이다. 결과 문서의 숫자는 `MEASURE_ROUNDS` 를 크게 준 별도 실행에서 얻는다. 그 실행의 N 은 결과 문서에 적는다.

씨앗이 같아도 스레드의 실제 실행 순서는 운영체제가 정하므로 회차의 결과가 재현된다는 뜻은 아니다. 씨앗이 고정하는 것은 시작 시점에 주는 흔들림의 열이다.

## 5. 스텁 지연

활성화 시나리오(A)는 검수 스텁이 일정 시간 기다렸다가 답하게 한다.

| 실행 | 지연 값 (ms) | 지정 방법 |
|---|---|---|
| 기본 | 0, 100, 500 | 환경변수 `MEASURE_DELAYS_MS` 를 주지 않는다 |
| 측정 | 0, 100, 500, 1000, 3000 | `MEASURE_DELAYS_MS=0,100,500,1000,3000` |

지연의 상한은 코드의 시간 제한을 따른다. S3 읽기는 시도당 3초에 전체 5초이고 Rekognition 은 5초다. 이 값들은 실제 AWS 응답 시간을 잰 것이 아니라 가정이다. 실제 지연이 이 범위 안에서 어떻게 분포하는지는 이 측정이 알려 주지 않는다.

## 6. 결과 문서가 담을 것

결과 문서(`concurrency-measure-result.md`)는 아래를 담는다.

- 시나리오와 지연 조건마다 N 과 불변식별 위반 횟수. 위반이 0이 아니면 새로 올린 이슈 번호를 함께 적는다.
- 관측값. 중복 검수 호출 수, 활성 커넥션 수의 최대와 평균, 저장 구간 대기 시간(p50, p95, 최대), 배치 점유에서 승자가 정확히 하나였던 회차의 비율.
- 환경과 측정한 커밋.
- 한계. 위 4절의 씨앗, 5절의 지연 가정, 3.1 절 A1 의 검수가 본 포스터를 읽는 방식이 가진 한계, 한 JVM 안의 경쟁이라는 범위.
