## 4. 해석

### v1

앱 서버의 DB 커넥션이 병목이다. 커넥션을 기다리는 요청이 400건을 넘고, 회차마다 커넥션 시간 초과가 1,400~2,400건 났다. RDS CPU 는 73% 로 여유가 있어, DB 서버보다 앞의 커넥션 풀이 먼저 찬다. 노출 1건이 노출 INSERT, 판정 기록, 원장을 한 트랜잭션에서 써 커넥션을 오래 쥔다.

### v2

v1 보다 나빠졌다. 커넥션을 쥐는 평균 시간이 45ms 에서 79ms 로 늘었다. 그런데 RDS CPU 는 73% 에서 46% 로, 커밋 수는 초당 408 에서 243 으로 줄었다. DB 가 일을 덜 하는데 요청이 커넥션을 더 오래 쥔다. 그래서 CPU 가 아니라 대기가 늘었다고 본다. 릴레이가 같은 `impression_log` 를 1초마다 읽고 고치는 동안 노출 INSERT 와 부딪힌 것으로 추정한다. 잠금 대기를 직접 재지는 않았다.

릴레이는 회차마다 밀린 노출이 늘어 37만 건에 닿았다. 1초에 1,000건을 넘기도록 설계했지만 실제로는 초당 약 20건만 넘겼다. 원인은 이 시험으로 가리지 못했다. 다음 시험에서 릴레이의 묶음 처리 시간과 잠금 대기를 함께 재야 한다.

### v3

요청이 쓰기와 커밋을 하지 않아 커넥션을 쥐는 평균 시간이 20ms 로 가장 짧다. 커넥션 시간 초과도 v2 의 4분의 1 로 줄었다. 하지만 커넥션 대기 최대는 여전히 580건이다. 요청에 남은 DB 읽기 2건(저장된 노출 확인, 쿠폰 소진)과 피드의 읽기가 여전히 풀을 채운다. 노출 저장 큐는 서버마다 상한 10,000건 가까이 찼고 1,607건을 버렸다.

피드와 노출의 p99 가 k6 시간 초과(60초)에 닿았다. 큐가 차면 요청이 100ms 까지 기다리고 그 사이 커넥션 풀이 비지 않아 일부 요청이 끝까지 끝나지 않은 것으로 본다. 측정이 한 회차뿐이라 v1, v2 의 평균과 같은 무게로 비교하지 않는다.

### v3b

v3 와 다른 것은 정산의 묶음 차감뿐이다. 릴레이가 넘긴 노출 1,000건을 노출마다 트랜잭션과 왕복을 열지 않고 묶음 하나로 처리한다(#1049). 그 결과가 커넥션 지표에 그대로 보인다. 커넥션 시간 초과가 4,717건에서 7건으로, 얻는 평균이 334ms 에서 227ms 로, 쥐는 평균이 20ms 에서 15ms 로 줄었다. 릴레이의 밀린 노출 최대는 104,677건에서 1,171건으로 줄었고, 셀 때 넘기지 못한 노출이 없었다. 노출 저장 큐는 v3 의 5분의 1 아래로 차 버린 노출이 없었다.

v3 의 오류와 60초 꼬리는 노출 저장 자체가 아니라 릴레이의 차감이 커넥션 풀을 오래 쥔 탓이었다고 본다. 노출 저장 큐가 차고 요청이 커넥션을 기다린 것은 그 결과다. 피드가 초당 56건, 노출이 초당 560건으로 세 버전보다 많이 나간 것도 같은 이유다.

여전히 커넥션 대기 최대가 492건이고 RDS CPU 가 88% 까지 올랐다. p99 가 10초 안팎인 것은 남은 읽기와 늘어난 처리량이 다시 풀과 DB 를 채웠기 때문으로 본다. 서빙 최적화(#1042, #1044)는 이 이미지에 들어 있지 않다. 그 효과는 다음 시험에서 따로 잰다.

## 5. 시험 중에 생긴 일

### V8 마이그레이션이 실패했다

v2 로 바꿀 때 adserving 의 V8 마이그레이션(`V8__adserving_impression_dispatch.sql`)이 실패했다. v1 이 쌓은 `impression_log` 37만 8천 행에 백필 `UPDATE` 를 한 문장으로 돌리다 JDBC `socketTimeout`(10초)에 걸렸다. 열과 인덱스를 더하는 DDL 은 되돌아가지 않아 열만 남았다. 그 뒤로는 앱이 뜰 때마다 `Duplicate column name 'dispatched_at'` 으로 멈췄다.

운영과 개발에서도 그날과 전날의 `impression_log` 가 10초 안에 다 고쳐지지 않을 만큼 많으면 같은 일이 생긴다. 알려진 마이그레이션 결함이고 별도 이슈에서 고친다.

시험을 이어 가려고 시험 DB 에서만 아래를 했다.

1. 남은 열 셋과 `idx_imp_dispatch` 를 지우고 `flyway_history_adserving` 의 실패한 V8 행을 지웠다.
2. 그사이 다시 뜬 v2 서버가 V8 을 또 돌려 백필이 다시 걸렸다. 그 쿼리를 끊고 `impression_log` 를 비운 뒤 1을 다시 했다.
3. 빈 테이블에서 V8 이 성공했다. 그 뒤 `reset` 으로 시드를 다시 넣었다.

그래서 v2 와 v3 는 빈 `impression_log` 에서 시작했다. v1 도 빈 테이블에서 시작해 세 버전의 시작 조건은 같다.

### v2 로 바꾸는 동안 앱 서버가 바뀌었다

서버를 한 대씩 다시 띄우는 동안 헬스체크에 실패한 서버를 오토스케일링 그룹이 새 서버로 바꿨다. v3 로 바꿀 때는 교체를 멈춰 두고 모든 서버를 함께 다시 띄웠다(`switch`). 측정 회차 전에는 앱 서버가 3대이고 모두 정상인지 확인했다.

### v3b 는 시간을 줄여 한 회차만 쟀다

워밍업 1회와 측정 1회만 돌렸다. v1, v2, v3 는 다시 재지 않고 오전의 결과를 비교에 썼다. 그래서 날마다 다른 환경 차이를 같은 날의 기준점으로 걷어내지 못했다. 환경은 같은 Terraform 구성으로 새로 띄웠고 데이터와 회차 설정도 같다.

- 부하 생성기의 1분 평균 CPU 최대가 52% 로 오전(16% 아래)보다 높았다. 처리량이 늘어 생성기의 일도 늘었다. 포화는 아니라 무효로 보지 않았다.
- Valkey 의 크레딧 최소가 1.3 이었다. 새 노드의 시작 크레딧이 낮은 데다 엔진 CPU 가 기준 성능(10%)을 넘어 15% 까지 올랐다. 바닥나지는 않았고 네트워크 허용량을 넘긴 일도 없어 무효로 보지 않았다.
- 05 부하 시험 대시보드는 비어 있었다. k6 의 지표가 그라파나에 닿지 않았다. 응답 수치는 k6 의 요약에서 적었다.
- 환경을 띄울 때 지난 환경이 남긴 RDS 슬로 쿼리 로그 그룹 때문에 Terraform 이 멈췄다. 그 로그 그룹을 상태로 가져온(`terraform import`) 뒤 다시 띄웠다.

### v3 는 한 회차만 쟀다

V8 복구와 서버 교체로 시간을 써 v3 의 측정 2, 3회차를 자동 정리 전에 돌리지 못했다. v3 의 결과는 한 회차의 값이다.
