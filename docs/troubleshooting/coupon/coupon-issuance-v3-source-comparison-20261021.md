# 예전 v3 측정 소스와 현재 구현의 로컬 대조

2026-10-21에 [앞선 로컬 측정](./coupon-issuance-v3-redis-soldout-local-20261021.md)의 발급 p95 2,060ms가 코드 변경으로 발생했는지 조사했다.
같은 현재 JAR를 다시 실행한 두 본시험에서 발급 p95는 497.49ms와 676.09ms였다.
현재 JAR의 이벤트 1개 대조에서는 두 번째 본시험의 발급 p95가 377.88ms, p99가 484.84ms였다.
현재 코드가 항상 2초대로 느려졌다는 가설은 재현하지 못했다.
앞선 2초 결과를 삭제하거나 이번 빠른 결과로 대체하지 않는다.

## 당시 측정에 쓴 코드와 실행 파일을 찾았다

[예전 상승 시험](./coupon-issuance-v3-rps-ramp-20261020.md)은 HEAD `58f0e29d`에 미커밋 변경을 더한 코드를 측정했다.
커밋만 체크아웃하면 실제 측정 코드와 다르므로 보관된 `measured-source.tar.gz`와 `server.jar`를 사용했다.
압축본의 소스 해시가 당시 `source-manifest.json`과 일치했고 JAR 해시도 기록과 일치했다.

| 자료 | SHA-256 |
|---|---|
| 당시 소스 압축본 | `52bc0a48243d02764a11d1002029f67aa608b96dc55b7cc3a53292b6977e843c` |
| 당시 실행 JAR | `02781c98d782dc623eceac335c037cf96bbb5be572e842bc85a84b44b15f1078` |
| 현재 실행 JAR | `802bd04a392d812480207a1ac50f98e4eb2658d2760542b72288fc12d0693c57` |

쿠폰 Java와 기존 Lua 및 추가된 Java 파일 85개를 비교해 53개가 같음을 확인했다.
나머지에는 발급 요청 경로 밖의 새 배치 작업과 이벤트 생성 코드도 포함된다.
주요 발급 경로에서 확인한 차이는 다음과 같다.

| 부분 | 당시 소스 | 현재 소스 |
|---|---|---|
| 자격 조회 | 회원마다 상태와 찜을 각각 조회했다. | 회원 상태는 묶음당 한 번, 찜은 캠페인당 한 번 조회한다. |
| DB 저장 | 여러 회원의 저장을 한 트랜잭션에서 처리했다. | 같은 구조를 유지하며 SQL 매개변수를 이름으로 바인딩한다. |
| 소진 응답 | HTTP 스레드가 DB 재확인과 광고 통보를 반복했다. | Redis 확정 소진을 먼저 응답하고 별도 작업자가 통보한다. |
| Redis 예약 완료 | 요청마다 한 번 완료하고 결과를 반환했다. | 같은 건별 완료 구조에 만료 검사와 SOLD_OUT 전환을 더했다. |
| 이벤트별 반복 | 이벤트마다 예약·재고 갱신·코드 조회를 수행했다. | 이벤트별 반복 구조를 유지한다. |

묶음 저장을 단건 저장으로 되돌린 변경이나 회원 상태 조회를 새로 건별 추가한 변경은 없었다.

## 동일 조건 대조

예전 JAR와 현재 JAR의 20개 이벤트 실행에는 AWS와 같은 여섯 스크립트를 사용했다.
JVM 최대 힙 768MiB, Hikari 8개, 작업자 4개와 같은 로컬 MySQL·Valkey 설정을 맞췄다.
각 JAR는 새 JVM에서 워밍업 안정 조건을 통과한 뒤 본시험을 수행했다.
완료된 작업을 모두 비우고 DB·Redis를 초기화한 다음 같은 JVM에서 한 번 더 수행했다.
앱 재시작 없는 두 번째 실행도 새 k6 프로세스를 사용했다.

현재 JAR의 이벤트 1개 대조는 재고 2,000장과 회원 5,000명 및 요청 시각을 유지했다.
한 이벤트의 재고를 2,000장으로 설정하고 모든 회원의 찜을 해당 캠페인에 배정했다.
이 대조에만 시나리오 값과 데이터 준비 스크립트의 개수 검사를 바꿨다.
HTTP 요청을 생성하는 스크립트는 그대로 사용했다.
과거의 일정 RPS 시험을 그대로 재현한 결과와 구분한다.

아래 지연은 발급 성공 2,000건만 집계한 ms 값이다.
모든 행에서 5,000건을 전송했고 미전송과 초과 발급은 없었다.

| 코드 | 이벤트 수 | 실행 | 중앙값 | p95 | p99 | 503 건수 |
|---|---:|---|---:|---:|---:|---:|
| 예전 측정 JAR | 20 | 첫 본시험 | 655.08 | 1070.74 | 1091.04 | 57 |
| 예전 측정 JAR | 20 | 같은 JVM 재실행 | 655.25 | 1056.76 | 1154.26 | 6 |
| 현재 JAR | 20 | 첫 본시험 | 293.31 | 497.49 | 592.86 | 21 |
| 현재 JAR | 20 | 같은 JVM 재실행 | 356.16 | 676.09 | 702.91 | 146 |
| 현재 JAR | 1 | 첫 본시험 | 58.70 | 466.71 | 542.81 | 14 |
| 현재 JAR | 1 | 같은 JVM 재실행 | 49.07 | 377.88 | 484.84 | 4 |

모든 본시험에서 DB와 Redis의 최종 발급 수는 총 2,000장으로 일치했다.
예전 JAR는 소진 뒤에도 READY를 유지하므로 상태 문자열 대신 완료 수와 남은 예약도 함께 대조했다.
현재 JAR는 모두 SOLD_OUT으로 끝났다.
503이 남았으므로 빠른 실행도 전체 성능 시험의 통과로 판정하지 않는다.

## 원인으로 확인한 부분과 확정하지 못한 부분

### 이벤트가 섞이면 묶음 안의 왕복 호출이 늘어난다

`CouponBatchIssuanceService.issueBatch`는 캠페인마다 찜을 조회한다.
이벤트마다 Redis 예약과 재고 UPDATE 및 코드 SELECT도 반복한다.
현재 20개 이벤트 첫 본시험의 재고 UPDATE는 1,077회였고 이벤트 1개에서는 318회였다.
같은 발급 2,000장을 처리했지만 호출 한 번에 바꾸는 재고 수가 달랐다.
첫 본시험의 발급 중앙값도 20개에서 293.31ms, 1개에서 58.70ms였다.

진단용 스레드 표본에서도 작업자들이 해당 SQL과 Redis 응답을 기다렸다.
기존 코드부터 남아 있던 이벤트별 반복이 다중 이벤트 조건에서 비용을 늘리는 근거다.
20개 이벤트라는 차이만으로 앞선 2초 지연 전체가 설명된다고 판단하지 않는다.

### 소진 응답의 DB 경합은 이번 개선으로 줄었다

예전 JAR 첫 본시험에서 Hikari 대기 연결은 표본 최대 148개였고 활성 연결은 8개였다.
현재 JAR의 20개 이벤트 첫 본시험에서는 대기 0개와 활성 최대 5개를 관측했다.
현재 코드의 소진 응답 p95는 첫 본시험 11.42ms, 같은 JVM 재실행 10.15ms였다.
표본 간격은 약 0.5초이므로 짧은 대기가 전혀 없었다는 뜻은 아니다.

### 예약 재고가 없지만 발급 완료는 아닌 구간에 503 경로가 남아 있다

`reserve_many.lua`는 available에서 순번을 꺼내지 못하면 남은 요청에 `-2`를 반환한다.
`CouponSequenceService.reserveAll`은 해당 값을 ISSUANCE_BUSY로 변환한다.
재고가 다른 요청에 전부 예약됐지만 completed가 total에 닿지 않은 구간에도 이 경로가 실행될 수 있다.
SOLD_OUT 사전 검사는 완료 수가 총량에 닿은 뒤에만 거절하므로 이 구간을 처리하지 않는다.

현재 20개 이벤트 실행에서 차단·복구 로그는 없었다.
HTTP 처리 스레드 상한은 200개이고 모든 응답은 10초 대기 상한보다 빨리 끝났다.
발급 대기열 상한은 2,000건이라 해당 조건으로 대기열 포화를 설명하기 어렵다.
503은 예약 중인 재고 부족 경로로 좁혀지지만 요청별 원인 계측은 추가하지 않았다.
재고가 아직 예약 중일 때 확정 소진으로 표시하면 롤백으로 재고가 돌아올 가능성을 잃으므로 그렇게 바꾸지 않는다.

### 앞선 2초 결과의 변동 원인은 아직 분리하지 못했다

현재 JAR와 같은 시나리오를 그대로 다시 실행해도 결과는 달랐다.
같은 JVM 재실행이 첫 본시험보다 느렸으므로 JIT 예열 하나로 설명할 수도 없다.
예전 기록은 한 이벤트에 일정 유입을 30초 유지했고 이번은 100건을 먼저 보낸 뒤 4,900건을 10초에 분산한다.
전체 성공 15,000건을 집계한 과거 500 RPS와 성공 2,000건을 집계한 이번 p95는 표본 구성도 다르다.

앱과 생성기 및 Docker가 같은 Mac을 공유한다.
호스트 자원 경합과 JVM 상태 및 DB I/O가 앞선 2초 결과에 기여한 비중은 측정하지 못했다.
이번 비교도 코드별 JVM 한 개와 두 번의 본시험이므로 엄밀한 개선율로 일반화하지 않는다.

## 다음 변경의 우선순위

- 작업자의 이벤트별 찜 조회·재고 갱신·코드 조회와 Redis 완료 시간을 나눠 계측한다.
- 다중 이벤트의 DB 호출을 함께 줄일 수 있는 계약과 SQL을 검토한다.
- 예약 중인 재고가 소진으로 확정되는 짧은 구간의 503 처리 방식을 정한다.

Redis 완료 호출을 묶는 변경은 앞서 정한 후순위를 유지한다.
이번 조사에서는 애플리케이션 코드를 바꾸지 않았으며 전체 테스트도 실행하지 않았다.

## 자료와 제외한 실행

[기계가 읽는 조사 결과](./coupon-issuance-v3-source-comparison-20261021.json)에 소스 해시, 여섯 본시험의 지연·거절, 실제 스크립트 해시와 SQL 증가량을 기록했다.
원본 로그와 실행기는 로컬 `/private/tmp/coupon-698-regression-analysis`에 있다.
JFR와 스레드 덤프를 켠 실행은 진단용으로만 사용했고 위 지연 비교에서 제외했다.
대용량 JFR JSON 분석이 겹쳐 워밍업에 실패한 예전 JAR 실행은 본시험에 진입하지 않아 제외했다.
포트 재사용 사전 검사와 이벤트 1개 준비 스크립트의 기존 범위 검사에 걸린 실행도 본시험에 진입하지 않았다.

모든 완료·중단 실행에서 이번 조사용 앱 프로세스와 DB·Valkey 컨테이너 및 볼륨을 정리했다.
시험용 토큰 파일도 삭제했으며 AWS 실행과 이미지 업로드는 하지 않았다.
