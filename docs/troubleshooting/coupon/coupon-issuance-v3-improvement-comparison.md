# 쿠폰 발급 v3의 묶음 커밋 도입과 부하 시험 기록

## 요약

| 구분 | 내용 |
|---|---|
| 발생한 문제 | v2는 재고 선택의 경합을 줄였지만 요청마다 DB 작업과 COMMIT을 반복했다. 제한된 커넥션 풀에서 요청이 대기해 응답 지연이 남았다. |
| 시도한 개선 | 발급 요청을 메모리 대기열에 모으고 작업자가 여러 요청을 한 트랜잭션으로 처리하게 했다. 카운터·재고 갱신과 회원 쿠폰 저장도 다건 SQL로 묶었다. |
| 확인한 결과 | 묶음 상한 100건으로 퍼널 DB 저장을 끈 300 RPS·60초 시험에서 18,000건을 모두 발급했고 성공 P95는 95.23ms였다. 여러 발급이 더 적은 COMMIT 호출을 나눠 쓰는 것도 확인했다.

## 기록 범위

v3는 v2의 순번 발급기를 유지하면서 여러 요청을 한 MySQL 트랜잭션으로 처리한 설계다.
[v2 설계](../../design/coupon/coupon-issuance-v2-design.md)는 재고 선택의 경쟁을 줄였지만 요청별 DB 작업과 커밋, 커넥션 풀 대기는 남았다.
DB 풀을 늘리는 대신 발급 요청을 모아 커밋 비용을 나눠 쓰도록 바꿨다.

이 문서는 2026-10-20의 묶음 커밋 도입 이유와 처리 구조, 부하 측정을 기록한다. 시각은 한국 시간이다.
v1·v2·v3는 내부 구현의 버전이며 HTTP 경로는 모두 `POST /v1/coupons`다.
현재 처리 순서와 설정값은 [API 설계](../../design/coupon/coupon-api-design.md#묶음으로-처리하는-쿠폰-발급)가 갖는다.
Redis 저장 구조와 장애별 절차는 [구조와 동작 설계](../../design/coupon/coupon_구조와_동작_설계.md#redis-순번과-예약), [장애 처리 설계](../../design/coupon/coupon_장애_처리_설계.md#redis-장애와-큐-복구)를 따른다.

## 1. 여러 발급 요청을 모아 한 번에 커밋하도록 바꿨다

변경 단위는 HTTP 응답이 아니라 DB에서 처리할 발급 요청이다.
작업자는 여러 요청을 하나의 트랜잭션으로 저장한다. 각 HTTP 요청은 커밋 뒤 자신의 결과를 따로 받는다.
성공을 먼저 응답하고 나중에 DB에 저장하는 구조로 바꾸지 않았다.

| 선택지 | 얻는 점 | 감수하는 비용 |
|---|---|---|
| v2처럼 요청마다 커밋한다. | DB 트랜잭션의 실패와 재시도 범위가 요청 한 건으로 좁다. | 요청 수만큼 트랜잭션과 커밋을 반복한다. |
| v3처럼 여러 요청을 묶어 커밋한다. | 여러 발급이 DB 왕복과 커밋 비용을 나눠 쓴다. | 메모리 대기열과 결과 전달이 필요하다. DB 예외는 묶음 전체에 영향을 준다. |

v3는 두 번째 방식을 선택했다. 대기열에서 기다리는 요청이 DB 커넥션을 잡지 않도록 요청 스레드와 발급 작업자를 나눴다.
트랜잭션만 묶으면 요청별 SQL 왕복은 남으므로 카운터와 재고 갱신, 회원 쿠폰 저장도 여러 행을 다루는 SQL로 바꿨다.
`JdbcTemplate`은 묶음 서비스의 Spring 트랜잭션에 참여한다. 저장 방식이 달라도 재고·카운터·회원 쿠폰의 커밋 경계는 하나로 유지했다.

발급 순서와 트랜잭션 경계는 [v3 설계도](../../design/coupon/coupon-issuance-v3-design.md)에 기록한다.

| 코드 | 맡은 역할과 변경 이유 |
|---|---|
| [CouponCommandService](../../../src/main/java/com/launchcatch/coupon/service/CouponCommandService.java) | 발급 진입점과 차단 복구·소진 통보를 조정한다. 트랜잭션 없이 결과를 기다린다. |
| [CouponIssueBatcher](../../../src/main/java/com/launchcatch/coupon/service/CouponIssueBatcher.java) | 대기열에서 요청을 모으고 작업자 수만큼 묶음을 처리한다. 커밋 후 예약을 완료하고 요청마다 결과를 돌려준다. |
| [CouponBatchIssuanceService](../../../src/main/java/com/launchcatch/coupon/service/CouponBatchIssuanceService.java) | 한 묶음의 자격·중복·한도를 판정하고 재고·카운터·회원 쿠폰을 한 트랜잭션으로 확정한다. |
| [CouponBatchIssueRepository](../../../src/main/java/com/launchcatch/coupon/repository/CouponBatchIssueRepository.java) | 카운터와 재고 갱신, 회원 쿠폰 INSERT를 여러 행을 다루는 SQL로 묶는다. |

묶음 크기는 상한이다. 작업자는 첫 요청을 받은 뒤 이미 쌓인 요청만 추가로 꺼내며 상한까지 차기를 기다리지 않는다.
한산하면 한 건도 바로 커밋한다. 요청이 몰리면 앞 묶음을 처리하는 동안 쌓인 요청들이 다음 묶음이 된다.
작업자 수는 동시 발급 트랜잭션 수를 제한하며 Hikari 풀의 크기와는 별도 설정이다.
대기열도 서버 프로세스마다 존재한다. Redis의 재고 순번 목록과 HTTP 요청 대기열은 서로 다르다.

### 정합성과 실패의 범위도 함께 정했다

묶음 안의 앞 요청까지 포함해 중복과 일일 한도를 검사한다.
같은 회원의 여러 요청은 일일 카운터 잠금으로 조정한다. 기존 DB UNIQUE·CHECK도 유지한다.
현재의 세부 잠금 순서와 Redis 예약 시점은 [발급 트랜잭션 설계](../../design/coupon/coupon-api-design.md#트랜잭션과-잠금)를 따른다.

중복·한도·찜 같은 요청별 거절은 해당 요청의 결과에 담는다.
Redis 재고 불일치 등으로 `CouponException`이 전파되면 해당 묶음을 롤백하고 모두 실패로 끝낸다.
이 문서의 시험 당시에는 그 밖의 `RuntimeException`에서 묶음을 반으로 나눠 각각 새 트랜잭션으로 재시도했다.
당시 코드는 데드락만 선별하지 않아 DB 접속 실패도 분할 재시도의 대상이었다.
이후 분할 재시도를 제거했다. 현재 처리는 [v3의 묶음 실패 설계](../../design/coupon/coupon-issuance-v3-design.md#5-요청별-거절과-묶음-실패를-구분한다)를 따른다.

요청의 대기 시간이 끝나도 작업자의 발급이 취소되지는 않는다.
그래서 Redis 완료 처리를 요청 스레드에서 작업자로 옮겼다. HTTP 대기 종료 뒤 커밋된 예약도 작업자가 완료한다.
메모리 대기열의 유실과 DB 커밋 결과 불명의 처리는 [장애 처리 설계](../../design/coupon/coupon_장애_처리_설계.md)를 따른다.

## 2. 묶음 커밋의 부하 시험 결과를 확인했다

### 실행 조건과 현재 코드의 차이

| 항목 | 측정 조건 |
|---|---|
| 대상과 자원 | 단일 이벤트에 서로 다른 회원이 요청했다. Java 21.0.11·MySQL 8.4.11·Valkey 9.0을 같은 Mac에서 사용했다. |
| 자원 상한 | Hikari 최대 8개와 JVM 최대 힙 2 GiB를 사용했다. Docker VM의 CPU 4개와 메모리 약 1.93 GiB를 MySQL·Valkey·k6가 공유했다. |
| 초기화 | 50 RPS·20초 워밍업 후 DB 발급 데이터와 Redis 큐를 초기화했다. 큐 초기화용 요청은 본 측정에서 제외했다. |
| 재고 | 300 RPS 시험은 18,200장, 1,000 RPS 시험은 30,200장, 피크 시험은 50,200장을 준비했다. |
| 묶음 설정 | 시작 로그에서 작업자 4개·최대 100건·대기열 2,000건을 확인했다. `peak-50k-batch-tuned`만 작업자 6개였다. |
| 현재 코드 | 현재 기본값은 작업자 4개·최대 500건이다. 100건 상한으로 측정한 결과를 현재 기본값의 검증으로 사용하지 않는다. |
| MySQL 진단 | 앞선 시험에서 binlog 커밋 설정을 변경한 기록이 있다. 각 실행의 DB 설정 전체 스냅샷은 없어 기본 설정에서의 결과로 단정하지 않는다. |
| 코드 식별 | 미커밋 구현을 바꿔 가며 측정했고 실행 JAR도 교체했다. 현재 남은 JAR나 초기 source-manifest만으로 모든 실행의 소스를 재현할 수 없다. |

아래 수치는 실행별 `analysis.json`에서 옮겼다. P95·P99는 201 응답의 지연이며 단위는 ms다.
미전송은 k6가 시작하지 못한 반복 수다. HTTP 시도와 미전송의 합이 예정 수와 다를 때도 원자료 값을 유지했다.
미전송이 있는 실행을 설정 RPS만큼 실제 요청을 보낸 시험으로 판단하지 않는다.
v1은 비동기 퍼널 저장을 켜고 측정했으므로 로그 저장을 끈 v2·v3와 같은 조건의 배수 비교는 하지 않는다.

### 퍼널 DB 저장을 끈 시험

| 실행 | 유입 | HTTP 시도 | 201 | 500·503 | 미전송 | 성공 P95 | 성공 P99 |
|---|---|---:|---:|---:|---:|---:|---:|
| `hot-300-60s-control` | 단건, 300 RPS·60초 | 16,337 | 16,337 | 0 | 1,663 | 3,354.48 | 3,486.89 |
| `hot-300-60s-batch2` | 묶음, 300 RPS·60초 | 18,000 | 18,000 | 0 | 0 | 95.23 | 168.75 |
| `rps1000-30s-single` | 단건, 1,000 RPS·30초 | 9,310 | 9,310 | 0 | 20,692 | 4,453.80 | 4,676.72 |
| `rps1000-30s-batch` | 묶음, 1,000 RPS·30초 | 30,000 | 30,000 | 0 | 0 | 784.23 | 859.18 |
| `peak-50k-single` | 단건, 50,000건 피크 | 8,404 | 8,404 | 0 | 41,601 | 6,368.79 | 7,184.74 |
| `peak-50k-batch` | 묶음, 50,000건 피크 | 32,187 | 32,187 | 0 | 17,805 | 1,042.75 | 1,224.81 |
| `peak-50k-batch-tuned` | 작업자 6개, 50,000건 피크 | 24,409 | 24,409 | 0 | 24,318 | 1,498.17 | 1,926.04 |

피크는 첫 10초에 2,500 RPS, 다음 20초에 1,250 RPS를 설정한 시나리오다.
위 실행의 네트워크 실패는 0건이었고 퍼널 DB 저장도 0건이었다.
300 RPS의 VU 상한은 800개였다. 1,000 RPS는 1,000개, 피크는 두 유입 구간에 각각 1,000개였다.

묶음의 300 RPS 재측정은 전송·발급·지연 목표를 통과했다.
앞선 `hot-300-60s-batch`는 17,873건 성공과 503 응답 127건이 있었으므로 성공한 재측정과 구분한다.
1,000 RPS는 전부 발급했지만 P95 700ms 목표를 넘었다. 50,000건 피크도 미전송과 지연 때문에 목표에 미달했다.
작업자를 6개로 늘린 피크 실행은 개선되지 않았다.

### 커밋과 디스크 동기화 관측도 함께 비교했다

| 1,000 RPS 실행 | 발급 성공 | COMMIT 호출 증가 | COMMIT 누적 시간(ms) | `Innodb_os_log_fsyncs` 증가 |
|---|---:|---:|---:|---:|
| `rps1000-30s-single` | 9,310 | 9,278 | 55,121.67 | 18,684 |
| `rps1000-30s-batch` | 30,000 | 1,435 | 14,989.66 | 8,499 |

COMMIT은 `digest-after.json`에서 `digest-before.json`을 뺀 값이다.
이 측정에서는 더 많은 발급을 더 적은 명시적 COMMIT 호출로 처리했다.
fsync는 DB 전체 지표이며 COMMIT 수와 일대일로 대응하지 않는다. digest 집계도 최종 발급 수와 정확히 일치하지 않는다.
따라서 이 표는 여러 요청이 커밋 비용을 나누는 방향을 뒷받침하며 순수한 커밋 비용 절감률을 증명하지 않는다.

묶음에서 DB 행 잠금 대기가 모두 0이 된 것은 아니다.
`hot-300-60s-batch2`는 3회·합계 54ms, `rps1000-30s-batch`는 11회·합계 445ms와 데드락 1회를 기록했다.
`peak-50k-batch`도 데드락 1회가 있었다. 재시도 뒤 HTTP가 성공한 사실과 DB 오류가 없었다는 주장은 구분한다.

### 비동기 퍼널 DB 저장을 켜면 공유 자원 경합이 다시 드러났다

| 실행 | 퍼널 저장 | HTTP 시도 | 201 | 500 | 미전송 | 성공 P95 | 성공 P99 | 저장된 issue 이벤트 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| `rps500-60s-single-logs` | 켰다. | 15,721 | 15,565 | 156 | 14,280 | 7,796.70 | 9,540.98 | 1,219 |
| `rps500-60s-batch-logs` | 켰다. | 27,614 | 27,614 | 0 | 2,387 | 2,815.27 | 5,148.86 | 7,395 |
| `rps500-60s-batch-logs-q10k` | 켰고 퍼널 큐를 10,000개로 바꿨다. | 23,881 | 23,881 | 0 | 6,055 | 2,483.83 | 3,885.86 | 12,144 |
| `rps500-60s-batch-nologs` | 껐다. | 28,378 | 28,378 | 0 | 1,623 | 2,389.34 | 4,758.08 | 0 |

각 실행은 500 RPS·60초와 VU 상한 1,000개를 사용했다. 네트워크 실패와 503은 0건이었다.
로그 저장을 끈 결과에도 미전송과 긴 지연이 남았으므로 500 RPS를 안정적으로 처리했다고 판단하지 않는다.
저장된 issue 이벤트 수만으로 모든 차이를 큐 거절로 단정하지 않는다. 유실·실패·잔여 작업의 분류에는 리스너 지표를 함께 봐야 한다.
또한 30초 시험과 60초 시험의 차이가 있어 1,000 RPS의 결과를 장시간 처리량으로 일반화하지 않는다.
위 로그 비활성화는 당시 부하용 설정이며 현재 코드에서 퍼널 저장을 제거한 변경은 아니다.

## 3. 발급 정합성과 남은 검증을 구분했다

위 표의 실행들은 회원 쿠폰 수·ISSUED 재고 수·일일 카운터 합이 발급 성공 수와 일치했다.
성공 응답 ID와 DB 쿠폰 ID를 대조한 결과 양쪽에서 빠진 쿠폰은 0건이었다.
이벤트·회원 중복과 일일 한도 초과, 재고 초과, 재고 코드 연결 오류와 카운터 불일치도 0건이었다.
이는 해당 부하 데이터의 결과다. 같은 회원의 동시 요청과 장애의 모든 조합을 증명하지 않는다.

현재 코드는 회원 상태와 찜을 아직 단건 공개 계약으로 조회한다.
묶음 커밋 뒤에도 이 조회는 남아 있으며 일괄 조회는 [#577](https://github.com/lunch-catch/lc-backend/issues/577)과 [#578](https://github.com/lunch-catch/lc-backend/issues/578)에 연결돼 있다.
다른 도메인의 저장소를 직접 JOIN해 이 계약을 우회하지 않았다.

현재 기본 묶음 크기 500건과 후속 예약 완료 처리의 성능은 다시 측정해야 한다.
실제 Redis 재시작·페일오버와 네트워크 분리, 여러 애플리케이션의 동시 복구도 이 부하 시험의 검증 범위 밖이다.
현재 구현은 한 이벤트의 Redis 준비 실패가 같은 묶음의 다른 이벤트 요청에도 영향을 줄 수 있다.
해당 제약을 해결한 것으로 기록하지 않는다.
