# 쿠폰 발급 장애 상황과 대응 결과

## 요약

연결 장애에서는 잘못된 발급을 막고, 연결이 돌아온 뒤 DB를 기준으로 Redis를 복구해 발급을 이어갔다. 서버 종료 시험에서도 발급 기록은 유지됐지만 반복 복구와 요청 실패가 나타났다.

| 장애 상황 | 어떻게 대응했는지 | 확인한 결과 |
|---|---|---|
| Redis 연결이 끊기거나 응답이 늦었다 | 발급을 잠시 막고 연결 복구 후 Redis를 다시 맞췄다 | 저장 내용은 바뀌지 않았고 다음 요청은 발급에 성공했다 |
| DB 연결이 끊겼다 | 발급을 중단했다. 이미 예약한 번호는 DB 기록을 확인한 뒤 정리했다 | 연결 복구 후 발급에 성공했다 |
| DB 저장 후 Redis에 완료를 알리지 못했다 | DB에 저장된 발급은 성공으로 유지했다 | 첫 쿠폰이 그대로 남았고 다음 요청도 성공했다 |
| 발급 중 서버가 갑자기 꺼졌다 | 재시작 후 새 요청이 DB를 확인해 남은 예약을 정리했다 | 새 요청 400건이 성공했고 예약 37개가 정리됐다 |
| 처리 중인 서버에 정상 종료를 요청했다 | 현재 코드는 웹 요청 정리 뒤에 발급 작업자를 종료하도록 순서를 정했다 | 과거 시험에서는 종료 전에 보낸 요청 150건도 503을 받았다 |

연결 장애는 2026-10-26에 현재 코드를 대상으로 로컬 전용 프록시 테스트로 확인했다. 시험 코드는 저장소에 포함하지 않고 결과만 기록한다. 서버 종료 수치는 2026-10-23 당시 빌드의 결과이며 현재 코드로 다시 측정하지 않았다. 남은 문제는 [문서 맨 아래](#아직-남은-문제)에 모았다.

DB는 실제 쿠폰 발급 기록을 저장하고, Redis는 발급할 재고 번호를 예약한다. 이 문서에서 “복구”는 DB 기록을 확인해 Redis의 남은 재고와 예약 상태를 다시 맞추는 작업이다.

## 1. Redis 연결이 끊기거나 응답이 늦어졌다

### 장애 상황과 시험 시나리오

Redis에 연결할 수 없는 상태에서 쿠폰 발급을 요청했다. 연결은 되지만 응답이 제한 시간보다 늦게 오는 경우도 시험했다.

### 어떻게 대응했는지

재고 번호를 제대로 예약했는지 알 수 없으므로 발급을 멈췄다. 해당 이벤트를 일시적으로 차단해 다른 요청도 불확실한 재고를 사용하지 못하게 했다.

연결이 돌아오면 다음 발급 요청이 DB를 확인해 Redis를 복구한다. 복구에 성공한 요청은 발급을 이어간다.

### 확인한 결과

장애 중에는 일시적 발급 불가 오류가 발생했다. 쿠폰 저장, 재고 차감, 회원의 발급 횟수는 바뀌지 않았다. 연결이나 응답 지연을 복구한 뒤에는 다음 요청이 발급에 성공했고 DB와 Redis의 수량도 일치했다.

이 오류는 API에서 503으로 응답하는 대상이다. 로컬 시험은 발급 서비스의 오류와 저장 상태를 확인했으며 실제 HTTP 응답 수신까지 검사하지는 않았다.

## 2. 발급 도중 DB 연결이 끊겼다

### 장애 상황과 시험 시나리오

두 시점에 DB 연결을 끊었다. 하나는 발급을 시작하기 전이고, 다른 하나는 Redis에서 재고 번호를 예약한 뒤 DB에 저장하려는 순간이다.

### 어떻게 대응했는지

발급을 시작하기 전에 DB 연결이 끊기면 오류로 끝낸다. Redis에서 재고 번호를 예약하는 단계까지 진행하지 않는다.

번호를 예약한 뒤 연결이 끊기면 그 번호를 바로 재고에 돌려놓지 않는다. 앱이 DB 응답을 못 받았더라도 저장은 끝났을 수 있기 때문이다. 해당 이벤트를 차단하고 다음 요청이 DB 기록을 확인해 Redis를 복구하도록 한다.

### 확인한 결과

| 연결을 끊은 시점 | 확인한 결과 |
|---|---|
| 발급 시작 전 | DB 연결 오류로 끝났다. 쿠폰·재고·회원 발급 횟수는 바뀌지 않았고 Redis 예약도 하지 않았다 |
| Redis 예약 후, DB 저장 시점 | DB 연결 오류로 끝났다. 이 시험에서는 쿠폰이 저장되지 않았고 예약 번호는 Redis에 남았다. 연결 복구 후 다음 요청이 예약을 정리하고 발급에 성공했다 |

DB 연결 오류는 API에서 500으로 응답하는 대상이다. 이 시험도 실제 HTTP 응답이 아니라 발급 서비스의 오류와 저장 상태를 확인했다.

## 3. DB에는 저장됐는데 Redis에 완료를 알리지 못했다

### 장애 상황과 시험 시나리오

쿠폰을 DB에 저장한 직후 Redis 연결을 끊었다. 발급은 끝났지만 Redis에 완료를 표시할 수 없는 상황이다.

### 어떻게 대응했는지

이미 DB에 저장된 쿠폰은 발급 성공으로 유지했다. Redis에 완료를 알리지 못했다는 이유로 같은 쿠폰을 다시 발급하거나 예약 번호를 재고에 돌려놓지 않았다.

대신 해당 이벤트를 차단했다. 다음 요청이 DB 기록을 확인해 이미 발급된 재고를 제외하고 Redis를 복구하도록 했다.

### 확인한 결과

첫 요청은 성공했고 DB에 쿠폰 1장이 저장됐다. 연결 복구 후 다른 회원이 요청했을 때도 발급에 성공했다. DB와 Redis의 발급 수는 2개로 일치했다.

## 4. 발급 중 서버가 갑자기 꺼졌다

### 장애 상황과 시험 시나리오

2026-10-23에 이벤트 20개와 이벤트당 재고 100장, 총 2,000장을 준비했다. 회원 1,200명이 6초 동안 한 번씩 요청하는 도중 앱 서버를 강제로 종료했다. 서버가 진행 중인 작업을 정리할 기회 없이 꺼지는 상황이다.

### 어떻게 대응했는지

DB에 저장된 쿠폰은 그대로 유지했다. 서버가 꺼져 Redis에 남은 예약은 다음 발급 요청이 DB를 확인해 정리하도록 했다.

응답을 못 받은 회원이 다시 요청하면 DB의 발급 기록을 확인한다. 이미 쿠폰을 받은 회원에게 같은 쿠폰을 다시 발급하지 않는다.

### 확인한 결과

| 사용자가 확인한 결과 | 요청 수 |
|---|---:|
| 성공 응답을 받았다 | 47건 |
| 처리 도중 연결이 끊겨 응답을 받지 못했다 | 425건 |
| 서버가 꺼진 뒤 연결이 거절됐다 | 728건 |

성공 응답 47건은 모두 DB에 쿠폰이 저장돼 있었다. 응답을 못 받은 요청은 합계 1,153건이었고, **그중 61건도 DB에 쿠폰이 저장돼 있었다.** 저장을 끝낸 뒤 응답을 보내기 전에 서버가 꺼진 경우다.

Redis에는 처리 중인 예약 37개가 남았다. 해당 요청의 DB 저장 작업은 되돌려졌다. 예약과 별개로 DB와 Redis의 발급 완료 수는 이벤트 20개 모두 일치했다.

서버를 다시 켠 뒤의 결과는 다음과 같다.

1. 서버 시작만으로는 남은 예약이 정리되지 않았다.
2. 서버가 꺼진 지 30초 뒤 새 요청 400건을 보냈다. 모두 발급에 성공했고 예약 37개도 정리됐다.
3. 응답을 못 받았지만 쿠폰이 저장돼 있던 61명은 재요청에서 모두 “이미 발급받음”(409)을 받았다. 저장되지 않은 회원 중 60명은 모두 발급에 성공했다.

최종 쿠폰 수와 회원별 발급 횟수는 예상과 일치했다.

## 5. 발급 요청을 처리하던 서버에 정상 종료를 요청했다

### 장애 상황과 시험 시나리오

2026-10-23에 앞과 같은 재고와 요청을 준비했다. 발급 요청을 처리하는 도중 서버에 정상 종료 신호를 보냈다. 서버가 이미 받은 요청을 마무리한 뒤 꺼지는지 확인하는 시험이다. 배포할 때 기존 앱이 종료되는 상황을 재현했다.

### 어떻게 대응했는지

현재 코드는 웹 요청을 정리하는 단계 뒤에 발급 작업자를 종료하도록 순서를 정했다. 발급 작업자를 종료할 때는 새 접수를 막고 아직 DB 저장을 확정하지 않은 요청을 취소한다. 진행 중인 작업에는 종료를 기다릴 기한을 둔다.

복구 작업의 종료 대기가 중단돼도 실행 중이거나 대기 중인 요청의 결과를 끝내도록 처리한다. 이 동작은 현재 단위 테스트에서 확인했다.

### 확인한 결과

| 요청을 보낸 시점 | 발급 성공(201) | 일시적 처리 불가(503) |
|---|---:|---:|
| 종료 신호 전 | 333건 | 150건 |
| 종료 신호 후 | 0건 | 717건 |

서버는 종료 요청을 받은 뒤 9초 만에 꺼졌다. 모든 요청이 응답을 받았고 Redis에 처리 중으로 남은 예약은 없었다.

## 아직 남은 문제

### 1. 같은 이벤트를 여러 요청이 반복해서 복구한다

현재 코드는 같은 서버에서 같은 이벤트를 동시에 복구하는 작업을 하나로 제한한다. 그러나 대기 중인 요청은 앞선 복구가 끝났는지 다시 확인하지 않아 같은 작업을 차례로 반복할 수 있다. 복구를 시작하기 직전에 이미 복구됐는지 확인하는 처리가 아직 필요하다.

### 2. 정상 종료 전에 받은 요청도 실패할 수 있다

당시에는 종료 전에 보낸 요청 150건도 발급을 마치지 못했다. 발급 작업자도 종료됐고, 결과를 기다리던 요청이 취소됐다.

데이터가 잘못되지는 않았지만 사용자는 다시 발급을 시도해야 했다

### 3. 새 발급 요청이 없으면 복구가 시작되지 않는다

복구는 다음 발급 요청이 들어와야 시작한다. 요청이 없으면 Redis의 남은 예약도 바로 정리되지 않는다.
