# 쿠폰 성능테스트 통합 요약

2026-10-26 AWS에서 v1, v2, v3 백엔드를 각각 3회, 총 9회 측정했다. 아래 대표값은 버전별 3회 평균이다.

## 시나리오

| 항목 | 조건 |
|---|---|
| 대상 API | POST /v1/coupons, 본문에 eventId를 보낸다. |
| 데이터 | 이벤트 20개, 이벤트당 재고 100장, 총 2,000장 |
| 요청 | 회원 5,000명이 각각 한 번 요청한다. 이벤트당 250건을 배분한다. |
| 유입 | 처음 100명은 즉시 요청한다. 이후 4,900명은 10초에 걸쳐 요청한다. 10초 구간의 평균 유입은 500요청/초다. |
| 기대 결과 | 발급 2,000건과 재고 소진 3,000건이며 자동 재시도는 없다. |
| 실행 | 워밍업 후 버전별 3회 측정한다. 매회 재고와 시험 데이터를 초기화한다. |
| 분리 | 버전별 DB와 Redis 논리 DB를 분리한다. 공유 RDS에 부하가 겹치지 않도록 순차 실행한다. |
| 수집 | Tomcat, DB 연결과 연결 대기를 1초 단위로 기록한다. |
| 설정 | Tomcat 최대 쓰레드 수 200개, DB 연결 상한 8개, v3 작업자 4개를 사용한다. |

워밍업 결과는 평균에서 제외했다. 같은 버전의 세 회차 사이에는 JVM을 재시작하지 않았다.

단위는 개다. Tomcat 최대 쓰레드 수는 설정값 200개다. 나머지 열은 각 회차에서 관측한 최대값을 세 회에 걸쳐 평균냈다.

DB 연결 사용은 전체 관측값에서 로깅용 2개를 구분해 `쿠폰 처리용 + 로깅용`으로 표시했다. `+2`는 로깅용 연결이다.

## 집계 기준

평균 요청 수는 각 회차의 실제 요청 5,000건을 요청을 보낸 10초로 나눈 뒤 세 회를 산술평균했다. 세 버전 모두 초당 평균 500건이다.

p95와 p99는 회차별 발급 성공 응답의 백분위수를 산술평균했다. HTTP 오류와 통계 유실은 회차별 건수를 평균냈으므로 소수로 표시될 수 있다. 정상 소진 409는 HTTP 오류에서 제외하며, 통계 유실은 처리 종료 후 실패 또는 거절로 끝난 건수다.

“Tomcat 쓰레드 최대 활성화 수”는 생성되어 유지된 HTTP 스레드 수(current)의 회차별 최대값을 평균낸 값이다. 유휴 스레드도 포함한다. v3는 80·90·97개의 평균인 89개다. DB 연결 대기는 연결을 기다리는 스레드 수다. 1초보다 짧은 피크는 관측에서 빠질 수 있다.

## 병목

| 버전 | 확인한 현상 |
|---|---|
| v1 | DB 연결 대기와 통계 작업 거절이 발생했다. |
| v2 | DB 연결 대기와 통계 작업 거절이 발생했다. |
| v3 | 이번 부하에서 포화 병목을 확인하지 못했다. HTTP 오류와 통계 유실은 없었다. |

v3 첫 회 p99는 1,112.6ms로 측정 스크립트의 1,000ms 기준을 초과했다. 평균값과 함께 해당 지연을 원본에 남겼다.

모든 회차에서 HTTP 발급 성공 2,000건과 DB 발급 2,000건이 일치했다. 쿼리별 실행 통계가 제공되지 않아 DB 내부의 특정 쿼리를 병목 원인으로 확정하지 않았다. 측정 대상은 기존 AWS 비교에 사용했던 백엔드 이미지이며 현재 체크아웃 코드의 결과로 해석하지 않는다.
