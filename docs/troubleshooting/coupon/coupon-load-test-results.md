# 쿠폰 v3 부하 시험 대표 결과

2026-10-22에 측정한 결과다. 로컬과 AWS에서 각각 가장 좋은 설정으로 끝까지 실행한 6회를 정리했다. 한 회의 최저값을 골라 합치지 않았으며 준비 부하와 중간 실험은 본 측정에 포함하지 않았다.

**아래 결과는 당시 JAR·이미지의 성능이다. 이후 공통 코드와 설정 변경을 제외했으므로 현재 코드의 성능으로 해석하면 안 된다.** 현재 코드와의 차이는 [아래 절](#현재-코드와의-차이)에 기록한다.

## 시험 조건

| 항목 | 조건 |
|---|---|
| 시나리오 | 캠페인 20개, 캠페인당 재고 100장, 전체 재고 2,000장 |
| 요청 | 서로 다른 회원 5,000명, 캠페인당 250건 |
| 부하 | 처음 100건을 보낸 뒤 나머지 4,900건을 10초에 걸쳐 전송 |
| 스크립트 | AWS에서 사용한 `coupon-multi-event.js`와 같은 스크립트, 자동 재시도 없음 |
| 반복 | 새 JVM 3개에서 각각 2회, 준비 부하 안정화 확인 후 본 측정 |
| 데이터 초기화 | 각 회차 전에 이전 작업 종료를 확인하고 DB·Redis의 시험 데이터 초기화 |
| 발급 처리 | 워커 4개, 묶음 최대 500건, 수집 대기 최대 20ms, 미완료 요청 상한 2,000건 |
| 연결·스레드 | Hikari 최대 8개, Tomcat 최대 200개 |
| JVM 힙 | `-Xms256m -Xmx768m` |
| 성능 목표 | 발급 성공 응답 p95 ≤ 700ms, p99 ≤ 1,000ms |

| 환경 | 애플리케이션 | DB·Redis | 부하 발생기 |
|---|---|---|---|
| 로컬 | M1 Mac 8코어·8GiB, Java 21.0.11 | 같은 Mac의 Docker MySQL·Valkey | 같은 Mac의 k6 |
| AWS | c7i.2xlarge 8 vCPU·16GiB, Java 21.0.9 | RDS db.t4g.micro, Redis cache.t4g.micro | 별도 m7i-flex.large |

로컬은 앱·DB·Redis·k6가 자원을 공유한다. AWS는 DB와 Redis가 별도 서버에 있다. 하드웨어와 측정 빌드도 달라 환경 간 차이를 코드의 개선율로 계산하지 않는다. AWS 대표 결과는 t3.small의 결과가 아니다.

## 로컬: 6회 모두 성능 목표 통과

시간 단위는 ms다. 성공 p95·p99는 HTTP 201 응답만, 소진 p95는 HTTP 409의 소진 응답만 집계했다.

| JVM-회차 | 성공 p95 | 성공 p99 | 소진 p95 | 성능 목표 |
|---|---:|---:|---:|---|
| 1-1 | 624.7 | 820.0 | 29.1 | 통과 |
| 1-2 | 342.8 | 364.1 | 93.2 | 통과 |
| 2-1 | 472.7 | 609.3 | 28.5 | 통과 |
| 2-2 | 325.4 | 346.4 | 16.8 | 통과 |
| 3-1 | 501.5 | 600.6 | 54.1 | 통과 |
| 3-2 | 206.8 | 232.9 | 37.3 | 통과 |

가장 빠른 회차는 3-2이며 성공 p95 206.8ms, p99 232.9ms였다. 6회 모두 k6 종료 코드가 0이었다.

## AWS: 6회 모두 500·503 없이 처리, 성능 목표는 5회 통과

같은 최종 이미지와 힙으로 JVM 3개에서 각각 2회 실행했다. Tomcat 처리 객체 캐시를 늘린 중간 실험은 채택하지 않았고 기본값 200을 사용했다.

| JVM-회차 | 성공 p95 | 성공 p99 | 소진 p95 | 성능 목표 |
|---|---:|---:|---:|---|
| 1-1 | 339.7 | 365.5 | 7.4 | 통과 |
| 1-2 | 192.7 | 212.4 | 6.4 | 통과 |
| 2-1 | 391.0 | 1,116.4 | 6.7 | p99 초과 |
| 2-2 | 193.7 | 200.2 | 19.2 | 통과 |
| 3-1 | 356.6 | 382.3 | 6.5 | 통과 |
| 3-2 | 400.4 | 415.3 | 6.4 | 통과 |

성공 p95는 모두 500ms 이내였다. 최저 p95는 1-2의 192.7ms, 최저 p99는 2-2의 200.2ms로 서로 다른 회차다.

2-1의 p99 초과 원인은 확정하지 못했다. 해당 회차의 DB 연결 획득 최대는 약 51.6ms, 연결 사용 최대는 329ms였고 연결 획득 시간 초과는 없었다. DB 연결 대기만으로 전체 지연을 설명할 수 없다. AWS CPU 프로파일을 회수하지 못해 JVM 정지·HTTP 대기·외부 시스템 왕복의 영향을 분리하지 못했다.

## 응답과 데이터 정합성

아래 수치는 로컬 6회와 AWS 6회에서 각각 확인했다.

| 항목 | 회차당 | 환경별 6회 합계 |
|---|---:|---:|
| 전체 요청 | 5,000 | 30,000 |
| 발급 성공 HTTP 201 | 2,000 | 12,000 |
| 소진 HTTP 409, `COUPON-006` | 3,000 | 18,000 |
| HTTP 500 | 0 | 0 |
| HTTP 503 | 0 | 0 |
| 그 외 응답·요청 누락 | 0 | 0 |
| 발급 통계 기록 | 2,000 | 12,000 |
| 통계 유실 | 0 | 0 |

모든 회차에서 캠페인당 성공 100건·소진 150건을 확인했다. DB 발급 수와 Redis 완료 수는 각각 100개였다. Redis 상태는 `SOLD_OUT`이며 남은 재고와 대기 예약은 0개였다.

정상 부하에서 오류가 없었다는 결과다. 장시간 운용이나 DB·Redis 장애에서도 503이 없다는 보장은 아니다. 커밋 여부를 확인할 수 없는 장애에는 실패 응답을 유지한다.

## 측정 빌드에 적용했던 개선과 비용

- Redis에서 소진을 먼저 판단해 소진 요청의 반복 DB 접근을 줄였다. 묶음의 소진 조회와 예약은 파이프라인으로 보내 이벤트별 왕복 대기를 줄였다.
- 배처 앞의 중복된 200건 제한을 제거하고 최대 20ms 동안 요청을 모았다. 워커 4개와 묶음 상한 500건은 유지했다. 요청이 적을 때에는 기존 5ms 대비 최대 15ms 더 기다릴 수 있다.
- Redis 부분 실행 여부가 불확실하면 관련 이벤트를 차단했다. 장애 시 잘못된 추가 발급을 막지만 복구 전까지 해당 이벤트의 발급이 제한된다.
- AWS 빌드에는 Redis 연결 풀과 JWT 파서 재사용도 적용했다. 풀은 연결 생성 비용을 줄이는 대신 유휴 연결을 유지한다. JWT 서명·만료 검증은 요청마다 수행했다.
- AWS 앱 서버를 8 vCPU·16GiB로 늘렸다. 비용이 증가하며 CPU와 메모리를 함께 바꿔 각각의 기여도는 분리하지 못했다. 작은 서버의 성능 문제가 코드만으로 해결됐다는 결과는 아니다.

쿠폰의 현재 구조와 장애 처리 기준은 [v3 설계](../../design/coupon/coupon-issuance-v3-design.md)와 [장애 처리 설계](../../design/coupon/coupon_장애_처리_설계.md)가 소유한다.

## 현재 코드와의 차이

측정 이후 사용자 요청에 따라 공통 필터·설정·보안·메트릭과 다른 도메인의 수정을 변경 범위에서 제외했다.

- 비동기 HTTP 응답을 기존 동기 응답으로 되돌렸다. 발급 결과를 기다리는 동안 Tomcat 요청 스레드를 점유한다.
- JWT 최적화와 wishlist의 여러 캠페인 일괄 조회를 제외했다. 찜 조회는 기존 공개 계약을 캠페인당 한 번 호출한다.
- Redis 연결 풀을 추가했던 의존성과 설정을 제외했다. 파이프라인은 기존 연결 설정을 따른다.
- 쿠폰 내부의 묶음 발급과 Redis 소진 확인·예약 완료는 유지했다.

제외 후 Java 21의 `compileJava`만 성공했다. **현재 코드로 테스트나 부하 시험을 다시 실행하지 않았다.** 이 문서를 정리하면서도 추가 실행하지 않았다.
