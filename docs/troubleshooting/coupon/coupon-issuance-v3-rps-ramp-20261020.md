# 쿠폰 발급 v3의 RPS를 100부터 높인 30초 부하 시험

2026-10-20에 현재 작업 디렉터리의 v3를 새로 빌드해 측정했다. 문서의 시각은 한국 시간이다.
퍼널 저장 거절은 최초 상승 시험의 400 RPS에서 처음 관측했다. API 지연과 전송 목표는 900 RPS에서 통과했으며 1,000 RPS의 두 실행에서 모두 미달했다. 전송된 요청의 HTTP 5xx와 네트워크 실패는 없었다.

현재 구현의 구조는 [v3 설계](../../design/coupon/coupon-issuance-v3-design.md)가 소유한다.
묶음 커밋을 도입할 때의 과거 측정은 [v3 개선 기록](./coupon-issuance-v3-improvement-comparison.md)에 있다.

## 시험 조건

| 항목 | 조건 |
|---|---|
| 코드 | HEAD `58f0e29d`에 기존 미커밋 변경이 있는 작업 디렉터리를 `./gradlew bootJar`로 빌드했다. 소스의 SHA-256 목록과 JAR의 SHA-256을 원자료에 보관했다. |
| API | `POST /v1/coupons`에 `eventId=10000`을 전달했다. v3는 HTTP 경로의 버전이 아니라 발급 구현의 버전이다. |
| 데이터 | ACTIVE 회원마다 한 번씩 같은 이벤트의 쿠폰을 발급했다. 회원의 찜과 충분한 재고를 준비해 업무 거절을 유도하지 않았다. |
| 유입 | k6의 `constant-arrival-rate`로 100 RPS부터 각 단계에 30초 동안 요청을 시작했다. 응답 대기는 별도이며 최대 60초를 허용했다. |
| 부하 발생기 | `grafana/k6:2.2.0` 컨테이너에 VU 1,000개를 미리 할당했다. 메모리 상한은 700 MiB다. |
| 애플리케이션 | Java 21.0.11의 단일 JVM을 Mac 호스트에서 실행했다. 초기 힙은 512 MiB이며 최대 힙은 2 GiB다. |
| 발급 설정 | 작업자 4개, 묶음 상한 500건, 발급 대기열 2,000건, 결과 대기 상한 10초를 사용했다. |
| 공유 자원 | Hikari 커넥션 최대 8개와 Tomcat 요청 스레드 최대 200개를 사용했다. 비동기 퍼널 DB 저장을 켰다. |
| DB | MySQL 8.4.11의 버퍼 풀은 128 MiB다. `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, binlog ON을 기록했다. |
| Docker | CPU 4개와 메모리 2,068,389,888바이트인 Docker VM에서 MySQL·Valkey·k6를 함께 실행했다. MySQL 컨테이너는 900 MiB, Valkey는 128 MiB로 제한했다. |
| 격리 | 기존 쿠폰 전용 DB `coupon_redis`와 포트 23306·26379를 사용했다. 시험 전 DB 덤프를 보관했다. |
| 준비 | 50 RPS·20초로 워밍업했다. 본 측정의 단계마다 종료 검증을 마친 뒤 다음 단계의 DB 발급 데이터와 Redis 순번 키를 초기화했다. |
| Redis 초기화 | 본 측정에 쓰지 않는 회원으로 초기화·복구 요청을 수행했다. 준비 중 503과 준비용 발급 1건은 본 측정의 HTTP·발급 수에서 제외했다. |
| 관측 | 단계마다 HTTP 원자료, Prometheus 전후 지표, DB 상태와 SQL digest 전후 값, 주기적인 잠금·자원 표본과 스레드 덤프를 수집했다. |

발급 시간만 `00:00:00`부터 `23:59:59`까지로 열었다. 운영 외부 연동 키는 로컬 시험용 값을 사용했다.
스케줄러와 시드 입력은 껐다. 퍼널 저장과 묶음 크기 등 발급 처리 설정은 측정 도중 바꾸지 않았다.

## 판정 방법

지연과 오류율은 [발급 성능 목표](../../design/coupon/coupon-api-design.md#발급-성능-목표)를 기준으로 비교한다.
P95는 700ms 이하, P99는 1,000ms 이하이며 HTTP 5xx와 네트워크 실패율은 0.1% 이하가 목표다.
이번 시험은 일정 RPS를 단계마다 30초 동안 유지하므로 원래 목표의 50,000건 피크 시나리오를 검증한 것은 아니다.

다음 실패를 구분한다.

- API가 500·503을 반환하거나 네트워크 요청이 실패하면 응답 실패로 기록한다.
- 응답이 모두 성공해도 P95·P99 기준을 넘으면 지연 목표에 미달한 것으로 기록한다.
- `dropped_iterations`가 있으면 부하 발생기가 예정된 요청을 시작하지 못한 것이다. 설정 RPS를 모두 전송했다고 해석하지 않는다.
- 발급 정합성은 성공 응답 ID와 DB 쿠폰 ID, ISSUED 재고, 일일 카운터를 대조한다. 준비용 발급 1건은 ID 대조에서 제외한다.
- 퍼널 이벤트의 저장·실패·거절은 별도 지표로 분류한다. 발급 성공과 통계 저장 성공을 같은 결과로 취급하지 않는다.

## 측정 결과

본 측정에서 전송한 요청은 모두 `201`이었다. HTTP 500·503과 네트워크 실패는 관측하지 못했다.
그렇더라도 퍼널 저장 거절과 지연 목표 미달, k6 미전송이 발생했다.

### 단계별 HTTP 결과

최초로 RPS를 올린 순서는 100, 200, 300, 400, 500, 600, 800, 1,000이다.
각 단계의 유입은 30초이며 P95·P99는 전송한 HTTP 요청의 응답 시간이다.

|---|---:|---:|---:|---:|---:|---|
| 100 | 3,000 | 3,000 | 0 | 59.52 | 131.94 | 통과했다. |
| 200 | 6,000 | 6,000 | 0 | 50.95 | 87.89 | 통과했다. |
| 300 | 9,000 | 9,000 | 0 | 64.99 | 105.41 | 통과했다. |
| 400 | 12,000 | 12,000 | 0 | 126.67 | 452.96 | 통과했다. |
| 500 | 15,000 | 15,000 | 0 | 364.54 | 654.64 | 통과했다. |
| 600 | 18,000 | 17,962 | 0 | 283.95 | 404.53 | 예정 수보다 적게 전송했다. |
| 800 | 24,000 | 24,000 | 0 | 560.48 | 753.98 | 통과했다. |
| 1,000 | 30,000 | 24,747 | 5,254 | 1,627.73 | 1,877.55 | 지연과 미전송 기준을 넘었다. |

1,000 RPS에서는 VU 1,000개 한도에 도달해 더 높은 RPS로 올리는 시험을 멈췄다.
이후 같은 서버에서 900 RPS로 경계를 보완하고 1,000 RPS를 재측정했다. 마지막에는 100 RPS로 부하를 내려 복귀를 확인했다.

| 목표 RPS와 실행 | 예정 요청 | HTTP 전송 | k6 미전송 | P95(ms) | P99(ms) | HTTP 지연·전송 판정 |
|---|---:|---:|---:|---:|---:|---|
| 900 보완 | 27,000 | 27,000 | 0 | 623.95 | 709.56 | 통과했다. |
| 1,000 재측정 | 30,000 | 27,709 | 2,292 | 1,332.62 | 1,582.51 | 지연과 미전송 기준을 넘었다. |
| 100 복귀 | 3,000 | 3,000 | 0 | 28.43 | 74.40 | 통과했다. |

첫 1,000 RPS 실행의 완료 처리량은 k6 전체 실행 시간 기준 794.01 RPS였다.
유입 30초가 끝난 뒤에도 응답을 기다렸으므로 이 값과 `HTTP 전송 / 30초`는 분모가 다르다.

600 RPS 실행은 예정 18,000건 중 17,962건만 보냈지만 `dropped_iterations`는 0이었다.
남은 38건의 차이는 이번 자료로 원인을 분류하지 못했다. 600 RPS를 빠짐없이 생성한 실행으로 인정하지 않는다.
1,000 RPS의 두 실행은 HTTP 전송과 k6 미전송의 합이 각각 예정 수보다 1건 많았다.
표에는 k6 원자료의 값을 그대로 남겼으며 합계를 맞추기 위해 미전송 수를 바꾸지 않았다.

### 퍼널 저장 결과

단계가 끝난 뒤 `analytics_funnel_event_total`의 종료 결과 합이 발급 성공 수에 도달할 때까지 기다렸다.
아래 저장 수는 `result="recorded"`, 거절 수는 `result="rejected"`의 단계별 증가량이다.
DB의 `event_log` 행 수에서도 준비용 이벤트 1건을 빼면 같은 저장 수가 나온다.
기록 실패와 중복에 해당하는 나머지 결과의 증가량은 없었다.

| 100 | 3,000 | 3,000 | 0 | 0.00% |
| 200 | 6,000 | 6,000 | 0 | 0.00% |
| 300 | 9,000 | 9,000 | 0 | 0.00% |
| 400 | 12,000 | 11,814 | 186 | 1.55% |
| 500 | 15,000 | 9,465 | 5,535 | 36.90% |
| 600 | 17,962 | 9,880 | 8,082 | 44.99% |
| 800 | 24,000 | 8,595 | 15,405 | 64.19% |
| 1,000 | 24,747 | 8,038 | 16,709 | 67.52% |
| 900 보완 | 27,000 | 8,935 | 18,065 | 66.91% |
| 1,000 재측정 | 27,709 | 8,819 | 18,890 | 68.17% |

400 RPS에서 API의 지연·전송 기준은 통과했지만 통계 저장 거절이 먼저 시작됐다.
이는 쿠폰 발급 트랜잭션 실패와 다르다. `event_log`의 수집 한계와 원천 업무 집계의 관계는 [분석 API 설계](../../design/analytics/analytics-api-design.md)가 소유한다.
이번 시험에는 퍼널 유실률의 별도 허용 기준을 새로 정하지 않았다. 위 표는 거절이 발생한 사실과 규모를 기록한다.

## 병목을 판단한 근거

### 퍼널 저장이 유입을 따라가지 못했다

400 RPS의 발급 성공 12,000건 중 186건이 퍼널 저장 전에 거절됐다.
1,000 RPS의 첫 실행에서는 24,747건 중 16,709건이 거절됐다.
종료 결과를 기다린 뒤 집계했으므로 이 거절을 아직 처리 중인 이벤트로 세지 않았다.

1,000 RPS의 스레드 덤프에서 `funnel-event-1`과 `funnel-event-2`는 모두 JDBC COMMIT 응답을 기다리고 있었다.
퍼널 저장 경로의 처리 한도가 먼저 드러났고 DB 커밋 지연도 함께 관측했다.
통계 저장을 끈 대조 시험은 수행하지 않았으므로 통계 저장이 발급 지연에 기여한 비율은 단정하지 않는다.

### 발급 작업자의 건별 I/O가 남아 있었다

1,000 RPS의 한 스레드 표본에서 Tomcat 요청 스레드는 200개였다.
이 중 198개가 `CouponIssueBatcher.submitAndAwait`에서 발급 결과를 기다리고 있었다.
발급 작업자 두 개는 회원 상태 조회 중이었고 다른 하나는 `CouponSequenceRepository.complete`에서 Redis 응답을 기다렸다.
800 RPS 표본에서도 작업자 세 개가 Redis 완료 응답을 기다리고 있었다.

1,000 RPS의 SQL digest 증가량은 회원 상태 조회 24,744회와 찜 조회 24,741회였다.
발급 24,747건과 거의 같은 횟수로 단건 자격 조회가 남아 있었다.
쿠폰 재고 UPDATE는 786회였으므로 쓰기를 묶은 뒤에도 이 조회까지 함께 줄어든 것은 아니다.
현재 코드의 작업자는 커밋 뒤 성공한 예약을 하나씩 완료한 다음 각 요청에 결과를 돌려준다.

관측한 현상은 다음 흐름과 맞는다.

**발급 작업자의 DB 조회·Redis 완료 대기 → HTTP 요청 스레드의 결과 대기 → 응답 지연 증가 → k6 VU 한도 도달과 미전송**

발급 대기열의 길이와 각 작업자 구간의 시간을 직접 계측하지는 않았다.
따라서 단건 조회와 Redis 왕복 중 하나만을 유일한 원인으로 확정하지 않는다.

### 커밋과 로그 파일 I/O의 비용이 컸다

SQL digest에서 COMMIT의 누적 실행 시간이 가장 컸다.
아래 COMMIT에는 쿠폰 발급뿐 아니라 퍼널 저장의 트랜잭션도 포함된다.
SQL digest의 집계 횟수는 HTTP 발급 수와 정확히 같지 않아 묶음당 발급 수의 정밀 계산에는 사용하지 않았다.

| 목표 RPS | COMMIT 횟수 | COMMIT 누적 시간(ms) | COMMIT 평균(ms) | 행 잠금 대기 증가 | Hikari active 최대 표본 | Hikari pending 최대 표본 |
|---|---:|---:|---:|---:|---:|---:|
| 100 | 5,911 | 9,019.99 | 1.53 | 0 | 6 | 0 |
| 300 | 15,983 | 35,606.92 | 2.23 | 0 | 6 | 0 |
| 500 | 12,982 | 38,911.88 | 3.00 | 0 | 6 | 0 |
| 800 | 9,950 | 31,716.03 | 3.19 | 0 | 6 | 0 |
| 1,000 | 8,824 | 31,040.95 | 3.52 | 0 | 6 | 0 |

첫 1,000 RPS에서 MySQL의 로그 파일 I/O 누적 대기는 InnoDB 로그 17,117.28ms와 binlog 14,420.68ms였다.
이 값은 여러 스레드와 호출의 누적값이다. SQL COMMIT 시간과 더해 HTTP 지연을 계산하지 않는다.
퍼널 작업자의 COMMIT 대기 표본과 함께 보면 DB 커밋·로그 I/O는 우선 확인할 비용이다.

반면 모든 본 측정에서 InnoDB 행 잠금 대기와 데드락 증가량은 0이었다.
Hikari active 표본의 최댓값은 6개였고 pending 표본은 모두 0이었다.
첫 1,000 RPS의 Hikari 획득 시간 합계도 약 28ms였다.
이번 결과를 재고 행 잠금이나 커넥션 8개의 포화로 설명할 근거는 없다.

첫 1,000 RPS에서 Redis의 연결 거절·키 축출·오류 응답 증가량은 모두 0이었다.
Redis 완료의 왕복 대기를 관측한 사실만으로 Redis 서버의 CPU 포화를 단정하지 않는다.
k6도 MySQL·Valkey와 같은 Docker VM을 사용했으므로 부하 발생기의 자원 비용이 섞여 있다.
서버만의 최대 처리량을 정하려면 부하 발생기를 분리한 재측정이 필요하다.

## 정합성과 시험의 한계

모든 본 측정에서 성공 응답 ID와 새 DB 쿠폰 ID가 일치했다.
DB의 회원 쿠폰 수·ISSUED 재고 수·일일 카운터 합도 준비용 1건을 포함해 서로 같았다.
이벤트·회원 중복, 일일 한도 초과, 재고 초과, 카운터 불일치와 쿠폰 코드 연결 오류는 모두 0건이었다.
HTTP 실패 뒤 DB만 커밋된 발급도 이번 데이터에서는 없었다.

마지막 100 RPS 시험은 높은 부하 뒤의 복귀를 확인한다.
시험 데이터와 Redis의 초기화는 거쳤지만 애플리케이션 프로세스는 다시 시작하지 않았다.
장애 중 같은 회원이 재시도하는 상황과 재고 소진, Redis 장애·복구, 여러 서버의 동시 발급은 검증 범위 밖이다.
10초 발급 대기 타임아웃과 발급 대기열 포화에 따른 HTTP 500·503도 이번 시험에서는 만나지 못했다.

900 RPS는 API 지연·전송 기준을 통과했지만 퍼널 저장 거절이 있었다.
900 RPS를 통계 수집까지 정상인 용량이나 장시간 유지 가능한 운영 한계로 정하지 않는다.
측정은 단계마다 30초였으며 같은 JVM의 JIT·캐시·GC 상태는 이어졌다.
진단 수집 비용과 로컬 Docker VM의 공유 자원도 결과에 포함된다.

초기 50 RPS 워밍업은 HTTP 1,000건을 모두 완료했다.
다만 다음 단계의 초기화가 워밍업의 종료 후 DB 검증과 겹쳤으므로 그 정합성 결과와 DB 증가량은 제외했다.
100 RPS 본 측정의 검증은 정상 완료됐으며 이후 단계는 검증 종료까지 직렬 실행했다.

## 다음 시험에서 분리할 항목

- 같은 900·1,000 RPS에서 퍼널 저장만 끈 대조로 DB 커밋 경합의 영향을 확인한다.
- 회원·찜의 단건 조회와 Redis 예약 완료의 왕복 시간을 각각 계측해 발급 작업자의 시간을 나눈다.
- 부하 발생기를 별도 환경으로 옮겨 같은 RPS를 빠짐없이 전송하는지 확인한다.
- 변경을 적용한 뒤에는 같은 조건을 반복하고 더 긴 실행으로 지연과 퍼널 거절이 계속 쌓이는지 확인한다.

이번 작업에서는 병목을 피하려고 커넥션 풀이나 작업자 수, 묶음 크기를 변경하지 않았다.

## 원자료와 다시 실행하는 방법

원자료는 [측정 디렉터리](../../../build/reports/coupon-v3-ramp-20261020/)에 저장했다.
`build/reports/`는 Git에서 제외되며 `gradle clean`으로 삭제될 수 있다. 핵심 결과와 판단 근거는 이 문서에도 남겼다.

| 파일 | 기록한 내용 |
|---|---|
| [measurements.json](../../../build/reports/coupon-v3-ramp-20261020/measurements.json) | 단계별 HTTP·퍼널·자원·SQL 증가량을 모았다. |
| [environment.json](../../../build/reports/coupon-v3-ramp-20261020/environment.json) | 호스트, Docker 자원, 컨테이너 설정과 DB 커밋 설정을 기록했다. |
| [소스 목록](../../../build/reports/coupon-v3-ramp-20261020/source-manifest.json), [소스 보관본](../../../build/reports/coupon-v3-ramp-20261020/measured-source.tar.gz), [JAR 해시](../../../build/reports/coupon-v3-ramp-20261020/jar-sha256.txt) | 미커밋 변경을 포함한 측정 코드와 실행 파일을 식별한다. |
| [서버 로그](../../../build/reports/coupon-v3-ramp-20261020/server.log) | 작업자 4개·묶음 상한 500건·대기열 2,000건의 시작 설정을 확인한다. |
| 각 실행의 `analysis.json`, `summary.json`, `raw.json.gz`, `command.json` | 요청 수와 상태, 지연, k6 판정, 성공 쿠폰 ID와 실행 명령을 기록했다. |
| 각 실행의 `timeline.ndjson`, `threads.txt`, `digest-before.json`, `digest-after.json` | 커넥션·잠금·CPU 표본과 스레드 대기, SQL 증가량을 기록했다. |
| 각 실행의 `prometheus-before.txt`, `prometheus-after.txt`, `analytics-drain.json` | 퍼널 종료 결과와 발급 수의 대조 근거를 기록했다. |
| 500 RPS 이후의 `db-waits-before.json`, `db-waits-after.json`, `redis-before.txt`, `redis-after.txt` | 로그 파일 I/O와 Redis 오류·명령 통계를 추가로 기록했다. |
| [bench-before.sql.gz](../../../build/reports/coupon-v3-ramp-20261020/bench-before.sql.gz) | 실행 전 전용 시험 DB를 보관했다. |

같은 전용 컨테이너와 보관한 JAR로 서버를 기동한 상태에서 단계 실행기를 호출한다.
실행 이름은 기존 결과와 겹치지 않게 정한다.

```bash
python3 build/reports/coupon-v3-ramp-20261020/tools/stage.py rps-100-retest 100 30
```

[단계 실행기](../../../build/reports/coupon-v3-ramp-20261020/tools/stage.py)는 데이터 준비와 Redis 초기화, 관측, 정합성 검증을 순서대로 수행한다.
동시에 호출해도 앞 단계의 검증이 끝날 때까지 파일 잠금으로 기다린다.
