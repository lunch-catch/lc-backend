# 쿠폰 발급 v1의 MySQL 병목과 개선 기록

## 요약

| 구분 | 내용 |
|---|---|
| 발생한 문제 | 재고 조회가 이미 발급한 앞 순번까지 반복해서 읽었다. 같은 이벤트에 요청이 몰리면 이벤트와 재고의 행 잠금 대기가 DB 커넥션 풀 포화로 이어졌다. |
| 시도한 개선 | 이벤트·상태·순번 인덱스를 준비하고 FORCE INDEX로 해당 인덱스를 사용하게 했다. 이벤트 배타 잠금을 제거하고 불필요한 조회도 줄였다. |
| 확인한 결과 | 같은 재고에서 SQL이 검사한 행은 17,023개에서 1개로, 5회 실행 중앙값은 11.80ms에서 0.08ms로 줄었다. 탐색 비용은 줄었지만 재고 선택의 행 경합은 남아 300 RPS 시험의 목표를 충족하지 못했다. 다음 재고를 고르는 책임을 분리하기 위해 v2 순번 발급기를 도입했다. |

## 기록 범위

2026-10-15의 최초 v1 측정과 2026-10-19의 개선 전·후 측정을 비교한다.
이벤트 행의 배타 잠금을 없애고 재고 조회가 상태 인덱스를 사용하도록 변경했다. 정상 발급 SQL은 12개에서 9개로 줄였다.
v1 개선 코드의 워밍업 후 단일 이벤트 200 RPS·20초 시험은 지연 목표를 통과했다.
더 긴 시험과 300 RPS 시험에서는 재고 행 경합이 남았다.

이 문서는 MySQL만으로 재고를 고르고 요청마다 커밋한 발급 구조를 v1로 부른다.
Redis 순번 발급기는 [v2 설계](../../design/coupon/coupon-issuance-v2-design.md), 여러 발급을 한 번에 커밋하는 구조는 [v3 설계](../../design/coupon/coupon-issuance-v3-design.md)로 나눈다.
v1·v2·v3는 내부 발급 구조의 버전이다. HTTP 경로는 모두 `POST /v1/coupons`다.
현재 코드의 처리 순서는 [API 설계](../../design/coupon/coupon-api-design.md#묶음으로-처리하는-쿠폰-발급)가 갖는다.

v1은 **MySQL에서 재고 탐색 → 상태 인덱스 추가 → FORCE INDEX로 실행 계획 고정 → 탐색 비용 감소 → 재고 행 경합 확인** 순서로 개선했다.
아래에서는 인덱스로 줄인 비용과 인덱스 뒤에도 남은 대기를 나눠 기록한다.

| 구분 | 시점과 코드 | 확인한 범위 |
| --- | --- | --- |
| v1 최초 측정 | 2026-10-15, `feat/284-coupon-issuance`의 당시 작업 디렉터리를 측정했다. | Java HttpClient로 측정했다. 찜 검증은 대역이며 소진 반영은 연결 전이었다. |
| v1 개선 | 2026-10-19 오후, 같은 HEAD에 커밋하지 않은 개선을 적용한 작업 디렉터리를 측정했다. | 별도 JDBC 프록시 없이 새로 빌드한 애플리케이션 JAR로 k6 시험 17개를 수행했다. |



## 1. 발급 결과와 재고를 MySQL 트랜잭션 하나로 확정했다

v1은 재고 선택과 일일 발급 횟수 증가, 회원 쿠폰 생성을 MySQL 안에서 처리했다.
요청 하나가 트랜잭션 하나를 사용하고 커밋이 끝난 뒤 성공을 응답했다.
DB 밖에서 재고를 예약하지 않으므로 발급 실패 때 재고와 발급 횟수를 같은 롤백으로 되돌릴 수 있었다.

| 데이터 | 발급에서 맡은 역할 |
|---|---|
| `coupon_event` | 영업일과 운영 상태, 발급 수량과 사용 조건을 제공했다. |
| `coupon_inventory` | 미리 준비한 쿠폰 코드와 순번을 보관했다. 가장 앞의 AVAILABLE 재고를 잠가 선택했다. |
| `coupon_daily_limit` | 회원과 영업일별 발급 횟수를 저장했다. 같은 회원의 동시 요청을 조정했다. |
| `member_coupon` | 회원에게 실제 발급한 쿠폰을 저장했다. 이벤트·회원 중복을 DB 제약으로 막았다. |

처음에는 이벤트 한 행을 배타 잠가 발급 전체를 직렬화했다.
서로 다른 회원도 같은 이벤트에서 기다리므로 이후 이벤트 배타 잠금을 제거했다.
회원별 한도와 재고의 쓰기 잠금은 유지했다. 발급 순서와 잠금 경계는 v1 설계도에서 설명한다.

이 설계는 DB 한 곳에서 발급 결과를 확정하는 대신 다음 재고를 찾는 탐색과 잠금 대기를 DB가 모두 맡는다.
후속 개선은 이 비용을 탐색 비용과 재고 선택의 경합으로 나눠 진행했다.

## 2. 최초 v1에서는 짧은 저부하 시험을 통과했지만 피크를 처리하지 못했다

최초 v1 측정의 단일 이벤트 100 RPS 시험은 10초 동안 1,000건을 모두 발급했다.
P95는 262.65ms, P99는 377.56ms였다. 첫 10초 2,500 RPS와 다음 20초 1,250 RPS를 시도한 피크 시험에서는 대부분의 요청을 전송하지 못했다.


당시 단일 이벤트의 이벤트 잠금 SQL 평균은 75.23ms였고 20개 이벤트로 분산했을 때는 1.50ms였다.
이 차이와 처리량을 함께 보고 같은 이벤트의 발급을 직렬화하는 구간을 개선 대상으로 잡았다. 순수 잠금 대기 시간만 분리한 수치는 아니다.

## 3. 측정에서 병목을 확인했다

### 이벤트 잠금을 잡은 채 검증과 저장을 수행했다

개선 전 코드는 회원·영업일 카운터를 먼저 잠그고 이벤트를 `SELECT FOR UPDATE`로 읽었다.
회원·프로필·찜·중복 조회와 재고 선택, 쿠폰 저장을 모두 이벤트 잠금 안에서 수행했다.
다른 회원의 요청도 같은 이벤트 행에서 기다렸고 기다리는 트랜잭션이 DB 커넥션을 점유했다.

단일 이벤트 100 RPS의 120초 시험에서 이벤트 잠금 SQL 평균은 55.63ms, 풀 획득 평균은 1,141.34ms였다.
관측한 최대 커넥션 대기 스레드는 194개였다. Hikari 커넥션 8개가 모두 사용되면 뒤의 요청은 풀 획득을 기다렸다.
3초 제한을 넘긴 요청은 `500 COMMON-001`로 응답했다.

### 재고 인덱스가 있어도 실제 실행 계획은 다른 인덱스를 선택했다

v1은 이벤트의 `AVAILABLE` 재고 중 가장 앞 순번을 찾아 `SELECT ... FOR UPDATE`로 잠갔다.
처음부터 순번을 지정하지 않으므로 요청마다 다음 재고를 찾는 탐색이 필요했다.
[V5 마이그레이션](../../../src/main/resources/db/migration/coupon/V5__coupon_inventory_available_index.sql)은 이 탐색을 위해 `(coupon_event_id, status, sequence_no)` 인덱스를 추가했다.
2026-10-19의 개선 전·후 측정에는 이미 이 인덱스가 있었다. 인덱스를 추가하기 전의 별도 부하 측정값은 확인한 원자료에 없다.

초기에 전체 테이블을 훑는 문제로 설명한 스캔 병목은 측정된 실행 계획과 구분해야 한다.
이 절의 원자료는 테이블 전체 스캔을 뜻하는 `type=ALL`을 근거로 삼지 않는다.
부하 중 실제 재고 선택 SQL은 `(coupon_event_id, sequence_no)` 인덱스를 선택한 경우가 있었다.
이 계획은 앞 순번부터 읽고 `AVAILABLE`인지 필터링하므로 발급된 재고가 쌓일수록 검사할 행이 늘었다.

75 RPS의 5분 재측정에서는 재고 선택 SQL 17,022회가 합계 136,034,793행을 검사했다. 요청당 평균 약 7,992행이다.
이 실행은 HTTP 시도 20,801건 중 17,022건이 발급됐고 3,569건은 500, 210건은 네트워크 실패였다. 별도로 k6가 시작하지 못한 반복은 1,700건이었다.

같은 재고 상태에서 두 인덱스를 강제로 지정해 SQL만 비교한 결과는 다음과 같다.
총재고는 22,700장이고 그중 17,022장이 이미 발급된 상태였다.

| SQL에서 지정한 인덱스 | 검사한 재고 행 | `Handler_read_next` | 5회 실행 중앙값 |
| --- | ---: | ---: | ---: |
| 이벤트·순번 인덱스를 지정했다. | 17,023 | 17,022 | 11.80ms |
| 이벤트·상태·순번 인덱스를 지정했다. | 1 | 0 | 0.08ms |

이 표는 같은 데이터에서 실행 계획의 스캔 비용을 분리한 진단이다. HTTP 응답이 같은 비율로 빨라졌다는 뜻은 아니다.
부하 종료 후에는 원래 SQL도 상태 인덱스를 선택했으므로 종료 후 한 번의 EXPLAIN만으로 부하 중 계획을 판단하지 않았다.

### 비동기 통계 저장도 같은 DB 커넥션 풀에서 기다렸다

통계 이벤트는 발급 커밋 후 별도 스레드에서 저장했다. HTTP 응답이 통계 저장 완료를 기다리지는 않았지만 DB와 커넥션 풀은 공유했다.
발급 요청이 풀을 점유하면 통계 저장도 늦어졌고 통계 큐가 차면 새 이벤트를 버렸다.

75 RPS의 5분 재측정에서는 발급 17,022건 중 통계 7,515건을 저장했다. 저장 실패는 72건이고 큐 포화로 거절한 이벤트는 9,435건이었다.
비동기로 옮긴 것만으로 공유 자원의 경합이 사라지지는 않았다.

## 4. 확인한 병목을 줄이기 위해 발급 경로를 변경했다

| 대상 | 개선 전 | 최종 개선 | 변경 목적과 확인 범위 |
| --- | --- | --- | --- |
| 이벤트 조회 | 이벤트 행에 배타 잠금을 잡았다. | 이벤트를 일반 조회한다. | 서로 다른 회원이 이벤트 한 행에서 모든 검증과 저장을 기다리는 구간을 제거했다. 회원 쿠폰 INSERT의 외래 키 검사에서 생기는 공유 잠금까지 없앤 것은 아니다. |
| 자격 검증 순서 | 카운터와 이벤트를 잠근 뒤 회원과 찜을 확인했다. | 이벤트·회원 상태·찜을 확인한 뒤 카운터를 잠근다. | 자격이 없는 요청이 카운터 잠금을 먼저 확보하지 않도록 했다. |
| 회원 조회 | `MemberInfo` 조회에 프로필 조회가 동반됐다. | `findCurrentStatus` 공개 계약으로 상태만 읽는다. | 발급에 필요하지 않은 프로필 SELECT를 제거했다. |
| 카운터와 중복 검사 | 카운터 엔티티를 잠금 조회하고 중복 SELECT 뒤에 횟수를 증가시켰다. | 카운터 UPSERT 뒤 조건부 UPDATE로 중복 부재와 일일 한도를 함께 검사한다. | 정상 경로에서 카운터 SELECT와 별도 중복 SELECT를 제거했다. 중복 검사는 UPDATE의 `NOT EXISTS`에 남아 있다. |
| 재고 선택 | JPA가 만든 SQL의 인덱스 선택을 최적화기에 맡겼다. | 네이티브 SQL이 기존 상태 인덱스를 `FORCE INDEX`로 지정한다. | 이미 발급된 앞 순번을 반복해서 훑는 실행 계획을 피하도록 했다. 재고 한 장의 쓰기 잠금과 순번 선택은 유지했다. |
| 발급 시간 재검사 | 재고 잠금 뒤에도 시각을 다시 검사했다. | 잠금 전 시간 검사를 통과한 요청을 대기 후에도 진행한다. | 서버의 대기 때문에 종료 시각을 넘긴 요청을 거절하지 않도록 정책을 바꿨다. 이 변경만의 성능 효과는 측정하지 않았다. |

이벤트 잠금 제거와 함께 운영 상태의 판정 시점도 명시했다. 발급 도중 운영 상태가 바뀌었을 때의 기준은 [발급 명세](../../api-spec/coupon-api-spec.md#쿠폰-발급)가 소유한다.
당시 v1은 회원·영업일 카운터의 조건부 증가와 재고 변경, 회원 쿠폰 INSERT를 같은 트랜잭션으로 묶었다.
재고를 잡은 뒤 저장이나 커밋에 실패하면 카운터와 재고도 함께 롤백했다.

발급 순서와 트랜잭션 경계는 [v1 설계도](../../design/coupon/coupon-issuance-v1-design.md)에 기록한다.

정상 발급의 동기 SQL은 SELECT 8개와 쓰기 4개에서 SELECT 5개와 쓰기 4개로 줄었다.

개선 후 재고 선택 SQL의 핵심은 다음과 같다. 반환 컬럼은 생략했다.

```sql
SELECT coupon_inventory_id
FROM coupon_inventory FORCE INDEX (idx_coupon_inventory_event_status_sequence)
WHERE coupon_event_id = ? AND status = 'AVAILABLE'
ORDER BY sequence_no
LIMIT 1
FOR UPDATE;
```

상태 인덱스는 이미 발급한 행의 반복 탐색을 줄인다. `FOR UPDATE`로 선택한 재고의 잠금은 트랜잭션 커밋까지 유지한다.
같은 이벤트에 몰린 요청들이 다음 재고를 고르는 경합은 이 변경 뒤에도 남는다.

## 5. 같은 조건으로 개선 전후를 측정했다

개선 전과 v1 개선 코드를 같은 소스 기준에서 각각 빌드해 같은 DB 스냅샷과 부하로 재측정했다. 아래에는 양쪽 실행이 모두 끝난 조건을 기록한다.
각 서버를 새로 시작하고 50 RPS·60초로 워밍업했다. 측정 전 데이터의 체크섬·행 수·자동 증가 ID도 대조했다.

| 시험 | 구현 | 유입 시간 | HTTP 시도 | 201 | 500·네트워크 실패 | 미전송 | 성공 P95(ms) | 성공 P99(ms) |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| hot-100-120s | 개선 전 | 120초 | 10,586 | 10,210 | 376 | 1,415 | 6,060.44 | 6,196.65 |
| hot-100-120s | 최종 | 120초 | 12,000 | 12,000 | 0 | 0 | 184.79 | 1,392.41 |
| hot-300-60s | 개선 전 | 60초 | 4,925 | 3,036 | 1,889 | 12,954 | 12,329.44 | 12,607.24 |
| hot-300-60s | 최종 | 60초 | 5,345 | 2,974 | 2,371 | 12,656 | 12,346.05 | 14,058.11 |
| spread-300-120s | 개선 전 | 120초 | 19,270 | 18,647 | 623 | 16,730 | 9,367.82 | 11,610.39 |
| spread-300-120s | 최종 | 120초 | 23,748 | 23,350 | 398 | 12,253 | 6,858.72 | 8,795.47 |

단일 이벤트 100 RPS에서는 최종 코드의 발급 성공 수와 지연이 나아졌지만 P99 1초 목표는 넘었다.

`spread`는 20개 이벤트에 요청을 분산한 시험이다. 미전송은 각 실행의 `analysis.json`에 저장된 k6 `dropped_iterations`를 옮겼다.
예정 요청 수에서 HTTP 시도 수를 뺀 값으로 미전송을 다시 계산하지 않았다. 일부 실행은 두 수의 합계가 예정 요청 수와 다르다.

### 단일 쿠폰의 재고 잠금 대기가 서버와 부하 발생기로 번졌다

`hot-300-60s`의 최종 실행에서는 같은 쿠폰의 재고를 발급하는 DB 구간에서 병목을 관측했다. 관측 결과를 종합하면 대기가 다음 순서로 번졌다고 판단했다.

**단일 이벤트에 요청 집중 → 재고 행 잠금 대기 → DB 커넥션 풀 포화 → HTTP 응답 지연 → k6 동시 실행 한도 도달**

- 재고 선택 SQL은 가장 앞의 `AVAILABLE` 재고를 쓰기 잠근다. 잠금 표본에서는 `coupon_inventory`의 상태 인덱스에서 쓰기 잠금 대기를 관측했다. 같은 실행의 재고 선택 SQL 평균은 127.23ms였으며 이 값은 순수 잠금 대기 시간만 분리한 수치가 아니다.
- 잠금을 기다리는 트랜잭션도 DB 커넥션을 점유했다. 커넥션 8개가 모두 사용됐고 커넥션을 기다리는 스레드는 최대 194개였다. 서버 로그에는 3초 동안 커넥션을 얻지 못한 오류가 남았다. HTTP 결과는 `500 COMMON-001` 2,157건과 네트워크 실패 214건이었다.
- 같은 DB와 커넥션 풀을 사용하는 통계 저장도 밀렸다. 측정 당시 통계 실행기는 스레드 2개와 대기열 1,000개를 사용했다. 발급 2,974건 중 통계 1,057건을 저장했고 저장 실패는 21건이었다. 대기열이 가득 차 거절한 통계 작업은 1,896건이었다. 통계 큐 포화는 발급 요청과 공유하는 자원의 경합이 통계 저장으로 번진 결과로 판단했다.

k6는 초당 300건을 60초 동안 시작하도록 설정했지만 실제 HTTP 시도는 5,345건이었다. 요청을 수행하는 반복의 평균 소요 시간은 9.38초였고 동시 실행 수는 설정 한도인 VU 800개에 도달했다.
사용 가능한 VU가 없어 새 반복을 시작하지 못했으므로 이 실행을 300 RPS를 실제 전송한 시험으로 해석하지 않는다. 통계 작업을 담는 대기열과 k6의 동시 실행 한도는 서로 다른 자원이다.

앞선 인덱스 대조의 0.08ms는 같은 데이터에서 SQL을 개별 실행한 5회 중앙값이다. 인덱스로 불필요한 스캔을 없애도 재고 잠금은 이후 저장과 커밋까지 유지된다.
따라서 개별 SQL의 스캔 비용 감소만으로 동시 요청의 잠금 경합이 해소됐다고 판단하지 않는다. 잠금 획득부터 커밋까지의 시간과 디스크 I/O·공유 자원 경합의 기여는 추가로 분리해 확인해야 한다.

같은 실행의 [측정 원자료](../../../build/reports/coupon-issuance-matched-20261019/hot-300-60s-after/analysis.json)와 [잠금·커넥션 관측 기록](../../../build/reports/coupon-issuance-matched-20261019/hot-300-60s-after/timeline.ndjson), [k6 실행 요약](../../../build/reports/coupon-issuance-matched-20261019/hot-300-60s-after/summary.json)을 근거로 판단했다.

20개 이벤트 300 RPS·120초의 대조는 위 표에 포함했다.
단일 이벤트 75 RPS·300초의 개선 후 실행은 HTTP 시도 21,968건 중 20,394건을 발급했다.
500 응답 1,486건과 네트워크 실패 88건, 미전송 533건이 있었고 성공 P95는 2,786.70ms, P99는 3,981.42ms였다.
이 조건의 개선 전 실행은 같은 대조 디렉터리에서 확인되지 않아 개선 후 관측값으로만 남긴다.

아래 재고 잠금과 통계 유실은 이번 대조와 구분한 앞선 단독 측정 기록이다.

### 이벤트 배타 잠금을 없애도 재고 한 장의 경합은 남았다

최종 코드의 단일 이벤트 300 RPS에서 재고 잠금 SQL의 MySQL 평균 시간은 31.81ms였다.
20개 이벤트 300 RPS의 첫 실행에서는 같은 SQL 평균이 0.42ms였고 잠금 대기 합계는 296ms였다.

### 발급 API가 목표를 통과해도 통계 이벤트는 유실됐다

통계 저장 실행기의 스레드 수와 큐, 공유 커넥션 풀은 이번에 변경하지 않았다.
최종 코드에서도 풀 포화와 통계 이벤트 거절이 관찰됐다.

| 최종 실행 | 발급 성공 | 통계 저장 | 저장 실패 | 큐 포화로 거절 |
| --- | ---: | ---: | ---: | ---: |
| 단일 이벤트 200 RPS, 워밍업 후 | 4,000 | 3,067 | 0 | 933 |
| 단일 이벤트 50,000건 피크 | 4,226 | 1,087 | 2 | 3,137 |
| 20개 이벤트 50,000건 피크 | 7,857 | 1,122 | 0 | 6,735 |

요청이 끝난 뒤 DB와 `analytics_funnel_event_total`의 증가량을 대조했다.
기록 완료·중복·저장 실패·큐 거절 수의 합계가 발급 성공 수와 일치했다. 위의 거절 수를 아직 처리 중인 이벤트로 세지 않았다.
분석이 허용하는 유실과 지표의 의미는 [분석 장애 처리 설계](../../design/analytics/analytics_장애_처리_설계.md#롤백-안-되는-효과-퍼널-이벤트-기록)가 소유한다.

## 8. v2에서는 재고를 찾는 책임을 Redis 순번 발급기로 옮겼다

v1의 인덱스 개선은 재고 한 장을 찾기 위해 읽는 행 수를 줄였다.
그러나 같은 이벤트의 다음 재고를 여러 트랜잭션이 함께 고르는 구조는 유지됐다.
상태 인덱스에서 관측한 재고 잠금 대기와 커넥션 풀 포화가 v2로 넘어간 근거다.

v2는 Redis에서 요청마다 서로 다른 재고 순번을 먼저 예약하도록 바꿨다.
MySQL은 배정된 순번의 재고를 조건부 갱신하고 발급 결과를 확정한다.
순번을 예약해 각 요청이 다른 재고를 갱신하도록 바꾼 과정은 [v2 설계](../../design/coupon/coupon-issuance-v2-design.md)에 이어 기록한다.
묶음 커밋을 도입한 뒤의 부하 시험은 [v3 개선 기록](./coupon-issuance-v3-improvement-comparison.md)이 갖는다.
