# 쿠폰 발급 v2의 순번 발급기 도입과 단건 커밋의 한계

## 요약

| 구분 | 내용 |
|---|---|
| 발생한 문제 | v1은 인덱스를 개선한 뒤에도 여러 요청이 같은 이벤트의 다음 재고를 선택하는 과정에서 잠금을 기다렸다. |
| 시도한 개선 | Redis가 요청마다 다른 재고 순번을 예약하도록 바꿨다. MySQL은 지정된 순번만 조건부 갱신하며 롤백한 예약은 반납하고 결과가 불확실하면 DB 기준으로 복구하게 했다. |
| 확인한 결과 | 퍼널 DB 저장을 끈 300 RPS·60초 시험에서 행 잠금 대기 증가량은 0회였다. 그러나 HTTP 시도 11,850건 중 발급 성공은 11,557건이었고 성공 P95는 7.95초였다. 커넥션 8개가 포화되는 문제가 남아 요청마다 반복하던 DB 작업과 커밋을 묶는 v3로 넘어갔다. |

## 기록 범위

v2는 Redis에서 재고 순번을 먼저 예약하고 MySQL에서 요청 한 건씩 발급을 확정한 설계다.
[v1 설계](../../design/coupon/coupon-issuance-v1-design.md)의 재고 선택 경합을 해결하려고 도입했다.
요청마다 커밋하던 방식은 유지했고 이후 커밋 비용을 줄이기 위해 [v3 설계](../../design/coupon/coupon-issuance-v3-design.md)로 넘어갔다.

이 문서는 순번 발급기 도입 당시의 설계와 2026-10-19의 측정 결과를 기록한다. 시각은 한국 시간이다.
현재 코드에는 v2의 단건 발급 서비스가 남아 있지 않다.
현재의 묶음 처리 순서는 [API 설계](../../design/coupon/coupon-api-design.md#묶음으로-처리하는-쿠폰-발급)가 갖는다.

## 1. 재고를 고르는 경쟁을 없애기 위해 순번을 먼저 배정했다

v1은 MySQL에서 가장 앞의 AVAILABLE 재고를 찾아 쓰기 잠금을 잡았다.
인덱스로 탐색이 빨라져도 같은 이벤트에 몰린 요청은 재고 선택 구간에서 기다렸다.
v2는 재고 선택을 Redis로 옮겨 각 요청이 서로 다른 `sequence_no`를 받도록 했다.

발급 순서와 트랜잭션 경계는 [v2 설계도](../../design/coupon/coupon-issuance-v2-design.md)에 기록한다.

### 순번 발급기는 남은 재고를 예약한다

Redis는 DB에서 읽은 AVAILABLE 순번을 목록으로 보관한다.
예약은 목록에서 순번을 꺼내 처리 중인 예약으로 옮긴다. 이 두 동작은 Lua 한 번으로 실행한다.
MySQL은 예약한 이벤트와 순번을 지정해 `status = 'AVAILABLE'`인 재고만 ISSUED로 바꾼다.
예상한 행 수만큼 갱신되지 않으면 성공으로 처리하지 않는다.

단순 증가 카운터만 사용하면 롤백한 요청의 순번을 다시 활용하기 어렵다.
예약과 반납을 둔 이유는 DB가 롤백한 재고를 다시 발급하고 예약 결과가 불확실한 재고를 함부로 재사용하지 않기 위해서다.
DB 커밋 후에는 예약을 완료한다. 롤백이 확정됐을 때만 순번을 반납한다.
DB와 Redis가 하나의 트랜잭션에 참여하지 않으므로 결과가 불확실하면 이벤트를 차단하고 DB를 기준으로 재구축한다.

이 변경은 모든 DB 잠금을 없애지 않는다.
재고 UPDATE의 쓰기 잠금과 회원별 일일 한도 잠금은 유지한다.
이벤트 공유 잠금도 사용한다. 복구는 같은 행의 배타 잠금으로 진행 중인 발급이 끝나기를 기다린다.
순번을 나눠 제거하려던 병목은 서로 다른 회원들이 같은 다음 재고를 선택하는 경쟁이다.

### 단건 커밋 방식의 첫 300 RPS 시험은 목표에 미달했다

2026-10-19 21:40의 `hot-300-60s-final`은 순번 발급기를 적용하고 비동기 퍼널 DB 저장을 끈 실행이다.
Hikari 최대 커넥션은 8개였다. 300 RPS·60초로 18,000건을 시작하도록 설정했다.

| HTTP 시도 | 201 | 500 | 미전송 | 성공 P95(ms) | 성공 P99(ms) | 행 잠금 대기 증가 |
|---:|---:|---:|---:|---:|---:|---:|
| 11,850 | 11,557 | 293 | 6,151 | 7,953.95 | 10,417.96 | 0회 |

재고를 고르는 잠금 대기는 관측되지 않았지만 커넥션 8개가 포화돼 요청이 기다렸다.
DB 발급 수와 ISSUED 재고 수, 일일 카운터 합은 11,557건으로 일치했다. 퍼널 이벤트 저장은 0건이었다.
원자료는 [실행 결과](../../../build/reports/coupon-redis-300rps/hot-300-60s-final/analysis.json)와 [커넥션·잠금 표본](../../../build/reports/coupon-redis-300rps/hot-300-60s-final/timeline.ndjson)에 있다.

초기 `hot-300-60s` 실행은 DB 커넥션 확보 실패에도 큐 전체를 복구하려던 구현이었다.
이후에는 예약 전 DB 실패와 확정된 롤백만으로 전체 큐를 재구축하지 않도록 좁혔다.
위 표는 그 변경 뒤의 결과다.

## 2. 다음 병목은 요청마다 반복하는 DB 작업과 커밋이었다

순번 도입 직후 정상 발급 SQL은 요청당 8개였다. BEGIN·COMMIT과 Redis 호출은 이 수에 포함하지 않았다.
이벤트 공유 잠금, 회원 상태·찜 조회, 카운터 생성·조건부 증가, 지정 순번 재고 갱신·코드 조회, 회원 쿠폰 INSERT를 수행했다.
순번을 예약해도 이 작업들과 커밋을 요청마다 반복했다.

`hot-300-60s-final`의 MySQL digest 차이에서 COMMIT은 11,556회, 누적 실행 시간은 79,806.08ms였다.
이 값은 여러 커넥션의 합계이며 HTTP 한 건의 처리 시간이 아니다.
측정 구간의 digest 차이는 최종 발급 11,557건과 한 건 차이가 있어 정확한 발급별 커밋 대조값으로 사용하지 않는다.
행 잠금 대기 0회와 풀 포화, 반복된 COMMIT 관측을 함께 보고 커밋 비용을 줄일 다음 설계를 선택했다.
커밋 동기화와 디스크 flush 각각의 기여를 분리해 측정한 결과는 없다.

SQL 한 개를 줄이려는 시도도 있었다. 신규 일일 카운터의 생성과 증가를 합치면 정상 경로는 7개가 됐다.
그러나 같은 회원이 여러 이벤트에 동시에 발급할 때 데드락이 재현돼 해당 시도는 되돌렸다.
요청당 8개는 당시 v2의 단건 경로를 측정한 값이다. v3의 묶음 경로는 SQL을 여러 행 단위로 다시 구성했다.

## 3. 예약과 DB 트랜잭션의 수명을 연결했다

당시 요청 스레드는 발급 트랜잭션 안에서 순번을 예약하고 DB 저장·커밋까지 수행했다.
Redis는 MySQL과 같은 트랜잭션에 참여하지 않으므로 예약 성공을 발급 성공으로 판단하지 않았다.
트랜잭션 종료 결과에 따라 예약을 완료하거나 반납했다.

발급 순서와 트랜잭션 경계는 [v2 설계도](../../design/coupon/coupon-issuance-v2-design.md)에 기록한다.

예약 ID를 둔 이유는 같은 순번이 반납 후 다시 예약될 수 있기 때문이다.
늦게 도착한 과거 요청의 완료·반납이 새 예약을 변경하지 않도록 순번과 예약 ID를 함께 확인했다.
예약 가능한 목록이 비어도 처리 중인 예약은 롤백될 수 있다. 목록이 비었다는 사실만으로 소진을 확정하지 않았다.

## 4. 장애 뒤에는 DB를 기준으로 순번 발급기를 다시 만들었다

DB 커밋 여부를 모르는 순번을 바로 반납하면 실제로 발급된 재고가 다시 예약될 수 있다.
그래서 결과가 불확실할 때는 새 발급을 차단하고 기존 DB 작업이 끝나기를 기다리는 방식을 골랐다.
복구는 이벤트의 배타 잠금으로 진행 중인 발급의 공유 잠금이 해제되기를 기다렸다.
그 뒤 DB의 AVAILABLE 순번으로 Redis를 다시 채웠다.

기준 데이터는 MySQL에 남겼다. Redis 연결이 돌아왔다는 사실만으로 발급을 재개하지 않았다.
오래된 예약도 즉시 반납하지 않고 DB 결과를 확인하는 복구 대상으로 삼았다.
요청이 없으면 복구도 실행하지 않는 방식으로 별도 스케줄러를 추가하지 않았다.
현재의 키와 예약 자료형은 [구조와 동작 설계](../../design/coupon/coupon_구조와_동작_설계.md#redis-순번과-예약)가 갖는다.
구체적인 차단·재구축 절차는 [장애 처리 설계](../../design/coupon/coupon_장애_처리_설계.md#redis-장애와-큐-복구)가 갖는다.

## 5. 재고 선택의 경합을 줄인 뒤 커밋 단위를 바꾸기로 했다

측정에서 행 잠금 대기 증가량은 0이었지만 요청 처리량과 응답 지연은 목표에 미달했다.
순번 발급기는 서로 다른 재고를 배정했지만 DB 연결과 COMMIT을 요청마다 사용하는 구조는 그대로였다.
DB 풀을 늘리는 대신 여러 발급이 한 트랜잭션의 비용을 나눠 쓰도록 바꾼 설계가 [v3](../../design/coupon/coupon-issuance-v3-design.md)다.

첫 300 RPS 실행의 서버는 Java 21.0.11, MySQL 8.4.11, Valkey 9.0을 사용했다.
로컬 단일 프로세스와 Hikari 최대 8개, JVM 최대 힙 2 GiB로 측정했다.
50 RPS·20초 워밍업 후 발급 데이터와 Redis를 초기화했다. 재고는 18,200장, k6 VU 상한은 800개였다.
이 측정은 비동기 퍼널 DB 저장을 끈 조건이다. 저장을 켠 v1과 같은 조건의 성능 배수로 비교하지 않는다.
실제 Redis 페일오버와 여러 서버의 동시 복구는 이 부하 시험의 검증 범위 밖이다.

이전 세션 「Redis 순번 발급기 실행계획 수립」에서 도입 이유와 단건 SQL 수, 되돌린 최적화 시도를 확인했다.
수치는 세션 요약 대신 실행별 JSON과 digest 전후 차이를 기준으로 옮겼다.
원자료인 `build/reports/`는 Git에 포함되지 않으며 `gradle clean`으로 지워질 수 있다.
