# Redis 소진 사전 응답을 적용한 v3 로컬 부하 시험

2026-10-21 한국 시각 21:29:39부터 21:31:16까지 개선한 v3를 로컬에서 한 회차 측정했다.
AWS 시험의 k6 스크립트와 시나리오 및 데이터 준비 스크립트를 그대로 사용했다.
요청 5,000건 가운데 발급 2,000건, 소진 2,889건, 일시적 발급 불가 111건을 받았다.
발급 p95는 2060.44ms이고 p99는 2078.43ms다.
발급 p95 700ms와 p99 1,000ms 및 정상 발급·소진 건수의 기준에 미달해 k6 종료 코드는 99다.
발급 정합성과 비동기 통계 저장은 통과했지만 전체 성능 시험은 통과하지 못했다.

## 실행 환경

| 항목 | 실제 환경 |
|---|---|
| 호스트 | MacBookAir10,1, Apple Silicon, CPU 8개, 메모리 8GiB다. |
| 앱 | Mac에서 Temurin Java 21.0.11로 실행했고 JVM 최대 힙은 768MiB다. |
| 부하 생성기 | 같은 Mac에서 k6 1.7.1 arm64를 직접 실행했다. |
| Docker | Docker Desktop 29.6.1이며 CPU 4개와 메모리 약 1.93GiB를 사용한다. |
| MySQL | 8.4.7이며 컨테이너 메모리 제한은 1GiB, 버퍼 풀은 256MiB다. |
| Valkey | 9.0-alpine이며 컨테이너 메모리 제한은 128MiB다. |
| Hikari | 최대 연결 8개다. |
| 발급 작업자와 대기열 | 작업자 4개, 최대 묶음 500건, 대기열 상한 2,000건이다. |
| Tomcat | 요청 스레드 상한은 200개다. |
| 소진 통보 | 작업자 1개가 이벤트별 접수를 합쳐 처리한다. |
| 발급 시간 | 밤에 측정할 수 있도록 00:00부터 23:59:59 전까지로 설정했다. |
| 연결 경로 | 앱과 생성기는 localhost를 사용한다. 앱은 포트를 통해 Docker의 DB와 Valkey에 연결한다. |

AWS와 요청 조건은 같지만 실행 환경은 다르다.
AWS는 앱·생성기·RDS·ElastiCache가 분리돼 있고 RDS MySQL은 8.4.11이다.
이번 로컬 측정에는 ALB와 Multi-AZ가 없다.
개선 전 코드를 같은 로컬에서 측정하지 않았으므로 이번 결과로 코드 변경의 개선율을 계산하지 않는다.

## 워밍업과 초기화

100명씩 20초 동안 두 차례 워밍업했다.
두 회차 모두 100건을 발급했고 비정상 응답은 없었다.

| 회차 | p95 | p99 |
|---|---:|---:|
| 1 | 52.98ms | 189.89ms |
| 2 | 45.45ms | 64.95ms |

원본 `assess-warmup.py`가 연속 두 회차의 안정 조건을 통과시켰다.
비동기 통계와 DB 작업 및 Redis 예약이 끝난 뒤 재고를 초기화했다.
앱은 재시작하지 않았고 본시험 전에 이벤트마다 DB AVAILABLE 100장과 발급 0건을 확인했다.
Redis도 available 100, pending 0, completed 0, state READY를 확인했다.
워밍업 회원 200명과 본시험 회원 5,000명은 서로 겹치지 않는다.

## 정합성과 관측 결과

| 항목 | 결과 |
|---|---|
| DB 발급 | 20개 이벤트에서 각각 재고 100장과 회원 쿠폰 100건을 확인했다. |
| 재고 초과·연결 불일치 | 없으며 DB의 재고 상태와 회원 쿠폰 및 일일 카운터가 일치했다. |
| Redis 종료 상태 | 모든 이벤트가 available 0, pending 0, completed 100, SOLD_OUT이었다. |
| 분석 통계 | 요청된 2,000건이 모두 recorded로 남았다. failed와 rejected는 0건이다. |
| 소진 통보 | 완료 20건이며 실패·접수 거절·만료는 0건이다. |
| Hikari 활성 연결 | 표본에서 최대 7개를 관측했다. |
| Hikari 대기 연결 | 표본에서 최대 0개였고 연결 획득 타임아웃 증가도 0건이다. |

| 생성기 RSS | 표본에서 최대 1162.80MiB였다. |

메트릭은 약 0.5초 간격으로 31개 표본을 수집했다.
표본 사이의 짧은 DB 연결 대기까지 없었다고 단정하지 않는다.
Tomcat 상한 도달과 생성기 전송 지연을 관측했지만 각 요인이 응답시간에 끼친 비중은 분리하지 않았다.
COUPON-008이 대기열 포화, 예약 중인 재고 부족, 복구 중 어느 경로에서 발생했는지는 이번 집계만으로 구분하지 않았다.

AWS와 같은 데이터 준비 스크립트에는 `ad_candidate`가 없다.
통보 20건은 후보 없음에 대한 정상 반환이며 실제 광고 후보 행 20개의 갱신을 검증한 결과가 아니다.
후보 없음 카운터도 20건 증가했다.

## 기록과 정리

원본 k6 요약, 앱·GC 로그, 메트릭 시계열, 스크립트 사본과 실행기는 작업 폴더의 `build/reports/coupon-local-load-20261021-698/`에 보관했다.
이 경로는 Git에 포함되지 않으며 `gradle clean`으로 삭제될 수 있다.

시험 뒤 앱 프로세스를 종료하고 이번 시험에서 만든 MySQL·Valkey 컨테이너와 볼륨만 삭제했다.
시험용 토큰 파일도 삭제했으며 ECR 업로드와 AWS 자원 변경은 하지 않았다.
