# LLM 구현 플로우

이슈 하나를 받아 도메인 코드와 테스트를 구현하는 순서다. 사람이 쓸 때도 LLM 에 맡길 때도 같다.

* 쓸지와 부르는 법, 동기와 비동기는 [`AGENTS.md`](../../AGENTS.md)의
  "LLM 기능 작업 플로우" 절이 갖는다.
* 작은 변경에는 씌우지 않는다. 한 줄 고치기, 오타, 설정값 조정은 그냥 한다.
* "작업 원칙" 은 `AGENTS.md` 의 그 절을 말한다. 원칙이 일반이고 이 문서의 단계가 그 적용이다.
  둘이 다르면 단계를 따른다.
* HTTP 입구인데 명세서가 없으면 [명세 작업 플로우](./명세_작업_플로우.md)가 먼저다.
* 브랜치와 보호 설정, 게이트, 배포는 [개발 배포 플로우](./개발_배포_플로우.md)에 있다.

## 막히면

**모호하면 묻는 것은 작업 원칙이 갖는다.** 이 문서는 물어야 하는 자리의 목록을 두지 않는다.
목록을 두면 목록 밖이 통과가 된다. 여기는 무엇을 들고 묻고 어디에 적는지를 정한다. 어느
단계에서도 일어나므로 순서 앞에 둔다.

| 모드 | 막히면 |
|---|---|
| 동기 | 선택지와 장단점을 들고 그 자리에서 묻는다. 이슈에도 적는다. 답이 오면 이어서 간다 |
| 비동기 | 임시로 정하고 이슈에 적는다. 멈추지 않는다 |

* 모아 두지 않고 그 결정이 나온 자리에서 묻는다. 모아서 한 번에 물으면 앞 결정이 뒤 결정의
  선택지를 이미 좁혀 놓는다.
* 물을 때 선택지와 각각 무엇을 잃는지 함께 낸다. 답하는 사람이 선택지를 되묻지 않게 한다.
* 동기에서도 이슈에 적는다. 대화 세션은 사라지고 이슈는 남는다.
* 동기에서 답이 오지 않으면 비동기와 같다. 기다리지 않는다.
* 비동기에서 멈추지 않는 것은 혼자 정해도 된다는 뜻이 아니다. 답을 기다리지 않는다는 뜻이다.
* 멈추는 자리는 적을 이슈가 없을 때뿐이다.
* 남의 도메인 타입과 마이그레이션의 열은 지어낼 수 없다. 그 갈래만 비우고 나머지를 끝낸다.
* 다른 도메인이 막으면 그 도메인의 이슈에도 적는다. 없으면 연다. 그 담당자는 내 이슈를
  보지 않는다.
* 공개 계약과 스키마는 정해져도 이 PR 에 넣지 않는다. 그쪽 문서와 마이그레이션이 먼저다.
* 임시로 정한 것은 설계서의 그 행과 테스트 이름과 PR 의 `리뷰 요청 사항` 셋에 표시한다.

## 기록은 어디에 남기나

셋이 담는 것이 다르다. 같은 것을 두 곳에 적지 않는다.

| 자리 | 담는 것 | 언제 |
|---|---|---|
| 이슈 | 막힌 자리, 물은 것, 이슈에서 정해진 것, 임시로 정한 것 | 작업 중에 그때그때 |
| 설계서 | 병합된 뒤의 기준 | 문서 단계에서 |
| PR 본문 | 정리한 결과와 리뷰어가 판단할 것 | PR 단계에서 |

* PR 에 경과를 옮겨 적지 않는다. 리뷰어는 `변경 이유` 절의 `Closes #<이슈번호>` 로 따라간다.
* 이슈에 적을 때는 아래 모양으로 적는다.

| 적을 것 | 쓰는 모양 |
|---|---|
| 막힌 자리와 막힌 이유 | 누가 그것을 소유하는지와 그 결정이 없으면 무엇을 못 쓰는지 |
| 이슈에서 정해진 것 | 누가 언제 어디에 적었는지 |
| 임시로 정한 것 | 여러 가지 선택지의 장단점 비교, 선택한 이유, 무엇이 오면 바꾸는지 |

## 순서

여덟 단계다. 가리킬 때는 번호가 아니라 이름으로 가리킨다. 단계를 옮겨도 참조가 성립한다.

### 1. 이슈

* 이슈 본문을 읽는다.
* 그 이슈에서 브랜치를 딴다. 명령과 이름은 [`AGENTS.md`](../../AGENTS.md)의 이슈와 PR 규칙,
  종류는 [개발 배포 플로우](./개발_배포_플로우.md) 1절이 정한다. 이미 그 브랜치면 그대로 쓴다.
* 완료 조건마다 무엇으로 확인할지 짝을 짓는다. 작업 원칙 "목표 중심으로 실행하기" 의 적용이다.
* 계획도 단계마다 검증과 짝지어 적는다. 돌려서 통과하는 것까지가 한 단계다.

| 이슈의 완료 조건 | 무엇으로 확인하나 |
|---|---|
| MEMBER 역할만 호출할 수 있다 | 통합 테스트. MEMBER 요청이 통과하고 다른 역할이 `403` 인지 본다 |
| 요청 제한이 명세대로 동작한다 | 단위 테스트. 60초 안의 일곱째 요청이 `429` 인지 본다 |
| 응답 필드가 명세와 같다 | 단위 테스트. 응답 DTO 를 명세서의 필드 표와 맞댄다 |

이 짝이 PR 단계의 `검증 방법` 표가 된다. 여기서 만들면 덮지 못한 축이 구현 중에 드러난다.

### 2. 읽기

코드를 쓰기 전에 읽는다. 순서는 `AGENTS.md` 의 "코드를 쓸 때 읽는 순서" 다.

**먼저 이 이슈의 입구를 가린다.** 입구가 무엇이냐로 계약이 어디 있는지가 갈린다. 한 이슈가
입구 둘을 가질 수도 있다.

| 입구 | 계약이 있는 곳 |
|---|---|
| HTTP 요청 | `docs/api-spec/` 의 그 도메인 명세서. 없으면 [명세 작업 플로우](./명세_작업_플로우.md)가 먼저다 |
| 이벤트 | 보내는 도메인의 `contract` 와 [설계 문서](../architecture/런치캐치_도메인_구조와_의존성_설계.md) 2.4. 명세서는 없다 |
| 시각(배치) | 이슈 본문과 [`런치캐치_배치_운영.md`](../design/ops/런치캐치_배치_운영.md). 명세서는 없다 |
| 다른 도메인의 호출 | 그 도메인이 부르는 `contract` 인터페이스 |

어느 입구든 아래는 공통이다.

* [`docs/CODEREVIEW.md`](../CODEREVIEW.md) 로 바꿀 경로에 걸리는 가이드를 고른다
* [설계 문서](../architecture/런치캐치_도메인_구조와_의존성_설계.md) 1.2 에서 그 데이터를 소유한 도메인과 애그리거트를 확인한다
* 1.3 과 1.4 로 패키지 자리와 부를 수 있는 계층을 확정한다
* [`docs/design/`](../design/) 에 그 도메인 디렉터리가 있으면 읽는다. 그 API 의 설계,
  모듈과 객체, 저장 구조와 동작, 그리고 멈췄을 때의 처리가 거기 있다

**저장소 밖의 문서는 열지 않는다.** 저장소에 없는 것은 아직 정해지지 않은 것이다.

**설계서가 이 이슈로 넘긴 것을 찾는다.** 명세서와 설계서가 구현이 정해야 하는 것을 다 정해
주지는 않는다. "아직 정해지지 않은 것" 절과, 본문에서 이슈 번호로 넘긴 자리를 함께 본다.
걸리는 것이 있으면 "막히면" 으로 간다.

HTTP 입구면 둘을 더 읽는다.

* [`docs/api-spec/`](../api-spec/) 의 그 도메인 명세서로 경로와 메서드, 요청과 응답 필드,
  상태 코드와 오류 코드, 권한을 확인한다
* [`docs/api-spec/api-spec.md`](../api-spec/api-spec.md) 로 공통 규약을 맞춘다. 응답 봉투,
  식별자, 시각, 목록 페이지네이션이다. 도메인 명세서는 이것을 다시 적지 않는다

다른 도메인의 `contract` 를 부른다면 그 도메인 설계 문서의 모듈 연결 절만 읽는다. 무엇을
돌려주고 낡은 값이 올 수 있는지가 거기 있다. 그 도메인의 나머지 절은 읽지 않는다.

**이 단계의 산출물은 이슈 댓글 한 줄이다.** 가린 입구와 읽은 문서를 적는다. 적지 않으면
읽었는지 알 수 없다.

    입구: HTTP 요청
    읽은 것: feed-api-spec.md, api-spec.md, feed-api-design.md, 설계 문서 1.2~1.4,
             campaign.contract 의 모듈 연결 절

### 3. 장애 처리

대상별 기본 처리는 [장애 처리 설계 가이드](../design/장애_처리_설계_가이드.md)에 있다.
여기서 다시 고르지 않는다. 이번 기능이 어느 대상에 기대는지 훑는다. 그러고 **기본 처리를
그대로 따르는지 아니면 벗어나는지**만 본다.

**벗어나면 그 코드의 블록 주석에 이유를 남긴다.** 테스트는 동작을 기록하지만 왜 그쪽을
골랐는지는 기록하지 않는다. 문서에 적는 것은 문서 단계가 한다.

**기본 처리 자체를 바꿀 일이면 이 기능의 PR 이 아니다.** 그 가이드를 고치는 PR 이다.

### 4. 단위 테스트

작업 원칙 "목표 중심으로 실행하기" 의 적용이다. 원칙은 테스트를 쓰고 통과시키게 하고 이
단계는 돌려서 실패를 먼저 확인하게 한다.

1. 협력자 시그니처를 확정한다. 저장소 메서드와 다른 도메인 `contract` 인터페이스다.
   확정할 수 없으면 "막히면" 으로 간다
2. 명세의 계약에서 테스트를 유도한다. 구현을 상상해서 쓰지 않는다
3. 돌려서 **실패를 확인한다.** 통과하면 그 테스트는 아무것도 검증하지 않는다
4. 통과하도록 구현한다
5. 다시 돌린다

서비스 계층에만 적용한다. 엔티티는 불변식이 생성자와 함께 자라므로 구현과 같이 쓴다.
통합 테스트는 컨텍스트가 떠야 해서 구현 뒤다.

### 5. 테스트 깊이

**모든 비즈니스 로직은 단위 테스트로 쓴다.** 게이트가 서비스 클래스의 모든 메서드에 테스트를
요구한다. 아래 넷은 그중 어디에 깊이를 쏟을지를 정한다.

1. 틀리면 사고가 나는 도메인 로직. 돈, 재고, 권한
2. 동시성이 걸리는 지점
3. 같은 요청이 두 번 올 때. 멱등성과 재시도
4. 영업일과 시각 경계

* 통합 테스트는 1 에만 쓴다. 2 와 3 과 4 는 단위 테스트로 쓰고, 그 셋이 돈이나 재고나
  권한에 걸리면 1 이라서 통합 테스트로 간다.
* 통합 테스트는 `@SpringBootTest` 로 애플리케이션 전체를 띄우고 기능의 실제 입구부터 DB
  저장까지 한 번에 확인한다. 슬라이스도, 저장소나 서비스만 부르는 것도 통합 테스트가 아니다.
* 이름을 `~IntegrationTest` 로 끝내고 도메인 패키지 바로 아래에 둔다.
* 입구만 다르고 나머지는 같다. 띄우는 범위와 DB 준비와 DB 를 다시 읽는 단언이 네 입구에서
  같고 바뀌는 것은 그 사이의 한 줄이다. 읽기 단계가 가린 입구를 그대로 쓴다.

| 읽기 단계의 입구 | 테스트에서 들어가는 한 줄 |
|---|---|
| HTTP 요청 | `mockMvc.perform(get("/v1/feed")...)` |
| 시각(배치) | 그 도메인이 등록한 `DailyJob` 구현의 `run(영업일)` |
| 이벤트 | `publisher.publishEvent(new XxxEvent(...))` |
| 다른 도메인의 호출 | 그 `contract` 빈을 주입받아 부른다 |

* 메서드를 직접 부르는 입구에는 `@Transactional` 을 붙이지 않는다. 테스트 트랜잭션에
  참여해 롤백되어 커밋 뒤에 도는 것을 못 본다.
* 권한은 HTTP 입구에서만 확인된다. 배치와 이벤트와 `contract` 호출은 보안 체인을 타지
  않아서 그 축의 칸에 `아니다` 를 적는다.
* getter 와 단순 위임과 DTO 매핑에는 깊이를 쓰지 않는다. 느린 통합 테스트로 단위에서 잡히는
  분기를 보지 않는다.

**이 단계의 산출물은 네 축의 표다.** 비우지 않는다. 그 표가 PR 단계의 `검증 방법` 이 된다.
여기서 만들면 구현 중에 빈 축이 드러난다.

| 축 | 테스트 |
|---|---|
| 1. 틀리면 사고가 나는 도메인 로직 | `FeedIntegrationTest.노출_상한에_닿은_캠페인을_내려주지_않는다` |
| 2. 동시성 | 아직 없다 |
| 3. 멱등성과 재시도 | 아니다 |
| 4. 영업일과 시각 경계 | `FeedServiceTest.서빙_시간대_밖이면_빈_피드다` |

칸의 뜻은 PR 단계가 정한다.

### 6. 문서

아래 둘을 같은 PR 에 넣는다. 없으면 만든다.

| 문서 | 담는 것 | 기준 |
|---|---|---|
| `docs/design/{도메인}/{도메인}_구조와_동작_설계.md` | 엔드포인트 하나에 속하지 않는 구조와 동작 | [구조와 동작 설계 가이드](../design/구조와_동작_설계_가이드.md) |
| `docs/design/{도메인}/{도메인}_장애_처리_설계.md` | 이 도메인이 기대는 대상과 기본 처리를 벗어난 것 | [장애 처리 설계 가이드](../design/장애_처리_설계_가이드.md) |

* 구조와 동작 설계 문서는 장을 비워 두지 않는다. 훑지 않은 장은 "아직 훑지 않았다", 해당
  없는 장은 "해당 없음" 으로 둔다. 구별하지 않으면 빠뜨린 것과 없는 것을 가릴 수 없다.
* 장애 처리 설계 문서는 기본 처리를 따르는 대상을 적지 않는다. 기대는 대상을 표로 적고
  벗어난 것만 그 아래에 적는다. 그 표가 있으면 빈 문서와 훑지 않은 문서가 구별된다.
* 엔드포인트 하나에서 출발하는 것은 `{문서명}-api-design.md` 가 갖는다. 엔드포인트 여럿이
  함께 쓰는 것은 위 문서로 옮기고 api 설계서는 링크로 가리킨다.
* 이슈에서 정해진 것과 임시로 정한 것을 여기로 옮긴다. 이슈는 경과를 갖고 설계서는 기준을
  갖는다.
* 두 문서는 가이드 부록의 틀을 그대로 따라 채운다. 장과 소제목을 다 둔다. 무엇을 적는지는 그
  두 가이드가 갖는다.
* **이어 쓸 때도 부록의 절이 다 있는지 본다.** 손으로 쓰다가 중간부터 이 플로우로 넘기면 그
  이슈의 범위만 채우게 되고, 처음부터 없던 절은 빠진 것으로 보이지 않는다.
* 빌드가 이것을 보지 않는다. 적지 않아도 다음 단계의 게이트는 통과한다. 그래서 단계로 둔다.

### 7. 범위와 확인

무엇을 하면 안 되는지는 작업 원칙 "단순함 우선" 과 "필요한 부분만 정밀하게 수정하기" 가
갖는다. 이 단계는 그것을 어떻게 확인하는지만 적는다.

    git diff --stat
    git status --short

**담기는 파일 목록을 만든다.** `git diff --stat` 의 파일마다 이슈의 어느 항목에서 나왔는지
한 줄로 적는다. 댈 수 없는 파일은 커밋에서 뺀다. 뺄 수 없으면 왜 담기는지 PR 단계의
`변경 내용` 에 적는다.

그다음 돌린다.

    ./gradlew check

**코드가 바뀌면 통과까지 돌린다.** 실패를 남긴 채 보고하지 않는다. 통과시키려고 검증 대상을
좁히지 않는다.

**고치는 동안에는 좁혀 돌린다.** `./gradlew test --tests '...'` 로 그 범위만 보고 마지막에 한 번
전체를 돌린다. 위 문장은 최종 판정을 좁히지 말라는 뜻이고 중간 루프를 좁히는 것과 충돌하지 않는다.

**문서만 바뀌면 돌리지 않는다.** 코드가 한 줄도 바뀌지 않아 결과가 base 와 같다. PR 게이트도 바꾼
파일이 `docs/` 아래뿐이면 테스트와 정적 분석을 건너뛴다(#661). 이때 테스트 깊이 표는 네 축을 모두
`아니다` 로 둔다.

**`./gradlew check` 가 보지 않는 것을 적어 둔다.** 고친 범위를 보지 않아서 서식만 바뀐
파일도 통과하고 쓰지 않는 설정값도 통과한다. 메서드 커버리지 게이트는 `service` 패키지만
세고 저장소와 쿼리는 세지 않는다. 그래서 직접 작성한 쿼리의 통합 테스트가 없으면, 게이트가
통과해도 그 쿼리는 한 번도 실행되지 않은 상태다. 그런 자리를 테스트 깊이 단계의 표에
`아직 없다` 로 적는다.

### 8. PR

**올리기 전에 develop 을 합친다.** 병렬로 돈 다른 작업이 같은 문서를 먼저 고쳤을 수 있다.
문서가 충돌하면 양쪽 내용을 모두 살려 합친다. 같은 문장을 양쪽이 다르게 고쳤으면 develop 쪽을 기준으로 둔다.
이 작업이 정한 것은 그 위에 다시 얹는다. 코드가 충돌하면 테스트를 다시 돌린다.

`AGENTS.md` 의 이슈와 PR 규칙을 따른다. 본문의 어느 절에 쓰는지는 아래로 정해 둔다.

* 테스트 깊이 단계가 만든 네 축 표를 `검증 방법` 에 옮긴다
* 요청 범위를 벗어난 파일이 담겼으면 왜 담겼는지 `변경 내용` 에 쓴다
* 기대는 대상과 기본 장애 처리를 벗어났는지는 `장애 처리` 절을 더해 표로 쓴다
* 지금 남은 임시 결정과 리뷰어가 판단할 것은 `리뷰 요청 사항` 에 쓴다

장애 처리에 맞는 절이 템플릿에 없어서 더한다. 맞지 않는 절에 밀어 넣으면 리뷰어가 찾지 못한다.

표의 칸에는 테스트 이름이나 `아니다` 나 `아직 없다` 를 적는다. 비우지 않는다.

* **테스트 이름**은 그 축을 덮는 테스트가 있다는 뜻이다
* **`아니다`** 는 이번 변경이 그 축을 건드리지 않았다는 뜻이다
* **`아직 없다`** 는 그 축을 건드렸는데 테스트가 없다는 뜻이다. 범위와 확인 단계가 말한
  자리가 여기다

**PR 을 올리는 방식도 모드에 따른다.**

| 모드 | PR 올리기 |
|---|---|
| 동기 | 제목과 본문을 보여 주고 올린다 |
| 비동기 | 바로 올린다 |

PR 을 올리면 `.github/CODEOWNERS` 가 리뷰어를 붙여 팀원에게 알림이 간다.
