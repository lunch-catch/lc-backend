# 작업 플로우

브랜치를 어떻게 따고 어떤 게이트가 병합을 막는지, 명세를 쓰고 기능 하나를 구현까지 어떤 순서로 가져가는지, 로컬과 QA 를 어떻게 돌리는지를 담는다.

이슈와 PR, 커밋의 규칙 자체는 이 폴더가 아니라 [작업 규칙](../../AGENTS.md)이 소유한다.

## 기능 하나를 만드는 순서

| 순서 | 문서 | 하는 일 | 부르는 사람 |
|---|---|---|---|
| 1 | [명세 작업 플로우](./명세_작업_플로우.md) | 도메인의 API 명세서와 설계서를 쓴다. 코드는 쓰지 않는다 | 작성자. 명령으로 부르지 않는다 |
| 2 | [LLM 구현 플로우](./LLM_구현_플로우.md) | 이슈 하나를 받아 도메인 코드와 테스트를 만든다. 테스트의 깊이와 막히는 자리의 처리를 정한다 | `/impl {이슈번호}` 로 부른다 |
| 3 | [개발 배포 플로우](./개발_배포_플로우.md) | 브랜치를 따고 PR 을 올려 게이트를 통과시키고 배포까지 간다 | 모두 |

1번을 2번보다 먼저 하는 이유가 있다. 명세서에 적히는 것이 대부분 공개 계약이라, 추측해서 채우면 프론트가 잘못된 계약을 받는다. 그래서 명세는 사람이 쓰고 구현만 명령으로 부른다.

## 이 폴더에 문서를 더할 때

순서를 담은 문서는 셋뿐이고 그 셋이 이어진다. 새 문서가 그 사이에 끼는 것이면 위 표에 줄을 더하고, 환경이나 운영이면 아래 표에 더한다. 이슈와 PR, 커밋, 문장 규칙은 여기에 적지 않고 `AGENTS.md` 에 적는다.
