# QA 실행

| 항목 | 내용 |
|---|---|
| 목적 | `docs/scenarios/` 의 시나리오를 QA 에이전트로 돌리는 사람이 무엇을 준비하고 어떻게 부르고 결과를 어떻게 읽는지 한곳에 둔다 |
| 범위 | 부르는 법, 준비할 것, 결과가 남는 곳, 결과를 이슈로 옮기는 법 |
| 관련 문서 | `../../.claude/agents/qa.md`(에이전트의 실행 지침), `../scenarios/README.md`(시나리오), `로컬_실행.md`(앱을 띄우는 법) |

**에이전트가 시나리오를 어떻게 돌리는지는 여기 적지 않는다.** 환경을 띄우는 순서, 묶음을 나누고 되돌리는 법, 역할마다 로그인하는 법, 판정 기준은 `qa.md` 가 갖는다. 이 문서는 그 에이전트를 부르는 사람이 읽는다.

## 1. 에이전트가 하는 일

에이전트는 시나리오 표의 단계를 로컬에서 실제로 실행하고 표의 기대 결과와 견준다. `backend.md` 는 API 를 직접 부르고 `owner.md`, `admin.md`, `user.md` 는 Playwright 로 화면을 누른다. 시나리오 문서의 `###` 절 하나를 돌릴 때마다 DB 와 캐시를 기본 세계가 들어간 직후로 되돌린다. 그래서 앞 묶음이 만든 데이터가 다음 묶음에 남지 않는다.

`localhost` 만 부른다. 개발 서버와 운영 서버는 API 가 요청마다 커밋해 되돌릴 수 없고 팀원이 함께 쓰는 데이터가 흔들려서 쓰지 않는다.

## 2. 준비할 것

처음 한 번만 하면 된다.

| 준비 | 하는 법 |
|---|---|
| `application-local.yml` | `로컬_실행.md` 2절대로 만든다. 비밀값이 들어 있어 에이전트가 만들지 않는다. 없으면 에이전트가 멈추고 만들어 달라고 한다 |
| Docker | Docker Desktop 을 켠다. 앱이 compose 로 MySQL 과 Valkey 를 띄운다 |
| Node 20 이상 | 프론트의 pnpm 이 Node 18 에서는 바로 죽는다. nvm 에 20 이상이 있으면 에이전트가 그것을 쓴다. 없으면 화면 시나리오는 모두 막힘으로 나오고 API 시나리오만 돈다 |
| lc-frontend | 클론해 두고 위치를 알려 준다. 에이전트는 그 저장소에서 `develop` 을 별도 worktree 로 받아 띄운다. 지금 쓰는 체크아웃은 건드리지 않는다 |
| Playwright | `scripts/qa/browser-setup.sh` 를 한 번 돌린다. 저장소 의존성에 넣지 않고 `.qa/tools` 에 받는다 |

다른 체크아웃이 로컬 MySQL 과 Valkey 를 이미 띄워 두었으면 컨테이너 이름이 부딪힌다. 에이전트가 `.env` 로 QA 전용 이름과 포트를 준다. 그 사람의 로컬 데이터가 든 컨테이너는 지우거나 덮지 않는다.

## 3. 부르는 법

Claude Code 에서 범위를 붙여 부른다.

    QA 돌려라 demo
    QA 돌려라 owner
    B-001~B-050 QA

| 범위 | 돌리는 것 |
|---|---|
| `demo` | `demo.md` 장면에 붙은 시나리오. 시연 흐름만 먼저 볼 때 쓴다 |
| `backend`, `owner`, `admin`, `user` | 그 문서 전체 |
| `O-001~O-026` 처럼 ID 범위 | 그 범위 |

시간이 오래 걸린다. `demo` 의 시나리오 97개가 1시간 남짓 걸렸다. 문서 하나 전체는 그보다 길어서 ID 범위로 나눠 부르는 편이 낫다.

**부르는 시각을 고른다.** 앱 시계는 고칠 수 없다. 선착순 발급(11:00 ~ 14:00)과 쿠폰 사용 시간에 걸린 시나리오는 그 시간 밖에 부르면 모두 막힘이다. 그 시나리오를 보려면 11:30 ~ 14:00 에 부른다.

**기본 세계는 기동한 날을 기준일로 들어간다.** 날이 바뀌면 에이전트가 컨테이너를 비우고 새로 띄워 스냅샷을 다시 뜬다. 그 사이 몇 분이 더 걸린다.

## 4. 결과

| 무엇 | 어디 |
|---|---|
| 보고서 | `.qa/report/<범위>-<YYYYMMDD-HHMM>.md` |
| 실패 화면 | `.qa/report/shots/` |
| 스냅샷 | `.qa/snapshot/` |

`.qa/` 는 git 이 무시하고 `gradle clean` 에도 지워지지 않는다. 지우고 싶으면 손으로 지운다.

보고서는 시나리오마다 통과, 실패, 막힘 중 하나를 적는다. 막힘은 시각 조건, 외부 서비스(카카오 로그인과 지도, 토스 결제, S3 업로드), 만들 수 없는 데이터 때문에 돌릴 수 없었던 것이다. 회원 로그인은 카카오뿐이라 에이전트가 로컬 비밀값으로 회원 토큰을 직접 만들어 쓴다. 카카오 로그인 흐름 자체만 막힘이다.

에이전트는 이슈를 열거나 `defects.md` 나 코드를 고치지 않는다. 결과를 어디로 옮길지는 부른 사람이 정한다.

## 5. 실패를 이슈로 옮기기 전에

**실패가 곧 코드 결함은 아니다.** 시나리오 표는 `../scenarios/README.md` 맨 위의 기준 커밋에서 뽑았다. 그 뒤 바뀐 화면이나 오류 코드는 표와 달라 실패로 나온다. 2026-10-23 의 `demo` 실행에서는 실패 16개의 대부분이 이 경우였다. 이럴 때 고칠 것은 코드가 아니라 시나리오 표다.

남은 실패는 이슈를 열기 전에 세 가지를 본다.

1. **명세와 견준다.** `docs/api-spec/` 이 그 동작을 정했으면 표가 틀린 것이다. 같은 실행에서 포인트 조정 뒤 소진액이 음수로 나온 것은 명세가 정한 동작이었다.
2. **데이터가 원인인지 본다.** 시나리오는 기본 세계 데이터(`db/base`) 위에서 돈다. 앱이 만들지 않는 상태를 데이터가 넣어 두었으면 고칠 것은 데이터다. 같은 실행의 환불 수수료 null(#896)과 리포트의 오늘 항목(#895)이 그랬다.
3. **백엔드인지 프론트인지 가른다.** 서버가 명세대로 응답했는데 화면이 잘못 보냈으면 lc-frontend 에 연다(lc-frontend #328).
