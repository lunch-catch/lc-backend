# LLM 기능 작업 플로우

기능 하나를 명세부터 구현까지 가져가는 순서다. 사람이 쓸 때도 LLM 에 맡길 때도 같다.

**쓸지와 부르는 법은 [`AGENTS.md`](../../AGENTS.md)의 "LLM 기능 작업 플로우" 절이 갖는다.**
작은 변경에는 이 순서를 씌우지 않는다. 한 줄 고치기, 오타, 설정값 조정은 그냥 한다.

브랜치와 보호 설정, 게이트, 배포는 [개발 흐름](./workflow.md)에 있다.
이 문서는 그 안에서 코드와 테스트를 어떤 순서로 만드는지를 담는다.

LLM 에 맡길 때 읽는 순서와 작업 원칙은 [`AGENTS.md`](../../AGENTS.md)에 있다.
원칙이 일반이고 이 문서의 단계가 그 적용이다. 단계가 원칙보다 좁은 자리에서는 단계를 따른다.

**명세와 구현은 이슈도 PR 도 따로 둔다.** 명세가 먼저 병합되어야 구현이 그것을 계약으로
삼을 수 있다. 구현하다가 명세를 고쳐야 하면 그것도 별도 PR 이다.

**이슈와 PR 이 담는 것이 다르다.** 이슈는 작업 중의 기록이다. 막힌 자리와 이슈에 물은 것과
이슈에서 정해진 것과 임시로 정한 것을 그때그때 적는다. PR 은 모두 수행하고 정리한
결과다. 경과를 옮겨 적지 않고 지금 상태와 리뷰어가 판단할 것만 적는다. 경과를 찾을 자리는
`변경 이유` 절의 `Closes #<이슈번호>` 가 가리킨다.

## 막히면

막히는 자리는 아래 단계가 정한다. 그 자리에서 무엇을 하는지는 어느 모드로 불렀느냐가 정한다.

| 모드 | 부르는 법 | 막히면 |
|---|---|---|
| 동기 | `llm 131`, `/impl 131` | 이슈에 적고 대화 세션에 묻는다. 답이 오면 이어서 간다 |
| 비동기 | `llm 131 async`, `/impl 131 async` | 임시로 정하고 이슈에 적는다. 멈추지 않는다 |

**동기에서도 이슈에 적는다.** 대화 세션은 끝나면 사라지고 이슈는 남는다. 적지 않으면 그
결정을 다음에 읽는 쪽에서 추측과 구별할 수 없다.

**동기에서 답이 오지 않으면 비동기와 같다.** 임시로 정하고 이슈에 적는다. 기다리지 않는다.

**임시로 정할 수 없는 것이 둘이다.** 다른 도메인의 `contract` 에 메서드를 더해야 하거나
마이그레이션에 열이 없을 때다. 그 타입과 열이 남의 도메인 것이라 만들 수 없다. 그 갈래만
비우고 나머지를 끝낸다. 비운 자리는 이슈에 적는다.

**멈추는 자리는 둘뿐이다.** 이슈 번호가 없을 때와 HTTP 입구인데 명세가 없을 때다. 앞은 적을
이슈가 없고 뒤는 명세 절로 보낸다.

## 명세

구현 전에 작성자가 도메인의 명세서와 설계서를 쓰는 단계다. 이 단계에서는 코드를 쓰지 않는다.

**명세를 먼저 쓰는 이유는 판정 가능한 목표를 만드는 것이다.** 구현부터 하고 명세를 나중에
맞추면, 명세가 구현을 설명하는 문서가 되어 계약 역할을 잃는다.

### 1. 읽기

- [`docs/api-spec/api-spec.md`](../api-spec/api-spec.md) 의 공통 규약. 경로, 인증,
  응답 봉투, 상태 코드, 식별자, 시각
- 그 도메인이 담당하는 기능 행. 같은 문서의 도메인과 문서 표에 있다
- [설계 문서](../architecture/런치캐치_도메인_구조와_의존성_설계.md) 1.2 에서 그 도메인이 소유한 데이터
- 2.2 와 2.4 에서 그 도메인이 공개하거나 의존하는 것

**공통 규약을 먼저 읽는다.** 목록 페이지네이션, 응답 봉투, 시각 표기처럼 이미 정해진 것을
도메인마다 다시 정하면 안 된다. 규약과 다르게 하려면 그 이유를 설계서에 적고 예외로 선언한다.

### 2. 두 문서로 나눈다

같은 내용을 두 곳에 쓰지 않는다. 다른 쪽은 링크로 가리킨다.

| 문서 | 독자 | 담는 것 |
|---|---|---|
| `docs/api-spec/{문서명}-api-spec.md` | 프론트, 백엔드 | 목록과 권한, 요청과 응답 필드(타입, 필수, null 가능, 설명), 상태 코드와 오류 코드, 클라이언트 규칙, 결과로 보이는 동작 |
| `docs/design/{도메인}/{문서명}-api-design.md` | 백엔드 | 근거(명세서의 계약, 저장 구조), 서버가 하는 일, 정한 이유, 성능 목표, 다른 도메인에 공개한 기능, 아직 정해지지 않은 것 |

명세서는 계약이다. 바뀌면 화면 코드가 바뀌므로 프론트에 알린다. 설계서만 바뀌면 알리지 않는다.

API 설계서는 엔드포인트에서 출발하는 것을 담고 도메인 설계 문서는 엔드포인트가 없거나
엔드포인트 여럿이 함께 쓰는 것을 담는다. 무엇을 적는지는
[구조와 동작 설계 가이드](../design/구조와_동작_설계_가이드.md)가 정한다.
이 단계에서 정해진 것부터 적고 나머지는 구현하면서 채운다.

### 3. 정해지지 않은 것은 이슈에 묻는다

작업 원칙 1번의 적용이다. 원칙은 모호하면 묻게 하고 이 단계는 물어야 하는 자리를 넷으로
못 박는다.

명세서에 적히는 것은 대부분 공개 계약이라 뒤에 바꾸기가 비싸다. 아래는 추측해서 채우지 않고
이슈에 물어 둔 뒤 빈칸으로 남긴다.

- 엔드포인트 경로와 메서드
- 오류 코드 문자열. 접두어가 도메인 단위인지 애그리거트 단위인지도 함께
- 응답 필드의 이름과 null 가능 여부
- 권한. 어느 역할이 부를 수 있나

설계서의 "아직 정해지지 않은 것" 절이 그 빈칸을 담는 자리다. 비워 두는 것이 잘못 채우는
것보다 싸다.

### 4. 결정마다 근거를 단다

설계서의 모든 결정에 근거를 붙인다. 명세서의 계약, 저장 구조의 테이블과 컬럼, 이슈
본문이다. "그게 자연스러워서" 는 근거가 아니다.

**근거는 저장소 안의 문서로 적는다.** 저장소 밖의 문서를 가리키면 읽는 사람이 그것을 따로
열어야 하고 판이 올라갈 때 가리킨 자리가 밀린다. 저장소 밖에서 온 결정은 API 설계서가
받아서 적는다. 그 문서만 그렇게 한다.

성능 목표도 값으로 적는다. 응답 시간과 동시 요청 수다. 값이 없으면 나중에 느려진 것을
느려졌다고 말할 수 없다.

### 5. 확인

- 공통 규약과 어긋난 것이 없다. 어긋나면 이유가 설계서에 있다
- 명세서의 오류 코드 표와 상태 코드가 서로 맞는다
- 문서 안의 상대 링크가 실제 파일을 가리킨다
- 설계서의 근거가 저장소 안의 문서를 가리킨다

### 6. PR

`AGENTS.md` 의 이슈와 PR 규칙을 따른다. 둘을 `리뷰 요청 사항` 절에 적는다.

- 지금 빈칸으로 남은 결정과 누가 정할 것인지
- 공통 규약의 예외를 만들었다면 그 이유

둘 다 판단이 갈리는 자리라 그 절이 맞다.

**누구에게 언제 물었는지는 쓰지 않는다.** 이슈가 갖는다. 이 절은 리뷰어가 지금 판단할 것만
담는다.

## 구현

이슈 하나를 받아 도메인 코드와 테스트를 구현하는 단계다.

시작은 셋이다. 이슈 본문을 읽는다. 완료 조건을 확인할 수 있는 것으로 바꾼다. 그 이슈에서
브랜치를 딴다. 명령과 이름 규칙은 [`AGENTS.md`](../../AGENTS.md)의 이슈와 PR 규칙 2번에 있고
종류는 [개발 흐름](./workflow.md) 1절이 정한다. 이슈 제목에 `[Feat]` 같은 접두어가 없으면
막힌 것으로 본다. 종류가 브랜치 이름에 들어가서 되돌리기 비싸다. 비동기면 `feat` 으로 두고
이슈에 적는다. 이미 그 이슈의 브랜치에 있으면 그대로 쓴다.

**완료 조건마다 무엇으로 확인할지 짝을 짓는다.** 작업 원칙 4번의 적용이다. 이슈 폼의 완료
조건은 문장이고 확인 방법이 붙어 있지 않다. 짝이 없는 항목은 막힌 것으로 본다.

| 이슈의 완료 조건 | 무엇으로 확인하나 |
|---|---|
| MEMBER 역할만 호출할 수 있다 | API 통합 테스트. MEMBER 요청이 통과하고 다른 역할이 `403` 인지 본다 |
| 요청 제한이 명세대로 동작한다 | 단위 테스트. 60초 안의 일곱째 요청이 `429` 인지 본다 |
| 응답 필드가 명세와 같다 | API 통합 테스트. 명세서의 필드 표와 맞댄다 |

**계획은 단계마다 검증과 짝지어 적는다.** 돌려서 통과하는 것까지가 한 단계다. 검증이 없는
단계는 끝났는지 알 수 없다.

    1. [할 것] -> 검증: [무엇으로]
    2. [할 것] -> 검증: [무엇으로]

이 짝이 9단계 PR 본문의 `검증 방법` 표가 된다. 그 표의 칸을 그때 처음 채우면 덮지 못한 축을
그 자리에서 알게 된다.

### 1. 읽기

코드를 쓰기 전에 읽는다. 순서는 `AGENTS.md` 의 "코드를 쓸 때 읽는 순서" 다.

**먼저 이 이슈의 입구를 가린다.** 입구가 무엇이냐로 계약이 어디 있는지가 갈린다. 입구는
넷이고 한 이슈가 둘을 가질 수도 있다.

| 입구 | 계약이 있는 곳 |
|---|---|
| HTTP 요청 | `docs/api-spec/` 의 그 도메인 명세서. 없으면 아래 명세 절이 먼저다 |
| 이벤트 | 보내는 도메인의 `contract` 와 [설계 문서](../architecture/런치캐치_도메인_구조와_의존성_설계.md) 2.4. 명세서는 없다 |
| 시각(배치) | 이슈 본문과 [`런치캐치_배치_운영.md`](../design/ops/런치캐치_배치_운영.md). 명세서는 없다 |
| 다른 도메인의 호출 | 그 도메인이 부르는 `contract` 인터페이스 |

어느 입구든 넷은 공통이다.

- [`docs/CODEREVIEW.md`](../CODEREVIEW.md) 로 바꿀 경로에 걸리는 가이드를 고른다
- [설계 문서](../architecture/런치캐치_도메인_구조와_의존성_설계.md) 1.2 에서 그 데이터를 소유한 도메인과 애그리거트를 확인한다
- 1.3 과 1.4 로 패키지 자리와 부를 수 있는 계층을 확정한다
- [`docs/design/`](../design/) 에 그 도메인 디렉터리가 있으면 읽는다. 그 API 의 설계,
  모듈과 객체, 저장 구조와 동작, 그리고 멈췄을 때의 처리가 거기 있다

**저장소 밖의 문서는 열지 않는다.** 그 둘에 없는 것은 아직 정해지지 않은 것이다.

**설계 문서의 미정 표를 같이 본다.** 명세서와 설계서가 구현이 정해야 하는 것을 다 정해
주지는 않는다. 명세 단계가 메우지 못한 빈칸은 설계서의 "아직 정해지지 않은 것" 절에 모여
있다. 이번 이슈가 그 절의 항목을 건드리면 2단계로 간다.

HTTP 입구면 둘을 더 읽는다.

- [`docs/api-spec/`](../api-spec/) 의 그 도메인 명세서로 경로와 메서드, 요청과 응답 필드,
  상태 코드와 오류 코드, 권한을 확인한다
- [`docs/api-spec/api-spec.md`](../api-spec/api-spec.md) 로 공통 규약을 맞춘다. 응답 봉투,
  식별자, 시각, 목록 페이지네이션이다. 도메인 명세서는 이것을 다시 적지 않는다

다른 도메인의 `contract` 를 부른다면 그 도메인 설계 문서의 모듈 연결 절만 읽는다. 무엇을
돌려주고 낡은 값이 올 수 있는지가 거기 있다. 그 도메인의 나머지 절은 읽지 않는다.

### 2. 막히는 자리

작업 원칙 1번의 적용이다. 아래 다섯은 모호한지 판단할 것도 없이 막힌 것으로 본다. 그 자리에서
무엇을 하는지는 위 "막히면" 절이 정한다.

되돌리기 비싼 자리다. 동기에서 추측해 고르지 않는다.

- 애그리거트 경계와 패키지 자리가 설계 문서로 결정되지 않는다
- 오류 코드 문자열, 엔드포인트 경로, 응답 필드. 공개 계약이라 프론트가 걸린다
- 다른 도메인의 `contract` 인터페이스에 메서드를 더해야 한다. 그 도메인 담당의 일이다
- 이슈가 요구하는 열이나 표가 마이그레이션에 없다. 스키마는 이슈 하나가 혼자 정하지 않는다
- 이슈가 설계서의 "아직 정해지지 않은 것" 절에 있는 항목을 정해야 한다. 그 절은 아직
  정해지지 않은 것을 모아 둔 자리다

**이슈에 적는다.** 2단계는 PR 보다 앞이라 쓸 PR 이 없다. 설계서에 적은 것은 병합되기
전까지 아무에게도 보이지 않는다. 이슈가 그 순간에 보이는 유일한 자리다. 아래 셋을 가리지
않고 적는다.

| 적을 것 | 쓰는 모양 |
|---|---|
| 막힌 자리와 막힌 이유 | 위 다섯 중 어느 것인지와 그 결정이 없으면 무엇을 못 쓰는지 |
| 이슈에서 정해진 것 | 누가 언제 어디에 적었는지. 설계서에는 6단계가 적는다 |
| 임시로 정한 것 | 고른 것과 버린 선택지, 고른 이유, 무엇이 오면 바꾸는지 |

**다른 도메인이 막으면 그 도메인의 이슈에도 적는다.** 그 담당자는 내 이슈를 보지 않는다.
기다리는 것이 있다는 사실은 그 사람의 이슈에 적혀야 알림이 간다. 그 이슈가 없으면 연다.

**정한 것은 설계서에 적는다.** `docs/design/{도메인}/` 이고 6단계가 그 일을 한다. 이슈에서
정해진 것도 적어 둔다. 적지 않으면 다음에 읽는 쪽에서 추측과 구별되지 않는다.

**공개 계약과 스키마는 정해져도 이 PR 에 넣지 않는다.** 명세서가 바뀌면 프론트가 먼저
읽어야 해서 명세와 구현을 따로 둔다. 스키마도 이슈 하나가 혼자 정하지 않는다. 그쪽 문서와
마이그레이션이 먼저다.

**그다음은 임시로 정할 수 있는지로 가른다.**

| 막는 것 | 할 것 |
|---|---|
| 남의 도메인 타입이나 열이 없어 코드를 쓸 수 없다 | 그 갈래를 비우고 나머지를 끝낸다. 비운 자리를 이슈에 적는다 |
| 그 밖 | 임시로 정하고 아래처럼 표시한다 |

**임시로 정한 것은 셋에 표시한다.** 설계서의 그 행에 지금 무엇으로 구현했는지 적는다. 그
결정을 덮는 테스트의 이름에 임시라는 것을 넣는다. PR 본문의 `리뷰 요청 사항` 에 무엇을
임시로 정했는지 적는다.

### 3. 서비스 계층은 단위 테스트를 먼저 쓴다

작업 원칙 4번의 적용이다. 원칙은 테스트를 쓰고 통과시키게 하고 이 단계는 돌려서 실패를 먼저
확인하게 한다.

1. 협력자 시그니처를 확정한다. 저장소 메서드와 다른 도메인 `contract` 인터페이스다.
   확정할 수 없으면 2번으로 돌아간다
2. 명세의 계약에서 테스트를 유도한다. 구현을 상상해서 쓰지 않는다
3. 돌려서 **실패를 확인한다.** 통과하면 그 테스트는 아무것도 검증하지 않는다
4. 통과하도록 구현한다
5. 다시 돌린다

서비스 계층에만 적용한다. 엔티티는 불변식이 생성자와 함께 자라므로 구현과 같이 쓴다.
통합 테스트는 컨텍스트가 떠야 해서 구현 뒤다.

### 4. 테스트의 깊이는 순서로 정한다

게이트는 서비스 클래스의 모든 메서드에 테스트가 있을 것을 요구한다.
아래 순서는 그중 어디에 깊이를 쏟을지를 정한다. 존재는 게이트가, 깊이는 이것이.

1. 틀리면 사고가 나는 도메인 로직. 돈, 재고, 권한
2. 직접 작성한 쿼리와 트랜잭션 경계
3. 동시성이 걸리는 지점
4. 같은 요청이 두 번 올 때. 멱등성과 재시도
5. 영업일과 시각 경계
6. API 응답 계약

1 은 단위 테스트로 먼저 쓴다. 3 과 4 와 5 는 통합 테스트가 필요한 경우가 많아 구현 뒤다.
6 은 API 통합 테스트로 권한과 상태 코드와 응답 모양을 함께 본다.

**2 는 통합 테스트를 같이 쓴다.** 직접 작성한 쿼리는 DB 가 있어야 실행된다.

통합 테스트는 컨텍스트를 띄워 여러 겹이 함께 도는 것을 본다. 컨트롤러 클래스의 테스트가
아니다. 이름을 `~IntegrationTest` 로 끝내야 하고 그것은 테스트 배치 규칙이 강제한다.

getter, 단순 위임, DTO 매핑에는 깊이를 쓰지 않는다. 게이트를 채우는 선에서 끝낸다.
느린 통합 테스트로 단위에서 잡히는 분기를 보지 않는다.

### 5. 기본 장애 처리를 따르는지 확인한다

대상별 기본 처리는 [장애 처리 설계 가이드](../design/장애_처리_설계_가이드.md)에
있다. 여기서 다시 고르지 않는다. 이번 기능이 어느 대상에 기대는지 훑는다. 그러고 **기본
처리를 그대로 따르는지 아니면 벗어나는지**만 본다.

**벗어나면 그 코드의 블록 주석에 이유를 남긴다.** 테스트는 동작을 기록하지만 왜 그쪽을
골랐는지는 기록하지 않는다. 문서에 적는 것은 6단계가 한다.

**기본 처리 자체를 바꿀 일이면 이 기능의 PR 이 아니다.** 그 가이드를 고치는 PR 이다.

### 6. 정한 것을 적는다

아래 둘을 같은 PR 에 넣는다. 없으면 만든다. 정한 것이 없는 장도 비워 두지 않는다.

| 문서 | 담는 것 | 기준 |
|---|---|---|
| `docs/design/{도메인}/{도메인}_구조와_동작_설계.md` | 엔드포인트 하나에 속하지 않는 구조와 동작 | [구조와 동작 설계 가이드](../design/구조와_동작_설계_가이드.md) |
| `docs/design/{도메인}/{도메인}_장애_처리_설계.md` | 이 도메인이 기대는 대상과 기본 처리를 벗어난 것 | [장애 처리 설계 가이드](../design/장애_처리_설계_가이드.md) |

**이번에 훑지 않은 장은 "아직 훑지 않았다" 로 둔다.** 해당 없는 장은 "해당 없음" 이다. 둘을
구별하지 않으면 다음 사람이 빠뜨린 것과 없는 것을 가릴 수 없다.

**엔드포인트 하나에서 출발하는 것은 `{문서명}-api-design.md` 가 갖는다.** 그 엔드포인트의
트랜잭션 경계와 응답을 만드는 순서가 그렇다. 엔드포인트 여럿이 함께 쓰는 것은 위 문서로
옮기고 api 설계서는 링크로 가리킨다.

구조와 동작 설계 문서를 채울 때 아래 일곱을 되짚는다. 장애 처리 설계 문서는 위 가이드의
유형별 점검 목록을 훑는다.

- 애그리거트를 하위 패키지로 둔 자리
- 인메모리 저장소에 둔 것. 키와 만료와 원본
- 한 트랜잭션에 묶은 것과 커밋 뒤로 미룬 것
- 조회를 조인 한 번으로 할지 나눠 부를지
- 다른 도메인의 것을 그대로 쓴 것. `contract` 인터페이스와 record 와 enum
- 영업일과 시각의 기준
- 보안 체인에 더한 경로

**빌드가 이것을 보지 않는다.** 적지 않아도 다음 단계의 게이트는 통과한다. 그래서 단계로 둔다.

### 7. 고친 범위를 센다

작업 원칙 2번과 3번의 적용이다.

    git diff --stat
    git status --short

- 담기는 파일이 이슈가 요구한 것뿐인지 센다. 서식만 바뀐 파일은 뺀다
- 바뀐 줄마다 이슈의 어느 항목에서 나온 것인지 댈 수 있는지 본다
- 요청하지 않은 설정 값과 확장 지점을 만들었으면 지운다
- 쓰이지 않게 된 import 와 변수는 이번 변경이 그렇게 만든 것만 지운다
- 관계없는 죽은 코드가 보이면 지우지 않고 PR 본문에 적는다

**`./gradlew check` 가 고친 범위를 보지 않는다.** 서식만 바뀐 파일도 통과하고 쓰지 않는 설정
값도 통과한다. 그래서 단계로 둔다.

### 8. 확인

    ./gradlew check

통과까지 돌린다. 실패를 남긴 채 보고하지 않는다. 통과시키려고 검증 대상을 좁히지 않는다.

**통과가 무엇을 보장하지 않는지 적어 둔다.** 메서드 커버리지 게이트는 `service` 패키지만
센다. 저장소와 쿼리는 세지 않는다. 그래서 직접 작성한 쿼리의 통합 테스트가 없으면, 게이트가
통과해도 그 쿼리는 한 번도 실행되지 않은 상태다. 그런 자리를 다음 단계의 표에 적는다.

### 9. PR

`AGENTS.md` 의 이슈와 PR 규칙을 따른다. 본문의 어느 절에 쓰는지는 아래로 정해 둔다.

- 건드린 축과 그에 대응하는 테스트 이름(4번의 여섯 순서)은 `검증 방법` 에 표로 쓴다
- 요청 범위를 벗어난 파일이 담겼으면 왜 담겼는지 `변경 내용` 에 쓴다
- 기대는 대상과 기본 장애 처리를 벗어났는지(5번)는 `장애 처리` 절을 더해 표로 쓴다
- 2번에서 지금 남은 임시 결정과 리뷰어가 판단할 것은 `리뷰 요청 사항` 에 쓴다

장애 처리에 맞는 절이 템플릿에 없어서 더한다. 맞지 않는 절에 밀어 넣으면 리뷰어가 찾지 못한다.

**경과는 옮겨 적지 않는다.** 2단계에서 무엇에 막혔고 누가 언제 정했는지는 이슈가 갖는다. PR
본문은 정리한 결과다. 리뷰어가 경과를 보려면 `변경 이유` 절의 `Closes #<이슈번호>` 를 따라간다.

표의 칸은 셋 중 하나로 적는다. 테스트 이름, `아니다`, `아직 없다` 다. 비우지 않는다.

- **테스트 이름**은 그 축을 덮는 테스트가 있다는 뜻이다
- **`아니다`** 는 이번 변경이 그 축을 건드리지 않았다는 뜻이다
- **`아직 없다`** 는 그 축을 건드렸는데 테스트가 없다는 뜻이다. 8단계가 말한 자리가 여기다

**PR 을 올리는 방식도 모드에 따른다.**

| 모드 | PR 올리기 |
|---|---|
| 동기 | 제목과 본문을 보여 주고 올린다 |
| 비동기 | 바로 올린다 |

PR 을 올리면 `.github/CODEOWNERS` 가 리뷰어를 붙여 팀원에게 알림이 간다.
