# adserving 장애 처리 설계

광고 서빙이 기대는 대상과 [장애 처리 설계 가이드](../장애_처리_설계_가이드.md)의 기본 처리를 벗어난 것을 적는다.
지금은 `GET /v1/feed` 의 후보 선별(#236), 배정 규칙(#307), serve 기록과 서빙 로그(#315)까지 훑었다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| Valkey | 요청 제한, 당일 이력, 하루와 세션 횟수, 유효 노출 수, serve 기록 | 기본(통과) |
| MySQL 읽기 | 그날 후보, 필터, 30일 찜 | 기본(오류로 올린다) |
| MySQL 쓰기 | 응답 뒤의 `serve_log`, `feed_visit_daily` | 벗어났다. 아래 |
| member 의 `MemberQueryService` | 온보딩, 위치, 노출 대상 판정 | 기본(오류로 올린다). 같은 프로세스 안의 호출이다 |
| billing 의 `BudgetQueryService` | 진행률, 노출 상한 | 벗어났다. 아래 |

## 벗어난 것

### 다른 도메인 호출: billing 의 `BudgetQueryService`

**원칙: 서빙할 피드가 아예 없을 때만 오류로 답하고 그 밖에는 서빙을 이어 간다**(#307 에서 정했다).
그날 후보를 MySQL 에서 읽지 못하면 내보낼 것이 없어 기본대로 오류다. 정산의 진행률은 카드를 고르는 규칙의 일부라
그것이 없어도 내보낼 카드는 있다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 기본대로 오류로 올린다 | 예산을 넘긴 캠페인이 나가지 않는다 | 정산 카운터(Valkey)가 멈추면 피드 전체가 멈춘다 |
| B. 진행률과 노출 상한 제외를 건너뛰고 배분 슬롯도 관련성으로 채운다 | 피드가 계속 나간다 | 그동안 예산을 넘긴 캠페인도 나가 공정성 규칙이 깨진다 |

B 를 고른다. 차감은 정산이 따로 막아(`NOT_BILLED_BUDGET`) 점주가 더 내지 않는다.
건너뛴 횟수는 `adserving_budget_unavailable_total` 이 센다.

조건에 맞는 후보가 0장인 것은 장애가 아니다. 예산 소진으로 0장이어도 명세대로 `200 NO_CANDIDATE` 다(#307).

### DB 쓰기: 응답 뒤의 `serve_log`, `feed_visit_daily`

기본 처리(트랜잭션을 되돌린다)는 응답과 한 몸인 쓰기를 전제로 한다. 서빙 로그는 응답 뒤 대기열이 묶어서 쓰고 판정과 과금에 쓰이지 않는다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 대기열이 차면 기다리고, 쓰기가 실패하면 다시 넣는다 | 빠지는 것이 줄어든다 | DB 가 느려지면 피드 응답까지 느려지고, DB 가 멈춘 동안 같은 묶음이 계속 실패해 뒤의 것까지 막는다 |
| B. 대기열이 차면 버리고, 쓰기가 실패하면 그 묶음을 버린다 | 피드 응답이 DB 에 묶이지 않는다 | 그만큼 서빙 로그와 접속 위치가 빠진다 |

B 를 고른다(#315). 서빙 로그는 유실을 0.1% 미만까지 허용한다(`feed-api-design.md` 유실 목표).
서빙 로그와 접속 위치는 서로 기대지 않아 따로 쓰고 따로 센다.
배포로 서버가 내려갈 때는 웹 서버가 요청을 다 받은 뒤 대기열을 멈추고 남은 것을 비운다. 비우는 사이에 DB 가 멈춰 있으면 그 묶음은 빠진다.

| 지표 | 세는 것 |
|---|---|
| `adserving_serve_log_dropped_total` | 대기열이 차서 버린 카드 수. 카드가 없는 피드는 접속 위치 1건으로 센다 |
| `adserving_serve_log_failed_total` | `serve_log` 쓰기가 실패해 버린 카드 수 |
| `adserving_feed_visit_failed_total` | `feed_visit_daily` 쓰기가 실패해 버린 접속 위치 수 |
| `adserving_served_cards_total` | 응답으로 내려준 카드 수. `serve_log` 건수와 대조해 유실률을 잰다 |

## 유형별 점검

### 캐시

| 시나리오 | 점검 결과 |
|---|---|
| 캐시 다운 | 해당 없음. 기본 처리(통과)를 따른다. 쓰는 곳마다 빠지는 규칙은 아래 표에 있다 |
| 캐시 스탬피드 | 해당 없음. 원본에서 다시 채우는 캐시가 아니다 |
| 분산 락 | 해당 없음. 락을 잡지 않는다 |
| 낡은 값 | 해당 없음. 정지와 탈퇴의 판정은 인증이 하고 회원 조회는 캐시하지 않는다 |

Valkey 가 멈춰 통과시킨 횟수는 `adserving_cache_bypass_total` 이 센다. 태그 `use` 로 쓰는 곳을 가른다.

| `use` | 로그 `event` | 통과시키면 |
|---|---|---|
| `feed_rate_limit` | `FEED_RATE_LIMIT_FAILED` | 요청 제한이 풀리고 `nextFeedAvailableAt` 이 응답 시각이 된다 |
| `daily_exclusion` | `FEED_DAILY_EXCLUSION_FAILED` | 넘긴 카드가 다시 보인다 |
| `serve_frequency` | `FEED_SERVE_FREQUENCY_READ_FAILED`, `FEED_SERVE_FREQUENCY_WRITE_FAILED` | 같은 카드가 하루 2회, 세션 1회를 넘겨 나온다 |
| `impression_count` | `FEED_IMPRESSION_COUNT_FAILED` | 유효 노출 수를 0 으로 보고 상한을 넘겨 내보낸다. 넘긴 노출은 과금되지 않아 손해는 플랫폼에 남는다 |
| `serve_record` | `FEED_SERVE_RECORD_WRITE_FAILED`, `FEED_SERVE_RECORD_READ_FAILED` | 쓰지 못하거나 읽지 못하면 그 카드의 노출이 무효(`EXPIRED_OR_UNKNOWN`)가 되어 과금되지 않는다 |

### DB

| 시나리오 | 점검 결과 |
|---|---|
| 다운, 연결 거부(읽기) | 해당 없음. 기본 처리(오류로 올린다)를 따른다 |
| 다운, 연결 거부(응답 뒤 쓰기) | `벗어난 것` 의 "DB 쓰기" 절 |
| 슬로우 쿼리, 응답 지연 | 아직 훑지 않았다 |
| 커넥션 풀 고갈 | 아직 훑지 않았다 |
| 데드락 | 해당 없음. 잠그는 쿼리가 없고 쓰기는 `INSERT IGNORE` 뿐이다 |
| 락 대기 초과 | 해당 없음. 잠그는 쿼리가 없다 |
| 제약 위반, 데이터 불일치 | 해당 없음. 같은 키는 `INSERT IGNORE` 가 넘긴다 |
| Primary 페일오버 | 아직 훑지 않았다 |
| 복제 지연 | 아직 훑지 않았다 |

### 외부 API

해당 없음. 외부 호출이 없다. 다른 도메인 호출(`BudgetQueryService`)은 같은 프로세스 안의 호출이고 `벗어난 것` 의 "다른 도메인 호출" 절에 있다.

### 애플리케이션

| 시나리오 | 점검 결과 |
|---|---|
| 요청이 몰린다 | 해당 없음. 사용자마다 60초 6회로 막는다. 목표 TPS 는 [`feed-api-design.md`](./feed-api-design.md) 에 있다 |
| 대용량 조회 | `아직 정하지 못한 것` 의 "그날 후보를 읽는 건수의 상한" |
| 배포로 서버가 내려간다 | `벗어난 것` 의 "DB 쓰기" 절 |
| 서버가 여러 대다 | 해당 없음. 스케줄러 작업이 없다. serve 기록은 Valkey 에 있어 서버끼리 함께 본다 |

### 롤백 안 되는 효과

해당 없음. 트랜잭션이 없다. Valkey 에 쓴 뒤 응답이 실패해도 되돌리지 않고, 내려준 횟수가 한 번 더 오를 뿐이다.

## 아직 정하지 못한 것

| 항목 | 지금 | 막는 것 |
|---|---|---|
| 지표의 경보 | 지표만 있고 경보는 걸지 않았다 | 통과시키거나 버린 것을 아무도 모른다 |
| 정산 일시 장애의 예외 타입 | `RuntimeException` 전체를 잡는다 | 프로그래밍 오류도 예산 규칙을 건너뛴다. 타입이 생기면 좁힌다(#324) |
| 서빙 로그 대기열의 크기와 묶음 수 | 5,000건과 50건으로 임시로 정했다 | 부하 시험 뒤 바꾼다 |
| 그날 후보를 읽는 건수의 상한 | 5000m 사각 범위로 한 번에 읽고 상한이 없다 | 한 지역의 후보 수가 커지면 메모리와 응답 시간이 함께 는다 |
