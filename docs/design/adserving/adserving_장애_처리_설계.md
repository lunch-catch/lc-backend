# adserving 장애 처리 설계

광고 서빙이 기대는 대상과, [장애 처리 설계 가이드](../장애_처리_설계_가이드.md)의 기본 처리를 벗어난 것을 적는다.
기본 처리를 그대로 따르는 대상은 표에만 두고 아래에 적지 않는다.

**지금은 `GET /v1/feed`(#230)의 경로만 훑었다.** 노출, 스와이프, 찜, 00:00 후보 적재는 구현하는 이슈에서 더한다.

## 기대는 대상

| 대상 | 유형 | 쓰는 곳 | 처리 |
|---|---|---|---|
| MySQL (`ad_candidate`, `swipe_log`, `feed_filter`, `impression_log`) | DB 읽기 | 피드 후보와 조건 | 기본 처리. 오류로 올린다 |
| MySQL (`serve_log`, `feed_visit_daily`) | DB 쓰기 | 응답 뒤 비동기 저장 | 벗어남. 아래 1 |
| Valkey 요청 제한 | 캐시 | 60초 6회 | 기본 처리. 통과시키고 센다 |
| Valkey 회원 당일 이력 | 캐시 | 하루 2회, 세션 1회 | 기본 처리. 통과시키고 센다 |
| Valkey serve 기록 쓰기 | 캐시 | 노출 검증의 근거 | 기본 처리. 통과시키고 센다. 결과는 아래 2 |
| billing `BudgetQueryService` | 다른 도메인 | 진행률, 노출 상한 | 벗어남. 아래 3 |
| member `MemberQueryService` | 다른 도메인 | 온보딩, 위치, 대상 필터 | 오류로 올린다. 대체값이 없다 |
| 서빙 로그 스레드 풀 | 애플리케이션 | 비동기 저장 | 벗어남. 아래 1 |

통과시킨 횟수는 `adserving_feed_fallback_total{target}` 로 센다. `target` 은 `rate_limit`, `serve_history`, `serve_cache`, `budget` 이다.
버린 서빙 로그는 `adserving_serve_log_dropped_total{reason}` 로 센다. `reason` 은 `queue_full`, `write_failed` 다.

## 벗어난 것

**1. 서빙 로그 쓰기가 실패하면 되돌리지 않고 버린다.** `임시(#230)`

DB 쓰기의 기본 처리는 트랜잭션을 되돌리는 것이다. 서빙 로그는 응답 뒤라 되돌릴 요청이 없고, 판정과 과금에 쓰이지
않는다(요구사항 100행). 대기열(1,000)이 차도 기다리지 않고 버린다. 기다리면 피드 응답이 늦어진다. 버린 건수로 유실률(목표
0.1% 미만)을 잰다. 배포로 내려갈 때는 대기열에 남은 작업을 20초까지 기다려 마친다.

**2. serve 기록을 못 쓴 카드도 내려준다.**

캐시 기본 처리대로 통과시키지만, 그 카드의 노출은 노출 검증에서 `EXPIRED_OR_UNKNOWN` 으로 무효가 되어 과금되지 않는다.
손해는 플랫폼이 진다. 점주 돈은 틀어지지 않는다.

**3. 예산 진행률을 읽지 못하면 예산 조건 없이 내려준다.** `임시(#230)`

정산은 카운터 장애면 대체값 없이 예외를 던지고 그 회차의 처리는 광고 서빙에 맡겼다(`BudgetQueryService` 주석).
막으면 정산 카운터 장애가 피드 전면 장애가 된다. 통과시키면 그 사이 진행률 1.2 초과와 노출 상한 도달 캠페인이 나간다.
과금은 정산이 차감할 때 따로 판정하므로(`NOT_BILLED_BUDGET`) 점주 돈은 틀어지지 않고 공정성만 흐려진다.
진행률을 0 으로 두어 배분 슬롯은 신규 우선과 생성 시각 순이 된다. 예외 종류를 가리지 않고 받는다. contract 가 종류를 정하지 않았다.

정산의 구현이 아직 없다(#193). 구현 빈이 없을 때도 같은 길로 보낸다. 그래서 #193 이 병합되기 전까지는 모든 요청이 예산 조건 없이 서빙되고 `target="budget"` 이 요청마다 오른다.

## 유형별 점검

| 유형 | 시나리오 | 이 도메인 |
|---|---|---|
| 캐시 | 캐시 다운 | 요청 제한, 이력, serve 기록 모두 통과시키고 센다 |
| 캐시 | 캐시 스탬피드 | 해당 없음. 원본에서 다시 채우는 캐시가 없다 |
| 캐시 | 분산 락 | 해당 없음 |
| 캐시 | 낡은 값 | 해당 없음. 정지 같은 즉시 제한은 회원 정보를 요청마다 읽는다 |
| DB | 다운, 슬로우 쿼리, 풀 고갈 | 공통 설정(Hikari 타임아웃)을 따른다 |
| DB | 데드락, 락 대기 | 해당 없음. 피드 경로는 잠그지 않는다 |
| DB | 제약 위반 | `serve_log` PK 중복은 UUIDv7 이라 일어나지 않는다고 본다. 나면 그 피드의 서빙 로그를 버린다 |
| DB | 복제 지연 | 해당 없음. 복제본을 읽지 않는다 |
| 외부 API | | 해당 없음 |
| 애플리케이션 | 요청이 몰린다 | 회원마다 60초 6회로 막는다. IP 제한은 두지 않는다(67행) |
| 애플리케이션 | 대용량 조회 | 5km 상자 안의 후보 수에 상한이 없다. 아직 재지 않았다 |
| 애플리케이션 | 배포로 서버가 내려간다 | 서빙 로그 대기열을 20초까지 마친다 |
| 롤백 안 되는 효과 | | 해당 없음 |

## 아직 정하지 못한 것

| 항목 | 막는 것 |
|---|---|
| 정산 진행률 장애 때 피드를 막을지 | 정산이 다른 기준을 요구하면 바꾼다 |
| 통과 횟수 지표의 경보 기준 | 운영 경보 규칙을 정할 때 |
