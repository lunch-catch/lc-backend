# adserving 장애 처리 설계

광고 서빙이 기대는 대상과, [장애 처리 설계 가이드](../장애_처리_설계_가이드.md)의 기본 처리를 벗어난 것을
적는다. 기본 처리를 따르는 것은 적지 않는다. 지금은 `GET /v1/feed`(#236)가 기대는 것만 훑었다.

## 기대는 대상

| 대상 | 쓰는 곳 | 기본 처리를 따르나 |
|---|---|---|
| Valkey: 요청 제한 카운터 | 피드 요청마다 | 따른다. 실패하면 통과시키고 `adserving_feed_rate_limit_bypassed_total` 로 센다 |
| Valkey: serve 기록과 당일 이력 | 피드 요청마다 읽고 쓴다 | 벗어난다. 아래 |
| MySQL 읽기: 후보, 필터, 스와이프, 찜, 노출 로그 | 피드 요청마다 | 따른다 |
| MySQL 쓰기: `serve_log`, `feed_visit_daily` | 응답 뒤 대기열 | 벗어난다. 아래 |
| billing `BudgetQueryService` | 피드 요청마다 | 따른다. 정산이 던진 예외를 그대로 올려 500 이다 |
| member `MemberQueryService` | 피드 요청마다 | 따른다 |

## 벗어난 것

**serve 기록과 당일 이력의 Valkey 가 멈추면 피드를 실패시킨다.** 캐시 기본 처리는 통과다. 이 데이터는
없으면 느려지는 것이 아니라 틀린다. serve 기록 없이 카드가 나가면 그 카드의 노출이 모두
`EXPIRED_OR_UNKNOWN` 이 되어 점주에게 과금 없는 노출이 된다. 당일 이력을 못 읽고 통과시키면 하루 2회 상한이
풀린다. 그래서 가이드 표의 예외("없으면 틀리는 곳은 거절한다")를 쓴다(#236, 작성자 결정).

**`serve_log` 와 `feed_visit_daily` 의 쓰기 실패는 되돌릴 트랜잭션이 없다.** 응답 뒤에 쓰므로 실패해도
응답은 그대로다. 실패한 행은 `adserving_feed_log_failed_total`, 대기열이 차서 버린 행은
`adserving_feed_log_dropped_total` 로 센다. 서빙 로그는 판정과 과금에 쓰이지 않는다(`feed-api-design.md`).

## 유형별 점검

| 유형 | 시나리오 | 피드 |
|---|---|---|
| 캐시 | 캐시 다운 | 요청 제한은 통과, serve 기록은 실패. 위 |
| 캐시 | 캐시 스탬피드 | 해당 없음. 원본에서 다시 채우는 캐시가 없다 |
| 캐시 | 분산 락 | 해당 없음 |
| 캐시 | 낡은 값 | 해당 없음. 회원 정보는 캐시하지 않는다 |
| DB | 다운, 슬로우 쿼리, 풀 고갈 | 기본 처리. 응답 뒤 쓰기는 대기열 스레드 2개만 풀을 쓴다 |
| DB | 데드락, 락 대기, 제약 위반 | 해당 없음. 피드는 트랜잭션을 열지 않고 `INSERT IGNORE` 와 새 PK 만 쓴다 |
| DB | 복제 지연 | 해당 없음. 복제본에서 읽지 않는다 |
| 외부 API | 전부 | 해당 없음 |
| 애플리케이션 | 요청이 몰린다 | 사용자마다 60초 6회로 막는다 |
| 애플리케이션 | 배포로 서버가 내려간다 | 대기열의 서빙 로그를 10초까지 마저 쓴다 |
| 롤백 안 되는 효과 | 커밋 뒤 실패 | 서빙 로그 쓰기 실패. 다시 집어 올리지 않고 센다 |

## 아직 정하지 못한 것

| 항목 | 막는 것 |
|---|---|
| 서빙 로그 유실 경보의 기준 | 버린 행과 실패한 행을 세지만 몇 건에 경보를 걸지 정하지 않았다 |
