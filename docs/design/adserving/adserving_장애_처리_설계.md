# adserving 장애 처리 설계

기준은 [장애 처리 설계 가이드](../장애_처리_설계_가이드.md)다. 기본 처리를 따르는 대상은 아래 표에만 두고,
벗어난 것만 그 아래에 적는다.

지금은 `GET /v1/feed`(#236)가 기대는 대상만 훑었다. 노출 수집, 스와이프, 찜, 00:00 후보 적재는 그 기능의
이슈가 더한다.

## 기대는 대상

| 대상 | 쓰는 자리 | 처리 |
|---|---|---|
| Valkey | 피드 요청 제한, 오늘 횟수와 세션, serve 기록 | 기본 처리(통과)를 따른다. 통과시킨 횟수를 `adserving_feed_cache_bypass_total{operation}` 으로 센다 |
| MySQL 읽기 | 후보, 필터, 스와이프 이력, 그날 유효 노출 수 | 기본 처리(오류로 올린다)를 따른다 |
| MySQL 쓰기 | 서빙 로그, 그날 첫 요청 위치 | 벗어난다. 아래 |
| billing `BudgetQueryService` | 예산 소진 진행률 | 벗어나지 않는다. 아래에 근거를 남긴다 |
| member `MemberQueryService` | 온보딩, 저장 위치, 성별과 연령대 | 오류로 올린다 |

## 벗어난 것

### 서빙 로그 쓰기는 되돌리지 않고 버린다

기본 처리는 트랜잭션을 되돌리는 것이다. 서빙 로그는 피드 응답 뒤에 다른 스레드가 쓰므로 되돌릴 응답이 없다.
쓰기가 실패하거나 대기열이 차면 그 묶음을 버리고 `adserving_serve_log_dropped_total{reason}` 에 카드 수만큼 센다.
`reason` 은 `queue_full` 과 `write_failed` 다.

버려도 되는 것은 서빙 로그가 판정과 과금에 쓰이지 않기 때문이다(요구사항 100행). 빠지면 진단이 "기록 없음" 을
보인다. 유실 목표는 0.1% 미만이고([`feed-api-design.md`](./feed-api-design.md) "유실 목표"), 위 지표와 응답
카드 수를 대조해 잰다.

### 정산의 진행률 조회가 실패하면 피드도 실패한다

이 처리는 기본을 벗어나지 않지만, 캐시 장애인데 통과시키지 않는 자리라 근거를 남긴다. 정산의 진행률은 정산이
Valkey 카운터로 계산하고 장애면 예외를 던진다. 광고 서빙은 그 예외를 그대로 올려 `500` 이 된다.

진행률을 모른 채 내려주면 예산의 1.2배를 넘긴 캠페인과 노출 상한에 닿은 캠페인을 거르지 못한다. 그 노출은
과금되지 않아 플랫폼이 공짜로 내준다. 금전 판정이라 틀린 값보다 실패를 고른다.

## 유형별 점검

| 유형 | 시나리오 | 이 도메인에서 |
|---|---|---|
| 캐시 | 캐시 다운 | 통과시킨다. 원본으로 폴백하지 않는다. 요청 제한과 하루 상한이 풀리고 serve 기록이 빠진다 |
| 캐시 | 캐시 스탬피드 | 해당 없음. 만료로 원본을 다시 읽는 캐시가 없다 |
| 캐시 | 분산 락 | 해당 없음 |
| 캐시 | 낡은 값 | 해당 없음. 정지나 탈퇴 판정을 캐시하지 않는다 |
| DB | 다운, 슬로우 쿼리, 풀 고갈 | 아직 훑지 않았다. 공통 설정을 따른다 |
| DB | 데드락, 락 대기 | 해당 없음. 피드는 잠그지 않는다 |
| DB | 제약 위반 | `feed_visit_daily` 는 `INSERT IGNORE` 라 두 번째 요청이 걸리지 않는다. `serve_log` 는 UUIDv7 PK 라 겹치지 않는다 |
| DB | 복제 지연 | 해당 없음. 복제본을 읽지 않는다 |
| 외부 API | 전부 | 해당 없음 |
| 애플리케이션 | 요청이 몰린다 | 요청 제한이 사용자마다 1분 6회로 묶는다 |
| 애플리케이션 | 배포로 내려간다 | 서빙 로그 실행기가 10초까지 남은 일을 마저 쓴다 |
| 롤백 안 되는 효과 | 커밋 뒤 실패 | 해당 없음. 피드는 커밋할 트랜잭션이 없다 |
