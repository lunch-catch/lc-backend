# adserving 요청 중 쓰기 설계

광고 서빙이 요청을 처리하는 중에 생기는 쓰기마다 [요청 중 쓰기의 지연과 유실 허용 범위 비교](../요청_중_쓰기의_지연과_유실_허용_범위_비교.md)의 방식 가운데 무엇을 고르는지 적는다.
쓰기마다 지금의 방식(v1)과 그 뒤에 바꿀 방식을 함께 둔다.

- 버전은 쓰기마다 따로 매긴다. 한 트랜잭션으로 함께 쓰이는 것은 하나로 센다. 노출 수집의 `impression_log` 와 정산 차감이 그렇다. 서빙 로그와 접속 위치는 대기열을 함께 쓰지만 한 트랜잭션이 아니라서 따로 센다.
- 방식은 비교 문서의 기호(A~F) 대신 이름으로 부른다. [구조와 동작 설계](./adserving_구조와_동작_설계.md) 7장의 결정 표도 선택지를 A, B, C 로 부르기 때문이다.
- 이 문서의 버전은 쓰기 구조의 버전이다. `serve_log.engine_version` 이 남기는 배정 규칙의 버전과 별개다.
- v1 의 쓰기마다 고른 이유와 빠지는 자리는 구조와 동작 설계 7장과 [장애 처리 설계](./adserving_장애_처리_설계.md)가 갖는다. 이 문서는 그 결정들을 방식별로 모아 본다.
- **버전마다 문서가 하나다.** v1 도 둔다. 그 문서가 밖에서 들어오는 링크의 과녁이 되고, v1 을 고른 이유가 [구조와 동작 설계](./adserving_구조와_동작_설계.md) 7장에 있다는 것을 그 문서가 가리킨다. 절 이름이 바뀌면 고칠 자리가 한 곳이다.
- **버전마다의 설계는 그 버전 문서가 갖는다.** 그 버전을 왜 올리는지, 무엇이 바뀌는지, 무엇을 대가로 내는지다. 이 문서는 1장의 표에서 그 문서들을 가리킨다. 버전을 올리는 PR 이 그 버전의 문서만 고치게 하려고 나눴다.

## 1. 쓰기마다 고른 방식

| 쓰기 | 목표 부하 | 유실 허용 | 버전과 방식 |
|---|---|---|---|
| 노출 수집(`impression_log` 와 정산의 판정 기록, 원장) | 초당 1,000건 | 0.1% 미만. 빠진 노출은 과금되지 않는다 | [v1](./adserving-impression-v1-design.md) 단건 동기. 노출 저장과 차감이 한 트랜잭션이다<br>[v2](./adserving-impression-v2-design.md) 차감을 아웃박스로 옮긴다<br>[v3](./adserving-impression-v3-design.md) 판정한 뒤 응답하고 `impression_log` 저장은 인메모리 큐에서 묶어 한다 |
| 서빙 로그(`serve_log`) | 초당 1,000행 | 0.1% 미만 | [v1](./adserving-serve-log-v1-design.md) 인메모리 비동기<br>[v2](./adserving-serve-log-v2-design.md) Redis Stream 으로 옮긴다. 그 문서의 진행 조건이 맞을 때만 한다 |
| 접속 위치(`feed_visit_daily`) | 회원마다 하루 한 행 | 목표 없음 | v1 인메모리 비동기 |
| 유효 노출 수 카운터(Valkey) | 초당 1,000건 | 빠지면 `impression_log` 로 다시 센다 | v1 커밋 뒤 실행 |
| 분석으로 가는 퍼널 이벤트 | 초당 1,000건(노출) | 허용한다(아키텍처 설계 2.4) | v1 커밋 뒤 전달 |

유효 노출 수 카운터와 퍼널 이벤트는 노출 수집의 커밋 뒤에 나간다. 노출 수집 v3 에서는 묶음 커밋 뒤에 나간다. 이 변경은 두 쓰기의 버전을 올리지 않는다. 노출 수집 v3 가 함께 바꾼다.

목표 부하와 유실 목표는 [`feed-api-design.md`](./feed-api-design.md) 의 "성능 목표" 와 "유실 목표" 가 갖는다.

스와이프와 찜(`swipe_log`, `wishlist`), 필터(`feed_filter`)는 버전을 나누지 않고 단건 동기로 둔다. 응답이 쓰기 결과(`applied`, 생성 여부, 저장한 필터)를 돌려줘서 비교 문서 5.1 의 조건 1에 걸린다. 쓰기 결과가 응답을 바꾸면 응답 전에 DB 에 반영해야 한다.

## 2. 쓰기마다의 v1

| 쓰기 | 방식 | 결정 |
|---|---|---|
| 노출 수집 | [단건 동기](./adserving-impression-v1-design.md) | 구조와 동작 설계 7장의 트랜잭션 표 "노출 수집" 행 |
| 서빙 로그와 접속 위치 | [인메모리 비동기](./adserving-serve-log-v1-design.md) | 구조와 동작 설계 7장 "서빙 로그와 접속 위치를 무엇으로 미루나"(#315), 장애 처리 설계 "DB 쓰기: 응답 뒤의 `serve_log`, `feed_visit_daily`" |
| 유효 노출 수 카운터 | 커밋 뒤 실행 | 구조와 동작 설계 7장 "유효 노출 수 카운터를 언제 올리나"(#323) |
| 퍼널 이벤트 | 커밋 뒤 전달 | 구조와 동작 설계 7장 "분석 이벤트를 커밋 뒤에 넘기는 일을 누가 맡나"(#349) |

## 3. v1 에 머무는 쓰기

| 쓰기 | 그대로 두는 이유 |
|---|---|
| 접속 위치 | 회원마다 하루 첫 요청 한 행뿐이고 유실 목표가 없다. 빠지면 추천 인원(FR-042)이 1명 줄 수 있다 |
| 유효 노출 수 카운터 | 빠져도 상한이 늦게 걸릴 뿐이고 `impression_log` 로 다시 센다(#323) |
| 퍼널 이벤트 | 퍼널은 유실을 허용하고 노출 수는 `impression_log` 로 센다(#349) |

## 4. 버전을 비교하는 지표

버전을 올리기 전에 지금 버전을 재고 올린 뒤에 같은 조건으로 다시 잰다. 시나리오와 데이터는 [`loadtest/`](../../../loadtest/README.md) 의 광고 서빙 시험이 갖는다.

- 측정한 커밋에 `adserving-{쓰기}-v{버전}` 태그를 붙인다. 예를 들어 `adserving-impression-v1`, `adserving-serve-log-v1` 이다. 태그가 있어야 나중에 이전 버전을 다시 띄워 나란히 잴 수 있다.
- 결과는 [`loadtest/`](loadtest/노출_수집_부하_시험_결과.md) 가 측정 조건과 함께 갖는다. 이 문서는 결과를 담지 않는다.
- 응답 시간만 비교하지 않는다. 버전을 올린 이유를 확인하는 지표를 함께 본다.

| 쓰기 | 공통 지표 | 버전을 올린 이유를 확인하는 지표 |
|---|---|---|
| 노출 수집 | `http_req_duration{api:impression}` 의 p95, p99, 초당 요청 수, 5xx 수 | `hikaricp_connections_pending` 과 `hikaricp_connections_active` 의 최대, MySQL 의 초당 커밋 수(`Com_commit`), 정산이 실패할 때 남은 노출 수. v2 부터는 릴레이의 밀린 행 수와 원장이 노출보다 늦게 남은 시간 |
| 서빙 로그 | `http_req_duration{api:feed}` 의 p95, p99, 초당 요청 수, 5xx 수 | `adserving_served_cards_total` 과 `serve_log` 건수로 잰 유실률, `adserving_serve_log_dropped_total`, 비정상 종료 때 잃은 행 수 |

## 5. 아직 정하지 못한 것

| 항목 | 정할 때 |
|---|---|
| 밀린 노출 수의 경보 문턱값 | 노출 수집 v2 의 부하 시험으로 |
| 노출 수집 v3 의 묶음 크기, 대기 상한, 큐 상한의 조정 | 노출 수집 v3 의 부하 시험으로 |
| 스트림 길이 상한과 소비자의 묶음 크기 | 서빙 로그 v2 를 진행할 때 |
