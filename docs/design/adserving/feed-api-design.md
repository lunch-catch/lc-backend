# 광고 서빙 (adserving) API 설계

광고 서빙 API를 서버가 어떻게 처리하는지와 그렇게 정한 이유를 적는다. 요청, 응답, 오류는 명세서 `../../api-spec/feed-api-spec.md` 에 있고 여기서는 반복하지 않는다.
명세서는 프론트가 보는 계약이고, 이 문서는 백엔드가 구현할 때 보는 문서다. 계약이 바뀌면 명세서를, 내부만 바뀌면 이 문서를 고친다.

| 근거 | 기준 |
|---|---|
| 요구사항 | 명세서 기능 FR-027, FR-064~FR-068, FR-071~FR-073, FR-089, FR-093~FR-094, FR-096~FR-097. 비즈니스 규칙의 공정성 절 |
| 저장 구조 | `db/migration/adserving/` 의 `V1`, `V2`: `ad_candidate`, `serve_log`, `impression_log`, `swipe_log`, `wishlist`, `feed_filter`, `feed_filter_category`, `feed_visit_daily`. 공통 DDL 규약은 같은 폴더의 `migration.md` |
| 설계 | `../../architecture/런치캐치_도메인_구조와_의존성_설계.md` 1.3, 2.2, 2.4 |

## 목록과 요구사항 ID

| 메서드 | 경로 | ID |
|---|---|---|
| `GET` | `/v1/feed` | FR-064, FR-093, FR-094, FR-096 |
| `POST` | `/v1/swipes` | FR-065 |
| `POST` | `/v1/impressions` | FR-066, FR-097 |
| `GET`, `PUT` | `/v1/feed-filter` | FR-067 |
| `GET` | `/v1/wishlist` | FR-072, FR-071 |
| `POST` | `/v1/wishlist` | FR-071 |
| `DELETE` | `/v1/wishlist/{campaignId}` | FR-073 |
| `GET` | `/v1/admin/feed-diagnosis/feeds` | FR-027 |

가게 추천 차단(FR-068, FR-089)과 캠페인 기준 진단(FR-027 후반)은 저장 구조에 근거가 없어 경로를 적지 않았다. `아직 정해지지 않은 것`에 남겼다.

**경로 이름.** `/v1/feed` 와 `/v1/feed-filter` 는 단수다. 사용자당 하나뿐인 리소스라 목록이 없다(`feed_filter` 의 PK 가 `member_id` 하나다).
그래서 필터 저장도 항목 추가가 아니라 전체 교체인 `PUT` 이다. `/v1/wishlist` 는 README 의 경로 절이 예시로 쓰는 표기를 따른다.

## 성능 목표

| API | 목표 TPS | 응답 지연 시간 | 에러율 | 근거 |
|---|---|---|---|---|
| `GET /v1/feed` | 500 | p99 500ms | 0.1% 미만 | 피크 동시 접속 5,000명(NFR-008) x 최근 60초 6회 제한(FR-064) / 60초 = 500이 상한 |
| `POST /v1/swipes` | 5,000 | p99 300ms | 0.1% 미만 | 피드 1회에 카드 10장. 500 x 10 = 5,000 |
| `POST /v1/impressions` | 10,000 | p99 200ms | 0.1% 미만 | NFR-010. 에러율은 서버가 받은 요청 가운데 5xx 와 시간 초과의 비율이다. 노출 유실률(NFR-015, 0.1% 미만)은 서버에 닿지 못한 노출까지 세야 하므로 에러율로 대신하지 않고 따로 잰다(아래 "유실 목표") |
| `GET /v1/wishlist` | 500 | p99 300ms | 0.1% 미만 | 10:50~11:00에 5,000명이 10초 안에 몰린다고 본다 |
| `POST`, `DELETE /v1/wishlist` | | | 0.1% 미만 | 가게 상세의 찜과 삭제 |
| `GET`, `PUT /v1/feed-filter` | | | 0.1% 미만 | 설정 화면 |
| `GET /v1/admin/feed-diagnosis/feeds` | | | 1% 미만 | 관리자 조회 |

**에러율은 서버 오류(5xx)와 시간 초과만 센다.** 입력 오류(4xx)와 속도 제한(`429`)은 의도한 거부라 뺀다.
`429` 를 넣으면 제한이 잘 작동할수록 에러율이 오른다. 운영 알림 기준(NFR-037, 노출 수집 오류율 1% 초과)은 목표와 따로 둔다.
**목표 TPS와 응답 지연 시간은 트래픽이 많이 몰리는 API 넷에만 둔다.** 나머지는 에러율만 본다. 검증은 k6 시나리오로 하고 기준은 쿠폰 오픈 전후의 피크 10:50~11:05 다. 서빙 시간대가 없어져도 오픈 시각이 그대로라 피크도 그대로라고 본다. 저녁에 따로 몰리는 트래픽이 있는지는 운영에서 본다(#498 에서 정했다).

## 유실 목표

| 대상 | 목표 | 재는 방법 | 빠졌을 때 |
|---|---|---|---|
| 노출 이벤트 | 0.1% 미만 (NFR-015) | 클라이언트 전송 카운터와 `impression_log` 건수 대조 | 집계도 차감도 되지 않는다. 플랫폼 손해이고 점주 손해는 아니다(FR-066) |
| 서빙 로그 | 0.1% 미만 (NFR-015) | 서버의 응답 카드 수 지표와 `serve_log` 건수 대조 | 진단(FR-027)에서 "기록 없음"이 된다. 판정과 과금은 바뀌지 않는다 |
| 일별 접속 위치 | 목표 없음 | 버린 건수만 지표로 센다 | 그날 첫 요청이 빠지면 추천 인원(FR-042)이 1명 줄 수 있다 |

**비동기 저장의 대기열이 차서 버린 건은 지표로 센다.** 버린 것을 세지 않으면 유실률을 잴 수 없다([장애 처리 설계 가이드](../장애_처리_설계_가이드.md) "모든 유형에 걸리는 것").

## `GET /v1/feed`

**서버가 하는 일**

1. 그날의 후보 스냅샷(`ad_candidate`)에서만 후보를 찾는다. 서빙 중에 다른 도메인 테이블을 읽지 않는다(FR-093)
2. 배분 3장(1, 4, 7번)은 예산 소진 진행률 오름차순, 관련성 7장은 관련성 점수(거리 45, 카테고리 선호도 35, 할인 20) 순이다(FR-093, FR-094, FR-096). 예산 소진 진행률이 1.2를 넘거나, 그날 유효 노출 수가 노출 상한(그날 예약액 / 그날 단가 x 1.05)에 닿은 캠페인은 두 슬롯 모두에서 뺀다(FR-096). 그날 예약액, 단가, 소진액은 정산의 `BudgetQueryService`로 읽고, 진행률은 광고 서빙이 그 값과 시간대별 가중치로 계산한다. 유효 노출 수는 광고 서빙이 자기 노출 로그로 센다. 예산에 닿은 뒤 상한까지 들어온 노출은 과금하지 않는다(`NOT_BILLED_BUDGET`, FR-100). 점수 식, 진행률 계산, 빈 자리 처리, 정산이 멈췄을 때의 처리는 [구조와 동작 설계](./adserving_구조와_동작_설계.md) 4장과 [장애 처리 설계](./adserving_장애_처리_설계.md)에 있다
3. 피드 필터의 카테고리는 10장 전부에, 정렬은 관련성 7장에만 적용한다(FR-067)
4. 같은 사용자에게 같은 캠페인은 하루 2회, 한 세션 1회까지만 내려준다. 30분 활동이 없으면 새 세션이다(비즈니스 규칙). 세는 곳은 구조와 동작 설계 3장에 있다
5. 찜한 캠페인과 패스한 캠페인은 사용자 당일 이력으로 뺀다. 이력은 00:00에 초기화된다(FR-099 (9), BR-040). 이력을 어디에 두는지는 [구조와 동작 설계](./adserving_구조와_동작_설계.md) 3장에 있다
6. 카드마다 serve 기록을 캐시(TTL 30분)에 쓰고, 응답 뒤 `serve_log` 와 그날 첫 요청 위치(`feed_visit_daily`)를 비동기로 쓴다. 캐시를 Valkey 에 두는 이유와 대기열은 [구조와 동작 설계](./adserving_구조와_동작_설계.md) 3장과 7장에 있다

**정한 이유**

- **서빙 시간대를 두지 않는다.** 요구사항이 바뀌어 10:00~12:59 를 없애고 하루 종일 카드를 내려준다. 그래서 `OUT_OF_SERVING_HOURS` 상태를 지웠다(#500 에서 정했다)
- **00:00 후보 적재가 끝나기 전에는 `NO_CANDIDATE` 다.** 전날 후보로 서빙하면 스와이프와 가게 상세 찜이 새 날 `ad_candidate` 를 보므로 적재가 끝날 때까지 `404` 이고, 오늘 계획이 없는 캠페인의 노출이 모두 `NOT_BILLED_NO_PLAN` 이 된다(#498 에서 정했다)
- **카드의 발급 오픈 시각과 사용 시간은 받은 시각과 관계없이 그대로 싣는다.** 캠페인의 매일 시각(HH:mm)이라 날짜가 없다. 그날 발급이 끝났는지는 사용자가 가게 상세나 쿠폰 API 에서 본다. 다음 발급 날짜를 담은 필드를 더하면 계약이 늘고 집행 기간 끝날의 규칙을 광고 서빙이 새로 정해야 한다(#500 에서 정했다)
- **위치를 보내지 않으면 저장 위치를 쓴다.** FR-064 "위치 획득에 실패하면 마지막 수동 입력 위치 사용"
- **위치 동의(`locationOptIn`)는 보지 않는다.** 좌표를 보냈거나 저장 위치가 있으면 피드를 주고, 둘 다 없으면 `ADSERVING-002` 다. FR-060 은 동의 거부 시 피드를 막으라고 읽히지만 FR-063 은 동의를 거부한 사용자가 주소를 직접 입력하게 한다. 직접 입력한 주소가 저장 위치가 되므로 FR-063 을 따른다(#236 에서 정했다)
- **후보가 10장 미만이면 탐색 반경을 넓힌다.** 5000 에서도 0장이면 `NO_CANDIDATE` 이고 `radiusM` 은 5000 이다. **임시**: FR-064 의 "후보가 모자라면" 을 10장 미만으로 읽었다. 기준이 정해지면 바꾼다(#236)
- **응답의 `radiusM` 은 캠페인의 노출 반경과 다른 값이다.** 탐색 반경은 1000, 2000, 3000, 5000 으로 넓혀 가고(FR-064 반경 확장), 캠페인이 지정하는 노출 반경은 `ad_candidate.target_radius` 의 500, 1000, 2000, 3000 이다. 단위가 같고 이름이 비슷해 `target_radius` 를 그대로 내려주기 쉬운데, 그러면 명세에 없는 `500` 이 나간다
- **"광고" 라벨을 서버가 내려주지 않는다.** 모든 카드가 광고라 서버가 켜고 끌 값이 없다. 포스터 HTML 안에는 광고 표시를 넣지 않기로 팀이 합의했다(`#628`, 포스터 디자인을 가리지 않게 하려는 것과, 서비스 가입과 약관 동의를 광고 수신 동의로 보기 때문이다). 카드 화면에서 "광고"를 표시할지는 클라이언트가 정한다(FR-064)
- **슬롯 유형과 배정 근거는 응답에 싣지 않는다.** 클라이언트가 쓸 곳이 없고, 배정 방식이 드러나면 공정성 정책을 거꾸로 이용할 수 있다. serve 기록(`serve_log`)에만 남겨 관리자 진단에서 본다
- **잔여 수량을 싣지 않는다.** 쿠폰이 소유한 값이라 광고 서빙이 읽으면 도메인 간 순환이 생긴다. 소진되면 쿠폰이 `CandidateStateUpdater` 로 알려 후보에서 뺀다
- **포스터는 HTML이 아니라 주소로 준다.** 카드 10장마다 포스터 본문을 실으면 응답이 무거워지고 캐시를 쓸 수 없다. 피드에 나오는 캠페인은 활성화를 마친 캠페인이고, 활성화 뒤에는 포스터를 고칠 수 없어(FR-052) 같은 주소는 항상 같은 포스터다. 그래서 주소에 버전을 붙이지 않고 `ad_candidate` 에 주소를 저장하지도 않는다. `campaignId` 로 만든다
- **서빙 로그와 접속 위치는 응답 뒤에 비동기로 쓴다.** 노출 검증은 캐시의 serve 기록으로 하므로 서빙 로그는 판정과 과금에 쓰이지 않는다(100행). 피드 1회에 10행이라, 동기로 쓰면 초당 5,000행의 쓰기가 응답 지연(p99 500ms)에 들어간다. DB 쓰기가 실패하면 피드까지 실패한다. 응답 뒤에 모아서 쓰면 둘 다 피한다. 대신 프로세스가 죽거나 쓰기가 실패하면 빠진다. 빠지면 진단(30행)이 "기록 없음"을 보인다. 목표는 "유실 목표" 절에 있다

**요청 제한 구현**

- 사용자마다 최근 60초 안의 요청 시각을 Valkey에 두고 센다. 분 단위 고정 창으로 세면 경계에서 두 배까지 받거나 `Retry-After` 가 들쭉날쭉해진다
- `Retry-After` = 가장 오래된 요청 시각 + 60초 - 지금(올림). `nextFeedAvailableAt` 도 같은 계산이다
- 거부된 요청은 횟수에 넣지 않는다. 넣으면 알려 준 시각에 다시 요청해도 또 거부될 수 있다
- IP 기준 제한은 두지 않는다. 공용 네트워크(회사, 학교)에서 여러 사용자가 한 IP를 쓴다(FR-064)

## `POST /v1/swipes`

- 중복 키는 `(serveId, 요청 사용자)` 다(FR-065, `swipe_log` PK). 다른 사용자가 같은 `serveId` 로 보낸 스와이프는 그 사용자의 기록으로만 남고 원래 사용자의 스와이프를 막지 않는다
- `WISH` 면 `wishlist` 에 넣는다. 이미 있으면 그대로 둔다(`wishlist` UNIQUE)
- 기록은 30일 관련성 카테고리 선호도에 쓰이고, 분석에는 `SwipedEvent` 로 비동기 전달된다(#349)
- **`404 ADSERVING-004` 는 오늘 `ad_candidate` 에 그 캠페인 행이 없을 때만이다.** 상태와 쿠폰 소진은 보지 않는다. 카드를 본 직후 캠페인이 멈추거나 쿠폰이 소진돼도 사용자의 스와이프는 남긴다. 대신 그날 끝난 캠페인도 찜에 들어간다(#379 에서 정했다). 그 찜은 넣을 때 종료로 표시되어 쿠폰 발급 자격과 알림 대상에서 빠지고 3일 뒤 지워진다(#780)
- **자정이 지나 전날 카드를 넘기면 새 날 기준이다.** 새 날 `ad_candidate` 에 행이 없거나 00:00 적재가 끝나기 전이면 `404` 다. 카드를 내려준 날 기준이면 서버가 `serve_log` 로 그날을 다시 읽어야 하고, 당일 이력이 어제 집합에 들어가 찜하거나 패스한 캠페인이 새 날 피드에 다시 나온다(#500 에서 정했다)
- **serve 기록으로 검증하지 않는다.** 명세에 그 오류가 없고, 다른 사용자의 serveId 도 그 사용자의 기록으로 남는다. 캠페인은 요청의 `campaignId` 를 쓴다
- 찜을 먼저, 스와이프 기록을 나중에 쓰고 당일 이력은 기록이 커밋된 뒤에 넣는다. 이유는 [구조와 동작 설계](./adserving_구조와_동작_설계.md) 7장에 있다

## `POST /v1/impressions`

**서버가 하는 일**

1. serve 기록이 캐시에 있는지 본다. 없으면 `EXPIRED_OR_UNKNOWN`
2. serve 기록의 사용자와 요청 사용자가 같은지 본다. 다르면 `NOT_OWNER`
3. 유효하면 한 트랜잭션 안에서 `impression_log` 에 저장하고, 처음 저장된 유효 노출이면 정산의 `PointDeductor` 로 노출 차감을 부른다. 그날 후보가 쿠폰 소진이면 차감을 부르지 않고 `sold_out` 으로 적는다(`NOT_BILLED_SOLD_OUT`)
4. 과금 판정(`BILLED`, `NOT_BILLED_BUDGET`, `NOT_BILLED_PAUSED`, `NOT_BILLED_NO_PLAN`)은 정산이 자기 기록(`deduction_result`)에 남긴다(FR-100). 차감의 영업일은 노출을 받은 날이다. 자정을 넘겨 받은 노출은 다음 영업일로 차감한다(#497, #498). 노출 저장, 판정, 원장이 함께 커밋된 뒤 응답하고, 실패하면 함께 롤백된다. 무효 노출도 사유와 함께 저장하고 차감은 부르지 않는다

**정한 이유**

- **과금 상태는 응답에 싣지 않는다.** 점주의 과금 정보라 사용자에게 줄 이유가 없다. 미과금 노출도 유효 노출이다
- **중복 키는 `(serveId, 요청 사용자)` 다**(FR-097, `impression_log` PK). 다른 사용자가 먼저 보낸 무효 노출이 원래 사용자의 유효 노출을 막지 못한다
- **`202` 를 쓴다.** 서버는 처리를 끝내고 판정을 돌려주지만, 클라이언트는 화면을 벗어나며 보낸 요청의 응답을 받지 못할 수 있어 응답에 의존하지 않는다(FR-097)
- **클라이언트는 기다리지 않지만 서버는 동기로 처리한다.** 기다리지 않는 이유는 스와이프를 끊지 않기 위해서다. 화면을 벗어나며 보낸 요청은 응답도 받지 못한다(FR-066). 서버가 비동기로 받지 않는 이유는 유효 노출의 저장, 판정, 원장이 한 트랜잭션이어야 하기 때문이다(FR-100). 비동기로 받으면 "받았다"고 답한 뒤 저장에 실패한 노출을 되살릴 길이 없다
- **요청의 `campaignId` 가 serve 기록과 다르면 serve 기록의 캠페인으로 저장하고 판정한다.** 무효 사유를 더하지 않고 불일치는 처음 저장된 노출이 커밋된 뒤 `adserving_impression_campaign_mismatch_total` 로 센다. 다시 온 요청과 롤백된 요청은 세지 않는다(#783). 과금은 서버가 실제로 내려준 캠페인에만 간다. 무효 사유를 더하려면 명세의 `invalidReason` 과 `impression_log.invalid_reason` 을 먼저 바꿔야 한다(#323 에서 정했다)
- **`invalidReason` 은 유효면 `null` 이다.** 사유는 무효일 때만 뜻이 있다. `impression_log.invalid_reason` 도 같은 규칙이라 `invalid_reason IS NOT NULL` 이 곧 무효 노출이다
- 요청이 많아지면 여러 건을 묶어 받는 방식으로 바꿀 수 있고, 검증과 중복 처리는 같다(FR-097)

## `GET`, `PUT /v1/feed-filter`

- `categories` 의 빈 배열을 전체 업종으로 읽는다(FR-067 예외). "아무것도 고르지 않음"을 따로 둘 이유가 없다
- **`GET` 은 `categories` 를 업종 코드 오름차순으로 돌려준다.** 같은 필터는 늘 같은 순서다. `feed_filter_category` 에 순서 컬럼이 없어 고른 순서는 남기지 않는다(#405 에서 정했다)
- 저장한 적이 없으면 `categories: []`, `sort: "DISTANCE"` 다. 피드가 필터 없는 회원을 다루는 기본값과 같다
- 필터는 `feed_filter`(정렬)와 `feed_filter_category`(업종)에 나눠 저장하고, `PUT` 은 둘을 한 트랜잭션에서 통째로 바꾼다
- **`PUT` 은 저장한 뒤 `GET` 과 같은 방법으로 다시 읽어 돌려준다.** 응답의 업종 순서가 조회와 같다
- **`PUT` 에 같은 업종이 두 번 오면 하나로 합친다.** 거부하면 명세의 오류 표에 없는 경우가 생긴다. 저장 구조도 PK 가 `(member_id, category_code)` 인 집합이다(#411 에서 임시로 정했다)
- **없는 업종 코드는 요청 타입의 애노테이션이 store 의 CHECK 와 같은 목록으로 가른다.** 업종 코드는 store 가 소유하는데 `contract` 로 공개하지 않았다. 공개되면 그것으로 바꾼다(#411 에서 임시로 정했다)

## `GET`, `POST`, `DELETE /v1/wishlist`

- **잔여 수량과 발급 가능 여부를 광고 서빙이 합쳐 주지 않는다.** 광고 서빙이 쿠폰을 부르면, 쿠폰이 발급 자격 확인을 위해 이미 광고 서빙의 찜 여부를 읽고 있어(FR-080) 도메인 간 순환이 생긴다(FR-072). 클라이언트가 화면에서 합친다
- `storeName`, `storeImageUrl`, `discount` 는 그날 후보 스냅샷(`ad_candidate`)에서 채운다. 스냅샷에 없는 캠페인이면 `null` 이다. 대표 이미지는 가게 이미지 중 LOGO다
- `wishedAt` 은 `wishlist.created_at` 이다. 찜할 때 행을 만들고 취소하면 행을 지우므로 둘이 같다
- **캠페인이 끝나면 찜을 바로 지우지 않고 종료로 표시한다.** 사용자가 찜한 캠페인이 끝난 것을 알 수 있게 하려는 것이다. `CampaignEndedEvent` 를 받아 그 캠페인의 찜을 종료로 바꾸고 `campaignEnded` 로 내려준다. 끝난 날(KST)을 빼고 3일 동안 보인 뒤 00:00 일일 작업이 지운다. 지우는 작업이 하루 한 번이라 72시간이 아니라 날로 자른다(#548 에서 정했다)
- **종료 여부는 `campaignEnded`(boolean)다.** 광고 서빙이 받는 것은 종료 이벤트 하나라 종료 여부만 정확히 안다. 문자열 상태는 ENDED 밖의 상태를 알 수 없고 캠페인의 상태 이름이 계약에 드러난다(#548 에서 정했다)
- **끝난 찜도 찜한 시각 순서에 섞는다.** 정렬을 바꾸지 않고 화면이 표시만 바꾼다(#548 에서 정했다)
- 페이지네이션을 두지 않는다. 사용자가 지운 찜은 바로 지우고 끝난 캠페인의 찜은 3일 뒤 지우므로, 진행 중인 캠페인 수에 최근 3일 동안 끝난 캠페인 수만 더해 쌓인다
- 사용자가 지우는 `DELETE` 는 행을 바로 지운다. 지운 찜을 남겨 두는 소프트 딜리트는 하지 않는다. 지우기가 유니크 키로 행 하나라 이득이 없고 모든 조회에 조건이 붙으며, 지웠다 다시 찜하면 유니크 키 때문에 행을 되살려야 한다(#548)
- `POST` 의 중복 키는 `(사용자, 캠페인)` 이다(`wishlist` UNIQUE)
- `POST` 는 그날 후보 행이 있는 캠페인만 받고 상태와 소진은 보지 않는다. 스와이프와 같다. 그날 후보가 아니면 이미 찜한 캠페인이어도 `404 ADSERVING-004` 다(#420)
- `POST` 로 찜한 캠페인도 당일 이력에 넣어 그날 피드에서 뺀다. 피드 5단계의 "찜한 캠페인은 당일 이력으로 뺀다" 를 가게 상세 찜에도 적용했다(#420)
- `DELETE` 뒤 10:50 알림 대상에서 빠지는 것은 따로 처리할 것이 없다. 알림이 10:50에 찜 목록을 읽어 보낸다(FR-073)
- `DELETE` 는 찜이 없어도, 그날 후보가 아니어도 당일 이력에 넣는다. 앞 요청이 Valkey 에 넣지 못했으면 다시 보낼 때 채워지고, 서빙 시간대가 없어져 00:00 후보 적재 전에 지운 찜도 그날 피드에서 빠진다(#547 에서 정했다)
- 숫자가 아닌 `campaignId` 는 공통 처리가 `400 COMMON-003` 으로 돌려준다. `api-spec.md` 의 `COMMON-002` 행(타입 불일치)과 다르다. 공통 규약의 어긋남이라 이 API 에서 따로 맞추지 않는다(#547)

## 다른 도메인에 공개한 기능

HTTP가 아니라 도메인 contract의 Java 클래스로 노출한다. 클라이언트는 쓰지 않는다.

| 공개 항목 | 쓰는 도메인 | 하는 일 |
|---|---|---|
| `WishlistQueryService` | coupon, notification | 찜 여부와 캠페인별 회원 일괄 찜 여부(FR-080 발급 자격), 그날 서빙 가능한 캠페인을 찜한 사용자(FR-076 10:50 발송 대상) |
| `CandidateStateUpdater` | coupon | 선착순 소진 시 그날 후보에 소진 표시(FR-093) |
| `ImpressionServedEvent`, `SwipedEvent` | analytics | 전환 퍼널 기록(impression, wish, pass). 비동기 |

**퍼널 이벤트 두 종은 아래처럼 나간다**(#349).

| 항목 | `ImpressionServedEvent` | `SwipedEvent` |
|---|---|---|
| 발행하는 때 | 유효 노출을 처음 저장할 때. 무효 노출과 이미 저장된 노출은 발행하지 않는다 | 스와이프 기록이 반영될 때(`applied: true`). 이미 넘긴 카드는 발행하지 않는다 |
| 발행하는 자리 | 노출 저장 트랜잭션 안 | 트랜잭션 밖. 기록은 이미 커밋돼 있다 |
| `eventId` | `impression:{serveId}`. 유효 노출은 serve 의 주인 것뿐이라 사용자를 넣지 않는다 | `swipe:{serveId}:{memberId}`. 스와이프의 중복 키가 (serveId, 사용자) 다 |
| `occurredAt` | 요청의 `displayedAt` 을 한국 시각으로 바꾼 값이다. `impression_log.displayed_at` 과 같다 | 요청의 `occurredAt` 을 한국 시각으로 바꾼 값이다. `swipe_log.occurred_at` 과 같다 |
| 캠페인과 가게 | serve 기록의 것 | 그날 후보의 것 |
| `wishId` | 없다 | `WISH` 면 그 사용자의 그 캠페인 찜의 id 다. 가게 상세에서 먼저 찜했으면 그 찜의 id 다. `PASS` 면 `null` 이다 |

`occurredAt` 은 클라이언트 시각이다. 퍼널은 사용자 행동의 순서를 보고, 이벤트와 원본 행의 시각이 같아야 추적할 수 있다. 미래 시각은 분석이 받을 때 보정하고, 늦은 시계로 과거에 찍힌 값은 보정되지 않는다.

**수신자는 아래 조건을 지킨다.** 왜 발행자가 아니라 수신자가 커밋 뒤를 맡는지는 [구조와 동작 설계](./adserving_구조와_동작_설계.md) 7장에 있다.

- `@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)` 와 `@Async` 로 받는다. 노출은 커밋된 뒤에만 넘어가고 롤백되면 넘어가지 않는다
- `fallbackExecution = true` 를 빠뜨리지 않는다. 스와이프는 트랜잭션 밖에서 발행돼, 빠뜨리면 스와이프 이벤트가 오류 없이 모두 사라진다
- 예외를 발행자에게 올리지 않는다. 실행기가 거절하면 버린다. 올리면 이미 커밋된 노출과 스와이프의 요청이 `500` 이 된다

알림이 쓸 10:50 발송 대상 조회는 아직 `WishlistQueryService` 에 없다. 쿠폰이 쓰는 두 메서드와 소진 반영만 있다(#163).

### `WishlistQueryService`

- **현재 유효한 찜은 `wishlist` 행이 있고 캠페인이 끝나지 않은 것이다.** 찜을 지우면 행이 지워지고, 캠페인이 끝나면 행은 3일 더 남지만 종료로 표시돼 유효하지 않다. `isWished` 와 `findWishedCampaignIds` 가 같은 기준을 쓴다(#163 에서 정했고 #548 에서 종료 표시를 더했다)
- 그날 후보인지는 보지 않는다. 00:00 후보 적재가 실패하거나 끝나기 전에 모든 발급이 막히고, 가게 상세에서 다음 날 캠페인을 찜하는 경우(FR-071 미정)에도 묶이기 때문이다
- 10:50 알림 대상 조회가 생기면 같은 기준으로 끝난 캠페인의 찜을 뺀다
- `findWishedCampaignIds` 는 찜이 없으면 빈 리스트다. 순서는 정하지 않는다
- **`findWishedMemberIds(campaignId, memberIds)` 는 쿠폰 묶음 발급이 캠페인당 한 번 부르는 일괄 조회다.** 회원마다 `isWished` 를 부르면 한 캠페인에 최대 500번 조회한다. 입력한 회원 가운데 유효하게 찜한 회원만 수정할 수 없는 집합으로 돌려주고 순서는 정하지 않는다. 기준은 `isWished` 와 같다(#578 에서 정했다)
- 입력은 500명까지이고 넘으면 `IllegalArgumentException` 이다. 쿠폰 묶음 발급의 최대 인원이며 늘릴 때는 계약 상수 `MAX_WISHED_MEMBER_IDS` 만 바꾼다. 회원 집합이 비면 조회하지 않고 빈 집합, null 이면 `IllegalArgumentException` 이다
- 잠그지 않는 읽기라 호출자의 트랜잭션 스냅샷을 본다. 조회 장애는 빈 집합으로 바꾸지 않고 올린다. 찜 여부가 발급 자격이라 실패를 찜 없음으로 바꾸면 발급이 조용히 거절된다

### `CandidateStateUpdater`

- **쿠폰은 마지막 재고를 발급한 트랜잭션이 커밋된 뒤 트랜잭션 밖에서 부른다.** 광고 서빙은 자기 트랜잭션에서 그 영업일의 후보만 바꾼다. 실패하면 그 갱신만 되돌아가고 쿠폰 발급과 성공 응답은 그대로다
- 받은 `soldOutAt` 을 그대로 쓴다. 부른 시각으로 바꾸지 않는다
- **다시 불러도 결과가 같다.** 이미 소진된 후보는 처음 소진 시각을 남긴다. `sold_out_at IS NULL` 인 행만 바꾼다(#163 에서 정했다)
- **그 영업일의 후보가 없으면 예외 없이 반환한다.** 쿠폰은 실패해도 발급을 유지해 예외를 받아도 할 일이 없다. 후보가 없는 경우는 `adserving_sold_out_candidate_missing_total` 로 센다(#163 에서 정했다)
- **반영이 빠지면 쿠폰이 `INVENTORY_EXHAUSTED` 로 발급을 거절할 때마다 다시 부른다.** 갱신 실패와 쿠폰 커밋 직후 프로세스 종료를 같은 방법으로 메운다. 소진 뒤 발급 요청이 없으면 복구되지 않는다. 빠진 동안의 소진 뒤 노출은 `NOT_BILLED_SOLD_OUT` 으로 걸러지지 않아 과금된다(#163 에서 정했다)

## 오류 코드를 나눈 기준

**판정에 업무 지식이 필요 없는 실패는 공통 코드를 쓴다.** 필수값 누락, 좌표 범위, `action` 과 정렬 값과 업종 코드 같은 고정 값, `serveId` 형식,
둘 중 하나는 있어야 하는 조건은 요청 타입의 애노테이션이 판정하므로 `COMMON-002` 로 온다.
`ADSERVING-` 코드는 후보, 사용자 상태, 정책을 봐야 판정할 수 있는 실패에만 둔다.

## 명세서를 나누며 새로 적은 것 (확인 필요)

이전 문서에 없던 값이라 명세서에 적으면서 정했다. 다르면 명세서와 함께 고친다.

| 위치 | 적은 내용 | 근거 |
|---|---|---|
| `GET /v1/feed` `latitude`, `longitude` | 범위 -90 ~ 90, -180 ~ 180 | 좌표 범위 오류가 `COMMON-002` 라고만 적혀 있었다 |
| `GET /v1/feed` `nextFeedAvailableAt` 예시 | 응답 시각과 같은 값으로 바꿨다 | 첫 요청이면 바로 다음 요청이 가능하다 |
| 진단 `slotType` | `ALLOCATION`, `RELEVANCE` | 이전 예시에 `ALLOCATION` 만 있었다 |
| 진단 `found: false` | `feedId`, `memberId`, `servedAt`, `settings` 는 `null`, `cards` 는 빈 배열 | 이전 문서는 `found` 만 적었다 |
| `POST /v1/wishlist` 오류 | `400 COMMON-002`(`campaignId` 누락) 추가 | 다른 API와 같은 규칙 |
