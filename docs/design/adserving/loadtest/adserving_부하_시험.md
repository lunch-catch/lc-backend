# adserving 부하 시험

광고 서빙의 쓰기 구조를 버전마다 같은 조건으로 재는 부하 시험의 환경, 데이터, 부하 생성기 설정, 회차, 돌리는 순서를 적는다.

- 무엇을 목표로 하는지는 [`feed-api-design.md`](../feed-api-design.md) 의 "성능 목표" 와 "유실 목표" 가 갖는다.
- 버전마다 무엇을 비교하는지는 [요청 중 쓰기 설계](../adserving_요청_중_쓰기_설계.md)의 "버전을 비교하는 지표" 가 갖는다.
- 시나리오와 스크립트는 [`loadtest/`](../../../../loadtest/README.md) 에 있다.
- 환경을 띄우고 내리는 법은 lc-infra 의 `docs/wiki/팀원-부하시험-환경.md` 가 갖는다.

## 1. 재는 것

| API | 부하 | 통과 기준 |
|---|---|---|
| `GET /v1/feed` | 초당 100건 | p99 300ms, 오류율 0.1% 미만 |
| `POST /v1/impressions` | 피드 1건마다 받은 카드 수만큼(최대 10건). 피드 초당 100건이면 최대 초당 1,000건 | p99 500ms, 오류율 0.1% 미만 |

두 기준은 `feed-api-design.md` 의 성능 목표와 같다. 오류율은 5xx 와 시간 초과만 센다. 통과 기준은 유지 구간(`phase:hold`)에만 건다.

스와이프와 찜 목록은 이 시나리오가 보내지 않는다.

## 2. 환경

lc-infra 의 `member-env.sh up --sha <커밋>` 으로 운영과 같은 인프라를 자기 AWS 계정에 한 벌 띄운다. 앱 이미지는 develop 커밋마다 GHCR 에 올라가는 `ghcr.io/lunch-catch/lc-backend:<SHA>` 다. 리소스 접두사는 `lunchcatch-lt` 이고, 같은 계정에 운영이 떠 있으면 띄우지 않는다.

서버 크기와 대수, DB 와 캐시의 등급, 부하 생성기의 인스턴스는 lc-infra 의 `docs/system-design/런치캐치_팀원_부하시험환경.md` 1절이 갖는다. 운영과 무엇이 다른지도 거기 있다. 아래는 이 시험이 그 위에 정하는 것이다.

| 자리 | 이 시험의 조건 |
|---|---|
| 앱 대수 | 3대로 고정한다. 아래에 이유와 명령이 있다 |
| 앱의 DB 커넥션 풀 | 서버마다 8. 7장이 이 값으로 커넥션 풀 병목을 가른다 |
| k6 | 1.7.1 |

**앱은 3대로 고정한다.** 앱 오토스케일링 그룹은 요청 수 기준으로 2대에서 3대까지 늘어난다. 회차 도중에 늘면 회차마다 조건이 달라 버전끼리 비교할 수 없다. `up` 뒤에 그룹의 최소와 원하는 대수를 3으로 올린다. `up` 을 다시 부르면 Terraform 이 되돌리므로 회차 전에 대수를 확인한다.

```bash
aws autoscaling update-auto-scaling-group --auto-scaling-group-name lunchcatch-lt-app \
  --min-size 3 --desired-capacity 3 --max-size 3
```

## 3. 데이터

`loadtest/adserving/gen_data.py` 가 만든다. 그날 예약과 후보는 넣지 않고 00:00 묶음이 만든다.

| 데이터 | 값 |
|---|---|
| 회원 | 40,000명. 온보딩을 마쳤고 중심 1km 안에 산다 |
| 가게와 캠페인 | 1,000개. 가게마다 진행 중 캠페인 하나, 반경 3,000m, 전 연령과 성별 |
| 하루 예산 | 캠페인마다 1,000,000포인트. 시험 중 예약액에 닿지 않는다 |
| 충전 | 점주마다 하루 예산의 40배 |
| 번호 | 3,000만 대역 |
| 중심 | 홍대입구역(37.5563, 126.9220) |

**홍대입구역에 두는 이유:** 기본 세계의 가게는 강남에 모여 있다. 강남에 두면 피드가 기본 세계 캠페인을 섞어 내려준다. 그러면 그 캠페인의 상태(계획 없음, 예약액 도달, 소진)에 따라 노출의 쓰기 양이 회차마다 달라진다. 노출, `serve_log`, 차감, 원장의 건수를 맞대 볼 수도 없다.

**가게를 1,000개로 두는 이유:** 피드는 그날 후보 전부를 거르고 점수를 매긴다. 후보가 많아야 운영에서 한 반경에 후보가 몰릴 때의 계산량을 잰다. 같은 캠페인은 한 세션에 한 번만 나오므로 회원 한 명이 카드 10장을 받는 피드는 100번까지다.

**데이터는 앱 서버에서 넣는다.** DB 보안 그룹은 앱, 배치, 모니터링만 받아 부하 생성기에서는 RDS 에 닿지 않는다. 앱 서버에서 앱 컨테이너의 접속 정보로 생성기를 돌려 넣는다.

**00:00 묶음은 재실행으로 돌린다.** 생성기가 그날 묶음의 실행 기록을 FAILED 로 넣는다. `loadtest/adserving/prepare.js` 가 서명한 관리자 토큰으로 수동 재실행 API 를 부른다. 묶음이 예약, 캠페인 활성화, 그날 후보 적재를 만든다.

## 4. 부하 생성기

`loadtest/adserving/feed_impression.js` 다.

| 설정 | 값 | 이유 |
|---|---|---|
| 실행 방식 | `ramping-arrival-rate` | 서버가 느려져도 반복이 정해진 속도로 시작된다 |
| 초당 피드(`FEED_RATE`) | 100 | 피드 목표다. 피드 100 x 카드 10 = 노출 1,000 |
| 램프업(`RAMP_UP_SECONDS`) | 60초 | 데워지지 않은 JVM 에 첫 초부터 목표 부하를 걸면 처음 쌓인 줄이 끝까지 남는다. 이 구간은 결과에서 뺀다 |
| 유지(`DURATION`) | 5분 | 결과는 이 구간만 센다 |
| 노출 보내는 방식 | 피드를 받자마자 카드 10장을 쉬지 않고 이어 보낸다 | 가장 가혹한 몰림을 본다 |
| VU(`PRE_VUS`, `MAX_VUS`) | 처음 200, 최대 2,000 | 목표대로면 반복 하나가 약 1.3초(피드 0.3초 + 노출 0.1초 x 10)라 130 이면 된다. 포화되면 약 12.5초라 1,250 이 필요하다 |
| 회원(`MEMBERS`) | 회차마다 10,000명 | 한 회원은 60초에 피드를 6번까지 받는다. 회차당 피드 약 3.3만 건이라 회원 한 명이 약 3.3번 받는다 |
| 위치 | 중심 0.5km 안 무작위 | 시험 캠페인만 후보가 된다 |
| 지표 전송 | Prometheus 로 5초마다 | Grafana 에서 앱과 DB 의 지표와 겹쳐 본다 |

- **노출 수는 따라 나오는 값이다.** 초당 노출은 피드 100건 x 성공한 피드의 카드 수다. 피드가 실패하면 그 피드의 노출은 나가지 않는다. 반복을 버리거나 카드가 10장보다 적을 때도 노출이 1,000건에 못 미친다. 결과를 볼 때 노출 요청이 실제로 초당 몇 건이었는지 먼저 본다.
- **생성기가 바쁘면 그 회차를 믿지 않는다.** 생성기의 CPU 가 높으면 요청을 늦게 보내거나 응답을 늦게 읽는다. 그 지연이 서버의 응답 시간으로 기록된다. 유지 구간에서 1분 평균 CPU 가 80% 를 넘은 회차는 무효로 보고 다시 잰다. 계속 넘으면 생성기를 키우거나 두 대로 나눈다.
- **반복을 버린 수를 함께 적는다.** VU 가 최대에 닿으면 k6 가 정해진 속도를 지키지 못하고 반복을 버린다(`dropped_iterations`). 그 수가 서버가 목표 속도를 받지 못했다는 신호다.

## 5. 회차

**환경은 한 번 띄우고 버전 사이에 비운다.** 이미지만 바꾸면 앞 버전이 쌓은 `impression_log`, `serve_log`, 원장, Valkey 의 노출 횟수가 다음 버전에 남아 뒤 버전이 불리하다. 그래서 버전을 바꿀 때 Valkey 를 비우고 시드를 다시 넣는다(`reset`). 시드는 시험 데이터와 그날 배치 기록을 지우고 다시 넣는다. 회원 대역도 버전마다 처음부터 다시 쓴다. 버전마다 환경을 새로 띄우면 버전마다 약 30분이 더 들어 고르지 않았다.

- RDS(T4g)는 Unlimited 라 CPU 크레딧이 바닥나도 느려지지 않는다. 버전 사이에 이어져도 된다.
- ElastiCache(t4g)는 Unlimited 가 없어 CPU 크레딧이나 네트워크 버스트가 바닥나면 기준 성능으로 떨어진다. 회차마다 `metrics` 로 보고 바닥났거나 네트워크 초과가 생긴 회차는 무효로 본다.
- DB 의 버퍼 캐시는 데워진 채로 다음 버전에 넘어간다. 버전마다 워밍업 회차가 있어 영향이 작다고 본다.
- 환경은 `member-env.sh up` 에 `MEMBER_HOURS` 를 주면 그 시간 뒤 자동으로 지워지고, 주지 않으면 지워지지 않는다(lunch-catch/lc-infra#92). 주면 측정 전체(6장의 순서)보다 넉넉히 준다. 주지 않았으면 끝난 뒤 `member-env.sh down` 으로 직접 내린다.

| 버전 | 이미지 |
|---|---|
| 노출 수집 v1 | `67f46b2e` |
| 노출 수집 v2 | `9aa6bae9` |
| 노출 수집 v3 | #1041 이 병합된 커밋 |

버전마다 워밍업 1회와 측정 3회를 돌린다. 회차 사이에 JVM 을 다시 띄우지 않는다.

| 회차 | 램프업 | 유지 | 회원 대역 | 결과 |
|---|---|---|---|---|
| 워밍업 | 60초 | 1분 | 30030001 ~ 30040000 | 뺀다 |
| 측정 1 | 60초 | 5분 | 30000001 ~ 30010000 | 3회 평균 |
| 측정 2 | 60초 | 5분 | 30010001 ~ 30020000 | 3회 평균 |
| 측정 3 | 60초 | 5분 | 30020001 ~ 30030000 | 3회 평균 |
| 프로파일링(필요할 때) | 60초 | 5분 | 30030001 ~ 30040000 | 뺀다. 측정 3회 뒤에 돌린다 |
| 추적(필요할 때) | 60초 | 5분 | 30030001 ~ 30040000 | 뺀다. 측정 3회 뒤에 에이전트를 붙여 돌리고 뗀다 |

서빙 시험(피드만, `--scenario feed`)은 같은 표를 회원 대역만 4만 뒤로 옮겨 쓴다. 워밍업 30070001, 측정 1~3 은 30040001, 30050001, 30060001, 진단은 30070001 부터다. 같은 커밋의 노출 회차를 잰 뒤 `reset` 없이 이어 잰다. 그래서 시드는 회원 80,000명(30000001 ~ 30080000)을 넣는다.

노출 횟수는 그날 내내 남는다. 같은 날 회차를 거듭하면서 같은 회원을 쓰면 뒤 회차일수록 카드가 줄어 회차마다 다른 대역을 쓴다.

## 6. 돌리는 순서

`loadtest/adserving/run.sh` 가 인스턴스에 SSM 으로 스크립트를 보내 돌린다. `AWS_PROFILE` 은 `member-env.sh up` 을 돌린 계정의 프로필이다. 시나리오와 시드 생성기는 떠 있는 앱과 같은 커밋(SSM `current-sha`)에서 받는다. `LOADTEST_REF` 로 브랜치나 커밋을 따로 고를 수 있다.

환경은 한 번만 띄운다. 첫 버전 뒤로는 버전마다 `switch` 와 `reset` 으로 바꾸고 2~4를 다시 한다(5장). `switch` 는 GHCR 에 그 커밋의 이미지가 있는지 먼저 보고, 없으면 아무것도 바꾸지 않고 멈춘다.

```bash
# 1. 환경을 띄우고 앱을 3대로 고정한다(2장)
AWS_PROFILE=<프로필> ./scripts/member-env.sh up --sha <이미지>     # lc-infra 에서

# 2. 데이터를 넣고 그날 00:00 묶음을 다시 돌린다
AWS_PROFILE=<프로필> loadtest/adserving/run.sh seed 80000
AWS_PROFILE=<프로필> loadtest/adserving/run.sh prepare

# 3. 워밍업과 측정 3회
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run v1-warmup 30030001 100 1m
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run v1-run1 30000001
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run v1-run2 30010001
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run v1-run3 30020001

# 어디서 시간을 쓰는지 보려면 측정 회차가 끝난 뒤 따로 돌린다. 결과에 적지 않아 워밍업 대역을 다시 쓴다
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run v1-run1-profile 30030001 100 5m --profile wall

# 요청 하나를 단계별로 보려면 에이전트를 붙여 다시 띄우고 돌린 뒤 뗀다. 프로파일링 회차와 같은 대역을 쓴다
AWS_PROFILE=<프로필> loadtest/adserving/run.sh switch <이미지> --tracing v1-tracing
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run v1-run1-tracing 30030001 100 5m
AWS_PROFILE=<프로필> loadtest/adserving/run.sh switch <이미지>

# 4. 회차마다 출력된 window 구간으로 서버 지표를 모은다. 행 수는 마지막 회차가 끝나고 10초 뒤에 맞대 본다
AWS_PROFILE=<프로필> loadtest/adserving/run.sh metrics <window 시작 ms> <window 끝 ms>
AWS_PROFILE=<프로필> loadtest/adserving/run.sh rows

# 다음 버전: 앱과 배치를 그 이미지로 다시 띄우고 비운 뒤 2~4를 다시 한다. 앱이 3대인지 먼저 확인한다
AWS_PROFILE=<프로필> loadtest/adserving/run.sh switch <다음 이미지>
AWS_PROFILE=<프로필> loadtest/adserving/run.sh reset

# 5. 대시보드를 남기고 환경을 내린다(lc-infra 에서). --lt 가 부하 시험 환경을 가리킨다
AWS_PROFILE=<프로필> ./scripts/loadtest-snapshot.sh --lt --label adserving-v1-run1 --from <window 시작 ms> --to <hold 끝 ms>
AWS_PROFILE=<프로필> ./scripts/member-env.sh down
```

### 측정 순서

커밋이 같은 버전은 이어 잰다. `switch` 와 `reset` 은 커밋이 바뀔 때만 한다.

| 순서 | 버전 | 시나리오 | 앞 버전과 같은 커밋인가 |
|---|---|---|---|
| 1 | 노출 수집 v1 | 피드와 노출 | 처음 |
| 2 | 노출 수집 v2 | 피드와 노출 | 아니다 |
| 3 | 노출 수집 v3 | 피드와 노출 | 아니다 |
| 4 | 노출 수집 v3b | 피드와 노출 | 아니다 |
| 5 | 서빙 v1 | 피드만 | 그렇다(v3b) |
| 6 | 노출 수집 v3c | 피드와 노출 | 아니다 |
| 7 | 서빙 v2 | 피드만 | 그렇다(v3c) |
| 8 | 노출 수집 v4 | 피드와 노출 | 아니다 |
| 9 | 서빙 v3(풀 켬) | 피드만 | 그렇다(v4) |
| 10 | 서빙 v3(풀 끔) | 피드만 | 그렇다. `switch <이미지> --no-pool` 로 다시 띄우고 `reset` 한 뒤 서빙 대역을 다시 쓴다. 풀 켬이 서빙 대역을 다 써서다 |

커밋마다 진단 회차를 하나 돌린다(#1088). 트레이싱을 붙이고 프로파일링을 `both` 로 함께 붙인 회차다. 결과에 적지 않는다.

```bash
# 서빙 시험. 같은 커밋의 노출 회차 뒤에 이어 잰다
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run serving-v1-warmup 30070001 100 1m --scenario feed
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run serving-v1-run1 30040001 100 5m --scenario feed

# 진단 회차. 트레이싱을 붙여 다시 띄우고 프로파일링을 함께 붙인다
AWS_PROFILE=<프로필> loadtest/adserving/run.sh switch <이미지> --tracing v1-tracing
AWS_PROFILE=<프로필> loadtest/adserving/run.sh run v1-run1-tracing-profile 30030001 100 5m --profile both
AWS_PROFILE=<프로필> loadtest/adserving/run.sh switch <이미지>
```

- 피드만 보낸 회차의 경고 로그는 `서빙_부하_시험_결과.md` 에 적힌다.
- 생성기는 그날 배치 기록을 지우므로 시험하는 날에 넣는다. 앱이 판단하는 영업일(Asia/Seoul)과 같아야 한다.
- 행 수를 회차 직후에 세면 아직 쓰이지 않은 행이 빠진다. 노출 수집 v3 는 응답 뒤 최대 200ms 에 저장하고 v2 부터는 릴레이가 1초마다 정산에 넘긴다.
- **회차가 끝나면 경고 로그 건수가 결과 문서에 적히고 커밋이 하나 생긴다.** `run` 이 그 회차 구간의 `ADSERVING_` 경고와 오류를 이벤트별로 세어 `노출_수집_부하_시험_결과.md` 의 `경고 로그` 절 표에 적는다. 푸시는 하지 않는다. 지금 브랜치에 커밋하므로 시험용 브랜치에서 돌린다. develop 에서 돌리면 develop 에 커밋이 생긴다.
- 워밍업(`-warmup`), 프로파일링(`-profile`), 추적(`-tracing`) 회차는 결과 문서에 적지 않는다. 프로파일링과 추적은 표본과 스팬을 만드는 비용이 들어 측정 회차와 나눈다. 무엇을 어떻게 보는지는 [`loadtest/README.md`](../../../../loadtest/README.md) 의 프로파일링 절과 추적 절이 갖는다.
- 같은 순서를 노트북에서 돌리려면 첫 인자로 `--local` 을 준다. 순서는 [`loadtest/README.md`](../../../../loadtest/README.md#로컬에서-돌리기) 가 갖는다.
- 앱에 `CDN_BASE_URL` 이 비어 있으면 그날 후보 적재가 실패한다. 부하 시험 환경은 lc-infra 가 채운다. 로컬에서는 아무 값이나 준다.

## 7. 모으는 지표

회차마다 아래를 남긴다. 어느 쪽이 병목인지 가르고 버전을 올린 이유를 확인하는 데 쓴다. `loadtest/adserving/run.sh metrics` 가 k6 밖의 지표를 회차 구간으로 뽑는다.

| 자리 | 지표 | 보는 것 |
|---|---|---|
| k6(유지 구간) | API 별 초당 요청 수, p50, p95, p99, 오류 수, 버린 반복(`dropped_iterations`), 노출 판정(유효, 무효) | 목표를 지켰는지. 노출이 실제로 초당 몇 건이었는지 |
| 앱 | Hikari 대기 최대, 사용 최대, 시간 초과 수, 커넥션 획득 평균 시간, 커넥션을 쥔 평균 시간, CPU 평균과 최대, 5xx 수 | 커넥션 풀이 병목인지 |
| DB | 초당 커밋과 INSERT, 돌고 있는 스레드 최대, RDS CPU 최대와 CPU 크레딧 잔량 | DB 서버가 병목인지. RDS 의 t4g 는 Unlimited 라 크레딧이 바닥나도 느려지지 않는다 |
| 캐시 | 노드마다 엔진 CPU 최대, CPU 크레딧 잔량 최소, 네트워크 허용량을 넘긴 패킷 수 | Valkey 가 병목인지. ElastiCache 의 t4g 는 크레딧이나 네트워크 버스트가 바닥나면 느려진다 |
| 쓰기 | `serve_log` 쓰기 실패와 버린 수, 내려준 카드 수, 노출과 `serve_log` 와 차감과 원장의 행 수 대조(`rows`) | 유실과 쓰기가 맞는지 |
| 노출 저장과 릴레이 | 릴레이의 밀린 노출 최대(v2 부터), 노출 저장 큐의 최대, 큐가 차서 버린 수, 실패한 묶음 수, 쓰지 못하고 버린 행 수(v3 부터) | 응답 뒤 저장이 따라가는지. 버린 노출은 유실률에 들어간다 |
| 부하 생성기 | 1분 평균 CPU 의 최대 | 생성기가 병목이 아닌지. 유지 구간에서 80% 를 넘으면 그 회차는 무효로 보고 다시 잰다 |

대시보드는 회차가 끝난 직후, 환경을 내리기 전에 lc-infra 의 `loadtest-snapshot.sh --lt` 로 남긴다. `--dash` 를 주지 않으면 01 개요부터 06 광고 서빙(`lc-overview` ~ `lc-adserving`)까지 여섯 장을 대시보드 높이 그대로 찍는다. 환경을 내리면 Prometheus 의 기록도 함께 사라진다.

- **범위는 회차 시작부터 유지 구간 끝까지 한 번 준다.** `run` 이 출력하는 `window` 의 시작과 `hold` 의 끝이다. `hold` 는 k6 가 로그에 남긴 시나리오 시작 시각(`scenario_start`)에 램프업을 더해 계산한다.
- **대시보드는 흐름을 보는 시계열이다.** 결과 수치는 k6 요약과 `metrics` 로 적는다. 대시보드는 그 수치가 왜 나왔는지(어느 지표가 먼저 올랐는지, 유지 구간이 안정됐는지)를 보는 근거다.
- **API 별 p99 는 둘을 견준다.** 05 의 응답 지연은 부하 생성기가 본 시간이고, API 별 p99(앱)는 앱이 잰 시간이다. 앞이 크면 그 차이가 앱 앞에서 스레드를 기다린 시간이다.

## 8. 결과를 남기는 곳

이 디렉터리가 함께 갖는다. 조건과 결과를 떨어뜨려 두면 다음 버전을 재려는 사람이 둘을 따로 찾는다. 이 문서는 결과를 담지 않는다.

- 측정한 커밋에 `adserving-{시험}-v{버전}` 태그를 붙인다. `{시험}` 은 결과 문서 하나에 대응하는 시험 이름이다. 노출 수집 부하 시험은 `impression`, 서빙 시험은 `serving` 이다. 무엇을 바꿨든 그 시험에서 잰 다음 커밋이면 다음 버전이다. 이미 붙인 `adserving-impression-v1` ~ `v3c` 는 그대로 둔다.
- **이 시험은 시험마다 문서 하나를 둔다.** 노출 수집은 `노출_수집_부하_시험_결과.md`, 서빙은 `서빙_부하_시험_결과.md` 가 갖는다. 버전끼리 비교하는 것이 목적이라 버전들이 한 문서에 나란히 있어야 읽힌다. 다른 시험이 이 모양을 따를 이유는 없다.
- 대시보드 PNG 는 버전마다 `impression-v{버전}/`, `serving-v{버전}/` 에 둔다.
