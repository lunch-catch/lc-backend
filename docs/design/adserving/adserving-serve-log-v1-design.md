# 서빙 로그 v1: 인메모리 비동기

피드가 응답한 뒤 서버 안의 대기열에 넣고 작업자가 묶어서 쓴다. 접속 위치(`feed_visit_daily`)도 같은 방식이다.

쓰기마다 어느 방식을 고르는지와 버전 목록은 [요청 중 쓰기 설계](./adserving_요청_중_쓰기_설계.md)가 갖는다.

**v1 을 그 방식으로 고른 이유와 정한 값은 이 문서가 갖지 않는다.** 아래가 그 자리다. 그 절의 이름이 바뀌면 이 문서만 고친다. 밖에서 들어오는 링크는 이 파일을 가리킨다.

**아래가 성립하는 것은 서빙 로그가 아직 v1 이기 때문이다.** 구조와 동작 설계는 현재 버전을 적고 버전이 올라가면 덮어쓴다. v2 로 올라가면 그 문서는 v2 를 적게 되고, 그때 v1 의 모양을 여기로 옮겨야 한다. 노출 수집이 그 과정을 거치며 v1 의 기록을 잃었다.

| 무엇 | 어디 |
|---|---|
| 이 방식을 고른 이유와 선택지 | [구조와 동작 설계](./adserving_구조와_동작_설계.md) 7장 "서빙 로그와 접속 위치를 무엇으로 미루나"(#315) |
| 대기열 크기, 묶음 크기, 차면 버리는 규칙, 종료할 때 비우기 | 같은 절 |
| 묶어 쓰고 차면 버리는 코드 | 같은 문서의 `ServeLogBuffer` 행 |
| 대기열이 차거나 쓰기가 실패할 때의 처리 | [장애 처리 설계](./adserving_장애_처리_설계.md) "DB 쓰기: 응답 뒤의 `serve_log`, `feed_visit_daily`" |

## 이 문서가 아직 갖지 않는 것

노출 수집 v1 은 한 건이 지나는 순서를 적지만 서빙 로그 v1 은 적지 않는다. 그 흐름이 피드 응답 경로에 속해 [구조와 동작 설계](./adserving_구조와_동작_설계.md)의 피드 순서도가 갖기 때문이다. 서빙 로그만의 설계를 적을 일이 생기면 여기에 쓴다.
