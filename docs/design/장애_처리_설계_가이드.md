# 장애 처리 설계 가이드

캐시, DB, 외부 API 처럼 이 서비스가 기대는 것을 **대상**이라고 부른다. 대상이 멈추거나
느려졌을 때 들어온 요청을 **막을지 통과시킬지**를 이 문서가 정한다. 같은 결정을 기능마다
다시 하지 않는다.

결정이 흩어져 있으면 "캐시가 죽으면 이 서비스는 어떻게 되나" 에 답할 자리가 없다. 같은
대상인데 도메인마다 다른 처리를 골라도 비교할 지면이 없다.

이 디렉터리의 나머지 문서는 도메인별 설계다. 이 문서는 그 설계를 쓸 때의 기준이다.

## 담지 않는 것

| 무엇 | 소유 |
|---|---|
| 복구 시간과 데이터 손실 한도, 타임아웃 값 | [qa-reliability-guideline.md](../software-quality/qa-reliability-guideline.md) |
| 경보가 울린 뒤 사람이 하는 일 | [qa-incident-response-guideline.md](../software-quality/qa-incident-response-guideline.md) 런북 8장(`INC-8-01`) 아직 쓰지 않았다 |
| 복구 직후 요청을 천천히 받는 방법 | [qa-incident-response-guideline.md](../software-quality/qa-incident-response-guideline.md) `INC-6-01` ~ `INC-6-04` |
| 같은 배치 작업이 두 대에서 함께 돌지 않게 막는 방법 | [런치캐치_배치_운영.md](./ops/런치캐치_배치_운영.md) 2장 |

여기는 **코드가 고를 수 있는 것**만 정한다.

**이 문서는 코드 점검 기준이 아니다.** 자동 리뷰가 설계 기록을 점검 기준으로 쓰면 지나간
결정으로 지적이 나온다. 그래서 이 문서를 자동 리뷰에 등록하지 않는다. 지금 코드가 지켜야
하는 것은 테스트와 `docs/code-convention`, `docs/software-quality` 가 소유한다.

## 모든 유형에 걸리는 것

**의존 대상은 멈춘 것보다 느려진 것이 위험하다.** 대상이 멈추면 호출이 즉시 실패해서
스레드가 돌아온다. 느려지면 스레드가 쌓여 그 대상 하나가 전체를 끌어내린다. 그래서 외부
호출마다 타임아웃을 둔다. 타임아웃이 없으면 호출하는 쪽이 멈춘 줄도 모르고 기다려서, 아래
처리가 돌 기회가 없다.

**대상이 멈췄는데 막지 않고 통과시킨 요청은 센다.** 요청을 막으면 사용자가 바로 알려 주지만
통과시키면 아무도 모른다. 캐시가 며칠 죽어 있어도 사용자는 불편을 못 느낀다. 그 사이 폐기한
권한은 계속 통과한다. 그래서 통과시킨 횟수를 지표로 내보내고 그 지표에 경보를 건다. 로그만
남기면 아무도 보지 않는다. 경보는 자원 지표가 아니라 이 횟수처럼 증상을 기준으로 건다.

**멈췄던 대상이 다시 살아날 때도 본다.** 복구가 두 번째 장애를 만든다. 캐시가 돌아오면 비어
있는 캐시에 요청이 전부 몰려 원본이 그때 죽는다. 끊어 두었던 외부 API 호출이 다시 열리면
쌓인 요청이 한꺼번에 나간다.

## 기본 처리

| 대상 | 기본 처리 | 왜 | 예외 |
|---|---|---|---|
| 캐시 | 통과시킨다 | 캐시는 성능 장치다. 없다고 로그인을 막으면 캐시 장애가 전면 장애가 된다 | 느려지는 것과 틀리는 것을 가른다. 선착순 수량과 같이 없으면 틀리는 곳은 거절한다 |
| DB 읽기 | 오류로 올린다 | 빈 값으로 보면 "없음" 과 "모름" 이 같아진다 | |
| DB 쓰기 | 트랜잭션을 되돌린다 | 부분 반영은 복구가 더 비싸다 | |
| 외부 API | 멱등한 연산의 재시도 가능한 오류만 재시도하고 한도에서 포기한다 | 상대가 답하지 않는다고 응답까지 멈추게 하지 않는다 | 멱등이 아니면 재시도하지 않고 결과를 조회해 확인한다. 로그인처럼 대체 경로가 없으면 즉시 실패를 알린다 |
| 애플리케이션 | 일시적 실패만 자동 재실행한다 | 데이터가 어긋난 실패는 몇 번 돌려도 같은 자리에서 터진다 | |
| 롤백 안 되는 효과 | 커밋 전에 기록하고 커밋 뒤에 실행한다 | 트랜잭션이 되돌릴 수 있는 것은 DB 쓰기뿐이다 | |

## 유형별 점검

위에서 정한 처리가 실제로 서는지는 상황을 하나씩 걸어 봐야 안다. 순서와 이름은 위 표와 같다.
도메인 설계 문서를 쓰는 사람이 이 목록을 훑고 해당 없는 것은 해당 없다고 적는다.

### 캐시

| 시나리오 | 검증할 것 |
|---|---|
| 캐시 다운 | 원본으로 폴백하는지, 아니면 전체 장애가 되는지 |
| 캐시 스탬피드 | 만료 순간 요청이 몰려 원본을 때리는지 |
| 분산 락 | 락을 캐시로 잡는데 캐시가 죽거나 락 TTL 이 만료된 경우 |
| 낡은 값 | 정지나 탈퇴처럼 즉시 제한이 필요한 판정이 낡은 캐시로 통과하는지. 그 자리는 캐시를 우회한다 |

### DB

| 시나리오 | 검증할 것 |
|---|---|
| 다운, 연결 거부 | 빠르게 실패하고 명확한 오류를 주는지, 복구 후 자동 재연결되는지 |
| 슬로우 쿼리, 응답 지연 | 쿼리 타임아웃이 걸리는지, 커넥션 풀이 고갈되어 전체 API 가 멈추지 않는지 |
| 커넥션 풀 고갈 | 풀 대기 상한을 넘기면 예외로 빠지는지, 무한 대기하지 않는지 |
| 데드락 | 교착으로 롤백된 트랜잭션에 재시도가 도는지 |
| 락 대기 초과 | 대기 상한을 넘겼을 때의 처리 |
| 제약 위반, 데이터 불일치 | 재시도하지 않고 그대로 올리는지. 몇 번 돌려도 같은 자리에서 터진다 |
| Primary 페일오버 | 쓰기 실패 구간 동안 데이터 유실이나 중복이 없는지 |
| 복제 지연 | 쓰기 직후 복제본에서 읽을 때 옛 데이터를 보는 문제 |

### 외부 API

| 시나리오 | 검증할 것 |
|---|---|
| 타임아웃 | connect timeout 과 read timeout 이 모두 설정되어 있는지 |
| 5xx, 연결 끊김 | 멱등한 연산인지 먼저 보는지. 재시도 횟수와 간격(백오프)이 적절한지 |
| 지속 장애 | 호출을 차단하고 폴백으로 가는지. 차단되어 부르지도 못한 것을 재시도 횟수에 세지 않는지 |
| 인증 거부 | 이 서비스의 설정 문제라 포기하지 않는지, 그 거부로 다른 호출까지 차단하지는 않는지 |
| 애매한 실패 | 요청은 보냈는데 응답을 못 받은 경우. 멱등이 아니면 재시도하지 않는지. 응답을 못 받은 것은 실패가 아니라 결과를 모르는 것이다 |

**호출을 차단할지와 영구 포기할지는 다른 질문이다.** 앞은 "지금 더 부르는 것이 무의미한가",
뒤는 "이 대상을 영원히 포기할 것인가" 다. 한 판정이 둘을 같이 맡지 않는다. 횟수로 포기한 것과
상대가 거부해 포기한 것도 운영 대응이 달라 구분해 기록한다.

결제가 이 유형의 가장 비싼 자리다. 이중 결제는 사용자 돈이 두 번 빠지는 것이고 되돌리는 데
사람이 붙는다.

### 애플리케이션

| 시나리오 | 검증할 것 |
|---|---|
| 요청이 몰린다 | 요청을 처리할 스레드가 바닥나고 응답이 느려지는지 |
| 대용량 조회 | 페이징 없이 전체를 읽어 OOM 이 나는지 |
| 배포로 서버가 내려간다 | 처리 중이던 요청을 마치고 내려가는지 (graceful shutdown) |
| 서버가 여러 대다 | 같은 스케줄러 작업이 두 대에서 함께 돌지는 않는지 |

### 롤백 안 되는 효과

| 시나리오 | 검증할 것 |
|---|---|
| 커밋 뒤 실패 | DB 는 반영됐는데 그 뒤의 외부 호출이나 알림이 실패한 경우 다시 집어 올리는지 |
| 커밋 전 성공 | 외부 효과는 나갔는데 커밋이 실패한 경우. 되돌릴 수 없으므로 순서를 바꿔야 하는 자리인지 |
| 보상 실패 | 되돌리는 처리 자체가 실패하는 경우 |

**순서가 핵심이다.** 실패한 뒤에 기록하도록 두면 커밋과 기록 사이의 모든 중단이 유실이
된다. 커밋 전에 기록해 두면 그 사이에 무엇이 멈춰도 다음 배치가 집어 올린다. 커밋 뒤에
실행하는 것은 실패할 수 있으므로 멱등이어야 한다.

한 트랜잭션 안에서 끝나는 일은 DB 가 되돌린다. 여기서는 **트랜잭션 경계 밖으로 나간
효과**를 본다. 모놀리스라 분산 트랜잭션은 없지만, 외부 호출이 끼는 순간 이 문제는 생긴다.

## 설계 문서

작성자는 도메인마다 하나씩 `docs/design/{도메인}/{도메인}_장애_처리_설계.md` 로 둔다. 기능마다 쓰지 않는다.
문서 수가 불어나고 테스트와 겹친다. 어느 도메인이 무엇에 기대는지가 곧 그 도메인의 장애
동작이라, 도메인 단위로 쓴다.

쓸 때 위의 유형별 점검 목록을 훑는다. 해당 없는 것은 해당 없다고 적는다. 빈 칸으로 두면 훑지
않은 것과 구별되지 않는다.

**기본 처리를 그대로 따르는 것은 적지 않는다. 벗어난 것만 적는다.** 그러면 설계 문서가 예외
목록이 되어 짧게 유지된다. 설계 문서가 비어 있으면 그 도메인은 전부 기본 처리를 따른다는
뜻이다.

| 적는 것 | 적지 않는 것 |
|---|---|
| 이 도메인이 기대는 대상 | 기본 처리를 그대로 따르는 대상 |
| 벗어난 대상과 그 이유 | 테스트가 이미 검증하는 동작의 재서술 |
| 아직 정하지 못한 것 | 인프라 복구 시간과 손실 한도 |

**병합된 뒤에는 코드와 테스트가 기준이다.** 이 문서는 그때 왜 그렇게 정했는지를 남긴다.
코드가 바뀌었는데 문서를 안 고치면 문서가 틀린 것이다. 그 어긋남을 막는 장치는 없다.
그래서 짧게 쓴다. 테스트로 옮길 수 있는 것은 옮긴 뒤 여기서 지운다.

## 부록. 설계 문서 틀

```markdown
# {도메인} 장애 처리 설계

이 도메인이 기대는 대상과 기본 처리를 벗어난 것을 적는다. 어디까지 훑었는지도 적는다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| 예: 캐시 | 요청 제한 | 기본(통과) |
| 예: other 의 `OtherQuery` | 상태 판정 | 벗어났다. 아래 |

## 벗어난 것

### {유형}: {대상}

선택지와 장단점, 고른 이유, 통과시킨 횟수를 세는 지표를 적는다.

## 유형별 점검

| 유형 | 점검 결과 |
|---|---|
| 캐시 | |
| DB | |
| 외부 API | |
| 애플리케이션 | |
| 롤백 안 되는 효과 | |

## 아직 정하지 못한 것
```

이 틀은 장을 채우라는 것이 아니다. 빠지면 드러나지 않는 셋을 자리로 잡아 둔 것이다. 기대는
대상, 유형 다섯의 점검 결과, 아직 정하지 못한 것이다.

- 기본 처리를 그대로 따르는 대상은 첫 표에 한 줄로 적고 `벗어난 것` 에는 두지 않는다.
- `유형별 점검` 의 칸은 셋 중 하나다. 해당 없는 이유, 아직 훑지 않았다는 말, 또는 `벗어난 것`
  의 어느 절인지다. 둘을 한 칸에 섞으면 훑은 것과 훑지 않은 것이 구별되지 않는다.
- 한 유형 안에서 시나리오마다 결과가 다르면 그 유형의 행을 시나리오로 쪼갠다.
