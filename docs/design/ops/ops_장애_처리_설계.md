# ops 장애 처리 설계

이 도메인이 기대는 대상과 기본 처리를 벗어난 것을 적는다. 어디까지 훑었는지도 적는다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| DB(MySQL) | `batch_execution_log`, `audit_log`의 모든 읽기·쓰기, `platform_setting`의 읽기 | 기본(오류로 올린다 / 트랜잭션을 되돌린다) |
| 배치 서버의 이어받기(`DailyJobScheduler.takeOverStale`, 1분마다) | 수동 재실행의 실제 재개(#1231) | 벗어났다. 아래 |

## 벗어난 것

### 수동 재실행의 재개를 배치 서버에 맡긴다 (#1231)

요청은 조건부 UPDATE(FAILED -> RUNNING, 소유자는 요청 표식)와 감사 로그를 한 트랜잭션에 커밋하고 끝난다.
감사 로그를 남기지 못하면 UPDATE 도 롤백되어 행이 `FAILED`로 남는다. 커밋 전에는 배치 서버에 보이지 않아,
감사 없는 재실행이 돌지 않는다.

실제 재개는 배치 서버의 이어받기가 다음 스캔에 집어 `BatchJobRunner.resume`으로 돈다. 요청을 받은 앱 서버에서
돌리지 않는 이유는 둘이다. 앱 서버는 요청용 시간 제한(쿼리와 트랜잭션 5초, #1221)을 받아 5초를 넘는 단계가 있는
묶음이 재실행으로 복구되지 않는다. 그리고 앱 서버는 생존 신호를 보내지 않아 2분을 넘는 재개를 배치 서버가 멈춘
것으로 보고 한 번 더 돌릴 수 있다.

집은 배치 서버가 재개 도중에 죽으면 생존 신호가 멈춰 2분 뒤 다른 배치 서버가 같은 재개 경로로 다시 돈다. 그래서
별도의 보상 처리를 두지 않는다. 배치 서버가 하나도 떠 있지 않으면 요청 표식인 행이 `RUNNING`으로 남는다. 그때는
00:00 묶음도 돌지 않아 배치 서버부터 살려야 한다.

## 유형별 점검

### 캐시

해당 없음. 이 도메인은 캐시를 쓰지 않는다. 플랫폼 설정값도 캐시 없이 읽을 때마다 DB를 읽는다.

### DB

| 시나리오 | 점검 결과 |
|---|---|
| 다운, 연결 거부 | 해당 없음. 기본 처리(오류로 올린다)를 따른다 |
| 슬로우 쿼리, 응답 지연 | 해당 없음. 기본 처리를 따른다. 조건부 UPDATE 한 문장뿐이라 느려질 지점이 적다 |
| 커넥션 풀 고갈 | 해당 없음. 기본 처리를 따른다 |
| 데드락 | 해당 없음. 기본 처리를 따른다. 수동 재실행은 행 하나만 건드려 데드락 가능성이 낮다 |
| 락 대기 초과 | 해당 없음. 기본 처리를 따른다 |
| 제약 위반, 데이터 불일치 | 해당 없음. 기본 처리(재시도하지 않고 올린다)를 따른다. 플랫폼 설정값이 없거나 정수가 아니거나 0 이하면 `IllegalStateException`으로 올린다. 0원 단가가 그대로 나가 모든 캠페인이 예산 부족으로 판정되는 일을 막으려는 것이다 |
| Primary 페일오버 | 아직 정하지 못한 것. 조건부 UPDATE가 페일오버 구간에 걸리면 재실행이 걸렸는지 불명확한 상태로 응답이 실패할 수 있다 |
| 복제 지연 | 해당 없음. 쓰기와 읽기를 모두 Primary로 보낸다(다른 도메인과 같다) |

### 외부 API

해당 없음. 이 도메인은 외부 API를 부르지 않는다.

### 애플리케이션

| 시나리오 | 점검 결과 |
|---|---|
| 요청이 몰린다 | 벗어났다. 위 "벗어난 것: 전용 실행기" |
| 대용량 조회 | 해당 없음. 이 도메인의 조회는 한 행 또는 한 영업일 범위뿐이다 |
| 배포로 서버가 내려간다 | 아직 정하지 못한 것. graceful shutdown이 접수된 재개를 끝까지 기다려 주는지 확인하지 않았다 |
| 서버가 여러 대다 | 해당 없음. 기본 처리(배치 운영 공통 규칙)를 따른다. 상세는 런치캐치_배치_운영.md 2장 |

### 롤백 안 되는 효과

| 시나리오 | 점검 결과 |
|---|---|
| 커밋 뒤 실패 | 벗어났다. 위 "수동 재실행의 재개를 배치 서버에 맡긴다" |
| 커밋 전 성공 | 해당 없음. 조건부 UPDATE 커밋 전에는 외부에 보이는 효과가 없다 |
| 보상 실패 | 해당 없음. 별도 보상 처리를 두지 않고 이어받기에 맡긴다(위 "벗어난 것" 참고) |

## 아직 정하지 못한 것

- Primary 페일오버 구간에 조건부 UPDATE가 걸렸을 때의 재시도 여부
- graceful shutdown이 접수된 재개 스레드를 기다려 주는지
- 거절(실행기 가득 참)과 이어받기 발생 횟수를 지표로 내보낼지
