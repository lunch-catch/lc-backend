# ops 장애 처리 설계

이 도메인이 기대는 대상과 기본 처리를 벗어난 것을 적는다. 어디까지 훑었는지도 적는다.

이 문서는 #362(배치 작업 수동 재실행)를 계기로 처음 쓴다. 플랫폼 설정값(`PlatformSetting`)이
기대는 대상은 이 PR이 건드리지 않아 아직 훑지 않았다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| DB(MySQL) | `batch_execution_log`, `audit_log`의 모든 읽기·쓰기 | 기본(오류로 올린다 / 트랜잭션을 되돌린다) |
| 애플리케이션 내부 실행기(`BatchExecutionRetryService`, `AggregationRecalculationService`와 같은 1스레드 전용 풀) | 수동 재실행의 실제 재개 접수 | 벗어났다. 아래 |
| 롤백 안 되는 효과(별도 스레드의 재개) | 수동 재실행 접수 뒤 실제 작업 실행 | 벗어났다. 아래 |

## 벗어난 것

### 애플리케이션: 전용 실행기(대기열 4, 1스레드)

관리자가 거의 동시에 여러 건을 재실행하면 대기열(4)이 가득 찰 수 있다. 가득 차면
`RejectedExecutionException`을 던지고, 이미 조건부 UPDATE로 RUNNING까지 바꾼 행을 다시
`FAILED`로 닫는다. 통과시키지 않고 거절하는 이유는 접수하지 못한 재개를 "실행 중"으로
남기면 아무도 닫지 않기 때문이다. 거절한 횟수는 지표로 아직 내보내지 않는다(분석의 A-05도
같다. 둘 다 관리자 수동 동작이라 빈도가 낮아 아직 미룬 상태다).

### 롤백 안 되는 효과: 수동 재실행 접수

**순서가 핵심이다.** 조건부 UPDATE(FAILED -> RUNNING)를 먼저 커밋하고, 그 뒤에 감사 로그를
남기고, 그 뒤에 실제 재개를 별도 스레드에 접수한다. 감사 로그 기록이나 접수 자체가 실패하면
그 자리에서 행을 다시 `FAILED`로 되돌린다(커밋 뒤 실패를 다시 집어 올리는 재시도 대신, 관리자가
같은 요청을 다시 보내게 한다. 관리자 수동 동작이라 사람이 바로 다시 누를 수 있어 별도의
재시도 장치를 두지 않는다).

접수에 성공한 뒤 재개가 도는 도중에 프로세스가 죽으면(별도 스레드라 요청은 이미 끝났다) 되돌릴
방법이 없다. 이 경우는 배치 운영 공통 규칙의 이어받기(`DailyJobScheduler.takeOverStale` ->
`BatchJobRunner.resume`)가
2분 뒤 다른 서버에서 같은 재개 경로로 다시 돈다. 그래서 별도의 보상 처리를 두지 않는다.

## 유형별 점검

### 캐시

해당 없음. 이 도메인은 캐시를 쓰지 않는다(플랫폼 설정값이 Caffeine을 쓰는지는 아직 훑지 않았다).

### DB

| 시나리오 | 점검 결과 |
|---|---|
| 다운, 연결 거부 | 해당 없음. 기본 처리(오류로 올린다)를 따른다 |
| 슬로우 쿼리, 응답 지연 | 해당 없음. 기본 처리를 따른다. 조건부 UPDATE 한 문장뿐이라 느려질 지점이 적다 |
| 커넥션 풀 고갈 | 해당 없음. 기본 처리를 따른다 |
| 데드락 | 해당 없음. 기본 처리를 따른다. 수동 재실행은 행 하나만 건드려 데드락 가능성이 낮다 |
| 락 대기 초과 | 해당 없음. 기본 처리를 따른다 |
| 제약 위반, 데이터 불일치 | 해당 없음. 기본 처리(재시도하지 않고 올린다)를 따른다 |
| Primary 페일오버 | 아직 정하지 못한 것. 조건부 UPDATE가 페일오버 구간에 걸리면 재실행이 걸렸는지 불명확한 상태로 응답이 실패할 수 있다 |
| 복제 지연 | 해당 없음. 쓰기와 읽기를 모두 Primary로 보낸다(다른 도메인과 같다) |

### 외부 API

해당 없음. 이 도메인은 외부 API를 부르지 않는다.

### 애플리케이션

| 시나리오 | 점검 결과 |
|---|---|
| 요청이 몰린다 | 벗어났다. 위 "벗어난 것: 전용 실행기" |
| 대용량 조회 | 해당 없음. 이 도메인의 조회는 한 행 또는 한 영업일 범위뿐이다 |
| 배포로 서버가 내려간다 | 아직 정하지 못한 것. graceful shutdown이 접수된 재개를 끝까지 기다려 주는지 확인하지 않았다 |
| 서버가 여러 대다 | 해당 없음. 기본 처리(배치 운영 공통 규칙)를 따른다. 상세는 런치캐치_배치_운영.md 2장 |

### 롤백 안 되는 효과

| 시나리오 | 점검 결과 |
|---|---|
| 커밋 뒤 실패 | 벗어났다. 위 "벗어난 것: 수동 재실행 접수" |
| 커밋 전 성공 | 해당 없음. 조건부 UPDATE 커밋 전에는 외부에 보이는 효과가 없다 |
| 보상 실패 | 해당 없음. 별도 보상 처리를 두지 않고 이어받기에 맡긴다(위 "벗어난 것" 참고) |

## 아직 정하지 못한 것

- Primary 페일오버 구간에 조건부 UPDATE가 걸렸을 때의 재시도 여부
- graceful shutdown이 접수된 재개 스레드를 기다려 주는지
- 거절(실행기 가득 참)과 이어받기 발생 횟수를 지표로 내보낼지
