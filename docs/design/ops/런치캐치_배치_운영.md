# 런치캐치 배치 운영

| 항목 | 내용 |
|---|---|
| 목적 | 배치 서버를 띄우고 운영하는 규칙을 한곳에 둔다 |
| 근거 | 하루 시간표대로 도는 작업과 그 실행 이력 테이블(`batch_execution_log`) |
| 관련 문서 | `런치캐치_도메인_구조와_의존성_설계.md` 2.1 규칙 6(스케줄러 책임), 2.4(배치를 별도 jar로 떼지 않는 이유) |

## 1. 서버 구성

배치 서버는 별도 코드가 아니라 같은 jar를 `batch` 프로필로 띄운 서버다. API 서버 N대는 기본 프로필로, 배치 서버 2대는 `spring.profiles.active=batch`로 배포한다. `application-batch.yml`에만 `launchcatch.scheduler.enabled: true`를 두고, 스케줄러 설정 클래스(`global.config.SchedulingConfig`)는 `@ConditionalOnProperty`로 이 값이 true일 때만 뜬다. `@EnableScheduling`은 메인 클래스가 아니라 이 설정 클래스에만 둔다. 각 도메인의 `job/` 클래스는 어느 서버에나 들어 있지만, 스케줄러가 없는 서버에서는 실행되지 않는다. 장애 대응 중 자동 실행을 멈출 때는 프로필은 그대로 두고 환경변수 `LAUNCHCATCH_SCHEDULER_ENABLED=false`로 끈다.

```java
@Configuration
@ConditionalOnProperty(name = "launchcatch.scheduler.enabled", havingValue = "true")
@EnableScheduling
public class SchedulingConfig {
}
```

스케줄러 자체는 여기서 `@Bean`으로 만들지 않는다. `ops/job/DailyJobScheduler`의 `@Component`다. 어느 서버에나 들어 있고, `@EnableScheduling`이 없는 서버에서는 `@Scheduled`가 붙은 메서드가 돌지 않는다.

그 클래스는 저장소를 직접 받지 않고 `BatchExecutionService`를 받는다. `job/`은 Entry 계층이고 Repository는 Service만 쓸 수 있어서, 저장소를 주입받으면 `계층_의존_규칙`이 떨어진다.

### 스프링 배치를 쓰지 않는 이유

배치는 스프링 배치가 아니라 `@Scheduled` 위에 직접 만든 틀이다. `job`, `step` 같은 말이 겹치지만 `JobRepository`도 메타 테이블도 쓰지 않는다.

**필요한 것이 조정이지 처리량이 아니어서다.** 여기서 푸는 문제는 "서버 두 대가 같은 작업을 겹쳐 돌지 않게 하고, 돌던 서버가 죽으면 다른 서버가 집어가게 하는 것"이다. 점유(`batch_execution_log`의 유일 키), 생존 신호와 이어받기(`owner_id`, `updated_at`), 실행 세대(`attempt_no`)가 그 답이고, 스프링 배치는 이 중 어느 것도 주지 않는다. 그쪽의 `JobRepository`는 같은 파라미터의 잡을 두 번 완료하지 못하게 할 뿐, 액티브-액티브 두 대의 점유나 임대 만료 이어받기는 범위 밖이다. 갈아타도 이 부분은 그대로 직접 만들어야 한다.

**반대로 스프링 배치의 강점은 지금 쓰이지 않는다.** 청크 커밋과 재시작 지점은 한 작업이 한 트랜잭션으로 안 끝날 만큼 클 때 값을 하는데, 지금 작업은 하루치를 한 번에 처리하고 배치 코드에 수동 페이징도 없다. 실패한 단계부터 다시 도는 것은 00:00 묶음이 이미 한다. 실행 이력과 수동 재실행도 `batch_execution_log`와 운영 API가 맡는다. 들여오면 메타 테이블 아홉 개의 소유를 정해야 하는데, 이 저장소는 마이그레이션을 도메인 폴더로 나누고 네이티브 쿼리가 남의 테이블을 읽지 못하게 막는다. 얻는 것보다 들어오는 개념이 많다.

**다시 볼 시점은 셋이다.** 한 작업이 한 트랜잭션으로 끝나지 않을 만큼 커질 때, 1만 건 중 몇 건만 건너뛰고 나머지를 처리해야 할 때, 단계가 늘어 단계 사이 입출력을 이어야 할 때다. 그때도 전부 갈아탈 필요는 없다. 무거워진 작업 하나만 스프링 배치로 돌리고 점유와 이어받기는 지금 틀이 감싸면 된다. `DailyJob.run` 안에서 `JobLauncher`를 부르는 모양이다.

## 2. 두 서버를 함께 쓰는 규칙

두 배치 서버는 모두 스케줄러를 켜고 같은 시각에 작업을 시도한다(액티브-액티브). 한쪽만 켜 두면 00:00에 장애가 났을 때 사람이 전환해야 하기 때문이다.

| 항목 | 규칙 |
|---|---|
| 중복 실행 | 작업 시작 시 `batch_execution_log`에 RUNNING 행을 먼저 넣는다. UNIQUE (job_name, business_date)에 걸리면 실행하지 않는다 |
| 00:00 묶음 | (1)~(10)은 `DAILY_0000` 행 하나로 점유한다. 점유한 서버가 단계를 차례로 실행하고, 단계마다 자기 job_name으로 행을 남긴다. 점유에 실패한 서버는 묶음 전체를 건너뛴다. 단계마다 따로 점유하면 앞 단계가 끝나기 전에 다른 서버가 뒤 단계를 실행할 수 있다 |
| 생존 신호 | 실행 중인 서버는 별도 스레드에서 30초마다 자기 행의 `updated_at`을 갱신한다. 갱신은 `owner_id`가 자기일 때만 하며, 0건이면 이미 넘겨받은 것이므로 다음 단계로 가지 않고 멈춘다 |
| 이어받기 | 다른 서버는 1분마다 RUNNING이면서 `updated_at`이 2분보다 오래된 행을 찾아 조건부 UPDATE로 `owner_id`를 바꾼다. 1건이 바뀐 서버만 이어받는다. 00:00 묶음은 SUCCESS가 아닌 첫 단계부터 다시 실행한다. 묶음도 등록된 단계도 아닌 작업은, 등록된 묶음 밖 작업(`StandaloneJob`)이면 이어받은 서버가 `run`을 다시 부르고(`#360`) 그 외에는 FAILED로 닫는다. 모든 작업이 멱등이라 겹쳐 실행된 단계가 있어도 결과는 같다. 이어받은 사실은 관리자에게 알린다 |
| 실행 세대 | `attempt_no`는 1부터 시작해 claim, 이어받기, 수동 재실행(retry, rerun)마다 하나씩 오른다(`#360`). 자동 재실행(`recordRetry`)은 올리지 않는다. 같은 서버가 같은 시도를 이어가는 것이라 소유자나 결과 공개의 전제가 바뀌지 않기 때문이다. 임대를 잃은 서버가 늦게 깨어나 결과를 공개하려 할 때, 그 트랜잭션 안에서 소유자와 세대가 지금도 자기 것인지 확인하는 데 쓴다(`BatchAttemptGuard.assertCurrentAttempt`) |
| 자동 재실행 | 일시적 오류로 분류한 예외만 다시 실행한다. MySQL 교착(1213), 락 대기 시간 초과(1205), 연결 오류, Valkey 응답 시간 초과가 여기 속한다. 30초, 1분 간격으로 최대 2회다. 다시 실행할 때마다 같은 행의 `retry_count`를 1 올리고 `retry_reason`에 사유를 남긴다. 00:00 묶음은 실패한 단계만 다시 실행한다. 그 외 예외는 다시 실행하지 않고 바로 FAILED로 둔다 |
| 실패 | 자동 재실행을 다 써도 실패하거나 일시적 오류가 아니면 FAILED로 확정하고 관리자에게 알린다. 관리자가 화면에서 누르거나 분석이 같은 (작업명, 영업일)로 재실행한다(`#359`, 분석은 전날 FAILED로 끝난 영업일을 사람 없이 다음 밤 자동으로 재실행해도 된다). 재실행은 새 행을 넣지 않고 기존 FAILED 행을 RUNNING으로 되돌린다. 이때 `finished_at`, `failure_reason`, `retry_reason`, `processed_count`를 비우고, `retry_count`를 0으로, `owner_id`를 실행하는 서버로, 시작 시각(`created_at`)을 이 시도의 시각으로 바꾼다. 이 UPDATE도 status가 FAILED일 때만 걸리게 해 두 번 눌러도 한 번만 실행된다. 분석의 자동 재실행이 성공하면, 전날 간 관리자 알림은 이미 지난 일이 된다 |
| 하루 한 번이 아닌 작업 | 캠페인별 사용 종료 시각마다 도는 쿠폰 만료는 job_name에 캠페인 id를 붙여 같은 키로 막는다 |
| 설정값 | 영업일 경계 작업은 Caffeine 캐시를 거치지 않고 실행 시점의 값을 DB에서 읽는다. 서버마다 최대 5분까지 다른 값을 볼 수 있기 때문이다 |
| 시각 | 두 서버는 NTP로 시계를 맞추고, 영업일은 Asia/Seoul 기준으로 판단한다 |
| 장애 | 배치 서버가 모두 멈춰도 피드, 노출 차감, 쿠폰 발급은 API 서버에서 계속 처리된다 |

```java
@Modifying
@Query("""
    UPDATE BatchExecutionLog l
       SET l.ownerId = :me, l.updatedAt = :now
     WHERE l.jobName = :jobName AND l.businessDate = :date
       AND l.status = 'RUNNING' AND l.updatedAt < :staleBefore
    """)
int takeOver(String jobName, LocalDate date, String me,
             LocalDateTime now, LocalDateTime staleBefore);
```

## 3. 구현

2장의 규칙은 `ops` 가 갖는다. 작업 내용은 각 도메인이 `ops.scheduler.DailyJob` 을 구현해 등록한다(설계 문서 규칙 6).

| 규칙 | 어디 |
|---|---|
| 중복 실행 차단 | `BatchExecutionService.claim`. `batch_execution_log` 의 유일 제약 위반을 "이미 점유됐다" 로 읽는다 |
| 00:00 묶음 점유와 단계 진행 | `DailyJobScheduler.runDailyBundle`(점유 확인) -> `BatchJobRunner.runBundle`, `runStep`(실제 진행, `#362`로 Service 계층에 옮겼다. 계층 규칙은 설계 문서 1.5절) |
| 생존 신호 | `DailyJobScheduler.sendHeartbeat` -> `BatchExecutionService.renewOwned`. 단계마다 `renew` 로 점유를 다시 확인하고 0건이면 멈춘다 |
| 이어받기 | `DailyJobScheduler.takeOverStale` -> `BatchExecutionService.takeOverStale`로 찾고, `BatchJobRegistry.classify`로 가른 뒤 `BatchJobRunner.resume`으로 다시 돈다(`#362`, `#585`). 조건부 UPDATE 로 한 번 더 판정해 1건을 받은 서버만 이어받는다 |
| 작업 이름 분류 | `ops.scheduler.BatchJobRegistry.classify`가 이름을 묶음, 단계, 묶음 밖 작업, 알 수 없음으로 가른다(`#585`). 이어받기, 관리자 수동 재실행, 이력의 `retryable`이 모두 이 판정을 쓴다. 단계 이름과 묶음 밖 작업 이름이 겹치거나 묶음 밖 작업끼리 겹치면 기동이 실패한다. 겹친 채 뜨면 단계로 먼저 분류되어 그 묶음 밖 작업이 조용히 다시 돌지 않기 때문이다. 등록되지 않은 이름으로 `resume`을 부르면 `IllegalArgumentException`이 난다 |
| 묶음 밖 작업 등록 | 자기 스케줄러에서 `claim`으로 `batch_execution_log`를 점유하는 작업은 모두 `ops.scheduler.StandaloneJob`을 구현해 등록한다(`#360`, `#585`에서 정했다). 그래야 멈춘 실행을 이어받거나 관리자가 다시 돌릴 수 있다. `claim`과 점유는 그 작업의 스케줄러가 직접 하고, 이 인터페이스는 이어받았을 때 다시 돌릴 길만 등록한다. 본보기는 분석의 `EventLogRetentionJob`이다. 이어받은 뒤의 재시도는 번들 단계와 같은 규칙(`BatchJobRunner.attempt`/`retryOrFail`)을 그대로 쓴다 |
| 실행 세대 확인 | `ops.contract.BatchAttemptGuard.assertCurrentAttempt(jobName, businessDate, attemptNo)`(`#360`)가 `BatchExecutionService.assertCurrentAttempt`에 위임한다. 호출자 트랜잭션에 참여해 행을 잠그고 소유자와 세대를 확인한다. 맞지 않으면 예외를 던져 그 트랜잭션을 롤백시킨다. `succeed`/`fail`의 소유자 조건만으로는 막지 못한다. 결과는 그 전에 이미 커밋된다. 이어받기와 수동 재실행으로 도는 묶음 밖 작업은 `BatchJobRunner`가 생존 확인, 재실행 기록, 닫기를 넘겨받은 세대로만 한다(`renewAttempt`, `recordRetryAttempt`, `succeedAttempt`, `failAttempt`, `#591`). 같은 서버가 새 세대를 잡으면 소유자 조건은 통과해서, 낡은 시도가 끝나며 새 시도의 행을 닫거나 재실행 횟수를 깎기 때문이다. 00:00 묶음 단계는 자기 세대를 몰라 지금처럼 소유자만 본다 |
| 자동 재실행 | `TransientFailures` 가 일시적 오류인지 가르고, `BatchExecutionService.recordRetry` 가 횟수를 올린다. 대기는 `RetryBackoff` 다. 묶음은 실패한 단계만 다시 돈다 |
| 실패 | `BatchExecutionService.fail`. 자동 재실행을 다 쓰면 FAILED 로 닫고 알린다 |
| 처리 건수 기록 | `BatchExecutionService.succeed(jobName, businessDate, processedCount)`(`#359`). 기존 `succeed(jobName, businessDate)`는 그대로 두고 `processed_count`를 `null`로 남긴다. 건수의 뜻은 호출하는 도메인이 정한다(분석은 원천 행을 못 봐서 집계 결과로 쓴 행 수를 넣는다, `#334`). 이어받기와 수동 재실행은 `StandaloneJob.runCounting`이 돌려준 건수로 닫는다(`#559`). 기본 구현은 `run`을 부르고 `null`을 돌려주어 건수 없이 닫으므로 건수가 필요한 작업만 재정의한다. `DailyJob`의 건수는 읽는 곳이 없어 `null`로 둔다 |
| 수동 재실행 | `BatchExecutionService.retry` 가 상태가 `FAILED` 일 때만 걸려 두 번 눌러도 한 번만 실행된다. `ops.contract.BatchRerunner.rerun(jobName, businessDate)`(`#339`)가 `FAILED`와 `SUCCESS` 둘 다 되돌리는 별도 경로로, `BatchExecutionService.rerun`에 위임해 분석이 부를 수 있다. 둘 다 되돌릴 때 시작 시각(`created_at`)과 `processed_count`를 새로 한다(`#359`). **다만 관리자가 쓸 HTTP API는 아직 없다.** 아래 "아직 비어 있는 것" 을 보라 |
| 관리자 알림 | `BatchAlert`. 알림 채널이 생기면 알림 도메인이 구현해 `@Primary` 로 올린다. 그때까지는 `LoggingBatchAlert` 가 로그로 남긴다 |

판정은 모두 조건부 UPDATE 로 두고 바뀐 행 수를 본다. 읽고 나서 판단하면 두 서버가 같은 상태를 읽고 둘 다 자기 것이라고 믿는 구간이 생긴다.

### 돌려 보고 알게 된 것

* **스케줄러 스레드 풀이 1이면 생존 신호가 돌지 않는다.** 묶음이 그 하나를 붙잡고 있어서, 멀쩡히 일하는 서버의 행이 2분 뒤 멈춘 것으로 보여 다른 서버가 빼앗는다. `application-batch.yml` 이 `spring.task.scheduling.pool.size` 를 4로 둔다
* **감사 시각의 시간대를 고정해야 한다.** 기본 제공자는 JVM 기본 시간대로 `created_at` 을 넣는데, 애플리케이션은 `Clock`(Asia/Seoul)으로 `finished_at` 을 넣는다. `chk_batch_finished` 가 두 시각을 견주므로 기준이 갈리면 안 된다. `JpaAuditingConfig` 가 `DateTimeProvider` 를 `Clock` 에 묶는다
* **상태와 종료 시각, 실패 사유는 한 문장에서 함께 바꿔야 한다.** `chk_batch_finished` 와 `chk_batch_failure_reason` 이 짝을 요구한다. 한쪽만 바꾸면 저장이 거부되고, 그 거부는 배치가 실패를 기록하려는 순간에 터져서 실패 기록 자체가 사라진다
* **자동 재실행 상한은 코드가 아니라 `WHERE` 에서 판정해야 한다.** 코드에서만 세면 두 서버가 겹쳐 돌 때 셋이 될 수 있고, 그때는 `chk_batch_retry` 위반으로 저장이 거부되어 재실행 기록 자체가 사라진다. `recordRetry` 가 0건을 돌려주는 것이 "더 돌리지 않는다" 다
* **수동 재실행은 `retry_count` 도 되돌려야 한다.** 남겨 두면 그 뒤의 자동 재실행이 시작부터 상한이라 한 번도 돌지 않고 바로 실패한다. `chk_batch_retry` 가 횟수와 사유를 짝으로 요구하므로 둘을 함께 비운다
* **묶음도 등록된 단계도 아닌 작업은 이어받아도 다시 돌릴 길이 없다.** 소유자만 바꿔 두면 내 생존 신호가 그 행을 영원히 살아 있게 만들어 아무도 멈춘 것을 모른다. 그래서 실패로 닫고 알린다

* **이어받은 뒤에는 "내 것인가" 를 먼저 봐야 한다.** 이어받기가 묶음 행과 단계 행을 함께 가져오고 `updated_at`을 지금으로 바꾼다. 그 뒤 묶음을 다시 도는 길에서 그 단계를 또 이어받으려 하면 "2분보다 오래된" 조건에 걸리지 않아 0건이고, 묶음이 "단계를 시작할 수 없다" 로 떨어진다. 이어받기가 존재하는 바로 그 상황에서 이어받기가 쓸모없어지는 것이라, 실제 시나리오를 통합 테스트로 재현해 두었다
* **행을 닫을 때도 소유자를 조건에 넣어야 한다.** 생존 신호가 끊겼다가 늦게 깨어난 서버는 자기가 아직 그 단계를 들고 있다고 믿는다. 소유자 조건이 없으면 그 서버가 `succeed`나 `fail`로 남이 실행 중인 행을 닫는다. 임대 시간이 지났다는 것은 상대가 멈췄다는 뜻이 아니라 그렇게 보였다는 뜻뿐이다
* **점유도 다른 판정과 같이 행으로 가른다.** 예외 모양으로 승패를 읽으면 그 모양이 바뀔 때마다 같은 문제가 반복된다(중복 키 예외인 줄 알았던 것이 평범한 `DataIntegrityViolationException`이었고, 길이 초과·CHECK 위반도 같은 예외였다). `claim`은 `INSERT ... ON DUPLICATE KEY UPDATE job_name = job_name`으로 중복을 흡수해 중복을 평범한 결과로 만들고(길이 초과·CHECK 위반은 그대로 예외다), 그 뒤 행을 다시 읽어 `owner_id`가 나인지로 점유를 가른다. 영향받은 행 수는 보지 않는다. 드라이버 기본값(`useAffectedRows=false`)에서 무변경 갱신도 1로 보고될 수 있다(`#526`)
* **두 서버가 같은 순간에 점유를 시도하면 락 대기 시간 초과나 교착으로 보일 수 있다.** InnoDB가 같은 경합을 항상 같은 예외로 내지 않기 때문이다. `claim`은 `TransientFailures.isTransient`로 이 경우를 가려 한 번 더 시도한다. 그 시점에는 상대의 트랜잭션이 끝나 있어 성공하거나 상대가 이미 점유한 것으로 깨끗하게 갈린다(`#515`)
* **두 서버가 같은 식별자를 쓰면 이어받기가 영원히 안 된다.** 살아 있는 서버의 생존 신호가 죽은 서버의 행까지 갱신하고, 이어받기는 "내 것이 아닌 행" 만 찾기 때문이다. `HOSTNAME`이 없는 환경에서 둘 다 같은 값을 받으면 그 상태가 된다. `BatchServerId`가 값을 주지 않았을 때 호스트 이름에 임의 접미사를 붙여 프로세스마다 다르게 만든다

* **소유자 조건은 닫을 때만이 아니라 재실행에도 필요하다.** 임대를 잃은 서버가 새 소유자의 재실행 예산을 깎고 사유를 덮어쓸 수 있었다. 닫는 쪽만 막아 두면 중간 상태는 그대로 남의 것을 건드린다. 그리고 기다린 뒤 다시 돌리기 전에 소유권을 한 번 더 본다. 보지 않으면 이어받은 서버와 같은 단계를 겹쳐 돈다
* **`created_at`이 `updatable = false`여도 JPQL 벌크 UPDATE로는 바뀐다(`#359`).** 그 속성은 Hibernate가 엔티티를 플러시할 때 그 컬럼을 UPDATE 문에 넣지 않게 막는 것이고, `@Modifying @Query`의 `UPDATE ... SET l.createdAt = ...`은 그 경로를 타지 않아 걸리지 않는다. 실제로 돌려 보고 확인했다
* **벌크 UPDATE로 올린 세대는 같은 요청 안에서 다시 읽어야 보인다(`#360`).** `takeOver`가 `@Modifying(clearAutomatically = true)`라 영속성 컨텍스트를 비우지만, 이어받기 전에 읽어 둔 엔티티 변수(`stale`)는 그 UPDATE 이전 값을 그대로 들고 있다. 그 값으로 `StandaloneJob.run`에 세대를 넘기면 항상 하나 모자란 세대가 전달된다. `BatchExecutionService.takeOverStale`이 UPDATE 성공 뒤 같은 행을 다시 조회해 돌려주는 이유다
* **묶음 밖 작업의 재시도는 번들 전용 처리만 떼어내면 그대로 재사용된다(`#360`).** `BatchJobRunner.attempt`/`retryOrFail`은 일시적 오류 판정, 재실행 기록, 대기, 임대 재확인까지 작업 종류를 가리지 않는다. 다른 것은 실패를 확정할 때 번들(`DAILY_0000`)까지 실패시키는 한 줄뿐이라, 그 한 줄만 호출자가 주는 콜백(`onFailure`)으로 바꾸면 묶음 단계와 묶음 밖 작업이 같은 경로를 탄다
* **묶음을 실제로 돌리는 로직은 Entry 계층(`job/`)이 아니라 Service 계층에 둬야 한다(`#362`).** 관리자 수동 재실행처럼 Service 계층의 다른 클래스가 그 실행을 다시 걸어야 하면, Entry 는 누구에게도 불리지 않는다는 계층 규칙(설계 문서 1.5절)에 막힌다. 그래서 점유 확인과 스케줄 트리거만 `DailyJobScheduler`(Entry)에 남기고, 실제로 도는 로직은 `BatchJobRunner`(Service)로 옮겼다

### 아직 비어 있는 것

2장의 나머지 넷은 구현이 없다.

| 규칙 | 왜 비어 있나 |
|---|---|
| 00:00 묶음의 단계 (1)~(10) | 각 도메인이 `DailyJob`을 구현해 등록할 자리다. 지금은 등록된 것이 없어 묶음이 바로 성공으로 닫힌다 |
| 관리자 수동 재실행 | 분석은 `ops.contract.BatchRerunner`로 재실행을 걸 수 있다(`#339`). 관리자가 화면에서 누르는 HTTP 경로만 아직 없다. 다른 관리자 기능과 함께 설계한다 |
| 설정값을 캐시 없이 읽기 | 플랫폼 설정값 조회 자체가 아직 없다. 그 코드가 생길 때 영업일 경계 작업만 캐시를 거치지 않게 둔다 |
| 시계 맞추기 | 배포 설정이라 코드가 아니다. 영업일 판정은 `ClockConfig`가 Asia/Seoul로 고정했다 |
| `StandaloneJob` 등록 | 위 "묶음 밖 작업 등록" 행대로 모두 구현하기로 했지만(`#585`) `KakaoUnlinkRetryScheduler`, `TemplateVersionPurgeScheduler`, `PgChargeReconciliationScheduler`는 아직 구현하지 않아 지금은 멈춰도 FAILED로만 닫힌다. 그 셋과 앞으로 생기는 같은 모양의 작업은 `#619`가 맡는다. 분석의 이벤트 로그 보존 삭제(`EventLogRetentionJob`)와 01:00 집계(`DailyAggregationJob`, `DAILY_AGGREGATION`, `#587`)는 이 인터페이스를 구현해 등록했다 |
| `BatchAttemptGuard` 실제 호출 | 분석의 일별 집계(`DailyAggregationRunner`, `#587`)가 하루 결과 공개 트랜잭션과 실패·재실행 기록 앞에서 부른다. `StandaloneJob.run` 뒤에 `BatchJobRunner`가 부르는 닫기는 아직 소유자만 보고 세대를 보지 않는다(`#591`) |
| 처리 건수 반환 | `StandaloneJob.run`은 건수를 돌려주지 못한다. 그래서 이어받기와 수동 재실행은 `BatchJobRunner`가 건수 없는 `succeed`로 닫아 `processed_count`를 `null`로 남긴다. 분석의 `EventLogRetentionJob`은 임시로 `run` 안에서 건수와 함께 먼저 닫는다. `#559`가 `StandaloneJob`에 `default Integer runCounting(...)`을 더해 해결한다. 기본 구현은 `run`을 부르고 `null`을 돌려주므로 건수가 필요한 작업만 재정의한다. `DailyJob`의 건수는 읽는 곳이 없어 위 "처리 건수 기록" 행대로 `null`로 둔다 |
