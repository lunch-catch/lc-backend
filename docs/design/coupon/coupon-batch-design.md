# 쿠폰 배치 설계

쿠폰 회차와 재고 생성, 발급 오픈, 발급 종료, 만료 처리, 정합성 검증을 다룬다.
HTTP의 발급 판정과 시간 경계는 [쿠폰 명세](../../api-spec/coupon-api-spec.md#쿠폰-발급)를 따른다.
점유, 생존 신호와 실행 세대는 [운영 배치 설계](../ops/런치캐치_배치_운영.md)를 따른다.

## 실행 시간

다섯 작업은 모두 `StandaloneJob`이다. `DailyJob`에는 쿠폰 단계를 추가하지 않는다.
선행 작업의 성공 여부를 조회하지 않으며 지정한 시각에 독립적으로 실행한다.
영업일과 실행 시각은 Asia/Seoul 기준이다.

| 작업명 | 실행 시각 | 처리 대상 |
|---|---|---|
| `COUPON_VERIFY` | 매일 02:00에 실행한다 | 전날 영업일의 정합성을 검사한다 |
| `COUPON_PREPARE` | 매일 03:00에 실행한다 | 오늘의 회차와 재고를 만든다 |
| `COUPON_OPEN` | 매일 11:00에 실행한다 | 오늘 ACTIVE 회차의 오픈 이벤트를 발행한다 |
| `COUPON_CLOSE` | 매일 14:00에 실행한다 | 오늘의 발급 종료 시간 도달을 실행 이력에 기록한다 |
| `COUPON_EXPIRE` | 매시 0·5·10분처럼 5분마다 실행한다 | 사용 시간이 끝난 ISSUED 회원 쿠폰을 만료한다 |

각 Job은 기존 `BatchExecutionService`로 자기 작업을 점유한다.
쿠폰의 `CouponBatchExecutionService`는 공개 조회로 실행 세대를 읽고 업무 함수를 실행한다.
성공과 실패, 재시도 횟수와 실행권 갱신은 기존 `BatchExecutionService`의 메서드로 기록한다.
공통 `ops` 코드와 설정은 변경하지 않는다.

쿠폰 실행 서비스는 모든 업무 실행 오류를 추가 최대 2회 재시도한다.
이어받기와 수동 재실행은 기존 `BatchJobRunner`가 등록된 `StandaloneJob.runCounting`을 호출한다.
이 경로도 쿠폰 실행 서비스의 같은 재시도 메서드를 거친다.
두 실행기는 기존 DB 행의 재시도 상한을 공유하므로 복구에서도 추가 재시도가 늘어나지 않는다.
최초 실행까지 총 3회이며 첫 재시도는 30초, 다음 재시도는 1분을 기다린다.
재시도 횟수는 기존 실행 행의 `retry_count`로 제한한다.
실행권을 잃거나 대기가 중단되면 더 실행하지 않는다.
두 번의 재시도 뒤에도 실패하면 FAILED로 남긴다.
만료 작업의 다음 주기 재실행은 [회원 쿠폰 만료](#회원-쿠폰-만료)를 따르고 나머지 작업은 운영의 수동 재실행으로 복구한다.
다른 도메인의 기본 정책은 기존대로 일시적 오류만 재시도한다.
실행 중인 작업의 복구는 운영의 이어받기를 사용한다.
시간 간격은 선행 데이터의 준비를 보장하지 않는다. 원천 데이터가 잘못됐으면 해당 작업이 실패하며 후속 작업을 자동으로 막지는 않는다.

새 테이블이나 컬럼은 추가하지 않는다.
처리 건수와 실패 사유는 기존 `batch_execution_log`를 사용한다.
정합성 검증의 처리 건수는 발견한 불일치 수다.
생성·만료의 처리 건수는 마지막으로 성공한 시도가 새로 처리한 건수이며 이전 시도의 부분 커밋은 합산하지 않는다.

## 회차와 재고 생성

`CampaignQueryService.findServableOn`의 캠페인을 대상으로 한다.
캠페인마다 별도 트랜잭션에서 실행 세대를 확인하고 `findByIdForUpdate`로 캠페인을 잠근다.
집행 기간과 ACTIVE·PAUSED 상태를 다시 확인한 뒤 기존 회차가 없으면 생성한다.
기존 회차는 다시 생성하거나 값을 덮어쓰지 않는다.

매장과 메뉴 정보는 `StoreQueryService`의 공개 조회로 받는다.
매장과 메뉴의 존재 및 메뉴가 해당 매장 소속인지를 검사한다.
할인 후 가격은 명세에 따라 할인액을 10원 단위로 반올림해 계산한다.
회차와 예정 수량만큼의 재고는 같은 트랜잭션에서 저장한다.
조회 페이지와 재고 INSERT 크기는 `CouponBatchTask.BATCH_SIZE`의 1,000건으로 통일한다.
배치 크기는 메모리에 읽거나 JDBC에 전달하는 단위이며 한 회차의 커밋은 나누지 않는다.

기존 `coupon_event`의 매장·메뉴·할인 정보는 발급 당시 값을 보존하는 API 계약이다.
`CouponEvent.Snapshot`은 기존 컬럼을 채우는 자바 인자 묶음이며 별도의 저장 구조가 아니다.

## 발급 오픈과 종료

회차의 `status`와 `status_changed_at`은 캠페인의 운영 상태를 나타낸다.
발급 시간 때문에 PAUSED를 ACTIVE로 바꾸거나 ACTIVE를 ENDED로 바꾸지 않는다.
오픈 작업은 ACTIVE 회차마다 `CouponIssueOpenedEvent`를 발행한다.
이벤트 ID는 `coupon-issue-opened:{회차ID}`이고 발생 시각은 당일 발급 시작 시각이다.
수동 재실행에서 같은 ID가 다시 발행될 수 있으며 분석 수신자가 이벤트 ID로 중복을 제거한다.

종료 작업은 발급 종료 시각을 확인하고 회차 수를 실행 이력에 남긴다.
HTTP 발급 API가 기존대로 시스템 시각을 검사하므로 14시부터 신규 요청을 거절한다.
종료 작업 자체가 별도 상태를 변경하지는 않는다.
종료 전에 검사를 통과한 요청이 종료 뒤 커밋되는 계약도 유지한다.

## 회원 쿠폰 만료

`CouponExpirationJob.expireCoupons`를 `@Scheduled(cron = "0 */5 * * * *", zone = "Asia/Seoul")`로 실행한다.
실행 시점에 `member_coupon.status = ISSUED`이고 `usable_end_at <= 현재 시각`인 회원 쿠폰을 찾는다.
회차와 재고만 있는 날짜는 만료 대상으로 삼지 않는다.
대상이 있는 영업일별로 실행을 점유하며 회원 쿠폰 ID는 1,000개씩 읽는다.
쿠폰마다 별도 트랜잭션으로 잠가 상태와 종료 시각을 다시 확인하고 만료한다.
USED와 REMOVED 상태는 변경하지 않는다.

과거 영업일도 조회하므로 서버 중단과 늦은 발급 커밋으로 남은 쿠폰은 다음 주기에 처리한다.
만료 대상이 남은 영업일은 기존 SUCCESS나 FAILED 실행을 다음 5분 주기에 다시 점유한다.
재점유는 재시도 횟수를 초기화하고 실행 세대를 올린다.
새 실행도 추가 최대 두 번 재시도하며 소진되면 FAILED로 기록한다.
만료 대상이 남아 있는 동안 다음 정기 실행에서 같은 절차를 반복한다.
RUNNING은 공통 이어받기에 맡기며 중복으로 시작하지 않는다.
동적으로 등록하는 예약과 메모리의 예약 목록은 두지 않으며 적재 후 예약 이벤트도 사용하지 않는다.
만료 상태가 다음 실행까지 늦게 반영되더라도 사용 API는 종료 시각을 직접 검사해 사용을 거절한다.

배치와 조회는 ISSUED에서 EXPIRED로 변경하는 트랜잭션에서 `CouponExpiredEvent`를 발행한다.
쿠폰 행 잠금으로 조회와 배치가 같은 쿠폰을 함께 만료하지 못하게 한다.
이벤트 ID는 `coupon-expired:{회원쿠폰ID}`이고 발생 시각은 쿠폰의 사용 종료 시각이다.
이미 EXPIRED인 과거 쿠폰의 이벤트를 소급 발행하지 않는다.
커밋 후 수신과 유실 허용 정책은 기존 퍼널 계약을 따른다.

## 정합성 검증

새벽 02시에 전날 영업일을 검사한다.
REPEATABLE_READ 트랜잭션에서 같은 시점의 쿠폰 테이블을 비교한다.
불일치 결과는 유형과 대상 ID를 커서로 삼아 1,000건씩 읽는다.
선행 배치의 완료 여부나 미처리 만료 대상의 존재로 검증을 보류하지 않는다.

| 검증 유형 | 비교하는 값 |
|---|---|
| 재고 수량·순번 | 회차의 예정 수량과 재고 수, 첫 순번과 마지막 순번을 비교한다 |
| 재고·회원 쿠폰 | 발급된 재고와 회원 쿠폰의 코드·회차 연결을 양방향으로 확인한다 |
| 일일 카운터 | 한국 발급일별 REMOVED 제외 수와 카운터를 비교하며 누락도 검사한다 |
| 사용 이력 | USED는 정확히 한 건, 다른 상태는 0건인지 확인하고 매장을 대조한다 |
| 사용 시간 | 회차·재고·회원 쿠폰의 사용 시간이 같은지 비교한다 |
| 만료 상태 | 사용 시간이 끝난 ISSUED와 사용 시간이 남은 EXPIRED를 검사한다 |
| 회차 중복 | 같은 매장·영업일에 회차가 여러 개 있는지 검사한다 |

불일치마다 유형, 대상 ID, 기대값과 실제값을 오류 로그에 남긴다.
검사를 끝냈으면 실행은 SUCCESS이며 발견한 불일치 수를 `processed_count`에 기록한다.
결과를 저장하는 별도 테이블이나 원본을 자동으로 고치는 기능은 두지 않는다.
검증 결과는 조회 시점의 정합성을 나타내며 이후의 커밋까지 보장하지 않는다.

## 검증 범위

모든 배치 쓰기는 `BatchAttemptGuard`로 실행 세대를 확인한다.
회차별·쿠폰별로 커밋하므로 중간 실패 뒤에도 완료한 행은 보존된다.
`CouponIntegrationTest.Batch`는 실제 MySQL에서 멱등 생성, 할인 반올림, 오픈·종료,
조회 만료 뒤 삭제, 증분 만료, 정합성 탐지와 실행 세대 상실을 확인한다.
최초 실행의 재시도 성공·소진과 1,001건의 재고·만료·불일치 처리도 검증한다.
재고만 있는 날짜의 실행 생략, 미사용 쿠폰의 종료 경계와 전날 미처리 쿠폰의 만료도 확인한다.
목록·상세 조회와 만료 배치가 서로 먼저 행을 잠그는 경우에도 커밋을 기다린 뒤 만료 이벤트를 한 번만 발행하는지 검사한다.
공개 조회의 제공자는 대역이므로 실제 도메인 간 연동을 확인한 것은 아니다.
