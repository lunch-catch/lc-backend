# coupon 장애 처리 설계

현재 발급·조회·삭제·QR 생성·사용 경로가 기대는 대상과 [장애 처리 가이드](../장애_처리_설계_가이드.md)의 기본 처리를 벗어나는지를 기록한다.
QR 사용 확정도 같은 기본 처리를 따르며 상태·사용 이력의 동시 롤백을 HTTP 통합 테스트로 확인한다.
업무상 거절의 상태·오류와 엔드포인트별 흐름은 [API 설계](./coupon-api-design.md)가 갖는다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| Redis 순번·예약 | 발급할 순번을 배정하고 완료와 롤백 반납을 기록한다 | 오류가 나면 해당 이벤트 발급을 차단하고 DB 기준으로 재구축한다. 아래 절을 따른다 |
| MySQL 읽기 | 이벤트·재고·카운터·회원 쿠폰·사용 이력과 분석용 집계를 읽는다 | 기본(오류로 올린다) |
| MySQL 쓰기 | 발급과 삭제·QR 교체·사용 확정·조회 시 만료 저장에 쓴다 | 기본(트랜잭션을 되돌린다) |
| member의 MemberQueryService | 발급·QR 생성·사용 자격과 이벤트 상태를 판정한다 | 기본(조회 장애를 전파한다). 정상적인 회원 부재와 구분한다 |
| owner의 OwnerStatusQuery | 사용 이력 조회·사용 확정에서 현재 ACTIVE 상태를 확인한다 | 기본(조회 장애를 전파한다). findCurrentStatus로 상태 캐시를 우회한다 |
| campaign의 CampaignQueryService | 이벤트 상태 조회에서 매장별 캠페인을 확인한다 | 기본(조회 장애를 전파한다) |
| campaign의 CampaignStatusChangedEvent, CampaignEndedEvent | 쿠폰 회차의 발급 상태를 바꾼다 | 기본(발행자와 같은 트랜잭션). 회차 갱신이 실패하면 예외를 전파하며 캠페인 변경도 되돌린다 |
| store의 StoreQueryService | 이벤트 조회의 매장 존재와 이력·QR 사용의 현재 관리 권한, QR 사용 좌표를 확인한다 | 기본(조회 장애와 내부 데이터 누락을 오류로 올린다) |
| adserving의 WishlistQueryService | 발급 자격과 이벤트 조회의 찜 여부를 확인한다 | 기본(조회 장애를 전파하고 발급은 롤백한다) |
| adserving의 CandidateStateUpdater | 발급 커밋 후 소진을 알린다 | 발급은 유지하고 소진 반영만 실패한다. 아래 절을 따른다 |
| 프로세스 내부 QR 인코더 | 토큰의 PNG 이미지를 만든다 | 기본(예외를 전파하고 QR 변경 트랜잭션을 되돌린다) |
| 프로세스 내부 이벤트 발행기 | 발급·사용 트랜잭션에서 퍼널 이벤트를 공개한다 | 분석 수신자가 커밋 후 비동기로 처리한다. 유실은 허용하며 아래 절을 따른다 |

## 벗어난 것

### 롤백 안 되는 효과: 분석 퍼널 기록

퍼널 유실을 허용하는 아키텍처와 #355의 결정에 따라 outbox는 두지 않는다.
발행과 수신의 수단은 [구조와 동작 설계 7장](./coupon_구조와_동작_설계.md#7-트랜잭션과-동시성)이 갖는다.
분석은 커밋 후 처리하므로 분석 저장 실패로 쿠폰 업무를 되돌리지 않는다.
비동기 실행기 거부와 저장 실패, 유실 관측은 분석 수신자가 소유한다. coupon에는 별도 실행기나 유실 카운터를 두지 않는다.
정상 조회의 빈 결과를 0건으로 바꾸는 것은 장애 처리가 아니다. 조회 예외는 빈 결과로 바꾸지 않는다.
분석용 집계도 같은 기본 처리를 따른다. 반환 값과 저장 상태에 따른 한계는 [집계 조회 계약](./coupon-stats-query-contract.md)이 갖는다.

### 롤백 안 되는 효과: 광고 후보 소진 반영

쿠폰 발급을 먼저 커밋한 뒤 소진을 반영하므로 광고 서빙의 실패로 완료된 쿠폰을 취소하지 않는다.
소진 통보 실패는 COUPON_SOLD_OUT_NOTIFICATION_FAILED로 기록하고 발급 성공을 유지한다.
소진 통보에 필요한 조회도 별도 작업자에서 수행하며 실패하면 같은 재시도 대상으로 남긴다.
호출 경계와 재시도는 [API 설계](./coupon-api-design.md#찜과-소진-contract-연결)가 갖는다.
접수 상한과 재시도 기간, 서버 종료 뒤 복구 한계도 같은 API 설계를 따른다.

## 유형별 점검

### 캐시

쿠폰 발급의 Redis 순번과 예약은 아래 복구 절을 따른다.
owner의 일반 상태 캐시를 QR 사용·이력 조회의 현재 상태 판정으로 대신 쓰지 않는다.
공용 인증의 캐시 장애 처리는 인증 도메인이 소유한다.

### DB

| 시나리오 | 점검 결과 |
|---|---|
| 다운, 연결 거부 | 해당 없음. 기본 처리대로 읽기 오류를 올리고 진행한 쓰기를 되돌린다. 부재·소진·빈 목록으로 바꾸지 않는다 |
| 슬로우 쿼리, 응답 지연 | `아직 정하지 못한 것`의 「DB 대기 상한」을 따른다 |
| 커넥션 풀 고갈 | 발급은 작업자 수(`coupon.issue.batch.workers`)만큼만 커넥션을 쓴다. 대기열이 가득 차면 기다리지 않고 `503 COUPON-008`로 거절하고, 결과를 `wait-timeout`보다 오래 기다리면 `500 COMMON-001`로 응답한다. 그 밖의 경로는 「DB 대기 상한」을 따른다 |
| 데드락 | 발급 묶음을 롤백하고 모든 요청에 오류를 전달한다. 자동 재시도는 하지 않는다. 카운터 잠금은 유니크 키를 고정해 회원 ID 순으로 잡는다 |
| 락 대기 초과 | 해당 없음. 기본 처리대로 오류로 올리고 롤백한다. 최대 대기와 재시도 안내는 「DB 대기 상한」에서 별도로 확인한다 |
| 제약 위반, 데이터 불일치 | 해당 없음. 재시도하지 않는다. 누락 스냅샷·누락 사용 이력·중복 매장 이벤트는 정합성 오류로 올린다 |
| Primary 페일오버 | 아직 훑지 않았다. 커밋 결과가 불명확한 요청과 재연결을 실제 환경에서 확인해야 한다 |
| 복제 지연 | 아직 훑지 않았다. 실제 읽기 라우팅과 쓰기 직후 조회의 일관성을 확인해야 한다 |

### 외부 API

해당 없음. 현재 coupon은 외부 API를 호출하지 않는다.
공개 contract는 같은 프로세스 안의 호출이다. 해당 호출의 DB 장애를 빈 Optional이나 빈 목록으로 바꾸지 않는다.

### 애플리케이션

| 시나리오 | 점검 결과 |
|---|---|
| 요청이 몰린다 | `아직 정하지 못한 것`의 「부하 목표와 잠금 대기」를 따른다 |
| 대용량 조회 | 목록·이력은 페이지 최대 100개이고 이벤트 상태 조회는 매장 최대 100개다. 해당 상한의 근거는 HTTP 명세다. 누적 통계의 장기 실행 계획은 아직 훑지 않았다 |
| 배포로 서버가 내려간다 | HTTP graceful shutdown 설정과 배처의 종료 대기를 사용한다. 아래 「발급 작업자의 종료」에 적용할 순서와 현재 구현의 차이를 적는다 |
| 서버가 여러 대다 | 생명주기 배치는 [쿠폰 배치 설계](./coupon-batch-design.md)의 점유와 실행 세대를 사용한다. 순번 복구의 동시성은 [이벤트 행의 DB 잠금](./coupon-issuance-v2-design.md#7-복구는-db-작업의-종료를-기다린-뒤-수행한다)으로 제어한다. 복구는 발급 요청이 시도하며 별도 스케줄러를 두지 않는다. 여러 프로세스의 부하·복구 시험은 아직 없다 |

### 롤백 안 되는 효과

외부 API는 호출하지 않으며 QR PNG 생성은 외부 저장 효과를 만들지 않는다. 퍼널 이벤트는 트랜잭션 안에서 발행하고 분석은 커밋 후 처리한다.
DB 커밋 후 응답 유실에 따른 업무 결과는 [구조와 동작 설계 9장](./coupon_구조와_동작_설계.md#9-실패-처리)이 갖는다.

| 시나리오 | 점검 결과 |
|---|---|
| 커밋 뒤 실패 | 「롤백 안 되는 효과: 분석 퍼널 기록」과 「롤백 안 되는 효과: 광고 후보 소진 반영」을 따른다 |
| 커밋 전 성공 | 해당 없음. AFTER_COMMIT 리스너는 롤백된 업무를 수신하지 않는다. QR 이미지를 만들었어도 DB 커밋에 실패하면 성공 응답하지 않는다 |
| 보상 실패 | 해당 없음. 현재 coupon에는 외부 보상 작업이 없다 |

## 발급 묶음의 자동 재시도

현재 발급 작업자는 실패한 묶음을 나누거나 자동으로 재시도하지 않는다.
묶음 서비스의 예외는 해당 묶음의 모든 요청에 전달한다.
Redis 예약의 반납과 차단은 [트랜잭션 종료 상태](./coupon-issuance-v2-design.md#5-롤백과-커밋-결과-불명을-구분한다)에 따라 수행한다.
복구 성공 후 발급을 이어가는 조건은 [복구 시작 조건](./coupon-issuance-v2-design.md#71-복구를-시작하는-조건)이 갖는다.
발급 조정 메서드가 미발급을 확인한 요청 한 건만 재접수하며 작업자가 실패한 묶음 전체를 다시 실행하는 흐름은 추가하지 않는다.

자동 재시도를 다시 추가할 때는 다음 조건을 모두 반영한다.

- 롤백이 확인됐고 재시도로 해결할 수 있는 오류만 대상으로 삼는다.
- DB 연결 실패와 제약 위반, 커밋 결과 불명은 재시도 대상에서 제외한다.
- 묶음을 반으로 나눠 재귀 호출하지 않는다.
- 재시도 횟수와 전체 처리 시간에 상한을 둔다. 큐에서 기다린 시간도 요청의 전체 대기 예산에 포함한다.
- 재시도할 오류 종류와 횟수·시간 상한을 확정하고 장애 시험으로 검증한 뒤 구현한다. 현재는 상한 값을 정하지 않았다.

## 발급 작업자의 종료

현재 설정은 `server.shutdown=graceful`과 `spring.lifecycle.timeout-per-shutdown-phase=30s`를 사용한다.
`CouponIssueBatcher.stop`은 접수를 멈춘 뒤 작업자마다 최대 5초씩 기다리고 대기열에 남은 요청을 실패로 완료한다.
작업자마다 기다리는 시간은 배처 전체의 종료 상한이 아니다. 대기가 끝나도 살아 있는 작업자가 있을 수 있다.
현재 배처의 기본 lifecycle phase만으로는 HTTP 처리가 끝난 뒤 배처를 종료하는 순서를 보장하지 못한다.

아래 순서로 보완한다. 설계만 정했으며 lifecycle 설정 변경과 종료 시험은 아직 하지 않았다.

1. readiness를 내려 트래픽 제외를 시작하고 HTTP 서버가 새 요청을 받지 않게 한다.
2. 이미 받은 HTTP 요청을 처리한다. 이 요청이 배처에 접수하고 결과를 기다릴 수 있도록 배처 작업자와 DB·Redis 연결을 유지한다.
3. 기존 HTTP 요청이 끝나거나 HTTP 종료 대기가 만료되면 배처의 새 접수를 닫는다. 접수 여부 검사와 대기열 등록을 함께 제어해 종료 검사 뒤 요청이 뒤늦게 들어오지 못하게 한다.
4. 시작하지 않은 요청은 취소하고 대기열에서 제거한다. 실행 중인 묶음은 [v3의 취소·처리 기한](./coupon-issuance-v3-design.md#61-요청-취소와-발급-작업의-기한을-연결한다)에 따라 종료한다.
5. 진행 중인 DB 트랜잭션의 종료를 확인하고 Redis 완료·반납까지 마친 뒤 발급 작업자를 종료한다.
6. 작업자 종료 뒤 DB 커넥션 풀과 Redis 클라이언트를 종료한다.

Spring lifecycle의 종료 phase는 HTTP 종료, 배처 종료, 의존 연결 종료 순서로 배치한다.
배처는 여러 작업자를 순서대로 각각 5초씩 기다리지 않는다. 배처 전체에 하나의 종료 기한을 두고 남은 시간만 기다린다.
현재 30초 설정은 phase별 제한이며 프로세스 전체 종료 시간을 뜻하지 않는다.
HTTP 대기·배처 정리의 예산과 배포 환경의 강제 종료 유예 시간을 맞추는 값은 구현 전에 확정한다.

배처의 비동기 종료 완료 통지는 작업자와 예약 정리가 실제로 끝난 뒤 호출한다.
기한이 끝났는데 작업자가 살아 있으면 정상 종료로 기록하지 않는다.
DB 커밋 여부를 모르는 예약을 임의로 반납하지 않으며 남은 이벤트와 미완료 작업을 관측할 수 있게 남긴다.
강제 종료 후 남은 예약은 [후속 발급 요청의 DB 기준 복구](./coupon-issuance-v2-design.md#71-복구를-시작하는-조건)로 처리한다. 요청이 없으면 복구도 진행하지 않는다.

종료 시험에서는 대기열에 있는 요청, DB 처리 중인 묶음, 커밋 뒤 Redis 완료 중인 묶음에 각각 종료 신호를 보낸다.
새 요청 차단부터 연결 종료까지의 실제 순서와 접수·종료 경쟁에서 결과를 기다리는 요청이 남지 않는지 확인한다.
유예 시간 초과와 강제 종료 시험에서는 후속 발급 요청이 남은 예약을 감지하고 DB 기준으로 복구하는지 확인한다.

## 아직 정하지 못한 것

| 항목 | 현재 확인한 것 | 후속 확인 |
|---|---|---|
| DB 대기 상한 | 현재 발급 전용 트랜잭션 제한 시간은 없다. 요청 기한을 공유하는 [v3 보완 설계](./coupon-issuance-v3-design.md#61-요청-취소와-발급-작업의-기한을-연결한다)를 정했다 | 쿼리·잠금·풀·Redis 대기의 구체적인 상한을 확정하고 취소·종료 시험으로 검증한다 |
| 부하 목표와 잠금 대기 | [v1 성능 개선 비교](../../troubleshooting/coupon/coupon-issuance-v1-improvement-comparison.md)에 로컬 부하와 잠금·풀 대기 결과를 기록했다 | 같은 조건의 장시간 시험과 부하 발생기를 분리한 피크 시험으로 검증을 보완한다 |
| QR 사용의 제공자 연결 | 쿠폰 저장과 공개 계약 소비는 HTTP 통합 테스트로 확인한다 | owner·store 제공자는 이 테스트에서 대역이므로 실제 제공자 DB·장애 검증은 해당 도메인의 테스트를 함께 확인한다 |
| 사용 시각의 일치 | 사용 이력을 JPA로 저장하고 auditing의 createdAt을 응답과 이력 조회에 사용한다 | 실제 HTTP 테스트가 마이크로초까지 같은 useTime을 저장하는지 검증한다 |
| 공개 계약 제공자 | store·adserving의 쿠폰 호출부와 장애 전파, 소진 실패 시 발급 유지를 테스트한다 | 통합 테스트의 다른 도메인 제공자는 대역이다. 실제 제공자 DB 동작은 해당 도메인의 테스트가 확인한다 |
| 퍼널 수신과 외부 효과 | 공개 타입 4종과 발급·사용의 발행을 구현했다. AFTER_COMMIT 리스너의 수신·롤백 제외를 HTTP 통합 테스트로 확인한다 | 오픈·만료 배치는 연결했다. 분석 수신자의 비동기 실행기·저장 실패·유실 관측은 수신자에서 확인한다 |
| 운영 복구 | 페일오버·복제 지연·종료 중 요청을 시험하지 않았다 | 실제 구성에 해당하는 장애를 재현해 남는 상태와 재요청 결과를 확인한다 |

## 배치 실패

독립 작업의 실행 시간, 부분 커밋, 이어받기와 정합성 결과 기록은 [쿠폰 배치 설계](./coupon-batch-design.md)를 따른다.
배치 장애 때문에 기존 HTTP 발급 시간과 이미 발급한 쿠폰의 사용 계약을 바꾸지 않는다.

## Redis 장애와 큐 복구

Redis 순번 발급기의 장애별 남는 상태와 대응은 [v2 설계도의 장애 시나리오](./coupon-issuance-v2-design.md#6-장애-시나리오와-대응)가 소유한다.
DB 작업 종료 확인과 재구축 순서, 재개 조건은 [복구 설계](./coupon-issuance-v2-design.md#7-복구는-db-작업의-종료를-기다린-뒤-수행한다)를 따른다.
v3도 같은 예약·반납·차단·복구 원칙을 사용한다. 요청별 거절과 묶음 실패의 구분은 [v3 설계도](./coupon-issuance-v3-design.md#5-요청별-거절과-묶음-실패를-구분한다)가 갖는다.
