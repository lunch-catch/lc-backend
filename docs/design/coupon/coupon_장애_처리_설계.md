# coupon 장애 처리 설계

현재 발급·조회·삭제·QR 생성·사용 경로가 기대는 대상과 [장애 처리 가이드](../장애_처리_설계_가이드.md)의 기본 처리를 벗어나는지를 기록한다.
QR 사용 확정도 같은 기본 처리를 따르며 상태·사용 이력의 동시 롤백을 HTTP 통합 테스트로 확인한다.
업무상 거절의 상태·오류와 엔드포인트별 흐름은 [API 설계](./coupon-api-design.md)가 갖는다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| MySQL 읽기 | 이벤트·재고·카운터·회원 쿠폰·사용 이력을 읽는다 | 기본(오류로 올린다) |
| MySQL 쓰기 | 발급과 삭제·QR 교체·사용 확정·조회 시 만료 저장에 쓴다 | 기본(트랜잭션을 되돌린다) |
| member의 MemberQueryService | 발급·QR 생성·사용 자격과 이벤트 상태를 판정한다 | 기본(조회 장애를 전파한다). 정상적인 회원 부재와 구분한다 |
| owner의 OwnerStatusQuery | 사용 이력 조회·사용 확정에서 현재 ACTIVE 상태를 확인한다 | 기본(조회 장애를 전파한다). findCurrentStatus로 상태 캐시를 우회한다 |
| campaign의 CampaignQueryService | 이벤트 상태 조회에서 매장별 캠페인을 확인한다 | 기본(조회 장애를 전파한다) |
| store의 StoreQueryService | QR 사용의 현재 매장 관리 권한과 좌표를 확인한다 | 기본(조회 장애와 내부 데이터 누락을 오류로 올린다) |
| 프로세스 내부 QR 인코더 | 토큰의 PNG 이미지를 만든다 | 기본(예외를 전파하고 QR 변경 트랜잭션을 되돌린다) |

## 벗어난 것

현재 확인한 구현에는 기본 처리를 벗어나 장애 중 요청을 성공시키는 경로가 없다.
정상 조회의 빈 결과를 0건으로 바꾸는 것은 장애 처리가 아니다. 조회 예외는 빈 결과로 바꾸지 않는다.
미연결 찜 조회와 광고 후보 소진 갱신도 장애 시 폴백이 아니다. 해당 기능을 아직 호출하지 않는 범위 제한이다.
그 상태와 근거는 [API 설계의 임시 구현 범위](./coupon-api-design.md#임시-구현-범위)가 소유한다.

## 유형별 점검

### 캐시

해당 없음. coupon은 직접 캐시를 쓰지 않는다.
owner의 일반 상태 캐시를 QR 사용·이력 조회의 현재 상태 판정으로 대신 쓰지 않는다.
공용 인증의 캐시 장애 처리는 인증 도메인이 소유한다.

### DB

| 시나리오 | 점검 결과 |
|---|---|
| 다운, 연결 거부 | 해당 없음. 기본 처리대로 읽기 오류를 올리고 진행한 쓰기를 되돌린다. 부재·소진·빈 목록으로 바꾸지 않는다 |
| 슬로우 쿼리, 응답 지연 | `아직 정하지 못한 것`의 「DB 대기 상한」을 따른다 |
| 커넥션 풀 고갈 | `아직 정하지 못한 것`의 「DB 대기 상한」을 따른다 |
| 데드락 | 해당 없음. 현재 coupon은 실패한 트랜잭션을 자동 재실행하지 않고 오류로 올린다. 실제 교착·복구 시험은 아직 훑지 않았다 |
| 락 대기 초과 | 해당 없음. 기본 처리대로 오류로 올리고 롤백한다. 최대 대기와 재시도 안내는 「DB 대기 상한」에서 별도로 확인한다 |
| 제약 위반, 데이터 불일치 | 해당 없음. 재시도하지 않는다. 누락 스냅샷·누락 사용 이력·중복 매장 이벤트는 정합성 오류로 올린다 |
| Primary 페일오버 | 아직 훑지 않았다. 커밋 결과가 불명확한 요청과 재연결을 실제 환경에서 확인해야 한다 |
| 복제 지연 | 아직 훑지 않았다. 실제 읽기 라우팅과 쓰기 직후 조회의 일관성을 확인해야 한다 |

### 외부 API

해당 없음. 현재 coupon은 외부 API를 호출하지 않는다.
공개 contract는 같은 프로세스 안의 호출이다. 해당 호출의 DB 장애를 빈 Optional이나 빈 목록으로 바꾸지 않는다.

### 애플리케이션

| 시나리오 | 점검 결과 |
|---|---|
| 요청이 몰린다 | `아직 정하지 못한 것`의 「부하 목표와 잠금 대기」를 따른다 |
| 대용량 조회 | 목록·이력은 페이지 최대 100개이고 이벤트 상태 조회는 매장 최대 100개다. 해당 상한의 근거는 HTTP 명세다. 누적 통계의 장기 실행 계획은 아직 훑지 않았다 |
| 배포로 서버가 내려간다 | 아직 훑지 않았다. 실제 종료 대기 중 트랜잭션 처리와 응답 유실을 확인해야 한다 |
| 서버가 여러 대다 | 해당 없음. 현재 배치와 프로세스 내부 잠금은 없다. 발급·쿠폰 변경은 MySQL 행 잠금과 제약을 사용한다. 여러 프로세스의 부하 시험은 아직 없다 |

### 롤백 안 되는 효과

현재 외부 API 호출과 이벤트 발행은 없다. QR PNG 생성은 외부 저장 효과를 만들지 않는다.
DB 커밋 후 응답 유실에 따른 업무 결과는 [구조와 동작 설계 9장](./coupon_구조와_동작_설계.md#9-실패-처리)이 갖는다.

| 시나리오 | 점검 결과 |
|---|---|
| 커밋 뒤 실패 | 현재 외부 효과에는 해당 없음. 후속 분석 이벤트는 「사용 이벤트와 외부 효과」를 따른다 |
| 커밋 전 성공 | 현재 외부 효과에는 해당 없음. QR 이미지를 만들었어도 DB 커밋에 실패하면 성공 응답하지 않는다 |
| 보상 실패 | 해당 없음. 현재 coupon에는 외부 보상 작업이 없다 |

## 아직 정하지 못한 것

| 항목 | 현재 확인한 것 | 후속 확인 |
|---|---|---|
| DB 대기 상한 | 발급 전용 트랜잭션 제한 시간은 없고 DB 오류는 공통 예외 처리로 전달한다 | 쿼리·잠금·풀 대기 상한과 클라이언트 대기 시간을 실제 설정·시험으로 대조한다 |
| 부하 목표와 잠금 대기 | 작은 동시성 기능 테스트만 있다. 발급 목표의 달성 여부는 검증하지 않았다 | [구조와 동작 설계 11장](./coupon_구조와_동작_설계.md#11-성능)의 비용을 바탕으로 부하·대기 시간을 측정한다 |
| QR 사용의 제공자 연결 | 쿠폰 저장과 공개 계약 소비는 HTTP 통합 테스트로 확인한다 | owner·store 제공자는 이 테스트에서 대역이므로 실제 제공자 DB·장애 검증은 해당 도메인의 테스트를 함께 확인한다 |
| 사용 시각의 일치 | 사용 이력을 JPA로 저장하고 auditing의 createdAt을 응답과 이력 조회에 사용한다 | 실제 HTTP 테스트가 마이크로초까지 같은 useTime을 저장하는지 검증한다 |
| 미연결 다른 도메인 | store는 QR 사용에 연결했다. 기존 이력·이벤트 조회의 매장 검증과 adserving #163 연결은 미완료다 | 연결할 때 그 대상이 느리거나 실패하는 경우를 추가로 점검한다 |
| 사용 이벤트와 외부 효과 | 아키텍처는 분석 퍼널의 커밋 후 비동기 기록과 유실을 허용하지만 coupon 구현은 없다 | 공개 이벤트 계약과 실행 수단을 준비할 때 커밋 전 성공·커밋 후 실패·유실 추적을 점검한다 |
| 운영 복구 | 페일오버·복제 지연·종료 중 요청을 시험하지 않았다 | 실제 구성에 해당하는 장애를 재현해 남는 상태와 재요청 결과를 확인한다 |
