# analytics 장애 처리 설계

이 도메인이 기대는 대상과 기본 처리를 벗어난 것을 적는다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| analytics MySQL | 이벤트 기록, 집계 공개, 조회 | 기본. 읽기는 오류로 올리고 쓰기는 롤백한다 |
| 원천 도메인의 `StatsQueryService` | 일별 결과 모으기 | 벗어났다. 아래에 적는다 |
| ops 배치 contract | 날짜 점유, 실행 세대 확인, 실행 결과 | 벗어났다. 아래에 적는다 |
| `CampaignQueryService` | 점주 리포트 소유 확인 | 기본. 읽기 실패를 오류로 올린다 |
| 비동기 실행기 | 퍼널 이벤트 기록 | 벗어났다. 아래에 적는다 |
| analytics MySQL | 이벤트 로그 보존 삭제 | 쓰기를 벗어났다. 아래에 적는다 |

## 벗어난 것

### 애플리케이션: 원천 도메인의 집계 조회

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 실패한 원천만 다시 호출한다 | 이미 모은 결과를 재사용한다 | 원천별 시점이 달라질 수 있다 |
| B. 하루 결과를 처음부터 다시 모은다 | 모든 원천을 같은 시도의 결과로 맞춘다 | 성공한 원천도 다시 호출한다 |

B를 사용한다. analytics는 여러 원천을 캠페인과 영업일로 합치므로 일부 결과만 재사용하면 한 공개 결과에 서로 다른 시점의 숫자가 섞일 수 있다. 일시적 오류만 트랜잭션 밖에서 기다린 뒤 다시 시도한다. 데이터 불일치와 제약 위반은 재시도하지 않는다.

원천이 준비되지 않았으면 날짜를 `SOURCE_NOT_READY`로 미처리 목록에 남기고 이전 공개 결과를 유지한다. 통과시킨 요청은 없으므로 별도 폴백 지표를 두지 않는다. 실패 날짜 수를 `analytics_aggregation_pending_dates`로 관측한다.

### 애플리케이션: ops 실행 점유

날짜를 점유하지 못하면 같은 날짜를 실행하지 않는다. 실행 도중 임대를 잃으면 공개 트랜잭션의 실행 세대 확인에서 롤백한다. 실행 세대 확인이 제공되기 전에는 늦은 서버의 공개를 완전히 막지 못하며 이슈 `#360`이 해결한다.

**2026-10-17 구현 상태.** `#360`은 병합됐지만 일별 집계 실행기는 아직 `BatchAttemptGuard`를 부르지 않는다. 정상 경로(claim, retry, rerun)에서 자기 실행 세대를 돌려받을 방법이 없고, `BatchExecutionRecord`에도 세대가 없기 때문이다. 그래서 늦게 깨어난 서버가 결과를 덮는 경우는 아직 막지 못한다. 단계마다 생존 신호(`renew`)를 갱신해 행을 잃었으면 더 돌지 않는 것으로 줄였다. 후속 작업에서 ops에 세대 조회를 요청하고 `StandaloneJob` 등록, `assertCurrentAttempt` 호출을 함께 붙인다.

수동 재계산 실행기가 가득 차 시작하지 못하면 이미 잡은 실행 행을 실패로 닫고 날짜를 미처리로 남긴다. 닫지 않으면 `RUNNING`으로 남아 다른 서버가 이어받아 의미 없이 실패 처리한다.

### 롤백 안 되는 효과: 퍼널 이벤트 기록

퍼널 기록은 원천 업무의 판정과 과금에 사용하지 않는다. 원천 트랜잭션 커밋 뒤 전용 비동기 실행기로 기록하고 큐가 가득 차거나 프로세스가 종료되면 유실을 허용한다. 유실을 허용하는 대신 돈과 맞아야 하는 건수는 원천 도메인의 집계 조회로 다시 센다.

**커밋 뒤에 받는 이유.** 일반 이벤트 수신은 발행하는 즉시 실행된다. 노출 처리가 트랜잭션 안에서 이벤트를 발행한 뒤 롤백되면 노출 로그와 포인트 차감은 취소되는데 `event_log`의 `impression` 행은 남는다. 분석이 실제로 없던 노출을 퍼널에 세게 된다. `AFTER_COMMIT`으로 받으면 커밋이 끝난 뒤에만 이벤트를 받고 롤백되면 받지 않는다.

**`fallbackExecution = true`를 켜는 이유.** `AFTER_COMMIT` 수신자는 활성 트랜잭션이 없으면 기본으로 호출되지 않는다. 오류도 로그도 남지 않는다. 스와이프는 트랜잭션 밖에서 발행하므로 이 속성이 없으면 스와이프 이벤트가 전부 사라진다. 이것은 허용한 유실이 아니라 배선 오류다. 트랜잭션 안에서 발행하는 노출과 쿠폰은 속성이 있어도 같게 커밋 뒤에 받는다. 수신 메서드 여섯 모두에 켠다.

**유실이 원천 업무로 번지지 않는 방법.** 동기 수신은 예외가 발행한 쪽으로 올라와 이미 커밋된 요청을 `500`으로 만든다. 이것은 기본 동작이므로 설계가 막아야 한다. 분석이 전용 실행기에 기록을 맡기고, 기록 실패는 예외 없이 경고 로그와 지표로만 남기고, 대기열이 차면 새 이벤트를 버린다. 실행기의 구조와 지표, `@Async`를 쓰지 않는 이유는 [analytics 구조와 동작 설계](./analytics_구조와_동작_설계.md)의 "퍼널 이벤트 수신과 비동기 기록"에 있다.

## 유형별 점검

### 캐시

해당 없음. analytics는 캐시와 분산 락을 사용하지 않는다.

### DB

| 시나리오 | 점검 결과 |
|---|---|
| 다운, 연결 거부 | 이벤트 요청과 조회는 오류로 올린다. 배치는 실패 날짜를 남긴다 |
| 슬로우 쿼리, 응답 지연 | 공통 쿼리 타임아웃을 따른다. 배치 공개 트랜잭션은 외부 호출을 포함하지 않는다 |
| 커넥션 풀 고갈 | 공통 풀 대기 상한에서 실패한다. 배치는 실패 날짜를 남긴다 |
| 데드락 | 일시적 실패로 분류될 때 하루 결과를 처음부터 다시 시도한다 |
| 락 대기 초과 | 일시적 실패로 분류될 때 하루 결과를 처음부터 다시 시도한다 |
| 제약 위반, 데이터 불일치 | 재시도하지 않는다. 이벤트 요청은 오류로 올리고 배치는 FAILED로 닫는다 |
| Primary 페일오버 | 쓰기 트랜잭션이 실패하면 공개 결과가 바뀌지 않는다 |
| 복제 지연 | 조회와 쓰기는 Primary를 사용한다 |

### 외부 API

해당 없음. analytics는 외부 HTTP API를 호출하지 않는다.

### 애플리케이션

| 시나리오 | 점검 결과 |
|---|---|
| 요청이 몰린다 | 목록 상한과 이벤트 요청 50건 상한으로 제한한다 |
| 대용량 조회 | 조회 기간과 페이지 크기 상한을 적용한다 |
| 배포로 서버가 내려간다 | 배치는 미처리 날짜를 남기고 다음 실행에서 다시 잡는다 |
| 서버가 여러 대다 | ops 실행 기록으로 날짜를 점유하고 실행 세대로 공개 권한을 확인한다 |

### 롤백 안 되는 효과

| 시나리오 | 점검 결과 |
|---|---|
| 커밋 뒤 실패 | 퍼널 기록은 유실을 허용한다. 일별 건수는 원천 집계 조회로 복구한다 |
| 커밋 전 성공 | 원천 업무 커밋 전에 analytics 이벤트를 처리하지 않는다 |
| 보상 실패 | 보상 작업이 없다. 집계는 다음 실행에서 하루 결과를 교체한다 |

## 아직 정하지 못한 것

| 항목 | 영향 |
|---|---|
| 이슈 `#360`의 실행 세대 contract | 여러 서버에서 늦게 끝난 실행의 공개 차단 |
| 비동기 실행기의 대기열 크기와 스레드 수의 측정값 | 지금 값(1000건, 2개)은 예시값이다. 퍼널 이벤트 유실 관측 |

### DB 쓰기: 이벤트 로그 보존 삭제

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 한 트랜잭션으로 모두 지운다 | 실패하면 전부 되돌아가 부분 반영이 없다 | 쌓인 양이 많으면 락을 오래 쥐어 이벤트 기록 쓰기를 막는다 |
| B. 1000행씩 청크마다 커밋한다 | 락을 짧게 쥔다. 중간에 실패해도 지운 만큼은 남는다 | 실패하면 일부만 지워진 상태가 된다 |

B를 사용한다. 지워지는 행은 보존 기간이 지나 어차피 지워질 행이라 일부만 지워져도 어긋나는 값이 없다. 남은 행은 다음 날 실행이 이어서 지운다. 실패하면 실행 행을 `FAILED`로 닫고 예외를 다시 던져 공통 스케줄러 관측이 알아차리게 한다. 서버가 멈추면 `StandaloneJob`으로 등록돼 있어 다른 서버가 이어받는다. 삭제는 멱등이라 다시 돌려도 남은 행만 지운다.

청크 사이에 쉬다가 중단 신호를 받으면 예외를 던져 위의 실패 경로를 탄다. 덜 지운 실행을 `SUCCESS`로 닫지 않기 위해서다. 서버 종료가 04:00 실행과 겹치면 실패 알림이 가고, 남은 행은 다음 날 실행이나 관리자 수동 재실행이 지운다.

| 중단 신호를 받았을 때 | 장점 | 단점 |
|---|---|---|
| A. 실패로 닫는다 | 기록이 사실과 맞다. 기존 실패 경로를 그대로 쓴다 | 배포로 서버가 내려가도 실패 알림이 간다. `FAILED` 행은 다른 서버가 이어받지 않는다 |
| B. 행을 `RUNNING`으로 둔다 | 생존 신호가 끊기면 2분 뒤 다른 서버가 이어받아 마저 지운다 | 중단 전용 예외와 `fail`을 건너뛰는 분기가 더 든다. 서버가 살아 있는데 중단되면 생존 신호가 행을 계속 살려 둔다 |

A를 사용한다. 중단은 배포와 04:00이 겹칠 때만 생기고, 남은 행은 늦어도 다음 날 지워진다.
