# 요청 중 쓰기의 지연과 유실 허용 범위 비교

HTTP 요청을 처리하는 중에 생긴 쓰기를 관계형 DB에 반영하는 방식들을, **응답 지연과 유실 허용 범위**에 따라 비교한다.
비교의 축은 데이터 종류가 아니라 **"응답 전에 쓰기를 어디까지 확인하고, DB에는 언제 반영하느냐"**다. 이 선택에 따라 응답 지연과 내구성(유실 여부)이 갈린다.
유실이 없어야 하는 쓰기와 일부 유실을 감수해도 되는 쓰기를 모두 다루며, 데이터별 적용 여부는 5장에 정리했다.
이 비교는 단일 관계형 DB, 동기 HTTP 요청, 응답 후에도 계속 실행되는 서버 프로세스를 전제로 한다.

## 언제 고려하나

쓰기량이 적고 응답 지연에 여유가 있다면, 요청 안에서 단건으로 바로 INSERT 하는 것이 가장 단순하고 유실도 없다.
아래 A~D, F는 쓰기량이 많아 단건 INSERT가 DB 부하나 응답 지연의 원인이 되거나, 요청 처리를 DB 장애와 분리해야 할 때 고려한다.
그중 F는 일부 유실을 감수하는 대신 가장 단순하게 응답 지연을 없애는 방식이다.
E는 트래픽과 관계없이 DB 쓰기와 DB 밖 후속 작업을 함께 보장해야 할 때 쓴다.

## 대상 방식

| 구분 | 방식 | 설명 |
|---|---|---|
| A | 동기 | 가상 스레드(Java 21+) + JVM 내부 큐 + 마이크로 배칭 (DB 커밋 후 응답) |
| B | Redis Stream | 응답 전 XADD, 컨슈머가 DB 반영 |
| C | 로컬 파일 로그 | 파일 기록 후 일괄 적재 |
| D | Kafka | 응답 전 발행, 컨슈머가 DB 반영 |
| E | 아웃박스 + 폴링/CDC | 비즈니스 데이터 저장과 DB 밖의 후속 작업(이벤트 발행, 외부 API 호출, 알림 등)을 함께 보장해야 할 때 |
| F | 인메모리 비동기 | 응답 후 JVM 내부 큐에 넣고, 별도 스레드가 모아서 DB 반영 |

## 1. 내구성과 지연

| 방식 | 응답 지연 증가 | 유실 허용 수준 | 남는 유실 지점 |
|---|---|---|---|
| A. 동기 | 수~수십 ms (배칭 대기 + INSERT) | 없음 | 사실상 없음 (DB 기본 설정(커밋 시 로그 fsync) 기준) |
| B. Redis Stream | 1ms 내외 | 장비 장애 시 소량 | AOF everysec 기준 미기록분(최대 약 1초), failover 시 미복제분. AOF를 끄면 마지막 스냅샷 이후 전부 |
| C. 로컬 파일 | 거의 없음 | 장비 장애 시 소량 | AsyncAppender 메모리 버퍼, OS 미flush분, 디스크 장애 |
| D. Kafka | ack 대기 시 수 ms | 매우 적음 | `acks=all` 설정 시 매우 낮음 (ack를 기다리지 않으면 프로듀서 버퍼 유실) |
| E. 아웃박스 + 폴링/CDC | 거의 없음 (기존 트랜잭션에 INSERT 1건 추가) | 없음 | 없음 (DB 커밋 = 후속 작업 기록) |
| F. 인메모리 비동기 | 없음 | 프로세스 종료 시 큐 전체 | 서버 비정상 종료(OOM, kill -9) 시 큐에 있던 전부, DB 장기 장애 시 큐가 가득 차 버린 쓰기 |

## 2. 장애 영향과 운영

| 방식 | DB 장애 시 요청 처리 | 추가 인프라 | 구현 난이도 | 여러 서버 |
|---|---|---|---|---|
| A. 동기 | **직접 영향** (지연, 실패) | 없음 | 낮음 | 각자 DB에 씀 |
| B. Redis Stream | 무관 (Redis 장애 시 fallback 필요) | Redis | 중간 | 공유 가능 |
| C. 로컬 파일 | 무관 | 없음 (대규모면 수집기, 컨테이너 환경은 영속 볼륨 필요) | 중간 | 서버별 파일 |
| D. Kafka | 무관 | Kafka 클러스터 | 높음 | 공유 가능 |
| E. 아웃박스 + 폴링/CDC | 비즈니스 자체가 DB 의존 | 없음 (CDC면 Debezium) | 중간~높음 | 공유 가능 |
| F. 인메모리 비동기 | 무관 (장애가 길면 큐 포화로 버림) | 없음 | 가장 낮음 | 서버별 큐 |

## 3. 짚어둘 점

- **A의 JVM 내부 큐는 "모으는 곳"일 뿐 저장소가 아니다.**
  요청 스레드는 큐에 넣은 뒤 DB 커밋이 끝날 때까지 기다렸다가 응답한다. 그래서 서버가 죽어도 응답을 받은 요청의 쓰기는 이미 DB에 있다.
  응답 후 큐에 넣고 뒤에서 저장하는 F와 달리 유실이 없는 이유다. 대기 비용은 가상 스레드로 줄인다.
  큐를 Redis에 두면 데이터가 이미 JVM 밖에 있으므로 DB 커밋을 기다릴 이유가 없어지고, Redis 쓰기 확인 후 응답하는 B가 된다.
- **F는 A와 같은 JVM 내부 큐를 쓰지만 응답 시점이 다르다.**
  A는 DB 커밋 후 응답하고, F는 큐에 넣자마자 응답한다. 그래서 F는 응답 지연이 없고 구현이 가장 단순하지만, 큐가 JVM 메모리에 있어 서버가 비정상 종료되면 큐에 있던 쓰기가 모두 사라진다.
  DB 저장 실패에는 성공 후 큐에서 비우는 방식으로 재시도할 수 있고, 정상 종료(배포)에는 종료 직전 flush로 대부분 지킬 수 있다. 비정상 종료만은 막을 수 없다.
  서버리스처럼 응답 후 프로세스가 멈추는 환경에서는 백그라운드 스레드가 돌지 않으므로 F와 A의 배처를 쓸 수 없다.
- **E는 비즈니스 데이터 저장과 DB 밖의 후속 작업을 함께 보장해야 할 때만 의미가 있다.**
  후속 작업에는 이벤트 발행, 외부 API 호출(결제 환불 요청), 알림 발송, 검색 인덱스나 캐시 갱신, 웹훅, 무거운 내부 비동기 처리 등이 있다.
  공통점은 DB 트랜잭션에 함께 묶을 수 없다는 것이다. 그래서 "할 일"을 같은 트랜잭션으로 outbox 테이블에 적어두고, 릴레이가 나중에 실행한다.
  후속 작업이 없거나, 같은 DB 안의 쓰기라 한 트랜잭션으로 묶을 수 있거나, 놓쳐도 괜찮다면 필요 없다.
  요청이 DB에 쓰는 것이 하나뿐이고 후속 작업도 없으면 outbox 테이블에 INSERT 하는 것은 A(동기 INSERT)와 같아진다.
- **B, D의 유실 수준은 "응답 전에 쓰기 완료를 확인하느냐"로 정해진다.**
  XADD 응답이나 Kafka ack는 Redis(AOF)나 Kafka 브로커가 자기 서버의 로그 파일에 쓴 뒤에 돌아온다. 이 응답을 받아야 데이터가 JVM 밖에 남는다.
  확인을 생략하고 응답하면 데이터가 아직 JVM 메모리에만 있으므로, F와 같은 수준의 유실을 허용하는 선택이 된다.
- **C에서 AsyncAppender를 쓰면 그 큐도 JVM 메모리다.**
  비정상 종료 시 일부 유실된다. 완전히 막으려면 동기 appender를 써야 하고, 그만큼 디스크 I/O 지연이 붙는다.

## 4. 선택 가이드

| 상황 | 추천 |
|---|---|
| 쓰기량이 적고 응답 지연에 여유가 있음 | 단건 동기 INSERT (A~D, F 불필요) |
| 일부 유실 허용(통계, 분석), 인프라 추가 없이 가장 단순하게 | F. 인메모리 비동기 |
| 유실 불가, 인프라 추가 없이, 수 ms 지연 감수 가능 | A. 동기 |
| 이미 Redis 운영 중, 요청 처리를 DB 장애와 분리하고 싶음 | B. Redis Stream |
| 대규모 트래픽, 장기 보관, 여러 소비처(정산, 분석) | D. Kafka |
| 추가 인프라 없이 대량 쓰기, 실시간성 불필요 | C. 로컬 파일 로그 |
| 비즈니스 DB 쓰기와 반드시 실행되어야 할 DB 밖의 후속 작업이 같이 있음 | E. 아웃박스 + 폴링/CDC |

## 5. 적용 범위

기준은 데이터 종류가 아니라 **쓰기 결과와 응답의 관계, 그리고 유실을 얼마나 허용하느냐**다. 아래 조건을 만족하는지에 따라 쓸 수 있는 방식이 정해진다.

### 5.1 방식별 필요 조건

| 조건 | A. 동기 | B, C, D | E. 아웃박스 + 폴링/CDC | F. 인메모리 비동기 |
|---|---|---|---|---|
| 1. 쓰기 결과가 응답 내용을 바꾸지 않음 | 불필요 (배처가 건별 결과를 돌려주면 됨) | **필요** | 불필요 (비즈니스 트랜잭션 안에서 처리) | **필요** |
| 2. 방금 쓴 값을 직후에 읽지 않음 | 불필요 (커밋 후 응답) | **필요** (DB 반영 지연) | 후속 작업만 지연 | **필요** (DB 반영 지연) |
| 3. 멱등 키가 있거나 중복에 안전함 | 필요 (타임아웃 후 fallback이나 재시도 시 중복 가능) | 필요 | 필요 (릴레이가 후속 작업을 중복 실행할 수 있음) | 필요 (재시도 시 중복 가능) |
| 4. 다른 쓰기와 별도 트랜잭션으로 저장돼도 됨 | 필요 (배처가 다른 요청들과 묶어 별도 트랜잭션으로 커밋) | 필요 (컨슈머가 나중에 별도 트랜잭션으로 반영) | 불필요 (비즈니스 쓰기와 같은 트랜잭션에 넣는 방식) | 필요 (별도 스레드가 나중에 커밋) |
| 5. 일부 유실을 허용함 | 불필요 | 장비 장애 시 소량 유실을 감수할 때 (설정으로 줄일 수 있음) | 불필요 | **필요** (프로세스 종료 시 큐 전체) |

A와 E는 유실이 없고, A는 1, 2번 조건도 없어도 되어 적용 범위가 가장 넓다.
B, C, D는 DB 반영 전에 응답하므로 "나중에 반영되어도 되는 쓰기"에 쓰며, 장비 장애 시 소량 유실을 감수한다.
F는 B, C, D의 조건에 더해 프로세스 종료 시 유실까지 허용해야 쓸 수 있다.

### 5.2 데이터별 적용 여부

O: 적용 가능, △: 가능하나 이점이 적거나 조건이 붙음, X: 적용 불가

| 데이터 | A | B, C, D | E | F | 비고 |
|---|---|---|---|---|---|
| 접근 로그, 감사 로그 | O | O | X | △ | 함께 저장할 비즈니스 데이터가 없어 E는 A와 같아짐. F는 접근 로그만 가능하고 감사 로그는 유실 불가라 쓰지 않음 |
| 분석용 이벤트 | O | O | X | O | 페이지 조회 등. 소량 유실은 통계에 영향이 적어 F도 가능하다 |
| 광고 서빙 기록 | O | O | X | △ | 과금이나 노출 검증의 근거라면 유실이 곧 손실이므로 F는 부적합하며, 통계용으로만 쓰면 F도 가능하다 |
| 조회수, 좋아요 수 같은 카운터 | O | O | X | O | 모아서 반영. F는 근사치를 허용할 때 |
| 최근 본 상품, 검색 기록, 마지막 접속 시각 | O | O | X | O | 덮어쓰기는 중복에 안전 |
| 알림 발송 이력 | O | O | X | △ | 이력으로 중복 발송을 막는다면 유실 시 재발송될 수 있어 F는 피함 |
| 선착순 발급 (쿠폰, 좌석) | O | △ | X | X | A: 배처가 건별 결과(발급, 품절, 이미 발급)를 반환, DB 실패 시 fallback 불가. B, C, D: Redis 같은 공유 저장소에서 판정하고 그 결과로 응답하면 가능(B는 판정과 XADD를 Lua로 원자 처리). 다만 DB 반영 전까지 최종 상태가 그 저장소에 있어 저장소 유실 시 발급 기록이 사라질 수 있음 |
| 잔액 차감 원장 저장 | O | X | X | X | 판정은 원자 연산(Redis 같은 공유 저장소의 Lua, DB 조건부 UPDATE)으로 하고 저장만 A로 |
| 과금 이벤트 (이벤트 저장 + 원장 저장 + 후속 처리 전달) | △ | △ | O | X | 이벤트와 원장을 한 트랜잭션에 쓰고 후속 처리(집계 등)에 넘길 때 E. append-only 이벤트 테이블 자체를 아웃박스로 쓸 수 있음. A는 후속 전달 없이 저장만 할 때 가능. 예산을 일정 비율 넘는 노출을 허용한다면, 이벤트만 적재하고 과금은 컨슈머가 처리하는 B, C, D도 가능하다 |
| 회원가입, 찜하기 후 바로 목록 조회 | △ | X | X | X | 직후 조회는 가능하나 트래픽이 적으면 배칭 이점이 적음 |
| 주문 저장 + 재고 차감 + 주문 이벤트 발행 | X | X | O | X | 함께 성공해야 하므로 E |

### 5.3 데이터 종류에 따라 달라지는 점

- **fallback 가능 여부**: 로그처럼 쓰기 결과가 응답을 바꾸지 않으면, DB 실패 시 다른 저장소에 남기고 정상 응답할 수 있다.
  선착순 발급처럼 쓰기 결과가 곧 응답이면 판정 자체를 못 한 것이므로 "잠시 후 다시 시도" 응답을 줘야 한다.
- **재시도 책임**: 배처는 한 번만 쓰고 결과만 돌려준다. 재시도나 fallback 판단은 응답 시간 예산을 아는 서버의 요청 처리 코드가 맡는다.
- **선착순 순서**: 서버가 여러 대일 경우에는 Redis 같은 한 곳에서 원자적으로 순서를 판정한다.
- **외부 저장소와의 이중 쓰기**: A와 E는 DB 트랜잭션 안의 쓰기만 보장하고, Redis 쓰기까지 함께 묶지는 못한다. Redis에서 판정한다면 최종 상태는 DB에 두고 Redis에는 DB로 다시 만들 수 있는 값(선착순 순번 등)만 맡긴다. 잔액처럼 최종 상태를 Redis에 둬야 한다면 DB 기준 대조 배치로 맞춘다.
  응답 지연을 우선한다면 Redis를 최종 상태로 두고 B로 DB에 반영하는 선택도 있다. 이때는 Redis 유실 시 기록이 사라질 수 있음을 감수한다.
