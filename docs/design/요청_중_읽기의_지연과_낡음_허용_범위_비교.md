# 요청 중 읽기의 지연과 낡음 허용 범위 비교

HTTP 요청을 처리하는 중에 필요한 읽기를 어디서 가져오는지의 방식들을, **응답 지연과 낡음 허용 범위**에 따라 비교한다.
비교의 축은 데이터 종류가 아니라 **"응답에 쓰는 값을 어디서 읽고, 그 값이 원본과 얼마나 뒤처질 수 있느냐"**다. 이 선택에 따라 응답 지연과 값의 신선도가 갈린다.
낡은 값으로 응답하면 안 되는 읽기와 얼마간 뒤처져도 되는 읽기를 모두 다루며, 데이터별 적용 여부는 5장에 정리했다.
이 비교는 단일 관계형 DB, 동기 HTTP 요청, 응답 후에도 계속 실행되는 서버 프로세스를 전제로 한다. 다른 도메인의 `contract` 를 부르는 읽기도 범위에 넣는다.

## 언제 고려하나

읽기량이 적고 응답 지연에 여유가 있다면, 요청마다 원본에서 바로 읽는 것이 가장 단순하고 낡음도 없다.
아래 B~E 는 그 읽기가 응답 지연이나 원본의 부하가 되거나, 요청 처리를 원본 장애와 분리해야 할 때 고려한다.
그중 D 와 E 는 지연을 가장 많이 줄이는 대신 서버마다 값이 달라질 수 있다.

## 대상 방식

| 구분 | 방식 | 설명 |
|---|---|---|
| A | 원본 직접 | 요청마다 그 값의 원본에서 읽는다. 대개 DB 다 |
| B | 분산 캐시 + 만료 | Valkey 같은 공유 캐시에 두고, 없으면 원본에서 읽어 채운다. 만료되면 다시 읽는다 |
| C | 분산 캐시 + 무효화 | B 에 더해 원본을 바꾼 쪽이 캐시를 지운다. 만료는 지우기가 실패했을 때의 안전망이다 |
| D | 서버 메모리 + 만료 | 서버마다 자기 메모리에 들고, 만료되면 그 서버가 다시 읽는다 |
| E | 서버 메모리 + 알림 무효화 | D 에 더해 바꾼 쪽이 알리고 모든 서버가 다시 읽는다. 만료를 안전망으로 둔다 |

## 1. 낡음과 지연

| 방식 | 응답 지연 증가 | 낡음 상한 | 서버 사이 차이 |
|---|---|---|---|
| A. 원본 직접 | DB 왕복 하나(수 ms). 집계나 범위 조회면 그 비용 | 없다 | 없다 |
| B. 분산 캐시 + 만료 | 캐시 왕복 하나(1ms 내외). 비었으면 원본 왕복이 한 번 더 | 만료까지 | 없다. 모든 서버가 같은 값을 본다 |
| C. 분산 캐시 + 무효화 | B 와 같다 | 지우기가 되면 거의 없다. 실패하면 만료까지 | 없다 |
| D. 서버 메모리 + 만료 | 없다 | 만료까지 | **있다.** 서버마다 다시 읽은 시각이 다르다 |
| E. + 알림 무효화 | 없다 | 알림이 닿으면 수 ms. 놓치면 만료까지 | 있다. 알림이 닿는 시차만큼 |

## 2. 장애 영향과 운영

| 방식 | 원본 장애 시 | 캐시 장애 시 | 추가 인프라 | 구현 난이도 |
|---|---|---|---|---|
| A. 원본 직접 | **직접 영향**(지연, 실패) | 해당 없음 | 없다 | 가장 낮다 |
| B. 분산 캐시 + 만료 | 캐시에 있으면 버틴다. 비어 있으면 영향을 받는다 | 원본으로 떨어져 A 가 된다 | 캐시 | 낮다 |
| C. 분산 캐시 + 무효화 | B 와 같다 | 지우기가 실패해 만료까지 낡는다 | 캐시 | 중간 |
| D. 서버 메모리 + 만료 | 들고 있는 동안 버틴다. 다시 읽을 때 영향을 받는다 | 해당 없음 | 없다 | 낮다 |
| E. + 알림 무효화 | D 와 같다 | 알림이 사라지고 만료가 메운다 | 알림 채널(캐시의 pub/sub 등) | 가장 높다 |

## 3. 짚어둘 점

- **캐시와 원본을 먼저 가린다.** 어떤 값은 그 저장소가 원본이고 DB 에 사본이 없다. 그 값에는 낡음이라는 개념이 없고, 저장소를 잃으면 값이 사라진다. 낡음을 적으려면 그 값의 원본이 어디인지부터 정해야 한다.
- **읽어서 채우는 캐시와 써서 채우는 파생 값은 비었을 때가 다르다.** B~E 는 비면 원본에서 읽어 채운다. 느려질 뿐 값은 맞다. 쓰는 쪽이 올려 두는 카운터나 집계는 비면 0 이나 빈 값이 돌아온다. 느려지지 않고 **틀린다.** 그래서 그 값에는 원본에서 다시 세는 길을 함께 둬야 하고, 그 길이 없으면 저장소를 한 번 잃은 뒤로 영구히 어긋난다. 낡음 상한도 다르게 읽는다. 만료가 아니라 올리는 쪽의 주기가 상한이다.
- **E 의 알림은 보장이 아니다.** 받는 쪽이 그 순간 붙어 있지 않으면 알림은 사라진다. 그래서 만료를 없애면 안 된다. 만료가 안전망이고 알림은 그 안전망에 닿기 전에 맞추는 장치다. 알림만 믿으면 놓친 서버가 다음 배포까지 낡은 값을 쓴다.
- **D 와 E 는 같은 사용자의 연속 요청이 뒤로 갈 수 있다.** 서버 둘이 다시 읽은 시각이 다르면, 첫 요청이 새 값을 보고 다음 요청이 옛 값을 본다. 사용자가 방금 바꾼 것이 사라져 보인다. 그 값을 사용자가 직접 바꾸는 것이면 D 와 E 를 쓰지 않거나, 바꾼 뒤의 응답을 그 서버가 책임지게 한다.
- **낡음 상한은 초로 정하지 않고 "그 값이 틀린 동안 무엇이 잘못되나"로 정한다.** 돈이 걸리면 그 동안 과금될 수 있는 양을 세고, 순서가 걸리면 뒤바뀔 수 있는 경우를 센다. 그 양이 받아들일 수 있는 범위면 그것이 상한이다.
- **방금 쓴 값을 직후에 읽으면 캐시가 깨진다.** 쓰고 바로 읽는 흐름에서 B~E 를 쓰면 쓰기 전의 값이 돌아온다. 그 흐름은 A 로 읽거나, 쓴 쪽이 캐시를 함께 고친다.
- **`contract` 호출은 그 도메인의 낡음을 그대로 물려받는다.** 부르는 쪽이 고를 수 있는 것은 그 결과를 다시 캐시할지뿐이다. 그 도메인이 자기 값을 얼마나 뒤처지게 두는지는 그쪽 설계서가 갖는다. 다시 캐시하면 두 낡음이 더해진다.
- **원본의 부하를 줄이려는 것과 지연을 줄이려는 것은 다르다.** 원본의 부하만 문제면 B 로 충분하다. 응답 지연까지 줄이려면 왕복이 없는 D 나 E 가 필요하고, 그 대가로 서버 사이 차이를 받는다.

## 4. 선택 가이드

| 상황 | 추천 |
|---|---|
| 읽기량이 적고 응답 지연에 여유가 있음 | A. 원본 직접 |
| 낡은 값으로 응답하면 안 됨 | A. 원본 직접 |
| 쓰고 바로 읽는 흐름 | A. 원본 직접 |
| 원본의 부하만 줄이면 됨. 모든 서버가 같은 값을 봐야 함 | B. 분산 캐시 + 만료 |
| B 에 더해 바뀐 것을 곧 반영해야 함. 바꾸는 쪽이 한 곳임 | C. 분산 캐시 + 무효화 |
| 응답 지연을 없애야 함. 얼마간 뒤처져도 됨 | D. 서버 메모리 + 만료 |
| D 가 필요하나 뒤처지는 동안의 손실이 큼 | E. + 알림 무효화 |
| 모든 요청이 같은 값을 봐야 하고 지연도 없애야 함 | 없다. 둘은 함께 얻지 못한다. 어느 쪽을 포기할지 정한다 |

## 5. 적용 범위

기준은 데이터 종류가 아니라 **그 값이 낡았을 때 무엇이 잘못되느냐, 그리고 서버마다 달라도 되느냐**다. 아래 조건을 만족하는지에 따라 쓸 수 있는 방식이 정해진다.

### 5.1 방식별 필요 조건

| 조건 | A. 원본 직접 | B, C | D, E |
|---|---|---|---|
| 1. 낡은 값으로 응답해도 됨 | 불필요 | **필요** | **필요** |
| 2. 방금 쓴 값을 직후에 읽지 않음 | 불필요 | **필요** | **필요** |
| 3. 서버마다 값이 달라도 됨 | 불필요 | 불필요 (모든 서버가 같은 캐시를 본다) | **필요** |
| 4. 바꾸는 쪽이 캐시를 지울 수 있음 | 불필요 | C 에 필요 | E 에 필요 |
| 5. 원본이 멈춘 동안에도 응답해야 함 | 쓸 수 없다 | 캐시에 있는 동안 된다 | 들고 있는 동안 된다 |

A 는 조건이 없어 적용 범위가 가장 넓고 비용도 가장 크다.
B 와 C 는 서버 사이 차이가 없어야 할 때 쓴다. D 와 E 는 그 차이를 받는 대신 왕복을 없앤다.

### 5.2 데이터별 적용 여부

O: 적용 가능, △: 가능하나 이점이 적거나 조건이 붙음, X: 적용 불가

| 데이터 | A | B, C | D, E | 비고 |
|---|---|---|---|---|
| 그날의 광고 후보 목록 | △ | O | O | 하루 한 번 적재되고 그 뒤로는 상태만 바뀐다. 요청마다 범위 조회면 부하가 크다. 소진 반영이 늦으면 그 동안의 노출이 과금될 수 있어 상한을 짧게 두거나 E 로 알린다 |
| 회원의 기본 정보 | O | O | O | 바뀌는 일이 드물다. 본인이 방금 바꾼 뒤의 첫 요청은 2번 조건에 걸린다 |
| 사용자가 저장한 필터 | O | O | X | 본인이 바꾸고 바로 다시 본다. 서버마다 다르면 바꾼 것이 사라져 보인다 |
| 추천이나 순위의 입력이 되는 집계 | △ | O | O | 근사치로 써도 결과가 조금 달라질 뿐이다. 요청마다 집계하면 원본이 버티지 못한다 |
| 한도나 상한을 판정하는 카운터 | O | O | △ | 낡은 동안 상한을 넘겨 통과시킬 수 있다. 넘긴 몫을 받아들일 수 있을 때만 D, E |
| 잔액이나 재고의 판정 | O | X | X | 낡은 값으로 판정하면 없는 것을 내준다. 원자 연산으로 판정하고 그 결과로 응답한다 |
| 권한과 역할 | O | △ | X | 거둔 권한이 남아 있으면 안 된다. B 와 C 는 폐기를 즉시 반영할 길이 있을 때만 |
| 다른 도메인의 진행률이나 상태 | 그쪽이 정한다 | △ | △ | `contract` 호출이다. 다시 캐시하면 두 낡음이 더해진다. 그 값으로 돈을 판정하면 다시 캐시하지 않는다 |
| 세션이나 단기 발급 기록 | - | - | - | 그 저장소가 원본인 경우가 많다. 그때는 이 표의 대상이 아니다(3장 첫 항목) |
| 쓰는 쪽이 올려 두는 카운터나 집계 | O | - | - | 읽어서 채우는 캐시가 아니라 B~E 에 들어가지 않는다. 비면 틀린 값이 돌아오므로 원본에서 다시 세는 길을 함께 둔다(3장 둘째 항목) |

### 5.3 데이터 종류에 따라 달라지는 점

- **낡음의 대가가 돈인지 모양인지**: 과금이나 재고가 걸리면 낡은 동안의 몫을 세어 상한을 정한다. 카드 순서나 추천 인원처럼 모양만 달라지면 상한을 넉넉히 둔다.
- **누가 바꾸는지**: 사용자가 자기 값을 바꾸면 2번 조건(쓰고 바로 읽기)과 3번 조건(서버 사이 차이)이 함께 걸린다. 운영자나 배치가 바꾸면 둘 다 걸리지 않아 D 와 E 를 쓸 수 있다.
- **무효화를 보낼 쪽이 있는지**: C 와 E 는 바뀌는 순간을 아는 코드가 있어야 한다. 외부에서 바뀌거나 만료로만 변하는 값에는 보낼 쪽이 없어 B 나 D 에 머문다.
- **되돌릴 수 있는지**: 낡은 값으로 내준 것이 되돌릴 수 없으면(발급, 차감) 상한을 두는 것으로 모자라고 A 나 원자 연산으로 간다.

## 6. 한 왕복으로 묶기

여러 읽기를 한 왕복으로 묶는 것은 **낡음을 바꾸지 않고 지연만 줄인다.** 그래서 위 축에 글자를 주지 않는다. 캐시의 파이프라인이나 DB 의 `IN` 조회가 그것이다.

- 어느 방식과도 함께 쓴다. B~E 에서 캐시 읽기 여러 개를 묶고, A 에서 DB 읽기를 묶는다.
- **실패가 묶음 단위로 온다.** 하나만 실패해도 묶음 전체가 실패하는 구현이면 그 전체에 우회값을 쓴다. 왕복 하나가 줄어드는 것과 실패 단위가 커지는 것을 함께 받는다.
- 묶으려면 그 읽기들이 서로의 결과에 기대지 않아야 한다. 앞의 결과로 뒤의 키를 만드는 읽기는 묶지 못한다.
