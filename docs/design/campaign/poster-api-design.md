# 포스터 (poster) API 설계

템플릿 관리 API와 점주의 포스터 생성 API, 사용자용 포스터 조회 API를 서버가 어떻게 처리하는지와 그렇게 정한 이유를 적는다. 요청, 응답, 오류는 명세서 `poster-api-spec.md` 에 있고 여기서는 반복하지 않는다.

| 근거 | 기준 |
|---|---|
| 요구사항(템플릿 관리) | 명세서 기능 FR-011~FR-016(생성, 수정, 목록, 버전별 임시저장, 게시, 활성화 관리) |
| 요구사항(점주의 포스터 생성) | V51 54행(FR-051, #376) |
| 요구사항(사용자용 포스터 조회) | `#198` 가게 도메인 요청 2번, 가게 담당 회신(2026-10-13). FR-071(가게 상세 조회) |
| 저장 구조 | `db/migration/campaign/` 의 `V1`, `V4`~`V6`: `template`, `template_version`, `template_quota`, `poster` |
| 설계 | `../../architecture/런치캐치_도메인_구조와_의존성_설계.md` 1.2절(포스터·템플릿은 캠페인 애그리거트가 흡수) |

## 템플릿 생성 · 수정

- LLM 호출은 트랜잭션 밖에서 한다(재시도 1회까지 포함해 최대 60초 걸릴 수 있어 트랜잭션을 길게 잡지 않는다)
- `requestId` 로 재시도를 식별한다. 같은 `requestId` 가 이미 저장된 버전에 있으면 LLM 을 다시 부르지 않고 그 결과를 그대로 돌려준다
- 관리자 1명당 생성·수정을 합쳐 분당 3회로 제한한다(`TemplateGenerationRateLimiter`). `requestId` 멱등성은 같은 요청의 네트워크 재시도만 막고, 관리자가 매번 새 `requestId`로 "다시 생성"을 반복 누르는 건 못 막는다. `AuthRateLimitFilter` 와 같은 고정 창 Redis 카운터(`auth_rate_limit.lua` 재사용)를 쓰되, 그쪽은 인증 전 IP 기준 필터인 반면 여기는 인증된 관리자 ID 기준으로 서비스 계층에서 센다. Redis 장애 시에는 세지 못할 뿐 막을 이유가 없어 통과시킨다(`장애_처리_설계_가이드.md`, 캐시 기본 처리)
- 같은 `requestId`가 저장되기 전에(= LLM 호출이 끝나기 전에) 다시 들어오면 `TemplateVersionRepository.findByRequestId` 조회가 둘 다 비어 있어 속도 제한을 두 번 세게 된다(코드래빗 리뷰로 찾음). `requestId`별로 Redis `SETNX`(TTL 60초)로 "이미 처리 중인 requestId인지"를 먼저 표시한다. TTL 60초는 이 LLM 호출의 실제 worst-case다(`BedrockConfig.API_CALL_TIMEOUT` 30초 x `BedrockTemplateHtmlGenerator`의 재시도 포함 최대 2회 호출)
- 이미 처리 중인 `requestId`면 속도 제한 횟수를 세지 않고 `POSTER-004`로 바로 거부한다. 조용히 통과시키면 호출한 쪽이 LLM을 또 불러 과금과 외부 호출이 중복된다(코드래빗 리뷰로 찾음). 저장 시점 `request_id` UNIQUE 제약은 중복 저장만 막을 뿐 중복 호출 자체는 못 막아서, 여기서 미리 막는 게 더 싸다
- 표시는 제한을 통과한 요청에만 남긴다. `isOverLimit`이 거부로 판정되면 방금 세운 표시를 바로 지운다(코드래빗 리뷰로 찾음). 안 지우면 거부된 요청의 재시도가 "이미 표시 있음"으로 `isOverLimit` 자체를 건너뛰어 제한을 우회한다. 지우는 순간과 완전히 동시에 들어온 재시도까지 막는 건 아니지만, 그 틈은 저장 시점 DB UNIQUE로 거르는 기존 경쟁과 같은 급이라 별도 락을 걸지 않는다
- 수정은 `findByIdForUpdate` 로 행 잠금을 잡고 버전 번호를 매긴다. 동시에 같은 템플릿을 수정하는 두 요청이 같은 번호를 매기는 경쟁을 막는다
- 정화(허용 태그/속성만 남김) → 슬롯 검증(필수 슬롯 존재) → 구조 검증(수정 시, 이전 버전과 슬롯 태그가 같은지) 순으로 검사한다
- **버전은 템플릿 한 개당 20개까지만 보존한다(`#410`).** 저장(위 잠금 안)과 같은 트랜잭션에서, 20개를 넘기면 가장 오래된 살아있는 버전 하나를 소프트삭제한다. 가장 오래된 버전을 찾는 조회(`findFirstByTemplateIdAndDeletedAtIsNullOrderByVersionNumberAsc`)와 (최신 번호 - 그 번호 + 1)의 비교로 판정해, 살아있는 개수를 세는 별도 집계 쿼리를 두지 않는다. DRAFT 동안 지워지는 버전은 항상 이 한 개뿐이라(게시 시의 전체 삭제와 다름) 살아있는 버전 사이에 빈틈이 없다는 것이 그 계산의 전제다
- **LLM 의 설명(`message`)을 버전마다 저장한다(`#516`).** LLM 은 짧은 설명 1~2문장과 ```html 코드펜스를 함께 답하고, 코드펜스 안은 HTML 로 밖은 `message` 로 나눈다. 코드펜스가 없으면 `message` 는 빈 문자열이다. `message` 는 정화와 슬롯 검증을 거치지 않은 LLM 문장이라 프론트가 HTML 이 아닌 텍스트로 보여줘야 한다. `template_version.message` 에 저장해 생성, 수정 응답과 버전 목록 응답이 같은 값을 돌려준다. 컬럼을 추가하기 전에 만든 버전은 `NULL` 이고 응답에서는 빈 문자열이다. 실패한 요청은 저장하지 않는다. 출력 토큰 상한(4000)은 그대로라 설명이 길수록 잘림 위험이 커지므로 프롬프트에서 설명을 1~2문장으로 제한한다
- **퀵 리플라이 제안(`suggestedPrompts`)은 모델이 이번 요청과 결과에 맞춰 만든다(`#732`, 고정 목록으로 내려주던 `#522`와 문구 규칙 `#308`을 대체).** 서버 고정 5문장은 항상 같아 요청과 맞지 않았다. 별도 모델 호출은 비용과 지연이 늘어 하지 않고, 같은 LLM 호출의 출력에 후속 제안을 함께 쓰게 한다. 출력 순서는 설명, "[제안] ..." 줄, HTML 코드펜스이고, 제안을 HTML 앞에 두어 출력이 잘려도 제안이 남게 한다
- **제안 내용 규칙.** 방금 요청으로 바꾼 속성(글자 크기, 색, 모서리 등)을 더 조정하는 제안만 한다. 양은 "조금 더 크게", "한 단계 작게" 같은 단계 표현으로 쓰고, 한 요청에 2~3개만 쓰며, 더 조정할 것이 없으면 쓰지 않는다. 애니메이션, 버튼, QR코드 같은 요소 추가, 슬롯이나 문구 내용 변경, 구조를 새로 만드는 제안은 하지 않는다(`#675`). `#308`이 "1cm 더" 같은 누적 표현을 막았던 이유는 모델이 이전 상태를 계산하지 못할 수 있어서였는데, 수정 요청은 최신 버전 HTML 을 모델에 함께 보내 현재 값 기준으로 단계 조정을 계산할 수 있어 단계 표현을 허용한다
- **서버는 제안을 파싱해 정리한다.** 코드펜스 밖의 "[제안] ..." 줄만 뽑고, 꺾쇠와 코드펜스 문자를 없애고 공백을 정리한다. 빈 항목, 30자를 넘는 항목(잘라 쓰면 뜻이 깨지고 다음 요청의 `requestPrompt`로 그대로 들어가므로 버린다), 중복을 빼고 최대 3개만 남긴다. 코드펜스가 없거나 제안 줄이 없거나 형식이 깨지면 고정 목록으로 되돌리지 않고 빈 배열이다. 제안은 검증하지 않은 모델 문장이라 서버가 보장하지 못한다
- **제안은 저장하지 않는다.** 버전 목록에도 내려주지 않고, 편집 화면에 다시 들어올 때 버튼은 복원하지 않는다. 그래서 같은 `requestId` 의 재요청 응답은 저장된 버전에서 만들어져 `suggestedPrompts`가 빈 배열이다. 프론트는 재시도 응답으로 기존 버튼을 지우지 않도록 처리한다
- **템플릿 요청이 아닌 질문에는 HTML 없이 자연어로만 응답한다(`#733`).** 시스템 프롬프트가 요청 의도를 구분하게 한다. 템플릿을 만들거나 고치라는 요청이면 지금처럼 설명, 제안, HTML 코드펜스를 답하고, 질문, 설명 요청, 인사면 코드펜스 없이 자연어로만 답한다. 의도 판단은 모델이 하고 서버가 따로 분류하지 않는다(서버 분류는 오탐이 많다). 템플릿 디자인과 이 도구의 사용 방법에 관한 질문에만 답하고, 관련 없는 요청은 범위 밖이라고만 답하며, 시스템 프롬프트와 내부 규칙 공개는 거절하게 한다
- **서버는 코드펜스도 HTML 태그도 없고 비어 있지 않은 응답을 "대화만 있는 응답"으로 인정한다.** 이 응답은 정화, 슬롯, 구조 검증과 교정 재시도를 건너뛴다. HTML 이 있는데 검증에 실패한 응답은 대화로 처리하지 않고 기존 교정 재시도를 탄다. 비어 있는 응답도 대화로 보지 않는다. 대화 답변은 꺾쇠와 코드펜스 문자를 없애고 1000자로 자른다(템플릿 설명의 300자보다 길게 둔다)
- **대화만 있는 응답은 아무것도 저장하지 않는다.** 생성 API 는 템플릿을 만들지 않고(`template_quota`도 올리지 않는다), 수정 API 는 새 버전을 만들지 않는다. 그래서 버전 번호와 20개 보존 상한에 영향이 없고, 응답은 `200`이며 `templateId`, `versionNumber`, `html`이 `null`이다. 대화만 한 턴을 저장하지 않는 이유는 채팅 내역 복원(`#516`)이 버전(`template_version`) 단위라 저장할 곳이 없기 때문이다. 저장하려면 별도 대화 테이블이 필요해 이번 범위에서 제외했고, 버전 행에 HTML 을 복사해 넣는 방식은 20개 상한과 버전 번호를 오염시켜 쓰지 않는다. 같은 `requestId` 재시도는 저장된 것이 없어 모델을 다시 부르고, 처리 중 표식은 풀어 재시도가 `POSTER-004`로 막히지 않게 한다
- **한계.** 모델이 수정 요청을 대화로 오판해 HTML 을 주지 않거나, 질문에 HTML 을 줄 수 있고 서버가 검증하지 못한다. 오판하면 관리자가 다시 요청한다. 대화만 있는 응답도 모델을 호출하므로 입력 검증(`#428`)과 분당 3회 제한(`#227`)을 그대로 거친다. 템플릿 개수 한도에 닿은 상태의 생성 요청은 모델을 부르기 전에 거부되므로 대화 질문도 `POSTER-003`으로 거부된다

- **버전 번호는 앞으로 당기지(재배치) 않는다.** `TemplatePublishRequest.versionNumber`(관리자가 직접 지정)와 버전 목록의 커서 페이지네이션이 번호를 고정 식별자로 쓴다. 번호를 당기면, 관리자가 화면에서 본 번호와 그 사이 밀려 바뀐 번호가 어긋나 다른 내용을 게시하거나 다른 페이지를 보게 된다. 번호는 계속 증가하고 지워진 번호는 다시 쓰지 않는다

- **요청 문구(`requestPrompt`)를 모델에 보내기 전에 서버가 코드로 거른다(`#428`).** 모델이 규칙을 지킬 거라 믿을 수 없는 안전 문제는 `TemplatePromptValidator`가 결정적으로 차단한다. 걸리면 Bedrock을 부르지 않아 비용도 들지 않는다. 사유마다 오류 코드가 달라 프론트가 구분해 안내한다: `POSTER-022` 너무 짧음(글자나 숫자 2자 미만, 자음 모음 낱자는 세지 않음), `POSTER-023` 제어 문자와 서식 문자(zero-width, 방향 전환 등), `POSTER-024` 프롬프트 인젝션 패턴, `POSTER-025` 개인정보 형식(전화, 사업자, 주민, 카드번호, 이메일)
- **검사 순서는 숨은 문자 → 짧음 → 인젝션 → 개인정보다.** 숨은 문자를 먼저 거부해야 zero-width 문자를 끼워 뒤의 검사를 피하는 시도를 막는다. 뒤의 검사는 NFKC 정규화와 소문자 변환, 공백 정리를 거친 문구로 한다. 저장하는 원문은 바꾸지 않는다
- **인젝션 패턴은 리소스 파일이다**(`campaign/prompt/injection-patterns.txt`). 파일이 없거나 비면 서버가 뜨지 않는다. 정상 요청이 걸리지 않도록 "이전 설정 무시" 같은 흔한 표현은 패턴에 넣지 않았다. 패턴이 완전하지 않아 우회될 수 있어 이 검사만 믿지 않고, 출력 쪽 정화와 슬롯 검증이 그대로 뒤를 받친다
- **거부된 요청도 분당 3회 제한에 센다.** 비용이 들지 않는 거부 응답으로 우회 패턴을 무제한 시험하지 못하게 하려는 것이다. 다만 모델을 부르지 않았으므로 같은 `requestId`의 "처리 중" 표식은 풀어, 문구를 고친 재요청이 `POSTER-004`로 막히지 않게 한다
- **욕설 검사는 두지 않는다(`#428`).** 템플릿 요청은 인증된 관리자만 보내고, 요청 문구는 모델 입력과 `request_prompt` 저장에만 쓰이며 포스터에 노출되지 않는다. 포스터에 보이는 텍스트의 금지 표현은 자동 검수가 따로 거른다. 모델 출력 쪽 안전은 가드레일 연결로 다룬다
- **범위 밖(`#428`)**: 수정 요청이 전체 디자인을 바꾸는 문제(A-5)와 브랜드 모방(A-8)은 이번에 다루지 않는다. 포스터 내용 요청(A-1), 지원하지 않는 기능(A-3), 충돌 요청(A-4)은 시스템 프롬프트와 응답 설명(`message`)으로 안내하는 2차에서 다룬다

- **반영하지 못한 요청은 응답 설명(`message`)으로 안내한다(`#675`).** 포스터 내용(가게명, 메뉴, 할인)을 요청한 경우(A-1), 쓸 수 없는 요소(애니메이션, 버튼, QR코드, 로고 등)를 요청한 경우(A-3), A4 비율과 충돌하는 요청(A-4)은 템플릿에 반영하지 않고, 시스템 프롬프트가 모델에게 무엇을 반영하지 못했는지 설명에 한 문장으로 밝히게 한다. 반영하지 못한 요청이 없으면 이런 문구를 쓰지 않게 한다
- **이 안내는 서버가 검증하지 못한다.** 입력 검증(`#428`)과 달리 모델이 프롬프트를 따르는지에 달려 있어, 서버는 거부하거나 보장하지 않는다. 단위 테스트는 프롬프트에 지시가 들어 있는지까지만 확인하고, 실제 효과는 개발 서버에서 시나리오별로 호출해 확인한다. 설명은 100자 이내로 쓰게 하고(`message`는 서버가 300자로 자르고 꺾쇠를 제거한다), 지시가 길어져 출력 토큰 상한(4000) 안에서 `GENERATION_TRUNCATED`가 늘지 않는지 함께 본다. 수정 요청에서 전체 디자인이 바뀌는 문제(A-5)와 브랜드 모방(A-8)은 다루지 않는다

## 템플릿 삭제

**서버가 하는 일**

1. `findByIdForUpdate` 로 행 잠금을 건다. 게시(`TemplatePublishService.publish()`)와 수정 저장(`TemplateReviseService.save()`)도 같은 잠금을 쓰기 때문에, 삭제 중인 템플릿을 동시에 게시하거나 수정하는 경쟁에서 한쪽이 끝날 때까지 다른 쪽이 기다리게 된다
2. `DRAFT` 가 아니면(`PUBLISHED`) `POSTER-006`(`TEMPLATE_NOT_DRAFT`)으로 거부한다. 수정이 쓰는 오류 코드를 그대로 재사용한다
3. 그 템플릿의 버전 전부를 JPQL 벌크 `DELETE` 로 먼저 하드삭제하고, 템플릿 행을 하드삭제한다. 같은 트랜잭션에서 `template_quota.current_count` 를 1 줄인다(`TemplateQuotaRepository.release()`)

**정한 이유**

- **버전은 20개 상한(`#410`) 안이라 엔티티로 하나씩 지우지 않고 벌크 `DELETE` 한 번으로 지운다.** 템플릿 게시 때의 버전 소프트삭제(`softDeleteAllByTemplateId`)와 같은 이유다
- **버전을 템플릿보다 먼저 지운다.** `template_version.template_id` 가 FK 로 `template` 을 가리켜서, 순서를 바꾸면 템플릿 행이 먼저 없어진 뒤 그 FK를 못 지운다
- **`template_quota.current_count` 를 줄이는 조건부 `UPDATE`(`release()`)를 새로 둔다.** 지금까지 이 카운터는 늘어나기만 했다(`TemplateQuotaRepository.tryReserve`). 삭제로 줄이지 않으면 실제 템플릿 개수가 상한 미만으로 내려가도 생성이 영구히 거부된다. `tryReserve` 와 같은 조건부 `UPDATE` 모양으로 둬, 읽어서 빼고 저장하는 방식의 레이스를 피한다
- **삭제 도중이나 삭제 뒤에 들어온 수정 요청은 따로 처리하지 않는다.** `TemplateReviseService.save()` 가 LLM 호출을 끝내고 저장 단계에서 같은 잠금(`findByIdForUpdate`)을 기다렸다가 들어오면, 그 시점엔 템플릿이 이미 없어 `findByIdForUpdate` 가 빈 값을 돌려주고 그대로 `POSTER-005`(`TEMPLATE_NOT_FOUND`)로 끝난다. 삭제 쪽이 수정 쪽의 존재를 알거나 막을 필요가 없다
- **`POSTER-006` 메시지를 "게시된 템플릿은 수정하거나 삭제할 수 없습니다"로 넓힌다.** 수정과 삭제가 같은 조건(`DRAFT` 아님)과 같은 코드를 쓰므로 오류 코드를 새로 만들지 않는다
- **동시성 테스트는 실제 스레드 경쟁을 만들지 않고, `findByIdForUpdate` 호출 여부(`verify`)까지만 확인한다.** 게시·활성화와 같은 기존 테스트 관례다

## 템플릿 목록 · 상세 조회

**서버가 하는 일**

1. 목록은 `createdAt` 내림차순 전체 조회다. 템플릿 개수에 상한(현재 100개, `#532`)이 있어 페이지네이션을 두지 않았다(비기능 제약이 아니라 업무 규칙상 상한). 상한이 10개일 때는 DRAFT 템플릿마다 최신 버전을 따로 조회해도 쿼리가 11번이었으나, 100개가 되면서 최신 버전을 한 번에 조회하도록 바꿨다(`findLatestAliveByTemplateIds`). 응답 크기는 템플릿 수에 비례해 커진다
2. 목록과 상세 모두 `html` 미리보기를 포함한다. `status` 가 `PUBLISHED` 면 `template.html_content`(게시 시 복사된 값), `DRAFT` 면 최신 임시저장 버전의 `html_content` 다

**정한 이유**

- **목록에도 미리보기 html을 넣는다(FR-013 "게시된 템플릿은 확정 버전을, 임시저장중인 템플릿은 최신 임시저장 버전을 미리보기로 표시").** 상세는 `htmlOf`로 템플릿 하나의 분기를 처리하고, 목록은 같은 분기(게시본은 `htmlContent`, DRAFT는 살아있는 최신 버전)를 DRAFT 템플릿의 최신 버전 일괄 조회로 채운다. 템플릿 개수 상한이 100개라 목록 전체에 미리보기를 포함하면 응답이 커질 수 있으나 현재 규모에서는 감당할 수준으로 본다
- **서버 검색·정렬·필터를 지원하지 않는다.** 템플릿 개수에 상한(현재 100개)이 있어 화면에서 처리하기로 최종 결정했다
- **`usageCount`(이 템플릿으로 만든 포스터 수)는 이번 범위에서 뺐다.** `poster` 도메인에 아직 코드가 없어 셀 데이터 소스가 없다. 항상 `0`을 내려주면 "진짜 0개"와 "집계 미구현"을 프론트가 구분할 수 없어, 포스터 도메인이 생기는 이슈에서 필드를 추가하기로 했다
- **`lastModifiedBy`/`lastModifiedAt` 은 `template` 테이블에 즉시 복사해 둔다.** 게시하는 순간 `template_version`이 소프트삭제되고 배치가 하드삭제하므로, `template_version` 쪽에만 수정자를 두면 게시된 템플릿은 조회 즉시 "수정자 없음"이 된다

## 템플릿 버전 목록 조회

- 소프트삭제(`deleted_at`)된 버전은 제외한다. 게시한 템플릿은 모든 버전이 삭제돼 있어 빈 배열이 된다
- 커서는 `versionNumber` 값 하나만 쓴다. 템플릿 안에서 유일하고 단조증가라 동점 처리용 키가 따로 필요 없다. 

## 템플릿 게시 · 활성화 관리

**서버가 하는 일**

1. 게시는 `findByIdForUpdate` 로 행 잠금을 잡는다. 수정(`TemplateReviseService.save()`)도 같은 잠금을 쓰기 때문에, 수정 중인 템플릿을 동시에 게시하거나 게시 중인 템플릿을 동시에 수정하는 경쟁에서 한쪽이 끝날 때까지 다른 쪽이 기다리게 된다
2. 게시할 버전을 먼저 조회한 뒤에(`findByTemplateIdAndVersionNumberAndDeletedAtIsNull`) 템플릿의 모든 버전을 소프트삭제한다(`softDeleteAllByTemplateId`, JPQL 벌크 `UPDATE` 한 번). 순서를 바꾸면 벌크 삭제가 먼저 끝나 버전 조회가 `deletedAt is null` 조건에 걸려 아무것도 못 찾는다
3. 버전의 하드삭제는 이번 범위에 없다. 별도 이슈([Feat] 템플릿 버전 삭제 배치)에서 다룬다
4. 활성화는 단일 엔티티의 플래그만 바꾸는 작업이라 잠금이 필요 없다. `findById` 로 가져와 상태(`PUBLISHED`)만 확인하고 바꾼다

**정한 이유**

- **게시/활성화 둘 다 `@Transactional` 을 메서드에 직접 붙인다.** 생성·수정은 LLM 호출(재시도 포함 최대 60초)을 트랜잭션 밖에 두려고 `TransactionTemplate` 으로 트랜잭션 구간을 손으로 나눴지만, 게시·활성화는 외부 호출이 없어 메서드 전체가 짧게 끝난다. 나눌 구간이 없으니 `@Transactional` 로 충분하다
- **게시 시의 버전 소프트삭제는 엔티티를 불러오지 않고 JPQL 벌크 `UPDATE` 로 처리한다.** 템플릿 한 개의 버전은 최대 20개뿐이지만(`#410`), 엔티티로 하나씩 불러와 바꾸면 버전마다 `UPDATE` 가 나가고 쓰지 않을 `html_content`(TEXT)까지 메모리로 읽는다. 벌크 `UPDATE` 는 버전이 몇 개든 쿼리 한 번이다. 수정 시 상한을 넘겨 지우는 버전은 항상 하나뿐이라 그쪽은 `id` 하나를 지정한 `UPDATE` 다
- **동시성 테스트는 실제 스레드 경쟁을 만들지 않고, `findByIdForUpdate` 호출 여부(`verify`)까지만 확인한다.** 레포지토리 레벨의 실제 락 대기를 검증하는 통합테스트가 지금 레포에 없어, 기존 테스트 관례와 맞춘다

## 점주 템플릿 목록 조회

**서버가 하는 일**

1. `status = PUBLISHED`이고 `active = true`인 템플릿만 `createdAt` 내림차순으로 조회한다
2. 점주 전용 응답(`templateId`, `name`, `html`)으로 매핑한다. `html`은 게시 시 확정된 `template.html_content`를 그대로 쓴다(게시된 템플릿만 대상이라 관리자 목록의 DRAFT 분기가 필요 없다)

**정한 이유**

- **관리자 목록(`TemplateListItemResponse`)을 재사용하지 않고 점주 전용 응답을 새로 둔다.** 관리자 전용 필드(`status`, `active`, `activatedBy`, `activatedAt`, `lastModifiedBy`, `lastModifiedAt`)를 점주에게 노출할 이유가 없다. `status`/`active`는 이미 필터링된 뒤라 값이 항상 같아 의미가 없고, 나머지는 관리자 내부 감사 정보다
- **서버 정렬/필터를 두지 않는다.** 관리자 목록과 같은 이유(템플릿 개수 상한)가 그대로 적용되고, 점주 목록은 거기서 PUBLISHED+active만 추려서 개수가 더 적다
- **권한은 OWNER 역할만 확인한다. 점주 상태(ACTIVE) 게이트는 걸지 않는다.** 캠페인 등록 1단계(FR-040)는 점주 상태가 ACTIVE가 아니면 `CAMPAIGN-001`로 막지만, 이 조회는 부작용이 없는 단순 조회라 같은 게이트를 걸 이유가 약하고 걸면 `POSTER-` 전용 403 오류 코드를 새로 추가해야 한다. 단순함을 택해 `ONBOARDING` 상태 점주도 조회를 허용한다
- **새 오류 코드를 추가하지 않는다.** 경로 파라미터가 없어 404 대상이 없고, 활성 템플릿이 없는 경우는 오류가 아니라 빈 배열(성공)이다. 역할 실패는 기존 공통 403 처리로 충분하다

## 포스터 생성

**서버가 하는 일**

1. 업로드 presign(`prepareUpload`)과 생성(포스터 본체) 둘로 나눈다. store의 가게 이미지
   업로드(#375, #389)와 달리 별도의 `confirmUpload` 엔드포인트를 두지 않는다. 업로드가 실제로
   끝났는지는 생성 요청 시점에 `S3Client.headObject`로 한 번만 확인한다. 그래서 중간 상태를
   들고 있는 엔티티(`StoreMenuImage`에 대응하는 것)가 없다. `objectKey`는 `prepareUpload`가
   `campaigns/{campaignId}/poster/{uuid}.{ext}`로 미리 만들어 응답으로만 돌려주고, 아무것도
   저장하지 않는다
2. 생성은 캠페인 조회(소유권·`DRAFT` 확인) → 템플릿 조회(게시·활성 확인) → `headObject` 확인
   → 캠페인 잠금 재확인 → 렌더링·저장 순서다. `headObject`는 DB 트랜잭션 밖에서 부른다
   (`DI-4-02`, #389 `confirmMenuImageUpload`와 같은 근거). 외부 호출 뒤에는
   `findByIdForUpdate`로 캠페인 잠금을 다시 잡고 `DRAFT` 상태를 재확인한다. 그 사이 다른 요청이
   캠페인 상태를 바꿨을 수 있어서다
3. `eventName`은 `store.contract.StoreQueryService.findAllById`로 읽은 가게명, `discount`는
   캠페인의 할인 대상·방식·값으로, `period`는 캠페인의 쿠폰 사용 가능 시간으로 서버가 문구를 만든다(`매일 11:30 ~ 15:00`, `#763`). 등록 순서가 쿠폰 조건, 포스터, 노출 대상, 하루 예산과 집행 기간이라 포스터를 만들 때는 집행 기간이 아직 없을 수 있고, 쿠폰 사용 시간은 1단계에서 이미 저장되기 때문이다. 집행 기간이 없다고 포스터를 거부하지 않는다(`POSTER-020` 집행 기간 오류 코드는 지우고 뒤 번호를 당겼다). 쿠폰 사용 시간을 나중에 바꿔도 이미 만든 포스터의 기간 문구는 자동으로 바뀌지 않는다. 포스터를 다시 만들어야 반영되며, 개발 단계의 알려진 한계다
   포스터에는 광고 표시(`adLabel`)를 넣지 않기로 팀이 합의했다(`#628`). 템플릿 생성은 `adLabel`을
   넣지 않고 모델이 써 넣은 것도 지운다. 광고 표시가 들어 있는 옛 템플릿으로 포스터를 만들 때는
   `[data-slot=adLabel]`을 HTML에서 지우고 `slot_values`에도 넣지 않는다. 이미 저장된 포스터와
   템플릿은 그대로 둔다
   메뉴명은 [store 조회 결과](../store/store-query-contract.md#메뉴-조회-결과-788)의 정상 메뉴 목록에서 읽는다(#788). 데이터 오류 메뉴는 정상 목록에 없으므로 기존 `COMMON-001` 내부 오류로 포스터 생성을 거부한다.
4. 템플릿의 `html_content`를 Jsoup으로 파싱해 슬롯 4개를 찾아 값을 채우거나(텍스트), `src`
   속성을 바꾼다(이미지). 슬롯을 못 찾으면 `POSTER-001`(`SLOT_CONTRACT_VIOLATION`)을 재사용해
   던진다. 템플릿이 게시 전에 이미 슬롯 검증을 거치므로, 여기서 못 찾는 것은 그 사이 데이터가
   깨진 것으로 본다
5. `poster`는 `campaign_id`로 조회해 있으면 덮어쓰고(`overwrite`), 없으면 새로 만든다
   (`campaignId`당 1건, `uk_poster_campaign_id`)
6. `title`은 `"{가게명} - {템플릿 이름}"`으로 만들고 100자를 넘으면 자른다

**정한 이유**

- **`prepareUpload`가 아무것도 저장하지 않는다.** store의 업로드 준비(#375, #389)는 포기한
  PENDING 행을 지우고 다시 받는 처리가 필요했는데, 그건 별도 `confirmUpload` 호출이 있어
  "업로드했지만 아직 확인 안 한" 중간 상태가 실제로 존재하기 때문이다. 포스터는 생성 요청
  하나가 업로드 확인과 저장을 함께 하므로 그런 중간 상태가 없다. 상태가 없으면 지울 것도 없다
- **`title`은 가게명을 앞에 둔다(#376 이슈 댓글에서 정함, 2026-10-17).** 점주가 본인 가게를
  홍보하려고 만드는 포스터인데 템플릿 이름만으로는 어느 가게의 포스터인지 검색하거나 구분할
  수 없다
- **`discount`/`period` 문구의 정확한 표현은 이 이슈가 정한다.** 명세서 어디에도 문구 형식이
  없어 "{대상} {값} 할인", "매일 HH:mm ~ HH:mm"(`#763` 전에는 집행 기간 "MM.dd~MM.dd")로 정했다. 다른 화면이 이 문구를 그대로 참조하지
  않으므로(포스터 HTML 전용) 바뀌어도 계약 변경이 아니다
- **`objectKey`를 URL로 바꾸는 로직을 campaign 안에 따로 둔다
  (`campaign.poster.PosterImageUrlResolver`).** `store.StoreImageUrlResolver`(#375)와 코드가
  같지만, campaign은 store의 내부 클래스를 가져다 쓸 수 없다(`contract`만 참조 가능,
  런치캐치_도메인_구조와_의존성_설계.md 1.3). 두 도메인에 걸친 중복이라
  `StoreUploadSupport`(#389)처럼 공용 클래스로 뽑을 수 없어 작게 복제했다
- **외부 호출(`headObject`) 뒤 캠페인 상태 재확인은 하지만 템플릿 상태 재확인은 하지 않는다.**
  캠페인은 점주가 그 순간에도 다른 요청으로 바꿀 수 있는 대상이라 재확인이 필요하다. 템플릿은
  관리자만 바꾸고 변경 빈도가 훨씬 낮아, 요청 사이 몇 초 안에 게시 취소나 비활성화가 끼어들
  가능성을 낮게 보고 다시 조회하지 않는다

- **포스터를 만들 때 이미지 슬롯의 크기 스타일을 서버가 보정한다(`#731`).** 서버는 업로드 파일의 가로세로 크기를 제한하거나 줄이지 않고, 이미지 칸의 크기는 템플릿(LLM 이 만든 CSS)이 정한다. 큰 이미지가 칸을 밀어내 포스터가 깨지는 것을 막으려고, 렌더링할 때 `<img data-slot="image">`에 `width:100%`, `height:100%`, `min-height:0`, `object-fit:cover`를 덧씌운다. 템플릿이 이미 가진 이미지 스타일(`border-radius`, `box-shadow` 등)은 그대로 두고, 보정 속성이 이미 있으면 서버 값으로 한 번만 덮어쓴다(속성 이름은 대소문자를 구분하지 않는다). 템플릿 HTML 에서 매번 새로 렌더링하므로 덮어쓰는 포스터에서도 중복되지 않는다
- **`cover`를 쓴 이유와 한계.** 비율을 유지한 채 칸을 채우고 넘치는 부분을 자른다(왜곡 없음). `contain`은 칸에 빈 여백이 생겨 포스터가 덜 꽉 차 보여 쓰지 않았다. 가운데 기준으로 잘려 중요한 부분이 위나 아래에 있으면 안 보일 수 있다. 이 보정은 화면 표시만 바꾸고 파일 크기는 줄이지 않는다. 로딩 부담은 프론트가 올리기 전에 줄이는 것으로 다룬다. 이미 저장된 포스터 HTML 은 바꾸지 않고, 새로 만들거나 덮어쓰는 포스터부터 적용한다. 칸에 높이 기준이 없는 템플릿에서는 `height:100%`가 먹지 않으므로, 시드 템플릿은 루트를 A4 비율의 세로 flex 로, 이미지 칸을 `flex:1`로 맞췄다

## 점주용 포스터 조회

**서버가 하는 일**

1. `campaignId`로 캠페인을 조회해 본인 소유인지 확인한다(`CAMPAIGN-005`). 캠페인 상태는 확인하지 않는다.
2. `poster`를 `campaign_id`로 조회한다(`uk_poster_campaign_id`, 1:1). 없으면 `POSTER-020`.
3. 조회한 포스터의 `id`, `campaign_id`, `template_id`, `title`, `html_content`를 그대로 돌려준다. 조회 시점에 다시 렌더링하지 않는다.

**정한 이유**

- **캠페인 상태와 무관하게 조회를 허용한다.** 점주는 캠페인이 `DRAFT`인 동안 포스터를 만들고(포스터 생성 API는 `DRAFT`에서만 호출할 수 있다), 그 직후에 자신이 만든 포스터를 바로 확인해야 한다. 사용자용 조회가 `DRAFT`, `SCHEDULED`를 비공개로 두는 것은 아직 시작하지 않은 캠페인을 외부에 노출하지 않는다는 공개 범위 판단이다. 본인 소유 캠페인을 보는 점주에게는 이 판단을 적용할 이유가 없다.
- **점주 상태(ACTIVE) 게이트는 걸지 않는다.** 점주 템플릿 목록 조회와 같은 이유다. 부작용이 없는 단순 조회라 게이트를 걸 이유가 약하고, 걸면 `POSTER-` 전용 403 오류 코드를 새로 추가해야 한다.
- **응답을 포스터 생성 응답과 같은 모양으로 둔다(`posterId`, `campaignId`, `templateId`, `title`, `html`).** 캠페인 상태는 이미 `GET /v1/owner/campaigns/{campaignId}`로 조회할 수 있어 이 응답에 `status`를 중복으로 넣지 않는다. `templateId`는 점주가 같은 템플릿으로 다시 만들 때 참고할 수 있고, `posterId`는 이후 포스터 단건을 다루는 기능이 생기면 바로 쓸 수 있다.
- **포스터가 없을 때를 새 오류 코드(`POSTER-020`)로 둔다.** 사용자용 조회는 캠페인이 없는 것, 비공개 상태인 것, 포스터가 없는 것 세 실패를 하나의 404로 묶는다. 존재하지만 비공개인 캠페인 ID를 외부에서 구별하지 못하게 하려는 판단이다. 점주용은 그 전에 이미 소유권 확인(`CAMPAIGN-005`)을 통과한 뒤의 실패라, "이 캠페인에 포스터가 아직 없다"는 사실을 알려줘도 점주가 이미 아는 자기 캠페인의 정보일 뿐이다. 그래서 소유권 실패와 포스터 미생성을 구분해 알려준다.

## 사용자용 포스터 조회

**서버가 하는 일**

1. `campaignId`로 캠페인을 조회한다. 없으면 `POSTER-0xx`(아직 구현 전).
2. 캠페인 상태가 `ACTIVE`, `PAUSED`, `ENDED` 중 하나가 아니면(`DRAFT`, `SCHEDULED`) 같은 `POSTER-0xx`.
3. `poster`를 `campaign_id`로 조회한다(`uk_poster_campaign_id`, 1:1). 없으면 같은 `POSTER-0xx`.
4. `poster.html_content`를 그대로 돌려준다. 조회 시점에 다시 렌더링하지 않는다.

**정한 이유**

- **세 실패를 모두 하나의 404 코드로 묶는다.** 캠페인이 없는 것과 비공개 상태인 것을 구분해 알려주면, 존재하지만 비공개인 캠페인 ID를 외부에서 구별할 수 있게 된다. 가게 담당과 "404로 통일"을 확인했다.
- **`ACTIVE`, `PAUSED`, `ENDED`를 공개로, `DRAFT`, `SCHEDULED`를 비공개로 가른다.** 가게 상세 화면이 "지금 보여줄 수 있는 캠페인"과 "끝났지만 기존 화면·링크에서 상태를 안내해야 하는 캠페인"을 모두 포함하되, 아직 시작하지 않은 캠페인의 포스터는 공개하지 않기로 가게 담당과 정했다. 포스터 조회가 허용된다고 쿠폰 발급도 가능한 것은 아니다. 그 판정은 쿠폰 도메인이 따로 한다.
- **조회 시점에 다시 렌더링하지 않는다.** `poster.html_content`가 이미 정화와 슬롯 검증을 거쳐 저장된 값이다(템플릿 생성·수정과 같은 검증 경로). 저장된 값을 그대로 돌려주는 게 가장 싸고, 포스터 내용이 바뀌면(이번 범위 밖) 다음 조회부터 최신 값이 자동으로 보인다.
- **캠페인이 참조하는 메뉴가 바뀌어도 포스터 HTML을 다시 만들지 않는다.** 메뉴 수정 처리 기준(가게 담당 회신, `#198`)이 "메뉴 이름·가격 수정으로 캠페인 설정을 다시 저장하지 않는다"로 정해졌다. 포스터 HTML과 가게 상세가 보여주는 현재 메뉴 정보가 서로 다를 수 있다는 것도 가게가 메뉴 담당과 공유하기로 했다.
- **성능 목표를 따로 세우지 않는다.** 캠페인 하나와 포스터 하나를 PK로 조회하는 단순 조회라 관리자 전용 템플릿 API들과 같은 수준(목표 없음, 아직 트래픽 추정 근거가 없음)으로 둔다.

## 오류 코드를 나눈 기준

요청 형식(필수값, 길이)처럼 판정에 업무 지식이 필요 없는 실패는 `COMMON-002` 를 쓴다.
`POSTER-` 코드는 템플릿의 상태와 구조를 봐야 판정할 수 있는 실패에만 둔다.
