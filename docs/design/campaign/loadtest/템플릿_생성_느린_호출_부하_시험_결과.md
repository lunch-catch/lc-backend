# 템플릿 생성 느린 호출 부하 시험 결과

모델 호출이 느린 채로 여러 개 겹칠 때 동시 호출 제한(벌크헤드 `bedrock`)이 정한 대로 거절하는지, 그동안 다른 API 가 얼마나 느려지는지 잰다. 이 문서는 측정하기 전에 질문과 통과 기준을 먼저 적고, 결과는 같은 문서의 뒤쪽에 적는다.

벌크헤드를 둔 이유와 상한 5를 고른 근거는 [캠페인 장애 처리 설계](../campaign_장애_처리_설계.md)의 "외부 API: Bedrock LLM" 절이 갖는다. 상한 5는 호출이 10초 걸린다는 가정에서 나왔고 측정으로 검증하지 않았다. 이 시험의 결과로 상한 5가 적절한지 확인한다.

## 1. 질문과 통과 기준

| 번호 | 질문 | 통과 기준 |
|---|---|---|
| Q1 | 관리자 8명이 동시에 템플릿 생성을 요청하면 모델 호출은 최대 5개만 나가고 나머지는 즉시 503(`POSTER-012`)이 되는가 | 모든 회차에서 성공 응답이 5건, `POSTER-012` 응답이 3건이다. 같은 순간에 진행 중인 모델 호출은 한 번도 5개를 넘지 않는다. 거절된 요청은 모든 회차에서 1초 안에 응답을 받는다 |
| Q2 | 느린 모델 호출 5개가 진행되는 동안 다른 API 의 응답 시간이 얼마나 늘어나는가 | 생성 요청이 도는 구간에서 잰 다른 API 의 최대 응답 시간이 300ms 이하다. 이 값은 [성능 효율성 가이드](../../../software-quality/qa-performance-efficiency-guideline.md)의 목록 조회 p99 다. 같은 API 를 생성 요청 없이 잰 기준 구간의 p50, p95, 최대를 함께 적어 늘어난 폭을 보인다 |
| Q3 | 요청 스레드가 고갈되지 않는가 | 생성 구간 동안 바쁜 스레드 수(`tomcat.threads.busy`)의 최대가 톰캣 스레드 상한 200 보다 작다. 생성 구간에 시작한 다른 API 호출 가운데 시간 초과로 끝난 것이 없다 |

Q2 의 기준은 한 JVM 안에서 잰 값에 운영 환경의 목표를 그대로 대 본 것이다. 네트워크 지연이 없어서 운영보다 작게 나온다. 그래서 절대값보다 기준 구간과 생성 구간의 차이가 이 시험의 주된 판단 근거다.

작업 스레드를 기다리는 요청 수(`tomcat.threads.queued`)는 Q3 의 통과 기준으로 쓰지 않고 기록만 한다. 톰캣은 쉬는 스레드가 있어도 요청을 실행기 대기열에 넣고, 쉬던 스레드가 그 요청을 꺼내 간다(tomcat-embed-core 11.0.20 의 `TaskQueue.offer`). 그래서 스레드가 넉넉한 동안에도 대기열 길이가 잠깐 1이 된다. 이 값이 0보다 크다는 것만으로는 스레드가 고갈됐다고 볼 수 없다.

기준에 못 미치는 결과가 나오면 이 이슈에서 고치지 않고 새 이슈를 올린 뒤, 그 번호를 결과 표의 해당 줄에 적는다.

## 2. 측정 방법

측정은 통합 테스트로 돌린다. 테스트가 앱을 실제 포트(`RANDOM_PORT`)로 띄우고 HTTP 로 부른다. MockMvc 는 톰캣의 작업 스레드를 거치지 않아 Q3 을 잴 수 없다. 시나리오와 데이터 생성기를 k6 로 두지 않은 이유도 있다. 실행 중인 앱에 스텁을 꽂으려면 그 빈을 운영 코드(`src/main`)에 넣어야 한다.

### 2.1 모델 호출을 대신하는 스텁

`BedrockTemplateHtmlGenerator` 는 그대로 쓰고, 그 안에서 부르는 `BedrockRuntimeClient` 만 스텁으로 바꾼다. 벌크헤드가 생성기 안의 `converse` 호출을 감싸므로, 생성기를 `FakeTemplateHtmlGenerator` 로 바꾸면 벌크헤드도 함께 빠진다.

스텁은 정한 시간만큼 기다린 뒤 슬롯 검증을 통과하는 고정 HTML 을 돌려준다. 이 문서에 적는 모델 응답 시간은 스텁이 정한 값이며 실제 Bedrock 의 응답 시간이 아니다.

| 조건 | 스텁의 동작 | 요청 하나가 모델을 부르는 횟수 |
|---|---|---|
| 기본 | 18.5초 뒤에 정상 HTML 을 준다 | 1 |
| 교정 재시도 | 18.5초 뒤에 슬롯 검증에 걸리는 HTML 을 주고, 교정 지시가 붙은 두 번째 호출에는 18.5초 뒤에 정상 HTML 을 준다 | 2 |

18.5초는 lc-infra 의 `docs/system-design/런치캐치_LLM_Bedrock.md` 2.0절에서 Sonnet 으로 출력 약 2,600토큰을 두 번 잰 값이다.

교정 재시도는 지연을 37초로 늘린 호출 하나로 흉내 내지 않는다. 실제 SDK 는 호출 하나를 30초에서 끊으므로 37초짜리 호출은 일어나지 않는다. 그리고 벌크헤드는 생성 요청 전체가 아니라 `converse` 호출 하나마다 자리를 잡는다. 첫 호출이 끝나면 자리를 반납했다가 두 번째 호출에서 다시 잡는다. 그 사이에 다른 요청이 자리를 가져가면 두 번째 호출이 거절될 수 있고, 이 경우는 실제로 두 번 불러야 나타난다.

### 2.2 시나리오

한 회차는 아래 순서로 돈다.

1. 기준 구간: 생성 요청 없이 다른 API 를 일정한 간격으로 불러 응답 시간을 잰다.
2. 생성 구간: 관리자 8명이 템플릿 생성을 한꺼번에 요청한다. 모든 생성 요청이 끝날 때까지 다른 API 를 1과 같은 간격으로 계속 부른다.
3. 회차가 끝나면 아래 3절의 값을 기록한다.

관리자 8명은 서로 다른 계정이다. 생성 요청의 분당 3회 제한(`TemplateGenerationRateLimiter`)이 관리자 1명당이라서다. 회차마다 새 관리자를 쓰고 `requestId` 도 요청마다 새로 만든다. 관리자의 토큰은 로그인 API 를 거치지 않고 테스트에서 발급한다. 로그인 API 는 IP 1개당 분당 10회로 막혀 있어서(`AuthRateLimitFilter`), 8명의 로그인이 다른 API 측정의 로그인 호출과 같은 한도를 나눠 쓰게 된다.

다른 API 는 둘을 잰다.

| API | 고른 이유 |
|---|---|
| 관리자 템플릿 목록 조회 (`GET /v1/admin/templates`) | 생성과 같은 도메인의 DB 조회이고, 관리자가 생성 결과를 기다리며 실제로 여는 화면이다 |
| 관리자 로그인 | DB 조회에 비밀번호 해시 검증이 붙어 CPU 를 쓴다. 분당 10회 제한에 걸리지 않는 간격으로 부른다 |

### 2.3 조건과 반복

| 항목 | 값 |
|---|---|
| 관리자 수 | 8 |
| 벌크헤드 상한 | 5, 기다리지 않음(`maxWaitDuration: 0ms`) |
| 톰캣 스레드 상한 | 200 |
| 모델 응답 지연 | 18.5초. 조건은 기본과 교정 재시도 둘이다 |

`./gradlew check` 에서는 같은 테스트를 짧은 지연과 적은 반복으로 돌린다. 실행 시간을 늘리지 않으려는 것이다. 18.5초 조건은 환경변수를 줄 때만 돈다. 환경변수 이름과 기본값은 측정 테스트의 코드가 갖는다.

## 5. 결과

세 질문 모두 통과 기준을 지켰다. 기준에 못 미친 항목이 없어 새로 올린 이슈는 없다.

### 5.1 Q1. 동시 호출 제한

| 조건 | 회차 | 성공 응답 | `POSTER-012` | 그 밖의 응답 | 동시에 진행한 모델 호출의 최대 | 벌크헤드 사용 최대 | 판정 |
|---|---|---|---|---|---|---|---|
| 기본 | 10 | 회차마다 5건 | 회차마다 3건 | 0건 | 5 | 5 | 통과 |
| 교정 재시도 | 10 | 회차마다 5건 | 회차마다 3건 | 0건 | 5 | 5 | 통과 |

| 조건 | 모델 호출 수 | 벌크헤드 거절 수 | 거절 응답 p50 | 거절 응답 p95 | 거절 응답 최대 | 성공 응답 p50 |
|---|---|---|---|---|---|---|
| 기본 | 50 | 30 | 58ms | 96ms | 96ms | 18,623ms |
| 교정 재시도 | 100 | 30 | 51ms | 61ms | 64ms | 37,108ms |

거절된 요청은 모두 0.1초 안에 응답을 받았다. 기준인 1초보다 훨씬 짧다. 교정 재시도 조건에서도 동시에 진행한 모델 호출은 5개를 넘지 않았다. 첫 호출을 마친 요청이 두 번째 호출에서 거절된 경우는 0건이다. 이 시나리오에서 0건이 나오는 이유는 6절이 적는다.

### 5.2 Q2. 다른 API 의 응답 시간

| API | 조건 | 구간 | 표본 수 | p50 | p95 | 최대 |
|---|---|---|---|---|---|---|
| 목록 조회 | 기본 | 기준 | 924 | 24ms | 36ms | 118ms |
| 목록 조회 | 기본 | 생성 중 | 935 | 23ms | 35ms | 72ms |
| 목록 조회 | 교정 재시도 | 기준 | 1,850 | 20ms | 27ms | 47ms |
| 목록 조회 | 교정 재시도 | 생성 중 | 1,858 | 20ms | 27ms | 61ms |
| 로그인 | 기본 | 기준 | 28 | 150ms | 166ms | 314ms |
| 로그인 | 기본 | 생성 중 | 29 | 146ms | 180ms | 194ms |
| 로그인 | 교정 재시도 | 기준 | 56 | 135ms | 157ms | 166ms |
| 로그인 | 교정 재시도 | 생성 중 | 58 | 139ms | 153ms | 158ms |

생성 구간의 최대는 목록 조회가 72ms, 로그인이 194ms 로 기준 300ms 이하다. 판정은 통과다. 기준 구간과 생성 구간의 p50 과 p95 는 두 API 모두 몇 ms 안에서 같다. 느린 모델 호출 5개가 도는 동안 다른 API 가 느려지지 않았다.

로그인의 기준 구간 최대 314ms 는 표본 28개 가운데 1개다. 생성 요청이 없는 구간의 값이라 판정에 들지 않는다. 같은 조건의 생성 구간 최대는 194ms 다.

### 5.3 Q3. 요청 스레드

| 조건 | 바쁜 스레드 최대 | 작업 스레드를 기다린 요청 최대 (기록만) | 생성 구간의 다른 API 시간 초과 | 판정 |
|---|---|---|---|---|
| 기본 | 9 | 0 | 0건 | 통과 |
| 교정 재시도 | 8 | 0 | 0건 | 통과 |

바쁜 스레드는 상한 200 가운데 많아야 9개였다. 모델 호출이 쥔 5개와 측정용 다른 API 호출이 쓴 몇 개다. 다른 API 호출은 실패 응답 없이 모두 성공했다.

### 5.4 상한 5에 대한 판단

이 시험은 상한 5를 낮출 이유를 찾지 못했다. 느린 호출 5개가 스레드를 쥐어도 바쁜 스레드는 상한의 5%를 넘지 않았고 다른 API 는 느려지지 않았다. 스레드만 보면 상한을 올려도 여유가 크다.

한편 상한 5에서는 관리자 8명이 한꺼번에 요청한 회차마다 3명이 `POSTER-012` 를 받았다. 호출 하나가 18.5초 걸리면 자리 5개로 1분에 약 16번을 만든다. 교정 재시도가 붙으면 약 8번이다. 속도 제한이 허용하는 최대는 관리자 8명이 1분에 3번씩 보내는 24번이다.

상한을 올릴지는 이 시험만으로 정하지 않는다. Bedrock 의 호출 한도와 비용을 함께 봐야 하는데 이 시험은 둘을 재지 않는다.

## 6. 한계

- 모델 응답 시간은 스텁이 정한 값이다. 실제 Bedrock 은 요청마다 응답 시간이 다르고, 출력 길이가 길수록 늘어난다. 실제 Bedrock 을 불러 대조하는 일은 이 시험의 범위가 아니다.
- 한 JVM 안에서 서버 한 대를 잰다. 운영은 앱 서버가 여러 대이고, 벌크헤드와 톰캣 스레드는 서버마다 따로 센다.
- 스텁은 네트워크를 쓰지 않는다. 실제 호출이 쓰는 HTTP 커넥션과 응답 본문을 읽는 비용은 측정에 들어가지 않는다.
- 관리자 8명이 한꺼번에 출발한다. 자리를 얻은 5명은 첫 호출을 마치고 자리를 반납한 뒤 같은 5명끼리 다시 자리를 잡으므로, 두 번째 호출이 거절되지 않는다. 요청이 시차를 두고 들어와 다른 요청이 그 틈에 자리를 가져가는 경우는 이 시험이 만들지 않는다.
- 로그인은 분당 10회 제한 때문에 표본이 조건과 구간마다 28~58개다. 목록 조회보다 p95 와 최대가 덜 안정적이다.
