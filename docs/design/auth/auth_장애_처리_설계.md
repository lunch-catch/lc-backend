# auth 장애 처리 설계

이 문서는 공통 상수와 회원 RT 회전의 장애 처리를 다룬다. 인증 모듈 전체의 장애 시나리오는 아직 훑지 않았다. 기존 요청별 실패 처리는 [auth API 설계](./auth-api-design.md)가 갖는다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| Valkey | RT 저장·회전·폐기 | 기존 auth API 설계의 토큰 처리 절을 따른다 |
| MySQL의 회원 RT 백업 | 회원 해시의 CAS와 반영 결과 확인 | DB 반영 실패가 확인되면 이번 요청의 Redis 회전을 보상한다 |
| OAuth 등록 설정과 Kakao API | 인가·토큰 교환·ID Token 검증 | 기존 auth API 설계의 사용자 인증 절을 따른다 |

## 벗어난 것

상수 통합으로 새로 기본 처리를 벗어나는 대상은 없다. 기존 정책의 예외는 아직 전체를 훑지 않았다.

### 회원 RT의 확정 표시

DB의 새 해시가 확정된 뒤 Redis 확정 표시만 실패하면 새 토큰의 발급 성공을 유지한다. DB를 되돌리거나 새 세션을 폐기하면 이미 반영한 회전까지 잃기 때문이다. `REFRESH_ROTATION_COMPLETION_FAILED` 로그를 남기며 이 표시를 자동으로 다시 쓰지는 않는다.

확정 표시가 실패하거나 DB 반영 직후 서버가 중단되면 옛 토큰은 남은 TTL 동안 처리 중으로 남을 수 있다. 옛 토큰으로 새 토큰을 발급하지는 않지만 확정 후 재사용에 따른 전체 폐기도 실행하지 못한다. DB가 옛 해시를 유지한 것이 확인되면 기존 보상 경로가 처리 중 표시를 정상 레코드로 복구한다. 다른 요청이 활성 포인터를 바꿨거나 보상이 실패하면 해당 요청의 저장소 오류를 유지한다.

## 유형별 점검

### 캐시

| 시나리오 | 점검 결과 |
|---|---|
| 캐시 다운 | 기존 DB 폴백을 유지한다. DB 반영 뒤 확정 표시만 실패한 경우는 위의 회원 RT 확정 표시 절을 따른다 |
| 캐시 스탬피드 | 이번 변경은 TTL이나 조회 횟수를 수정하지 않는다 |
| 분산 락 | 별도 락 대신 원자적인 Lua 회전과 DB 해시 CAS를 사용한다 |
| 낡은 값 | 회원의 처리 중 표시는 이번 요청의 새 해시가 일치할 때만 확정하거나 복구한다. 관리자 키와 폐기 표시는 유지한다 |

### DB

회원 DB의 기존 CAS와 별도 트랜잭션을 유지한다. DB 실패 뒤 새 해시가 확인되면 성공시키고 옛 해시가 확인되면 Redis 회전을 복구한다. DB 장애 시나리오 전체는 아직 훑지 않았다.

### 외부 API

Kakao 등록 ID의 값과 설정 경로를 유지한다. 타임아웃·재시도·호출 차단과 외부 API 장애 시나리오 전체는 아직 훑지 않았다.

### 애플리케이션

상수 클래스는 불변 문자열만 제공한다. 회원 회전 중 서버가 중단되면 위의 회원 RT 확정 표시 절에 적힌 처리 중 상태가 남을 수 있다. 나머지 배포 시나리오는 아직 훑지 않았다.

### 롤백 안 되는 효과

상수 참조는 외부 효과를 만들지 않는다. 회원 RT의 Redis 효과는 DB와 함께 롤백되지 않으므로 위의 회원 RT 확정 표시 절을 따른다. 나머지 DB와 Valkey의 부분 실패 처리는 auth API 설계를 따른다.

## 아직 정하지 못한 것

이번 상수 통합에 남은 미정 사항은 없다. 기존 인증 정책의 미정 사항은 auth API 설계의 해당 절을 따른다.
