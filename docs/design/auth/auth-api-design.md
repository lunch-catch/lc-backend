# 인증 (auth) API 설계

인증 API를 서버가 어떻게 처리하는지와 그렇게 정한 이유를 적는다. 요청, 응답, 오류는 명세서 [auth-api-spec.md](../../api-spec/auth-api-spec.md) 에 있고 여기서는 반복하지 않는다.
명세서는 프론트가 보는 계약이고, 이 문서는 백엔드가 구현할 때 보는 문서다. 계약이 바뀌면 명세서를, 내부만 바뀌면 이 문서를 고친다.

| 근거 | 기준 |
| --- | --- |
| 요구사항 | 명세서 기능 FR-002~FR-004(관리자), FR-028~FR-031(점주), FR-059, FR-061, FR-062(사용자), FR-091(공통 토큰 정책) |

관리자 계정 발급(FR-001)은 [admin-api-design.md](../admin/admin-api-design.md), 사용자 온보딩(FR-060)과 탈퇴(FR-086)의 계약은 [member 명세](../../api-spec/member.md), 점주 회원가입·로그인·내 정보 조회·튜토리얼 완료 처리는 [owner-api-design.md](../owner/owner-api-design.md)에 있다. member의 서버 처리 설계는 PR #474가 추가하는 `docs/design/member/member-api-design.md`가 갖는다.

## 경로를 정한 기준

**경로는 동사가 아니라 리소스다.** 토큰이 리소스이고 로그인은 생성, 로그아웃은 삭제다.
표준 메서드로 표현되지 않는 재발급만 콜론 커스텀 메서드로 쓴다
(`API-3-01`, `API-3-08`, [api-design-guideline.md](../../code-convention/api-design-guideline.md)).
`/login`, `/logout` 같은 동사 경로는 그 항목에 걸린다.

사용자 로그인 경로에 `kakao` 가 들어가지 않는다. **로그인 수단이 카카오 하나로 못 박혀 있어**
토큰을 만드는 경로도 하나다. 수단을 늘릴 때 무엇을 함께 고쳐야 하는지는 아래 "사용자" 절에 적는다.

## 공통 토큰 정책 (FR-091)

`Path=/` 로 두면 안 되는 이유가 둘이다. 피드 조회처럼 Refresh 가 필요 없는 모든 요청에 14일짜리
토큰이 따라가 접근 로그와 프록시에 남는 면이 넓어진다. 그리고 쿠키 이름이 `refreshToken` 하나이므로
한 브라우저에서 역할을 바꿔 로그인하면 서로를 덮어쓴다.

`Path` 자체는 같은 오리진 안에서 격리를 보장하지 않는다. 진짜 방어는 `HttpOnly` 와
`SameSite=Strict` 이고, `Path` 는 노출 면을 줄이는 층 하나로 둔다.

끝의 슬래시가 필요하다. RFC 6265 5.1.4 의 path-match 는 쿠키 `Path` 가 요청 경로와 같거나,
`Path` 가 `/` 로 끝나거나, 요청 경로의 다음 글자가 `/` 여야 성립한다. 재발급이
`tokens:refresh` 라 다음 글자가 콜론이므로 `Path` 를 `/v1/auth/tokens` 로 좁히면
그 요청에는 쿠키가 실리지 않는다. 그래서 한 단계 위인 `/v1/auth/` 에 둔다.

- **Refresh Token의 관계형 DB 해시는 장애 시 재발급 폴백에도 사용한다.** 평상시에는 인메모리 저장소에서 토큰을 조회하고 회전한다. 캐시 조회나 회전이 장애로 실패하면 DB의 SHA-256 해시, 만료 시각과 계정 상태를 검증하고, 이전 해시가 일치할 때만 CAS로 새 해시와 만료 시각을 갱신한다. 캐시가 정상적으로 만료·폐기·재사용을 판정한 토큰에는 폴백하지 않는다. DB 해시는 로그아웃 시 폐기 대상 확인에도 사용한다.

점주 상태의 원본·캐시 조회·커밋 후 무효화·동시 변경의 한계는 [점주 상태 조회 설계](../owner/owner-status-cache.md)를 따른다. RT와 AT 폐기 정보는 상태 캐시와 별개이며 점주 토큰 처리 절에서 정의한다.

## 관리자

### 계정 발급과 로그인

[관리자 설계](../admin/admin-api-design.md)의 처리 절차와 저장 구조를 따른다.

### 토큰 재발급

1. 43자 Opaque Token 형식과 관리자 역할을 확인한 뒤 Redis를 조회한다. 캐시 조회 장애·부재 또는 회전의 타임아웃 이외 저장소 장애는 DB 백업으로 폴백한다. DB에서 해시·만료·활성 상태·관리자 역할을 검증한다
2. 새 Refresh Token으로 교체한다. **같은 토큰으로 동시에 두 요청이 와도 하나만 성공한다**
3. 이미 교체된 토큰이 다시 오면 그 계정의 Refresh Token 폐기를 먼저 커밋한다. 실패 감사 로그는 별도 트랜잭션으로 저장하며, 저장 장애는 폐기를 취소하지 않는다. 감사 저장 실패 시 관리자 ID·실패 사유를 운영 로그에 남기며 자동 재처리는 하지 않는다(FR-003)
4. 캐시 레코드가 없으면 DB의 현재 해시·만료·활성 관리자 상태를 검증해 복구한다. 캐시 회전이 정상적으로 무효·재사용을 판정한 경우에는 폴백하지 않는다
5. 회전은 로그인과 같은 관리자 행 잠금 아래 이전 해시를 비교하고 발급 순번을 증가시킨다. 성공 감사 로그도 같은 DB 트랜잭션에 저장하며, 캐시 게시는 커밋 후 순번으로 오래된 게시를 차단한다
6. 캐시 회전 타임아웃은 새 레코드를 후속 조회해 확인한 경우에만 DB 회전을 진행한다. 결과 미확정은 `503 / AUTH-002`이며 새 쿠키를 발급하지 않는다. 이 경우 기존 토큰으로 자동 반복 재시도하지 않고 다시 로그인한다

DB 회전 실패 후에는 별도 트랜잭션으로 현재 해시를 확인한다. 롤백이 확인되면 이번 회전의 캐시 상태가 그대로인 경우에만 기존 토큰을 복구한다. 새 해시의 커밋이 확인되면 성공 처리하고, 다른 로그인·폐기 또는 결과 미확정 상태에서는 기존 토큰을 복구하지 않는다. 결과 미확정은 `503 / AUTH-002`이며 다시 로그인한다.

캐시 장애·유실로 DB 폴백한 동안에는 과거 토큰의 재사용 흔적을 복원할 수 없다. 이전 해시와 일치하는 현재 토큰만 회전하며, 교체된 토큰은 거부한다.

Redis의 관리자 두 역할에 폐기 순번을 게시해 이전 로그인·회전의 지연된 게시를 막는다. 이후 더 높은 순번의 새 로그인은 허용한다. 재사용 폐기는 Refresh Token만 대상으로 하며 Access Token 폐기 기준은 갱신하지 않는다.

Redis의 재사용 기록 없이 DB 현재 해시만 불일치하면 재사용으로 확정하지 않고 무효 토큰으로 거부한다. Refresh Token 폐기 자체가 실패하면 저장소 장애로 응답한다.

## 점주

### 문서와 구현의 담당 범위

회원가입·로그인·내 정보 조회·튜토리얼 완료는 [점주 API 설계](../owner/owner-api-design.md)를 따른다. 이 절은 점주 토큰 재발급·로그아웃과 AT 폐기 검증을 정의한다. 요청·응답·오류는 [인증 명세의 점주 절](../../api-spec/auth-api-spec.md#점주)을 따른다.

점주 계정과 토큰 저장 상태는 owner가 관리한다. 재발급·로그아웃의 컨트롤러와 서비스도 owner에 둔다. auth는 공통 JWT 발급·쿠키·인증 필터와 `AccessTokenValidationPolicy` 계약을 제공한다.

### `POST /v1/owner/auth/tokens`

[점주 API 설계의 로그인 절](../owner/owner-api-design.md#로그인)을 따른다.

### `POST /v1/owner/auth/tokens:refresh`

1. `OwnerTokenRefreshService`가 Redis에서 요청 RT를 조회하고 처리 중으로 표시한다. Redis 장애일 때만 DB의 현재 RT 해시로 점주를 찾는다. 정상적으로 토큰 없음·폐기·재사용을 판정한 결과를 DB로 우회하지 않는다.
2. 독립된 트랜잭션에서 점주 행을 잠근다. DB의 RT 해시·만료 시각과 로그인 가능한 현재 계정 상태를 확인한다. 상태 캐시는 사용하지 않는다.
3. 새 RT 해시·만료 시각을 저장하고 발급 순번을 증가시킨다. 같은 순번을 AT의 `issuanceVersion` 클레임에 넣는다. 최근 로그인 시각은 변경하지 않는다.
4. DB 커밋 후 별도 트랜잭션에서 현재 상태·해시·순번을 재확인한다. DB 연결과 잠금을 반환한 뒤 `saveIfNewer`로 Redis에 새 RT를 게시한다. TTL은 DB에 저장된 만료 시각까지 남은 시간이다.
5. 기존 RT의 처리 중 표시를 재사용 감지 대상으로 확정한다. DB 커밋 후 Redis 게시만 실패하면 재발급 성공을 유지한다. 처리 중 표시가 확정되지 않으면 기존 RT는 만료까지 처리 중으로 남을 수 있다.

DB 회전에 실패하면 별도 트랜잭션과 행 잠금 아래 기존 해시가 유지되는지 확인한다. 유지되는 경우에만 Redis의 소비 표시를 복구한다. 더 최신 로그인이나 회전이 확정됐다면 이전 RT를 복구하지 않는다.

확정된 RT 재사용을 감지하면 DB에서 현재 RT를 제거하고 발급 순번을 증가시킨다. `clearRefreshToken`은 AT 폐기 순번도 함께 저장한다. 커밋 후 Redis에서 RT를 폐기하고 AT 폐기 순번을 반영한다. DB와 Redis는 하나의 트랜잭션이 아니므로 부분 실패는 명세의 저장소 오류와 복구 한계를 따른다.

### `DELETE /v1/owner/auth/tokens`

1. 공통 인증 필터와 OWNER 권한 규칙을 통과한 주체 ID를 `OwnerLogoutService`에 전달한다.
2. 독립된 트랜잭션에서 점주 행을 잠근다. Redis 삭제에 사용할 기존 RT 해시를 보관한 뒤 RT 해시·만료 시각을 제거한다. 발급 순번을 증가시키고 같은 순번을 AT 폐기 기준으로 저장한다.
3. DB 커밋 후 `OwnerLogoutTokenRepository`로 대상 RT와 이전 발급 순번을 폐기한다. 더 최신 로그인에서 발급한 RT는 유지한다.
4. `OwnerAccessTokenVersionRepository`로 Redis의 AT 폐기 순번을 반영한다. RT 폐기와 AT 차단은 한쪽이 실패해도 각각 시도한다.
5. 두 Redis 작업까지 성공한 뒤 공통 `AuthCookieFactory`로 삭제 쿠키를 만든다. 쿠키 Path와 오류 응답은 인증 명세를 따른다.

DB 커밋에 실패하면 Redis를 변경하지 않는다. Redis 반영이 실패해도 이미 커밋된 DB의 RT·AT 폐기는 유지한다. 기존 AT로는 폐기 작업을 재시도할 수 없다. 실패 작업을 영구 기록하거나 자동 복구하는 배치는 현재 없다.

### AT 폐기 순번 검증

`OwnerAccessTokenPolicy`는 공통 `AccessTokenValidationPolicy`를 구현한다. `ApiSecurityDefaults`가 등록된 정책을 JWT 필터에 전달한다. owner는 추가 클레임의 발급 순번과 폐기 순번을 비교하며 auth는 점주 엔티티를 직접 조회하지 않는다.

검증은 별도 읽기 트랜잭션으로 DB의 `access_token_revoked_version`을 먼저 조회한다. 계정이 없거나 JWT 발급 순번이 폐기 순번 이하면 인증을 거부한다. DB에서 허용된 토큰에만 Redis의 폐기 순번을 추가 검사한다.

DB 조회 장애는 일반 인증에서도 통과시키지 않는다. Redis 조회 장애의 LENIENT 정책은 DB 검증을 통과한 AT에만 적용한다. REQUIRED 검증은 저장소 장애를 호출자에게 전달한다.

발급 순번은 큰 정수의 정밀도를 유지하도록 문자열로 서명한다. 순번 없는 기존 JWT는 0으로 취급한다. 폐기 순번은 감소시키거나 만료시키지 않는다. `V4__owner_access_token_revoked_version.sql`은 기존 계정의 현재 RT 순번보다 이전인 AT를 차단한다. RT가 없는 계정은 현재 순번까지 차단한다. 기존 Redis 폐기 정보 유실로 과거 AT가 살아나는 것을 막으며 배포 후 일부 기존 세션은 재로그인이 필요하다.

## 사용자

### `GET /v1/auth/kakao/authorize`

로그인과 탈퇴 재인증은 같은 인가 흐름을 쓰며, 재인증 옵션도 서버가 관리한다.

#### 서버가 하는 일

- 서버는 충분히 예측 불가능한 `state`, `nonce`를 만들고 Redis에 `state -> nonce`를 5분 동안 저장한다. 같은 state는 원자적으로 한 번만 소비한다.
- 서버는 Redis state를 소비해 저장된 nonce를 얻는다. 카카오 token endpoint에는 서버 설정의 redirect URI, client secret, authorization code를 보내며, 카카오가 돌려준 `id_token`의 서명과 nonce를 검증한다. 카카오 로그인에서는 검증한 `id_token.sub`를 `member.provider_user_id`로 조회해 회원을 식별하거나 가입시킨다. 탈퇴 재인증에서는 같은 sub가 현재 인증 쿠키의 회원이 가진 provider ID와 일치하는지 확인한다.

state는 callback과 서버가 시작한 인가 시도를 묶고, 프론트의 `sessionStorage` 대조는 다른 브라우저에서 시작한 callback 주입을 막는다. nonce는 검증된 `id_token`이 바로 이 인가 시도에서 발급됐는지 확인한다.

### `POST /v1/auth/tokens`

저장 구조와 설정도 그 전제로 되어 있다.

| 어디 | 지금 모습 |
| --- | --- |
| `member` 테이블 | `provider_user_id` 하나뿐이고 `provider` 열이 없다. 주석이 "카카오 회원번호" 다 |
| 유일 키 | `uk_member_provider_user_id (provider_user_id)`. 소셜 구분 없이 번호만으로 유일하다 |
| `application.yml` | `spring.security.oauth2.client.registration` 아래에 `kakao` 하나만 있다 |

**소셜을 하나라도 더하려면 셋을 같이 고친다.** 하나만 고치면 조용히 깨진다.

1. `member` 에 `provider` 열을 더한다
2. 유일 키를 `(provider, provider_user_id)` 로 바꾼다. **이것을 빼면 다른 소셜의 같은 번호가
한 계정으로 합쳐진다.** 서로 모르는 두 사람이 같은 계정을 쓰게 되고, `provider` 를 모르는
조회는 틀린 사람을 집는다
3. 요청에 어느 소셜인지 가리는 값을 더한다. 경로를 소셜별로 쪼개지 않는다. 만드는 리소스가
같은 토큰이라 경로가 같아야 하고, 달라지는 것은 무엇으로 인증했는지라는 입력이다

**처리 절차 중 서버 안쪽**

1. state를 Redis에서 원자적으로 소비해 저장된 nonce를 얻는다. 없거나 만료됐거나 재사용했으면 거부한다
2. 인가 코드를 카카오 token endpoint에 서버 설정의 redirect URI와 client secret으로 교환한다. 받은 `id_token`의 서명, 발급자, audience, nonce를 검증하고 카카오 회원번호를 얻는다

3. `MemberLoginService`가 별도 DB 트랜잭션에서 회원을 찾거나 만든다. 동시 최초 가입이 UNIQUE에 걸리면 새 트랜잭션에서 기존 회원을 다시 찾는다.
4. 재가입은 [member 구조와 동작 설계](../member/member_구조와_동작_설계.md#재가입-판정과-시각-경계)에 따라 탈퇴 이력과 연결 해제 상태를 검사한 뒤 새 회원을 만든다. `newMember=true`와 미완료 온보딩을 반환한다. 기존 ACTIVE 회원은 마지막 로그인 시각만 갱신하며 카카오 프로필을 덮어쓰지 않는다.
5. `MemberTokenService.issue`가 토큰을 발급하고 DB에 RT 해시를 저장한다. 회원 생성과 토큰 발급은 한 트랜잭션이 아니므로 토큰 저장 실패 뒤에도 회원 행이 남을 수 있다.

### 사용자 토큰 재발급과 로그아웃

사용자는 `MemberTokenService`와 `OpaqueRefreshTokenLifecycle`을 사용한다. 관리자·점주의 개별 토큰 처리와 저장 순서까지 같다는 뜻으로 읽지 않는다.

| 흐름 | 실제 처리와 한계 |
|---|---|
| 발급 | DB 해시 저장이 먼저다. Redis 저장만 실패하면 로그를 남기고 발급은 성공한다 |
| 정상 재발급 | Redis에서 원자적으로 회전한 뒤 `MemberRefreshTokenBackupStore.rotateIfMatches`가 별도 트랜잭션으로 이전 해시를 비교해 DB를 갱신한다 |
| Redis 장애 | `DataAccessException`일 때만 DB 현재 해시·만료·ACTIVE 상태를 확인하고 CAS로 회전한다. Redis가 정상적으로 무효·만료를 판정한 경우에는 DB를 우회하지 않는다 |
| DB 회전 실패 | 현재 해시를 다시 확인한다. 새 해시가 있으면 성공으로 보고, 이전 해시가 있으면 이번 Redis 회전을 되돌린다. 다른 값이거나 확인 불가이면 새 캐시 토큰 폐기를 시도하고 저장소 오류를 반환한다 |
| 재사용 감지 | 현재 RT를 폐기하고 AT valid-after도 갱신한 뒤 재사용 오류를 반환한다. DB 폴백 중에는 과거 RT의 Redis 재사용 흔적을 복원할 수 없다 |
| 로그아웃 | 필수 토큰 폐기를 수행하고 커밋 뒤 카카오 로그아웃을 호출한다. 카카오 호출 실패는 로그만 남기며 서비스 로그아웃을 되돌리지 않는다. 영속 재시도 큐는 없다 |

DB와 Redis의 변경은 원자적이지 않다. 저장소 오류가 나면 일부 토큰 변경이 이미 적용됐을 수 있다. 컨트롤러는 서비스가 성공한 뒤에만 새 쿠키 또는 삭제 쿠키를 응답한다. 탈퇴의 연결 해제 큐와 카카오 로그아웃의 실패 로그는 서로 다른 복구 방식이다.

### 인증 요청 제한

`AuthRateLimitFilter`는 로그인·재발급 POST 여섯 경로의 IP 카운터를 공유한다. 카카오 인가 URL GET과 로그아웃 DELETE는 대상이 아니다. Redis 오류이면 요청을 통과시키며, 초과 응답은 본문 없이 `429`와 `Retry-After`를 보낸다. 상한과 윈도우는 현 구현의 값이며 부하 측정으로 검증한 수치가 아니다.

## 접근 제어

아래 기본 거부 설명은 목표 계약이다. 현재 `SecurityConfig.defaultFilterChain`은 `authenticated()`이므로 어느 도메인도 선언하지 않은 경로에는 인증만 요구한다. 이 차이와 관리자 사용자 목록의 체인 선언은 별도 PR #484가 코드와 함께 고친다. 해당 PR의 수정 문단은 이 PR에서 덮어쓰지 않는다.

이 절은 구현할 접근 제어 계약이다. 현재 점주 내 정보 조회·로그아웃의 OWNER 인가, 튜토리얼 완료의 OWNER·ACTIVE 검증, 약관 동의의 OWNER·ONBOARDING 검증은 구현되어 있다. 계정 상태 변경 서비스와 캐시 무효화 호출부 및 일반 업무 API의 상태 제한은 아직 연결되어 있지 않다. 상태 변경을 추가할 때 DB 변경과 커밋 후 무효화 등록을 한 점주 서비스 작업으로 묶고, 각 업무 API는 역할과 필요한 현재 상태를 직접 검증해야 한다.

**이 판정의 오류 코드는 이 문서가 소유하지 않는다.** 점주 상태(`ONBOARDING`, `ACTIVE`,
`SUSPENDED`)는 점주 도메인의 데이터이고, 역할만 아는 인증 모듈은 그 값을 판정할 수 없다.
코드는 점주 도메인의 문서가 정한다.

**이 표는 한곳에 두지만 구현은 도메인마다 나뉜다.** 도메인을 가로지르는 불변식이라 한 표로
봐야 빠진 곳이 보이는데, 인증 모듈은 자격을 확인할 수 없어서 각 도메인이 자기 경로를 선언한다.

경로는 접두어가 아니라 **그 API를 가진 도메인의 보안 설정**이 선언한다. 허용 역할은 [명세의 접근 제어 표](../../api-spec/auth-api-spec.md#접근-제어)대로 접두어를 따른다.

| 예 | 선언하는 곳 |
| --- | --- |
| `/v1/admin/payments/**`, `/v1/owner/points/**` | billing 보안 설정 |
| `/v1/admin/dashboard/**`, `/v1/events` | analytics 보안 설정 |
| `/v1/admin/members`, `/v1/members/**` | member 보안 설정 |
| `/v1/admin/auth/**`, `/v1/admin/admins` | admin 보안 설정 |

**어느 도메인도 주장하지 않은 경로는 거부된다.** `SecurityConfig`의 기본 체인이 `anyRequest().denyAll()`이다. 선언을 빠뜨리면 열리지 않고 막히는 쪽으로 실패하므로, 이 표와 구현이 어긋나면 `403` 으로 드러난다. 조용히 열리는 경우는 없다(#483).

기본 체인은 ERROR 디스패치만 통과시킨다. 컨테이너나 필터가 `sendError`로 끝낸 요청은 `/error`로 다시 들어오는데, 이 경로는 어느 도메인도 선언하지 않아 기본 체인이 받는다. 거부하면 원래 오류가 `403`으로 덮인다. 이미 정해진 오류 응답을 그리는 것뿐이라 새로 열리는 업무 경로는 없다.

## 오류 코드를 나눈 기준

요청 형식이 틀린 경우처럼 **판정에 인증 지식이 필요 없는 실패는 공통 코드를 쓴다.**
요청 값 검증은 요청 타입의 애노테이션이 판정하고 경로마다 결과가 다르지 않다.

**이 표는 `AUTH-` 만 소유한다.** 카카오 인증 실패(`AUTH-007`)는 토큰을 만드는 경로에서 생기는 인증 실패이므로 여기서 정의한다.
정지 이력 재가입 거부(`MEMBER-003`)처럼 사용자 데이터를 보고 판정하는 코드는 사용자 도메인 문서가 정의한다.
점주 가입도 같은 이유로 이 문서를 떠났다. 경로가 여기 있다는 이유로 남의 코드를 여기 적으면
소유자가 둘이 되고, 한쪽만 고치는 날 갈린다.

**카카오 인증 실패는 `AUTH-007`로 통합한다.** 로그인과 탈퇴 재인증이 같은 검증을 쓰므로 코드도 하나다.
정지 이력 판정은 사용자 도메인이 아는 것이라 `MEMBER-003`을 `member.md`가 소유한다.

## 구현 대조 범위

카카오 인가·로그인과 회원 토큰은 `MemberAuthController`, `KakaoAuthorizationService`, `KakaoLoginStateRepository`, `KakaoIdTokenExchanger`, `MemberLoginService`, `MemberTokenService`, `MemberRefreshTokenBackupStore`, `OpaqueRefreshTokenLifecycle`을 대조했다. 쿠키와 요청 제한은 `AuthCookieFactory`, `AuthRateLimitFilter`를 확인했다. 원본의 자동 로그인 선택, 회원 응답에 프로필 이미지를 넣지 않는다는 과거 설명은 현재 구현과 달라 옮기지 않았다. 관리자·점주 내부 처리의 기준은 각 도메인의 설계서다.
