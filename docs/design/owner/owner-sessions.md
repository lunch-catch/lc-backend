# 점주의 여러 기기 로그인

점주 로그인마다 `OwnerSession`을 생성한다. 같은 브라우저의 탭은 HttpOnly 쿠키를 공유하며 서로 다른 기기는 별도 세션을 사용한다.
관리자와 회원 인증은 변경하지 않는다. HTTP 계약은 [인증 명세의 점주 절](../../api-spec/auth-api-spec.md#점주)이 소유한다.

## 저장 구조와 잠금

`owner_session`은 점주 ID, 임의의 UUID 세션 키, RT의 현재·직전 SHA-256 해시, 직전 RT의 유예 시각, 만료·폐기 시각, 발급 순번과 세대를 저장한다.
`owner_session.owner_id`는 같은 도메인의 `owner.owner_id`를 외래 키로 참조한다. 점주를 물리적으로 삭제하려면 세션을 먼저 삭제한다.
토큰 원문은 DB와 로그에 저장하지 않는다. 세션 키는 인증 수단이 아니며 서명된 AT의 `ownerSession` 클레임으로만 받는다.
JWT 검증은 auth가 담당하고 세션의 소유자·현재 상태·만료·폐기·세대 검증은 owner가 담당한다.

기존 점주의 Redis 소비 표시·DB 백업·커밋 후 순번 게시·DB 확인 후 복구 순서를 세션별로 적용한다.
MySQL의 세션 행이 상태·만료·현재 해시의 원본이다. Redis의 활성 포인터와 발급·폐기 순번은 계정 ID 대신 세션 키로 분리하여 다른 기기의 토큰을 덮어쓰지 않는다.

| Redis 키 | 값과 용도 |
|---|---|
| `ownerSessionToken:{RT해시}` | 점주 ID·OWNER·세션 키와 PENDING 또는 REVOKED 소비 표시 |
| `ownerSessionActive:{세션키}` | 해당 세션의 현재 RT 해시 |
| `ownerSessionVersion:{세션키}` | 지연된 게시를 거부하는 19자리 발급·폐기 순번 |
| `ownerSessionRevoked:{세션키}` | 해당 세션의 AT 폐기 표시 |

로그인·회전·로그아웃은 점주 행을 먼저 잠근 독립 트랜잭션에서 처리한다. 상태 변경과의 순서를 맞추고 같은 세션의 동시 회전을 직렬화한다.
DB 저장·커밋이 실패하면 토큰을 반환하지 않고 `AUTH-002`로 응답한다. 커밋 후에만 Redis 게시와 컨트롤러의 쿠키 발급을 수행한다.
게시 전 별도의 짧은 DB 확인으로 현재 해시·발급 순번·상태를 재검사하고 DB 연결을 반환한 뒤 Redis를 호출한다.
Lua가 세션별 발급 순번을 비교하므로 늦게 도착한 게시가 최신 RT나 로그아웃 결과를 덮어쓰지 못한다.
세션별 Redis 키는 만료 시간을 둔다. 폐기 표시는 RT의 남은 수명과 AT 수명 중 긴 시간 동안 보관하며 DB 폐기는 키 유실과 무관하게 유지한다.

## 로그인과 갱신

비밀번호 비교는 DB 저장 트랜잭션 밖에서 수행한다. 점주 행을 잠근 뒤 상태·비밀번호를 다시 확인하고 새 세션과 최근 로그인 시각을 저장한다.
기존 세션은 변경하지 않는다. 같은 점주의 만료된 세션은 다음 로그인 트랜잭션에서 정리한다.

갱신은 기존 소비 Lua로 Redis RT를 PENDING으로 표시하고 세션을 찾는다. Redis 장애·캐시 유실은 DB 해시 조회로 폴백하며 DB 상태와 해시를 검증해야 한다.
Redis에서 폐기한 현재 RT를 DB 폴백으로 되살리지 않는다. 직전 RT의 REVOKED는 동시 갱신 유예 여부를 DB에서 판정한다.
점주 행 잠금 아래 현재·직전 RT와 상태를 다시 확인한다. 현재 RT는 새 무작위 토큰으로 회전하고 만료를 갱신 시점부터 1일 연장한다.
회전 직후 10초 동안 같은 세션의 현재·직전 RT 요청은 모두 성공시키되 AT만 발급한다. RT와 RT 만료는 다시 변경하지 않는다.
직전 RT를 받은 다른 탭이 정상 갱신 때문에 로그아웃되는 일을 막고 여러 응답이 RT 쿠키를 덮어쓰지 않게 하기 위한 유예다.
회전이 커밋되면 새 RT를 세션별 순번으로 게시하고 이전 RT의 소비 표시를 REVOKED로 확정한다.
DB 회전에 실패하면 별도 트랜잭션에서 점주를 잠그고 기존 RT 해시가 여전히 유효할 때만 PENDING을 복구한다. 이미 바뀌거나 폐기된 RT는 복구하지 않는다.
유예 중 현재 RT는 교체하지 않으므로 소비 표시만 복구한다.
유예가 끝난 직전 RT의 재사용은 해당 세션만 DB에서 폐기하고 Redis 폐기를 반영한 뒤 `AUTH-004`로 응답한다. 다른 기기는 유지한다.
직전보다 오래된 토큰은 `AUTH-003`으로 거절한다. 세션마다 직전 해시 하나만 보관하며 전체 토큰 이력은 쌓지 않는다.
새 RT 응답이 유실되어 유예가 지난 경우에는 다시 로그인한다. 유예 중에는 탈취된 직전 RT도 AT를 받을 수 있으므로 유예는 정상 중복 처리에 필요한 짧은 구간으로 제한한다.

## 로그아웃과 계정 전체 차단

로그아웃은 서명된 AT의 세션 키와 인증 주체 ID로 해당 세션만 폐기한다. RT 쿠키는 없어도 된다.
같은 브라우저의 탭은 쿠키와 세션을 공유하므로 로그아웃도 함께 반영된다. 다른 기기의 세션은 유지한다.
AT 인증은 매번 새 DB 트랜잭션에서 점주와 세션을 읽고 Redis의 세션 폐기 표시를 추가 검사한다.
DB 장애는 일반 인증에서도 통과시키지 않는다. Redis 조회 장애의 LENIENT 허용은 DB 검증을 통과한 AT에만 적용하고 REQUIRED는 `AUTH-002`다.
DB 로그아웃 커밋 후 Lua로 해당 세션의 RT와 AT를 함께 폐기한다. Redis 폐기 실패는 `AUTH-002`지만 DB 폐기는 되돌리지 않는다.
조회 중 이미 시작한 요청까지 취소하지는 않으며 폐기가 커밋된 뒤 시작하는 인증부터 차단한다.

로그인·RT 갱신은 ONBOARDING·ACTIVE만 허용한다. AT의 업무별 상태 제한은 기존 점주 서비스가 판정하며 유효한 AT를 가진 정지·탈퇴 점주의 내 정보 조회·로그아웃은 유지한다.
계정 상태 변경 시 전체 토큰을 폐기해야 하면 점주 잠금 아래 `Owner.clearRefreshToken()`을 호출한다.
이 메서드는 `session_generation`을 증가시켜 기존 모든 세션을 차단한다. 이후 새 로그인은 새 세대를 사용한다.
상태를 나중에 복구해도 이전 세션이 되살아나지 않아야 하는 상태 변경은 전체 폐기를 함께 수행해야 한다.

## 장애 처리

로그인·회전의 DB 저장이 확정된 뒤 Redis 게시·소비 확정만 실패하면 성공을 유지한다. DB 해시 검증과 다음 갱신의 폴백으로 유효한 세션을 이어간다.
게시 전 DB 확인이 실패하면 `AUTH-002`다. 이미 RT가 회전됐을 수 있으므로 쿠키를 받지 못하면 다시 로그인한다.
로그아웃·재사용의 Redis 폐기 실패도 `AUTH-002`다. DB 폐기는 유지하며 기존 AT로 HTTP 재시도를 보장하지 않는다.
DB와 Redis를 하나의 트랜잭션으로 묶지 않으며 자동 재처리 큐는 없다. 로그에는 점주 ID·이벤트·예외 타입만 남기고 토큰·해시를 남기지 않는다.

## 기존 단일 토큰과의 호환

호환은 새 코드가 기존 토큰을 검증하는 방향으로 제공한다. 구버전 코드가 새 세션을 처리하는 방향은 지원하지 않는다.
배포 전에 발급한 AT에는 `ownerSession`이 없다. 해당 AT는 기존 DB·Redis 발급 순번 검증을 유지한다.
세션 테이블에서 찾지 못한 RT는 기존 재발급 경로로 처리한다. 기존 토큰을 새 기기 세션으로 자동 전환하지 않으며 다음 로그인부터 새 세션을 사용한다.
기존 토큰의 로그아웃·재사용은 `clearLegacyRefreshToken()`으로 기존 단일 토큰만 폐기한다. 새 세션의 세대는 변경하지 않는다.
기존 Redis 소비 표시·DB 폴백·커밋 후 게시·부분 실패 정책은 [기존 토큰 처리](../auth/auth-api-design.md#기존-단일-토큰의-호환-처리)를 따른다.

## 프론트엔드 연계

새 탭에서는 쿠키가 자동 전송되는 `GET /v1/owner/me`로 인증 상태를 복원한다. AT가 만료됐다면 기존 갱신 API를 호출한 뒤 다시 조회한다.
갱신 성공 응답에 RT 쿠키가 없어도 정상이다. 브라우저가 가진 최신 RT를 유지한다.
탭의 메모리 상태나 `sessionStorage`만으로 로그인 화면을 결정하는 프론트엔드라면 복원 처리가 필요하다.
이 저장소는 백엔드이므로 화면 전환과 탭 사이 상태 알림은 프론트엔드에서 확인한다.
