# owner 장애 처리 설계

[공통 장애 처리](../장애_처리_설계_가이드.md)의 기본 처리에서 벗어난 곳만 설명한다.
RT 회전·로그아웃의 상세는 [인증 설계](../auth/auth-api-design.md)의 점주 절 중 `POST /v1/owner/auth/tokens:refresh`·`DELETE /v1/owner/auth/tokens` 항목, 상태 조회는 [상태 캐시 설계](owner-status-cache.md)의 "상태 변경과 접근 제어를 연결할 때의 조건" 절이 소유한다.

기본 범위는 PR 작성자가 `gyudongjeong`인 develop 반영 기능이다. 로그인 저장소 실패는 [#71](https://github.com/lunch-catch/lc-backend/issues/71), 회전·보상은 [#121](https://github.com/lunch-catch/lc-backend/issues/121), 로그아웃 부분 실패는 [#132](https://github.com/lunch-catch/lc-backend/issues/132)를 참조한다.
DB 현재 상태·롤백은 [#137](https://github.com/lunch-catch/lc-backend/issues/137)과 [#151](https://github.com/lunch-catch/lc-backend/issues/151), 최종 등록·캐시 삭제 실패 허용은 [#502](https://github.com/lunch-catch/lc-backend/issues/502)가 근거다.
#121의 과거 AT 차단 한계와 현재 DB 우선 검증은 구분한다. 현재 동작은 코드·테스트를 따르며 #534는 문서 작성 이슈다.

2026-10-21에 확인한 develop을 기준으로 하며 다른 작성자의 관리자 점주 목록 기능은 포함하지 않는다. 이미지·메뉴 업로드 장애는 [store 장애 설계](../store/store_장애_처리_설계.md)가 소유한다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| MySQL `owner` | 계정·상태·튜토리얼·현재 토큰·폐기 순번 | 기본(읽기 오류를 올리고 쓰기를 롤백한다). AT 검증은 아래 예외를 따른다 |
| Valkey 상태 캐시 | 일반 `OwnerStatusQuery.findStatus` | 벗어났다. 아래 "상태 조회 캐시" 절 |
| Valkey RT·소비 표시·순번 | 로그인·토큰 재발급·로그아웃 | 벗어났다. 아래 "RT 회전·폐기" 절 |
| Valkey AT 폐기 순번 | DB 폐기 검증 후 추가 검사 | 벗어났다. 아래 "AT 폐기 기준 검증" 절 |
| store의 조회·저장 contract | 화면 복원과 등록 조정 | 기본(장애를 전파하고 저장 실패는 같은 TX의 점주 변경도 롤백한다) |

## 벗어난 것

### 캐시: 상태 조회 캐시

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 캐시 장애면 상태 조회를 거부한다 | DB 폴백 부하가 없다 | 캐시 장애가 상태 조회 중단으로 이어진다 |
| B. DB 원본을 조회하고 캐시 저장 실패는 결과를 유지한다 | 캐시 장애 중에도 원본 상태를 반환한다 | 동시 만료·복구 시 DB 부하가 늘 수 있다 |

B를 따른다. 미스·캐시 읽기 장애는 DB로 폴백하고 DB 오류를 점주 부재로 바꾸지 않는다. `findCurrentStatus`와 트랜잭션 중 `findStatus`는 캐시를 우회한다.
중요한 쓰기는 DB 현재 상태와 행 잠금으로 검사한다. 일반 캐시의 허용 지연은 O2, 복구 부하와 통과 횟수의 전용 지표·경보는 O1에 남긴다. 근거는 [상태 캐시 설계](owner-status-cache.md)다.

### 캐시: RT 회전·폐기

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Redis에서 확인하지 못한 토큰을 모두 DB로 우회한다 | 캐시 상태와 무관하게 현재 RT를 조회할 수 있다 | 정상적인 무효·재사용 판정을 뒤집을 수 있다 |
| B. 저장소 장애에만 DB 현재 RT를 검증한다 | 정상적인 거부 판정을 지키면서 장애 중 유효한 RT는 사용할 수 있다 | DB 부하가 늘고 과거 재사용 기록은 복원하지 못한다 |

B를 따른다. 점주는 Redis의 정상적인 토큰 없음·처리 중·재사용 판정을 DB로 우회하지 않는다. 상세는 [인증 설계](../auth/auth-api-design.md)의 점주 `POST /v1/owner/auth/tokens:refresh` 항목이 소유한다.
로그인·토큰 재발급은 DB 커밋 뒤 요청 안에서 직접 게시하며 Redis 게시만 실패하면 성공을 유지한다. 소비 표시 확정 실패도 DB의 이전 해시 거부는 유지하지만 만료까지 처리 중 표시가 남을 수 있다.
로그아웃은 DB 폐기 뒤 RT·AT Redis 반영을 각각 시도하고 하나라도 실패하면 `AUTH-002`를 반환한다. 이미 커밋한 RT·AT 폐기는 되돌리지 않으므로 이전 AT로 HTTP 재시도하는 복구를 보장하지 않는다.
DB 실패 뒤 소비 표시 복원은 별도 잠금 아래 이전 RT가 여전히 유효할 때만 허용한다. 상세 확인·복원 절차는 인증 설계를 따르며 자동 재처리 큐는 없다. 통과·게시 실패 지표는 O1, 중단·보상 유실은 O5에 남긴다.

### DB·캐시: AT 폐기 기준 검증

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Redis만 검사한다 | 인증마다 DB를 읽지 않는다 | 폐기 키 유실로 이전 AT가 다시 허용될 수 있다 |
| B. DB를 먼저 확인하고 Redis를 추가 검사한다 | Redis 유실과 독립적으로 DB 폐기를 지킨다 | 인증마다 DB 읽기가 추가된다 |

B를 따른다. DB 계정 부재·조회 장애는 `LENIENT`도 인증을 거부하고 `REQUIRED`의 조회 장애는 `AUTH-002`다. Redis 장애의 `LENIENT` 통과는 DB 검증을 통과한 AT에만 적용하며 `REQUIRED`는 `AUTH-002`다.
근거는 [인증 설계](../auth/auth-api-design.md)의 점주 "AT 폐기 순번 검증" 절이다. Redis 장애 통과 지표·경보는 O1에 남긴다.

### 롤백 안 되는 효과: 커밋 뒤 상태 캐시 삭제

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 상태 변경 TX 안에서 캐시를 삭제한다 | 별도 후속 작업이 없다 | DB 롤백에도 캐시가 바뀌며 미커밋 상태를 다시 채울 수 있다 |
| B. 커밋 뒤 콜백에서 삭제한다 | 커밋된 변경에만 무효화를 적용한다 | 콜백 전 중단이나 삭제 실패 때 유실될 수 있다 |

B를 따른다. `ACTIVE` 전환은 store 최종 등록과 같은 TX에 두고 삭제만 `TransactionSynchronization.afterCommit`에서 실행한다.
삭제 실패는 `OWNER_STATUS_CACHE_INVALIDATION_FAILED`를 남기고 상태 변경 성공을 유지한다. 영속 큐는 없으며 TTL만으로 커밋 후 30초 내 최신화를 보장하지 않는다.
근거는 [상태 캐시 설계](owner-status-cache.md)의 "상태 변경과 접근 제어를 연결할 때의 조건" 절이다. 허용 지연은 O2, 유실 복구와 운영 책임은 O5에 남긴다.

해당 없음. 이 범위의 점주 기능은 외부 사업자 API를 호출하지 않는다. 이미지 업로드의 S3 처리는 store가 소유한다.

## 아직 정하지 못한 것

| ID | 남은 일 |
|---|---|
| O1 | 캐시 동시 만료·복구와 BCrypt·AT DB 확인·점주 행 잠금 부하를 측정한다. 상태 폴백·토큰 게시 실패·`LENIENT` 통과 지표·경보는 미구현이며 운영 로그만으로 요구를 충족했다고 보지 않는다 |
| O2 | 기능 담당자가 상태 캐시의 허용 지연과 사용 가능한 권한 판정을 합의한다. 정지·탈퇴는 후속 범위이며 RT·AT 폐기와 보상도 함께 정한다 |
| O3 | DB 지연·풀 고갈·재연결·페일오버를 실제 환경에서 검증한다. 설정된 드라이버·풀 대기·TX 제한만으로 복구를 보장하지 않는다 |
| O4 | 점주 서비스에 일반 데드락 자동 재시도는 없다. 안전한 재시도 범위·횟수와 소유자를 정하며 회전 결과 확인을 업무 전체 재시도로 설명하지 않는다 |
| O5 | 종료 중 RT 게시·상태 캐시 삭제·소비 표시 복원 실패의 복구 방식과 운영 책임을 정한다. 현재 영속 복구 배치는 없다 |
