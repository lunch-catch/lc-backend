# 점주 상태 조회

점주 상태 원본은 `owner.status`다. JWT와 공통 인증 객체에는 점주 상태를 저장하지 않는다.

다른 도메인은 `owner.contract.OwnerStatusQuery`를 사용한다. `findStatus`는 Redis를 먼저 조회하고, 캐시 미스 또는 Redis 장애 시 DB에서 상태 컬럼만 조회한다. 존재하지 않는 점주는 빈 Optional을 반환하며, DB 장애는 호출자에게 전파한다. 일반 조회 결과는 `ownerStatus:{ownerId}`에 저장하고 `owner.status-cache.ttl-seconds`로 TTL을 설정한다. 기본값 30초는 조정 가능한 초기값이며 성능 및 최신성 요구에 맞춰 변경한다.

`findCurrentStatus`는 캐시를 우회한다. 즉시 제한이 필요한 중요한 작업에서 사용한다. 트랜잭션 중 `findStatus`도 DB를 조회하며 미커밋 상태를 캐시에 저장하지 않는다. 트랜잭션 격리 수준에 따른 스냅샷과 동시 상태 변경까지 이 조회만으로 직렬화하지는 않는다.

현재 상태 변경 서비스는 없다. 정지, 탈퇴, 온보딩 완료 기능을 추가할 때 DB 상태를 변경하는 트랜잭션 안에서 `OwnerStatusService.invalidateAfterCommit(ownerId)`를 호출해야 한다. 롤백 시 캐시는 유지하고 커밋 성공 후 삭제한다. 삭제 실패 및 조회와 삭제의 경합에서는 TTL까지 이전 상태가 남을 수 있다. 로그인 때만 캐시를 채우는 방식은 사용하지 않는다.

로그인은 기존처럼 DB의 점주 상태와 비밀번호를 확인한다. 조회 계약 자체는 접근 허용 정책을 결정하지 않으며 각 기능에서 반환된 상태에 맞는 정책을 적용해야 한다.

## 상태 변경과 접근 제어를 연결할 때의 조건

현재 `invalidateAfterCommit`을 호출하는 상태 변경 서비스와 `findStatus`를 사용하는 업무 소비자는 없다. 현재 점주 보안 체인은 로그인과 가입 경로만 선언하며, 상태 조회 기반이 있다는 사실만으로 `/v1/owner/**`에 `ONBOARDING` 제한이 구현된 것은 아니다.

상태 변경 기능을 추가할 때 점주 도메인의 서비스 작업 하나가 DB 변경과 커밋 후 무효화 등록을 함께 소유해야 한다. 범용 `changeStatus(ownerId, newStatus)`로 임의 전이를 허용하지 말고, 가게 최종 등록·정지·탈퇴별 전이 조건과 필수 시각을 검증한다. 호출 도메인은 점주 계약을 통해 이 작업을 요청한다. 이 로그인 PR에는 상태 변경 기능을 추가하지 않는다.

`ONBOARDING → ACTIVE`의 낡은 캐시는 잠시 403을 만들 수 있지만, `ACTIVE → SUSPENDED/WITHDRAWN`의 낡은 캐시는 권한을 유지시킬 수 있다. 재발급 판정과 즉시 제한이 필요한 처리는 `findCurrentStatus` 또는 동등한 DB 조회를 사용한다. 중요한 변경은 동일 트랜잭션의 잠금 또는 조건부 갱신으로 상태 검사 이후의 경합도 막는다. 정지·탈퇴 기능은 RT 폐기 및 AT 컷오프와 저장소 장애 시 재시도·보상 정책까지 구현해야 하며 캐시 삭제만으로 인증을 폐기하지 않는다.

삭제 실패와 조회·삭제 경합을 제거한 것은 아니다. TTL은 캐시 저장 시점부터 계산하므로 지연 재저장이 있으면 상태 변경 커밋 후 30초 내 최신화를 보장하지 않는다. 기본 TTL 30초는 초기 설정이고 팀이 허용한 보안 지연 한도가 아니다. 상태 조회 캐시를 최종 권한 판정에 사용할 수 있는지는 기능별로 팀이 합의해야 한다.

## 로그인 RT 게시 순서

점주 행 잠금 아래 RT 해시와 `refresh_token_issuance_version`을 함께 갱신한다. DB 커밋 후 별도 짧은 트랜잭션에서 현재 상태·해시·순번을 재확인하고 DB 연결과 잠금을 반환한다. Redis는 `saveIfNewer` Lua로 더 큰 발급 순번만 게시하여 늦게 도착한 이전 로그인 게시가 최신 활성 포인터를 덮어쓰지 않게 한다. TTL은 DB 만료 시각의 남은 시간으로 계산하며, 순번은 19자리 문자열로 비교해 64비트 정밀도를 유지한다.

순번 키 `refreshTokenIssuanceVersion:OWNER:{id}`는 토큰 만료와 함께 삭제하지 않는다. 토큰 만료 뒤 지연된 옛 게시를 거부하기 위한 별도의 순서 정보이며 점주 상태 캐시가 아니다. Redis 유실이나 최신 게시 실패에서는 DB와 Redis의 즉시 일치가 보장되지 않는다. 후속 점주 재발급 구현은 DB 현재 해시·만료·상태를 확인해야 한다.

첨부 명세 기반의 `auth-api-spec.md`는 앞으로 구현할 재발급·로그아웃 정책도 포함한다. 이 브랜치에서 추가로 구현한 것은 로그인 RT 게시 순서 보장과 명세 정리이며, 점주 재발급·로그아웃·상태 변경·상태별 업무 인가는 아직 구현하지 않았다.
