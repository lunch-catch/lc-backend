# member API 설계

[member API 명세](../../api-spec/member.md)의 응답을 서버가 어떻게 만드는지와 그렇게 정한 이유를 적는다. 도메인 공통 구조는 [member 구조와 동작 설계](./member_구조와_동작_설계.md)가, 외부 의존이 멈췄을 때의 처리는 [member 장애 처리 설계](./member_장애_처리_설계.md)가 갖는다.

## 1. 적용 범위

| 묶음 | API |
|---|---|
| 온보딩과 프로필 | `PUT /v1/members/me/onboarding`, `GET /v1/members/me`, `PATCH /v1/members/me` |
| 대표 저장 위치 | `PUT`·`GET`·`DELETE /v1/member-profiles/location` |
| 탈퇴 | `POST /v1/members/me:withdraw` |
| 카카오 연결 해제 통보 | `GET`·`POST /webhook/kakao/unlink` |
| 관리자 사용자 목록 | `GET /v1/admin/members` |

### 온보딩과 프로필

`MemberProfileService`의 쓰기는 회원 행을 먼저 잠근다. 탈퇴도 같은 행을 잠그므로 탈퇴 직전 상태를 들고 프로필을 새로 만들거나 동의를 되돌리는 요청을 직렬화한다. 동시에 들어온 온보딩도 두 번째 요청이 완료 상태를 확인하고 거절한다.

온보딩 전 위치 설정이 프로필을 먼저 만들 수 있다. 온보딩은 기존 프로필이 있으면 성별·연령대·완료 시각만 채워 위치를 보존한다. 프로필이 없을 때만 새로 만든다. 완료 여부와 위치 동의로 `feedAvailable`을 계산한다.

PATCH는 DTO의 null을 미수정으로 취급한다. 동의는 값이 바뀔 때만 동의·철회 시각을 갱신한다. 응답의 `profile`은 완료 전이면 null로 숨기며, 시각은 KST 오프셋으로 바꾼다. 카카오 프로필 이미지와 탈퇴 뒤 재가입 시 정보 갱신은 로그인 흐름이 수행한다.

### 대표 저장 위치

`MemberLocationService.save`는 회원 행을 잠그고 탈퇴 상태를 확인한다. `MemberProfile.create`는 회원과 연결된 미완료 프로필을 만들 수 있으므로 온보딩 전에도 저장된다. 회원당 프로필 한 행의 위치 네 필드를 함께 대체한다.

`MemberLocationRequest`가 좌표 쌍·범위·문자열 길이를 검증한다. 주소만으로 좌표를 구하는 외부 API는 호출하지 않는다. `location_opt_in`은 거절 조건이 아니며 GPS 수집 동의의 준수는 클라이언트 규칙이다.

조회는 프로필이 없으면 네 필드가 null인 결과를 만든다. 삭제는 프로필의 위치 네 필드만 비운다. 행 자체를 지우면 성별·연령대와 온보딩 완료도 사라지므로 행을 유지한다. 탈퇴만 프로필 행을 삭제한다.

좌표는 `DECIMAL(10,7)`에 매핑한다. 저장 위치에는 노출·접속 로그의 반올림을 적용하지 않는다. 저장 위치를 다른 도메인에 주는 계약은 아래 7장이 갖는다.

### 관리자 사용자 목록

`AdminMemberService`가 입력을 검사하고 KST 가입일 범위를 `[시작일 00:00, 종료 다음 날 00:00)`으로 바꾼다. 닉네임은 공백을 정리한 접두사 검색이며 숫자도 닉네임으로 처리한다. `MemberRepositoryImpl`이 LIKE 특수문자를 이스케이프한다.

목록 조회와 COUNT를 읽기 전용 트랜잭션에서 수행한다. 정렬 키 뒤에는 회원 ID를 같은 방향으로 붙이고 로그인 시각 null은 CASE 정렬로 항상 뒤에 둔다. 탈퇴 시 이미 비식별 처리한 닉네임을 그대로 반환하므로 목록에서 다시 마스킹하지 않는다. 성능 요구는 1만 건 기준 1초 이내이며 이번 문서 대조에서 달성을 측정하지 않았다.

## 2. 탈퇴

`POST /v1/members/me:withdraw`는 다음 순서로 처리한다.

1. 카카오 재인증 코드를 검증한다. 카카오 로그인과 같은 `state -> nonce` 저장·검증 로직을 쓰고, 재인증한 카카오 회원번호가 현재 인증된 회원의 `provider_user_id`와 일치하는지 확인한다.
2. 회원을 잠그고 카카오 번호를 확보한다. 탈퇴 이력과 필요한 연결 해제 작업을 먼저 기록한 뒤 `member.status`를 `WITHDRAWN`으로 바꾼다. 회원의 카카오 번호는 비우고 탈퇴 시각을 기록한다. 개인정보는 즉시 비식별 처리하되 행은 남긴다.
3. Refresh Token을 폐기하고 Access Token valid-after를 기록한다. 인증 쿠키는 서비스 호출이 끝난 뒤 컨트롤러가 `Max-Age=0`으로 만료한다.
4. **2~3번과 같은 트랜잭션에서 기록한 연결 해제 작업은 최초 호출을 선점한 상태로 커밋한다.** 작업 행의 존재는 연결 해제가 성공으로 확정되지 않았다는 뜻이다.
5. 커밋 후 트랜잭션 밖에서 카카오 연결 해제를 동기로 호출한다. 이 호출은 HTTP 응답 전이다. 성공하면 큐 행을 지우고, 실패해도 탈퇴는 완료로 응답한다. 남은 행은 매일 03시 배치가 재시도한다. 재시도 규약은 [장애 처리 설계의 외부 API 절](./member_장애_처리_설계.md#외부-api)에 있다.

**적재를 호출보다 먼저 하는 이유.** "실패하면 그때 적재"로 두면 탈퇴 커밋과 적재 사이의 모든 중단이 유실이 된다. 프로세스가 죽거나 적재 자체가 실패하면 회원은 `WITHDRAWN`인데 재시도 큐는 비어 있고, 카카오 연결은 영원히 남는다. 응답이 `204`라 클라이언트도 운영도 알 수 없다. 먼저 적재하면 그 사이에 무엇이 멈춰도 다음 배치가 집어 올린다.

탈퇴 이벤트(`MemberWithdrawnEvent`)는 발행하지 않는다. 발급받은 쿠폰의 즉시 만료(FR-009)는 쿠폰 도메인이 회원 `status`를 조회해 처리해야 한다.

### 탈퇴 시 내부 데이터 처리

명세서의 "탈퇴 시 데이터 처리" 표는 응답에 보이는 값만 적는다. 아래는 응답에 보이지 않는 저장 값의 처리다.

| 데이터 | 처리 | 이유 |
| --- | --- | --- |
| 성별, 연령대, 저장 위치 4컬럼 | `member_profile` 행 삭제 | `ck_member_profile_onboarding` 때문에 컬럼만 비울 수 없다 |
| 알림, 위치 동의 | `opt_in=false`, 시각 컬럼 `NULL` | |
| `provider_user_id` | 회원에서는 NULL, 탈퇴 이력에 보관 | 재가입 식별과 제한 판정. 저장 구조는 [구조와 동작 설계 3장](./member_구조와_동작_설계.md#3-저장)이 갖는다 |
| `suspended_at` | 유지 | 정지 이력 재가입 차단 기준 |
| 카카오 회원번호 사본 | `kakao_unlink_failure`에 두었다가 unlink 성공 시 삭제 | |
| `profile_image_url`, `last_login_at` | `NULL` | |

재가입의 판정과 새 회원 생성은 [구조와 동작 설계](./member_구조와_동작_설계.md#재가입-판정과-시각-경계)를 따른다. 옛 회원은 재활성화하지 않는다.

## 3. 카카오 연결 해제 통보

`GET`·`POST /webhook/kakao/unlink`는 카카오가 부르는 서버 간 경로다. `/v1/` 접두사가 없고 이 서비스의 JWT를 쓰지 않는다. 컨트롤러가 `Authorization: KakaoAK {Admin Key}`와 `app_id`를 직접 검증한다.

- 최초 가입 계정이면 로컬 탈퇴와 이력 저장, 토큰 폐기를 수행한다. **unlink는 다시 호출하지 않는다.**
- 현재 회원이 없으면 이미 탈퇴했거나 없는 계정으로 보고 아무것도 바꾸지 않는다. 진행 중인 해제 작업도 삭제하지 않는다.
- 재가입 계정의 통보는 [구조와 동작 설계의 판정과 한계](./member_구조와_동작_설계.md#연결-해제-웹훅의-구분-한계)에 따라 계정을 유지하고 경보로 남긴다.
- 검증 실패와 내부 처리 실패 모두 **항상 `200`** 을 돌려주고 로그만 남긴다. 실패를 응답 코드로 드러내면 카카오 재시도를 유발한다.

## 4. 데이터 보존과 삭제

다른 도메인의 기간은 원본에 적힌 보존 정책을 기록한 것이다. 해당 도메인의 삭제 배치가 실제로 등록돼 실행되는지까지 이 문서에서 검증한 것은 아니다. member가 직접 구현한 삭제와 타 도메인의 보존 정책을 구별해 읽는다.

| 구분 | 데이터 | 기준 |
| --- | --- | --- |
| 영구 보관 | 운영 감사 로그(`audit_log`) | 삭제하지 않음 |
| 탈퇴 후에도 유지 | 옛 `member` 행과 탈퇴 이력 | 카카오 번호는 이력에 남기고 회원에서는 비운다. 최종 보존 기간과 삭제 배치는 미정이다 |
| 기간 유지 후 삭제 | `event_log`, `serve_log`, `impression_log` | 13개월, 야간 배치 삭제 |
| 기간 유지 후 삭제 | `swipe_log` | 31일 |
| 기간 유지 후 삭제 | `feed_visit_daily` | 8일, 좌표는 소수점 3자리 반올림 |
| 기간 유지 후 삭제 | 피드 서빙 캐시 | 30분 |
| 사용자가 삭제할 때까지 | 저장 위치 | 탈퇴하면 `member_profile`과 함께 삭제 |
| 탈퇴 시 삭제 | `member_profile`, 토큰, 카카오 회원번호 사본(unlink 성공 후) | 2장 참고 |
| 규칙 없음 | 정산 원장, 결제, 환불 | 삭제 규칙과 법정 보존 기간이 정해지지 않음 |

## 5. 구현 제외 기능을 다시 채택할 때 정할 것

**회원과 점주 상태 변경(FR-009).** 지금 `member` 테이블에는 `suspended_at`, `suspended_until`, `suspension_reason` 컬럼만 있고 정지·해제를 수행하는 엔티티 메서드, API, 정지 감사 로그는 없다. 정지 기간 만료를 로그인 시점에 `ACTIVE`로 되돌리고 영구 정지를 `2099-12-31`로 두는 안이 있었지만 구현되지 않았다. 점주 정지 시 캠페인을 PAUSED로 바꾸는 처리는 FR-009에 있으나, 도메인 정의는 점주 쪽이 다른 도메인을 호출하지 않는다고 하여 서로 맞지 않는다. 상태 변경 API를 다시 채택할 때 함께 정한다.

## 6. 아직 정해지지 않은 것

| 항목 | 현재 기준 |
| --- | --- |
| 탈퇴 회원 행의 최종 파기 시점과 기간 | **정리 배치는 일단 구현하지 않는다(2026-10-06 결정).** 운영 배치에 "탈퇴자 보존 기간 경과 시 파기"가 있으나 기간 수치가 없고, 확정될 때 다시 정한다 |
| 파기 시 유지할 식별자 | 탈퇴 이력의 카카오 번호와 정지 이력을 지우면 제한 판정이 달라진다. 이력 보존 기간과 식별자 파기 기준을 함께 정한다 |
| 법정 보존 기간과 대상 | FR-086이 "법정 기간 데이터 보존"만 적었고 수치와 대상 데이터가 없음 |
| 점주 증빙서류 파기 기한 | 요구사항 명세서의 법적 요건에 "탈퇴 시 파기 기한 명시"가 있으나 값이 없음 |
| 점주가 `WITHDRAWN`이 되는 경로 | 점주 본인 탈퇴 API와 상태 변경 API가 모두 없음. 탈퇴 시 점주 이메일, 대표자 성명, 사업자등록번호 처리도 미정 |
| 점주 목록 `keyword`의 상호 검색 | 가게 도메인에 상호 검색 결과의 점주 ID 목록을 돌려주는 조회가 필요하며 제공 방식 미정 |
| 로그 보존 기간 | 레포에 설정이 없고 인프라 수집 시스템에서 정해야 함 |

## 7. 다른 도메인에 공개하는 회원 조회

`MemberQueryService`는 단건 `findById(Long memberId)`와 일괄 `findAllById(List<Long> memberIds)`를 제공한다. 상태만 필요한 호출자를 위한 `findCurrentStatus`와 `findCurrentStatuses`는 아래에 따로 적는다. [MemberInfo](../../../src/main/java/com/launchcatch/member/contract/MemberInfo.java)는 상태·온보딩·동의, 저장 좌표, 성별·연령대와 닉네임을 반환한다. HTTP 내 정보 DTO와는 별개의 계약이다.

`findCurrentStatus(Long memberId)`는 프로필을 조회하지 않고 현재 회원 상태만 `Optional<MemberStatus>`로 반환한다. 없는 회원은 빈 결과를 반환하며 조회 장애는 호출자에게 그대로 전달한다. 쿠폰 발급은 이 계약으로 현재 ACTIVE 회원인지 확인한다.

`findCurrentStatuses(Set<Long> memberIds)`는 프로필을 조회하지 않고 회원 ID를 키로 현재 상태를 `Map<Long, MemberStatus>`로 반환한다. 저장소를 한 번만 부르며 `ACTIVE`, `SUSPENDED`, `WITHDRAWN`을 `findCurrentStatus`와 같은 값으로 돌려준다. 없는 회원은 결과에서 빠지고 빈 집합은 저장소를 부르지 않고 빈 결과를 반환한다. 입력이 1,000개를 넘으면 `IllegalArgumentException`을 던진다. 조회 장애는 빈 결과로 바꾸지 않고 호출자에게 그대로 전달한다. 쿠폰 묶음 발급은 이 계약으로 묶음의 회원 상태를 한 번에 확인한다.

`findAllById`의 일괄 입력은 최대 1,000개다. 없는 회원은 결과에서 빠지며 순서를 보장하지 않는다. `MemberQueryServiceImpl`은 프로필을 함께 조회하고 프로필이 없으면 좌표·성별·연령대를 null로 반환한다. 회원 상태와 동의를 최종 사용 조건으로 판정하는 일은 호출자가 맡는다.

분석용 `MemberStatsQueryService.dailyStats(LocalDate)`의 반환값과 계정 생성·탈퇴를 집계하는 기준는 [구조와 동작 설계 3~5장](./member_구조와_동작_설계.md#3-저장)이 갖는다.

## 8. 구현을 대조한 범위

`MemberController`, `MemberProfileController`, 요청·응답 DTO, `MemberProfileService`, `MemberLocationService`, `MemberWithdrawalService`, `AdminMemberService`, `MemberRepositoryImpl`, `MemberQueryServiceImpl`, 회원·프로필 엔티티와 마이그레이션을 대조했다. 오래된 원본의 오류 번호 결번, 프로필 이미지 미수집, 위치 API 미구현과 좌표 3자리 반올림 설명은 현재 구현과 달라 옮기지 않았다.
