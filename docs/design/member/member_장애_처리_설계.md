# member 장애 처리 설계

이 문서는 이슈 #357의 분석용 회원 집계 조회가 기대는 대상을 훑었다. 기존 회원 HTTP API와 카카오 연동은 아직 훑지 않았다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| MySQL | 회원 일별 지표 COUNT 조회 | 기본 처리에 따라 오류로 올린다 |

## 벗어난 것

기본 처리를 벗어난 것은 없다.

## 유형별 점검

### 캐시

회원 일별 지표 조회는 캐시를 사용하지 않는다. 기존 member 기능의 캐시 사용은 아직 훑지 않았다.

### DB

| 시나리오 | 점검 결과 |
|---|---|
| 다운, 연결 거부 | 기본 처리에 따라 빈 값으로 바꾸지 않고 오류로 올린다 |
| 슬로우 쿼리, 응답 지연 | 공통 JDBC 소켓 타임아웃을 따른다. 별도 쿼리 타임아웃은 아직 정하지 않았다 |
| 커넥션 풀 고갈 | 공통 Hikari 풀 대기 상한을 넘으면 오류로 올린다 |
| 데드락 | 읽기 전용 COUNT라 쓰기 잠금을 잡지 않는다 |
| 락 대기 초과 | 읽기 전용 COUNT라 명시적 잠금을 잡지 않는다 |
| 제약 위반, 데이터 불일치 | 쓰지 않는 조회라 제약 위반을 만들지 않는다. 매핑 오류는 재시도하지 않고 올린다 |
| Primary 페일오버 | 읽기 실패를 오류로 올리고 analytics의 재집계에 맡긴다 |
| 복제 지연 | 별도 읽기 복제본을 사용하지 않는다 |

### 외부 API

회원 일별 지표 조회는 외부 API를 부르지 않는다. 기존 member 기능의 외부 API는 아직 훑지 않았다.

### 애플리케이션

| 시나리오 | 점검 결과 |
|---|---|
| 요청이 몰린다 | analytics의 일별 집계와 재집계만 호출한다. 별도 공개 HTTP 입구는 없다 |
| 대용량 조회 | DB가 COUNT만 반환하므로 회원 행을 메모리에 올리지 않는다 |
| 배포로 서버가 내려간다 | 상태를 쓰지 않는다. 호출자가 같은 영업일을 다시 조회할 수 있다 |
| 서버가 여러 대다 | member가 스케줄러를 등록하지 않는다. 실행 점유는 analytics와 ops가 소유한다 |

### 롤백 안 되는 효과

회원 일별 지표 조회에는 트랜잭션 밖으로 나가는 효과가 없다.

## 아직 정하지 못한 것

- 운영 회원 수에서 COUNT 쿼리가 목표 시간을 넘길 때 적용할 인덱스와 별도 쿼리 타임아웃은 아직 정하지 않았다.
- 기존 member 도메인의 캐시와 외부 API 장애 처리는 다음 member 기능 변경 전에 훑는다.
