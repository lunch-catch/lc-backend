# admin 장애 처리 설계

[공통 장애 처리](../장애_처리_설계_가이드.md)에서 벗어난 선택과 점검 범위를 적는다.
회전 결과 확인·보상의 세부 알고리즘은 [인증 설계](../auth/auth-api-design.md), 저장 구조는 [구조와 동작 설계](admin_구조와_동작_설계.md)가 소유한다.

기능 구현 담당자는 **gyudongjeong**이다. 2026-10-23에 확인한 develop을 기준으로 한다. 구현 근거는 closed 이슈 [#51 계정 발급](https://github.com/lunch-catch/lc-backend/issues/51), [#84 로그인](https://github.com/lunch-catch/lc-backend/issues/84), [#116 토큰 재발급](https://github.com/lunch-catch/lc-backend/issues/116), [#118 로그아웃](https://github.com/lunch-catch/lc-backend/issues/118)이다.
계정 목록 조회는 [#649](https://github.com/lunch-catch/lc-backend/issues/649), 로그인 감사 저장은 [#703](https://github.com/lunch-catch/lc-backend/issues/703)을 함께 대조했다.
특히 #84의 캐시 게시 실패 허용, #116의 DB 폴백·보상·결과 불명, #118의 부분 실패·감사 실패를 대조했다. 현재 동작은 코드·테스트를 기준으로 하며 #534는 문서 작성 이슈로만 구분한다.

신규 로그인 세션도 기존 Valkey 회전·MySQL 백업·복구 절차를 따른다. 현재 해시와 게시·폐기 순번의 관리 단위만 계정에서 세션으로 분리한다. 이 문서의 캐시 장애·복구 및 별도 감사 저장 정책은 두 경로에 공통으로 적용한다.

## 이 도메인이 기대는 대상

| 대상 | 쓰는 곳 | 처리 |
|---|---|---|
| MySQL 읽기 | `admin`의 계정 목록·계정·현재 RT 조회 | 기본(오류로 올린다). AT 폐기 기준 조회는 아래 예외를 따른다 |
| MySQL 쓰기 | 계정 발급·RT 갱신·RT와 AT 폐기 | 기본(트랜잭션을 되돌린다). 커밋 결과 확인·보상은 인증 설계가 소유한다 |
| Valkey RT·회전 기록 | 토큰 재발급의 조회·원자 회전 | 벗어났다. 아래 "RT 저장소" 절 |
| Valkey(커밋 뒤) | 로그인·토큰 재발급의 RT 게시, 로그아웃의 RT·AT 폐기 반영 | 벗어났다. 아래 "커밋 뒤 캐시 반영" 절 |
| Valkey AT 폐기 순번·기존 JWT 폐기 시각 | DB 검증 후 추가 확인 | 벗어났다. 아래 "AT 폐기 기준 검증" 절 |
| ops의 `AuditLogWriter` | 계정 발급·토큰 재발급 성공 감사 | 기본(업무 변경과 함께 롤백한다). 같은 프로세스 안의 호출이다 |
| ops의 `AuditLogWriter`(별도 TX) | 로그인 성공·식별 가능한 실패, 로그아웃 성공·토큰 재발급 실패 감사 | 벗어났다. 아래 "별도 감사 저장" 절 |

## 신규 세션의 실패 처리

| 실패 | 처리 |
|---|---|
| 로그인 DB 저장·JWT 서명 | 세션·순번을 같은 TX에서 롤백한다. 쿠키를 발급하지 않는다 |
| 갱신 DB 저장·성공 감사·JWT 서명 | 현재 세션 변경을 롤백하고 DB 결과 확인 뒤 조건부 Redis 복구·보상을 수행한다 |
| 재사용 감지 | 해당 세션 RT 폐기를 먼저 커밋하고 Redis를 정리한다. 기존 관리자 정책대로 AT는 유지하며 다른 기기에 영향 없이 AUTH-004를 반환한다 |
| AT 검증 DB 조회 | LENIENT는 인증을 거부하고 REQUIRED는 AUTH-002다 |
| 로그아웃 폐기 DB 저장 | 실패를 반환하며 성공 쿠키를 발급하지 않는다 |
| 커밋 응답 유실 | 성공을 단정하지 않고 쿠키를 발급하지 않는다. 클라이언트는 재로그인한다 |
| 커밋 뒤 로그인·로그아웃·재사용 감사 실패 | 이미 정한 인증 결과와 폐기를 유지하고 자격증명을 제외한 운영 로그를 남긴다 |

Redis 게시 실패는 DB 백업으로 성공을 유지한다. Redis 회전 타임아웃과 DB 결과 확인·보상, 로그아웃 Redis 정리 실패는 기존 정책을 따른다. 지연 게시·폐기는 세션별 순번으로 막는다. 상세 트랜잭션과 보존 한계는 [관리자 API 설계](admin-api-design.md)를 따른다.

## 벗어난 것

### 캐시: RT 저장소

기본 처리(통과)로 RT 검증을 생략할 수는 없다. Redis 조회 장애·부재와 회전의 타임아웃 이외 저장소 장애는 DB 폴백 대상이다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Redis에서 확인하지 못하면 모두 거부한다 | DB 폴백이 필요 없다 | 캐시 장애·유실만으로 유효한 현재 RT도 사용하지 못한다 |
| B. 허용된 조건에서만 DB의 현재 RT를 검증한다 | 캐시 장애·유실 중에도 현재 RT로 재발급할 수 있다 | DB 부하가 늘고 과거 재사용 기록은 복원하지 못한다 |

B를 따른다. 현재 해시·만료·`ACTIVE` 상태·관리자 역할을 행 잠금 아래 검증한다. 캐시 회전이 정상적으로 무효·재사용을 판정한 결과에는 폴백하지 않는다.
Redis 선행 회전 뒤 DB가 실패하면 현재 해시를 확인해 커밋 여부를 판단하고 조건부 보상한다. 회전 타임아웃·DB 커밋 결과를 확정하지 못하면 `AUTH-002`로 끝내고 새 쿠키를 내리지 않는다. 상세 조건은 [인증 설계](../auth/auth-api-design.md)의 관리자 "토큰 재발급" 절이 소유한다.
통과·폴백 횟수의 전용 지표와 경보는 미구현이며 A1에 남긴다.

### DB·캐시: AT 폐기 기준 검증

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Redis의 폐기 기준만 확인한다 | 요청마다 DB를 읽지 않는다 | 키 유실·장애 시 DB에서 폐기한 AT가 허용될 수 있다 |
| B. DB를 먼저 확인하고 Redis를 추가 검사한다 | Redis 유실과 독립적으로 DB 폐기를 지킨다 | 관리자 인증마다 DB 읽기가 추가된다 |

B를 따른다. DB 조회가 실패하면 `LENIENT`도 인증을 거부하고 `REQUIRED`는 `AUTH-002`를 반환한다. DB 검증을 통과한 AT만 Redis를 추가 검사하며, 이 검사 장애는 `LENIENT`에서 통과시키고 `REQUIRED`에서 `AUTH-002`로 거부한다.
근거는 [관리자 API 설계](admin-api-design.md)의 "발급 순번 검증과 배포" 절이다. Redis 장애를 통과시킨 횟수의 전용 지표와 경보는 A1에 남긴다.

### 롤백 안 되는 효과: 커밋 뒤 캐시 반영

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 같은 DB 트랜잭션에 반영할 일을 저장하고 재처리한다 | 커밋 뒤 중단돼도 작업을 다시 집어 올릴 수 있다 | 작업 저장과 재처리 기반이 추가된다 |
| B. 요청 안에서 DB 커밋 뒤 직접 호출한다 | 별도 큐 없이 처리하고 DB 잠금을 먼저 반환한다 | 중단·실패한 캐시 작업을 영속적으로 재처리하지 못한다 |

현재는 B다. 로그인·토큰 재발급은 DB 저장을 기준으로 하므로 RT 게시만 실패하면 로그를 남기고 성공을 유지한다. 후속 재발급의 DB 복구 조건은 [인증 설계](../auth/auth-api-design.md)를 따른다.
로그아웃의 Redis 정리 실패는 `AUTH-002`로 응답하고 성공 감사를 생략한다. 이미 커밋한 DB의 RT·AT 폐기는 유지되므로 이전 AT로 HTTP 재시도를 해야 폐기가 완성되는 구조는 아니다. 순번 비교로 지연된 이전 캐시 작업이 최신 상태를 덮지 못하게 한다.
근거는 [관리자 API 설계](admin-api-design.md)의 "로그인"·"로그아웃" 절이다. 영속 재처리 필요성은 A5에 남기고, 실패 횟수의 지표와 경보는 A1에 남긴다.

### 롤백 안 되는 효과: 별도 감사 저장

계정 발급·토큰 재발급 성공 감사는 업무 변경과 함께 롤백한다. 아래는 로그인 결과·로그아웃·재사용 감지에서 인증 처리와 감사 저장을 나누는 선택이다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 인증 변경과 감사를 같은 트랜잭션에 묶는다 | 업무 변경과 감사가 함께 남는다 | 감사 장애가 로그인·필수 폐기까지 롤백시킨다 |
| B. 인증 결과를 정한 뒤 별도 트랜잭션으로 감사를 쓴다 | 감사 장애가 원래 인증 결과를 바꾸지 않는다 | 감사 기록이 누락될 수 있다 |

B를 따른다. 로그인 성공과 식별 가능한 실패는 `REQUIRES_NEW` TX로 감사 저장하며 감사 실패가 원래 인증 결과를 바꾸지 않는다. 없는 계정·서비스 진입 전 거절은 DB 감사 대신 로그·메트릭으로 기록한다. 로그인 감사 장애는 `ADMIN_LOGIN_AUDIT_FAILED`와 `admin.login.audit.failed`로 남긴다. 운영 알림 연결·임계치는 합의에 따라 범위에서 제외하며 [로그인 감사 설계](admin-api-design.md#로그인-감사)가 근거다.

로그아웃 성공 감사만 실패하면 성공 응답을 유지한다. 토큰 재발급 실패 감사는 식별 가능한 관리자에 대해 별도로 시도하며, 감사 실패가 원래 오류나 이미 커밋한 RT 폐기를 취소하지 않는다.
각각 `ADMIN_LOGOUT_AUDIT_FAILED`, `ADMIN_TOKEN_REISSUE_AUDIT_FAILED` 운영 로그를 남긴다. 자동 재처리는 없으며 지표·경보와 영속 복구 필요성은 A1·A5에 남긴다. 근거는 [관리자 API 설계](admin-api-design.md)의 "저장 구조와 감사 로그"·"로그아웃" 절이다.

## 아직 정하지 못한 것

| ID | 남은 일 |
|---|---|
| A1 | 캐시 다운·복구 시 DB 폴백 집중과 BCrypt·계정 행 잠금 부하를 측정한다. 장애 중 통과·폴백·캐시 게시 실패·로그아웃과 재발급의 감사 누락 전용 지표와 경보는 미구현이다. 운영 로그만으로 공통 가이드의 지표 요구를 충족했다고 보지 않는다 |
| A2 | DB 지연·풀 고갈·재연결·페일오버를 실제 환경에서 검증한다. 공통 `application.yml`의 드라이버·풀 대기 제한과 DB 전용 트랜잭션의 `timeout`은 있으나 장애 주입 검증은 하지 않았다 |
| A3 | 관리자 서비스에 일반 데드락·락 대기 초과 자동 재시도는 없다. 안전한 재시도 범위·횟수와 소유자를 정한다. 회전 복구 확인은 업무 전체 재시도와 구분한다 |
| A4 | 공통 `server.shutdown: graceful` 설정은 있으나 DB 커밋 뒤 캐시·감사 호출 전 중단은 남는다. [관리자 API 설계](admin-api-design.md)의 "배포 확인 기록과 담당자 인계"에 따라 실제 요청 종료·구버전 혼용 방지·롤백을 검증한다 |
| A5 | 회전 결과 확인·보상 실패 시 저장소 오류를 반환하며 영속 재처리 큐는 없다. 로그인 실패 후 조건부 DB 정리도 실패하면 이번 RT 해시가 남을 수 있다. 회전 보상과 커밋 후 작업 실패의 영속 복구 필요성을 담당자가 판단한다 |
| A6 | 관리자 수가 적다는 합의로 목록을 페이지네이션 없이 조회한다. 계정 수 증가 시 메모리·응답 크기와 제한 필요성을 측정한다 |
