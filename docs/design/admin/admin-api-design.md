# 관리자 API 설계

HTTP 요청·응답은 [관리자 명세](../../api-spec/admin-api-spec.md)와 [인증 명세](../../api-spec/auth-api-spec.md#관리자)를 따른다. 이 문서는 관리자 계정 발급·목록 조회·로그인·토큰 재발급·로그아웃의 트랜잭션, 저장 구조와 장애 처리를 정의한다.

## 계정 발급

계약은 [관리자 계정 발급](../../api-spec/admin-api-spec.md#관리자-계정-발급)을 따른다.

### 서버가 하는 일

1. 발급자 권한과 Access Token 폐기 기준을 확인하고 로그인 ID 중복을 검사한다.
2. DB 트랜잭션 밖에서 초기 비밀번호를 BCrypt로 해싱한다. 비밀번호 평문은 저장하지 않는다.
3. DB 트랜잭션에서 발급자 행 잠금을 획득하고 현재 상태·권한과 요청 토큰의 폐기 여부를 재확인한다. 검증을 통과하면 새 계정을 `ACTIVE`로 저장한다.
4. 계정 저장과 `ADMIN_ACCOUNT_CREATE` 감사 로그 저장을 같은 트랜잭션으로 처리한다. 하나가 실패하면 함께 롤백한다.

### 정한 이유

비밀번호 해싱을 트랜잭션 밖에서 수행하여 행 잠금 시간을 줄인다. 계정과 감사 로그를 함께 저장하여 감사 기록이 없는 계정 발급을 막는다.
동시 요청의 로그인 ID 중복도 DB UNIQUE 제약으로 차단한다.
계정 발급과 로그아웃은 같은 발급자 행 잠금으로 순서를 확정한다. 로그아웃이 먼저 커밋되면 이전 순번 또는 폐기 시각 이전의 토큰으로 계정을 만들 수 없다. 계정 발급이 먼저 잠금을 얻어 커밋되면 발급은 유효하며 이후 로그아웃이 생성한 계정을 삭제하지 않는다.

## 계정 목록 조회

계약은 [관리자 계정 목록 조회](../../api-spec/admin-api-spec.md#관리자-계정-목록-조회)를 따른다.

1. 기존 계정 보안 체인에서 최고 관리자 역할을 검사한다. 서비스에서 토큰 폐기 기준을 필수 확인하고 DB의 현재 요청자 상태·권한을 다시 확인한다.
2. 읽기 전용 트랜잭션에서 활성 관리자 계정만 검색하고 생성 시각·PK 내림차순으로 반환한다. DB 쿼리에서 응답의 세 필드만 선택하므로 비밀번호 해시와 토큰 정보는 목록 조회 결과에 담기지 않는다.
3. 검색어를 소문자로 정규화하고 LIKE의 `%`, `_`, `!`를 이스케이프한다. 목록 조회는 계정이나 감사 로그를 변경하지 않는다.

관리자 수가 적다는 팀 합의로 페이지네이션을 적용하지 않는다. 목록 조회는 상태를 변경하지 않으므로 발급 경로의 행 잠금을 사용하지 않는다.

## 로그인

계약은 [관리자 로그인](../../api-spec/admin-api-spec.md#관리자-로그인)을 따른다.

### 서버가 하는 일

1. 관리자 계정을 조회하고 BCrypt로 비밀번호를 비교한다. 없는 계정에는 더미 해시로 비교한다. UTF-8 72바이트 초과 비밀번호도 더미 비교 후 동일한 실패로 처리한다.
2. 계정 없음, 비밀번호 불일치, 비활성 또는 관리자 역할이 아닌 경우 모두 동일한 `AUTH-001`을 반환한다.
3. DB 트랜잭션에서 관리자 행을 잠그고 현재 상태·역할·검증한 비밀번호 해시를 다시 확인한다.
4. 계정의 발급 순번을 증가시키고 그 순번으로 `admin_login_session`을 새로 만든다. 기존 세션과 `admin`의 배포 전 RT는 바꾸지 않는다.
5. RT의 SHA-256 해시·만료와 세션별 RT 게시 순번을 DB에 저장한다. 세션 순번을 AT의 `issuanceVersion`에 넣는다. JWT 서명도 같은 트랜잭션 안의 메모리 연산으로 끝낸다.
6. 커밋 뒤 세션별 Redis 키에 기존 `saveIfNewer` Lua로 RT를 게시한다. 게시 실패만으로 로그인을 실패시키지 않고 DB 백업을 유지한다. DB·서명 실패는 세션 생성과 순번 증가를 함께 롤백하며 쿠키를 발급하지 않는다. 로그인 감사는 별도 트랜잭션으로 기록한다.

### 정한 이유

계정당 RT 하나를 교체하면 다른 기기의 갱신이 실패한다. 로그인마다 세션을 분리하고 기존 Redis 회전·DB 백업·복구 구조를 세션별로 확장한다. 공용 `RefreshTokenRepository.scoped`가 동일한 Lua를 별도 키 공간에서 실행한다. Redis 소유자 ID에는 관리자 ID 대신 세션 PK를 넣고 DB에서 실제 관리자와 연결한다. 기존 계정 단위 키는 배포 전 토큰의 호환용으로 유지한다.

같은 브라우저의 탭은 HttpOnly 쿠키를 공유한다. 로그인 응답의 관리자 정보를 탭별 메모리에만 보관하는 프론트는 새 탭 진입 시 서버 인증을 확인해야 한다. 갱신 직렬화와 로그아웃 상태 동기화도 프론트가 수행하며 구체적인 연계 조건은 인증 명세를 따른다.

### 로그인 감사

관리자 로그인은 비밀번호를 보호하기 위해 본문 로깅에서 제외한다. 본문과 쿠키를 읽지 않는 감사 필터를
보안 체인 앞에 두어 입력 오류와 횟수 제한 거절도 기록한다. 서비스가 식별한 계정의 결과는 서비스에서 기록하며
필터는 나머지 요청을 기록한다.

애플리케이션 로그는 큐가 차면 버려질 수 있어 성공과 식별 가능한 계정의 실패를 감사 저장소에도 남긴다.
없는 계정은 `audit_log.admin_id`의 NOT NULL 제약 때문에 저장할 수 없으며 공격 시 쓰기 부하도 고려해 로그와 메트릭으로 처리한다.
IP별 횟수 제한은 분산 시도의 계정별 쓰기량 상한이 아니므로 계정별 실패 메트릭을 제공한다.
계정 잠금은 정상 관리자의 해제 절차까지 필요한 별도 보안 기능이어서 포함하지 않는다.
법령상 접속기록 요건과 보존의 한계는 [공통 로깅 근거](../../code-convention/logging-project-rationale.md#10-관리자-로그인-감사-필터를-따로-둔-이유)를 따른다.

식별 가능한 계정의 로그인은 서비스가 결과에 따라 `ADMIN_LOGIN_SUCCESS` 또는 `ADMIN_LOGIN_FAILED`를 기록한다. 성공과 일반 거절은 INFO, HTTP 5xx에 해당하는 실패는 ERROR로 기록한다. 메시지 필드는 `adminId`, `httpStatus`이고 시각은 로깅 프레임워크가 기록한다. 없는 계정과 서비스 진입 전 거절은 `AdminLoginAuditFilter`가 최종 HTTP 상태와 `durationMs`를 기록한다.

클라이언트 IP는 `ClientIpResolver.resolve(request)`로 정해 로그인 요청을 처리하는 동안 MDC의 `clientIp`에 넣는다. 기록 후 기존 값을 복원하고 기존 값이 없으면 제거한다. `traceId`는 변경하지 않는다. 본문과 쿠키를 읽지 않으며 비밀번호, 토큰 원문과 예외 메시지도 감사 로그에 담지 않는다.

로그인 서비스는 성공과 식별 가능한 계정의 실패를 `AuditLogWriter`로 별도 트랜잭션에 저장한다. `action=ADMIN_LOGIN`, `target`은 관리자 ID 문자열이며 `detail`은 `result=SUCCESS` 또는 `result=FAILURE`와 MDC의 `clientIp`를 담는다. 감사 저장 실패는 원래 로그인 결과를 바꾸지 않으며 `ADMIN_LOGIN_AUDIT_FAILED` ERROR와 `admin.login.audit.failed` 메트릭을 남긴다.

계정별 실패는 `admin.login.failed`의 `adminId` 태그로 센다. 없는 계정과 횟수 제한 거절은 DB에 저장하지 않고 `admin.login.rejected`의 `reason=UNKNOWN_ACCOUNT`, `reason=RATE_LIMIT`로 센다. 로그인 ID, IP와 자격증명은 메트릭 태그에 넣지 않는다. 이번 후속 작업은 로그와 메트릭까지 제공하며 운영 알림 연결과 임계치 설정은 합의에 따라 범위에서 제외한다. 서비스가 식별 가능한 계정의 결과를 기록하면 필터는 같은 요청을 중복 기록하지 않는다. 처리 표시는 요청 종료 시 제거해 다음 요청으로 넘어가지 않게 한다.

## 토큰 재발급

1. `AdminTokenService`가 43자 Opaque Token 형식을 확인한다. `AdminSessionService`는 세션 전용 Redis 기본 레코드에서 세션 PK와 역할을 읽는다.
2. 기존 `compareAndRotate` Lua로 RT를 원자 회전한다. 이전 RT는 원래 남은 TTL 동안 tombstone으로 남긴다. 정상 `NOT_FOUND` 결과를 DB로 우회하지 않는다.
3. 관리자 행, 세션 행 순서로 잠그고 현재 계정 상태·역할·전체 폐기 기준과 세션의 폐기·만료·이전 해시를 검증한다. 새 해시·만료와 증가한 RT 게시 순번, 성공 감사를 같은 DB 트랜잭션으로 저장한다. AT의 세션 순번은 유지한다.
4. 커밋 후 새 RT를 `saveIfNewer`로 게시한다. Redis 게시 실패만으로 성공을 취소하지 않는다. 지연된 이전 게시와 폐기는 세션별 순번으로 막는다.
5. Redis 재사용 감지 시 해당 세션의 `refresh_revoked`와 증가한 RT 게시 순번을 먼저 커밋하고 캐시를 폐기한다. 별도 실패 감사를 시도하고 `AUTH-004`를 반환한다. 기존 관리자 정책대로 AT 폐기 기준은 바꾸지 않는다. 다른 세션의 AT·RT도 유지한다.

### 장애 복구

- Redis 조회 장애·캐시 부재는 DB의 현재 RT 해시로 세션을 찾는다. 회전의 타임아웃 이외 저장소 장애도 DB 해시·만료·계정 상태 검증으로 복구한다. 정상적인 무효·재사용 판정을 우회하지 않는다.
- Redis 회전 타임아웃은 새 RT 레코드와 소유자를 후속 조회해 성공을 확인한 경우에만 DB 회전을 진행한다. 결과 미확정은 `AUTH-002`이며 새 쿠키를 발급하지 않는다.
- Redis 선행 회전 뒤 DB 실패는 별도 트랜잭션으로 현재 해시를 재검사한다. 새 해시 커밋이 확인되면 성공으로 복원한다. 이전 해시와 롤백이 확인되면 이번 Redis 회전이 그대로인 경우에만 `rollbackRotation`으로 복구한다.
- 더 최신 회전·폐기 또는 복구 결과 불명 상태에서는 이번 새 해시만 보상 정리하고 오류를 반환한다. DB 장애 중 과거 Redis tombstone 전체를 복원하지 못하는 한계도 기존과 같다.

같은 RT의 동시 요청을 멱등 성공으로 바꾸지 않는다. 쿠키를 공유하는 탭 간 갱신 직렬화는 프론트 연계 조건이다. 서로 다른 세션의 동시 회전은 각각 성공한다.

## 로그아웃

계약은 [인증 명세의 관리자 절](../../api-spec/auth-api-spec.md#관리자)을 따른다.

1. 인증한 AT의 관리자 ID·역할·`issuanceVersion`으로 세션을 찾는다. 관리자 행, 세션 행 순서로 잠그고 계정·세션을 재검사한다.
2. 해당 세션을 `revoked=true`로 커밋한다. 계정 전체 AT 폐기 순번이나 다른 세션의 RT는 바꾸지 않는다.
3. 커밋 후 그 세션의 Redis 폐기 순번을 게시하고 해당 해시를 정리한다. Redis 실패는 `AUTH-002`이며 DB 폐기는 유지한다. 성공 감사는 캐시 정리 후 별도 트랜잭션에서 기록하고 감사 실패만으로 폐기를 취소하지 않는다.
4. 발급 때와 동일한 Path의 인증 쿠키를 삭제한다. 같은 쿠키를 공유하는 탭들도 로그아웃되고 다른 기기는 유지된다.

### 배포 전 단일 기기 토큰의 호환 처리

세션 Redis 레코드와 DB 현재 해시에 해당하지 않는 RT는 기존 `AdminTokenService`의 Redis 회전·DB 복구로 처리한다. 상세 절차는 [인증 설계](../auth/auth-api-design.md#배포-전-단일-기기-토큰)를 따른다. 세션이 없는 AT의 로그아웃은 기존 `AdminLogoutService`의 계정 전체 DB 폐기 후 Redis 정리를 유지한다. Redis 정리가 실패해도 DB 폐기는 유지하며 `AUTH-002`를 반환한다. 이 전체 폐기 기준은 신규 세션에도 적용된다. 신규 세션을 발급하려면 다시 로그인한다.

## 발급 순번 검증과 배포

신규 세션의 순번은 로그인 시 계정 행 잠금 아래 한 번 할당하고 회전해도 유지한다. AT 검증은 별도 읽기 트랜잭션에서 세션과 현재 계정을 조회해 역할·활성 상태·세션 만료·폐기와 계정 전체 폐기 순번을 함께 확인한다. 신규 세션은 Redis 추가 검사를 하지 않는다.

세션에 해당하지 않는 AT만 기존 DB 폐기 순번·시각과 Redis의 추가 검사를 따른다. DB 장애는 LENIENT에서도 거부하며 REQUIRED에서는 `AUTH-002`를 반환한다.

admin V4는 신규 세션 테이블만 만들며 기존 RT·폐기 데이터를 지우지 않는다. 신규 세션을 모르는 서버는 세션 폐기를 검증하지 못하므로 이전 서버와 혼용하지 않는다. 전환 시 모든 서버를 세션 검증 버전으로 교체하고 두 기기의 로그인·한쪽 로그아웃·다른 쪽 갱신을 확인한다. 롤백도 세션 폐기 검증을 유지하는 버전만 사용한다. 전환 전 V3의 폐기 데이터도 보존한다.

아래 V3 최초 전환 절차는 기존 폐기 기준 도입에 대한 운영 인계 자료다.

### 배포와 롤백 절차

현재 backend의 deploy.yml은 infra/scripts/deploy.sh를 호출하는 롤링 배포다. 배포 스크립트와 워크플로는 인프라 담당자가 소유한다. 관리자 로그아웃 PR에서는 이 파일들을 변경하지 않으며, 아래 절차를 운영자와 함께 수행하고 결과를 기록한다. 현재 자동화는 배포 도중 구버전 혼용 금지와 DB 폐기 검증을 지원하는 이미지로의 롤백 제한을 강제하지 않는다. 실제 운영 배포·롤백은 아직 검증하지 않았다.

1. 릴리스 담당자와 최초 전환 일정을 정한다. main 병합은 운영 배포를 자동 실행하므로 병합 전에 트래픽 차단과 기존 앱 중지 준비를 완료한다. develop 병합의 개발 배포도 별도로 기존 앱 중지 후 신규 앱 기동 순서를 확인한다. 준비되지 않은 상태에서는 일반 자동 배포로 최초 전환을 시작하지 않는다.
2. 관리자 인증 경로와 관리자 토큰을 허용하는 모든 보호 경로의 외부 트래픽을 차단한다. member·billing 등 다른 도메인의 관리자 접근 경로도 포함한다. 차단은 애플리케이션 외부에서 수행하고 실제 차단 응답을 확인한다. 진행 중인 요청을 종료하고 구버전 앱을 모두 중지한다. ASG 자동 복구·스케일링과 구버전 배치가 이전 앱을 다시 기동하지 않도록 인프라 담당자가 조치한다.
3. 구버전이 요청을 처리하지 않는 상태에서 admin V3 마이그레이션을 적용한다. 새 앱 기동 시 Flyway가 적용하는 경우에도 기존 앱 중지가 먼저여야 한다. 기존 발급 순번까지 폐기하고 기존 JWT 폐기 시각을 설정하므로 배포 전 Access Token은 무효화된다. 마이그레이션 DB 세션의 시간대가 애플리케이션과 같은 Asia/Seoul인지 확인한다.
4. DB 폐기 검증이 포함된 버전으로 모든 인스턴스를 교체한다. 인스턴스별 실제 이미지 SHA와 구버전 인스턴스가 0개인지 확인한다. 배포 스크립트의 완료 로그와 API 문서 응답만으로 인증 검증이 완료됐다고 판단하지 않는다.
5. 트래픽 차단을 유지한 채 새 로그인 성공, 배포 전 JWT 거부, 로그아웃 JWT 거부를 확인한다. 격리된 검증 환경에서 폐기 Redis 키가 없는 경우에도 거부되는지 확인한다. 운영 Redis의 키를 임의로 삭제하지 않는다. 검증 결과와 테스트한 이미지 SHA를 기록한 뒤 트래픽을 재개한다.
6. 롤백 대상은 DB 폐기 검증을 유지하는 것으로 검증한 이미지 SHA만 별도로 기록하고 인프라 담당자가 그 이미지로 복구한다. V3 컬럼과 폐기 데이터를 보존한다. 최초 전환 실패 시 트래픽 차단을 유지하며 검증 없는 구버전으로 자동 복귀하지 않는다. DB 폐기 검증이 없는 버전으로의 강제 복귀는 일반 롤백에서 제외하고 JWT 서명 키 교체를 포함한 별도 사고 대응으로 다룬다.

### 배포 확인 기록과 담당자 인계

릴리스마다 다음 표에 실행 기록을 남긴다. 체크 항목을 작성한 것과 실제 검증을 완료한 것을 구분한다. 현재는 확인 기록이 없으므로 아래 항목을 완료했다고 판단하지 않는다. 토큰 원문·해시·비밀번호는 기록하지 않는다.

| 확인 항목 | 담당 | 남길 근거 | 현재 상태 |
| --- | --- | --- | --- |
| 운영·개발 최초 전환 일정과 자동 배포 순서 | 릴리스·인프라 담당자 | 대상 환경, 배포 SHA, 병합·차단 계획 | 미확인 |
| 모든 관리자 토큰 허용 경로 차단 | 인프라 담당자 | 차단 시각, 실제 차단 응답, 우회 진입점 확인 | 미확인 |
| 기존 요청 종료와 구버전 앱 중지 | 인프라 담당자 | 앱·배치 중지 결과, 자동 재기동 방지 조치 | 미확인 |
| V3 적용과 DB 세션 시간대 | 관리자·인프라 담당자 | 마이그레이션 결과, Asia/Seoul 확인 | 미확인 |
| 전체 서버의 실제 이미지 일치 | 인프라 담당자 | 인스턴스별 SHA, 구버전 0대 조회 결과 | 미확인 |
| 로그인 성공과 폐기 JWT 거부 | 관리자 담당자 | 검증 이미지 SHA, 요청 조건, 응답 상태 | 미확인 |
| Redis 폐기 키가 없는 경우의 거부 | 관리자 담당자 | 격리 검증 환경, 이미지 SHA, 응답 상태 | 미확인 |
| 호환 롤백 이미지와 폐기 데이터 보존 | 관리자·인프라 담당자 | 검증된 롤백 SHA, V3 보존 확인 | 미확인 |
| 검증 후 트래픽 재개 | 인프라 담당자 | 재개 시각, 외부 인증 검증 결과 | 미확인 |

이 PR에서 보완하는 것은 최초 전환·롤백의 실행 조건과 확인 기록이다. 수동 절차만으로 실수나 우회를 기술적으로 막을 수는 없다. 배포·롤백의 자동 강제가 필요하면 팀장님 담당의 lc-infra와 워크플로에서 별도 작업으로 반영한다. 그 전에는 인프라 담당자의 실행 확인 없이 배포 안전성이 보장됐다고 판단하지 않는다.

## 저장 구조와 감사 로그

### `admin`

로그인 응답의 `adminId`, `name`, `role`은 각각 `admin_id`, `name`, `role` 컬럼에 대응한다.

| 필드·처리 | DB 컬럼 |
| --- | --- |
| 관리자 식별자 | `admin_id` |
| 로그인 ID | `login_id` |
| BCrypt 비밀번호 해시 | `password_hash` |
| 이름 | `name` |
| 역할 | `role` |
| 상태 | `status` |
| Refresh Token SHA-256 해시 | `refresh_token_hash` |
| Refresh Token 만료 시각 | `refresh_token_expires_at` |
| 로그인·재발급·폐기 순번 | `refresh_token_issuance_version` |
| Access Token 폐기 순번 상한 | `access_token_revoked_version` |
| 기존 JWT 폐기 시각 | `access_token_valid_after` |
| 비활성화 시각 | `deleted_at` |
| 생성·수정 시각 | `created_at`, `updated_at` |

- `login_id`는 UNIQUE다.
- `role`은 `ADMIN`, `SUPER_ADMIN`, `status`는 `ACTIVE`, `DELETED`다.
- Refresh Token 해시와 만료 시각은 둘 다 `NULL`이거나 둘 다 값이 있어야 한다.
- `DELETED` 상태는 `deleted_at`이 있어야 하고 Refresh Token 해시가 없어야 한다. 그 외 상태는 `deleted_at`이 없어야 한다.
- 발급 순번은 기본값 `0`의 음이 아닌 BIGINT다. 마이그레이션 `V2__admin_refresh_token_issuance_version.sql`에서 추가한다.
- Refresh Token 원문은 DB에 저장하지 않는다. `admin`의 RT 열은 배포 전 단일 기기 토큰의 호환용이다. 신규 세션 저장은 아래 표를 따른다.

| 테이블 | 저장하는 것 | 제약과 조회 |
|---|---|---|
| `admin_login_session` | 관리자 ID, AT 세션 순번, 역할, 현재 RT 해시·만료, RT 게시 순번, RT 폐기와 세션 폐기 여부 | `(admin_id, issuance_version)`과 현재 해시 UNIQUE |

| Redis 데이터 | 키 |
|---|---|
| 세션 RT·tombstone | `adminSession:refreshToken:{hash}` |
| 현재 RT 포인터 | `adminSession:activeRefreshToken:{role}:{sessionId}` |
| 게시·폐기 순번 | `adminSession:refreshTokenIssuanceVersion:{role}:{sessionId}` |

기본 레코드와 포인터는 RT 만료까지 유지하며 tombstone은 이전 RT의 남은 TTL을 따른다. 순번 키는 기존 저장소처럼 TTL을 두지 않는다. DB 세션 행이 없으면 호환 AT로 판정되므로 만료·폐기 행은 임의로 삭제하지 않는다. 자동 정리는 별도의 안전한 보존 정책을 정한 뒤 추가한다.

### `audit_log` (`ops` 소유)

| 이벤트 | `admin_id` | `action` | `target` | `detail` | 실패 정책 |
| --- | --- | --- | --- | --- | --- |
| 계정 발급 성공 | 발급자 ID | `ADMIN_ACCOUNT_CREATE` | 새 계정의 `loginId` | `role=ADMIN` 또는 `role=SUPER_ADMIN` | 계정 저장과 함께 롤백 |
| 토큰 재발급 성공 | 대상 관리자 ID | `ADMIN_TOKEN_REISSUE` | 관리자 ID 문자열 | `result=SUCCESS` | DB 회전과 함께 롤백 |
| 재발급 중 기록 대상 실패 | 대상 관리자 ID | `ADMIN_TOKEN_REISSUE` | 관리자 ID 문자열 | `result=FAILURE;reason=<사유>` | 별도 트랜잭션, 감사 실패 시 운영 로그 |
| 로그아웃 성공 | 대상 관리자 ID | `ADMIN_LOGOUT` | 관리자 ID 문자열 | `result=SUCCESS` | 폐기 후 별도 트랜잭션, 감사 실패만으로 성공 취소하지 않음 |

재발급 실패 감사는 식별 가능한 관리자에 대해 `REUSE_DETECTED`, `ROTATION_RESULT_UNKNOWN`, `DB_ROTATION_FAILED`, `DB_FALLBACK_FAILED`, `COMPENSATION_FAILED` 등의 사유로 기록한다. 토큰 누락·형식 오류 등 모든 실패에 감사 로그가 생기는 것은 아니다.
