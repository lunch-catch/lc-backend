# billing 성능 개선

정산이 앞으로 해야 할 성능 작업을 한 곳에 모은다. 아직 측정한 값이 없다. 아래 후보는 모두 가정이고, 측정이 병목을 가리킨 뒤에만 적용한다.

이 문서는 두 갈래를 다룬다. 하나는 노출 차감 경로(`PointDeductorImpl`)이고 다른 하나는 분석이 부르는 집계 조회(`BillingStatsQueryService`, 이슈 #352)다. 목표 TPS와 측정 계획은 [정산 배치 설계](./billing-batch-design.md)가 소유하고, 요청 하나의 비용 표는 [구조와 동작 설계 11장](./billing_구조와_동작_설계.md#11-성능)이 소유한다. 여기서는 다시 적지 않는다.

## 1. 현재 상태

| 항목 | 상태 |
|---|---|
| 노출 차감 목표 | 초당 10,000건(NFR-014). 달성하는지 측정하지 않았다 |
| 부하 측정 도구 | 없다. `PointDeductorImpl` 의 `TODO(부하 테스트 실행)` 로만 남아 있다(이슈 #193 작업 8) |
| 집계 조회 실행 시간 | 측정하지 않았다 |

`PointDeductorImpl` 의 주석이 가리키는 `노출 차감 성능 개선 선택지.md` 와 `노출 차감 부하 테스트.md` 는 이 저장소에 없다. 저장소 밖 문서라 이 문서에 옮기지 않았다. 후보의 이름(A, B-1 등)은 그 문서의 것을 코드 주석에서 가져왔다.

## 2. 노출 차감 경로

노출 하나가 Valkey 왕복 1회와 INSERT 2건(`deduction_result`, `point_ledger`)을 부른다. 과금 10,000건/초면 INSERT만 최대 20,000건/초다.

측정은 구간을 나눠 위에서부터 본다. 앞 구간이 목표에 못 미치면 뒤 구간을 고쳐도 소용없다.

| 순서 | 구간 | 먼저 볼 것 |
|---|---|---|
| 0-a | Valkey 왕복 1회 | Lua 내용과 커넥션 설정. 여기서 1만 건이 안 나오면 DB 개선은 소용없다 |
| 0-b | `deduction_result` INSERT | 아래 후보 A, C-1, B-1, B-2 |
| 0-b' | `point_ledger` INSERT | 아래 후보 C-2, B-1, F |

| 후보 | 내용 | 바꾸는 것 | 비용 |
|---|---|---|---|
| A | `serveId` 를 v7 UUID 로 발급 | 광고 서빙이 발급 방식을 바꾼다 | 다른 도메인과 합의가 필요하다 |
| C-1 | `deduction_result` 의 기본 키를 `serve_id` 로 | 마이그레이션 | 스키마 변경이다 |
| C-2 | DEDUCT 가 쓰지 않는 원장 조회 인덱스를 점검한다 | 마이그레이션 | 인덱스가 줄면 다른 조회가 느려질 수 있다 |
| B-1 | 두 INSERT 를 한 요청으로 보낸다 | 차감 전용 데이터소스 | 커넥션 구성이 늘어난다 |
| B-2 | BILLED 면 `deduction_result` INSERT 를 생략한다 | 명세 변경(4단계) | 판정 기록의 의미가 바뀐다 |
| F | 원장을 분 단위 묶음 행으로 쓴다 | 명세 변경(4단계) | 원장이 노출 단위 근거가 아니게 된다 |
| E-1 | 커넥션 풀 설정 | 설정 | 커밋 비용(fsync)이 병목일 때 INSERT 자리가 아니라 이쪽을 본다 |

명세를 바꾸는 후보(B-2, F)는 맨 마지막에 둔다. 적용 전후는 `./gradlew perfTest` 로 비교한다. 하네스는 `PointDeductor` 만 부르므로 바꾸지 않는다.

계획 캐시의 기본 크기 100,000과 만료 24시간도 측정 전 임시값이다.

## 3. 집계 조회(#352)

일 1회 배치라 노출 차감 경로와 달리 쓰기 부하는 없다. 문제는 원장과 판정이 쌓일수록 읽는 양이 늘어난다는 점이다.

| 쿼리 | 읽는 방식 | 늘어나는 비용 |
|---|---|---|
| CHARGE, REFUND, ADJUST 합 | 기록 시각 범위. `idx_point_ledger_owner_created` 는 `owner_id` 가 앞이라 점주 없이 시각만으로는 쓰지 못한다 | 날짜 범위 풀 스캔 |
| 그날 합계(`ledgerSum`) | 위와 같다 | 위와 같다 |
| 미소진 잔액 | 그날 말 이전의 모든 행 합. 누적이다 | 원장 전체를 읽고 날마다 커진다 |
| 과금 상태 수 | `deduction_result` 를 영업일만으로 묻는다. 인덱스가 `campaign_id` 앞이다 | 영업일 전체 스캔 |

### 3.1. 누적 쿼리와 전날 스냅샷

`ledgerSum` 은 그 영업일 하루치만 더한다. 누적인 것은 미소진 잔액뿐이다.

정산에는 잔액 스냅샷이 없다. `PointLedger` 가 잔액 컬럼과 캐시를 두지 않는 설계라 정산은 날짜별 잔액을 저장하지 않는다. 분석의 `daily_settlement_analytics.unspent_balance` 에 날짜별 값이 저장되지만, 정산이 분석을 읽으면 의존 방향이 거꾸로 간다.

그래도 스냅샷 방식은 쓸 수 있다. 원장은 추가만 하고 `created_at` 이 단조롭게 늘어서, 영업일이 끝난 뒤 그날 말까지의 누적 값은 바뀌지 않는다. 그러면 분석이 `전날 말 미소진 잔액 + 그날 합계` 로 계산해도 누적 쿼리와 같은 값이 나온다. 다만 조건이 둘 있다.

| 조건 | 이유 |
|---|---|
| 그날 합계가 미소진 잔액과 같은 유형을 더해야 한다 | 다르면 날마다 오차가 쌓인다. 지금은 같은 네 유형이다 |
| 전날 값이 없거나 틀리면 그 날부터 처음부터 다시 계산한다 | 실패한 날 뒤로 오차가 이어진다 |

### 3.2. 미소진 잔액의 정의

분석 스키마의 `unspent_balance` 주석을 따라 `CHARGE + REFUND + ADJUST + DEDUCT` 의 누적 합으로 정했다. 점주 잔액에 예약 중 포인트(예약액 - 소진 - 해제)를 더한 값과 같아서 해제가 실패해 예약이 남은 날도 쓰이지 않은 포인트를 센다. 그날 합계도 같은 네 유형을 더하므로 3.1 의 스냅샷 계산이 성립한다.

이 정의는 analytics 스키마 주석에서 읽었고, 분석 쪽에서 맞다고 확인받았다.

### 3.3. 인덱스 후보

측정 전에는 만들지 않는다. 노출마다 DEDUCT 를 쓰는 경로에 인덱스 유지 비용을 얹기 때문이다.

| 후보 | 대상 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| `point_ledger(created_at)` 또는 `(entry_type, created_at)` | 기록 시각 범위 쿼리 | 날짜 범위 스캔이 인덱스 범위 스캔이 된다 | DEDUCT INSERT 마다 인덱스 한 개를 더 쓴다 |
| `deduction_result(business_date, campaign_id, billing_status)` | 과금 상태 수, DEDUCT 의 영업일 조인 | 영업일만으로 묻는 쿼리가 인덱스를 탄다 | 판정 INSERT 마다 인덱스 한 개를 더 쓴다 |
| 3.1 의 스냅샷 계산 | 미소진 잔액 | 누적 스캔이 사라진다 | 분석의 전날 값에 기대는 계약이 생긴다 |

두 인덱스는 노출 차감 INSERT 를 느리게 하므로 2장의 측정에서 INSERT 구간 여유를 먼저 본다. 여유가 없으면 인덱스보다 3.1 의 스냅샷 계산이 맞다.
