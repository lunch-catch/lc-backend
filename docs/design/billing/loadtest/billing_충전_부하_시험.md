# 충전 부하 시험

점주의 충전(주문 생성과 승인 확정)이 몰릴 때 두 가지를 본다. 하나는 충전이 빠지거나 두 번 들어가지 않는지다. 다른 하나는 한 점주에게 몰린 충전이 다른 점주의 충전을 느리게 하지 않는지다.

시나리오와 SQL 은 저장소 루트의 `loadtest/billing/` 이 갖는다. 환경을 띄우고 내리는 일은 lc-infra 의 `scripts/member-env.sh` 가 갖는다.

## 1. 시나리오

`charge_concurrency.js` 는 두 시나리오를 함께 돌린다.

| 시나리오 | 한 반복이 하는 일 | 한 반복의 요청 수 |
|---|---|---|
| `charge` | 주문을 하나 만들고 한 번 승인 확정한다 | 2 |
| `duplicate` | 주문을 하나 만들고 같은 승인 확정을 동시에 두 번 보낸다 | 3 |

결제는 토스 대신 부하 시험 목(`LoadTestPaymentGateway`)이 200ms 뒤 승인한다. 시험 점주는 `seed.sql` 이 4,000만 대역에 2,000명을 넣는다.

앱은 점주마다 주문과 승인 확정을 합쳐 10초에 3회까지 받는다. 넘친 요청은 429 로 돌려보낸다. 상한을 둔 이유는 [구조와 동작 설계 7장의 결정 표](../billing_구조와_동작_설계.md#중복-쓰기와-점주-잔액의-결정)가 갖는다. k6 는 429 를 실패로 세지 않고 `rate_limited` 로 따로 센다.

## 2. 회차

| 회차 | 점주 대역 | 점주 수 | 초당 `charge` | 초당 `duplicate` | 보는 것 |
|---|---|---|---|---|---|
| r3 | 40000001 | 1 | 50 | 20 | 한 점주에게 몰린 충전 |
| c1 | 40000002 ~ 40001001 | 1,000 | 10 | 3 | 정상 부하의 충전. `NO_RATE_LIMIT=true` 로 돌려 429 가 하나라도 나오면 실패로 본다 |
| 워밍업 | 40001002 ~ 40002000 | 999 | 10 | 3 | 앱을 데운다. 결과에 적지 않는다 |

c1 은 점주 한 명이 10초에 3회를 넘지 않게 둔다. 점주가 2명 이상이면 두 시나리오가 점주 대역을 초당 반복 수의 비율로 나눠 쓴다. 그래서 c1 은 점주 한 명에게 약 77초마다 돌아온다.

부하는 10초 동안 0에서 목표까지 올린 뒤 2분 유지한다.

## 3. 판정

| 항목 | 기준 |
|---|---|
| 정합성 | `verify.sql` 의 점검 9개가 모두 0 이다. 재조회와 재예약 워커가 남은 행을 처리한 뒤에 본다 |
| 승인 수 | k6 의 `approved_payments` 를 회차끼리 더한 값이 `verify.sql` 의 `approved_payments` 와 같다 |
| 격벽 | r3 와 c1 을 함께 돌려도 c1 의 실패율이 0% 이고 `rate_limited` 가 0 이다. 승인 확정 p95 가 c1 단독일 때와 같은 수준이다 |
| 상한 | r3 의 넘친 요청이 429 로 끝나고 그 밖의 실패가 없다 |

## 4. 돌리는 순서

1. `member-env.sh up` 으로 환경을 띄운다.
2. `seed.sql` 로 시험 대역을 넣는다.
3. 워밍업을 1분 돌린다.
4. 1분 기다려 재예약 워커가 워밍업의 대기 행을 처리하게 한 뒤 `seed.sql` 을 다시 넣는다. 앱은 다시 띄우지 않는다.
5. r3 와 c1 을 한 부하 생성기에서 함께 돌린다.

       k6 run ... -e OWNERS=1 -e RATE=50 -e DUP_RATE=20 -e DURATION=2m loadtest/billing/charge_concurrency.js
       k6 run ... -e OWNER_OFFSET=1 -e OWNERS=1000 -e RATE=10 -e DUP_RATE=3 -e NO_RATE_LIMIT=true -e DURATION=2m loadtest/billing/charge_concurrency.js

6. k6 가 끝나면 바로 `verify.sql` 을 돌린다. `UNKNOWN`, `stuck_attempt`, `reservation_pending` 이 0 이 아니면 2~3분 간격으로 다시 돌린다.
7. `UNKNOWN` 이 두 번 연달아 줄지 않으면 재조회 아웃박스의 `last_error` 를 본다.

## 5. 결과

### 2026-11-04, 상한을 두기 전 (#1122 를 연 회차)

앱 이미지는 develop 9128fd82 다. 회차를 따로 돌렸다.

| 회차 | 실패율 | 승인 확정 p95 | 주문 p95 | k6 승인 수 | 정합성 |
|---|---|---|---|---|---|
| c1 단독 | 0% | 299ms | 48ms | 1,624 | 점검 전에 다음 seed 가 데이터를 지워 보지 못했다 |
| r3 단독 | 1.1% | 6.21s | 4.08s | 6,166 | 9개 0, 워커 처리 뒤 `UNKNOWN` 11 |

r3 가 도는 동안 앱 서버마다 커넥션 대기가 190 가까이 올랐다. 점주 계정 행의 잠금 줄에 선 트랜잭션이 각자 공용 커넥션을 쥐고 기다려, 행을 잠그지 않는 주문 생성까지 느려졌다. `UNKNOWN` 11건은 부하 시험 결제 목이 승인 기록을 서버끼리 함께 보지 못해 남았다(#1123).

### 2026-11-13, 상한을 둔 뒤 (#1122 합격 시험)

앱 이미지는 develop 648295d7, 시나리오는 fc1f3d9 다. r3 와 c1 을 함께 돌렸고 구간은 10:45:15 ~ 10:47:26 (KST) 이다.

| 회차 | 요청 수 | 실패율 | `rate_limited` | 승인 확정 p95 | 중복 승인 확정 p95 | 주문 p95 | k6 승인 수 |
|---|---|---|---|---|---|---|---|
| r3 | 8,793 | 0% | 8,754 | 13.26ms | 19.17ms | 16.94ms | 3 |
| c1 | 3,620 | 0% | 0 | 292.95ms | 289.23ms | 43.53ms | 1,623 |

p95 는 유지 구간의 값이다. r3 의 응답 시간은 대부분 DB 에 가기 전에 돌아온 429 의 것이다.

`verify.sql` 은 k6 직후에 승인 1,626건, `REQUESTED` 33건, 점검 9개 모두 0 이었다. `UNKNOWN` 과 `reservation_pending` 도 0 이라 워커를 기다리지 않았다.

대시보드는 같은 구간의 [05 부하 시험](./charge-pair1/lc-loadtest.png)과 [03 앱과 JVM](./charge-pair1/lc-app-jvm.png)이다. 03 에서 커넥션을 얻지 못하고 시간 제한에 걸린 횟수는 구간 내내 0 이었다.

1. **c1 은 r3 와 함께 돌아도 단독일 때와 같았다.** 실패율 0%, 429 0건이고 승인 확정 p95 는 292.95ms 로 11-04 단독 회차(299ms)와 같은 수준이다. 몰린 요청이 커넥션을 받기 전에 429 로 돌아가 다른 점주의 커넥션을 먹지 않았다.
2. **승인 수가 맞다.** k6 의 승인 3 + 1,623 = 1,626 이 DB 와 같다.
3. **`REQUESTED` 33건은 r3 의 주문 가운데 승인 확정이 429 를 받은 것이다.** 결제대행사를 부르지 않아 `pg_tid` 가 없고 돈이 움직이지 않았다. `stuck_attempt` 0 이 그 근거다.
4. **몰리는 동안에는 그 점주 자신의 승인 확정도 막힌다.** 상한이 주문과 승인 확정을 합쳐 세므로, 창마다 먼저 온 주문이 3회를 채우면 뒤따른 승인 확정이 429 를 받는다. r3 는 2분 동안 3건만 승인됐다. 정상 충전은 10초에 3회를 넘지 않아 이 일을 겪지 않는다. 몰린 점주의 클라이언트는 `Retry-After` 뒤에 다시 시도한다.
5. **#1123 의 경로는 이 회차에서 지나지 않았다.** 상한이 풀이 바닥나는 것을 막아 결과를 기록하지 못한 결제(`UNKNOWN`)가 생기지 않았다. 다른 서버의 목이 승인한 결제를 승인으로 답하는지는 `LoadTestPaymentGatewayTest` 가 확인한다.
