# 가게 등록 진행 상태 저장 기반

## 범위

store 도메인이 진행 상태를 소유한다.
이번 변경은 진행 상태 저장·수정 기반과 점주 내 정보의 재개 단계 조회를 다룬다. 단계별 GET·POST·PATCH와 약관 API 연동은 후속 작업이다.
입력값은 각 단계의 기존 업무 테이블에 저장하고 진행 상태에는 점주 ID, 가게 ID, 재개 단계와 버전만 둔다.

## 단계

TERMS → STORE_INFO → LOCATION → HOURS → IMAGES → MENU(선택) 순서다.
REVIEW와 COMPLETE는 저장하지 않는다.
STORE_INFO는 가게 기본 정보 등록 및 사업자등록번호 검증을 함께 처리하며 화면에는 가게·사업자 정보로 표시한다.
호출자는 기본 정보 저장과 사업자 검증 성공을 모두 확인한 뒤 STORE_INFO를 완료한다. 실패하면 STORE_INFO를 유지한다.
TERMS와 STORE_INFO에서는 가게 ID가 없다. STORE_INFO 완료 시 생성된 가게 ID를 연결하며 LOCATION 이후에는 가게 ID가 반드시 있어야 한다.
메뉴 등록은 선택이며 메뉴가 0개인 가게도 최종 등록할 수 있다.
메뉴를 저장하거나 건너뛰더라도 재개 단계는 MENU이며 최종 등록 여부는 store.finalized를 사용한다.
따라서 MENU라는 단계 값만으로 메뉴 입력 완료나 최종 등록 가능 여부를 판단하지 않는다.
최종 등록 서비스는 약관과 필수 업무 데이터를 다시 검증하되 메뉴 존재 여부나 MENU 저장 이력을 필수 조건으로 검사하지 않는다.
메뉴를 등록한 경우에만 해당 메뉴의 필수값과 이미지 조건을 검증한다.

가게 대표 이미지와 선택한 내부 이미지의 저장이 완료되면 MENU로 진행하며 메뉴 입력 또는 건너뛰기를 선택할 수 있다.
건너뛰기에는 메뉴 저장 요청이나 빈 메뉴 행 생성이 필요하지 않다. 필수 단계가 완료된 가게는 메뉴 없이 최종 등록을 요청할 수 있다.
메뉴 저장은 최종 등록 확정과 구분하며 afterSave는 진행 단계만 계산한다.
조회와 화면 복원에서는 store.finalized를 먼저 확인한다.

| 저장 상태 | 화면 복원 동작 |
|---|---|
| finalized=false, resumeStep=MENU | 메뉴가 있으면 저장된 입력값을 복원한다. 메뉴 입력 또는 건너뛰기를 선택하고 최종 등록을 이어서 진행한다 |
| finalized=true | 등록이 완료되었으므로 resumeStep과 관계없이 온보딩을 종료한다 |

메뉴 화면의 등록 완료 버튼에서 메뉴 저장과 최종 등록을 함께 처리하는 경우에도 필수 조건을 다시 검증해야 한다. 메뉴 미입력이나 전체 삭제는 허용하며 메뉴가 없다는 이유로 최종 등록을 거절하지 않는다.
최종 등록 확정이 성공한 뒤에만 클라이언트가 온보딩을 종료한다.
최종 등록 확정과 조회 API의 구현은 후속 작업이다.

## 저장 계약

- 최초 초기화는 TERMS, storeId=null, version=0이다.
- initialize는 기존 진행 상태를 초기화하지 않고 그대로 반환한다.
- 최초 초기화 호출자는 같은 트랜잭션에서 점주 행을 먼저 잠그고 계정과 ONBOARDING 상태를 확인해야 한다.
- 잠금 순서는 점주 행 → 진행 상태 행 → 단계별 데이터다.
- StoreRegistrationProgressService는 Propagation.MANDATORY로 호출자의 쓰기 트랜잭션에 참여한다.
- 단계 저장 서비스는 진행 상태 행을 먼저 잠그고 요청 버전을 확인한 뒤 입력값을 검증하고 저장해야 한다.
- completeStep은 같은 트랜잭션에서 호출하며 버전과 현재 단계를 다시 확인하고 버전을 1 증가시킨다.
- version은 JPA 자동 버전이 아니라 진행 상태 행의 비관적 쓰기 잠금 아래 명시적으로 증가시키는 요청 버전이다.
- 입력값이 같거나 MENU에 머무는 저장도 버전을 증가시킨다.
- completeStep은 현재 단계 완료에 사용하며 단계 건너뛰기와 이전 단계 완료 요청을 거부한다.
- reviseStep은 현재 단계와 완료한 이전 단계 수정에 사용한다. 재개 단계와 가게 ID를 유지하고 버전을 1 증가시킨다.
- 모든 이전 단계와 현재 단계는 수정할 수 있다. 아직 도달하지 않은 미래 단계는 수정할 수 없다.
- 현재 단계 완료에는 completeStep을 사용한다. MENU를 저장하면 같은 경로로 MENU를 유지하고 버전을 증가시킨다. 메뉴를 건너뛸 때는 MENU 완료 요청을 필수로 요구하지 않는다.
- 수정 요청에도 같은 잠금 순서와 요청 버전 검사를 적용한다. 수정 입력값과 진행 상태 버전은 함께 커밋하거나 롤백한다.
- 호출자는 완료한 이전 단계 수정 후에도 필수 조건이 충족되는지 검증해야 한다. 이후 단계의 저장 데이터는 보존한다. 현재 단계의 미완료 입력 저장 기준은 단계별 API 계약에서 정한다.
- 이 내부 서비스는 ONBOARDING 절차에 사용한다. ACTIVE 점주의 운영 정보 수정은 별도 서비스에서 처리한다.
- STORE_INFO 완료 시 본인 소유의 finalized=false 가게를 연결하고 LOCATION으로 진행한다. 진행 상태 서비스는 사업자 검증을 직접 수행하지 않으며 호출자가 검증 성공을 보장해야 한다.
- TERMS와 STORE_INFO 단계에서는 가게 ID가 없어야 한다. STORE_INFO 완료 시 생성된 가게 ID를 연결하며, LOCATION 이후 단계에서는 가게 ID가 반드시 있어야 한다.
- 실패 예외를 잡아 성공으로 바꾸지 않으며 입력값과 진행 상태를 함께 롤백한다.
- 객체 스토리지 업로드와 외부 사업자 검증 호출은 DB 트랜잭션 밖에서 처리한다.

이전 단계 수정은 완료 조건이 계속 충족되는 경우에만 허용한다. 사업자 정보 수정 시 재검증에 성공해야 반영하며 실패하면 변경을 롤백한다. 현재 재개 단계와 이후 단계의 저장 데이터는 유지한다.
현재 브랜치에는 약관 API 구현이 없으며 약관 기능 연동과 진행 상태 자동 생성은 후속 작업이다.
기존 약관 동의 내역을 신규 진행 상태에 반영하는 초기화 정책도 연동 작업에서 정의해야 한다.
다른 도메인은 store.contract의 공개 조회 계약으로 진행 단계를 읽으며 store의 entity나 repository를 참조하지 않는다.

## 카카오 가게 정보 전달

프론트엔드가 카카오맵 검색과 가게 선택을 담당한다.
백엔드는 프론트가 선택한 가게 정보를 전달받으며 카카오맵 검색 API를 제공하지 않는다.
GET /v1/owner/kakao-places는 구현 대상에서 제외한다.
/v1/owner/stores/{storeId}/location은 프론트가 최종 확정한 카카오 가게 정보를 전달받아 위치를 저장하는 후속 API로 유지한다.
현재 두 경로의 HTTP API는 구현되어 있지 않으며 LOCATION 단계는 유지한다.
전달받은 가게 정보만으로 사업자 검증이 완료된 것으로 판단하지 않는다.

기존 저장 구조에는 카카오 장소 ID(`kakao_place_id`), 가게명(`name`), 주소(`address`)와 좌표(`latitude`, `longitude`)가 있다.
프론트와 실제로 전달할 필드, 필수 여부, 길이와 좌표 검증 기준을 후속 API 계약에서 확정한다.
카카오 가게 정보가 LOCATION의 주소·좌표 입력에 어떻게 반영되는지도 같은 계약에서 정한다.
이번 변경에서는 요청 DTO나 등록·사업자 검증 API를 추가하지 않는다.

## 마이그레이션 전제

기존 진행 상태 데이터는 없다. V4는 단계 값과 가게 ID 유무에 대한 DB 제약만 변경한다.
기존 V2는 이미 적용된 DB의 체크섬을 유지하기 위해 수정하지 않는다.
TERMS와 STORE_INFO에서는 가게 ID가 NULL이고 LOCATION 이후에는 필수다.
기존 데이터 변환과 기존 가게 연결 복원은 구현하지 않는다.

## 재접속과 단계별 요청

재접속 시 현재 재개 단계와 그 단계에 저장된 입력값만 조회한다.
이전 단계의 입력값 전체를 모아 반환하거나 여러 단계의 화면을 한 번에 복원하지 않는다.
이전 단계 수정 화면에 필요한 입력값은 해당 단계의 GET으로 별도 조회한다.

| 메서드 | 역할 | 재개 단계 |
|---|---|---|
| GET | 현재 단계 복원 또는 수정할 단계의 저장 내용 조회 | 변경하지 않는다 |
| POST | 현재 단계의 입력을 검증·저장하고 완료 처리 | 성공하면 다음 단계로 이동한다 |
| PATCH | 현재 단계 또는 완료한 이전 단계의 저장 내용 수정 | 유지한다 |

GET은 진행 상태를 생성하거나 수정하지 않는다.
POST와 PATCH는 요청 버전을 검사하며 업무 데이터와 진행 상태 버전을 함께 커밋하거나 롤백한다.
PATCH는 전달한 항목만 수정하며 누락한 항목은 유지한다. 필드별 삭제 가능 여부는 각 단계 API 계약에서 정한다.
PATCH만으로 다음 단계로 이동하지 않는다. 현재 단계에서 다음으로 진행할 때는 POST로 완료를 요청하고 전체 필수 조건을 다시 검증한다.
단계별 경로·요청·응답과 미완료 입력값의 저장 구조는 후속 API 계약에서 정의한다.

## 공개 조회 계약

store.contract.StoreRegistrationQuery.findResumeStep은 점주의 재개 단계 문자열만 반환한다.
진행 상태가 없으면 최초 단계 TERMS를 반환하며 조회 중 진행 상태를 생성하지 않는다.
점주 내 정보 응답은 [owner-api-spec.md](../../api-spec/owner-api-spec.md)의 내 정보 조회 절을 따른다.
단계 입력값과 이전 단계 전체 데이터는 내 정보 응답에 넣지 않는다.

## 내부 오류

| 코드 | 상태 | 조건 |
|---|---|---|
| STORE-001 | 409 | 요청 버전이 현재 버전과 다름 |
| STORE-002 | 409 | 완료 요청 단계가 현재 단계와 다름 |
| STORE-003 | 409 | 진행 상태 초기화 전 완료 요청 |
| STORE-004 | 403 | 본인 소유의 미확정 가게가 아닌 가게 연결 요청 |

이번 작업에서 진행 상태용 StoreErrorCode와 StoreException을 추가한다.
HTTP 경로와 요청·응답 계약은 후속 API 구현에서 정의한다.

## 브랜치 적용 기준

이슈 #249를 위해 약관 기능에 의존하지 않는 내부 기반으로 구성한다.
현재 store 도메인에는 오류 코드 구현이 없으므로 진행 상태 오류는 STORE-001부터 연속해서 부여한다.
약관 기능과 병합할 때에는 오류 코드 중복을 확인하고 명세와 테스트를 함께 조정한다.
