# 가게 등록 진행 상태 저장 기반

## 범위

store 도메인이 진행 상태를 소유한다.
이번 변경은 진행 상태 저장·수정 기반과 점주 내 정보의 재개 단계 조회를 다룬다.
STORE_INFO의 PUT 저장은 #415에서 구현하며 계약과 처리는 [가게 API 설계](store-api-design.md#store_info-저장-415)를 따른다.
진행 상태 조회는 #453에서 구현하며 [가게 API 명세](../../api-spec/store-api-spec.md#get-v1owneronboarding)를 따른다.
내 가게 통합 조회는 구현된 store-api-spec.md의 계약을 따른다. 나머지 단계의 PUT 저장과 최종 등록은 각 기능의 후속 작업에서 구현한다.

입력값은 각 단계의 기존 업무 테이블에 저장하고 진행 상태에는 점주 ID, 가게 ID, 재개 단계와 버전만 둔다.

## 단계

TERMS → STORE_INFO → LOCATION → HOURS → IMAGES → MENU(선택) 순서다.
REVIEW와 COMPLETE는 저장하지 않는다.
STORE_INFO는 가게 기본 정보 등록 및 사업자등록번호 검증을 함께 처리하며 화면에는 가게·사업자 정보로 표시한다.
호출자는 기본 정보 저장과 사업자 검증 성공을 모두 확인한 뒤 STORE_INFO를 완료한다. 실패하면 STORE_INFO를 유지한다.
TERMS와 STORE_INFO에서는 가게 ID가 없다. STORE_INFO 완료 시 생성된 가게 ID를 연결하며 LOCATION 이후에는 가게 ID가 반드시 있어야 한다.
메뉴 등록은 선택이며 메뉴가 0개인 가게도 최종 등록할 수 있다.
메뉴를 저장하거나 건너뛰더라도 재개 단계는 MENU이며 최종 등록 여부는 store.finalized를 사용한다.
따라서 MENU라는 단계 값만으로 메뉴 입력 완료나 최종 등록 가능 여부를 판단하지 않는다.
최종 등록 서비스는 약관과 필수 업무 데이터를 다시 검증하되 메뉴 존재 여부나 MENU 저장 이력을 필수 조건으로 검사하지 않는다.
메뉴를 등록한다면 각 메뉴의 이미지, 메뉴명과 가격이 모두 필수다. 이 조건은 온보딩 등록과 ACTIVE 상태의 메뉴 추가·수정에 동일하게 적용한다.
메뉴가 0개인 경우는 허용하지만 메뉴가 있는데 이미지가 없는 상태를 정상 등록으로 취급하지 않는다.

가게 대표 이미지와 선택한 내부 이미지의 저장이 완료되면 MENU로 진행하며 메뉴 입력 또는 건너뛰기를 선택할 수 있다.
건너뛰기에는 메뉴 저장 요청이나 빈 메뉴 행 생성이 필요하지 않다. 필수 단계가 완료된 가게는 메뉴 없이 최종 등록을 요청할 수 있다.
메뉴 저장은 최종 등록 확정과 구분하며 afterSave는 진행 단계만 계산한다.
조회와 화면 복원에서는 store.finalized를 먼저 확인한다.

| 저장 상태 | 화면 복원 동작 |
|---|---|
| finalized=false, resumeStep=MENU | 메뉴가 있으면 저장된 입력값을 복원한다. 메뉴 입력 또는 건너뛰기를 선택하고 최종 등록을 이어서 진행한다 |
| finalized=true | 등록이 완료되었으므로 resumeStep과 관계없이 온보딩을 종료한다 |

메뉴 화면의 등록 완료 버튼에서 메뉴 저장과 최종 등록을 함께 처리하는 경우에도 필수 조건을 다시 검증해야 한다. 메뉴 미입력이나 전체 삭제는 허용하며 메뉴가 없다는 이유로 최종 등록을 거절하지 않는다.
최종 등록 확정이 성공한 뒤에만 클라이언트가 온보딩을 종료한다.
최종 등록 확정과 조회 API의 구현은 후속 작업이다.

## 단계별 필수 입력

| 단계 | 프론트에서 전달할 업무 입력값 | 저장 컬럼 |
|---|---|---|
| STORE_INFO | 상호명(필수) | store.name |
| STORE_INFO | 업종(필수) | store.category_code |
| STORE_INFO | 대표자 성명(필수) | store.representative_name |
| STORE_INFO | 사업자등록번호(필수) | store.business_registration_number |
| STORE_INFO | 전화번호(필수) | store.phone |
| LOCATION | 카카오 장소 ID(필수) | store.kakao_place_id |
| LOCATION | 도로명 주소(필수) | store.road_address |
| LOCATION | 위도·경도(모두 필수) | store.latitude, store.longitude |

전화번호는 STORE_INFO에서 받으며, 프론트가 필수 입력값으로 전달해야 한다.
LOCATION에서는 카카오 장소 ID, 도로명 주소와 위도·경도만 받으며 전화번호나 STORE_INFO의 기본 정보를 다시 받거나 덮어쓰지 않는다.
진행 상태의 요청 버전은 위 업무 입력값과 별도로 기존 공통 저장 계약을 따른다.
각 단계 완료 시 필수값 누락·null과 문자열의 빈 값·공백을 거절하며 위도와 경도는 함께 전달해야 한다.
요청 DTO의 필드명·형식·길이 등 세부 검증과 실제 저장 처리는 후속 단계별 API 구현에서 정의한다.

## 저장 계약

- 최초 초기화는 TERMS, storeId=null, version=0이다.
- initialize는 기존 진행 상태를 초기화하지 않고 그대로 반환한다.
- 최초 초기화 호출자는 같은 트랜잭션에서 점주 행을 먼저 잠그고 계정과 ONBOARDING 상태를 확인해야 한다.
- 잠금 순서는 점주 행 → 진행 상태 행 → 단계별 데이터다.
- StoreRegistrationProgressService는 Propagation.MANDATORY로 호출자의 쓰기 트랜잭션에 참여한다.
- 단계 저장 서비스는 진행 상태 행을 먼저 잠그고 요청 버전을 확인한 뒤 입력값을 검증하고 저장해야 한다. 최초 동의만 가능한 TERMS는 요청 버전을 받지 않고 서버가 잠근 현재 버전으로 완료한다.
- completeStep은 같은 트랜잭션에서 호출하며 버전과 현재 단계를 다시 확인하고 버전을 1 증가시킨다.
- version은 JPA 자동 버전이 아니라 진행 상태 행의 비관적 쓰기 잠금 아래 명시적으로 증가시키는 요청 버전이다.
- 입력값이 같거나 MENU에 머무는 저장도 버전을 증가시킨다.
- completeStep은 현재 단계 완료에 사용하며 단계 건너뛰기와 이전 단계 완료 요청을 거부한다.
- reviseStep은 현재 단계와 완료한 이전 단계 수정에 사용한다. 재개 단계와 가게 ID를 유지하고 버전을 1 증가시킨다.
- TERMS는 최초 동의 후 수정하지 않는다. 나머지 단계는 현재 단계와 완료한 이전 단계를 수정할 수 있으며 미래 단계는 수정할 수 없다.
- ONBOARDING의 PUT 저장 서비스는 현재 단계의 필수 조건을 충족하면 completeStep을 호출한다. TERMS 이외의 완료한 단계 재저장에는 reviseStep을 호출하며 TERMS 재저장과 미래 단계 저장은 거부한다.
- MENU를 저장하면 MENU를 유지하고 버전을 증가시킨다. 메뉴를 건너뛸 때는 MENU 저장 요청을 필수로 요구하지 않는다.
- 수정 요청에도 같은 잠금 순서와 요청 버전 검사를 적용한다. 수정 입력값과 진행 상태 버전은 함께 커밋하거나 롤백한다.
- 호출자는 완료한 이전 단계 수정 후에도 필수 조건이 충족되는지 검증해야 한다. 이후 단계의 저장 데이터는 보존한다. 현재 단계의 미완료 입력 저장 기준은 단계별 API 계약에서 정한다.
- 이 내부 서비스는 ONBOARDING 절차에 사용한다. ACTIVE 점주의 운영 정보 수정은 별도 서비스에서 처리한다.
- STORE_INFO 완료 시 본인 소유의 finalized=false 가게를 연결하고 LOCATION으로 진행한다. 진행 상태 서비스는 사업자 검증을 직접 수행하지 않으며 호출자가 검증 성공을 보장해야 한다.
- TERMS와 STORE_INFO 단계에서는 가게 ID가 없어야 한다. STORE_INFO 완료 시 생성된 가게 ID를 연결하며, LOCATION 이후 단계에서는 가게 ID가 반드시 있어야 한다.
- 실패 예외를 잡아 성공으로 바꾸지 않으며 입력값과 진행 상태를 함께 롤백한다.
- 객체 스토리지 업로드와 외부 사업자 검증 호출은 DB 트랜잭션 밖에서 처리한다.

이전 단계 수정은 완료 조건이 계속 충족되는 경우에만 허용한다. 사업자 정보 수정 시 재검증에 성공해야 반영하며 실패하면 변경을 롤백한다. 현재 재개 단계와 이후 단계의 저장 데이터는 유지한다.
약관 저장과 진행 상태 연동은 [가게 API 설계](store-api-design.md#점주-약관-동의)를 따른다.
다른 도메인은 store.contract의 공개 조회 계약으로 진행 단계를 읽으며 store의 entity나 repository를 참조하지 않는다.

## 최종 등록 이후 설정

온보딩에서 메뉴를 등록하지 않은 점주도 ACTIVE 상태에서 설정을 통해 메뉴를 최초 등록할 수 있다.
설정에서는 영업시간과 가게 사진을 수정하고 메뉴를 추가·수정할 수 있다.
메뉴 등록·수정은 메뉴 이미지, 메뉴명과 메뉴 가격을 모두 갖추고 이미지 객체 확인을 마친 뒤 성공으로 처리한다.
메뉴가 아예 없는 경우와 등록된 메뉴의 필수 이미지가 누락된 경우를 구분한다. 메뉴 미등록은 허용하지만 등록된 메뉴의 이미지가 없거나 미검증 상태이면 조회 오류로 처리한다. 조회 정책은 [가게와 메뉴 조회 계약](store-query-contract.md#이미지-url)을 따른다.

ACTIVE 설정 요청은 본인 소유의 최종 등록된 가게인지와 점주의 현재 상태를 확인해야 한다.
운영 정보 변경은 온보딩 재개 단계와 진행 상태 버전을 변경하거나 진행 상태를 새로 생성하지 않는다.
영업시간·가게 사진·메뉴의 PUT 저장 API는 ONBOARDING과 ACTIVE 설정 화면에서 공용으로 사용한다.
같은 API 안에서도 점주 상태에 따라 온보딩 진행 상태 처리와 운영 정보 수정을 구분한다. ACTIVE 요청에 온보딩 진행 상태 초기화·완료·수정 메서드를 호출하지 않는다.
영업시간의 ACTIVE 동시 수정과 요청·응답 계약은 [영업시간 저장 설계](store-api-design.md#영업시간-저장)를 따른다. 사진·메뉴의 설정 계약은 후속 API에서 확정한다.

## 카카오 가게 정보 전달

프론트엔드가 카카오맵 검색과 가게 선택을 담당한다.
백엔드는 프론트가 선택한 가게 정보를 전달받으며 카카오맵 검색 API를 제공하지 않는다.
GET /v1/owner/kakao-places는 구현 대상에서 제외한다.
/v1/owner/stores/{storeId}/location은 프론트가 최종 확정한 카카오 가게 정보를 전달받아 위치를 저장하는 후속 API로 유지한다.
현재 두 경로의 HTTP API는 구현되어 있지 않으며 LOCATION 단계는 유지한다.
전달받은 가게 정보만으로 사업자 검증이 완료된 것으로 판단하지 않는다.

LOCATION에서 프론트가 최종 확정한 카카오 장소 ID, 도로명 주소와 위도·경도를 저장한다.
단계별 필수 항목과 저장 대상은 이 문서의 단계별 필수 입력 절을 따른다. 카카오 장소 정보의 전화번호로 STORE_INFO에서 받은 전화번호를 덮어쓰지 않는다.
이번 변경에서는 요청 DTO나 등록·사업자 검증 API를 추가하지 않는다.

## 마이그레이션 전제

기존 진행 상태 데이터는 없다. V4는 단계 값과 가게 ID 유무에 대한 DB 제약만 변경한다.
기존 V2는 이미 적용된 DB의 체크섬을 유지하기 위해 수정하지 않는다.
TERMS와 STORE_INFO에서는 가게 ID가 NULL이고 LOCATION 이후에는 필수다.
기존 데이터 변환과 기존 가게 연결 복원은 구현하지 않는다.

## 확정된 HTTP 메서드

온보딩·가게 관리에서 새로 구현할 조회·저장 API는 다음 방식으로 확정한다.

| 메서드 | 용도 |
|---|---|
| GET | 내 가게 정보와 입점 등록 진행 상태 조회 |
| PUT | TERMS는 최초 동의만 허용한다. 나머지 단계는 최초 저장과 수정에 사용하며 같은 단계의 입력을 덮어쓴다 |
| POST | 가게 최종 등록과 이미지 업로드 URL 발급 |

단계별 저장·수정을 위해 POST나 PATCH를 따로 추가하지 않는다. 이 결정은 프로젝트의 다른 기능에서 사용하는 기존 PATCH를 변경하지 않는다.
PUT 요청에는 해당 단계의 전체 입력값을 포함한다. 값을 바꾸지 않는 항목은 기존 값으로 보내며 다른 단계의 정보는 다시 보내지 않는다.
조회 통합 방식, 구체적인 경로와 DTO, 필수값 누락·null·빈 배열의 처리와 버전 충돌 응답은 후속 API 명세에서 정한다.

## 단계별 저장

여섯 단계의 저장은 PUT으로 요청한다. TERMS는 최초 동의만 허용하며 나머지 단계는 다시 저장하면 해당 단계의 입력을 덮어쓴다.
단계 저장과 수정에는 PUT만 사용하며 단계별 POST 완료 요청이나 PATCH 부분 수정 API는 추가하지 않는다.

| 단계 | 저장 기능 |
|---|---|
| TERMS | 가게 생성과 별개로 점주 ID 기준의 최초 약관 동의만 저장하며 완료 후 수정은 거부한다 |
| STORE_INFO | 기본 정보와 사업자등록번호를 검증하고 최초 저장 성공 시 가게 초안을 생성한다. Mock 검증 결과를 반환한다 |
| LOCATION | 프론트에서 최종 확정한 카카오 장소 ID·도로명 주소·좌표를 저장한다 |
| HOURS | 영업시간을 저장하며 ACTIVE 가게 관리에서도 같은 API를 사용한다 |
| IMAGES | 업로드한 객체 키로 가게 사진을 저장하며 ACTIVE 가게 관리에서도 같은 API를 사용한다 |
| MENU | 각 메뉴의 이미지 객체 키·메뉴명·가격을 저장하며 ACTIVE 설정에서 최초 추가·수정할 때도 같은 API를 사용한다 |

ONBOARDING에서는 기존 요청 버전 비교와 잠금 순서를 유지한다. 단계 데이터와 진행 상태는 함께 커밋하거나 롤백한다.
TERMS 이외 단계는 같은 내용을 다시 저장해도 버전이 증가한다. 오래된 버전은 충돌로 거부하며 최신 버전으로 완료한 이전 단계를 재저장하면 재개 위치를 유지한다.
현재 단계 저장 성공은 다음 단계로 진행하지만 이미 완료한 단계의 재저장은 다음 단계 진행을 반복하지 않는다.
PUT의 전체 덮어쓰기에서 누락 필드·null·빈 배열을 어떻게 처리할지는 각 단계 명세에서 확정한다. 기존 PATCH의 누락 필드 유지 규칙을 그대로 적용하지 않는다.
기본 정보·사업자 정보의 이전 단계 수정은 재검증 등 완료 조건을 계속 충족해야 한다.

## 최종 등록과 이미지 업로드

가게 최종 등록은 단계별 PUT 저장과 분리한 POST 요청으로 처리한다.
서버는 약관과 필수 업무 데이터를 다시 검증하고 가게의 finalized=true와 점주의 ONBOARDING에서 ACTIVE 전환을 함께 확정해야 한다.
메뉴 미등록은 허용하지만 등록한 메뉴는 이미지·메뉴명·가격을 모두 갖춰야 한다.

이미지 업로드 URL 발급은 POST로 요청하며 용도·형식·크기를 검증하고 업로드 주소, 객체 키와 만료 시각을 반환한다.
프론트 요청안은 presigned POST 방식이다. 현재 S3 설정의 presigned PUT 기반과 구분하며 실제 발급 방식·응답 형식·업로드 확인은 후속 업로드 API에서 확정한다.
객체 키를 저장할 때는 해당 점주·용도의 업로드인지와 이미지 객체 확인 완료 여부를 검증해야 한다.

설정에서 메뉴를 삭제하기 전에 캠페인에서 사용 중인지 조회할 수 있어야 한다.
별도 조회 API와 내 가게 조회의 메뉴별 inUse 표시 중 어느 방식으로 제공할지는 후속 명세에서 정한다.
화면의 삭제 버튼 비활성화와 별개로 서버도 삭제 요청 시 사용 중인 메뉴의 삭제를 거부해야 한다.
현재 로컬에는 업로드 발급·객체 확인·메뉴 사용 여부 조회와 최종 등록 API 구현이 없다.

## 조회와 재접속

단계별 GET은 제공하지 않는다. 프론트는 내 가게 조회와 입점 등록 진행 상태 조회로 필요한 정보를 가져온다.
내 가게 조회에 상세 저장값과 진행 정보를 모으고 별도 진행 상태 조회는 화면 이동에 필요한 단계 정보 중심으로 분리한다.

| 조회 | 반환할 내용 |
|---|---|
| 내 가게 조회 | 가게 ID와 전체 저장 정보, 약관 동의와 각 단계의 저장·완료 상태, 재개 위치와 최종 등록 가능 여부. 가게 생성 전에도 약관·진행 정보는 반환한다 |
| 입점 등록 진행 상태 조회 | 화면 이동에 필요한 현재·재개 단계 중심의 가벼운 조회. 상세 저장값과 단계별 완료 여부는 내 가게 조회가 담당한다 |

전체 가게 정보를 조회하더라도 프론트는 재개할 단계의 화면만 복원할 수 있다.
기존의 현재 단계 입력값만 반환하는 조회와 이전 단계 수정용 GET은 위 두 조회로 대체한다.
내 가게 조회는 실제 업무 데이터로 단계별 완료 여부와 첫 미완료 단계를 계산해야 한다. 저장된 resumeStep만으로 완료 여부를 단정하지 않는다.
MENU 미입력은 최종 등록 불가 사유가 아니다. 선택 메뉴의 입력 여부와 필수 단계 완료·최종 등록 가능 여부를 구분한다.
이미 최종 등록된 가게는 온보딩을 다시 시작하지 않는다.

GET은 가게나 진행 상태를 생성하지 않는다. 내 가게 조회가 storeId를 생성하는 것도 아니다.
가게 초안 생성 전 응답과 메뉴 미입력·선택 항목의 null·빈 배열 구분은 후속 API 명세에서 확정한다.
내 가게 조회에는 온보딩 초안을 읽는 별도 조회가 필요하다. 최종 등록된 가게만 읽는 기존 쿠폰용 StoreQueryService의 조건은 완화하지 않는다.

## 후속 구현 순서와 미확정 사항

프론트 의존 작업을 풀기 위해 내 가게 조회와 최종 등록을 우선 구현한다.
내 가게 조회로 ID를 얻으려면 기본 정보 저장과 초안 생성도 필요하며 최종 등록 성공에는 필수 단계 저장이 선행되어야 한다.
후속 구현에서는 전체 기능을 한 번에 합치지 않고 위 선행 관계에 맞춰 진행한다.

- 사업자 Mock 검증 실패 시 입력값·초안을 저장하지 않는 #415 계약을 적용한다. 응답과 재검증 실패 처리는 [가게 API 명세](../../api-spec/store-api-spec.md#가게-등록-온보딩-2단계-기본-정보와-사업자-mock-검증)가 소유한다.
- 약관 동의와 진행 상태의 최초 생성·연동은 [가게 API 설계](store-api-design.md#점주-약관-동의)를 따른다. 약관은 가게 생성 전에도 저장한다.
- 단계별 완료 여부와 최종 등록 가능 여부는 최종 등록 서비스와 같은 검증 기준을 사용한다. 선택 단계 MENU의 완료 표현은 [진행 상태 조회 명세](../../api-spec/store-api-spec.md#get-v1owneronboarding)를 따른다.

- 통합 조회의 응답 구조, PUT 저장 요청·응답, 이미지 업로드 방식과 ACTIVE의 동시 수정 규칙을 확정한다.
- 구체적인 HTTP 경로와 DTO는 예시 주소를 그대로 확정하지 않고 각 기능 구현 전에 명세로 정한다.

## 공개 조회 계약

현재 구현된 store.contract.StoreRegistrationQuery.findResumeStep은 점주의 재개 단계 문자열만 반환한다.
이 계약은 /v1/owner/me의 현재 단계 표시에 사용하며 전체 가게 정보, 단계별 완료 여부와 최종 등록 가능 여부 조회를 대체하지 않는다.
진행 상태가 없으면 최초 단계 TERMS를 반환하며 조회 중 진행 상태를 생성하지 않는다.
점주 내 정보 응답은 [owner-api-spec.md](../../api-spec/owner-api-spec.md)의 내 정보 조회 절을 따른다.
단계 입력값과 이전 단계 전체 데이터는 내 정보 응답에 넣지 않는다.

## 내부 오류

| 코드 | 상태 | 조건 |
|---|---|---|
| STORE-001 | 409 | 요청 버전이 현재 버전과 다름 |
| STORE-002 | 409 | 완료 요청 단계가 현재 단계와 다름 |
| STORE-003 | 409 | 진행 상태 초기화 전 완료 요청 |
| STORE-004 | 403 | 본인 소유의 미확정 가게가 아닌 가게 연결 요청 |

이번 작업에서 진행 상태용 StoreErrorCode와 StoreException을 추가한다.
HTTP 경로와 요청·응답 계약은 후속 API 구현에서 정의한다.

## 브랜치 적용 기준

이슈 #249를 위해 약관 기능에 의존하지 않는 내부 기반으로 구성한다.
현재 store 도메인에는 오류 코드 구현이 없으므로 진행 상태 오류는 STORE-001부터 연속해서 부여한다.
약관 기능과 병합할 때에는 오류 코드 중복을 확인하고 명세와 테스트를 함께 조정한다.
