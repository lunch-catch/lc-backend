# 도메인 경계 리뷰 가이드

이 문서는 **점검 항목만 담는다.** 문서가 셋으로 나뉘고 역할이 다르다.

| 문서 | 담는 것 |
|---|---|
| 이 문서 | 번호 붙인 점검 항목, 근거 절, 강제 수단 |
| [domain-boundary-rationale.md](./domain-boundary-rationale.md) | 왜 리뷰 항목인가, 위반이 코드에서 어떤 모양인가, 테스트가 못 보는 것 |
| [런치캐치_도메인_구조와_의존성_설계.md](../architecture/런치캐치_도메인_구조와_의존성_설계.md) | 규칙의 내용과 근거. 계층과 도메인과 의존 방향을 그렇게 정한 이유 |

**규칙의 내용은 설계 문서가 소유한다.** 같은 설명을 가이드나 근거 문서에 옮기지 않는다.
어긋나는 순간 어느 쪽이 기준인지 알 수 없게 된다.

항목마다 **근거 절**과 **강제 수단**을 적었다. 대부분은 `ArchitectureTest` 가 빌드에서
막으므로 리뷰가 먼저 잡지 못해도 `./gradlew check` 에서 걸린다. 강제 수단이 없는 항목만
사람과 봇이 보는 유일한 방어선이다.

| 번호 | 다루는 것 | 근거 |
|---|---|---|
| `DPB-1-*` | 계층 배치와 공개면 | 설계 문서 1.3, 1.4 |
| `DPB-2-*` | 도메인 간 참조 | 2.1 규칙 1과 2, 2.5 |
| `DPB-3-*` | 모듈 층위 (`global`, `auth`, `ops`) | 1.1, 2.1 규칙 3과 5 |
| `DPB-4-*` | 의존 방향과 통보 | 2.1 규칙 4와 6, 2.2 ~ 2.4 |

## 1. 계층 배치와 공개면

점검 항목
* `DPB-1-01` 공개할 것을 `{도메인}/contract/` 에 두고 나머지를 계층 구조나 계층 밖 허용 위치에 두었는가
  계층 구조는 `controller`, `listener`, `job`, `service`, `repository`, `entity` 다.
  계층 밖에 허용하는 것은 둘이다. `config/`, `dto/`, `exception/`, `client/` 은 부를 코드가 없어 계층이 아니고(1.4절), HTTP 와 DB 와 스케줄에 기대지 않는 순수 계산 로직은 계층 구조에 넣지 않고 그 패키지 바로 아래에 둔다(1.3절).
  그 밖의 폴더를 새로 만들면 어느 계층인지, 아니면 왜 계층이 아닌지 PR 에 적는다.
  근거: 1.3절, 1.4절. 강제: 없다. 리뷰가 본다
* `DPB-1-02` `contract` 에 인터페이스와 record, enum 만 두었는가
  근거: 1.3절. 강제: `contract에는_인터페이스_record_enum만_둔다`
* `DPB-1-03` `contract` 가 `entity` 와 `repository` 를 참조하지 않는가
  근거: 1.3절. 강제: `contract는_entity와_repository를_참조하지_않는다`
* `DPB-1-04` Controller 와 Entry(`listener`, `job`)가 Service 만 부르는가
  근거: 1.4절 표. 강제: `계층_의존_규칙`
* `DPB-1-05` Service 가 자기 도메인 Repository 와 다른 도메인 `contract` 인터페이스만 부르는가
  근거: 1.4절 표. 강제: `계층_의존_규칙`
* `DPB-1-06` Repository 가 다른 계층을 부르지 않는가
  근거: 1.4절 표. 강제: `계층_의존_규칙`
* `DPB-1-07` Controller 와 Entry 가 다른 계층에서 호출되지 않는가
  근거: 1.4절. 진입점은 둘뿐이다. 강제: `계층_의존_규칙`

## 2. 도메인 간 참조

점검 항목
* `DPB-2-01` 다른 도메인의 `entity` 와 `repository` 를 직접 참조하지 않는가
  근거: 2.1절 규칙 1. 강제: `도메인_내부는_같은_도메인에서만_쓴다`
* `DPB-2-02` 도메인 간 연관을 객체 참조가 아니라 ID 로 갖는가
  근거: 2.1절 규칙 1. 강제: `엔티티는_다른_도메인_엔티티를_참조하지_않는다`
* `DPB-2-03` 다른 도메인의 데이터를 그 도메인이 공개한 `contract` 로만 다루는가
  근거: 2.1절 규칙 1. 강제: 부분적이다. `DPB-2-01` 이 막는 것은 `entity` 와 `repository` 참조뿐이고,
  `service` 클래스를 직접 주입받는 것은 `계층_의존_규칙` 이 Service 간 호출로 보아 통과시킨다
* `DPB-2-04` 분석의 조회가 집계 결과만 읽는가
  근거: 2.1절 규칙 2. 집계 배치만 예외다. 강제: `분석_조회는_집계만_읽는다`
* `DPB-2-05` 관리자가 다른 업무 도메인을 의존하지 않는가
  근거: 1.2절. 기능은 데이터를 소유한 도메인에 둔다. 강제: `관리자는_다른_업무_도메인을_의존하지_않는다`

## 3. 모듈 층위

점검 항목
* `DPB-3-01` `global` 이 아무것도 의존하지 않는가
  근거: 1.2절 표. 도메인 지식이 없어야 모두가 쓴다. 강제: `기술_공통은_아무것도_의존하지_않는다`
* `DPB-3-02` `auth` 가 업무 도메인과 `ops` 를 의존하지 않는가
  근거: 2.1절 규칙 5. 강제: `인증_모듈은_어떤_도메인도_의존하지_않는다`
* `DPB-3-03` `ops` 가 어떤 업무 도메인도 의존하지 않는가
  근거: 2.1절 규칙 3. 설정을 아래에서 제공하는 모듈이다. 강제: `운영은_어떤_도메인도_의존하지_않는다`
* `DPB-3-04` 도메인마다 권한 검사를 따로 만들지 않고 `auth` 를 가져다 쓰는가
  근거: 2.1절 규칙 5. 강제: 없다. 리뷰가 본다

## 4. 의존 방향과 통보

점검 항목
* `DPB-4-01` 새로 생긴 간선이 2.2절 그래프의 방향을 따르는가
  근거: 2.2절. 화살표는 모두 왼쪽에서 오른쪽이다. 오른쪽에서 왼쪽으로 가는 간선은 순환 후보다.
  강제: 없다. `DPB-4-02` 가 실제 순환만 잡으므로 방향 판단은 리뷰가 한다
* `DPB-4-02` 도메인 간 순환이 생기지 않는가
  근거: 2.1절 규칙 6. 강제: `순환_의존이_없다`
* `DPB-4-03` 이벤트 타입을 발행 도메인의 `contract` 에 두었는가
  근거: 2.4절. 발행자 안쪽에 두면 수신자가 발행자의 내부를 import 한다. 강제: `이벤트_타입은_정해진_도메인_contract에_둔다`
* `DPB-4-04` 새 이벤트를 만들 때 2.4절 표와 `ArchitectureTest.EVENT_HOME` 을 함께 고쳤는가
  근거: 2.4절. 강제: `이벤트_타입은_정해진_도메인_contract에_둔다` 가 목록에 없는 이벤트를 가리켜 실패한다
* `DPB-4-05` 직접 호출과 이벤트 중 무엇을 쓸지 2.4절 기준으로 정했는가
  근거: 2.4절. 이벤트는 직접 호출하면 순환이 생기는 자리에서만 쓴다. 강제: 없다. 리뷰가 본다
* `DPB-4-06` 스케줄러가 실행 순서와 멱등만 책임지고 작업 내용은 해당 도메인이 구현하는가
  근거: 2.1절 규칙 4. 강제: 없다. 리뷰가 본다

## 강제되지 않는 항목

아래 다섯은 `ArchitectureTest` 가 막지 못한다. 리뷰에서 놓치면 그대로 들어간다.

| 항목 | 왜 자동화되지 않는가 |
|---|---|
| `DPB-1-01` | 무엇을 공개할지는 의도의 문제다. 잘못 공개해도 구조는 성립한다 |
| `DPB-2-03` | 다른 도메인의 `service` 를 주입받는 것을 `계층_의존_규칙` 이 Service 간 호출로 보아 통과시킨다 |
| `DPB-3-04` | 권한 검사를 손으로 구현했는지는 호출 패턴으로 가려지지 않는다 |
| `DPB-4-01` | 방향이 맞는지는 그래프 설계 의도를 알아야 판단된다. 테스트는 실제 순환만 잡는다 |
| `DPB-4-05`, `DPB-4-06` | 설계 판단이라 코드 형태로 드러나지 않는다 |
