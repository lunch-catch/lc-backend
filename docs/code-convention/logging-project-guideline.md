# 로깅 리뷰 가이드

이 문서는 **점검 항목만 담는다.** 문서가 셋으로 나뉘고 역할이 다르다.

| 문서 | 담는 것 |
|---|---|
| 이 문서 | 번호 붙인 점검 항목, 근거 절, 강제 수단 |
| [logging-project-rationale.md](./logging-project-rationale.md) | 왜 리뷰 항목인가, 위반이 코드에서 어떤 모양인가, 테스트가 못 보는 것 |
| [로그_설계.md](../observability/로그_설계.md) | 규칙의 내용과 근거. 장치와 설정과 도구를 그렇게 정한 이유 |

**규칙의 내용은 설계 문서가 소유한다.** 같은 설명을 가이드나 근거 문서에 옮기지 않는다.
어긋나는 순간 어느 쪽이 기준인지 알 수 없게 된다.

항목 번호는 공통 로깅 규칙 4판의 `LOG-*` 식별자를 그대로 쓴다. 그래서 번호가 이어지지 않는다.

항목마다 **근거 절**과 **강제 수단**을 적었다. 테스트가 막는 항목은 `LOG-7-08` 하나이고 그마저 부분적이다.
나머지는 리뷰가 유일한 방어선이다.

| 장 | 번호 | 근거 |
|---|---|---|
| 1. 장치와 문맥 | `LOG-1-01`, `LOG-2-03`, `LOG-8-05` | 설계 문서 2장, 3장, 13장 |
| 2. 성공과 실패의 기록 | `LOG-4-01`, `LOG-4-04`, `LOG-5-02`, `LOG-5-04`, `LOG-6-01`, `LOG-8-06` | 4장, 5장 |
| 3. 민감 정보 | `LOG-7-03`, `LOG-7-08`, `LOG-7-13` | 4장, 6장 |
| 4. 외부 클라이언트, 감사 기록, 로그 테스트 | `LOG-8-07`, `LOG-8-09`, `LOG-8-11` | 4장, 7장, 12장 |

## 1. 장치와 문맥

점검 항목
* `LOG-1-01` 공통 장치가 남기는 것(접근 로그, 외부 호출 로그, 스케줄러의 시작과 끝)을 업무 코드가 다시 남기지 않았는가
  근거: 2장. 강제: 없다. 리뷰가 본다
* `LOG-2-03` 이벤트명을 `event=` 뒤에 리터럴로 썼는가
  근거: 13장. 강제: 없다. 리뷰가 본다
* `LOG-8-05` 클라이언트 IP 를 `ClientIpResolver` 로 정했는가
  `getRemoteAddr()` 를 이 클래스 밖에서 직접 쓰지 않는다. `ForwardedHeaderStrategy` 와 `server.tomcat.remoteip.internal-proxies` 는 함께 켜지 않는다.
  근거: 3.1절, 4장. 강제: 없다. 리뷰가 본다

## 2. 성공과 실패의 기록

점검 항목
* `LOG-4-01` Redis 실패를 `RedisFailureClassifier.causeLabel` 로 분류해 `reason` 키에 넣었는가
  근거: 4장. 강제: 없다. 리뷰가 본다
* `LOG-4-04` 예외의 원인을 남길 때 예외 메시지 대신 `FailureLogDetails.from` 이 뽑은 원인 정보를 썼는가
  근거: 4장. 강제: 없다. 리뷰가 본다
* `LOG-5-02` 예상된 클라이언트 쪽 거절을 WARN 이 아니라 INFO 로 남겼는가
  근거: 5.3절. 강제: 없다. 리뷰가 본다
* `LOG-5-04` 정상 운영에서 대량으로 나오는 거절을 `ErrorCode.isExpectedTraffic()` 로 정의했는가
  근거: 4장, 5.1절. 강제: 없다. 리뷰가 본다
* `LOG-6-01` DB 상태 변경의 성공 로그를 `TransactionLogging.afterCommit` 으로 커밋 뒤에 남겼는가
  롤백됐거나 커밋 결과를 모르는 트랜잭션의 실패는 `TransactionLogging.afterFailure` 로 남긴다.
  근거: 4장. 강제: 없다. 리뷰가 본다
* `LOG-8-06` `isExpectedTraffic()` 경로를 거치지 않는 예상된 거절을 `AccessLogSignal.markExpected` 로 표시했는가
  근거: 4장, 5.1절. 강제: 없다. 리뷰가 본다

## 3. 민감 정보

점검 항목
* `LOG-7-03` 개인정보를 로그에 남길 때 `PiiMasker` 로 가렸는가
  근거: 4장. 개인정보를 가리는 유일한 유틸이다. 강제: 없다. 리뷰가 본다
* `LOG-7-08` 요청이나 응답에 넣은 새 민감 필드가 접미사 규칙에 걸리지 않으면 `app.logging.sensitive-keys.extra` 와 6.1절의 키 표에 더했는가
  근거: 6.1절, 6.2절. 강제: 부분적이다. `HttpBodyLoggingFilterTest` 의 민감 키 테스트는 테스트에 적힌 키 목록만 검사한다.
  설정과 그 목록에 함께 빠뜨린 키는 통과한다
* `LOG-7-13` 메시지에 민감한 값이 들어가는 외부 예외를 스택 대신 `FailureLogDetails` 의 원인 정보로 남겼는가
  근거: 6.4절의 목록. 원인 체인 안에 그 예외가 있어도 같다. 강제: 없다. 리뷰가 본다

## 4. 외부 클라이언트, 감사 기록, 로그 테스트

점검 항목
* `LOG-8-07` `WebClient.builder()`, `WebClient.create()` 를 `global/config` 밖에서 부르지 않았는가
  근거: 7장, 7.1절. 강제: 없다. 리뷰가 본다. 공통 규칙은 빌드에서 막게 하지만 이 저장소는 그 빌드 규칙이 없다
* `LOG-8-09` 로그를 검증하는 테스트가 `LogCapture` 로 로그를 모았는가
  근거: 4장. 강제: 없다. 리뷰가 본다
* `LOG-8-11` 관리자 행위와 돈이 오간 처리의 감사 기록을 로그가 아니라 `AuditLogWriter` 로 썼는가
  근거: 4장, 12장. 로그는 큐가 차면 버려진다(9장). 강제: 없다. 리뷰가 본다

## 강제되지 않는 항목

`LOG-7-08` 을 뺀 모든 항목은 테스트와 빌드가 막지 못한다. 리뷰에서 놓치면 그대로 들어간다.

| 항목 | 왜 자동화되지 않는가 |
|---|---|
| `LOG-1-01` | 업무 코드의 로그가 장치의 로그와 같은 것을 다시 남기는지는 두 로그의 뜻을 알아야 가려진다 |
| `LOG-4-01`, `LOG-4-04`, `LOG-7-13` | 예외를 어떤 키로 남겼는지는 로그 호출의 인자로만 드러나고, 그것을 검사하는 규칙이 없다 |
| `LOG-2-03` | 이벤트명이 리터럴인지 검사하는 빌드 규칙이 없다 |
| `LOG-5-02`, `LOG-5-04`, `LOG-8-06` | 어느 거절이 예상된 것이고 정상 운영에서 대량으로 나오는지는 업무의 판단이다 |
| `LOG-6-01` | 로그 호출이 트랜잭션 안에 있는지는 호출 위치만으로 가려지지 않는다 |
| `LOG-7-03` | 어느 값이 개인정보인지는 값의 뜻을 알아야 가려진다 |
| `LOG-7-08` | 테스트는 적힌 키 목록만 본다. 새 필드가 민감한지는 사람이 정한다 |
| `LOG-8-05`, `LOG-8-07`, `LOG-8-09`, `LOG-8-11` | 장치를 우회하는 호출을 막는 빌드 규칙이 없다 |
