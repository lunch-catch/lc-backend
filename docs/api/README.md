## 공통 규약

### 경로

```
/v1/...            사용자(USER)와 로그인 전 공개 경로
/v1/owner/...      점주(OWNER)
/v1/admin/...      관리자(ADMIN, SUPER_ADMIN)
```

**소비자가 다르면 경로를 나눈다.** 같은 리소스라도 화면과 권한과 노출 필드가 다르다. 예를 들어 캠페인은
점주가 `/v1/owner/campaigns` 로 등록하고 관리자가 `/v1/admin/campaigns` 로 조회한다.
리소스는 명사 복수형이고 계층을 경로로 드러낸다.

```
GET    /v1/stores/{storeId}                          단건
GET    /v1/stores                                    목록
POST   /v1/owner/campaigns                           생성
PATCH  /v1/owner/campaigns/{campaignId}              부분 수정
DELETE /v1/wishlist/{campaignId}                     삭제
```

표준 메서드로 표현할 수 없을 때만 콜론 표기의 커스텀 메서드를 쓴다. 상태 전이가 대표적이다.

```
POST /v1/owner/campaigns/{campaignId}:activate
POST /v1/owner/campaigns/{campaignId}:pause
POST /v1/owner/campaigns/{campaignId}:resume
POST /v1/admin/templates/{templateId}:publish
```

위 경로는 규약을 보이는 예시다. 확정 경로는 각 문서에 적는다.

### 인증

| 주체 | 로그인 수단 | Access Token | Refresh Token | 역할 |
|---|---|---|---|---|
| 관리자 | 자체 아이디와 비밀번호 | JWT 30분 | 1일 | `ADMIN`, `SUPER_ADMIN` |
| 점주 | 이메일과 비밀번호 | JWT 30분 | 14일 | `OWNER` |
| 사용자 | 카카오 OIDC (인가 코드) | JWT 30분 | 14일, 자동 로그인 미체크 시 세션 쿠키 | `USER` |

**토큰은 헤더가 아니라 쿠키로 오간다** (94행). 두 토큰 모두 `HttpOnly`, `SameSite=Strict` 쿠키로
내려가고, 클라이언트는 토큰 값을 읽거나 `Authorization` 헤더에 싣지 않는다. 응답 본문에도 토큰을 넣지 않는다.

```
Set-Cookie: accessToken=<JWT>; HttpOnly; SameSite=Strict; Path=/
Set-Cookie: refreshToken=<opaque>; HttpOnly; SameSite=Strict; Path=/
```

- **Refresh Token은 회전한다.** 재발급마다 새 토큰으로 바꾸고, 이미 바꾼 토큰이 다시 오면 그 계정의 세션을 전부 끊는다(64, 94행)
- **로그아웃은 Access Token도 막는다.** 로그아웃 시각을 기준 시각(cutoff)으로 저장해 그 전에 발급된 Access Token을 거부한다(7, 34, 94행)
- **권한은 역할로 판정한다.** 역할이 맞지 않으면 `403` 이다(94행). 기본값은 거부이고, 로그인 전에 열린 경로는 로그인, 토큰 재발급, 점주 회원가입, 카카오 인가 코드 교환뿐이다
- **점주는 상태로 한 번 더 막는다.** `ONBOARDING` 점주는 입점 등록 API만 쓸 수 있고, `ACTIVE` 가 된 뒤 나머지 점주 API가 열린다(32행)
- **로그인 실패는 사유를 구분하지 않는다.** 계정 없음, 비밀번호 불일치, 사용 불가 상태를 모두 같은 `401` 로 돌려준다(5, 32행)

### 응답 봉투

성공과 실패가 같은 모양이다. 클라이언트가 분기 전에 파싱을 끝낼 수 있다.

```json
{
  "code": "SUCCESS",
  "message": "요청이 성공적으로 처리되었습니다.",
  "data": { }
}
```

**성공 여부는 `code` 가 `SUCCESS` 인지로 판별한다.** 실패면 `data` 가 `null` 이고 `code` 와 `message` 가
`global.exception.ErrorCode` 에서 나온다. 코드는 `도메인-번호` 형식이다. 던지는 자리에서 문장을 지어내지 않는다.

```json
{
  "code": "COUPON-003",
  "message": "선착순 수량이 모두 소진되었습니다.",
  "data": null
}
```

### 상태 코드

| 코드 | 언제 |
|---|---|
| `200` | 조회, 수정 성공 |
| `201` | 생성 성공 |
| `202` | 접수만 하고 응답에 의존하지 않는 요청. 노출 이벤트 수집(99행) |
| `204` | 삭제 성공, 본문 없음 |
| `400` | 입력 형식이나 값이 잘못됨 |
| `401` | 인증이 없거나 유효하지 않음, 로그인 실패 |
| `403` | 인증은 됐으나 역할이나 상태가 맞지 않음 |
| `404` | 리소스가 없음 |
| `409` | 현재 상태에서 할 수 없는 요청 (중복, 상태 충돌). 예: 관리자 ID 중복(4행) |
| `422` | 형식은 맞으나 업무 규칙 위반. 예: 활성 캠페인이 있는 점주의 환불 요청(52행) |
| `429` | 요청 빈도 초과. 피드 조회는 사용자 ID 기준 분당 2회(67행) |

**권한이 없으면 존재 여부와 무관하게 `403` 을 낸다.** 권한은 있는데 없을 때만 `404` 다.
그렇지 않으면 응답 코드가 남의 가게나 캠페인의 존재를 알려주는 통로가 된다.

### 목록과 페이지네이션

```
GET /v1/stores?pageSize=20&pageToken=eyJ...&sort=DISTANCE
```

| 파라미터 | 뜻 |
|---|---|
| `pageSize` | 한 번에 받을 개수. 기본 20, 최대 100 |
| `pageToken` | 다음 페이지 커서. 비우면 처음부터 |
| `sort` | 정렬 키. 리소스마다 허용값이 다르다 |

```json
{
  "stores": [ ],
  "nextPageToken": "eyJ..."
}
```

**`nextPageToken` 이 비어 있으면 마지막 페이지다.** 전체 건수는 기본으로 주지 않는다(78행 페이지 커서).
커서 방식이라 페이지를 넘기는 동안 새 데이터가 들어와도 항목이 밀리거나 건너뛰지 않는다.

정렬 키는 **허용 목록으로 검증한다.** 클라이언트가 보낸 문자열을 쿼리에 붙이지 않는다.
가게 목록의 "활성 캠페인 보유 가게 상단"(72행)은 정렬 키가 아니라 서버가 항상 먼저 적용하는 규칙이다.

### 식별자

**응답에 내부 `BIGINT` 대리 키를 숫자로 그대로 내보낸다.** 외부 노출용 식별자는 아직 도입하지 않았다.
도입하면 이 명세의 경로 변수와 응답 필드가 함께 바뀐다.

| 식별자 | 형식 | 근거 |
|---|---|---|
| 대부분의 ID (`storeId`, `campaignId`, `memberId` 등) | 숫자 | `전체.sql` 공통 규칙 5 |
| `serveId` | UUIDv7, 36자 문자열 | 용어 정의 30행. DB에는 `BINARY(16)` |
| QR 토큰 | 문자열 | 85행 서명 토큰, 60초, 1회용 |

### 시각

**모든 시각은 Asia/Seoul 기준이다**(비기능 42행). 응답의 시각은 ISO 8601에 오프셋을 붙이고
(`2026-10-01T11:00:00+09:00`), 영업일처럼 날짜만 있는 값은 `2026-10-01` 로 보낸다.
영업일은 서버가 계산한다. 클라이언트가 보낸 날짜로 영업일을 정하지 않는다.

### 개인정보

- **탈퇴한 점주와 사용자는 개인정보를 마스킹한 뒤 목록에 표시한다**(10, 11행)
- **점주가 보는 발급과 사용 이력에서 사용자 식별 정보는 닉네임 일부만 보인다**(59행)
- **위치는 저장 위치 말고는 남기지 않는다.** 노출 로그와 접속 기록의 좌표는 소수점 3자리로 반올림한다(66, 67, 99행)
- 토큰은 쿠키로만 오가므로 응답 본문과 로그에 토큰 값을 남기지 않는다

### 멱등성

별도 헤더를 두지 않는다. **같은 요청이 두 번 와도 결과가 하나뿐이도록 업무 키로 막는다.**

| 요청 | 중복을 막는 키 | 근거 |
|---|---|---|
| 노출 이벤트 수집 | `(serveId, 요청 사용자)` UNIQUE | 99행 |
| 스와이프 찜과 패스 | 같은 사용자의 같은 `serveId` 는 최초 1건만 | 68행 |
| 선착순 쿠폰 발급 | `(eventId, 사용자)` UNIQUE. `eventId` 는 캠페인마다 하루 하나인 선착순 오픈 | 83행, 비기능 24행 |
| 결제 승인 콜백 | 결제 ID | 49행 |
| QR 사용 처리 | QR 토큰 1회용 | 85행 |
| 관심 가게 등록과 해제 | 이미 등록된 것을 다시 등록해도 성공 | 77행 |
| 전환 퍼널 수집 | `event_id` | 100행 |

같은 키로 다시 오면 새로 처리하지 않고, 이미 처리된 결과를 성공으로 돌려주거나 중복으로 거부한다.
어느 쪽인지는 각 문서에 적는다.

### 클라이언트가 응답을 기다리지 않는 요청

노출 이벤트(99행)와 화면 조회 퍼널 이벤트(map_view, wishlist_view, poster_open, 100행)는
화면을 벗어나는 순간에도 보내야 하므로 `keepalive` 옵션으로 전송하고 응답에 의존하지 않는다.
실패하면 1회 재시도하고 포기한다(비즈니스 규칙 8행).

## 아직 정해지지 않은 것

명세를 쓰면서 **요구사항에는 있으나 현재 스키마(`전체.sql`)에 근거가 없는 것**들이다.
API 를 확정하기 전에 결정이 필요하다.

| 항목 | 요구사항 | 현재 스키마 |
|---|---|---|
| 저장 위치 목록 | 93행(필수) "저장 위치 목록 표시 (별명, 주소)" | `member_profile` 이 회원과 1:1이라 위치를 하나만 담는다 |
| 관심 가게 | 77, 78행(권장), 이를 쓰는 80, 81행 알림 | 관심 가게 테이블이 없다 |
| 가게 추천 차단 | 71, 92행(권장) | 차단 목록 테이블이 없다. `feed_filter` 는 정렬과 카테고리만 담는다 |
| 영업신고증 업로드 | 38행(권장) 파일 메타데이터 저장 | 파일을 담을 테이블이나 컬럼이 없다 |
| 검수 기준 관리 | 29행(권장) 기준값 5종과 변경 이력 | 전용 테이블이 없다. `platform_setting` 키로 둘지 정해야 한다 |

결정되면 테이블을 더하는 마이그레이션과 함께 해당 문서에 절을 더한다.
