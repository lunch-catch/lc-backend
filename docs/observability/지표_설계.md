# 지표 설계

앱이 내보내는 지표를 어떤 이름과 꼬리표로 내보내기로 했는지, 그리고 그렇게 정한 까닭을 적는다.
받아서 모으고 보여 주는 쪽은 lc-infra 의 모니터링 설계가 갖는다.

| 내용 | 갖는 곳 |
|---|---|
| 앱이 내보내는 지표의 설계(이 문서) | `docs/observability/지표_설계.md` |
| 지표를 어디까지 해내야 하는지(시계열 수, 꼬리표 값의 종류, 수집 주기, 보존 기간) | [qa-observability-guideline.md](../software-quality/qa-observability-guideline.md) 2장 `OBS-4-*` |
| 트레이스와 프로파일 | [트레이싱과_프로파일링_설계.md](./트레이싱과_프로파일링_설계.md) |
| 수집 구조, 보관, 대시보드, 기준 초과 판정 패널 | lc-infra 의 `docs/system-design/백엔드공통_모니터링_설계.md` |
| 경보 | lc-infra 의 `docs/system-design/백엔드공통_알람과알림_설계.md` |

## 1. 목적

지표는 원인을 좁히는 첫 단계다. 어느 종류(API, 릴레이, 워커, cron 작업, 의존성)가 기준을 넘었는지 지표가 먼저 알린다.
그 뒤에 트레이스와 프로파일로 내려간다. 내려가는 순서는 [트레이싱과_프로파일링_설계.md](./트레이싱과_프로파일링_설계.md) 1장이 갖는다.

앱은 Micrometer 로 지표를 만들고 액추에이터의 `/actuator/prometheus` 로 내보낸다. 액추에이터는 요청을 받는 포트와 나눠 `8081` 에서 뜬다.

## 2. 모든 지표에 붙는 꼬리표

`application.yml` 의 `management.metrics.tags` 가 모든 지표에 꼬리표 셋을 붙인다.

| 꼬리표 | 값 | 가르는 것 |
|---|---|---|
| `application` | `APP_NAME`. 없으면 `lunchcatch` | 서비스 |
| `instance` | `APP_INSTANCE_ID`. 없으면 `local` | 같은 서비스의 서버 여럿. 로컬 구성(lc-infra 의 `observability/local/compose.yaml`)은 `local` 을, 부하 시험 환경을 닮게 앱 서버와 배치 서버를 나눈 로컬 구성(`compose.lt-like.yaml`)은 배치 서버에 `local-batch` 를 준다 |
| `version` | `APP_VERSION`. 없으면 `local` | 배포한 판. 롤링 배포 중에 두 판이 섞인 구간을 가른다 |

## 3. 공통 지표

도메인과 상관없이 `global/config` 가 내는 지표다. 같은 것을 여러 곳에서 재면 이름을 하나로 두고 꼬리표로 나눈다.
그래서 대시보드는 쿼리 하나로 모두 그리고, 새 릴레이나 워커가 생겨도 대시보드를 고치지 않는다.

### 3.1 요청과 호출

| 지표 | 꼬리표 | 재는 것 | 클래스 |
|---|---|---|---|
| `http.server.requests.histogram` | `uri` | API 마다의 요청 시간. p99 를 계산하는 구간을 내보낸다. 구간의 상한은 60초다 | `HttpLatencyHistogramHandler` |
| `http.server.requests.target` | `uri`, `method`, `outcome`, `result` | 요청이 그 API 의 목표 안에 끝났는지(`within`, `over`). 목표는 6장의 `api` 값이다 | `HttpLatencyHistogramHandler` |
| `http.client.requests.histogram` | `client.name`, `uri` | 바깥 서비스를 부르는 호출의 시간. 구간의 상한은 30초다 | `HttpClientLatencyHistogramHandler` |
| `http.client.failures` | `client.name` | 바깥 호출의 실패 수. 5xx 와 응답 없음만 센다. 4xx 는 카드 거절 같은 업무상 거절에도 와서 세지 않는다 | `HttpClientLatencyHistogramHandler` |
| `aws.sdk.calls` | `service`, `operation`, `model`, `outcome` | AWS SDK 호출(Bedrock Runtime, S3, Rekognition)의 시간. LLM 은 모델마다 정상 시간이 크게 달라 모델로 나눈다 | `AwsSdkCallMetricsInterceptor` |
| `aws.sdk.failures` | `service` | AWS SDK 호출의 실패 수 | `AwsSdkCallMetricsInterceptor` |

요청 수와 상태값별 오류율은 Spring Boot 가 내는 `http.server.requests` 와 `http.client.requests` 가 갖는다. 위 지표는 그 지표에 없는 구간과 목표 판정만 더한다.

히스토그램의 기록에는 그때 처리하던 요청의 트레이스 ID 가 exemplar 로 붙는다(`ExemplarConfig`). 그래프의 점에서 그 트레이스로 넘어가는 길이다.
트레이싱 에이전트를 붙이지 않은 앱에서는 이 빈을 만들지 않아 지표가 그대로다.

### 3.2 뒤에서 처리하는 일

| 지표 | 꼬리표 | 재는 것 |
|---|---|---|
| `outbox.relay.backlog` | `relay` | 릴레이의 미발행 건수 |
| `outbox.relay.oldest.age` | `relay` | 지금 넘길 수 있는 미발행 가운데 가장 오래 기다린 건의 대기 시간 |
| `outbox.relay.abandoned` | `relay` | 상한만큼 실패해 넘기기를 포기한 건수. 0 보다 크면 사람이 보고 고친다 |
| `outbox.relay.publish.delay` | `relay` | 넘긴 순간에 잰, 그 건이 생긴 뒤 넘기기까지 걸린 시간. 품질 목표의 경계인 5초를 구간에 넣고 상한을 15분으로 둔다 |
| `async.worker.queue.size` | `worker` | 워커의 대기열에 쌓인 일 수 |
| `async.worker.oldest.age` | `worker` | 가장 오래 기다린 일의 대기 시간 |
| `async.worker.queue.capacity` | `worker` | 대기열의 크기 |
| `batch.job.duration` | `scheduler`, `outcome` | cron 작업의 실행 한 번에 걸린 시간 |
| `batch.job.last.success.timestamp` | `scheduler` | 마지막으로 성공한 시각 |
| `batch.job.running.since` | `scheduler` | 도는 동안 그 실행이 시작된 시각. 돌지 않으면 0 이다 |

릴레이와 워커의 지표는 `BacklogMetrics` 가, cron 작업의 지표는 `SchedulerLoggingAspect` 가 낸다.
꼬리표 값(`relay`, `worker`, `scheduler`)은 6장 기준값의 키와 같게 쓴다.

릴레이의 대기 시간은 지금 넘길 수 있는 건만으로 잰다. 다시 넘길 시각을 기다리는 건과 포기한 건을 넣으면 재시도 중인 건 하나로도 기준을 넘고, 포기한 건이 남아 대기 시간이 끝없이 자란다.
대기 시간은 긁을 때의 시각으로 센다. 릴레이가 멈춰 값을 갱신하지 않아도 대기 시간이 계속 늘어 멈춘 것이 드러난다.

### 3.3 런타임

| 지표 | 꼬리표 | 재는 것 | 클래스 |
|---|---|---|---|
| `tomcat.threads.queued` | `name` | 톰캣에서 작업 스레드를 기다리는 요청 수. 스레드가 모두 차면 사용률은 100% 에서 더 오르지 않아, 포화가 얼마나 심한지는 이 값으로만 보인다 | `TomcatQueuedRequestsMetrics` |
| `jvm.threads.kind` | `kind` | 플랫폼 스레드를 이름 끝의 숫자를 지운 종류로 묶은 수. 어느 종류가 언제부터 늘었는지를 지난 구간까지 본다 | `ThreadKindMetrics` |
| `hikaricp.connections.usage` | Boot 기본 | 커넥션을 빌려 돌려줄 때까지의 시간. 품질 문서 데이터 무결성의 두 기준(100ms, 1초)을 구간에 넣어 넘은 수를 근사 없이 센다 | `application.yml` 의 `management.metrics.distribution` |

## 4. 시계열 수를 막는 규칙

시계열 수는 꼬리표 값 조합의 곱으로 는다. 운영 Prometheus 가 감당하지 못하면 수집 전체가 멈춘다. 그래서 아래를 지킨다.

| 규칙 | 까닭 | 적용한 곳 |
|---|---|---|
| Boot 기본 지표에 구간을 켜지 않고 이름을 따로 둔다 | `http.server.requests` 에 구간을 켜면 상태값, 메서드, 예외의 조합마다 구간이 70개 남짓 붙어 시계열이 수만 개로 는다. 같은 이름에서 일부만 켜면 지표 종류가 섞여 수집 전체가 실패한다 | `http.server.requests.histogram`, `http.client.requests.histogram` |
| 구간을 단 지표에는 꼬리표를 최소로 단다 | 구간 수가 곱해지는 지표라서다 | 요청은 `uri` 하나, 바깥 호출은 `client.name` 과 `uri` |
| 값이 늘 수 있는 꼬리표에 상한을 둔다. 상한을 넘은 뒤 처음 보는 값은 받지 않고, 이미 받은 값은 계속 남긴다 | 엔드포인트나 스레드 이름이 늘어도 시계열이 상한 x 구간 수를 넘지 않게 한다 | API 200개, 바깥 호출 100개, 스레드 종류 50개 |
| ID, 이메일, URL 원문을 꼬리표에 넣지 않는다 | 값이 끝없이 는다. `uri` 는 경로 원문이 아니라 Spring 이 준 경로 틀이다 | 모든 지표 |
| 종류를 묶을 때 이름 중간의 숫자는 남긴다 | `http-nio-8080-exec` 와 `http-nio-8081-exec` 를 가른다 | `jvm.threads.kind` |

수치 기준(지표 하나당 시계열 수, 꼬리표 값의 종류)은 [qa-observability-guideline.md](../software-quality/qa-observability-guideline.md) 2장이 갖는다.

### 4.1 첫 건을 놓치지 않게 0 으로 미리 만든다

`increase()` 와 `rate()` 는 시계열의 첫 표본을 기준으로만 쓰고 증가분에 넣지 않는다. 실패가 처음 생길 때 1 로 시작하는 시계열은 그 첫 한 건이 빠진다.
그래서 실패 수와 실패한 실행의 타이머는 0 인 시점을 미리 둔다.

| 지표 | 0 으로 만드는 때 |
|---|---|
| `http.client.failures` | 기동 때 등록한 상대. 등록하지 않은 상대는 첫 호출 때 |
| `aws.sdk.failures` | 서비스의 첫 호출 때. 배포 뒤 그 서비스의 맨 첫 호출이 실패하면 그 한 건은 놓친다 |
| `batch.job.duration` 의 `failure` | 배치 서버의 기동 때 작업마다 |
| `outbox.relay.publish.delay` | 릴레이를 등록할 때 |

## 5. 도메인 지표

도메인의 업무 결과와 실패는 그 도메인이 직접 낸다. CPU 와 응답 시간이 정상이어도 핵심 기능이 실패하고 있을 수 있어서다.
도메인 지표는 그 도메인의 서비스나 `config` 에서 `MeterRegistry` 로 만든다. 지표가 무엇을 세는지는 그 지표를 쓰는 도메인 설계서가 적는다.

| 규칙 | 까닭 |
|---|---|
| 이름은 도메인 이름으로 시작한다 | 대시보드와 쿼리가 도메인마다 지표를 모아 찾는다 |
| 꼬리표 값은 정해진 목록(에러 코드, 결과 종류, 까닭 종류)에서만 온다 | 4장의 시계열 수를 지킨다 |

| 도메인 | 이름의 예 |
|---|---|
| 관리자 | `admin.login.failed`, `admin.login.rejected` |
| 광고 서빙 | `adserving_served_cards_total`, `adserving_impression_dropped_total`, `adserving_impression_dispatch_backlog` |
| 분석 | `analytics_aggregation_total`, `analytics_aggregation_step_seconds`, `analytics_funnel_event_total` |
| 정산 | `billing.payment.confirm`, `billing_deduct_batch_failed_total` |
| 캠페인 | `campaign_bedrock_bulkhead_rejected_total` |
| 쿠폰 | `coupon.issue.results` |

도메인이 지표를 더하는 순서(지표, 대시보드, 경보, 부하 시험 캡처)는 lc-infra 의 `docs/wiki/팀원-도메인-모니터링.md` 가 갖는다.

## 6. 기준 초과의 기준값

API, 릴레이, 워커, cron 작업이 처리 시간의 기준을 넘었는지 가르는 값이다. `application.yml` 의 `lunchcatch.observability.targets` 가 갖고 `OverrunThresholdProperties` 가 읽는다.

| 종류 | 기본값의 키 | 이름별 값의 키 | 이름별 값이 재는 것 |
|---|---|---|---|
| `api` | `api-default` | `"[메서드 경로]"` | API 의 p99 |
| `relay` | `relay-default` | `relay` 꼬리표 | 릴레이의 발행 지연 p99 |
| `worker` | `worker-default` | `worker` 꼬리표 | 가장 오래 기다린 일의 대기 시간 |
| `job` | `job-default` | `scheduler` 꼬리표(`클래스.메서드()`) | 실행 한 번이 끝나야 하는 시간. 도메인 설계서의 마감을 시작에서 잰 시간으로 옮긴다 |

종류마다 기본값이 있어야 한다. 이름별 값이 없는 것은 기본값으로 판정한다. 기본값이 빠지면 앱이 뜰 때 막는다. 기본값의 게이지가 이름 `default` 를 써서 이름별 키로 `default` 를 쓰지 못한다.

값의 원본은 도메인 설계서의 성능 목표와 품질 문서다. 이 설정은 그 사본이다. 원본을 바꾸면 이 설정도 같은 PR 에서 고친다.

앱은 이 값을 게이지 `overrun.threshold{kind, name}` 로 내보낸다(`OverrunThresholdMetrics`). Prometheus 에서는 `overrun_threshold_seconds` 다.
판정을 지표 쪽에 두지 않고 기준값을 지표로 내보내는 까닭은 기준이 API 와 작업마다 달라서다. 대시보드와 부하 시험의 판정은 쿼리 하나에서 이 게이지로 이름마다 다른 기준을 거른다.
`api` 의 값은 요청을 받을 때에도 쓴다. `http.server.requests.target` 이 이 값으로 `within` 과 `over` 를 가른다. 구간에는 목표 값이 없고 메서드도 없어 쿼리로는 API 마다의 목표로 세지 못해서다.

이 값을 함께 쓰는 곳이 둘 더 있다. 둘 다 lc-infra 에 있다. 값을 바꾸면 함께 본다.

| 쓰는 곳 | 쓰는 방식 |
|---|---|
| 판정 패널(개요, API, 백그라운드 작업, 앱 서버 자원, 부하 시험 대시보드) | 게이지로 이름마다의 기준을 걸러 넘은 것을 보인다 |
| `observability/alloy/tracing.alloy` | 같은 값으로 기준을 넘은 요청의 트레이스를 남긴다. 게이지를 읽지 않고 값을 옮겨 적어서, `api` 의 값을 바꾸면 이 파일도 고친다 |

## 7. 정할 것

| 항목 | 고를 길 | 정하는 데 필요한 것 |
|---|---|---|
| 도메인 지표의 이름 꼴 | 점으로 잇는 Micrometer 꼴(`billing.payment.confirm`) / 밑줄과 `_total` 을 직접 쓰는 Prometheus 꼴(`adserving_served_cards_total`) | 지금 두 꼴이 섞여 있다. Prometheus 에서는 둘 다 밑줄 꼴로 바뀌어 수집에는 문제가 없다. 하나로 맞추면 이미 있는 대시보드와 경보의 쿼리를 함께 고쳐야 한다 |
| 결과를 나누는 자리 | 꼬리표로 나눔(`coupon.issue.results{result}`, `analytics_aggregation_total{result}`) / 이름에 넣음(`billing_deduct_batch_failed_total`, `adserving_impression_dropped_total`) | 지금 두 방식이 섞여 있다. 꼬리표로 나누면 쿼리 하나로 결과마다의 비율을 낸다 |
