# 트레이싱과 프로파일링 설계

트레이싱과 프로파일링을 무엇에 쓰고, 무엇을 잡고, 어느 환경에서 어떻게 켜는지를 정한다.
범위는 로컬, 개발 서버, 부하 시험 환경이다. 운영은 이 문서의 범위가 아니다.

| 내용 | 갖는 곳 |
|---|---|
| 트레이싱과 프로파일링의 설계(이 문서) | `docs/observability/트레이싱과_프로파일링_설계.md` |
| 샘플링을 어디까지 해내야 하는지(판정 기준과 수치) | [qa-observability-guideline.md](../software-quality/qa-observability-guideline.md) 3장 `OBS-5-*` |
| 켜고 끄는 명령(`switch --tracing`, `--profile`) | [loadtest/README.md](../../loadtest/README.md) 의 프로파일링과 추적 절 |
| Alloy 의 테일 샘플링, Tempo, Pyroscope 의 설정 | lc-infra 의 `observability/` |

## 1. 목적

두 도구는 원인을 좁히는 단계가 다르다.

| 도구 | 답하는 질문 | 단위 |
|---|---|---|
| 트레이싱 | 어느 실행이, 어느 호출 단계에서 오래 걸렸나 | 요청이나 작업 실행 하나 |
| 프로파일링 | 그 단계 안의 어느 코드가 시간을 썼나. 계산했나 대기했나 | 구간 전체의 합계 |

원인은 이 순서로 좁힌다.

1. 지표 그래프에서 기준을 넘은 종류를 본다.
2. 트레이스에서 기준을 넘은 실행을 열고 오래 걸린 호출 단계를 찾는다.
3. 프로파일링의 wall 에서 그 단계의 어느 코드가 시간을 썼는지 본다. 스팬이 없는 코드와 대기도 보인다.
4. 프로파일링의 cpu 와 견준다. cpu 에서도 크면 계산이고, 작으면 대기다.

트레이싱은 계측을 끼운 지점만 본다. 그 사이의 코드는 프로파일링이 본다. 그래서 둘을 함께 둔다.

## 2. 트레이싱의 대상

| 대상 | 잡는 방식 |
|---|---|
| HTTP 요청 | 에이전트가 요청마다 맨 위 스팬을 만든다 |
| `@Scheduled` 작업 | 에이전트가 실행마다 맨 위 스팬을 만든다 |
| 요청 안에서 실행기(`ExecutorService`, `CompletableFuture`)에 넘긴 일 | 에이전트가 트레이스 문맥을 넘겨 원래 요청의 트레이스 아래에 붙인다. 스팬은 그 안의 계측 지점이 만든다 |
| 대기열을 꺼내 처리하는 워커 | 에이전트가 맨 위 스팬을 만들지 않아 트레이싱하지 않는다. 밀린 양은 지표로, 처리에 쓴 코드는 프로파일링으로 본다 |
| 외부 API 호출 | 에이전트가 HTTP 클라이언트 호출마다 스팬을 만든다 |

워커의 처리를 원래 요청과 잇는 일(대기열에 문맥을 담아 꺼낼 때 링크로 붙이는 일)은 코드를 고쳐야 한다. 이 문서는 정하지 않는다.

## 3. 스팬의 굵기

스팬은 원인을 좁히는 단계 하나에 하나를 둔다. 같은 일을 겹쳐 재는 층과, 많고 짧아 감싼 스팬으로 충분한 호출은 스팬으로 두지 않는다. 스팬을 만드는 일 자체가 요청마다 비용을 낸다(7장).

| 계측 | 둘지 | 이유 |
|---|---|---|
| 톰캣(HTTP 요청) | 둔다 | 트레이스의 뿌리다 |
| JDBC | 둔다 | DB 시간은 쿼리 단위로 봐야 한다 |
| 외부 HTTP 클라이언트 | 둔다 | 외부 호출은 따로 봐야 하는 단계다 |
| 스프링 스케줄링 | 둔다 | 작업 실행의 뿌리다 |
| 실행기 문맥 전파 | 둔다 | 스팬을 만들지 않고 트레이스를 잇는다 |
| Spring Data 저장소, Hibernate | 정할 것 | 쿼리 하나에 JDBC 와 함께 세 겹이 된다. JDBC 하나로 충분할 수 있다 |
| Lettuce(Valkey 명령) | 정할 것 | 명령마다 스팬이라 파이프라인의 명령 수만큼 생긴다. 끄면 Valkey 시간이 이름 없는 빈 구간이 된다 |

피드 요청 하나에 계측을 모두 두면 스팬이 34~47개 생겼다(2026-11-06 로컬). Lettuce 가 약 20개, Spring Data 와 Hibernate 와 JDBC 가 약 16개, 메서드 목록이 9개였다.

### 우리 코드의 메서드

우리 코드의 메서드에는 스팬을 만들지 않는다. 트레이스에서 I/O 스팬 사이의 이름 없는 빈 구간이 길면 그 구간의 코드는 프로파일링의 wall 로 본다.

| 고를 길 | 잃는 것 |
|---|---|
| 스팬을 만들지 않고 프로파일링으로 봄(고름) | 드물게 느린 요청 한 건의 원인이 프로파일링의 합계에 묻힌다. 워커의 처리가 트레이스로 남지 않는다 |
| 설정 목록(에이전트의 `OTEL_INSTRUMENTATION_METHODS_INCLUDE`) | 클래스와 메서드 이름을 손으로 맞춰야 하고, 이름이 바뀌면 조용히 어긋난다 |
| `@WithSpan` 애너테이션 | 빌드에 의존성이 더해지고 도메인 코드를 고친다 |

부하 시험의 기준 초과는 대개 한 건이 아니라 p99 전체가 밀리는 것이라 합계로 보는 프로파일링으로 충분하다고 봤다. 드물게 느린 한 건을 쫓아야 하면 그 단계에 `@WithSpan` 을 붙인다.

## 4. 트레이싱의 표본

표본은 두 단계에서 고른다.

| 단계 | 어디서 | 방식 | 고르는 것 |
|---|---|---|---|
| 1 | 앱(에이전트) | 헤드 샘플링. 요청이 시작될 때 고른다 | 스팬을 만들 요청 |
| 2 | Alloy | 테일 샘플링. 트레이스가 끝난 뒤 모든 스팬을 보고 고른다 | Tempo 에 남길 트레이스 |

앱이 고르지 않은 요청은 스팬이 없어 Alloy 가 남길 수 없다. 그래서 오류와 느린 요청을 빠짐없이 남기려면 앱은 모든 요청에 스팬을 만들어야 한다(`always_on`). 대신 앱이 그 비용을 낸다.

### Alloy 의 테일 샘플링

수치는 [qa-observability-guideline.md](../software-quality/qa-observability-guideline.md) 3장의 판정 기준을 따른다. 이 문서는 그 기준을 어떻게 적용하는지만 정한다.

| 판정 기준의 대상 | 적용 |
|---|---|
| 오류 응답 | 상태가 `ERROR` 인 트레이스 |
| 느린 요청 | HTTP 요청의 트레이스(맨 위 스팬에 `http.route` 가 있는 것) 가운데 전체가 **300ms** 를 넘은 것. API 목표 가운데 가장 낮은 값(피드)이라 어느 API 의 기준 초과도 놓치지 않는다. 목표가 500ms 인 API 는 300~500ms 도 남아 저장량이 조금 늘 뿐이다. `@Scheduled` 작업은 이 규칙에서 뺀다 |
| 핵심 거래 경로 | 실패하면 돈이나 데이터를 잃는 요청이다([qa-reliability-guideline.md](../software-quality/qa-reliability-guideline.md) 의 SLO 등급). 아래 목록의 경로다. 피드는 조회라 일반 조회다 |
| 일반 조회 | 위에 들지 않은 요청과 `@Scheduled` 작업 |

핵심 거래 경로는 아래와 같다. 모두 10% 남긴다. 경로는 `http.route` 의 값이고 정렬한 자리에 한 줄씩 더한다.

| 경로 | 도메인 |
|---|---|
| `POST /v1/admin/payments/{paymentId}:recheck` | 정산 |
| `POST /v1/admin/point-adjustments` | 정산 |
| `POST /v1/admin/refund-requests/{refundRequestId}:approve` | 정산 |
| `POST /v1/admin/refund-requests/{refundRequestId}:reject` | 정산 |
| `POST /v1/admin/settlement-mismatches/{mismatchId}:closeWithoutAdjustment` | 정산 |
| `POST /v1/impressions` | 광고 서빙 |
| `POST /v1/owner/payments` | 정산 |
| `POST /v1/owner/payments/{paymentId}:confirm` | 정산 |
| `POST /v1/owner/refund-requests` | 정산 |

`POST /v1/swipes`, `POST /v1/wishlist`, `POST /v1/events` 가 핵심 거래 경로에 드는지는 정할 것이다(8장).

지연 기준은 트레이스 전체(맨 위 스팬)의 시간을 본다. 그 안의 메서드 하나만 오래 걸린 경우는 이 규칙으로 남지 않는다.

`@Scheduled` 작업은 오류면 모두 남고 아니면 1% 만 남는다. 작업은 00:00 묶음처럼 오래 걸리는 것이 정상인 것이 많아, 요청의 300ms 를 걸면 정상인 실행이 모두 남는다. 작업의 기준 초과는 실행 시간 하나가 아니라 종류마다 정한 지표(밀린 양, `batch.job.duration`, 멈춰 끝나지 않는 실행은 `batch.job.running.since`)로 판정하고, 그 기준은 부하 시험의 기준 초과 기록(#1128)이 갖는다. 작업의 트레이스는 그 판정에 쓰지 않으므로 지연 규칙을 걸지 않는다. 기준을 넘은 실행도 오류가 아니면 1% 만 남는다.

## 5. 프로파일링

| 항목 | 정한 것 |
|---|---|
| 도구 | async-profiler. 앱을 다시 띄우지 않고 돌고 있는 앱에 붙인다 |
| 종류 | cpu(`itimer`, 10ms)와 wall(50ms). 둘을 한 기록(JFR)으로 함께 뜨고 나눠 보낸다. 같은 부하와 같은 시간에 뜬 둘을 견줘야 계산과 대기를 가를 수 있다 |
| 남기는 스택 | 우리 컨트롤러, `@Scheduled` 메서드, 우리 워커를 지나는 스택. 그 위의 프레임워크 프레임과 쉬는 스레드는 버린다 |
| 저장소 | Pyroscope |

wall 은 간격마다 스레드를 일부만 돌아가며 뜬다. 그래서 wall 의 합계를 cpu 의 합계와 바로 견주지 않고, 각 그래프 안의 비율로 본다.

## 6. 환경마다 켜는 방식

| 환경 | 트레이싱 | 프로파일링 |
|---|---|---|
| 로컬 | 정할 것. 요청이 적어 모든 요청을 남겨도 비용이 문제 되지 않는다 | 필요할 때 붙인다 |
| 개발 서버 | 정할 것. 지금은 받을 Tempo 가 없다 | 정할 것 |
| 부하 시험의 측정 회차 | 정할 것. 켜면 결과 수치가 틀어진다(7장). 계측을 줄여 다시 잰 비용이 비용 한도 안이면 켜고, 넘으면 끈다 | 정할 것. 비용이 보이지 않았다(7장) |
| 부하 시험의 진단 회차 | 켠다(`always_on`). 진단 회차의 응답 시간은 결과에 쓰지 않는다 | 켠다 |

## 7. 비용

### 잰 방법

비용은 같은 조건에서 끔과 켬을 견줘 잰다. 아래를 지키지 않으면 비용이 부풀거나 묻힌다.

- **회차마다 같은 상태에서 시작한다.** 회차가 남긴 기록(노출, 서빙, 원장, 이벤트)이 쌓이면 뒤 회차가 느려진다. 데이터를 저장해 두고 회차마다 되돌린다.
- **끔과 켬을 번갈아 여러 번 돌린다.** 시간에 따른 흔들림이 양쪽에 고르게 섞인다.
- **주기 작업이 유지 구간에 걸리지 않게 시작 시각을 맞춘다.**
- **응답 시간보다 앱 CPU 를 먼저 본다.** 응답 시간은 회차 하나가 튀면 크게 흔들린다.

### 잰 값(로컬)

부하 시험 환경을 흉내 낸 로컬 구성에서 쟀다(2026-11-06). 앱은 CPU 2개와 2GB, 배치는 따로, MySQL 은 CPU 2개와 1GB, Valkey 는 512MB 다. 앱 1대에 초당 피드 33건, 유지 5분, 설정마다 3회다.

| 설정 | 피드 평균 | 앱 CPU |
|---|---|---|
| 끔 | 8.9ms | 34.8% |
| 트레이싱, 앱에서 10% 만 고름 | 10.3ms | 40.2% |
| 트레이싱, 앱에서 1% 만 고름 | 11.3ms | 41.5% |
| 프로파일링 cpu + wall | 10.4ms | 35.2% |

- 트레이싱은 앱에서 고르는 비율을 10% 에서 1% 로 낮춰도 CPU 가 줄지 않았다. 계측 지점을 지나며 문맥을 만들고 넘기는 비용이 대부분이라고 본다. 그래서 비용은 비율보다 계측 범위(3장)로 줄인다.
- 프로파일링은 앱 CPU 가 끔과 같았다.
- 1% 는 다른 설정과 번갈아 돌리지 않고 몇 시간 뒤에 쟀다. 끔을 다시 재 확인해야 한다.

### 비용 한도

정할 것. 측정 회차에 켜 둘 수 있는 비용의 한도(예: 앱 CPU 몇 %p)를 정한다.

## 8. 정할 것

| 항목 | 고를 길 | 정하는 데 필요한 것 |
|---|---|---|
| Spring Data, Hibernate 계측 | 끈다(JDBC 만) / 둔다 | 끄고 잰 비용 |
| Lettuce 계측 | 끈다(빈 구간은 프로파일링으로 봄) / 둔다 | 끄고 잰 비용 |
| 측정 회차의 트레이싱 | 켠다 / 끈다 | 계측을 줄여 다시 잰 비용과 비용 한도 |
| 측정 회차의 프로파일링 | 켠다 / 진단 회차에만 | 부하 시험 환경(AWS)에서 잰 비용 |
| 로컬과 개발 서버의 트레이싱 | 늘 켬 / 필요할 때 | 개발 서버에 Tempo 를 둘지 |
| 비용 한도 | 앱 CPU 몇 %p | 팀의 판단 |
| 배치 서버의 트레이싱 | 진단 회차에 앱 서버와 함께 켬 / 켜지 않음 | 배치 서버에 에이전트가 붙는지 확인 |
| cron 배치의 기준 초과 트레이스 | 마감을 넘은 실행을 모두 남김 / 지금처럼 오류와 1% 만 | 도메인 설계서의 마감(#1131) |
| `POST /v1/swipes`, `POST /v1/wishlist`, `POST /v1/events` 의 표본 | 핵심 거래 경로(10%) / 일반 조회(1%) | 그 요청이 실패하면 돈이나 데이터를 잃는지(쿠폰 발급, 이벤트 유실) |
