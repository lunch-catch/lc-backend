## 1. 목적

로그는 실행 한 건에서 무슨 일이 있었는지를 남긴다. 지표가 기준을 넘은 종류를 알리고, 트레이스가 오래 걸린 단계를 짚으면, 로그가 그 실행의 경고와 오류를 보인다.
그래서 로그는 트레이스와 같은 `trace_id` 로 묶이고, 업무 코드가 따로 쓰지 않아도 요청과 작업마다 남는 장치를 둔다.

## 2. 공통 장치

모든 장치는 `global/logging` 패키지에 있다. 업무 코드가 이 장치가 남기는 내용을 다시 쓰지 않는 규칙(`LOG-1-01`)은 [가이드 1장](../code-convention/logging-project-guideline.md#1-공통-장치)이 갖는다.

| 층 | 클래스 | 하는 일 | 남기는 이벤트 |
|---|---|---|---|
| 요청 컨텍스트 | `MdcLoggingFilter` | 가장 먼저 실행된다. MDC 에 `trace_id`, `method`, `uri`, `clientIp` 를 넣고 요청이 끝나면 비운다. `trace_id` 는 에이전트가 연 트레이스가 있으면 그 ID, 없으면 형식에 맞는 요청 헤더 `X-Trace-Id`, 그것도 없으면 새로 만든 값이다. 응답 헤더 `X-Trace-Id` 로 돌려준다 | 없음 |
| 기술 로그 | `HttpBodyLoggingFilter` | 요청마다 접근 로그를 남기고 4xx, 5xx 는 가린 바디를 함께 남긴다 | `HTTP_ACCESS` |
| 기술 로그 | `ExternalApiLoggingExchangeFilter` | `WebClientConfig` 의 `WebClientCustomizer` 가 모든 `WebClient.Builder` 에 붙인다. 쿼리 문자열을 뺀 경로만 남긴다 | `EXTERNAL_API_CALL`, `EXTERNAL_API_CALL_FAILED` |
| 기술 로그 | `TraceIdExchangeFilter` | 나가는 호출에 `X-Trace-Id` 헤더를 싣는다. 지금은 받는 쪽이 이 헤더를 쓰지 않아 효과가 없다 | 없음 |
| 기술 로그 | `SchedulerLoggingAspect` | `@Scheduled` 메서드마다 시작, 끝, 실패를 남긴다. 마지막 성공 시각을 게이지 `batch.job.last.success.timestamp`(태그 `scheduler`)로, 도는 동안 그 실행이 시작된 시각을 게이지 `batch.job.running.since`(태그 `scheduler`. 돌지 않으면 0)로, 실행마다 걸린 시간을 타이머 `batch.job.duration`(태그 `scheduler`, `outcome`. 히스토그램)으로 내보낸다. 스케줄러를 켠 서버는 기동 때 `@Scheduled` 메서드마다 `outcome="failure"` 타이머를 0 으로 만들어 첫 실패도 `increase()` 에 잡힌다. 실행마다 `LogContext.open` 으로 새 `trace_id` 와 `job`(작업 이름)을 MDC 에 넣고 끝나면 되돌린다. 실패하면 애스펙트가 `SCHEDULER_FAILED` 에 스택까지 남기고 다시 던진다. 스케줄러의 오류 처리기(`SchedulingConfig.ALREADY_LOGGED`)는 같은 실패를 다시 남기지 않는다. 알림은 `SCHEDULER_FAILED` 에 건다 | `SCHEDULER_START`, `SCHEDULER_END`, `SCHEDULER_FAILED` |
| 기술 로그 | `AdminLoginService`·`AdminLoginAuditFilter`(`admin`) | 관리자 로그인 감사의 기록 대상과 처리 방식은 [관리자 API 설계의 로그인 절](../design/admin/admin-api-design.md#로그인)을 따른다 | `ADMIN_LOGIN_SUCCESS`, `ADMIN_LOGIN_FAILED`, `ADMIN_LOGIN_AUDIT_FAILED` |
| 이벤트 로그 | `GlobalExceptionHandler`(`global/exception`), `AuthExceptionHandler`(`auth/exception`) | 전역 예외 핸들러다 | 이벤트명 없음 |

## 3. 요청과 실행을 하나로 묶는 값

로그의 요청 ID 는 `trace_id` 하나다. 에이전트가 붙어 그 요청이나 실행의 트레이스가 열려 있으면 그 트레이스의 ID 를 쓰고(`AgentTrace`), 없으면 앱이 만든다.
키 이름과 값을 에이전트와 같게 두어, 에이전트가 있으면 로그의 `trace_id` 로 Grafana 에서 트레이스까지 넘어간다.

에이전트가 없을 때 `MdcLoggingFilter` 와 `LogContext` 가 만드는 값은 요청을 받을 때 만든 문자열 하나를 MDC 에 넣는 간이 구현이다.
OpenTelemetry 같은 분산 추적이 아니라서 span 의 부모 자식 관계도, HTTP, DB, Redis 호출의 자동
계측도 없다. 이 서비스는 모놀리스 하나이고 서비스 경계를 넘는 호출은 카카오와 토스뿐이다. 두
외부 서비스는 우리 헤더를 이어받지 않는다. 그래서 그때의 `trace_id` 는 한 프로세스 안에서 요청 한 건의
로그를 묶는 데 쓰인다. 그것만으로도 접근 로그와 이벤트 로그를 잇고, 업무 식별자가 정해지기 전의
로그까지 묶는다.

`TraceIdExchangeFilter` 는 나가는 호출에 `X-Trace-Id` 를 싣지만 지금은 받는 쪽이 없어 효과가 없다.
우리가 만든 다른 서비스를 호출하게 될 때 바로 쓰려고 미리 둔 것이고, 비용은 거의 없다. 여러 서비스에
걸친 지연 분석이 필요해지면 이 필터를 걷어 내고 OpenTelemetry 로 옮긴다.

MDC 는 스레드에 붙지만 Reactor `Context` 는 구독에 붙는다. Reactor 는 실행 스레드를 고정하지 않으므로
스케줄러를 바꾸면 MDC 가 자동으로 따라가지 않는다.[R4][R5] 1판은 "외부 클라이언트를 `.block()` 으로
동기 호출하는 동안은 스레드가 바뀌지 않아 문제가 없다" 고 적었는데 틀린 설명이다. `.block()` 은 호출한
스레드가 결과를 기다릴 뿐이다. `ExternalApiLoggingExchangeFilterTest` 로 확인한 결과 `doOnNext` 와
`doOnError` 는 응답 Publisher 가 신호를 보낸 스레드에서 실행됐다. 요청 스레드에서 신호를 보내면 MDC 가
남았고 다른 스레드에서 보내면 `trace_id` 가 빠졌다. 실제 WebClient 요청의 콜백이 항상 Reactor Netty
이벤트 루프에서 돈다고 단정하지 않는다. 이 저장소에는 Reactor 컨텍스트와 MDC 를 잇는 장치가 없다.

에이전트도 스팬이 열린 스레드의 로그에 `trace_id` 를 넣는다. 앱이 같은 키에 같은 값을 넣으므로 두 값이 갈리지 않는다.
전에는 앱이 `traceId` 를 따로 만들어, 에이전트를 붙인 환경의 요청 로그에 서로 이어지지 않는 두 값이 함께 찍혔다.
언제 에이전트를 붙이고 무엇을 트레이싱하는지는
[트레이싱과 프로파일링 설계](./트레이싱과_프로파일링_설계.md) 가 갖는다.

Micrometer Tracing 의 `management.tracing.sampling.probability` 는 `application.yml` 에 두지 않는다.
이 저장소에는 Micrometer Tracing 의존성이 없어 그 설정은 어느 환경에서도 효과가 없다. 두면 트레이싱이
켜져 있다고 오해하게 만든다. Micrometer Tracing 을 들이면 현재 스팬의 `traceId` 와 `spanId` 를 MDC 에
잇는다.[R15] 이 저장소는 에이전트가 같은 일을 하므로 들이지 않는다. 트레이싱의 표본은 에이전트의 샘플러
설정과 Alloy 의 테일 샘플링이 정한다.

## 4. 로그의 모양과 설정

`src/main/resources/logback-spring.xml` 이 갖는다.

| 프로필 | 항목 | 값 |
|---|---|---|
| `local` (기본 프로필) | 출력 | 콘솔 텍스트. 패턴에 MDC 값과 `%F:%line` 을 넣는다 |
| `local` | 루트 레벨 | DEBUG |
| `prod` | 인코더 | `LogstashEncoder`. MDC 키 `trace_id`, `method`, `uri`, `clientIp`, `job` 을 필드로 넣고 운영 필드를 더한다 |
| `prod` | 스택 | `ShortenedThrowableConverter`. 예외당 30 프레임, 최대 8192자, 원인 먼저, 프레임워크 패키지 일부 제외 |
| `prod` | appender | `AsyncAppender`. `queueSize=8192`, `discardingThreshold=0`, `neverBlock=true`, `includeCallerData=false`. `maxFlushTime` 은 지정하지 않아 기본 1초다 |
| `prod` | 운영 필드 | `service=lunchcatch`, `version`(배포가 넘기는 `APP_VERSION`. 없으면 `local`) |
| `prod` | 루트 레벨 | INFO |

### 4.1 로컬 설정의 모양

`%F` 는 호출 위치 정보를 계산하므로 빠른 변환자가 아니다.[R2] 로컬은 트래픽이 적고 동기 로깅이라 부담이
작다. IntelliJ 콘솔은 `ClassName.java:42` 모양을 클릭하면 그 줄로 가는 링크로 만든다. 그래서 로컬에서만
켠다. `%logger{36}` 바로 뒤에 괄호로 시작하는 글자를 붙이면 Logback 의 패턴 파서가 그 괄호를 다른
변환자의 시작으로 읽는다. Logback 문서도 리터럴 괄호를 이스케이프하도록 정한다.[R2]
`LogbackPatternTest` 는 이스케이프하지 않으면 뒤의 메시지가 출력되지 않고 이스케이프하면 출력되는 것을
현재 Logback 버전에서 확인한다. 지금 패턴은 괄호 없이 쓴다.

`logback-spring.xml` 주석은 `%X{trace_id:-}` 같은 기본값 문법이 Log4j2 전용이라 Logback 이 지원하지 않는다고
적는다. 1판도 이 설명을 옮겨 적었는데 틀렸다. Logback 의 `%X{key:-default}` 는 값이 없을 때 기본값을
출력한다.[R2] `LogbackPatternTest` 도 같은 동작을 확인한다. 지금 패턴은 기본값 없이 `%X{trace_id}` 를
써서 값이 없으면 빈 문자열이 찍힌다. 이 선택은 그대로 두고 주석만 고친다.

로컬의 루트 레벨이 DEBUG 인 이유는 접근 로그 필터가 정상 응답의 바디를 DEBUG 에서만 남기기 때문이다.
서드파티까지 DEBUG 라 기동 로그가 길다. 줄이려면 시끄러운 로거만 따로 올린다.

### 4.2 운영 스택 설정의 값

스택이 길게 쏟아지는 것을 막으려고 예외당 30 프레임, 최대 8192자로 자르고 클래스 이름을 36자로
줄인다. 원인을 먼저 보이게 하고 설정한 정규식과 연속해서 일치하는 프레임을 줄인다.[R3] 이 변환기는
예외 메시지를 그대로 출력하고 메시지 마스킹 기능을 제공하지 않는다.[R3] 현재 제외한 패키지가 진단에
필요한 프레임까지 숨기는지는 실제 스택을 보고 조정한다.

## 5. 버리는 쪽을 고른 appender

공통 규칙 `LOG-8-02` 의 이 저장소 사정이다.

2026-08-30 부하 시험에서 선착순 쿠폰의 혼잡 응답 24,000건이 몰렸다. 로그 큐가 차자 요청 스레드가
큐에 자리가 날 때까지 기다렸다. 스레드가 묶이니 새 연결을 받지 못했고, 로드 밸런서가 연결 오류
11,590건과 504 응답 13,374건을 냈다. 혼잡이 5,134건이던 회차에는 연결 오류가 0건이었다.

그래서 `neverBlock=true` 로 맞바꿈을 뒤집었다. 로그를 잃지 않으려고 느려지던 것을, 느려지지 않으려고
로그를 버리는 쪽으로 바꿨다. Logback 은 이 설정에서 큐가 차면 이벤트를 버리고 호출자를 막지 않는다.
`discardingThreshold=0` 은 큐가 차기 전에 INFO 이하를 미리 버리지 않게 한다.[R1] `queueSize` 는
1024 에서 8192 로 올렸다. 버리는 것은 마지막 수단이고, 순간의 폭주는 큐가 흡수하는 편이 낫다는
프로젝트 판단이다. `coupon_issue_results_total` 을 등록하거나 증가시키는 코드는 현재 저장소에 없으므로
이 지표가 버린 로그를 센다고 보지 않는다.

종료할 때 큐를 비우는 시간(`maxFlushTime`)은 지정하지 않아 기본 1초다.[R17] 큐 8192건이 차 있는 상태에서
배포가 인스턴스를 내리면 이 시간 안에 내보내지 못한 로그는 버려진다.[R1] graceful shutdown 의
30초와 Logback 종료 순서가 같은 시간 예산을 공유한다고 보장할 근거는 없다. 실제 종료 순서를 측정한 뒤
값을 정한다. 이 사건과 같은 이유로 버려지면 안 되는 감사 기록은 로그가 아니라 `AuditLogWriter` 로
감사 저장소에 쓴다(공통 규칙 `LOG-8-11`).

## 6. 스케줄러 게이지

마지막 성공 시각 게이지는 작업이 처음 실행된 시각으로 초기화한다. 계속 실패하는 작업도 잡기
위해서다. 성공할 때만 값이 갱신되므로 실패만 반복하면 값이 그대로 낡아 알람이 울린다. 0 으로 두면
기동 직후부터 낡은 값으로 보여 첫 실행 전에 알람이 울린다. 대신 이 방식에는 빈틈이 둘 있다. 게이지는
첫 실행에서 생기므로 재기동 뒤 작업이 한 번도 돌지 않으면 시계열이 없다. 재기동할 때마다 값이 그 시각으로
다시 시작하므로, 재기동이 잦으면 계속 실패하는 작업도 낡아 보이지 않는다. 앞의 것은 시계열이 없을 때
결과를 만드는 `absent()` 조건으로 막는다.[R9] 뒤의 것은 실패 이벤트(`SCHEDULER_FAILED`)의 건수 알림이
함께 잡는다. 실제 경보 선택자가 배치 서버만 고르는지는 확인하지 않았다.

태그 이름은 `job` 이 아니라 `scheduler` 다. Prometheus 가 대상을 스크랩할 때 `job` 라벨을 자동으로
붙이고 그 값은 설정한 스크랩 잡 이름이다.[R10] 애플리케이션이 같은 이름의 태그를 내보내면
`honor_labels` 가 기본값인 `false` 일 때 애플리케이션의 라벨은 `exported_job` 으로 바뀐다.[R11]
이 경우 `job` 을 기준으로 작성한 알람은 스케줄러 이름이 아니라 스크랩 잡 이름을 본다. `lc-infra` 의
실제 `honor_labels` 값은 확인하지 않았다.

## 7. 액추에이터 포트

로거 레벨을 런타임에 바꾸는 수단(`LOG-5-07`)은 액추에이터의 `loggers` 엔드포인트다. 액추에이터는
`management.server.port=8081` 로 분리되어 있다.

8080 에는 `/actuator` 경로가 아예 없어서 바깥에서 막는 규칙이 필요 없다. `loggers`
엔드포인트를 노출하더라도 8081 이 외부에 열려 있지 않으면 바깥에서 로그 레벨을 바꿀 수 없다.

## 8. 보존 기간

로그의 보존 기간(`LOG-8-10`)은 아래와 같다. 기간을 정하는 설정은 lc-infra 가 갖는다.

| 대상 | 보존 기간 |
|---|---|
| 운영 로그(Loki) | 30일 |
| 개발 서버 로그(CloudWatch) | 30일 |
| 감사 기록(`AuditLogWriter` 가 DB 에 쓰는 것) | 최소 1년. 지우는 작업을 두지 않는다 |

운영 로그는 운영 Grafana 에서 본다. OIDC 로 로그인하고 허용한 대역에서 들어온 팀원은 모두 Viewer 로 가입되어 로그를 볼 수 있다.
