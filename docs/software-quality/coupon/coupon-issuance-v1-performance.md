# MySQL 쿠폰 발급 v1 성능 측정

2026-10-15에 `feat/284-coupon-issuance`의 커밋 전 변경 사항을 측정했다. 기준 develop은 `d0a49c882f04f083e3a6b70f4e4fa0d1c40dd1a4`다.
발급 구조와 임시 광고 서빙 처리는 [쿠폰 발급 설계](../../design/coupon/coupon-api-design.md#mysql-쿠폰-발급-v1)를 따른다.
성능 합격 기준은 [발급 성능 목표](../../design/coupon/coupon-api-design.md#발급-성능-목표)가 소유한다.

이 문서는 당시의 측정 기록이다. 측정에 사용한 부하 테스트와 전용 Gradle 작업은 제거했다.
측정 당시의 트랜잭션 제한과 혼잡 오류 변환도 현재 구현에서는 제거했다.

## 실행 환경과 범위

| 항목 | 측정 환경 |
| --- | --- |
| 실행 호스트 | macOS aarch64이며 JVM이 CPU 8개를 인식했다. |
| Java | Temurin 21.0.11을 사용했다. |
| DB | Docker의 MySQL 8.4.10을 사용했다. |
| Docker 자원 | CPU 4개와 메모리 약 1.93 GiB를 할당했다. |
| 애플리케이션 | Spring Boot HTTP 서버 한 대와 Hikari 커넥션 최대 8개를 사용했다. |
| HTTP 처리 | Tomcat 작업 스레드의 최대 수는 공통 설정인 200개를 사용했다. |
| 부하 발생기 | 서버와 같은 JVM에서 Java HttpClient와 가상 스레드를 사용했다. |
| 시험 JVM | 최대 힙 2 GiB를 사용하고 JaCoCo를 껐다. |
| 인증과 회원 조회 | 실제 JWT 쿠키와 회원 contract 구현을 사용했다. |
| 광고 서빙 | 찜 여부는 true이며 후보 소진 반영은 TODO로 남겼다. |
| 발급 시간 | 부하 시험에서만 00:00 이상 23:59:59 미만으로 넓혔다. |

이 결과는 로컬 환경의 기준값이다. 운영 DB의 디스크·CPU와 네트워크 지연은 재현하지 않았다.
부하 발생기와 서버가 CPU와 힙을 공유하므로 운영 용량을 확정하는 결과로 사용할 수 없다.
다중 서버는 측정하지 않았다. 광고 서빙 연동 비용도 포함하지 않았다.

## 측정 당시의 실행 방식

측정 당시에는 Java 21과 전용 Gradle 작업으로 부하 테스트를 실행했다.
전용 작업은 MySQL과 Valkey 컨테이너를 준비했다. Redis 순번 발급기는 사용하지 않았다.
시험은 별도 테스트 DB의 쿠폰 데이터와 `coupon-benchmark-` 접두사를 가진 시험 회원을 준비하고 종료 시 제거했다.
일반 `./gradlew check`에서는 부하 시험을 실행하지 않았다.

결과는 `build/reports/coupon-issuance/summary.csv`와 시나리오별 CSV에 남는다. `environment.txt`는 실행 환경을 기록한다.
CSV의 시간은 부하 발생기가 예정한 요청 시각부터 응답 완료까지 측정한다. 스케줄러가 늦게 전송한 시간도 포함한다.
완료 RPS와 성공 RPS는 마지막 응답까지 기다린 전체 시간으로 나눈다. 201 응답만의 P95와 P99도 따로 기록한다.

워밍업 후 단일 이벤트에 100·500·1,000 RPS를 각각 10초간 시도한다.
단일 이벤트와 20개 이벤트에 각각 첫 10초 2,500 RPS, 다음 20초 1,250 RPS로 50,000건을 시도한다.
이 두 시나리오는 요청 수만큼 재고를 준비하고 회원마다 한 번만 요청한다. 소진 오류가 빠르게 반환되어 발급 성능을 좋아 보이게 하지 않도록 구성했다.
별도로 재고 100개에 5,000건을 보내는 소진 시나리오를 측정한다.

부하 발생기는 응답이 느려져도 예정한 요청 속도를 낮추지 않는다. 동시에 대기하는 요청은 2,048개로 제한한다.
상한을 넘은 요청은 HTTP로 보내지 않고 `CLIENT_DROPPED`로 기록한다. 전송하지 못한 요청을 API 응답 건수나 성공 처리량에 포함하지 않는다.
클라이언트 드롭이 있는 시나리오는 요구한 전체 HTTP 부하를 전달하지 못했으므로 목표 부하의 합격 판정에 사용할 수 없다.
HTTP 응답 대기는 120초까지 허용했다. 서버 대기열이 길어졌다는 이유로 시험 클라이언트가 먼저 포기하여 늦은 커밋을 누락하지 않도록 했다.

## 정합성과 병목 판단

각 시나리오는 응답이 끝난 뒤 201 수와 회원 쿠폰 수, ISSUED 재고 수, 카운터 합계를 비교한다.
회원 쿠폰과 재고 코드의 연결, 이벤트의 일치, 이벤트·회원 중복 및 일일 한도 초과도 검사한다.
독립된 동시성 통합 테스트는 같은 회원의 중복 요청과 여러 이벤트 동시 요청, 삭제 후 재발급, 저장 실패 롤백과 시간 경계를 검증한다.

타이머의 이벤트 잠금 평균에는 쿼리 실행과 DB 왕복 시간이 포함된다. MySQL의 `Innodb_row_lock_waits`와 `Innodb_row_lock_time` 증가량도 함께 기록한다.
MySQL 잠금 시간은 동시에 기다린 트랜잭션들의 시간을 더한 값이므로 시나리오의 경과 시간보다 클 수 있다.
혼잡 응답 COUPON-008은 가용성 목표에서 HTTP 5xx로 계산한다. 의도한 오류 코드로 응답했다는 이유로 성공으로 보지 않는다.

전체 시나리오에서 100 RPS는 전부 전송하고 성공했으며 지연 목표도 만족했다. 500 RPS부터 HTTP 대기열과 DB 커넥션 대기 때문에 지연이 크게 증가했다.
단일 이벤트 피크의 이벤트 잠금 쿼리 평균은 75.23ms였다. 20개 이벤트 분산 피크는 1.50ms였다.
InnoDB 잠금 대기 합계는 단일 이벤트 피크 346,278ms와 분산 피크 4,387ms였다.
이벤트를 나누면 처리량이 높아진 결과와 함께 보면 한 이벤트를 잠그는 구조가 주요 병목임을 보여 준다. 잠금 쿼리 시간 전체를 순수 잠금 대기로 보지는 않는다.

현재 v1은 피크 성능 목표를 충족하지 못했다. 클라이언트 드롭이 많아 요구한 50,000건의 HTTP 유입 전체를 전달하지 못했으며 실제 전송한 요청의 지연도 목표를 초과했다.
v2에서는 Redis 도입 여부와 함께 단일 이벤트의 직렬 DB 구간을 줄이는 방법을 검토해야 한다.
Redis로 대기 순번만 발급하고 같은 DB 잠금을 그대로 유지하면 최종 발급 처리량의 병목은 남는다.
다음 측정은 부하 발생기를 별도 호스트로 분리하고 충분한 동시 요청을 유지하여 HTTP 유입 전체를 전달해야 한다. 여러 서버와 실제 광고 서빙을 연결한 조건도 별도로 검증해야 한다.

## 기능 검증 결과

최종 `./gradlew check`는 테스트 2,095개 성공과 부하 시험 1개 제외로 통과했다. 부하 시험은 별도 태스크로 실행했다.
서비스 메서드 커버리지 게이트도 통과했다. 실제 MySQL 발급 통합 테스트 20개가 모두 통과했다.
전체 시험에서 Spring 컨텍스트를 캐시할 때 기본 512MiB 힙이 소진되어 일반 시험 JVM의 최대 힙을 1GiB로 설정했다.
시험 힙 변경은 애플리케이션 JVM이나 DB 설정을 바꾸지 않는다. 기능 검증 통과와 피크 성능 목표 미달은 별도로 판단한다.
