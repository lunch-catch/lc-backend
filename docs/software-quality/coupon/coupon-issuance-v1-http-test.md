# 쿠폰 발급 최소 기능의 HTTP 검증

2026-10-15에 API 연동을 위한 MySQL 쿠폰 발급 최소 기능을 실제 HTTP 요청으로 확인했다.
실행한 코드는 `feat/284-coupon-issuance`의 `5b30fe40`을 기준으로 한다. 이후 같은 브랜치의 주석 변경은 실행 동작을 바꾸지 않는다.
발급 구조는 [쿠폰 API 설계](../../design/coupon/coupon-api-design.md#mysql-쿠폰-발급-v1)를 따른다.

## 검증 범위

쿠폰 발급 제어에 Redis 순번 발급기와 분산 락, 대기열을 사용하지 않았다. 재고와 일일 횟수, 회원 쿠폰은 MySQL 트랜잭션으로 처리했다.
HTTP 요청의 성공과 오류 응답을 확인하고 작은 규모의 동시 요청에서 중복·초과 발급을 검사했다.
현재 구현으로 부하 테스트는 시행하지 않았다. 처리량과 P95·P99, 대규모 유입 및 다중 서버에서의 동작은 검증하지 않았다.

## 실행 조건

| 항목 | 조건 |
| --- | --- |
| 기존 서버 | 실행 중인 `localhost:8080`으로 요청 5건을 보냈다. 한국 시간 15시 이후라 기본 발급 시간인 11:00 이상 14:00 미만을 벗어났다. |
| 보완 서버 | 같은 실행 클래스패스의 임시 `localhost:18080`으로 요청 34건을 보냈다. 발급 시간을 시험용으로 00:00 이상 23:59:59 미만으로 넓혔다. |
| 데이터 | 로컬 MySQL에 회원 11명과 이벤트 16개, 재고 28개를 추가했다. 기존 행을 초기화하거나 덮어쓰지 않았다. |
| 인증 | 로컬 키로 생성한 MEMBER JWT를 실제 accessToken 쿠키에 담았다. 카카오 로그인과 Refresh Token 발급은 검증하지 않았다. |
| 회원 조회 | 회원과 프로필 조회는 실제 공개 contract의 구현을 사용했다. |
| 임시 처리 | 찜 검증은 생략했고 광고 후보 소진 갱신은 TODO 상태였다. |
| 실행 종료 | 임시 서버를 종료한 뒤 기존 서버의 health HTTP 200을 확인했다. 시험 데이터는 수동 확인을 위해 로컬 DB에 남겼다. |

기존 서버에서 발급 시간 이후 요청이 COUPON-002로 거절되는 것을 확인했다. 정상 발급의 201 응답은 발급 시간을 넓힌 보완 서버에서 확인했다.
이 결과를 기본 설정의 기존 서버에서 정상 발급까지 성공한 결과로 해석하지 않는다.

## HTTP 결과

실제 HTTP 39건 모두 기대한 상태 코드와 응답을 반환했다. 정상 발급 12건의 회원 쿠폰 ID와 발급 시각은 DB의 ID와 created_at에 일치했다.

| 확인 항목 | 결과 |
| --- | --- |
| 정상 발급 | 201과 회원 쿠폰 ID, 한국 시간의 발급 시각을 반환했다. |
| 인증과 입력 오류 | 쿠키가 없으면 401 AUTH-005, 필수값이 없으면 400 COMMON-002, 소수 ID이면 400 COMMON-003을 반환했다. |
| 없는 이벤트 | 404 COUPON-001을 반환했다. |
| 발급할 수 없는 이벤트 | 중지 상태와 어제·내일 영업일, 기본 발급 시간 이후 요청에 409 COUPON-002를 반환했다. |
| 정지된 회원 | 403 COUPON-003을 반환했다. |
| 중복 발급과 재고 소진 | 각각 409 COUPON-005와 COUPON-006을 반환했다. |
| 일일 한도 | 같은 회원의 네 번째 발급을 409 COUPON-007로 거절했다. |
| 삭제 후 발급 | 삭제한 이벤트의 재발급은 COUPON-005로 거절했고 다른 이벤트에서는 발급을 허용했다. |
| 연관 API | 일일 한도 조회는 200, 발급 쿠폰 삭제는 204를 반환했다. |

## 작은 규모의 동시 요청

| 조건 | 결과 |
| --- | --- |
| 같은 회원이 같은 이벤트에 10건을 동시에 요청했다. | 1건만 발급하고 나머지 9건은 COUPON-005로 거절했다. |
| 서로 다른 회원 5명이 재고 3개를 동시에 요청했다. | 3건만 발급하고 나머지 2건은 COUPON-006으로 거절했다. |
| 같은 회원이 서로 다른 이벤트 4개에 동시에 요청했다. | 3건만 발급하고 나머지 1건은 COUPON-007로 거절했다. |

이 세 조건에서 중복·초과 발급을 관찰하지 않았다. 이 결과는 대규모 동시성이나 처리 용량을 보장하지 않는다.

## DB 확인

| 항목 | 건수 |
| --- | ---: |
| 정상 발급 응답과 생성된 회원 쿠폰 | 각각 12 |
| 현재 ISSUED 회원 쿠폰 | 11 |
| REMOVED 회원 쿠폰 | 1 |
| ISSUED 재고 | 12 |
| 일일 발급 횟수 합계 | 11 |
| 이벤트·회원 중복 발급 | 0 |
| 재고 코드와 이벤트 연결 오류 | 0 |
| 일일 한도 초과와 카운터 불일치 | 0 |

삭제는 재고를 복구하지 않고 일일 횟수만 돌려주므로 ISSUED 재고 12개와 카운터 합계 11개는 정상이다.
재고 소진이나 회원 상태로 거절된 시험 회원은 카운터 행도 남지 않아 실패한 요청의 롤백을 확인했다.

첫 정상 발급 한 건의 Hibernate SQL 로그에서는 SELECT 6개와 쓰기 4개, 총 10개가 실행됐다.
회원 조회 contract 한 번이 회원과 프로필을 읽는 SELECT 두 개를 실행했다. 트랜잭션 제어와 더미 데이터 준비, 사후 DB 조회는 이 수에서 제외했다.

## 후속 검증

실제 찜 조회와 광고 후보 소진 갱신을 연결한 뒤 전체 발급 흐름을 다시 검증해야 한다.
Redis 도입과 성능 개선, 부하 테스트는 별도 작업에서 판단한다. 이번 최소 기능은 그 작업이 완료됐다고 주장하지 않는다.
