# 시나리오별 데이터 묶음

[시나리오 문서](README.md) 1,252개의 "필요한 데이터 상태" 를 DB 와 캐시에 넣을 **데이터 묶음** 으로 바꾼 것이다. 시나리오마다 어느 묶음으로 확인하는지는 [data-map.md](data-map.md) 에 있다. 시연 데이터 작업(#741)의 기본 세계는 이 문서의 "기본 세계" 묶음으로 만든다.

기준 코드: lc-backend develop `9f4ab523`, lc-frontend `3f3e056` (2026-10-22). 컬럼과 제약은 Flyway 마이그레이션과 맞췄다.

## 요약

| 항목 | 개수 |
|---|---|
| 묶음 | 268 (기본 세계 169, 실행으로 만듦 36, 확인 전용 63) |
| 시나리오 | 1,252 (묶음이 붙은 것 845, 데이터가 아닌 것 407) |

## 분류

| 분류 | 뜻 | 어떻게 넣나 |
|---|---|---|
| 기본 세계 | 정상 흐름과 화면 상태를 만드는 행 | #741 의 버전 마이그레이션(`V__`). 로컬, 개발, 운영 |
| 실행으로 만듦 | 로그인 세션, 리프레시 토큰, 속도 제한 키처럼 API 를 불러야 생기는 상태. DB 해시와 Valkey 키가 맞아야 해 행을 직접 넣으면 안 된다 | 확인할 때 API 를 불러 만든다 |
| 확인 전용 | 일부러 깨뜨린 데이터, 1만 건 같은 대량 데이터, 공유 서버에서 다른 작업을 깨뜨리는 상태(RUNNING 배치 등) | 공유 환경에 넣지 않는다. 로컬이나 부하 시험 DB 에서 그 시나리오를 볼 때만 넣고 지운다 |

**데이터가 아닌 시나리오**: `NONE:입력` 화면에서 입력해 만든다, `NONE:장애` 장애를 일으켜 본다, `NONE:시각` 시각이 되어야 한다, `NONE:외부` 카카오나 토스가 정한다, `NONE:없음` 데이터가 없어야 한다.

## 읽을 때

- 표의 번호(예: `store_id=2001`)는 묶음끼리의 관계를 보이려는 예시다. 실제 마이그레이션은 고정 번호 없이 고유 키(아이디, 이메일, 가게 이름)로 넣는다 (#741 1절)
- 날짜는 `baseDate` 기준이다. `D` 는 baseDate, `D-1` 은 그 전날이다. 시연은 baseDate = 2026-10-28
- 점주 한 명에 끝나지 않은 캠페인은 하나뿐이다(앱 규칙). 캠페인 상태마다 점주를 따로 둔다
- 쿠폰 이벤트는 DB 행만 넣으면 된다. Valkey 큐가 없으면 첫 발급 요청이 DB 기준으로 큐를 다시 만든다(`CouponSequenceRecoveryService`). AVAILABLE 과 ISSUED 의 합이 발급 수량과 같아야 한다
- "화면을 연 뒤 UPDATE" 가 적힌 묶음은 경합 시나리오다. 미리 넣지 않고 확인 중에 값을 바꾼다
